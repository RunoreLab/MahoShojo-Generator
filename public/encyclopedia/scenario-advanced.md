本页讲的是“情景卡进阶玩法（连续性）”：让同一个故事跨多次生成延续，而不是在 2000 字左右的一次性叙事里把一切讲完。

## 0) 先判断：你是否真的需要进阶

原作者建议先问自己两个问题：

1) 你想讲的故事能否在单次生成的篇幅限制内完整表达？  
2) 你想做的情景是否需要复杂的数值计算/逻辑判断？  

如果两者都“是”，很多时候用站内的情景生成器（箱庭物语）就够了（见：`/encyclopedia/scenario-generator`）。  
如果存在“否”，就可以考虑“继承式情景”（也就是：分集推进 + 数据继承）。

## 1) 核心思路：把“上一集回顾”写回卡里

做法是把“可复用的信息”写进角色卡的运行态字段：

- 历战记录：`arena_history.impact`（更像“日志/结算/存档”）
- 状态栏：`current_state.summary`（更像“当前状态快照/面板”）

只要你让模型 **在每次生成结束时按固定格式写入这些字段**，下一次生成就能把它们当作“上一集回顾”继续推进。

> 重要提醒：strict 天梯为了可重复性，会限制“读历战/读状态”。长线继承不是坏事，只是玩法目标不同。想了解口径：`/encyclopedia/guidance`。

## 2) 操作层：怎么改 JSON（以及怎么不把自己坑死）

### 2.1 两种编辑方式（选你顺手的）

- **档案馆编辑（推荐）**：站内直接编辑数据卡，省去格式化、编码、上传等步骤。
- **外部编辑器**：例如 PC 用 VSCode，移动端用 MT 文件管理器，或用网页格式化工具（如 `www.json.cn`）。

无论用哪种方式：**改之前先留一份备份**，遇到敏感词触发导致保存失败时更容易自救（参考：`/encyclopedia/sensitive-words`）。

### 2.2 JSON 只要记住这几条就够用

- JSON 是“数据”，不是“代码”：你只是在填表，不是在写程序。
- `{}` 是对象（装键值对），`[]` 是数组（装字符串或对象）。
- 键值对长这样：`"键": "值"`；两项之间要有英文逗号 `,`。
- 尽量用**英文半角标点**（`"`、`,`、`:`），避免全角符号和中英文混用造成解析失败。

## 3) 两种记录方式（建议按复杂度选）

### 方式 A：单字符串协议（结构简单时推荐）

当你只需要少量字段时，用分隔符把数据压在一行里更稳：

- 明确“必须遵守/强制输出”
- 指定写入位置（impact 或 summary）
- 指定需要记录的数据类型
- 给出固定格式（分隔符、字段名、示例）

原因是：这些字段本质是字符串，过度结构化反而更容易在叙事里跑偏。

**你在规则里至少要写清 4 个要素：**

1) **优先级声明**：例如“必须严格遵守/必须写入/不得省略”。  
2) **写入位置**：写到 `arena_history.impact` 还是 `current_state.summary`。  
3) **记录的数据类型**：你要哪些字段（HP/腐蚀/物品/时间线/好感度…）。  
4) **固定格式 + 示例**：给出分隔符、字段名、以及一条完整示例。

**推荐格式模板（示意）**

请尽量保持“一行到底”，用半角分隔符：

```
【节点:<名称>】<一句摘要>『HP:X/Y|腐蚀:<等级>(<表现>)|状态:<增益/减益>|物品:<清单>|关键行动:<标记>|备注:<环境/情报>』
```

你也可以直接给出一条“长得像最终产物”的示例，让模型更容易对齐：

```
节点「苍穹腐化」结束：成功击瞎风暴头颅，但被凋灵吐息波及。『HP:85/90|腐蚀:轻度(小臂皮肤出现紫斑)|状态:轻度震伤|物品:凋灵头颅碎片x1|关键行动:暂无|备注:确认攻击头颅可中断牵引光束』
```

> 小技巧：字段是字符串时，**不要要求“分段/小标题/多段落”**——你越结构化，模型越容易把“叙事文本”混进去。

### 方式 B：结构化记录（数据复杂时再用）

当你确实需要更多维度（例如好感度、时间线、地点、相关 NPC 等），可以设计“更结构化”的记录方式，但要付出更高的调试成本。

原作者提示：只要你写得足够清楚，甚至可以做到**不同角色记录不同结构**；也可以引入“全局数据卡”去记录与参演角色无关但又需要继承的数据。

一个常见做法是把状态栏当作“面板”，把你关心的变量用分隔符拼出来，例如：

```
[日期:2024-09-01] [时间:上午] [状态:正常输出的状态摘要] <|> [地点:教学楼天台] <|> [同场景:是] <|> [相关NPC:同桌/班主任] <|> 好感度:10→12 (δ+2；理由:日常闲聊+1，帮忙+1)
```

如果你准备做“时间线连续”，建议在规则里明确：

- 时间必须单调递增（不能上一集“上午”，下一集突然回到“清晨”）
- 当用户引导会导致时间不合理时，模型要优先保证时间线合理（用叙事去圆，而不是硬写崩）

### 全局数据卡（可选）

当你需要记录“全局变量”（例如关卡进度、地图变化、公共物品栏、剧情旗标），可以考虑额外带上一张“只负责记录的卡”。你需要在规则里明确：

- 它**不参与战斗/不抢戏**，只负责记录与结算
- 每次续写都要带上它，否则继承会断档

## 4) 状态栏 vs 历战记录：选哪一个？

原作者给的区别总结（很实用）：

- 写状态栏：更省体积、更省 token（省钱提速）
- 写历战记录：更像全过程存档，而且可在档案馆做回溯/删除（更适合长线）

推荐做法是：状态栏写“关键信息快照”，历战写“完整结算/日志”。

## 5) 常见失败原因：规则漏洞与模型选择

如果模型不按你的要求记录内容：

- 先检查是否选到了过弱/过于轻量的模型（不同 provider/模型差距很大；轻量模型更容易“忘格式/偷懒”）。  
  站内可在生成页面的「自定义 AI 能力提供商」里手动选择更稳的模型（例如避免 Lite，改用 Flash/Pro）。
- 再检查规则本身是否存在冲突/漏洞：这往往需要你逐字逐句读，结合具体战报找“模型为什么误解了你”。  
  经验上，最常见的坑是：同一段规则里既让它“自由发挥”，又要求“必须严格按格式输出”，或者给了两套互相不兼容的格式。

这件事很难靠一篇教程讲完，更多是反复试错与掌握“模型的阅读方式”。

> 补充：当继承内容越来越长时，模型也可能“挑着看”。如果你发现它开始忽略早期信息：把状态栏改成只存快照、把历战改成只存最近 N 个节点，通常能显著改善稳定性。

## 6) 让叙事在正确的地方停下

为了让继承数据可控，你需要明确告诉模型“什么时候结束/中断故事”。常见两类：

1) 叙事时长控制：例如“每次只推进约 25 分钟叙事时长”  
2) 叙事节点控制：例如“发生 X 情况时必须中断”  

停下的意义不是“让故事变短”，而是给下一次续写留一个**清晰的接力点**：停点附近务必写清楚“当前目标/未解悬念/下一步行动”。

## 7) 其他小技巧（可选）

- **文风过滤/风格锁定**：用规则要求固定叙事视角、用词、节奏（例如“偏日常”“偏悬疑”“偏热血”），通常能提升连载观感。
- **降敏与误伤控制**：你可以要求模型避免输出直白高风险措辞，改为更中性、更抽象的表达（参考：`/encyclopedia/shield-words`）。
- **作者/彩蛋字段**：部分玩家会在卡面写入类似 `Creator` 的字段，用来做作者标记或触发彩蛋；是否生效取决于具体情景与提示词设计，不保证通用。

## 8) 长线高阶情景卡设计攻略（从“设定”到“引擎”）

如果你想把情景卡做成“能跑几十回合”的长期玩法，建议换一个视角：  
它不只是“背景设定”，而是一份 **TRPG/文字冒险的规则引擎配置**——你在用自然语言把模型固定成「地下城主（DM）」+「存档管理员」。

一个长期可玩的情景，通常至少有四个模块（缺一个都容易跑偏）：

1) **核心循环（Game Loop）**：每回合玩家做什么、模型必须产出什么、何时结束/中断。  
2) **状态机（State Machine）**：哪些变量必须被“写回卡里”，让下一回合能继承。  
3) **世界法则（Guardrails）**：战力边界/风格禁则/逻辑约束，防止机械降神与设定塌方。  
4) **随机与模拟（RNG & Simulation）**：事件表/判定规则/概率，让体验更像“游戏”而不是“续写”。

### 典型案例拆解（看完再做五步法）

一些“特别稳、特别能跑长线”的情景卡，往往会把模型当成 **DM + 数据管理员**，并在卡里写出类似下面的设计点（思路比文字更重要）：

1) **用结构化写入对抗“金鱼记忆”**  
   - 不是指望模型“记住”，而是强制它**在每回合写回状态**：时间/地点/资源/人物关系/剧情旗标。  
   - 这样下一回合的上下文天然带着“存档”，不容易吃书。

2) **用“世界观锁”防止设定塌方**  
   - 强制战力映射：跨世界观时，把“概念级/唯心级”能力降维到题材能容纳的规则里（例如用“代价、限制条件、冷却、资源消耗”来约束）。  
   - 用容器限制全能角色：例如职阶/流派/职业的弱点要真实存在，避免“全能神”。

3) **用 RNG 把“续写”变成“模拟”**  
   - 事件表 + 骰子判定，让剧情分支更像游戏进程，而不是作者在脑补结局。  
   - 注意把“随机性”和“剧情合理性”分层：骰子决定结果等级，叙事负责把过程写得合理。

4) **用叙事护栏与禁令抵消底模偏好**  
   - 例如：禁止机械降神、允许失败与死亡、鼓励博弈与代价，而不是自动合家欢收束。  
   - 这类约束越短越硬越好；炫技式的“伪汇编/系统报错”会烧 token，通常只值得用在最关键的 1～3 条死命令上。

> 提醒：任何“系统格式/强制命令”的写法，都应该只用于强调你的玩法规则；不要用它尝试绕过平台/模型的安全策略与合规边界。

下面给一套可直接落地的五步法（按顺序做，稳定性会明显提高）。

### 第一步：先定“核心循环”（你希望每回合怎么推进）

把“自由聊”变成“可玩的回合制”，你至少要写清三件事：

- **回合单位**：每次生成推进多长（例如“约 25 分钟/半天/一天/一个节点”）。  
- **回合产物**：每回合必须输出哪些东西（正文/结算/接力点/可选行动）。  
- **结束条件**：达成胜利/失败/阶段目标时如何收束（以及何时必须停下，给下一回合接力）。

常见、好用的核心循环模板（示意）：

1) **日程循环**：晨/午/晚/夜 → 推进事件 → 结算状态 → 留 3～6 个可选行动。  
2) **关卡循环**：进入节点 → 解决冲突/获得线索 → 结算 → 指向下一节点（门槛/代价/风险）。

> 小技巧：时间线请要求“单调递增”。如果你不写这句话，模型很容易上一回合“傍晚”，下一回合突然回到“清晨”。

### 第二步：再做“记忆容器”（哪些信息必须写回卡里）

长期玩法最常见的崩坏点不是文笔，而是**状态不一致**：上一集说没蓝了，下一集又开大；上一集受伤，下一集满血复活。  
解决方式就是：把“必须继承的事实”做成**强制写入**。

在本站，最实用的两块写回位置是：

- **历战记录（更像存档/结算）**：`arena_history.impact`（概念字段；实际会落到 `entries[].impact`）  
- **状态栏（更像快照/面板）**：`current_state.summary`（可选：`current_state.fields`）

建议你先做“最小可运行状态机”：只存 6～10 个**必需变量**，跑稳了再加。

**推荐变量清单（按需选，别全塞）**

1) **全局状态**：天数/日期、当前地点、当前目标、正在进行的事件旗标（Active Events）。  
2) **角色状态**：HP/MP/理智/疲劳、关键增益/减益、关键道具/资源。  
3) **上一集回顾**：1～2 句即可（防止吃书）；重要信息写进 impact，不要混进正文里。

**写入模板（示例，建议你按自己的题材改字段名）**

```
【结算/写入要求｜必须遵守】
1) 在本回合结束时，必须写入：
   - current_state.summary：用一行“面板”格式写快照（时间/地点/HP/资源/关键旗标）。
   - arena_history.impact：用一段“结算”格式记录本回合的关键变化（发生了什么、变量怎么变）。
2) 时间必须单调递增；若用户引导导致时间矛盾，以时间线合理性优先，用叙事圆回来。
```

如果你准备做更结构化的状态栏，可以在规则里写明 `current_state.fields` 的字段表（示意）：

```json
[
  { "id": "day", "label": "天数", "type": "number", "value": 3 },
  { "id": "hp", "label": "生命值", "type": "string", "value": "85/90" },
  { "id": "location", "label": "地点", "type": "string", "value": "教学楼天台" }
]
```

> 注意：`fields` 是“表格化字段”，适合少量关键变量；想塞长文本，请用 `current_state.summary`，否则维护成本会暴涨。

### 第三步：写“世界法则”（让剧情不塌方、不机械降神）

世界法则的目标不是“限制创作”，而是防止两类常见跑偏：

1) **战力/逻辑失真**：突然开挂、凭空变物资、无代价复活、越级碾压。  
2) **风格漂移**：题材从悬疑变日常，从硬核变说教，从克系变合家欢。

你可以把规则分成两层写（更容易维护，也更少冲突）：

- **硬规则（必须/禁止）**：战力边界、资源守恒、死亡/代价、禁则。  
- **软规则（倾向/优先）**：文风、镜头语言、节奏、喜好，但不破坏硬规则。

**写法建议**

- 关键句尽量短：“必须/禁止/不得省略/优先级最高”。  
- 避免在同一段里同时写“自由发挥”+“必须严格按格式”，容易互相打架。  
- 如果你确实要用“看起来很系统”的格式（如 `MANDATORY_RULE:`），建议只用于强调**你自己的玩法规则**，不要试图用它去绕开平台/模型的安全策略与合规边界。

### 第四步：加入随机性（让体验像游戏，而不是固定剧本）

随机性不是为了“抽奖”，而是为了让玩家感到：世界在运转、风险可预期但结果不唯一。

两个最实用的做法：

1) **事件表**：列 10～30 个事件，按“常见/少见/稀有”分层。  
2) **骰子判定**：例如 D100，把区间映射到结果等级（成功/部分成功/失败/灾难）。

一个好用的 D100 区间模板（你可以直接改概率）：

- 01～50：常见事件（推动剧情，但代价小）  
- 51～80：少见事件（出现阻碍/诱惑/分支）  
- 81～95：稀有事件（关键线索/强敌/重大转折）  
- 96～100：极端事件（灾难/背叛/“代价换突破”）

> 小技巧：写清“骰子结论优先级”。你可以允许“弱者补正/难度曲线”，但要把它写成“软补正”，避免与 RNG 的硬结果冲突。

### 第五步：做“可维护性设计”（别把自己坑死）

高阶情景最怕两件事：**Token 爆炸**和**规则过度防御**。

- **Token 预算**：状态栏只存快照；历战只存最近 N 条；长文本设定放在“情景正文”，不要每回合重复粘贴。  
- **规则去重**：把最重要的 3～7 条硬规则反复强调，其余放到“附录/参考”。  
- **先跑小样**：用 3～5 回合做“稳定性验收”——先验格式、再验时间线、再验变量一致性，最后才追求文笔与花活。

如果你发现模型开始“挑着看”：

1) 缩短规则（删掉炫技格式与重复描述）  
2) 缩短状态（只留快照 + 最近 N 条历战）  
3) 把“必须遵守的格式”放到更靠前的位置，并用示例对齐  

## 9) v0.8.1：把章节规划直接写进情景卡

如果你现在做的是 **连续战报专用情景卡**，除了旧的“继承数据写回”思路，`v0.8.1` 还补上了一条更直接的能力：让情景卡自己声明“这条故事大概应该写几章”。

写法是给情景卡增加一个可选扩展字段：

```json
"_battle_story": {
  "total_chapters": 6,
  "plan_mode": "suggested"
}
```

字段含义：

- `total_chapters`：总章节数，当前范围是 `1-20`
- `plan_mode`：章节规划模式，只支持 `suggested` 或 `fixed`

两种模式的区别：

- **`suggested`**：情景卡只给一个默认值。用户在 `/arena` 新建连续战报时，仍可改成“不限制”或别的自定义章节数。
- **`fixed`**：情景卡强制固定章节数。用户在 `/arena` 新建连续战报时会被锁定为这个章节数，不能改。

它适合解决两类典型问题：

1) **固定节奏型情景**：例如“3 幕式校园日常”“6 阶段 BOSS 战”“固定回合数闯关”  
2) **弱引导型情景**：你希望用户默认按 4～6 章推进，但又不想完全锁死玩法

### 什么时候该用 `fixed`，什么时候该用 `suggested`？

推荐口径很简单：

- **大多数长线情景先用 `suggested`**：给一个默认章节数即可，保留用户改成更短、更长或不限制的自由。
- **只有当规则强依赖固定章数时再用 `fixed`**：例如每章对应一个明确阶段、每章必须触发一段固定机制、或者你在卡里写了“第 N 章必须发生什么”。

如果你只是“觉得 5 章比较好看”，那通常不值得上 `fixed`。

### 它和旧的“继承式长线设计”是什么关系？

章节规划解决的是 **章节节奏与收束**，不是状态继承本身。

也就是说：

- `_battle_story` 负责告诉 AI “这是第几章 / 总共几章 / 终章该不该收束”
- `arena_history` / `current_state` / `narrative history` 仍然负责“上一章到底发生了什么”

这两套能力最好配合用，而不是互相替代。

### 额外注意事项

- 当前只有 **主情景** 会被 `/arena` 的连续战报章节规划读取；辅助情景不会单独决定章节上限。
- 结构化情景卡与通用情景卡（Markdown）都支持 `_battle_story`。
- 这部分扩展字段不会参与原生签名；你可以在 `/character-manager` 里直接编辑，而不会因为改章节规划就立刻丢失原生性。
- 达到计划章节上限后，连续战报会禁用“继续续写”和“创建分支”的新章节追加，但仍允许“重写最后一章”。
