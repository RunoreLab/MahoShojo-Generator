# 引导 / 裁判事件 / 读写状态

> 作者：末伏之夜  
> 更新时间：2026-01-03

本页解释几类“会显著改变对局走向/可重复性”的开关与输入：它们会影响对战叙事，也会影响 **strict/free 排位是否计分**。

## 1) 故事方向引导（userGuidance）

你可以把它理解为“这一局玩家想让故事怎么走”的额外输入。  
它对叙事影响很大，但会降低“对局可比性”。

对于排位机制：只要出现用户引导，就 **不计严格排位分**（但可能仍计自由排位分）。

## 2) 角色引导（character_guidance）

某些生成链路允许你对某个参战角色附加“角色级别的额外引导”。  
它和 userGuidance 类似，会提高可控性，但也更容易让对局“不可比/可刷”。

对于排位机制：只要任一参战者存在非空的 `character_guidance`，就 **不计严格排位分**。

## 3) 随机判定事件（adjudication events）

判定事件通常用于：

- 强行加入“额外判定规则”
- 让裁判在关键节点按你设计的规则裁决

它属于强干预项。在 strict 梯子里默认视为“非严格对局”，因此不计严格排位分。

## 4) 读写运行态（历战/状态栏）

运行态字段通常指：

- 历战记录：`arena_history.impact`
- 状态栏：`current_state.summary`

如果一局对战读取了这些内容（读历战/读状态），就相当于引入了“上一局/长线剧情”的外部上下文，会削弱可重复性。

因此 strict 梯子要求：

- 不读历战（`read_arena_history = 0`）
- 不读状态栏（`read_current_state = 0`）

> 注意：这不代表“读写运行态不好”。它非常适合长线情景与剧情续写；只是它不属于严格排位分的统计口径。

## 5) strict/free 计分口径（实现版摘要）

为了减少争议，这里给出最直白的口径（以服务端实现为准）：

- free：对局完成 + 1v1 + 有可用的脱敏 IP（`ip_anonymized`）  
- strict：在 free 基础上额外要求：classic 模式 + 已登录 + 无 userGuidance + 无裁判事件 + 不读历战/状态 + 无角色引导
