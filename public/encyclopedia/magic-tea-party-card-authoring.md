# 魔法茶会：角色卡/情景卡进阶（协议与 mtp_notice）

> 作者：[末伏之夜](https://github.com/notuhao)  
> 更新时间：2026-01-18

魔法茶会是“长期对话”环境：对话历史会越来越长，还会叠加角色档案、世界书、情景设定、摘要与更新草案等信息。  
因此**同一张卡在竞技场能稳定生效，在茶会里可能会跑偏**——这不是你写卡不行，而是“上下文结构与优先级”变了。

本条目给出两类内容：

1) **写更适合茶会的角色卡/情景卡**（提高遵循度、减少跑偏）  
2) **特殊协议适配**：如何用 `mtp_notice` 做“可解析的提示/报错”，以及如何把“写入不可达字段”的要求映射到茶会的阶段机制

## 1) 茶会与竞技场的关键差异（写卡前先对齐预期）

- **竞技场**：单次生成、强结构化约束（战报 schema），情景模式会强强调“情景最高优先级”。
- **魔法茶会**：多轮对话 + 多目标输出（正文/选项/摘要/更新），情景设定在长上下文中更容易被稀释。

结论：在茶会里，**“规则要短、要硬、要反复出现”**；把关键规则埋进长段落，遵循度会明显下降。

## 2) 茶会的三阶段与“协议重映射”

魔法茶会的生成逻辑分为三个常见阶段（对应三类按钮/能力）：

1) **叙事阶段**：生成开场 / 继续生成 / 发送消息  
   - 输出：JSONL（旁白/对白/choices 可选）或 Markdown
   - 重点：推进剧情与对白

2) **选项阶段**：生成选项（或合并输出里的 choices）  
   - 输出：仅 1 行 JSON（`{"type":"choices","items":[...]}`）
   - 重点：给出“玩家可选行动”

3) **记录更新阶段**：生成更新草案 / 写入（或合并输出里的 updates）  
   - 输出：仅 JSON（更新草案），最终写入到角色卡的 `arena_history` / `current_state`
   - 重点：把“已发生的事实变化”写成可落库的记录

这意味着：很多“竞技场协议卡”的字段要求，在茶会里需要**语义映射**，而不是照抄字段名。

### 2.1 常见字段映射（茶会不会直接输出这些字段名）

如果你的卡里出现这些要求：

- `article.body`：把它当作**叙事正文要求**（比如天气、节奏、叙事禁词）
- `headline`：把它当作**会话标题/标题风格要求**（由茶会自动标题或你手动改标题解决）
- `article.analysis` / 正确游玩指引：把它当作**玩法提示**（推荐用 `notice(level=info)` 输出一次）
- `officialReport.winner`：把它当作**胜者判定**（写入草案阶段会有 `hasWinner/winner`）

如果卡里“强制要求输出这些字段”，建议改成：  
**叙事阶段不输出字段名；需要阻断时输出 `mtp_notice`；需要写入时改为写 impact/currentStateSummary。**

## 3) 如何写更适合茶会的情景卡

茶会更容易“情景跑偏”，建议你在情景卡里增加一个**短、硬、可重复**的“锚点块”：

- 时间/地点（必须固定）
- 核心事件（必须发生/必须推进到哪里）
- 禁则（绝对不能发生）
- 必出场要素（必须出现的 NPC/组织/道具/地点）

建议写法（示例风格）：

```
【情景锚点（请反复遵守）】
- 时间：……
- 地点：……
- 核心事件：……
- 禁则：……
```

另外，避免这些写法：

- 把关键禁则埋在 3000 字故事梗概的中间
- 规则只写“氛围感”，不写“必须/禁止”
- 同时堆 3 份互相打架的世界书/情景（茶会会被稀释到谁都不听）

## 4) 如何写更适合茶会的角色卡

角色卡建议把“稳定信息”前置成列表：

- **口吻**：常用句式、称呼习惯、说话节奏
- **能力边界**：能做什么、不能做什么（用“禁止/必须”写清楚）
- **禁忌与边界**：不接受的互动方向、敏感话题（减少误伤与跑偏）
- **关系与动机**：对其他角色的态度、短期目标

如果你希望茶会能“持续继承”：

- 把变化写进 `current_state.summary`（即时状态）  
- 把重大事件写进 `arena_history.entries[].impact`（历战影响）  
然后在茶会里开启“读取当前状态/读取历战记录”，并在需要时生成更新草案写入。

## 5) 特殊读写协议适配：把“写入要求”落到茶会能做的事

很多协议卡的诉求其实是两件事：

- **叙事要遵循**（风格、禁词、节奏、世界观）
- **记录要可落库**（状态栏/历战记录的格式）

在茶会里，推荐把“记录协议”明确写成这两条的格式模板：

- `current_state.summary` 的格式模板（例如固定栏目、必须包含时间轴）
- `arena_history.entries[].impact` 的格式模板（例如必须包含参与者/结果/关键变化）

然后在茶会中：

1) 叙事阶段只负责“演绎”，不强行输出字段名  
2) 记录更新阶段再按模板生成 `impact/currentStateSummary`，由写入逻辑落到卡片里

提示：茶会写入 `arena_history` 时会新增一条 `type="tea-party"` 的记录，并会移除 `signature`。

## 6) `mtp_notice`：自定义提示/报错（可解析、会从正文剥离）

`mtp_notice` 是魔法茶会支持的一种“提示信号”：你可以让模型输出一个**独立的 notice 行/块**，前端会把它从正文剥离出来，用醒目的提示框展示。

适用场景：

- 卡组缺少依赖（例如必须携带某张“妖精卡/全局数据卡”）
- 当前输出模式不符合协议（例如必须 JSONL、必须生成选项）
- 需要告知用户“此卡仅适用于竞技场/仅适用于写入阶段”

### 6.1 JSONL 模式：输出 notice 行（推荐）

输出一行 JSON（不要带代码块）：

```jsonl
{"type":"notice","level":"error","code":"missing_required_card","message":"未检测到播种者妖精，请检查是否放入“[妖精]兰兰”。","meta":{"stage":"narration"}}
```

规则建议：

- `level=error`：用于“硬错误”。为避免混淆，建议在 `error` 时**只输出 notice**，不要输出旁白/对白/choices。
- `level=warning|info`：用于提示，不阻断正文。
- `code`：用短英文/下划线，便于去重与检索。
- `meta`：可选；包含 `stage/roleId/scenarioId` 时，前端更容易对重复提示去重。

### 6.2 Markdown 模式：输出 `mtp_notice` 块

Markdown 模式下建议用围栏（内容为 JSON）：

```mtp_notice
{"type":"notice","level":"warning","code":"protocol_hint","message":"该情景包含强协议：建议切换到 JSONL 模式以获得稳定的选项/更新草案。"}
```

也支持“单行简写”（更适合模型临时输出）：

```
mtp_notice: level=warning, message="请注意，当前输入缺少角色卡"
```

## 7) 一个实用改写套路：把“竞技场协议卡”变成“茶会友好版”

当你遇到这种卡：

- 强制要求输出 `officialReport/headline/article.*`
- 强制要求“每轮都写状态栏/历战”

你可以按这个顺序改：

1) 把“headline/article.body”的要求改写成**叙事风格要求**（不提字段名）  
2) 把“写状态栏/历战”的要求改写成**impact/currentStateSummary 的模板要求**  
3) 把“缺依赖/缺关键输入”改写成 `mtp_notice(level=error)`  
4) 需要选项时，明确写“选项阶段必须输出 X 条 choices（保留编号/前缀）”
