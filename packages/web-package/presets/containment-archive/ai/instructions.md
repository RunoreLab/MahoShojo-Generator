# 存续院收容档案 · 生成说明

本包只有一个目标文件：`data/archive.json`。你（AI）只写这份**结构化档案内容**，不写 HTML、不写 CSS、不写脚本。页面版式、十二节骨架、等级徽章、密级黑条、模因闸门、打印规则与全部附录组件都由包本体提供。你还可以用可选的 `structure` 自己编排章节顺序、合并章节、改名和插入过渡段。

## 一、输出契约

1. 只输出一个 JSON 对象，不要 Markdown 围栏、不要前导说明、不要结尾总结。
2. 顶层必填只有 `identity`、`summary`、`containment`、`description`、`modules`；`monitoring`、`moduleData`、`structure` 都是可选增强。`identity` 只强制 `code` 与 `name`，其余身份字段缺失时运行时会补默认值。
3. `modules` 决定哪些模块可用；`structure` 决定它们怎么排、怎么合并、叫什么。**没有进入装配的模块不会出现，也不会留空标题或占位**。
4. 最后另起一行追加元数据注释块（见第八节）。它位于整份输出的最后一行，宿主会在校验前剥离。
5. 不得输出全角方括号占位符、`XXX`、`待填写`、`示例` 等占位内容；所有字段都必须是本场档案的真实记录。
6. 校验是“宽进”的：schema 只保证页面能渲染。多写字段会被忽略，少写字段会用默认值，单值/数组、字符串/数字、对象/数组都可以混用。**不要为了迎合 schema 删掉能支撑叙事的内容**。
7. 即使内容密度不够，也只会收到运行时提醒，不会生成失败。先保证产出一份可渲染的档案，再追求丰富度。

## 二、结构速查（先照最小版写）

### 最小可用 JSON

只写这五个顶层字段就能出页面；`modules` 可以是空数组。

```json
{
  "identity": { "code": "CX-P-2428", "name": "折翼的巡夜人" },
  "summary": "人形异常，夜间巡游旧城区，现处收容观察。",
  "containment": { "protocols": ["夜间关闭巡游路线并设双人值守。", "每周核对一次休谟读数。"] },
  "description": { "paras": ["外观与行为……", "异常机制……", "来历与代价……"] },
  "modules": []
}
```

需要附录时，把模块 id 放进 `modules`，并在 `moduleData` 里给对应数据：

```json
{
  "identity": { "code": "CX-P-2428", "name": "折翼的巡夜人" },
  "summary": "人形异常，夜间巡游旧城区，现处收容观察。",
  "containment": { "protocols": ["夜间关闭巡游路线并设双人值守。"] },
  "description": { "paras": ["外观与行为……", "异常机制……", "来历与代价……"] },
  "modules": ["interview", "sign"],
  "moduleData": {
    "interview": { "subject": "夜班值守员", "interviewer": "档案科问询员", "lines": [{ "q": "你看见了什么？", "a": "走廊尽头有人。" }] },
    "sign": { "rows": [{ "role": "档案科", "name": "值班撰写员" }] }
  }
}
```

速记：

- 只写最小版不会失败；写多了也不会失败。
- 等级写 `相柳`、`四级`、`L4`、`4` 都可以；密级写 `L4`、`4`、`四级` 也都可以。

- `description` 可以直接写数组，`containment.protocols` 可以直接写一段字符串；运行时会归一化。
- `structure` 缺失就用默认顺序；`structure` 里写了未声明/未知 id 只会被忽略。
- 某模块没有 `moduleData` 时，该模块会被跳过，不影响其他章节。

## 三、建档顺序

1. 先读角色卡与战报事实：身份、能力、代价、关系、胜负、战斗后果。
2. 做建档判定：这是人形异常（P）、模因（M）、物品（I）、空间（S）还是异种（B）。
3. 写基础章节（收容措施、项目描述、监测数据），按对象类型决定取舍、合并与改名。
4. **按对象实际留下的“物证形态”尽量多选模块**，目标 5–8 个；素材够就继续加，不要为了省篇幅砍掉能支撑叙事的附件。每个模块都必须有真实对应内容。
5. 用 `structure` 编排顺序；事故型按时间推进，人物型以访谈为主干，地点型以舆图为锚。
6. 写元数据，核对胜负与角色名没有被改写。

档案是记录，不是战报改写。胜利者、失败者、伤亡与代价必须与战报一致，不得为了让档案“好看”而反转结果。

**篇幅基线**：正文建议 3000–5000 字，硬上限约 6000 字。少而空是失败，多而有据是合格；但禁止为凑数堆空壳。

## 四、内容密度建议（软约束）

以下是质量目标，不是 schema 门槛。达不到只会收到运行时 `console.warn` 与诊断字段，**不会阻断生成**；请优先保证页面能渲染，再按素材逐步补足。

| 部分 | 建议目标 |
|---|---|
| 全文正文 | 3000–5000 字，不超过约 6000 字 |
| `containment.protocols` | 建议 ≥ 5 条，每条写清执行者、条件与动作 |
| `description.paras` | 建议至少 3 个各自成段的层次：外观与行为、异常机制、来历与代价 |
| `monitoring.readings` | 建议 ≥ 4 行，至少 1 行 `wt` 或 `ng` |
| `log` | 建议 ≥ 12 行转写，至少 1 处异常帧（用 `cap` 写清异常） |
| `interview` | 建议 ≥ 6 轮问答，至少 1 处拒答、回避或前后矛盾，用 `note` 标出 |
| `timeline` | 建议 ≥ 8 个节点，至少 1 个 `crit: true` |
| `photo` | 建议 ≥ 2 张，图注彼此有信息差异，不能只换角度 |
| `letter` | 建议正文 ≥ 300 字，至少 2 段 |
| `sandbox` | 建议 ≥ 3 段污染文本，末尾有明确应对结论 `after` |
| `map` | 建议 ≥ 3 个标记点，每个点位都有叙事用途 |
| `list` | 建议 ≥ 6 条物证，至少 2 种不同状态 |
| `report` | 建议 ≥ 800 字，写清处置、代价、收尾与后续观察 |

## 五、字段说明

### identity

| 字段 | 规则 |
|---|---|
| `code` | 项目编号，形如 `CX-P-2428`。P/M/I/S/B 对应类型；后四位尽量取自角色卡的稳定编号或本场序号。 |
| `name` | 项目正式名，通常取角色名或称号，1–40 字。 |
| `aliases` | 别名、俗称、行动代号，建议最多 6 个；没有就写 `[]`。也可直接写一个字符串。 |
| `typeCode` | `P` 人形异常 / `M` 模因 / `I` 物品 / `S` 空间 / `B` 异种。也接受小写或中文。 |
| `typeName` | 类型中文名，如“人形现实扭曲者”。 |
| `grade` | 山海八级：`无`、`乘黄`、`夔`、`相柳`、`女娲`、`息壤`、`共工`、`建木`。也可写 `四级`、`L4`、`4`，运行时会映射到对应等级。 |
| `clearance` | `L1`–`L5`。与项目危险度、附录敏感度匹配；也可写 `4`、`四级`，运行时会归一化为 `L4`。 |
| `site` | 收容站点，如 `Site-CX-03`。 |
| `hume` | 休谟基线，如 `94.2 / ±0.3`。 |
| `disrupt` | 现实扰动当量，如 `0.7 Sv`。 |
| `filed` | 归档日期 `YYYY-MM-DD`；也可用 `date` 别名。 |
| `status` | 当前状态，如 `收容中`、`观察中`、`已失效`。 |

**只有 `code` 与 `name` 是必填**；上表其余字段都可以省略，运行时会给默认值（grade 默认“无”、clearance 默认 `L3`、status 默认“观察中”）。

`summary`：建议 50–120 字，档案口吻的总述，只陈述事实与判定，不写宣传语。

### containment

- `protocols`：建议 5–10 条收容措施，每条 8–300 字。写“谁在什么条件下做什么”，不写空泛口号；少于 5 条只会被软检查提醒，不会阻断生成。也可直接写一段带换行的字符串。
- `notice`：可选，一句收容要点，显示在金色警示框。
- `specs`：可选，收容间参数（温度、湿度、休谟稳定度等），每条 `{label, value, ratio}`；`ratio` 为 0–100 的进度条比例。
- `supplies`：可选，常备物资 `{name, qty}`，`qty` 写成字符串更稳。
- `emergency`：可选，1–4 张应急卡片 `{level, title, body, steps[]}`。`level` 如“一级”“二级”。
- `taboo`：可选，1–4 条禁忌 `{title, text}`。

### description

- `paras`：建议 3–8 段，每段 20–600 字。按“外观与行为 → 异常机制 → 来历与代价”组织，三个小节各自成段。也可直接把 `description` 写成字符串数组，运行时会转成 `paras`。
- `deleted`：可选，一行已删除段落的说明，页面会显示为红线删除块。
- `quote`：可选，`{text, source}`，用于一句现场记录或研究者批注；也可直接写字符串。
- `tabs`：可选，建议 2–4 个标签页 `{label, body}`；用于外观 / 行为 / 来源 / 附录摘要。
- `atlas`：旧写法，可选，山海图志 `{title, text[], caption, beast}`；若已声明 `atlas` 模块，以模块数据为准，这里不用再写。图志正文建议 2–4 段，`beast` 取山海八级之一；`caption` 省略时按兽形取内置图注，不必强行补写。

### monitoring

- `radar.axes`：建议六项：`危险性`、`扩散性`、`智能`、`隐蔽性`、`可交流`、`收容难度`。不足/超出六项时运行时会补齐或截断。
- `radar.values`：六项 0–5 的数值，也可写成逗号分隔字符串。
- `hume`：`{base, readout, flux, anchor, alert}`；`base` 建议 70–110，`anchor` 如 `NOMINAL`、`STRAIN`。
- `readings`：建议 4–12 行监测记录 `{time, reading, operator, judge}`；`judge` 接受 `ok`（正常）、`wt`（观察）、`ng`（异常），也接受“正常/观察/异常”，运行时会归一化。建议至少 1 行为 `wt` 或 `ng`。

## 六、附录选择与模块速查表

| 对象留下的素材 | 声明模块 | 关键数据 |
|---|---|---|
| 有监控、走廊、夜间记录 | `log` | `cam/site/date/entries[{t,v,cap}]`，`t` 为秒，≥ 12 行且至少 1 处异常帧 |
| 有问询、口供、采访 | `interview` | `subject/interviewer/lines[{q,a,note}]`，≥ 6 轮，至少 1 处拒答或矛盾 |
| 需要以“院外采风”笔法再写一次形态 | `atlas` | `title/text[]/caption/beast`，建议 2–4 段；`beast` 取山海八级之一（八级各有独立线稿），写不出形态就别选 |
| 有明确的事故先后顺序 | `timeline` | `events[{date,title,text, crit}]`，≥ 8 节点，至少 1 个 `crit` |
| 有现场照片、遗物照片、文件照片 | `photo` | `items[{art,cap,no,note}]`，`art` 取 `corridor/object/document/exterior`，≥ 2 张且图注有信息差异 |
| 有信件、纸条、遗书、封存物 | `letter` | `label/body[]/sign/date`，正文 ≥ 300 字 |
| 有模因污染、必须隔离的文本 | `sandbox` | `note/body[]/after`，建议 ≥ 3 段污染文本，末尾写明确应对结论 |
| 有地点、路线、设施布局 | `map` | `region/scale/points[{x,y,name,coord,text}]`，≥ 3 个有叙事用途的标记 |
| 有收缴清单、物证清单、库存 | `list` | `items[{no,name,qty,status,note}]`，≥ 6 条，至少 2 种状态 |
| 有战斗后的处置、收尾、复盘 | `report` | `body[]`，≥ 800 字，写清处置、代价、收尾与后续观察 |
| 档案需要正式归档生效 | `sign` | `rows[]` 可选，默认三个职务签章位 |

模块规则：

- `modules` 内不要重复；**建议目标 5–8 个**。素材够就继续加，直到对象留下的证据都被用上；不要为了省篇幅砍掉能支撑叙事的附件。
- 少而空是遗憾，多而有据是合格。每个模块都应有真实对应内容；为凑数声明的空模块会被运行时跳过并记录，但不会阻断生成。
- 只给已声明模块写 `moduleData`；未声明的模块不需要写数据，也不要留空对象占位。
- 模块数据缺字段时组件会降级渲染；缺到没有任何内容时该模块不会装配，也不会留下空章。
- `report` 不再固定末尾，可以随叙事位置走；`sign` 仍固定最后（档案法理收尾，不可移动）。
- 未知模块名会被忽略并在控制台记录，不会让页面崩溃，但**不要故意写未知模块**。
- `atlas` 默认落在“项目描述”之后、“监测数据”之前；写进 `structure` 就以 `structure` 为准，也可以 `merge` 进描述或其他章节。
- 图志不是装饰：它是用“院外采风”的笔法把项目形态再描述一次。写不出形态就别声明 `atlas`；`beast` 选错等级会显得敷衍，未知名会回退到项目等级对应兽形并记入 `normalized`。
- 旧写法 `description.atlas` 仍可用；但若同时声明了 `atlas` 模块，只渲染模块那一次，描述下的子节自动让位。
- `modules` 可以写字符串数组、`[{id:"log"}]` 对象数组或 `{"log":true}` 映射，运行时会统一归一化。

## 七、编排：可选 `structure`

`structure` 是顶层可选数组。没有它时，运行时使用默认顺序：收容措施 → 项目描述 → 监测数据 → 按 `modules` 顺序 → 签批。写了它，就以它为准。

每个元素：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `containment` / `description` / `monitoring` / 任一模块 id / `note` |
| `title` | 否 | 覆盖本章节中文标题；附录仍会自动加“附录 A：”前缀 |
| `en` | 否 | 覆盖英文副题；不写则用模块默认副题 |
| `merge` | 否 | 字符串数组：把这些模块或基础章节并入本节，合成一个带一个编号的章节 |
| `note` | 否 | 仅 `id:"note"` 时使用：过渡段正文，纯文本，可含 `[[密文|等级]]` |

规则：

- `structure` 出现时，**只有列进 `structure`（含 `merge`）的模块才会装配**；已声明但没列进去的模块不加载、不出现。
- 章节编号（壹、贰、叁……）和附录字母（A、B、C……）由运行时自动重排。删除、合并、改名都不会出现跳号或空章。
- `note` 元素不编号、不进目录，只作为两节之间的过渡段；可以有 `title`，正文用空行分段。
- `merge` 里的模块只出现一次；重复、未知、未声明的 id 会被忽略并记录，不影响其他章节。
- `sign` 无论写在 `structure` 的哪个位置，都固定最后；不要把它写进 `merge`。
- 基础章节也可以删减、合并、改名。原网页的十二节骨架与编号规则仍在，但允许按对象删减、合并、改名：例如对象是地点时，把 `monitoring` 并入 `description`，或删掉与对象无关的监测节。删减后编号与目录由运行时自动重排。
- 不要为了“凑满十二节”保留空章；空章会被运行时不装配，留下的空洞反而破坏叙事实感。

### 编排建议：怎么排才好看

| 对象类型 | 主干 | 编排要点 |
|---|---|---|
| 事故型 | 监控 + 时间轴 | 先收容边界，再按时间推进；把 `log` 与 `timeline` 合并成“事故复盘”，在事故前后各放一段 `note` 交代视角。`report` 可紧跟在复盘之后，不必压到卷末。 |
| 人物型 | 访谈 | 以 `interview` 为主干，前面用 `description` 建立人物，后面接 `photo` / `letter` 作为佐证；访谈中的拒答与矛盾要保留，不要替受访者圆场。 |
| 地点型 | 舆图 | 以 `map` 为锚，先给空间再给事件；`monitoring` 可并入 `description`，`log` 改为“巡查记录”，`list` 作为现场物证清单。 |
| 物品型 | 清单 + 影像 | 以 `list` 建立物证序列，`photo` 提供视觉证据，`sandbox` 用于必须隔离的污染文本；`report` 写处置与封存结论。 |

## 八、元数据规则（MAHOSHOJO_ARENA_META）

### 位置

Web 包路径下，元数据块紧跟在 `data/archive.json` 的最后一个 `}` 之后，另起一行，整块写在同一行：

```
<!-- MAHOSHOJO_ARENA_META {"version":1,"report":{"headline":"…","winner":"…"},"impacts":[{"characterName":"…","impact":"…","currentStateSummary":"…"}]} -->
```

- 必须是输出文件的**最后一行**，用 `<!--` 与 `-->` 完整闭合。
- 同一份输出只能出现一次；不得在 JSON 内部、`summary`、`description` 或任何正文段落里复述。
- 宿主会在 JSON 解析与 schema 校验前剥离该块；剥离后页面里不得留下任何元数据文字。
- 与自由 Web 的差异：自由 Web 把同一格式的注释块放在 `</html>` 之后；Web 包的目标是 JSON，因此它紧随 JSON 之后。标记名、字段和“最后一行 + 注释包裹”的规则不变。

### 字段

| 字段 | 必填 | 规则 | 取数来源 |
|---|---|---|---|
| `version` | 是 | 固定 `1` | 规范 |
| `report.headline` | 是 | 档案标题，含项目编号与项目名，如 `CX-P-2428「折翼的巡夜人」收容评估` | 战报标题 + 本档案 `identity`，不得另起一个和档案无关的标题 |
| `report.winner` | 是 | 本场胜利者，逐字采用战报判定；团队战写获胜方全部角色名，平局写战报给出的平局表述 | 战报“胜利者”段 |
| `impacts[].characterName` | 是 | 参战角色名，必须与角色卡 / roster 逐字一致 | roster 或角色卡 |
| `impacts[].impact` | 是 | 1–2 句，该角色在本场之后的成长、感悟或变化；只能总结已经发生的事 | 战报事实 |
| `impacts[].currentStateSummary` | 是 | 1–2 句，事件结束后的即时状态；可写伤势、情绪、关系变化、收容状态 | 战报事实 + 档案状态 |

`impacts` 覆盖本场全部参战角色，顺序不限，但角色名不得错写、漏写或合并。不要添加规范以外的字段。

### 正例

```
<!-- MAHOSHOJO_ARENA_META {"version":1,"report":{"headline":"CX-P-2428「折翼的巡夜人」收容评估","winner":"白鹭"},"impacts":[{"characterName":"白鹭","impact":"在左翼受伤后接受了地面作战训练，开始承认自己需要同伴。","currentStateSummary":"左翼轻伤，情绪稳定，暂列观察名单。"},{"characterName":"夜灯","impact":"第一次在正面交锋中败北，但仍拒绝承认对方的战术优势。","currentStateSummary":"右臂骨折，已收容于 Site-CX-03 医疗翼。"}]} -->
```

### 反例

| 反例 | 问题 |
|---|---|
| 缺少 `-->` 或注释块被截断 | 宿主无法识别，角色更新被禁用 |
| `"winner": ["白鹭"]` | 类型错，胜利者必须是字符串 |
| 战报写夜灯获胜，元数据写白鹭 | 编造胜负，档案与战报矛盾 |
| 把 `MAHOSHOJO_ARENA_META` 写进 `description.paras` | 混进正文，剥离后仍会残留可见文字 |
| 输出两个 META 块 | 重复块，解析失败 |
| 在 `summary` 里写“本次元数据将更新角色状态” | 正文复述元数据，属于泄漏 |
| 只写 `report`，不写 `impacts` | 缺角色更新，宿主会判定元数据不完整 |
| 为了“戏剧性”把败者写成胜者 | 档案是记录，不是战报改写 |

## 九、内容禁忌

- 不出现撰写员姓名或人设，署名统一为职位（如“档案科 · 值班撰写员”）。
- 不出现“本模板”“示例数据”“请填写”等元话语。
- 不写 HTML 标签、脚本、外部链接。
- 需要权限遮蔽的段落用 `[[文字|等级]]`，例如 `[[其真名已按 L4 封存|4]]`；等级取 1–5。
- 档案里的传说、传闻与事实要分级表述：未经证实的内容必须写成“据称”“记录显示”，不得冒充结论。

## 十、内容边界与设定忠实性

- 本包是虚构档案创作形式。可以写悬疑、未知、失落、失败与严肃冲突，以克制、非猎奇的方式表现；不要靠持续绝望、渲染残酷或折磨制造气氛。
- 禁止成人或露骨性内容、性暴力或性剥削、R18G 血腥猎奇、伤害本体的拟态缝合改造、仇恨歧视、现实人身攻击、现实政治影射或煽动，以及教唆违法危险行为的具体方法。档案文体、遮蔽黑条与“实验记录”都不能豁免这些边界。
- 准确理解角色的身份、性格、知识、目标和全部相关能力，保留能力的效果、条件、限制及明确例外。不能为了让收容成功而删除、削弱或曲解能力、追加弱点与代价，也不能把机构的评价、指控或危险度标签当成角色的客观事实。
- 收容是本场虚构情境中的行动或暂时状态，不预定机构一定获胜、目标一定有罪。只有本场事件支持时才写收容成立；允许协商、观察、暂缓处置或未能收容，不强行注入永久能力或永久限制。
- 正文始终区分亲历事实、机构观点、传闻、推测、临时状态与永久变化。权限遮蔽属于阅读演出，不是对现实读者的权限授予，也不是实际保密协议。
- 元数据与档案应彼此一致。`impacts` 及 `currentStateSummary` 只记录本场已经发生且有依据的变化，不把计划中的措施、未实施的实验、假设结局或收容要求写成既成事实，不把本场临时条件自动写成角色永久设定。
- 输出继续遵守宿主当次授权的 JSON 目标与文末尾注合同。若宿主未要求某类胜负或角色更新字段，以宿主合同为准，不为了填充上述示例编造胜负、伤势、成长或关系变化。
