# 流式战报元数据：不规范输出解析路线评估（2026-02-02）

本文讨论“流式生成战报”如何携带**角色更新**等结构化元数据，并重点对比两条增强不规范输出解析的路线：

1. 继续采用当前的 `<!-- MAHOSHOJO_ARENA_META … -->` 形式（提示词不变），通过更强的条件匹配/容错解析来提升成功率  
2. 修改提示词，要求模型输出**带标注的 JSON 代码块**，若不规范则调用项目内的 JSON 修复工具进行修复

> 结论先行：**优先推荐路线 1 作为主协议**，并在工程上“可选地”兼容路线 2 作为兜底（或实验开关），长期最稳健的方向是**正文与元数据分通道**（SSE/事件流），彻底避免“从 Markdown 里捞结构化数据”的天然不确定性。

更新记录：
- 2026-02-03：根据补充前提（“注释与 JSON 代码块都会短暂显示，用户已习惯；只要最终能隐藏即可”），补充了对路线 2 与 SSE/事件流的可行性分析，并加入“元数据可视化入口”建议。

---

## 1. 现状：本项目如何在流式战报中携带元数据

### 1.1 元数据注入（模型输出 + 系统追加）

- **角色更新元数据（模型输出）**：由 `lib/arena/logic.ts` 的 `createStreamPromptBuilder` 要求模型在全文最后一行追加：
  - 以 `<!-- MAHOSHOJO_ARENA_META ` 开头，以 ` -->` 结尾
  - 内含 JSON：`{ version:1, report:{headline,winner}, impacts:[...] }`
- **系统 telemetry 元数据（服务端追加）**：`pages/api/arena/generate-stream.ts` 在流式结束时额外拼接：
  - `<!-- MAHOSHOJO_TELEMETRY_META {"version":1,"usage":...,"narrativeHistoryReadCount":...} -->`

### 1.2 元数据提取/修复/归一化（前端结束后处理）

前端在流式读取结束后进行“最终后处理”（`components/arena/hooks/useBattleEngine.ts`）：

- 先剥离 telemetry 注释并解析（用于 UI 展示 token、叙事历史读取条数等）
- 再在允许写入时解析更新元数据：
  - `lib/arena/stream-meta.ts` 的 `extractStreamUpdateMeta()`
  - 内部会：
    - 只扫描尾部窗口（`MAX_TAIL_CHARS=120_000`）
    - 通过 marker 精确匹配找到最后一个 meta block（支持 HTML 注释 + “松散 marker 块”）
    - 通过括号配对定位 JSON span
    - 做 “中文引号/零宽字符/Python-ish 字面量/省略号占位符” 的最小替换
    - 调用通用修复管线 `repairNormalizeValidate()`（`lib/repair-pipeline.ts`，内部用 `jsonrepair`）
    - 用 Zod schema 校验 + 清洗归一化（去重、字段名兼容、trim 等）

### 1.3 当前机制的关键特性

- **协议层面**：元数据与正文“同一条 text/plain 流”传输，只在结束后解析并更新
- **展示层面**：通过“结束后剥离”避免 HTML 注释最终漏出到 UI（但最后一段 chunk 到达时可能短暂闪现）
- **容错层面**：现有解析对很多典型不规范已经有覆盖（单引号、未加引号 key、尾逗号、snake_case、中文引号、`True/False/None`、`……/...` 等）

## 1.4 体验前提补充：注释/代码块都会“短暂露出”，关键在于“最终隐藏 + 可诊断”

补充前提（来自产品反馈）：

- 无论是 HTML 注释元数据还是 JSON 代码块元数据，在**流式生成接近尾声**时都可能被渲染到战报里（直到“完成后剥离”生效）。
- 用户已经习惯这类“系统尾巴”，因此两者在体验维度的差异不再是决定性因素。

因此，路线评估的 UX 关键点更应调整为：

1. **是否能做到“解析完成后可靠隐藏”**（最好是 0 闪现：在线剥离/尾部缓冲；退一步是结束后剥离）  
2. **是否能给用户一个“查看元数据/解析状态”的入口**，用于定位“为什么更新失败”（边界问题/JSON 问题/语义问题）

补充：一个与“注释/代码块形式无关”的隐藏策略是 **尾部缓冲（tail buffering）**：

- 前端/服务端在流式转发时不立即把所有文本渲染/下发，而是始终保留最后 N 字符在缓冲区中；
- 当缓冲区超过 N 时才把“更早的部分”输出/渲染；
- 流结束后，对剩余尾部做一次 meta 剥离（或事件拆分），这样即使模型把元数据放在最后，也能做到“基本不闪现”。

N 的经验值通常在 `2k~8k` 之间，需要在“隐藏效果”和“尾部延迟”之间取平衡。

## 2. 问题定义：我们真正想增强的“不规范输出”有哪些

把问题拆开，有三类“失败形态”，它们对路线选择的影响不同：

1. **边界找不到**（协议不完整）  
   典型：漏了 `-->`、marker 漏写/被改写、meta 没放在最后、混入多段注释/无关正文，导致“根本定位不到 meta 区段”。

2. **JSON 不可解析**（语法/编码不规范）  
   典型：非 JSON 语法、混入解释性文本、把数组中间用省略号表示、引号/转义错、把 JSON 包在其它壳里等。

3. **语义不可用**（能 parse 但不能安全更新）  
   典型：impacts 覆盖不全/多余、角色名不匹配或歧义、字段含义漂移（impact 写成剧情段落）、超长文本导致写入失败/性能问题。

路线 1 与路线 2 主要影响的是 **(1)+(2)**；而 **(3)** 更依赖“更新前的校验与安全策略”，不完全靠输出格式解决。

---

## 3. 路线 1：继续采用 HTML 注释尾部元数据（提示词不变），增强解析

### 3.1 优点

- **对用户更友好（在同等“会短暂露出”的前提下仍略占优）**：注释一般比代码块更“像尾部系统信息”，对正文阅读干扰更小；并且更符合“正文禁止字段名/JSON”的叙事体验目标。
- **对现有链路侵入最小**：提示词、客户端/服务端协议、日志落库都不需要大改，主要集中在 `stream-meta.ts` 的容错增强即可。
- **已有修复基础强**：当前实现已经结合了“边界提取 + jsonrepair + schema 清洗”，路线 1 并不是“纯 regex 硬啃”，而是“协议定位 + 通用修复管线”的组合。

### 3.2 缺点/瓶颈

- **LLM 对 HTML 注释的遵循度存在上限**：某些模型/供应商容易漏 `-->`、把注释拆行、或者在注释外追加解释。
- **解析层会越来越复杂**：要兼容更多“非协议输出”，很容易堆叠规则，维护成本上升。
- **仍是 in-band**：元数据混在正文流里，想做到“边生成边更新”会很难（需要在线增量解析或分通道）。

### 3.3 在“提示词不变”前提下，解析侧还能怎么增强（建议项）

建议优先做“收益大且可控”的容错，避免引入过强的误判风险：

1. **支持“缺失闭合符”的尾部兜底（谨慎）**  
   当检测到尾部出现 `<!-- MAHOSHOJO_*` 且之后存在可配对 JSON span 时，可考虑把“从该注释起直到文本末尾”视为 meta 并剥离。  
   风险：若正文中提到 marker 字符串，可能误剥离；因此必须加严条件（例如只在尾部 2k~10k 字符内命中、且前缀必须包含 `<!--`，并且 JSON span 在 marker 后紧邻出现）。

2. **“在线剥离”以消除 UI 闪现（体验项）**  
   在前端流式拼接过程中，一旦检测到尾部开始出现 `<!-- MAHOSHOJO_...`，即可停止把后续内容渲染到 UI（但仍保留在 buffer 里用于最终解析/更新）。

3. **更明确的“安全失败”策略（语义层）**  
   即使 parse 成功，也建议把以下情况当作“不可用元数据”，触发降级/重做更新，而不是硬更新：
   - impacts 覆盖率过低（例如 < 50%）且用户开启了写入
   - 角色名无法唯一匹配参战列表（歧义/多命中）
   - 单条 impact/currentStateSummary 超过阈值（避免写入失败）

4. **可观测性：把“修复率/失败原因/覆盖率”记录下来**  
   例如记录：是否命中 marker、是否走了 jsonrepair、schema 校验失败的 top issue、impacts 覆盖率等，用于后续决定是否值得切路线 2。

> 小结：路线 1 的推荐策略不是“无限加正则”，而是围绕 **边界定位更稳 + 失败更可控 + 可观测性更强** 做增量增强。

## 4. 路线 2：要求模型输出“带标注的 JSON 代码块”，并用 JSON 修复工具兜底

### 4.1 预期收益

- **模型更容易产出“接近合法”的 JSON**：相比 HTML 注释，很多模型对 ```json 围栏的遵循度更高，结构更稳定。
- **更容易定位边界**：围栏天然提供 begin/end，比 `<!-- ... -->` 更像“显式分隔符”。
- **与现有修复管线契合**：项目已有 `repairNormalizeValidate()` 会 strip code fence + jsonrepair + schema 校验，逻辑可复用。

### 4.2 主要成本与风险

- **体验风险“可控但需要配套”**：既然两者都会短暂露出，路线 2 的关键在于配套“在线剥离/尾部缓冲”，以及提供可视化入口（让用户知道这是系统元数据而非正文）。
- **需要修改提示词（兼容性/回归风险）**：现有流式提示词明确禁止正文输出代码块；路线 2 必须重写规则，并确保不同模型都能稳定遵守“正文/元数据”分界。
- **仍是 in-band**：本质上还是把结构化数据塞在同一条文本流里，只是换了包装。

### 4.3 如果要做路线 2，建议的“协议形态”与落地要点

为了降低误判与 UI 漏出，建议不要只依赖“出现 ```json 就是 meta”，而是引入“明确标注行”：

- **推荐格式（示例）**：
  - 文末追加一行：`---MAHOSHOJO_ARENA_META`
  - 紧接一个代码块：```json { ... } ```
  - 代码块后不得再输出任何内容

落地要点：

1. **解析只认“最后一个标注 + 围栏”且限制在尾部窗口**（与现状一致）  
2. **前端必须做“在线剥离/隐藏”**，否则 UI 体验大概率变差  
3. **与路线 1 并行一段时间**：解析层同时接受“HTML 注释 meta”与“标注 JSON 围栏 meta”，避免一次切换带来大面积回归  

### 4.4 路线 2 的一个折中变体：仍用 HTML 注释，但允许“多行 + ```json 围栏”写在注释内部

如果你们想利用“模型更会写代码块 JSON”的优势，但又不想让用户看到代码块，可以考虑：

- 仍要求：`<!-- MAHOSHOJO_ARENA_META ... -->`
- 但允许注释内部写成：
  - `<!-- MAHOSHOJO_ARENA_META ```json\n{...}\n```\n -->`

解析层只需继续从注释中定位 `{...}`（或直接把注释内容丢给 `repairNormalizeValidate`），即可兼容。

这个折中方案常见收益是：**不破坏 UI**、且对模型而言“像在写 JSON”。

## 5. 结论与建议（推荐的演进路径）

### 5.1 推荐选择

- **短期（低风险优先）**：以路线 1 为主，继续坚持 `<!-- MAHOSHOJO_ARENA_META ... -->` 作为稳定协议  
  - 重点投在：边界兜底（谨慎）、在线剥离/尾部缓冲、语义级安全失败、可观测性
- **短期（若愿意承担提示词改动风险，换取更高 JSON 合规率）**：在保持路线 1 兼容的前提下，引入路线 2（“标注行 + JSON 围栏”）作为**可选输出**  
  - 建议灰度：先让解析器同时兼容两种格式，再逐步把提示词切到更倾向 JSON 围栏
- **长期（最稳健）**：正文与元数据分通道（SSE/事件流：`markdown`/`meta`/`telemetry`/`done`）  
  - 让 meta 变成真正的 JSON event，从根上消除“从 Markdown 中解析 meta”的不确定性，并天然支持“默认不渲染 meta、但可点开查看”

### 5.2 为什么不建议直接“全量切到路线 2”

即使路线 2 让 JSON 更规范，它也没有解决核心矛盾：**元数据仍混在正文流里**（in-band）。  
在“二者都会短暂露出且用户已习惯”的前提下，路线 2 的价值更偏向“让 JSON 更规范、更容易修复”。但从工程风险看，一次性全量切换仍可能带来：

- 提示词规则重写导致的短期波动（不同模型对代码块/标注行的遵循度差异）
- 解析器需要同时面对“注释协议”和“围栏协议”的灰度期（否则切换窗口内会回归）

因此更合理的策略是：

- 保持路线 1 为主协议（体验最稳）
- 用路线 2 做兜底或实验，而不是一刀切

## 5.3 SSE / 事件流路线：在“不增加 AI 调用与 token”的前提下是否可行？

在本项目里，“SSE/事件流路线”可以理解为：**把同一次生成请求的响应格式，从 `text/plain` 改为 `text/event-stream`（或提供可选格式）**，并把正文、元数据、telemetry 以不同事件类型发给前端。

### 可行性判断（结合当前实现）

1. **不会增加 AI 调用次数**  
   仍然只调用一次 `generateWithStreamAI`；差别只在“服务端如何把上游流包装给客户端”。

2. **不会增加 LLM token 消耗**  
   SSE 是 HTTP 传输层封装，会增加少量网络字节（`event:`/`data:` 行），但不影响模型计费 token。

3. **各 AI 提供商支持性**  
   由于 SSE 封装发生在服务端，AI 提供商只需要“能流式/能生成文本”（当前已满足）。即便某些提供商实际是“缓冲后一次性吐出”，也不影响协议正确性，只是用户看到的流式体验会更像一次性返回。

4. **Cloudflare Pages / Edge Runtime 支持性**  
   现有 `/api/arena/generate-stream` 已经使用 `ReadableStream` 进行流式透传与尾部追加注释，说明部署侧具备“边读边写响应”的能力。将响应的 `Content-Type` 换成 `text/event-stream`（并按 SSE 帧格式输出）在技术上是同一类能力。

### 工程落地时最容易踩的坑（提前规避）

1. **EventSource 只支持 GET**  
   本项目生成请求是 POST（请求体较大），因此更现实的做法是：
   - 继续用 `fetch(POST)`，但服务端返回 `text/event-stream`；
   - 前端用 `ReadableStream + TextDecoder` 自己解析 SSE 帧（而不是用 EventSource）。

2. **代理/压缩导致缓冲**  
   某些链路会对响应做缓冲或压缩，影响“边到边显示”。建议在 SSE 响应上显式设置：
   - `Content-Type: text/event-stream; charset=utf-8`
   - `Cache-Control: no-cache, no-transform`
   - 并避免对 SSE 做 gzip（如果部署链路默认开启压缩，需要确认不会吞掉 flush）

3. **断线/超时语义**  
   现在已经有 `idle/total timeout`，SSE 方案需要明确：
   - 超时后发 `event: error` 还是直接断流
   - 客户端如何把“半截正文”与“失败原因”呈现出来

### SSE 路线带来的直接收益

- **默认不渲染元数据**：前端只渲染 `markdown` 事件，不需要“先渲染再剥离”，从根上解决“尾部系统信息闪现/污染正文”的问题。
- **元数据可诊断**：可以额外发送 `meta_raw` / `meta_parsed` / `meta_error` 事件，让前端把“原始输出 + 修复后结果 + 失败原因”完整展示给用户或写入日志。

### 推荐的事件类型设计（示例）

- `event: markdown`：`data:` 为增量正文 chunk（或按时间片聚合）
- `event: meta`：`data:` 为“修复 + schema 校验 + 清洗”的结构化对象（用于角色更新）
- `event: meta_raw`（可选）：`data:` 为原始 meta 文本（用于调试，注意长度与隐私）
- `event: telemetry`：`data:` 为 usage / aiModel / narrativeHistoryReadCount 等
- `event: done`：`data:` 为 `{ ok: true }` 或包含耗时、输出字节等诊断信息
- `event: error`：`data:` 为错误信息（用于流式失败时前端展示）

> 备注：如果担心 raw 太长，可做截断（例如最多 4k~8k 字符）并标注 `truncated=true`，同时仍把全量输出存 R2 供后台排查。

### 迁移策略（避免一次性破坏兼容）

推荐采用“协议协商/双端点”方式平滑迁移：

- 方案 A：同一路径协商（推荐）
  - 客户端带 `Accept: text/event-stream` 或 `?format=sse`
  - 服务端按需返回 SSE 或旧版 `text/plain`
- 方案 B：新增 SSE 端点
  - 例如增加 `/api/arena/generate-stream-sse`
  - 旧端点保持不变，便于回滚/对比

在迁移期建议保留“旧解析逻辑”作为 fallback（例如 SSE 解析失败就退回到纯文本 + 尾部剥离）。

## 5.4 “查看元数据输出”的用户入口：SSE 与非 SSE 都应提供

无论采用路线 1/2（in-band）还是 SSE（out-of-band），都建议提供一个统一的“诊断入口”，避免用户只能看 console：

建议 UI 形态（不限定实现）：

- 战报卡片右上角：`元数据` / `诊断` 按钮（默认折叠）
- 弹窗内容建议包含：
  1. **解析状态**：命中 marker？是否使用 jsonrepair？schema 校验是否通过？失败原因（简短）
  2. **结构化结果（parsed meta）**：用于更新的最终对象（可复制）
  3. **原始输出（raw meta）**：用于定位“模型到底输出了什么”（可复制，必要时截断）
  4. **覆盖率与歧义**：impacts 匹配参战角色的比例、是否存在多命中/无法匹配
  5. **telemetry**：模型名、token 统计（若有）

这样一来，即使用户遇到“更新失败/更新不完整”，也能快速判断问题在：
- 边界没命中（没输出 marker / 没放尾部）
- JSON 不可修复（语法太乱）
- schema/语义不可用（impacts 覆盖不足、名字不匹配）

## 6. 建议的验证与观测指标（用于决策是否需要路线 2）

建议把以下指标写入日志/telemetry（不一定展示给用户）：

- meta 命中率：输出中是否出现可识别 marker
- 修复率：是否走了 jsonrepair、repair 后是否仍失败
- schema 失败原因：top issues（例如 impacts 非数组、字段类型错误）
- 覆盖率：impacts 匹配到参战角色的比例（X/Y）
- 更新成功率：最终写入 D1 成功与否（区分“解析失败/写入失败”）

当你们能用数据回答“失败主要集中在 (1) 还是 (2) 还是 (3)”时，路线选择会非常清晰：

- 若主要是 (2) JSON 语法问题 → 引入“围栏 JSON”或变体收益大  
- 若主要是 (1) 边界问题 → 强化 marker/分隔符与尾部兜底更关键  
- 若主要是 (3) 语义不可用 → 应优先做“更新前校验/歧义拒绝/重做更新”，而不是换包装
