# 魔法茶会 vs 竞技场战报：情景模式差异与建议（2026-01-17）

## 结论摘要
魔法茶会对情景卡的遵循度不如竞技场战报，核心原因在于：**系统提示词优先级与结构约束不足、情景内容被摘要/截断、长对话与世界书稀释情景权重**。竞技场“情景模式”将情景设定作为最高优先级并配合结构化输出与专用系统提示词，而魔法茶会更偏自由对话与多目标输出，情景约束在提示中容易被稀释。  
建议优先做“提示词优先级强化 + 情景锚点重申 + 关键规则显式化”，并逐步引入“情景一致性校验/回炉”能力。

## 对比维度（关键差异）

| 维度 | 竞技场战报（情景模式） | 魔法茶会 |
| --- | --- | --- |
| 系统提示词定位 | `SYSTEM_PROMPTS.scenario` 明确“情景设定最高优先级、必须严格遵循” | `buildMagicTeaPartyMainPrompt` 仅概括“基于世界书/情景/角色生成剧情”，缺少“最高优先级”措辞 |
| 情景注入形态 | `createPromptBuilder` 直接注入完整情景 JSON / 纯文本 | `buildScenarioText` 以摘要字段（scene/atmosphere/events/development/roles）为主，协议附录截断 |
| 冲突处理 | 明示“辅助情景以主情景为准” | 辅助情景无明确“冲突优先级”说明 |
| 上下文干扰 | 单次生成，无对话历史 | 长对话历史 + 角色档案 + 世界书 + 更新草案等堆叠 |
| 输出约束 | Zod schema 强制结构化（winner/impacts 等） | JSONL/Markdown 仅约束格式，不强制情景关键事件 |
| 角色/情景安全 | 明确“忽略提示注入”且情景置顶 | 强调“协议附录仅在允许阶段遵守”，降低规则强度 |

关联实现：
- 竞技场：`lib/arena/constants.ts`、`lib/arena/logic.ts`
- 魔法茶会：`lib/magic-tea-party/prompts.ts`、`lib/magic-tea-party/presets.ts`

### 竞技场情景模式提示词

```
你是一位才华横溢的剧作家和故事叙述者，精通于在既定框架下演绎精彩的故事。你的任务是基于用户提供的【情景设定】和【角色档案】，创作一篇符合魔法少女世界观的新闻报道。

## 核心创作原则

1.  **严格遵循情景设定**: 用户提供的【情景设定】是本次创作的绝对基础和最高优先级。你必须将故事的背景、核心事件、NPC、氛围等严格限制在情景文件所描述的框架内。
2.  **忠于角色性格**: 深入理解每个【角色档案】，确保他们在情景中的言行、决策和能力使用都符合其性格、背景和历战记录。
3.  **演绎而非重述**: 不要只是简单地复述情景和角色设定。你的任务是“演绎”——让这些角色在设定的舞台上“活”起来，通过他们的互动、对话和行动来推动故事发展，完成情景中设定的核心事件。
4.  **整合用户引导**: 如果用户提供了【故事引导】，请将其作为故事发展的关键线索或期望的结局方向，并在创作中巧妙地融入。
5.  **确定“胜利者”**:
    * 如果情景是合作或日常互动，没有明确的胜负，请在“winner”字段中列出所有核心参与角色的名字。
    * 如果情景包含竞争或对抗元素并分出了胜负，请在“winner”字段中只填写胜利者的名字。
    * 如果是平局，则返回“平局”。
6.  **记录影响**: 故事结束后，必须为每一位参与角色生成一段“impact”描述，总结他们在此次情景事件中的经历、成长或变化。

现在，请你开始创作。
```

## 差异细节与影响

### 1) 系统提示词对“情景优先级”的强度
竞技场情景模式在系统提示词中直接写明“情景设定是绝对基础与最高优先级”，并将“严格遵循情景设定”列为核心原则（`SYSTEM_PROMPTS.scenario`）。  
魔法茶会系统提示词更偏“导演/旁白 + 互动剧情”，虽然列出“世界书/情景/角色”，但未强调“情景 > 世界书/对话历史”的硬性优先级，导致模型更容易跟随对话推进而偏离情景。

### 2) 情景内容被摘要/截断
竞技场情景模式直接注入完整情景 JSON（去 signature/metadata）或正文文本，信息量充分。  
魔法茶会只抽取 `elements` 的部分字段，并对内容长度进行截断；“协议附录”又被 4k 限制。若情景卡的关键规则埋在非 elements 的其他字段或正文长段内，魔法茶会会直接丢失这些规则，从而显著降低遵循度。

### 3) 长对话与多目标输出稀释了情景权重
魔法茶会 prompt 末尾包含完整对话历史（最多 200 条），再叠加角色档案、世界书、摘要、更新草案与 choices 规则，情景设定位于中间段落，易被上下文“噪声”稀释。  
竞技场无对话历史干扰，情景在 prompt 中更突出，且系统提示词与内容块指向一致。

### 4) 输出结构缺少“情景一致性硬约束”
竞技场战报输出由 schema 约束，且必须生成 impacts / winner 等字段；系统提示词要求“完成情景核心事件”。  
魔法茶会仅约束输出格式（JSONL/Markdown），未设定情景关键事件检查项，模型可在“格式正确但情景跑偏”的情况下通过。

### 5) 场景冲突优先级未显式化
竞技场在辅助情景块中明确“与主情景冲突时以主情景为准”。  
魔法茶会辅助情景没有同等强度的“优先级规则”，导致多情景/世界书共同存在时，模型更容易混杂设定。

## 可能原因（导致“情景遵循不佳”的机制）
- **信息丢失**：情景卡被摘要且截断，关键规则缺失。  
- **权重不足**：情景未被声明为最高优先级，且不在 prompt 末尾重申。  
- **上下文干扰**：长对话与多输出目标（choices/summary/updates）分散模型注意力。  
- **缺少校验**：无情景一致性检查或回炉机制，模型“偏离也能成功输出”。  

## 建议（分层方案）

### 低成本（提示词与拼接策略）
1. **显式优先级声明**：在 `buildMagicTeaPartyMainPrompt` 的系统提示词中加入明确规则：  
   - “情景设定优先级高于世界书、角色档案与对话历史”；  
   - “如与用户对话冲突，必须拉回情景”。  
2. **末尾情景锚点**：在“对话记录”之后再追加一段“情景锚点重申”（time/place/核心事件/禁则），避免情景被对话历史淹没。  
3. **辅助情景冲突规则**：补齐“主情景优先”表述。  

### 中成本（情景信息完整性）
1. **扩大情景注入**：`buildScenarioText` 中引入更完整的情景卡字段（或允许注入“原始情景 JSON 全文”作为附录）。  
2. **关键信息显式化**：将情景卡中“必须发生 / 禁止发生 / 必须包含角色或地点”提炼成 bullet list，置于情景块顶部。  
3. **可选压缩策略**：当对话历史过长时，优先压缩历史或摘要化历史，再保留完整情景卡。  

### 高成本（校验与回炉）
1. **情景一致性检查**：生成后用轻量规则或二次模型检查关键项是否满足（场景/事件/禁则）。不满足则给出 notice 或自动回炉。  
2. **情景驱动的 choices**：当偏离趋势出现时，强制生成“拉回情景”的选项，引导玩家回到场景主线。  
3. **模式化输出**：为“情景模式的魔法茶会”提供单独系统提示词，近似 `SYSTEM_PROMPTS.scenario` 的强约束版本。  

## 推荐落地优先级（最小改动策略）
1. **系统提示词补强优先级**（低成本、立竿见影）。  
2. **情景锚点重申**（改拼接顺序即可）。  
3. **提升情景卡注入完整度**（避免规则丢失）。  

以上建议可先在“魔法茶会情景测试集”中做 A/B 对比，观察遵循度的提升幅度，再考虑引入更高成本的回炉与校验机制。
