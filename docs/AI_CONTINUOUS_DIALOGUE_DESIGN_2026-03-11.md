# AI 连续对话能力设计讨论稿（2026-03-11）

> 状态：讨论稿，尚未实施。目标是结合仓库现状，明确“连续对话/连续生成”在战报与角色卡场景中的可行做法、边界与推荐路线，供后续开发时参考。

## 1. 背景与目标

当前项目中的大多数 AI 生成功能，本质上仍是“一次请求 -> 一次结果”：

- 角色卡生成：用户提交问卷或名字，后端拼接单次 prompt，直接返回最终角色卡。
- 战报生成：前端提交当前参战角色、情景、用户引导与若干附加上下文，后端一次性生成完整战报。

这类模式的优点是简单、稳定，但存在两个明显上限：

1. 长文本困难  
   单次输出越长，越容易遇到模型跑偏、结构损坏、被截断、Cloudflare 超时、上下文不够等问题。

2. 修改成本高  
   当用户想“保留已有结果，只改其中一部分”时，当前模式更像重新生成，而不是持续协作式修改。

因此，本讨论聚焦两个需求：

1. 在战报生成中支持“连续对话式”的多轮续写，生成多份连续战报，拼成长故事。
2. 在角色卡生成后支持“连续对话式”的多轮修改，逐步打磨角色卡，而不是每次完全重来。

本文结论先行：

- 这两个方向都**可做**。
- 但不建议直接把它理解成“把 provider 原生 chat messages 透传给模型就行”。
- 更适合本仓库现状的做法，是做成**基于会话状态的多请求连续生成**：每一轮仍然是独立 HTTP 请求，但请求会读取上轮留下的会话状态、摘要、分支与工作草稿。

## 2. 仓库现状审计

## 2.1 AI 基础封装仍以“单个 prompt 字符串”为核心

当前通用封装主要是：

- `lib/ai.ts`
- `lib/stream/raw-ai.ts`

它们的共同特点是：

- 对外输入是 `systemPrompt + promptBuilder(input)` 产出的单个 prompt。
- 没有通用的“消息数组会话模型”抽象。
- 结构化输出、回退修复、流式读取、reasoning 采集都围绕“单轮请求”设计。

这说明如果要做连续对话，不能假设项目已经有一个现成的通用 chat runtime。

## 2.2 角色卡生成链路是典型的一次性生成

代表文件：

- `pages/api/generate-magical-girl.ts`
- `pages/api/generate-magical-girl-details.ts`
- `pages/api/generate-magical-girl-details-stream.ts`
- `pages/details.tsx`
- `pages/name.tsx`

现状特点：

- 输入以问卷答案、语言、Lore 为主。
- 输出是一次性完整角色卡，流式版本也只是“单轮流式输出”，不是多轮会话。
- `pages/api/generate-magical-girl-details.ts` 还承担了“原生性签名”判定逻辑；输入条件满足时，结果可能保留原生签名。

这意味着角色卡场景在加入“连续修改”后，必须明确处理两个问题：

1. 会话如何保存工作中的角色版本。
2. AI 修改后的结果是否还能保留原生性。

第二点尤其关键。结合 `pages/character-manager.tsx` 当前的保存逻辑，可以得出一个很明确的约束：

- **AI 驱动的结构性修改默认应视为衍生修改，必须移除 `signature`，不得假装仍是原生卡。**

## 2.3 战报链路虽然不是会话式，但已经具备“连续叙事”的部分基础

代表文件：

- `pages/api/generate-battle-story.ts`
- `pages/api/arena/generate-stream.ts`
- `components/arena/hooks/useBattleEngine.ts`
- `lib/arena/logic.ts`
- `components/arena/stores/useNarrativeHistoryStore.ts`
- `components/arena/components/NarrativeHistorySettings.tsx`

现状特点：

- 战报生成也是单轮请求。
- 但已经支持多种“跨轮上下文”：
  - `readArenaHistory` / `writeArenaHistory`
  - `readCurrentState` / `writeCurrentState`
  - `readNarrativeHistory` / `writeNarrativeHistory`
- 前端已有本地叙事历史存储，能够把战报正文累计下来，并在后续 prompt 中回读。

这意味着：

- 战报场景其实已经有一个“弱连续生成”雏形。
- 真正缺的不是“能不能续写”，而是**会话组织能力**：
  - 哪些历史要读
  - 如何压缩
  - 如何分支
  - 如何继续写“下一章”
  - 如何把连续多章组织成可管理的对象

## 2.4 魔法茶会已经实现了本仓库里最成熟的“连续会话能力”

代表文件：

- `lib/magic-tea-party/types.ts`
- `lib/magic-tea-party/storage.ts`
- `lib/magic-tea-party/history.ts`
- `lib/magic-tea-party/prompts.ts`
- `lib/magic-tea-party/useMagicTeaPartyChat.ts`
- `pages/api/magic-tea-party/generate-stream.ts`
- `pages/api/magic-tea-party/generate-updates.ts`
- `pages/api/magic-tea-party/apply-updates.ts`

它已经具备的能力包括：

- 本地会话持久化（IndexedDB）
- 消息历史裁剪与 token 预算
- 摘要
- 分支会话
- 更新草案生成与应用
- 流式会话体验

但需要注意两点：

1. 它虽然是“连续对话”，本质上仍然是把消息历史编译进一个大 prompt，而不是直接依赖 provider 原生 chat session。
2. 它的产品目标是角色扮演对话，不是战报，也不是角色卡编辑。

因此，魔法茶会最值得复用的是**会话方法论和基础能力**，而不是直接拿来当通用壳。

## 3. 需求拆分：这其实是两个不同问题

## 3.1 战报连续生成

目标不是“聊天”，而是：

- 用多轮生成把一个长故事拆成多个章节或多份战报。
- 每一轮都基于上一轮结果继续推进。
- 最终仍然保留竞技场已有的角色状态更新、历战记录、叙事历史积累能力。

这里的重点是**叙事连续性**和**角色状态一致性**。

## 3.2 角色卡连续修改

目标也不是普通聊天，而是：

- 用户围绕当前角色卡不断提修改意见。
- AI 根据当前卡面与历史修改意图，生成下一版改动。
- 用户可以确认、回退、分支、继续改。

这里的重点是**可控编辑**，而不是长篇叙事。

这两个场景共享“会话”这个外观，但输出形态完全不同：

- 战报输出是正文 + 元数据 + 角色状态更新。
- 角色卡输出更适合是草案补丁或改动提案，而不是直接覆盖整卡。

所以不建议一开始就试图做一个“统一的万能 AI 聊天框架”。

## 4. 方案对比

## 4.1 方案 A：给通用 AI 封装直接加 `messages` 支持，走 provider 原生多轮 chat

思路：

- 扩展 `lib/ai.ts` / `lib/stream/raw-ai.ts`，让其接受消息数组。
- 战报和角色卡都把历史消息直接传给模型。

优点：

- 概念上最直观，最像“连续对话”。
- 若某些模型对原生 messages 优化更好，理论上可能得到更自然的连贯性。

问题：

1. 当前仓库的大量能力建立在“单个 prompt 字符串”之上  
   包括：
   - 结构化 JSON 输出
   - promptBuilder 组合
   - 提示词注入防御
   - 流式元数据约束

2. 跨 provider 一致性会下降  
   本项目要兼容 OpenAI、Google、DeepSeek 及自定义兼容通道；直接转向原生 messages，兼容成本会变高。

3. 这不能自动解决“长期记忆压缩”问题  
   就算改成 messages，也仍然需要摘要、裁剪、分支与状态快照。

结论：

- 这是一个**可做但不应优先**的基础设施改造。
- 它不是连续对话能力的前置条件。

## 4.2 方案 B：保持“单轮请求”，但引入显式会话状态与上下文编译层

思路：

- 每次请求仍然调用当前的单轮生成接口。
- 但请求前，先从会话对象里取出：
  - 初始上下文
  - 摘要记忆
  - 最近几轮内容
  - 当前工作快照
- 再把它们编译成当前这一轮的 prompt。

优点：

- 与当前仓库最兼容。
- 复用现有 `generateWithAI` / `generateWithStreamAI`。
- 更适合 Edge Runtime 和现有 API 结构。
- 可以逐场景定制上下文结构，而不是被通用 chat 绑死。

问题：

- 需要单独设计会话模型、摘要策略、分支机制。
- 需要前端或服务端承担更多状态管理。

结论：

- **这是推荐方案。**

## 4.3 方案 C：直接复用魔法茶会作为通用连续对话壳

思路：

- 让战报续写和角色卡修改都借魔法茶会 UI / 存储 / 会话机制来跑。

优点：

- 已有成熟的会话、分支、摘要、更新草案体系。

问题：

1. 产品语义不匹配  
   魔法茶会是角色扮演对话，战报与角色卡编辑都不是同一类产物。

2. 输出协议不匹配  
   魔法茶会偏向 JSONL/Markdown 侧信道；战报需要固定战报格式和角色更新元数据；角色卡修改更需要补丁草案。

3. 当前茶会默认是 BYOK 设计  
   与站内系统通道和原生签名等逻辑并不天然一致。

结论：

- 只建议复用其中的**方法和局部模块**，不建议直接把两个需求塞进茶会壳里。

---

## 5. 推荐设计：多请求会话化，而不是单次长请求自循环

## 5.1 核心设计原则

1. 每一轮仍然是独立请求  
   不做“服务端开一个长循环，自己连续问自己好几轮再一次性吐给前端”的设计。

2. 会话状态显式化  
   连续能力来自 `session state`，不是来自 provider 的黑箱上下文。

3. 永远区分三层上下文

- 固定种子层：角色、情景、问卷 Lore、初始规则
- 滚动记忆层：摘要、状态快照、章节摘要、编辑摘要
- 最近窗口层：最近 1 到 3 轮正文或指令

4. 先做 local-first  
   参考魔法茶会，MVP 先放浏览器本地存储；如确有跨设备需求，再补云端同步。

5. 不做“先抽象大而全框架，再接业务”  
   先把战报连续生成和角色卡连续修改分别做通，再抽低层公共能力。

## 6. 战报连续生成推荐方案

## 6.1 推荐目标形态

不是“单份超长战报”，而是：

- 一个“连续战报会话”
- 会话下有多章战报
- 每章都是一份独立、可展示、可保存、可导出的战报
- 会话层负责把这些章节组织成连续长故事

这比强迫模型一次写 5000~10000 字更稳妥。

## 6.2 为什么战报场景最适合先做

因为现有链路已经有三块关键基础：

1. 角色状态写回  
   已有 `current_state` 与 `arena_history` 更新能力。

2. 叙事历史累积  
   已有本地 `narrativeHistory` 存储与读取能力。

3. 流式展示  
   已有 `/api/arena/generate-stream` 与 `useBattleEngine`。

换句话说，战报连续生成更像是在现有竞技场上补一个“章节会话层”，而不是从零发明新产品。

## 6.3 推荐上下文模型

每个连续战报会话建议至少维护：

- `seed`
  - 初始角色快照
  - 初始情景
  - 问卷 Lore
  - 生成设置
- `chapters`
  - 每一章的正文 Markdown
  - headline / winner / generationId
  - 章节摘要
- `workingCombatants`
  - 应用上一章 impacts 与 currentState 之后的最新角色快照
- `sessionSummary`
  - 对前文主线的压缩摘要
- `branches`
  - 支持从任意章节分叉续写

推荐的 prompt 组装顺序：

1. 当前角色最新快照
2. 当前情景与固定规则
3. 会话摘要
4. 最近 1~2 章完整正文
5. 用户本轮追加引导

而不是把全部章节全文都塞回去。

## 6.4 推荐交互

MVP 交互建议：

- 生成首章
- “继续续写”
- “基于本章分支续写”
- “重写本章但保留前文”
- “导出整段连续故事”

这里“继续续写”本质上就是一次新的战报生成请求，只是上下文换成“会话上下文 + 当前角色状态 + 最近章节”。

## 6.5 与现有竞技场能力的衔接方式

建议沿用现有更新逻辑，而不是另写一套：

- 每章输出仍然允许 `impacts` 与 `currentStateSummary`
- 仍可选择是否写入 `arena_history`
- 仍可选择是否写入 `current_state`
- 若开启 `writeNarrativeHistory`，每章正文仍可进入叙事历史

新增的只是：

- 会话对象本身
- 章节摘要
- 分支关系

## 6.6 不建议的做法

1. 不建议让模型一轮里“连续输出三份战报”  
   这会让单次请求结构更脆弱，也更难同步角色状态。

2. 不建议直接把完整叙事历史无限制读回  
   必须有摘要和最近窗口，否则 token 很快失控。

3. 不建议把连续战报先并入魔法茶会  
   竞技场已有角色更新链路，拆出去反而损失现成能力。

## 7. 角色卡连续修改推荐方案

## 7.1 角色卡场景的关键区别

战报是“生成新正文”，角色卡修改是“围绕已有对象做变更”。

因此，角色卡连续修改最重要的不是消息历史，而是：

- 当前工作版本是什么
- 本轮到底改了哪些字段
- 是否允许用户确认/回退

如果继续沿用“每轮都整卡重写”的思路，问题会很多：

- 模型容易误改无关字段
- 用户很难看出改了什么
- 原生性边界不清晰
- 回退困难

## 7.2 推荐输出形态：补丁草案，而不是直接覆盖整卡

推荐做成两阶段：

1. `generate-edit-draft`
   - 输入：当前卡、会话摘要、最近几轮编辑指令、用户本轮要求
   - 输出：补丁草案

2. `apply-edit-draft`
   - 前端展示改动预览
   - 用户确认后再应用到当前工作卡

这样能复用魔法茶会里“生成更新草案 -> 应用更新草案”的经验，但输出目标换成角色卡字段。

## 7.3 为什么补丁比整卡重写更合适

优点：

- 改动范围可见
- 可以做字段级校验
- 可以做回退与分支
- 更容易避免模型误伤无关字段
- 更容易结合 `validateDataCard`

尤其是对结构化卡（魔法少女 / 残兽）来说，补丁模式明显更安全。

## 7.4 推荐会话模型

每个角色卡编辑会话建议维护：

- `baseCard`
  - 会话起点卡快照
- `workingCard`
  - 当前工作版本
- `messages`
  - 用户编辑指令与系统回应摘要
- `sessionSummary`
  - 对历史编辑意图的压缩摘要
- `checkpoints`
  - 每次应用补丁后的版本快照
- `pendingDraft`
  - 当前未确认的补丁草案

推荐交互：

- 用户输入：“保留她的花名，但把战斗风格改得更偏支援”
- 后端返回：
  - 改动摘要
  - 触达字段列表
  - 候选补丁
  - 风险提示
- 用户选择：
  - 应用
  - 重新生成草案
  - 丢弃
  - 基于当前版本继续说下一轮修改意见

## 7.5 对不同卡模板的处理建议

### 结构化角色卡

适用：

- `magical-girl`
- `canshou`

推荐：

- 走字段级补丁
- 明确 `touchedPaths`
- 应用后立即跑 `validateDataCard`

### 通用角色卡 / 通用情景卡

适用：

- `general`
- `general-scenario`

推荐：

- 主体内容通常是 Markdown 长文
- 允许“整段重写 + diff 预览”
- 不强求非常细粒度的 JSON 补丁

### 原生卡

强约束：

- **只要 AI 对内容做了结构性修改，默认移除 `signature`。**
- 不应尝试把 AI 修改后的卡伪装成“仍然原生”。

这与当前 `character-manager` 的原生性保存逻辑是一致的，也能避免后续审核与用户认知混乱。

## 7.6 不建议的做法

1. 不建议 AI 改完直接自动落盘  
   必须给用户一个草案确认面板。

2. 不建议第一版就支持所有卡模板的统一 JSON Patch  
   结构化卡和 Markdown 卡应分模式处理。

3. 不建议保留原生签名  
   除非后续产品重新定义“AI 辅助编辑后的原生性”，否则默认降级为非原生最安全。

---

## 8. 公共能力建议复用，但不要过度泛化

推荐抽出来共享的，是这些低层能力：

1. 本地会话存储
   - 可参考 `lib/magic-tea-party/storage.ts`

2. 历史裁剪与 token 预算
   - 可参考 `lib/magic-tea-party/history.ts`

3. 摘要与滚动记忆
   - 战报会话与角色卡编辑会话都需要

4. 分支与 checkpoint
   - 两个场景都需要“回到上一版继续”

5. 草案应用模式
   - 可参考 `generate-updates` / `apply-updates`

不建议现在就抽象一个“万能 SessionEngine”，原因很简单：

- 战报和角色卡修改的输出协议不同
- 角色卡修改还牵涉签名和校验
- 战报还牵涉角色状态写回与章节组织

更务实的路线是：

- 先做两个垂直会话
- 等二者都稳定，再抽真正共用的部分

## 9. 数据与命名建议

结合仓库现有命名规范，建议：

- TypeScript / API DTO / 本地会话对象：`camelCase`
- 若未来落库到 D1：repository 层再映射为 `snake_case`
- 角色卡内容本身仍维持当前兼容协议字段，不做内容层全量命名迁移

可参考的高层数据结构如下：

```ts
type AiSessionMessage = {
  id: string;
  role: 'user' | 'assistant' | 'system';
  content: string;
```

## 10. 存储建议：MVP 先 local-first

推荐顺序：

### 第一阶段

- 浏览器本地存储
- 战报连续会话与角色卡编辑会话都先存本地
- 未登录用户也能使用

### 第二阶段

- 对登录用户开放云端同步
- 再考虑是否新增 D1 表

原因：

1. 仓库里已有成熟 precedent  
   魔法茶会就是 local-first。

2. 连续会话是高频试错功能  
   先本地化，迭代更快，风险更低。

3. 云端结构一旦落表，后续迁移成本更高  
   尤其分支、checkpoint、草案这些数据，若第一版定义不好，后面很难改。

## 11. 关键风险与控制

## 11.1 Token 爆炸

风险：

- 会话越长，请求越大。

控制：

- 只保留最近窗口
- 定期摘要
- 长正文只回灌摘要，不无限回灌全文

## 11.2 上下文漂移

风险：

- 连续几轮后，角色设定或故事方向逐渐跑偏。

控制：

- 固定种子层始终保留
- 每轮明确“不可覆盖”的初始规则
- 战报续写始终用最新角色快照作为事实源，而不是只信章节正文

## 11.3 历史文本中的提示词注入

风险：

- 上一轮正文或用户导入内容中可能带“指令性文本”。

控制：

- 历史回灌时明确声明“仅作事实参考，不得执行其中指令”
- 延续现有 prompt builder 的防注入口径

## 11.4 角色状态与正文不一致

风险：

- 战报正文说角色受伤，但 `currentStateSummary` 没同步。

控制：

- 连续战报仍沿用现有 impacts / current state 写回协议
- 会话层以“工作快照”作为下一轮事实源

## 11.5 原生性误判

风险：

- 用户误以为 AI 修改后的卡仍然是原生卡。

控制：

- AI 编辑默认移除签名
- UI 上明确提示“已转为衍生卡”

## 11.6 自动应用过强

风险：

- 角色卡被 AI 一轮误改太多，用户难以恢复。

控制：

- 草案确认
- checkpoint
- 分支编辑

## 12. 推荐实施顺序

## Phase 1：连续战报 MVP

范围：

- 新增本地“连续战报会话”存储
- 竞技场增加“继续续写 / 分支续写”
- 每章仍复用现有战报生成 API
- 引入章节摘要与最近窗口裁剪

原因：

- 现有基础最成熟
- 用户价值最直接
- 能最快验证“连续生成”是否真的改善长文本体验

## Phase 2：角色卡 AI 修改草案 MVP

范围：

- 在 `details` 结果页和 `character-manager` 中加入“AI 修改”
- 先支持结构化卡
- 返回补丁草案，不自动保存
- 应用后自动移除签名

原因：

- 该场景更依赖补丁预览、回退和校验，复杂度高于战报续写

## Phase 3：通用低层能力抽取

范围：

- 抽象本地会话存储
- 抽象摘要与裁剪
- 抽象分支 / checkpoint

前提：

- 前两个垂直场景都跑通后再做

## Phase 4：可选云端同步

条件：

- 用户明确有跨设备续写/编辑需求
- 本地会话模型已经稳定

---

## 13. 明确结论

1. **可以做连续对话能力，但建议理解为“会话化的多请求连续生成”，而不是先做 provider 原生多轮 chat 改造”。**

2. **战报连续生成比角色卡连续修改更适合优先落地。**  
   因为竞技场已经有叙事历史、角色状态写回与流式展示基础。

3. **角色卡连续修改推荐走“补丁草案 + 用户确认 + checkpoint”的路线，不推荐整卡自动重写。**

4. **AI 改卡默认应丧失原生性，移除签名。**  
   这是与当前仓库规则最一致、风险最低的处理方式。

5. **短期不建议先做万能通用会话引擎。**  
   先做两个垂直能力，再抽公共层，工程风险更低。

---

## 14. 后续开发前建议先确认的三个决策

1. 连续战报会话是否只做本地存储，还是登录用户默认云同步？
2. 角色卡 AI 修改第一期是否只支持结构化卡，暂不覆盖 `general` / `general-scenario`？
3. 连续战报的“章节摘要”是否允许引入额外一次轻量 AI 摘要，还是优先使用启发式摘要？

在这三个问题明确后，就可以进入更细的接口设计与 MVP 实施拆分。
