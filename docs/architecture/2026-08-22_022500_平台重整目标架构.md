# MahoShojo-Generator 平台重整目标架构

状态：`active`
日期：2026-08-22
最近修订：2026-08-27（同步 Arena 多人 Hono + Redis 首发与开发/生产双门禁）
适用范围：Web、Admin、香港 Hono、D1 Gateway、Arena Room runtime、Desktop、Mobile、本地库与多人基础设施
规范性：本文件解释长期结构；可测试强制要求以实施规格为准。

## 1. 架构目标

本次重整同时重划：

1. **部署边界**：哪些代码独立构建、部署和回滚。
2. **执行边界**：哪些操作在设备、Cloudflare、香港服务器、Room runtime 或数据库网关执行。
3. **信任边界**：哪些结果可以成为官方签名、排位、多人与治理事实。
4. **数据所有权**：哪些数据属于设备、账号或服务器权威。
5. **资源责任**：哪一方承担 AI、CPU、连接、数据库和存储成本。

总原则：

> 本地能够完成的默认在本地完成；只有需要项目资源、全局共享状态或服务器信任根的能力才联网。

Direct 与 local 路径不经过项目 API。Hosted、签名、严格排位、多人与线上数据才进入服务器路径。

`apps/arena-room` / Durable Object 只保留为未来 Phase H 可能批准的独立 `RoomRuntime` adapter。只有真实容量、全球 RTT、multi-instance ownership/fencing 或 Room DR 需求触发后才建立该部署单元；在此之前不得把 Service Binding / cross-deployment GenerationBridge 重新变成 v1 前置条件。

### 2.1 Hosted 运行时容灾视图

目标态把“业务入口”和“物理执行节点”分离：

```text
Web / Installed Client
        │
        ▼
stable logical Hosted API endpoint
        │
        ├──────── primary ───────▶ apps/api / Hono HK
        │                              │
        │                              ▼
        │                         D1 Gateway
        │                              │
        └──────── DR ────────────▶ apps/web / Next/OpenNext adapter
                                       │
                                  native D1 binding
        │                              │
        └──────────────────────┬───────┘
                               ▼
                              D1
```

- Hono HK 是默认 Hosted 主执行面；Cloudflare Next/OpenNext 只对显式 DR manifest 中的能力提供长期灾备 adapter。
- 客户端不应把 `homura` 等物理 Hono origin 编码为目标架构中的唯一入口；切流由 Cloudflare 或等价独立控制面完成。
- Hono/Next 共享业务 core，只保留运行时 adapter 差异；legacy app-to-app 动态 import 必须移除。
- DR Next 在可行时直接使用 D1 binding/Sessions，避免与 Hono 同时依赖 D1 Gateway；两种 DatabaseProvider 必须保持同一一致性 contract。
- safe/read 请求可按健康状态自动选择 DR；generation/stream/settlement 等非幂等操作在开始前选定 runtime，执行可能已经开始后不得盲目跨 runtime 重放。

具体 Cloudflare Load Balancing、Worker routing 或其他切流产品由实施阶段依据账号能力、成本和长流 CPU 数据选择；不得为了容灾把全部长流无条件重新代理进高 CPU Worker。

### 3.1 依赖方向

```text
domain                contracts
   ▲                      ▲
   │                      │
ai-core  local-library  cloud-client  multiplayer-core
   ▲          ▲              ▲              ▲
   └──────────┴──────────────┴──────────────┘
```

必须满足：

- `packages/*` 不导入 `apps/*`；
- `domain` 不依赖框架、DOM、Node 数据库、Tauri 或 Cloudflare；
- `contracts` 不读取环境变量；
- 客户端包不导入服务器密钥、D1 管理能力或管理 API 实现；
- Web、Desktop、Mobile 不直接互相导入源码；
- 不通过 `@/*` 跨 package 穿透内部文件，使用 package exports。

### 3.2 运行时端口

上层业务依赖端口，而不是平台判断：

```ts
interface AiExecutionPort {
  execute(
    request: AiExecutionRequest,
    signal: AbortSignal,
  ): Promise<AiExecutionResult>;
  stream(
    request: AiExecutionRequest,
    signal: AbortSignal,

interface CardRepository {
  get(id: string): Promise<LocalCardRecord | null>;
  list(query: LocalCardQuery): Promise<LocalCardPage>;

}

interface SecureVault {
  setSecret(ref: string, value: string): Promise<void>;
  getSecret(ref: string): Promise<string | null>;
  deleteSecret(ref: string): Promise<void>;
}
```

实现示例：

- `BrowserIndexedDbCardRepository`
- `SqliteCardRepository`
- `TauriDirectAiExecutor`
- `ElectronDirectAiExecutor`
- `HostedAiExecutor`
- `TauriStrongholdVault`
- `PlatformKeychainVault`

组件不得散落 `if (isDesktop)` / `if (offline)` 来决定业务语义。

### 3.3 Shared core 与 runtime adapter

跨 Hono/Next 的 Hosted 业务复用同样遵循端口化原则：service/domain/contracts 不导入 Hono Context、NextRequest、Cloudflare binding 或具体 Redis client；`apps/api` 与 `apps/web` 各自提供 adapter。DR adapter 的存在不得成为 app-to-app 源码导入或复制业务 handler 的理由。

## 4. 执行模式

| 模式 | 执行位置 | 项目资源 | 官方签名 | Strict | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| `direct-local` | 用户设备/localhost | 否 | 否 | 否 | Ollama、LM Studio |
| `direct-remote` | 用户设备到自定义 Endpoint | 否 | 否 | 否 | BYOK、自建代理 |
| `hosted` | 项目服务器 | 是 | 可 | 按资格 | Web 官方通道 |
| `authoritative` | 项目服务器/Room 服务 | 是 | 是/验证 | 是 | 签名、排位、多人结算 |

`hosted` 和 `authoritative` 可以由同一服务器承载，但权限、审计和结果语义必须区分。

## 5. Direct Provider 架构

### 5.1 Catalog 与 Profile

Catalog 只提供预设：

```text
provider preset
  -> display name
  -> adapter
  -> default endpoint
  -> documentation
  -> model suggestions
```

用户保存的是本地 Profile：

```ts
type DirectProviderProfileV1 = {
  version: 1;
  id: string;
  name: string;
  adapter: 'openai-compatible' | 'anthropic' | 'google';
  baseUrl: string;
  modelId: string;
  apiKeyRef?: string;
  secretHeaderRefs?: Record<string, string>;
  publicHeaders?: Record<string, string>;
  generationDefaults?: {
    maxOutputTokens?: number;
    temperature?: number;
    thinking?: Record<string, unknown>;
  };
  transport?: {
    allowPublicHttp?: boolean;
    maxRedirects?: number;
  };
  createdAt: string;
  updatedAt: string;
};
```

MVP 必须支持 `openai-compatible + arbitrary baseUrl`。其他 adapter 渐进实现。

### 5.2 Native Executor

Renderer 只能调用窄命令：

```text
listProviderProfiles()
saveProviderProfile()
testProviderProfile()
streamGeneration(profileId, normalizedRequest)
cancelGeneration(requestId)
```

不得暴露：

```text
fetchAny(url, headers, body)
readAnyFile(path)
runShell(command)
getAllSecrets()
```

### 5.3 Endpoint 安全

- Profile 只能由用户设置页显式创建或确认导入。
- 卡片、Prompt、场景、网页链接和多人 payload 不得静默创建/修改 Profile。
- 远端默认要求 HTTPS。
- `localhost`、loopback 与私有网段允许 HTTP，以支持本地模型和局域网服务。
- 公网 HTTP 需要醒目警告和逐 Profile 确认。
- 拒绝 `file:`、`data:`、`javascript:` 等非 HTTP(S) scheme。
- 不提供“忽略所有 TLS 错误”的全局开关。
- 重定向默认最多 3 次；跨 Origin 不转发 Authorization、API Key、Cookie 或 secret headers。
- 禁止覆盖 `Host`、`Content-Length`、`Connection` 等传输层 header。
- Direct 请求不携带项目 Cookie、Legacy Bearer、Better Auth session 或 activity token。
- 日志、错误和导出必须脱敏秘密。

## 6. 本地库架构

### 6.1 记录模型

```ts
type LocalCardExecutionProvenance =
  | 'downloaded'
  | 'direct-local'
  | 'direct-remote'
  | 'imported'
  | 'edited';

type LocalCardProvenance =
  | {
      kind: 'official-signed';
      signature: string;
      signatureVersion?: number;
      signatureKeyId?: string;
      execution?: LocalCardExecutionProvenance;
    }
  | {
      kind: 'signature-invalid';
      signature: string;
      signatureVersion?: number;
      signatureKeyId?: string;
      execution?: LocalCardExecutionProvenance;
    }
  | {
      kind: 'unsigned';
      execution?: LocalCardExecutionProvenance;
    };

type LocalCardRecord = {
  id: string;
  schemaVersion: number;
  cardType: 'character' | 'scenario' | 'history' | 'questionnaire';
  title: string;
  data: unknown;
  contentDigest: string;
  provenance: LocalCardProvenance;
  cloudRef?: {
    cardId: string;
    cloudRevision?: string;
    copiedAt: string;
  };
  createdAt: string;
  updatedAt: string;
  deletedAt?: string;
};
```

`official-signed` 与 `signature-invalid` 都必须保留非空签名证据；历史有效签名可以没有 `signatureVersion` 或 `signatureKeyId`。`unsigned` 不携带 provenance 签名证据。该结构标签只表达客户端记录状态，不替代服务器验签，也不要求改写 legacy `data.signature`。

`cloudRef` 只描述来源或显式副本关系，不代表自动同步。

### 6.2 Web

- 使用独立 IndexedDB；
- schema upgrade 只向前迁移；
- 调用 `navigator.storage.persist()` 与 `navigator.storage.estimate()`；
- 提供导出、导入和恢复；
- 明确提示清除站点数据会删除本地库。

### 6.3 Installed APP

- SQLite 保存可查询记录；
- 大对象进入应用数据目录；
- 文件写入采用临时文件 + 原子替换；
- 高风险迁移前做备份或可回滚 snapshot；
- API Key 进入 Secure Vault，不进普通数据库。

### 6.4 备份格式

推荐版本化 archive：

```text
manifest.json
cards/*.json
assets/<digest>.<ext>
```

`manifest.json` 至少包含格式版本、导出时间、条目数、摘要和 checksum，不包含 API Key、session、authkey 或设备秘密。

## 7. Cloud 与权威边界

### 7.1 上传

```text
local record
  -> contract validation
  -> auth / account state
  -> slot / size budget
  -> content policy
  -> metadata normalization
  -> signature verify
  -> cloud persistence
```

### 7.2 原生签名

- 服务器私钥/秘密永不进入客户端；
- 客户端只可展示和携带签名；
- 服务器是验签和签发的最终权威；
- 本地编辑可能使签名失效；
- 是否升级到非对称签名另立设计。

### 7.3 Strict

Strict 至少要求：

- 服务器可解析的在线实体 ID；
- 服务器生成或验证的 generation record；
- 服务器资格检查；
- 服务器计算 winner/eligibility；
- 服务器写入幂等 rating event。

本地库记录即使携带有效旧签名，MVP 也必须先显式进入线上库并获得服务器实体 ID，才能参与 Strict。

### 7.4 Hosted 运行时容灾与数据层级

服务器计算节点与业务事实源分离：

| 层级 | 典型状态 | 故障/清空后的要求 |
| --- | --- | --- |
| durable-authoritative | D1 业务事实、按领域定义的 R2/final generation 对象、rating/settlement/audit | 不得由 Redis/VPS/client 推断或替代 |
| session-authoritative | Hono RoomActor + Redis Room checkpoint（membership、Shared Config、Proposal、generation reservation mirror 等活跃会话事实） | Redis/VPS 丢失可以终止/重建 Room，但不得改变 durable-authoritative 事实 |
| reconstructable | Redis generation replay/cache、查询快照、可重建索引 | 回源 durable authority 或明确降级 |
| ephemeral/lossy | rate limit window、presence、Pub/Sub、允许损失 telemetry 聚合 | 可以丢失，但不得改变已成立业务事实 |

判断状态能否只放 Redis 的标准是：丢失该状态后是否允许“终止/重建会话且 durable business truth 仍正确”，而不是简单按“重要/不重要”或“高频/低频”分类。Room checkpoint 是可恢复的会话权威，不是永久业务数据库。

VPS 本地磁盘只保存部署包、临时文件、日志和可重建运行态，不保存唯一用户资产、rating、settlement 或 audit truth。香港服务器整机丢失后，应能以新实例 + secret + D1/R2/Redis 连接恢复持久业务服务；若 Room Redis checkpoint 一并丢失，v1 允许活动房间 replacement/rejoin，不依赖旧磁盘或客户端副本伪造原服务器权威。

D1 本身仍是 Hono 与 Cloudflare DR 的共同依赖故障域。本轮不引入第二套 SQL 双写；D1 outage 时线上权威能力显式降级，Local/Direct 能力继续可用，并使用 Time Travel / 长期导出 runbook 恢复数据库。

## 8. Arena 多人协作架构

当前 Arena 多人 v1 的产品/协议语义继续有效，但首发运行时已由 2026-08-25 ADR 修订为 Hono + Redis：

```text
Host / Member existing Arena UI
        │
        │ logical Hosted HTTPS/WSS
        │ short-lived room ticket
        ▼
apps/api / Hono HK
  ├─ Room WebSocket ingress
  ├─ RoomActorRegistry
  │    └─ one active writer per room
  ├─ RedisRoomStore
  │    └─ conditional checkpoint + TTL
  └─ RoomGenerationPublisher
       └─ existing authoritative Arena generation
                │
                ├─ D1 / R2 authoritative terminal facts
                └─ batched safe Room projection
                         │
                         ▼
                    all viewers

Redis room directory
  ├─ TTL-bound discovery record
  └─ bounded public sorted-set derived index
```

强制边界：

- Arena 多人仍使用现有 `/arena`；v1 Room realtime 归属 `apps/api` / Hono，不建立第二套 Arena，也不要求独立 `apps/arena-room`。
- 任一活动 `roomId` 在同一时刻只有一个可改变 Room session authority 的 RoomActor/owner。v1 初始只允许一个 room-capable Hono 实例；启用多实例前必须另立 ownership + fencing 方案或迁移到独立协调 runtime。
- Room Shared Config 是白名单投影；完整 Arena store、UI state、`userProviderConfig`、API credential、完整 host-local payload 和不需要共享的 generation sensitive input不得进入 Redis checkpoint、Room log 或成员广播。
- 房主本地完整 payload 只有 authoritative generation 真正需要时才按既有 generation contract 临时发送给 generation service；Room plane 不复制或持久化它。
- 成员在本地修改 working copy；Proposal 使用 typed semantic change + typed `expectedBase` / precondition，online `DataCardRef` 使用可验证 `versionToken`。
- authority-changing command 先验证当前状态，再纯逻辑推导 next state，以 `roomEpoch + revision/checkpointVersion` 等 predecessor 条件 CAS 提交 Redis checkpoint；提交成功后才安装 actor next state、ack 和 broadcast。旧 actor/recovery writer 不得无条件覆盖新 epoch。
- Redis 不可用时 authority-changing command fail closed。单实例阶段优先使用 RoomActor 有界内存 fan-out；Pub/Sub 只在真实跨进程消费者出现后采用，Streams 只在真实 bounded replay 需求出现后采用。
- reconnect 以 `roomEpoch` 作为 fencing boundary：same epoch 可以 bounded replay/snapshot；new epoch 必须 full snapshot/rejoin/recovery。较大的旧 revision 不得覆盖新 epoch。
- generation start 冻结 shared config、participant snapshot、revision、`collaborativeInfluence` 与引用版本，并使用稳定 `generationRequestId`；浏览器/API retry 不得产生第二次 authoritative generation。
- 房主浏览器不是 AI stream 中继。generation 与 Room 同处 `apps/api` 时使用进程内/服务内 `RoomGenerationPublisher`；story delta 批量 fan-out，最终正文/terminal 仍以既有 generation persistence / R2 为权威。
- Redis directory record/index 只做 public/unlisted discovery；create/recovery/close 与 checkpoint 在同一 Lua/CAS 边界维护，返回前重验 current open/epoch/host authority。absent/expired checkpoint 不得被 stale index member 复活。Arena v1 不发布 D1 Room directory migration。
- WebSocket upgrade 使用 Node/Hono 当前支持的 server adapter，独立审计 Origin、ticket、message schema、size/rate limit、per-user connection cap、heartbeat、backpressure 与 slow-consumer policy。
- Development Gate 与 Production / Integration Gate 分离：B1–G 可以在隔离环境先开发验证，但 production WSS/ticket、DNS/LB/Access、production migration 和 Room DR activation 必须继续等待对应平台生产门禁。
- `apps/arena-room` / Durable Object / Hibernation / DO alarm /跨部署 GenerationBridge 只在真实容量、多地域、multi-instance coordination 或 Room DR 价值触发 Phase H 后重新评估；future adapter 必须复用同一 contract，不能与 Hono 对同一 epoch 无协议双写。
- 旧 PVP 去留不影响该 v1 继续推进。

具体规范遵循 `ADR-arena-room-portable-runtime-hono-redis-first`、`SPEC-arena-multiplayer-hono-redis-runtime-amendment-v1` 和配套 Hono + Redis 实施计划。

## 9. Admin 架构

Cloudflare Access 是入口控制，origin isolation 按部署形态选择：

```text
Worker-hosted Admin:
Browser -> Cloudflare Access -> apps/admin Worker -> application RBAC

Self-hosted/VPS Admin:
Browser -> Cloudflare Access -> Tunnel / equivalent private ingress
        -> origin validates Access assertion
        -> application RBAC
```

强制边界：

- Cloudflare Access 不是应用层授权的替代品；
- 自托管 origin 校验 Access assertion 的 signature/JWKS、issuer、audience、expiry；
- 自托管/VPS origin 必须有 Tunnel 或等价的 direct-origin bypass 防护；Worker 本身作为 origin 时不为形式一致强制增加 Tunnel；
- 管理浏览器不得持有 D1 管理 Token；
- 高风险操作必须有 reason、幂等、版本检查和审计；
- 数据导出和批量操作有额外权限；
- `feat/admin` 中的本地可信 handler 在上线前逐一威胁建模。

## 10. 资源与超时

服务器预算由服务端配置控制：

- user/IP concurrency；
- request burst；
- daily quota；
- max output；
- idle timeout；
- total timeout；
- provider timeout；
- memory/socket budget；
- D1/R2/DO limit。

Hono 主执行面还必须观察 Node/进程级容量信号，而不能只看请求成功率：process CPU、RSS/heap、event-loop utilization/delay、active request/stream/socket、AI upstream active/TTFB/abort、D1 round trip/rows、Redis latency/error/memory/eviction，以及 runtime/DR selection。容量告警阈值在真实生产基线后冻结，不在设计文档中凭空指定。

Direct 执行：

- 不使用项目额度；
- 默认不强制项目 total timeout；
- 支持用户 Stop；
- 可提供用户自定义 idle/total guard；
- 防止 APP 自身内存无限增长，使用流式落盘或窗口化累积。

多人房间：

- 单实例 Hono 观察 active rooms/socket、RoomActor queue/latency、event-loop、RSS/heap 与 Redis checkpoint latency/error/memory；
- WebSocket 通过 heartbeat/idle cleanup 识别死连接，并对 slow consumer 使用有界队列与 close/resync；
- presence 不按固定频率写 D1；
- story chunk 不写 D1，final report 回源权威 generation storage；
- room list 使用 limit/cursor 和索引；
- 资源指标不记录用户正文、API Key、完整 Proposal 或完整本地卡。

## 11. 发行与供应链

### Desktop

```text
version tag
  -> GitHub Actions matrix build
  -> tests
  -> platform bundle
  -> updater signature
  -> SHA-256
  -> artifact attestation
  -> draft release
  -> publish release（仓库启用时使用 immutable release）
```

- Updater public key 在客户端；
- private key 在受保护环境并有离线备份；
- workflow actions 尽量 pin 到完整 commit SHA；
- 已发布 release 资产不得覆写；
- 失败发布使用新版本修复，不替换既有二进制。

### Android

- 使用固定 signing key；
- GitHub Release 上传 APK、checksum 和 attestation；
- APP 可以提醒和下载，但安装流程遵循 Android 权限与用户确认；
- 不把 Desktop Updater 协议直接复制到 Android。

### iOS

独立处理 App Store、TestFlight、Web Distribution 或其他符合资格的路径。

## 12. Legacy 与兼容

- 本轮保持 Legacy 登录行为；
- Local 功能不要求登录；
- Online API 继续兼容当前认证；
- Monorepo 搬迁只能做行为等价适配；
- Auth 收口必须单独 ADR、迁移指标和回滚。

## 13. 旧 PVP 与 Multiplayer Core

旧 PVP 去留不阻塞结构重整，也不阻塞 Arena 多人 v1。

若低使用决定下线，优先保留/抽取：

- room lifecycle；
- participant/role；
- optimistic version；
- idempotency；
- simultaneous decisions；
- event log；
- presence/chat；
- recovery/stalled handling；
- audit。

牌堆、隐藏手牌、PVP winner glue、PVP 专用 Bot 和结算 UI 可以作为产品层移除。抽取时应优先兼容 Arena 多人的已冻结契约，而不是把 PVP schema 原样提升成通用层。
