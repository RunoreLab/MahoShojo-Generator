# 本地优先与服务器权威边界决策

状态：`accepted`
日期：2026-08-22
决策标识：`ADR-local-first-authority-boundary`

## 背景

MahoShojo-Generator 是公开源码、通过 GitHub 与网页发布的开放项目。现有 Web 应用把大量 AI 请求、生成流、数据读取和账户能力集中在 Cloudflare 与香港服务器 Hono 服务上。

Desktop/Mobile 具备直接访问用户自有 AI 服务、本地模型、本地数据库和文件系统的能力。若仍把所有操作绕经项目服务器，会持续占用项目连接、内存、CPU、数据库和运维资源，也会限制用户使用 Ollama、LM Studio、局域网模型或自建兼容端点。

同时，客户端自由度不能与严格排位、原生签名、多人权威状态混在一起。

## 决定

### 1. 采用 Local-first / Direct-first

Desktop/Mobile 默认在设备本地完成所有能够安全本地完成的能力，包括：

- 数据卡创建、编辑、校验、导入和导出；
- 本地卡库、草稿、会话和历史；
- 用户自有供应商的 Direct AI 调用；
- 本地 OpenAI-compatible 模型服务调用；
- 非权威的本地故事、战报、对话和沙盒玩法。

这些能力不得要求登录，也不得为了统一接口而默认绕经项目服务器。

### 2. 服务器只承担必要能力

以下能力继续由服务器参与或保持服务器权威：

- 项目承担成本的 Hosted AI；
- 官方原生签名；
- 严格排位与权威评分事件；
- 多人房间、共享状态、Proposal 校验、权威生成与结算；
- 线上卡库、卡槽、公开发布与社区数据；
- 账号、消息、举报、审核、徽章与治理；
- 管理后台；
- 需要项目秘密或数据库权限的操作。

Desktop/Mobile 首期可以不提供 Hosted AI。

### 3. 客户端不可信

无论客户端是否为官方 GitHub Release、Tauri、Electron、Android APK 或用户自行编译的 fork，服务器均必须把它视为攻击者可控制的客户端。

服务器不得相信客户端提交的：

- `isNative=true`；
- 原生性或“官方执行”声明；
- 胜者、评分变化或排位资格；
- generation provenance；
- 多人房间 revision、隐藏状态或结算结果；
- 管理员身份；
- 未经验证的 Cloud Card ID 与作者字段。

所有服务器权威结果必须由服务器重新计算、验签、授权或持久化。

### 4. Direct 结果的权威限制

由用户自定义远端供应商、本地模型、导入内容或客户端编辑产生的结果：

- 可以保存到本地库；
- 可以用于沙盒、自由创作和允许的休闲玩法；
- 可以显式上传到线上库并接受服务器验证；
- 不得由客户端自行签发官方原生签名；
- 不得直接进入严格排位；
- 不得直接形成权威多人结算或评分事件。

### 5. Arena 多人协作边界

Arena 多人协作 v1 继续采用：

- Room Shared Config 安全白名单投影；
- Provider/API credential 不进入房间；
- host-local 完整内容不进入共享状态，只发送受限 stub；
- 普通成员本地编辑，提交 typed Proposal；
- 服务器/DO 校验 Proposal 并维护 revision；
- 房主发起唯一一次服务器 Arena 生成；
- Durable Object 只协调、持久化最小房间状态和广播。

未来若允许 Direct 生成在房间内共享，只能作为明确标记的非权威休闲模式，不能复用 v1 的权威生成、原生签名或 Strict 语义。

### 6. 资源限制按执行责任划分

- Hosted/服务器执行继续受项目配置的并发、额度、输出、空闲超时、总时长、CPU、内存和数据库预算约束。
- Direct/本地执行不使用项目资源时，不套用项目配额与生成时长限制。
- Direct/本地执行必须支持用户主动取消，并允许用户配置可选超时；首期不得强制沿用 Web 的 300 秒空闲限制。
- 客户端本地自由不得被解释为服务器也提供无限资源。

### 7. Legacy 登录本轮不变

Legacy 登录、authkey 和 Better Auth 双轨兼容保持现状。本轮只允许为 Monorepo 搬迁做等价适配，不改变用户行为或下线策略。

## 影响

### 正面影响

- APP 可以在无账号、弱网或断网环境下独立使用。
- BYOK 和本地模型不再消耗项目 AI 与流式连接资源。
- 用户可放宽生成时长、输出和模型选择。
- 原生、排位、多人和治理仍有清晰的服务器信任根。
- Web、APP 和服务器可以围绕能力端口演进，而不是围绕单一部署形态耦合。

### 代价

- 需要建立本地执行适配器、Secure Vault、本地库和导入导出。
- 同一功能可能存在 Direct 与 Hosted 两种实现，需要合约测试。
- 本地结果不能获得与 Hosted 相同的官方权威权益。
- APP 的错误处理、网络兼容和供应商差异由客户端承担更多责任。

## 不采用的方案

- **所有 AI 请求继续经过项目服务器**：即使用户使用自己的 API Key，也会继续消耗项目流式连接和运维资源，并限制本地模型。
- **把服务器签名密钥放入 APP**：公开仓库和用户设备无法保护长期服务器秘密。
- **把官方 APP 视为可信客户端**：开源客户端可以被修改、重新编译或直接绕过 UI 调用 API。
- **多人房间传播完整本地配置**：完整本地卡、Provider Profile、API Key 和运行态不应进入房间存储或广播。
