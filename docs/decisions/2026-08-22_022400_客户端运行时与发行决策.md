# 客户端运行时与发行决策

状态：`accepted`
日期：2026-08-22
决策标识：`ADR-client-runtime-release`

## 背景

项目计划发布 Desktop 与 Mobile 客户端，并通过 GitHub Releases 分发开源构建。客户端需要复用 React/TypeScript、本地 Direct AI、SQLite、本地文件和 Secure Vault，同时不得把服务器秘密编译进公开产物。

MahoShojo-Generator 是 GitHub/Web 发布的开源项目，不按其他拟在 Steam 发布的闭源商业项目设计发行与防护。

## 决定

### 1. Desktop 首选 Tauri 2

Desktop 默认采用：

```text
Tauri 2 + Vite/React/TypeScript + Rust-side runtime adapters
```

主要原因：

- 适合复用现有 React DOM/Tailwind；
- 提供细粒度 capabilities；
- 支持 SQLite、HTTP、文件和 Stronghold；
- 能生成 Windows MSI/NSIS、Linux AppImage 和 macOS bundle；
- 官方 Updater 支持签名校验和静态更新 JSON/GitHub Release 资产。

Direct AI、文件、数据库与秘密操作应通过窄 IPC/command 暴露，不向 renderer 提供通用 shell、任意文件系统或无限制原生 API。

### 2. Electron 是后备方案

只有 Desktop PoC 出现以下不可接受问题时，才转 Electron：

- 系统 WebView 导致核心页面或长流无法达到支持矩阵；
- Rust/native adapter 的维护成本明显超过收益；
- 关键 Node AI 库或流式协议无法以合理成本实现；
- 安装、更新或平台兼容门禁连续失败。

采用 Electron 时必须遵循：

- `nodeIntegration=false`；
- `contextIsolation=true`；
- renderer sandbox；
- 只通过验证 sender 的 preload/IPC 暴露窄能力；
- 不加载带 Node 权限的远端内容；
- 不关闭 `webSecurity`。

### 3. Mobile 最终运行时暂缓冻结

Mobile 先对比 Tauri Mobile 与 Capacitor。PoC 必须验证：

- Direct 自定义 Endpoint 与长流取消；
- SQLite；
- Secure Vault；
- 本地库导入导出；
- 代表性 React DOM 页面；
- Android 签名构建和 GitHub Release；
- 深链接和文件选择；
- CI 可维护性。

PoC 通过后单独形成 Mobile Runtime ADR。Expo/React Native 只在决定重做原生移动 UI 时重新进入比较。

### 4. 自定义 Endpoint 由 Native Direct Executor 发起

不向 WebView renderer 暴露通用任意 URL fetch 能力。

```text
React UI
  -> providerProfileId + normalized request
  -> narrow IPC
  -> Native Direct Executor
  -> user-selected endpoint
```

Native Executor 必须：

- 只读取用户显式保存的 Provider Profile；
- 隔离和保护 API Key/secret header；
- 不携带项目 Cookie、Bearer 或活动令牌；
- 限制跨域重定向时的凭据传播；
- 支持取消、流式读取和结构校验；
- 对公网明文 HTTP 发出警告；
- 不允许卡片或外部内容静默修改 Endpoint。

### 5. Desktop 使用 GitHub Releases 与签名更新

Desktop 发布基于版本 tag 和 GitHub Release。最低发布物：

- 平台安装包；
- SHA-256 checksum；
- Tauri updater signature；
- `latest.json` 或等价静态更新清单；
- release notes；
- GitHub artifact attestation。

Tauri updater 公钥可以进入公开仓库和客户端；私钥只存在于受保护 CI/发布环境。私钥必须有离线备份和丢失/泄漏预案。

Windows 代码签名证书与 Tauri updater 签名是两个独立信任层。首期可先保证 updater 签名，代码签名视项目资源另行增加。

### 6. Mobile 分发不复用 Desktop Updater 假设

- Android
  - 可通过 GitHub Releases 发布使用稳定 signing key 签名的 APK；
  - APP 可检查版本并引导用户下载、校验和安装；
  - 不承诺无交互静默更新；
  - signing key 必须长期保管。
- iOS
  - 分发、签名、审核和地区要求独立设计；
  - 不把 GitHub Release 直接下载 IPA 视为通用正式发行方案；
  - 不阻塞 Web、Desktop 与 Android。

### 7. 公开仓库秘密边界

可以公开：

- Tauri updater 公钥；
- checksum；
- 非秘密 Endpoint 模板；
- `env.example` 的变量名与占位值；
- API contracts。

不得公开或编译进入客户端：

- updater 私钥；
- Android signing private key；
- Apple signing private keys/certificates；
- `SIGNATURE_SECRET_KEY`；
- 项目 AI Key；
- Better Auth secret；
- D1/R2/Cloudflare 凭据；
- Access service token；
- 生产 SSH key。

## 影响

### 正面影响

- Desktop 有明确默认栈，不阻塞后续开发。
- Electron 和 Mobile 仍保留证据驱动的替代路径。
- GitHub Releases 与项目开源定位一致。
- 更新信任根和服务器签名信任根互相隔离。
- 任意 Endpoint 的自由不会等同于向 renderer 开放任意原生能力。

### 代价

- Desktop 需要 Rust adapter 和跨平台打包 CI。
- Mobile 仍需 PoC，不能直接承诺所有平台同日发布。
- Android GitHub 分发更新体验不如应用商店。
- macOS/Windows 代码签名可能产生额外成本和证书管理工作。

## 不采用的方案

- **同时维护 Tauri 与 Electron**：先以 Tauri PoC 得出证据，只有失败门禁触发后才实现 Electron fallback。
- **让正式 APP 加载远端 Web 主页面**：正式 APP 应打包本地 UI，避免远端内容直接获得本地 capability。
- **把 Desktop Updater 当作移动端通用自动更新**：Android/iOS 的签名、安装和分发受各自平台规则约束。
