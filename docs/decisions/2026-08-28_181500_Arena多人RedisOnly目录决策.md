# Arena 多人 Redis-only Room Directory 决策

状态：`accepted`
日期：2026-08-28
决策标识：`ADR-arena-multiplayer-redis-only-room-directory`
部分取代：`ADR-arena-room-portable-runtime-hono-redis-first` 的 D1 Room Directory 决定

## 1. 决策关系与适用范围

本 ADR 取代 [Arena Room 运行时可移植与 Hono + Redis 首发决策](./2026-08-25_104400_ArenaRoom运行时可移植与HonoRedis首发决策.md)
中“D1 `arena_multiplayer_rooms` 继续作为 v1 派生目录”以及对应 orphan reconciliation 的决定。

旧 ADR 的 Hono + Redis 首发、单写者、checkpoint、epoch fencing、服务器权威、secret 隔离、非幂等不盲目重放
与 generation durable persistence 等决定继续有效。本 ADR 只改变活动 Room directory 的存储和一致性边界。

## 2. 背景

GMR-06 曾实现 Redis checkpoint 到 D1 directory 的安全派生投影。实现证明 D1 row 不能在 Redis checkpoint
缺失、过期或 epoch 不匹配时创建、恢复或授权 Room；它只保存第二份发现元数据。为了维持这份非权威副本，运行时
仍需 registration、跨存储补偿、closing tombstone 和两类 reconciler。

Arena 多人 v1 接受活动 Room 随 Redis runtime 故障或 TTL 到期而终止，并以 replacement Room 恢复协作。既然
D1 directory 不能恢复同一个 Room authority，它在首发阶段没有提供足以抵消双存储一致性成本的新增能力。

## 3. 决定

Arena 多人 v1 使用 Redis-only Room Directory：

1. Redis Room checkpoint 是活动 Room 的唯一 session authority。
2. 每个可发现 Room 可以有一个有界 Redis directory record；public Room 额外进入一个有硬分页上限的 sorted-set
   index。二者都是 derived data，不得创建或复活 Room。
3. create、authority recovery/lifecycle update 与 close 对 checkpoint、directory record、public index 的变化必须处于
   同一 Redis Lua/CAS 原子边界；未知提交结果沿用 RoomActor quarantine/recovery，不得异步盲重放目录写。
4. list、lookup 与 join 在成功前必须重新验证 current checkpoint 的严格解析、open lifecycle、exact `roomEpoch`、host
   authority 与 deadline。stale/malformed candidate 只能 exact-CAS/lazy cleanup，不能删除并发 replacement。
5. presence/heartbeat 不得重排 public index；低频 lifecycle refresh 可以延长 exact directory record TTL，但不得产生
   高频发现写放大。
6. `arena_multiplayer_rooms`、D1 Room adapter、Redis-to-D1 registration/compensation/tombstone/reconciler 不进入 v1
   runtime 或 production/preview migration chain。
7. 既有 D1/R2 generation durable facts、账户、数据卡、排位和治理数据不受本 ADR 影响。

## 4. 故障与恢复语义

- Redis checkpoint absent/expired 时，directory record/index 即使残留也不得返回成功或允许 join。
- Redis 不可用或 key type/mutation response 无法证明成功时，authority-changing command 必须 fail closed。
- Redis/VPS 整体丢失时不保证保留同一 `roomId`；房主可以创建 replacement Room。最终 generation 结果仍按既有
  D1/R2 storage contract 恢复，不把 directory 提升为永久业务事实。
- production/preview 若历史上已存在 `arena_multiplayer_rooms`，不得依据本 ADR 自动 `DROP TABLE`；必须另立带备份、
  回滚和人工授权的 schema operation。

## 5. 影响

正向影响：

- Room lifecycle 与 discovery 只跨一个原子运行时边界，消除非权威双写补偿状态机；
- 不发布没有独立恢复价值的 v1 D1 schema；
- public/unlisted 产品契约、服务器最终校验与未来 RoomRuntime 可移植性保持不变。

代价与限制：

- public discovery 与活动 Room 一样依赖当前 Redis runtime；Redis 故障时不会由 D1 提供陈旧的“可发现”假象；
- 跨 Redis cluster/region 的统一发现、SQL 搜索、运营审核或 durable registration 仍未提供；这些需求必须由真实指标
  触发新的 ADR，而不是恢复历史实现即视为完成。

## 6. 不采用的方案

- **保留 D1 derived directory**：没有恢复 authority 的价值，却保留跨存储补偿与 reconciliation。
- **把 D1 row 提升为 authority**：无法证明 membership、revision、epoch、Proposal 或 generation reservation，违反
  服务器权威和 fail-closed 边界。
- **先保留 schema 以后再用**：增加生产迁移与回滚负担，同时把未决未来需求伪装成当前契约。
- **只维护 Redis index、不重验 checkpoint**：会让 stale index 影响 join/lookup 权威。

## 7. 未来重新评估

只有出现可量化的跨 cluster/region discovery、durable registration、复杂查询/审核或 Redis directory 容量证据时，
才新建 ADR，明确第二存储保存的事实、authority 等级、双写未知结果、补偿/重放、migration 与回滚语义。历史 GMR-06
实现只作为参考，不构成恢复授权。
