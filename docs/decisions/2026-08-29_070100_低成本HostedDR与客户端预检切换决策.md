## 背景

平台重整已经形成 Hono 主执行面、Next/OpenNext DR adapter、双 DatabaseProvider、readiness、capability manifest、fault suite 和 production activation gate。较早设计有意把实际 Cloudflare Load Balancing、DNS 或 Worker router 留待后续授权，但后续门禁仍把 stable control plane 未纳管视为 production build/默认分支并轨前置。

已确认：Cloudflare Load Balancing 会带来额外付费和维护复杂度，项目现阶段不采用。默认架构应只利用 GitHub 默认分支已经依赖且被明确认可的资源，以及可用免费资源；只有真实运行数据证明必要时再单独决策。

同时，现有 Next DR 不是无价值的重复实现。它与 Hono 共享 service/domain/contracts，并已经积累 capability、数据 transport、版本偏差、secret、故障与 no-replay 约束。直接删除会损失低成本容灾能力和未来恢复基础。

因此需要把“保留双运行时”与“购买托管流量控制面”解耦，并为客户端在首次生成 dispatch 前进行一次健康选择建立正式边界。

## 决定

### 1. 冻结“无新增付费产品依赖”默认约束

成本基线定义为：变更合入时 GitHub 默认分支已经依赖、且已明确承认的产品与资源。本决定形成时，默认分支为 `feature/v0.2.0_Battle_Growth_MahoShojo`，观察 HEAD 为 `07d8edf1544cf30867e81f929748a73ecd3cd362`。feature/refactor 分支中仅作为候选设计出现、尚未购买或授权的产品不计入成本基线。

默认 production、默认 CI、默认 production build 和默认分支并轨：

- **MUST NOT** 依赖相对于该成本基线新增的固定付费产品、付费附加项或必须购买的托管 control plane；
- **MUST NOT** 因未购买 Cloudflare Load Balancing 或等价产品而失败；
- **MAY** 继续使用项目已有服务器、已有 Cloudflare 产品和当时可用免费额度；
- **MUST NOT** 把免费额度描述为无限资源或成本承诺；
- 预期显著增加已有计量开支、资源规格或运营负担的变更 **MUST** 由人工审阅。

这里约束的是默认依赖和新增开支，不是承诺项目永远不付费。未来引入付费能力必须通过本 ADR 第 10 节的重新决策门禁。

### 2. 保留 Hono primary + Next/OpenNext DR

- `apps/api` / Hono 继续是 Hosted HTTP 默认主执行面；
- `apps/web` / Next.js/OpenNext 继续为 `config/hosted-dr-capabilities.json` 中明确登记的 capability 提供 DR adapter；
- 两个 runtime 必须继续调用共享 service/domain/contracts，不建立两套业务实现；
- DR adapter 不因取消 Cloudflare LB 而被重新定义为待删除 legacy wrapper；
- D1/R2/Redis/DO/VPS 本地状态的权威边界沿用较早 accepted ADR/spec，不在本决策中变化。

### 3. 默认生产路由改为客户端 pre-dispatch selection

默认 routing mode 为 `client-preflight`，而不是 `managed-control-plane`。

每个新的 generation intent 在发送首个生成 POST 之前：

1. 客户端对 manifest 声明的 Hono primary readiness endpoint 发起一次有界 GET；
2. primary ready 时，把该 operation 固定到 Hono，并只向 Hono发送首次 POST；
3. primary 不可达、超时、返回 non-ready 或协议无效时，读取该 route/method 的 manifest policy；
4. 只有 `safe-read` 或 `drMode=new-request-only` 的 operation 才能继续检查 DR readiness；
5. DR ready 时，把该 operation 固定到 Next/OpenNext DR，并只向 DR 发送首次 POST；
6. `drMode=fail-closed`、未登记、contract 未验证或 DR non-ready 时明确降级，不尝试 DR POST。

这里的“切换”只发生在首次 dispatch 之前。它不是在 Hono POST 失败后把同一个请求重发到 DR。

### 4. dispatch boundary 后禁止透明跨 runtime 重放

以下任一事件发生后，operation 视为已经进入或可能进入 dispatch boundary：

- 客户端开始向选定 runtime 写入 request body；
- fetch/transport 已提交 POST，无法证明服务器未收到；
- runtime 已创建 request/generation identity、reservation、Provider attempt 或权威写入；
- 客户端只观察到 timeout、断线、abort、`connection reset` 或未知网络错误。

进入该边界后：

- 客户端 **MUST NOT** 自动把原 POST 改发另一 runtime；
- timeout/断线 **MUST** 被分类为 ambiguous outcome，而不是“肯定未执行”；
- 恢复 **MUST** 使用稳定 request/generation identity、状态查询、stream resume、terminal lookup 或显式用户决策；
- 只有 manifest、权威去重和 contract test 已证明 durably idempotent 的 command，才可按其独立策略重试；
- explicit HTTP error 也不自动等同于“未 dispatch”；v1 不做 POST 后自动 failover。

### 5. manifest 决定资格，客户端不得猜测

`config/hosted-dr-capabilities.json` 继续是 route/method/request class/DR/replay 的机器事实源。

- `safe-read`：可以在新请求开始前选择健康 runtime；
- `new-request-only`：可以在首次 POST 前因 primary non-ready 选择 DR；
- `fail-closed`：客户端不得发送 DR 写请求；
- 未登记 route/method：不得参与自动 DR；
- future durably-idempotent command：必须有 operation ID、权威去重、双 runtime contract test 和明确 replay policy。

当前常规 generation family 中已经登记为 `new-request-only` 的接口是首期客户端预检目标。Arena generation、部分 companion route 和其他 `fail-closed` operation 保持现状，不能为了“覆盖率”放宽。

### 6. 允许客户端获得最小公开路由元数据

客户端 preflight 需要知道公开 primary origin、公开 DR placement、probe path 和 capability policy。它们可以由 manifest 生成最小 client projection；这不构成 secret 泄露，因为公开 API origin 不是安全边界。

client projection：

- **MAY** 包含公开 HTTPS origin、probe path、routing mode、route/method eligibility 和非秘密 contract version；
- **MUST NOT** 包含 Provider key、数据库凭据、签名 secret、Access token、内部网络地址或高权限 binding；
- **MUST** 由生成器/validator 从机器 source of truth 产生，不能在多个客户端手写漂移；
- 服务端仍把客户端及其选择结果视为不可信，继续执行 CORS、auth、rate limit、capability guard 和 authority validation。

### 7. readiness 只用于新请求选择，不是业务正确性证明

Primary readiness 至少反映该 runtime 当前所需的 D1/Redis 依赖；DR readiness 至少反映该 capability 的 runtime、binding、secret 与数据库 transport 是否可用。readiness：

- 只证明“现在可尝试接收一个新请求”；
- 不证明后续 Provider 永远可用；
- 不证明已经 dispatch 的 operation 未执行；
- 不替代 route capability guard、鉴权、额度、内容安全和业务校验；
- 不允许通过缓存一个长时间健康结果绕过每个新 generation intent 的选择边界。

首期使用单次、短、有界的 primary probe；只有 primary non-ready 时才额外探测 DR。具体超时和错误投影由配套 spec 冻结。

### 8. 托管 stable control plane 保留为 optional-disabled

现有与 managed control plane 相关的 manifest 字段、selector seam、validator、测试、文档和演练证据，在维护代价低时保留，状态统一解释为 `optional-disabled` / `reference-only`：

- `controlPlane.provisioning=not-provisioned` 是接受的默认状态；
- 不创建 LB pool/monitor、DNS 切流、Worker router 或相关生产 secret；
- 默认 build/merge/release 不要求 production control-plane evidence；
- 可选代码继续通过低成本静态/单元契约测试时可以留在 CI；
- 若某段代码只制造持续维护、误报 blocker 或安全漂移而没有当前价值，可以在实施阶段单独删除，但必须先确认归档恢复点完整；
- 不得为了保留可选代码让 current path 出现双 source of truth。

### 9. 替换 production gate，而不是先放开再补实现

当前 production build 对未纳管 stable control plane fail closed。实施本决策时必须原子替换为 `client-preflight` gate：

- routing mode 显式且合法；
- primary/DR public origin 与 probe path 由 manifest 生成并通过 HTTPS/origin 校验；
- Hono CORS 允许受信 Web origin；
- Next DR artifact 和 capability guard 对 eligible route 可用；
- `fail-closed` operation 不被投影为 DR eligible；
- client bundle 不包含 secret/internal endpoint；
- selector/no-replay/ambiguous outcome 测试通过；
- production config 缺失或自相矛盾时继续 fail closed。

在这些替代门禁完成前，不得只删除原 build blocker。完成后，stable control plane 未 provisioned 不再是独立 blocker。

### 10. 未来重新引入付费 control plane 的门禁

Cloudflare Load Balancing、其他托管 LB、Worker reverse proxy 或等价 control plane 只有同时满足以下条件才可进入默认架构：

1. 新 accepted ADR 明确取代本决策的相应部分；
2. 有真实 incident、SLO、可用性、客户端版本碎片化或运营数据证明客户端 preflight 不足；
3. 决策者明确批准产品、月度/计量预算、告警和停用条件；
4. 对 SSE/长流、Provider 成本、origin retry 和 non-idempotent dispatch 语义完成供应商级验证；
5. 证明不会因代理 retry/failover 创建第二次 Provider 或第二份权威效果；
6. 有 preview/isolated drill、production change window、回滚 owner 和可审计证据；
7. client-preflight 路径有明确迁移/兼容策略，不能形成两个同时写入的无主控制面。

### 11. 可观察性与用户体验

客户端 selector 应记录低基数、无敏感内容的 decision telemetry，例如 routing mode、route family、selected placement、probe outcome、timeout class 和 decision latency。不得记录 prompt、生成正文、API key、Authorization、Cookie 或完整用户输入。

用户最终错误应区分：

- primary 与 DR 都不可用；
- capability 当前不允许 DR；
- 已 dispatch 后连接中断、结果状态未知；
- 明确的 Provider/额度/内容安全/鉴权错误。

不得把所有情况压成“网络错误，请重试”，从而诱导用户制造重复生成。

## 影响

### 正面影响

- 不需要新增 Cloudflare LB 固定开支；
- 保留 Hono/Next 双 runtime 和已有容灾投资；
- 生成前切换实现范围小、可测试、易回滚；
- 付费 control plane 从默认 blocker 降为未来可选增强；
- no-replay 边界比“失败后自动换后端”更清晰；
- 常规 generation 可以在 Hono 明确不健康时继续使用现有 Next DR。

### 代价与限制

- 每个新 generation intent 增加一次 primary readiness RTT；
- 客户端会获得公开 physical origin/placement 元数据；
- primary probe 刚通过后仍可能立刻故障，v1 不做 POST 后透明 failover；
- 未更新或第三方客户端不会自动获得新 selector；
- `fail-closed` capability 在 Hono 故障时仍会降级；
- 客户端、本地网络或 DNS 视角可能与其他用户不同，不能提供全局流量控制面的统一判断；
- 需要替换当前 build/activation gate，并补 selector 与端到端测试。

这些限制在当前成本、规模与维护能力下可以接受；未来若实际数据表明不可接受，再按第 10 节重新决策。

## 不采用的方案

- **立即购买 Cloudflare Load Balancing**：增加固定开支和运营面，当前没有足够运行数据证明必要。
- **自建 Worker reverse proxy 模拟 LB**：会让 SSE/长流重新经过额外代理，增加 CPU、流量、retry 和故障域，不是“免费版 LB”的等价替代。
- **DNS 手工切换作为每次故障机制**：传播和缓存不确定，操作依赖人工，不能解决已 dispatch 请求语义。
- **Hono POST 报错/断线后自动重发 Next**：无法证明第一次未执行，可能重复计费和权威写入。
- **删除全部 Next DR**：丢失已经验证的共享 adapter、D1 binding/Sessions、readiness、fault contract 和未来恢复基础。
- **让所有 capability 都 `new-request-only`**：忽略 Arena/Redis/secret/authority 差异，会把未验证路径伪装为可用容灾。
