# Desktop 公开库持久缓存与离线降级决策

状态：`accepted`（设计决策；待实现）
日期：2026-10-06
决策标识：`ADR-desktop-public-library-offline-cache`
接受依据：维护者要求 Desktop 在公开服务不可达时可浏览、搜索、筛选及使用已缓存内容，不因单纯年龄淘汰；恢复在线后更新到当前服务内容。本轮授权文档与决策，不授权代码、批量下载或生产修改。

- 2026-10-08 r2（K 系列审查收口）：§4 淘汰确认口径对齐规格 r3/r4——展示的是当前缓存总量而非预计删除量，降低预算不立即裁剪既有缓存；§3 撤回语义补齐进程内屏障与「摘要不复活旧正文」边界，机制细节以规格 DESK-CACHE-006/007 的最新口径（当前 r6）为准。

## 1. 选择：公开资料的持久只读快照

Desktop 新增公开库持久缓存，作为公开产品数据的**派生只读快照**，不成为第二个服务器，不与用户明确保存的本地库合并。它可在服务失联时维持部分可用，但不宣称当前公开性、完整覆盖或权威资格。

缓存正记录的“需要刷新”和“可以删除”分开：**不得仅因缓存时间长、未访问或 soft stale 而删除**（用户显式开启的满额淘汰只在新写入需要空间时按使用次序回收，见 §4）。旧 Web cache 的 24 小时 hard TTL/256 条淘汰策略不适用于此 Desktop 缓存。此项不自动改变 Web 缓存策略；先抽共同数据/查询语义，Web adapter 保持既有行为，后续要改变 Web 存储/离线启动另行评估。

这精确补充[本地库与所有权 ADR](./2026-08-22_022300_本地库与数据所有权决策.md)：缓存仍不是 device-owned 正式资产，也不授予 server-authoritative 权限，但项目可以为公开资料采用比旧缓存更保守的保留政策。

## 2. 范围：实际读过的摘要和正文，而非整站镜像

只捕获公开接口中校验成功的摘要页及按需成功读到的完整正文；不后台遍历整库、不自动抓取卡片内外链/图片/Web 包，不持久化任意 HTTP 回复。私有卡、收藏关系、账号头像/消息、鉴权元数据不进入可跨账号使用的公共缓存。

摘要可离线检索；**只有摘要不能声称正文可用**。正文缺失的记录可以展示，使用动作明确不可用。缓存包含哪些记录、正文是否齐全、上次确认时间均须可解释。查询/排序只针对本机已缓存子集，不借用曾经的线上 total 伪造完整库。

无须先保存到本地库才能临时使用可用快照；但希望长期拥有的卡片应显式“保存到本地库”，形成独立副本。缓存更新/撤回不能传播删除或覆盖该副本。

## 3. 在线恢复与更新

用户主动进入公开库时可以先显示快照，但同时尝试读取当前线上结果；请求成功后展示**当前线上查询**，不一直停留在离线数据。在线页活动期间的重连提示触发一次有界查询，去重和退避；关闭在线面不建立永久轮询。网络布尔标记不是服务器可达证明。

不将缓存与线上列表做无标识的 union；旧缓存中未出现在当前在线页的卡仍保留在“已缓存资料”视图，不能假装当前服务器正在返回它。新摘要与旧正文分开管理，不能用新元数据悄悄给旧正文盖上新版本/签名。

**缺页不等于删除。** 搜索、筛选、分页、排序变化或一次空页不授权清除其它缓存。只有对该卡的受控公开单卡读取明确返回业务不可用，或未来已核实的逐项撤回契约，才能使对应公开缓存失效。404 页面、鉴权故障、超时、429、5xx、schema/版本未知不构成批量删除证据。

已知撤回从公开缓存可见/可选集合移除并处理其缓存正文；保留最小失效信息防止旧请求把它复活。撤回证据自确认起在进程内生效，不依赖失效标记成功落盘；同卡日后恢复公开只恢复摘要面——撤回前正文不得仅凭重新到达的摘要复活，须由撤回确认之后发起的请求带回的新正文真实落盘后，缓存才重新交付该卡正文。已经明确保存的本地副本和当前生成的冻结输入不被远端撤回自动删除。离线时尚未得知撤回不可避免，不宣称客户端能实时执行远端删除。

## 4. 容量不是隐藏的淘汰器

缓存默认有字节预算，避免无提示的磁盘占用。预算由用户决定：可以设定具体值，也可以明确选择「不设上限」。默认满额策略是**暂停新增/增长写入并提示管理**，不删除旧卡片。当前线上读取与使用不因缓存写失败而失败。允许成功的新版本原子替换同卡旧版本；写入失败保留旧快照。

用户可以在设置中**显式开启**「满额时淘汰最久未使用」，默认关闭。开启后，只有在新写入需要空间时，才按最近使用时间回收最少量的公开快照。这是用户对自己磁盘的选择，不是隐藏的年龄淘汰：不因时间流逝或 soft stale 自行触发，不触及正式本地库副本、在途冻结输入或撤回失效信息；开启前说明影响。

不设上限时没有逻辑预算，但磁盘写满/IO 失败仍按故障处理：暂停增长、保留旧快照，不无限重试，也不改成自动删卡。

用户可以明确清理缓存、调整预算或暂停捕获。暂停模式下减少预算不自动抹掉已有资料；淘汰模式下把预算降到低于现有占用须经用户确认才生效，确认界面如实展示当前缓存占用与条目/完整正文数量——这些数字是缓存总量而非预计删除数；预算确认即生效，但实际回收只发生在后续写入确实需要空间时，不要求精确的预计删除量预检。清理前说明影响和正文数量；保留未清理的本地库、账号和秘密。预算是逻辑存储载荷上限，不声称等于 SQLite 文件/RSS/临时事务峰值，另以实测监控文件增长与磁盘失败。

## 5. 物理隔离与故障边界

首版选择 native 固定持久数据子目录中的独立 `public-read-cache.sqlite`，沿用已有 SQLite 依赖；不是 OS 临时缓存目录，不复用 Web AI session DB，也不加入正式 `library.sqlite` 的业务表。

独立库的理由是失败、生命周期和备份范围不同：缓存坏了应降级而不能阻止用户本地库启动；可重建公开资料不应膨胀现有完整库备份，也不应因正式库恢复而被回滚。只需一份缓存 schema/migration 与单进程串行写入，不新增数据库服务、通用仓储引擎或多设备同步。

D2 portable archive/备份不包含该缓存，也不得清理它；用户保存为正式本地卡后才进入原本备份范围。缓存自己的快照导出/整库预下载不是首版任务。

## 6. 权限与使用边界

普通单人/Direct 可以明确使用缓存正文；UI 显示快照来源和时效。来自公开库的历史 ID/原生标志、签名字段不代表当前可用授权。Strict、多人可执行引用、公开写入继续向服务器重新物化/验权；缓存结果不可替代该环节。

缓存是资料提供者，不是第二执行者；网络恢复、缓存刷新或保存失败不自动发 AI、不换执行位置、不改在途输入。收到的可执行 HTML/Web 包不因“已缓存”而获信任，仍受 D4 隔离。

## 7. 不采用的替代方案

不采用无限延长 HTTP freshness、把网络失败伪造成普通成功、将本地库当 cache、默认 TTL/LRU 正缓存淘汰（用户显式开启的满额淘汰见 §4，不属于此列）、任何 TTL 删除、分页扫描推断全库删除、自动镜像/同步/上传、自动离线计赞排队、共享账号缓存或大型事件/证据平台。

HTTP 缓存的 revalidation 和应用保存资料是不同层次；本设计明确产品快照用途，不绕过 no-store/private/受保护来源。依据及查阅日期见调研的一手资料表。实施仍遵守[复杂度预算](./2026-09-01_193200_平台复杂度预算与故障降级决策.md)。
