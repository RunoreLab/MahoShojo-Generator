# 本地库与数据所有权决策

状态：`accepted`
日期：2026-08-22
决策标识：`ADR-local-library-data-ownership`

## 背景

现有线上数据卡库受账号、卡槽、数据库与社区语义约束。大量实验卡、私人卡、草稿和只在当前设备使用的内容并不需要上传服务器。

项目已经使用 IndexedDB 保存 AI 会话、Challenge、公开卡缓存等数据，但这些存储分别是会话或缓存，不能直接承担“用户拥有且不可随意清理”的正式本地卡库。

Desktop/Mobile 还可以使用 SQLite、应用数据目录和系统安全存储，提供更稳定的本地体验。

## 决定

### 1. 新增正式【本地库】

本地库与线上库并列，是产品的一等数据源。

用户在创建、导入或保存数据卡时，应明确选择：

- 保存到本地库；
- 保存/上传到线上库；
- 同时保存本地副本并显式上传线上副本。

本地库不占线上卡槽。只有创建或更新线上卡记录时才执行线上卡槽和权限检查。

### 2. 数据所有权分层

统一采用三类数据所有权：

1. `device-owned`
   - 本地卡、本地草稿、本地会话、本地历史、Provider Profile 和设备设置。
2. `cloud-user-data`
   - 用户账号下的线上私有卡、公开卡、收藏、点赞、云端历史和个人资料。
3. `server-authoritative`
   - 官方签名、严格排位、多人共享状态、审核、举报、徽章和治理结果。

客户端不得把 `device-owned` 数据直接声明为 `server-authoritative`。

### 3. 存储位置与原生性正交

至少分别记录：

```text
storageLocation = local | cloud
provenance = official-signed | unsigned | signature-invalid
```

例如：

- 从线上下载且未修改的原生卡，可以是 `local + official-signed`；
- 本地 Direct 生成卡是 `local + unsigned`；
- 编辑了签名覆盖字段的原生卡是 `local + signature-invalid`。

服务器上传入口必须重新验证签名和 provenance，不相信客户端标签。

### 4. 各平台存储

- Web
  - 使用独立 IndexedDB 数据库，例如 `mahoshojo-local-library`；
  - 不复用 AI session DB、公开卡 cache 或 localStorage；
  - 请求 `navigator.storage.persist()`，展示持久化状态和空间估计；
  - 必须提供导出与恢复提示。
- Desktop/Mobile
  - 使用 SQLite 保存结构化数据；
  - 大型图片、附件和导出包放在应用数据目录或内容寻址文件区；
  - API Key 和秘密 header 不得放入普通 SQLite，使用 Secure Vault；
  - 本地 schema 必须有版本和迁移记录。

### 5. 首期不做自动双向同步

首期只提供显式操作：

- `保存到本地库`
- `上传副本到线上库`
- `下载副本到本地库`
- `导入`
- `导出`
- `备份/恢复`

不建立持续的 `localId <-> cloudId` 双向同步、自动合并、删除 tombstone 或冲突解决。需要同步时另立 ADR 和协议规格。

### 6. 上传是新的信任边界

任何本地卡上传到线上时，服务器必须重新执行：

- schema 与版本校验；
- 大小和资源限制；
- 权限、卡槽与账户状态检查；
- 内容安全和审核策略；
- 作者与系统字段归一化；
- 签名验证；
- 幂等和冲突处理。

官方 APP 来源不能绕过这些检查。

### 7. 可移植备份

本地库必须支持版本化导出。导出包不得默认包含：

- API Key；
- secret headers；
- Better Auth session；
- Legacy authkey；
- 设备密钥；
- 服务器凭据。

导入必须先展示摘要、版本、条目数、冲突策略和将要访问的文件；导入卡片不得自动创建 Provider 或发起网络请求。

### 8. 多人中的本地内容

Arena 多人 v1 允许房主本地保留完整内容，但房间共享状态只能保存安全投影或 host-local stub。普通成员不得把本地导入内容直接作为 Proposal 的可执行 payload。

这不影响本地库在单人模式中的完整自由度。

## 影响

### 正面影响

- 用户可以保存大量本地卡而不消耗 D1/R2 与线上卡槽。
- APP 在未登录、断网和弱网环境下仍可工作。
- 私人内容无需上传项目服务器。
- 本地和云端的信任、同步和计费语义更清晰。
- Web 现有 IndexedDB 经验可以复用，但不会污染缓存和会话职责。

### 代价

- 用户需要理解本地库不自动跨设备。
- Web 本地数据仍可能因用户清除站点数据而丢失。
- 需要导入导出、迁移和备份测试。
- 本地与线上同时存在时，需要清晰展示来源和副本关系。

## 不采用的方案

- **把本地库放进公开卡缓存**：缓存允许淘汰，本地库是用户持久数据。
- **把全部 D1 schema 复制到设备**：账户、审核、排位、PVP 和治理表没有本地等价的全局语义。
- **首期自动同步**：会立即引入冲突、删除、签名、卡槽和审核状态的复杂组合。
