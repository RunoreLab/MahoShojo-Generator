## 1. 精确后继关系与非目标

本 ADR 接续 [DESK-098 的服务器版本化协议](./2026-10-10_161000_Hosted连续故事版本化创建协议.md)和 [DESK-099 的耐久候选存储](../specs/2026-09-30_160000_Desktop客户端实施规格.md#desk-099-hosted-连续故事非秘密耐久候选存储2026-10-10)。它只把 DESK-095 的“仅普通单次”限制扩展到同一 `arena_hosted_stream` 中明确列出的 `create-story-stream`、`reconcile-story` 两个 operation；其他 command/ACL、旧 C1/C2/C3 权限和 shared C0 状态机保持。

本片 **MUST NOT** 接入 `/battle`、`/arena` 的 Hosted 故事 owner/UI 或开放其页面 capability，不新增 active discard、服务器故事库、额外模型调用、自动摘要、分支/重写/删除、Strict/多人、D4 执行或发布入口。旧 Web 无 story header 的 DTO、包装/hash、保存和角色语义不变。历史 DESK-098/099 的完成范围与验证记录仍按当时切片理解，不据本次批准倒填历史验收。

## 2. 同一库、同一槽与 durable create-once

### 2.1 Schema 7 的唯一持久变化

`library.sqlite` **MUST** 保留 `MIGRATION_6` 原字节，只通过 `MIGRATION_7` 给原 `arena_story_pending` 增加可空 `create_claim TEXT`。不新增 jobs/墓碑表、数据库、产品槽或秘密槽。生产初始化中的 Arena transport 与 LocalLibrary/binder **MUST** 共享同一个 `Arc<StoryStore>`，不得另开库或另建一套 admission/Flight registry。

`create_claim` **MUST** 是 Native-only 闭合对象：

- `version: 1`，`attemptId` 为 Native 随机的既有 instance-token 形状
- `storyProtocolVersion: 'arena-story-v1'`
- `inputDigest: 'sha256:<64hex>'`，与所在 manifest 的原件摘要严格相同
- `clientBodyHash: '<64hex>'`，为下节定义的非秘密创建意图摘要
- `funding: { mode: 'system' | 'preset', providerId, modelId, generationOverrides? }`，来自同一次受信 resolver 的归一化非秘密投影；覆盖参数限既有 maxOutputTokens/temperature/thinking 合同
- `observedGeneration: null | { generationId, serverPayloadHash: null | '<64hex>' }`，只由 Native 接受原请求的受检响应或 lookup 后补写；已知 generation/hash 不得改绑

product/request/actor/session/operation 身份从所在 active manifest 取得并一起重验，不在 claim 另存可漂移副本。只读 `PendingSnapshot` **MAY** 返回 `createClaim`；renderer manifest、上传和 command **MUST NOT** 提供 claim 写入/清除/重置入口，也不得提供 `notSent`、`retryAllowed` 或 `modelCompletedProof`。

每行 `byteLength(metadata) + byteLength(create_claim or '')` **MUST** 合计不超过 65,536 bytes，仍最多两条 active 加两条 upload。未发布 upload 的 claim **MUST** 为 NULL；新 active revision **MUST** 在同一发布事务从原 active 复制 Native claim，不能通过 renderer 携带。普通进程重启保留 claim；备份恢复继续加 restored fence，不能清 claim 获得重创权限。成功原子保存/receipt 事务释放原 pending 时随之释放 claim；本片不承诺跨 pending 生命周期或删除后的永久请求注册表。

历史 v1–v6 backup 校验与恢复 **MUST** 保持兼容。读取/audit v6 数据库不得 SELECT 尚不存在的新列；表存在性按其原 schema6 引入版本判断，新列另作 v7 条件检查，不能把合法 v6 pending 表误判为不应存在。恢复后迁移、v7 claim 保留及 restored fence 分别验收。

### 2.2 一次 permit 与保守失败边界

只有 claim 首次耐久写入成功的原进程 **MAY** 获得不可 Clone、单次消费的 Native create permit；permit 绑定 product/request/actor/inputDigest/attemptId，不绑定会随 revision 换代的 token。重启后已有 claim 不再发 permit。输入、资金和可完成的 preflight **SHOULD** 在 claim 前验证；跨 POST 边界前仍 **MUST** 在同一 admission 中重验 active row/claim/身份并消费 permit，随后才置 dispatched。

claim 表示“可能已派发”，不是完成证明。claim 后即使在 POST 前退出，或之后遇到 secret/网络前置失败，也 **MUST** 仅用原 request lookup/resume；404、回放不完整、能力撤回和 renderer 的“未派发”声明 **MUST NOT** 清 claim、补发 permit 或自动重 POST。该保守边界可能留下尚未生成但仍占槽的作品，本片无 active discard，不能静默覆盖或丢弃它。未来 UI **MUST** 保留作品并清楚说明状态；显式放弃与释放槽须另片决定和实现，不能从本 ADR 推导其权限。

## 3. 同 product 的统一准入与锁序

StoryStore/LocalLibrary **MUST** 使用每 product 短 admission 锁；生产 `seal_arena_story_pending` binder 在同一 admission 中读取唯一 `ArenaState` Flight 真相，不复制其状态作为另一套 registry。

- 普通 `create-stream`、`create-json` 和新 story create **MUST** 经过相同门禁。只要存在 active pending，普通 create 无论 `replaceRequestId`、Flight terminal 或 model completed 均拒绝，原秘密槽不被覆盖
- story create **MUST** 匹配 exact active key、actor、inputDigest，且非 restored、无 save attempt/冻结 commit、model 未 completed、claim 缺省
- 能创建或重绑 Flight 的 lookup restore/resume/reconcile 路径 **MUST** 受原 product/request/actor 围栏约束；同一原任务的合法控制保持可达，陌生任务不能借 lookup 占槽或换秘密
- 首次 seal 与 prepare **MUST** 串行。普通 Flight 已 prepare 且未 terminal 时拒绝首次 seal；同 requestId 的普通 Flight 不能冒认 story Flight。无 active pending 时，仅无 Flight，或明确 terminal 且 request 不同的既有 Flight（含成功保存并释放 pending 的旧 story），允许首次 story seal
- 后续 exact story revision **MAY** seal 并原样传递 claim；Native Flight **MUST** 有明确 Story purpose/claim 关联。模型 terminal 不代表角色或本地保存已经解决，也不释放 pending 占槽

锁序固定为 admission → 既有 stages/attempts/inputs → connection。Flight 查询在同 admission 内单独短段完成并释放，再进入 connection；不得持 connection 调用 `ArenaState::prepare`。token→product 的预读先释放 connection，再取 admission，并在正式操作内重读复核；原件、snapshot 与真正 claim 的受检读取不得依赖分离 describe/read 形成 TOCTOU。网络 await **MUST NOT** 持 admission、SQLite connection、Flight 或维护锁。

## 4. 窄请求、三个摘要与原始 JSON

单一请求合同为 [`desktop-arena-story-transport`](../../packages/contracts/src/desktop-arena-story-transport.ts)，pending 合同仍为 [`desktop-arena-story`](../../packages/contracts/src/desktop-arena-story.ts)。

`create-story-stream` 只接受 operation/product/requestId/actor/pendingRevision/inputDigest/clientBodyHash、互斥的 systemConfig/presetConfig 和可选 replaceRequestId。它 **MUST NOT** 接受 renderer body、URL、headers、secretRef、ProviderKey 或 internalGuidance；body 只取 exact sealed input。pendingRevision 是当前读取断言，不进入创建意图摘要，后续 revision 不改变原创建意图。

三个摘要的作用 **MUST** 分开：

1. `inputDigest`：原 input JSON 的 UTF-8 bytes SHA-256，带 `sha256:`；Native 重算并验证 manifest/session/action/index/source/request 关系
2. `clientBodyHash`：`arena-story-v1`、inputDigest 与冻结 funding 的非秘密意图摘要，无前缀；不含 Key/Cookie/token、最终 POST wrapper 或服务端摘要
3. `serverPayloadHash`：Hono 原 semantic payload hash，仅从原 generation 的受检响应/lookup 接受；不得以任一本地摘要替代

旧单次 bodyHash 机制不适用于跨 TS/Rust 的故事意图。新 clientBodyHash **MUST** 使用独立 binary v1 编码：固定 ASCII `desktop-arena-story-client-body-v1\0`、`arena-story-v1\0`，inputDigest 的 32 bytes，funding tag u8，provider/model 的 u32BE UTF-8 byte length 与原字节，override mask，随后按位序编码 tokens u32BE、temperature IEEE754 binary64 BE（-0 归 0）、thinking mode/effort 闭合枚举。空 overrides 归缺省，缺省 funding 归 system/default；catalog alias 与模型选择仍沿原 resolver。TS/Rust **MUST** 消费[同一 16 例金样](../../packages/contracts/fixtures/desktop-story-client-body-intent.json)，Native 重算并比对 renderer 声明。这不是通用 JSON canonicalization，不改变 DESK-060/061、本地库摘要、旧 bodyHash 或服务端 semantic hash。

业务 JSON 顶层成员 **MUST** 保留 RawValue，固定 wrapper 只额外注入受信 customProvider；不得经 Value 解析再 `.json()` 重序列化原业务内容，也不得递归删除卡片中与秘密词同名的业务字段。原输入与角色来源中的孤立 UTF-16 JSON 转义 **MUST** 保真；此处不声称既有 SSE Value 投影已经支持所有孤立转义。

最终发送 UTF-8 body 连同 funding/Key/封套 **MUST** 完整计入既有 12 MiB 请求门禁；超限保留原件、POST=0，不截文或自动改用另一模型。服务端 wrapper 与展开请求各自的 DESK-098 门禁继续有效；32 角色、4 MiB 正文/推理、16 MiB 角色响应和 128/384 MiB 存储预算均不扩容。

## 5. 固定目标、控制与故事角色对账

新建固定走 DESK-095 Hono origin 的 `/api/arena/session/generate-next`，复用原 actor/funding、SSE parser、Channel、cursor、分项预算与 late-response 防护。新建 **MUST** 在 dispatch 前检查独立 story readiness，并校验新创建响应的 story header echo；原 lookup/status/resume/stop 不要求 story echo，不因能力撤回被锁住。不能 fallback 到 Next/DR/Direct，也不重写 C0。

`reconcile-story` 仅接受 operation/product/requestId/actor/pendingRevision/inputDigest/generationId；没有 renderer combatants 或 completed 证明。Native **MUST** 从同一 sealed input 的 `chapterContext.workingCombatants` 取 RawValue，沿 DESK-097 原 actor 与固定 Next runner 进行角色对账，不能把它当作生成 fallback。

新角色 POST **MUST** 要求非 restored、无 save attempt/冻结 commit、role unresolved、manifest.modelCompleted，并通过 fresh 原 request lookup 证明 generation 相同且服务端 completed。已采纳 roleResponse 只回读原件，不能再 POST。明确 HTTP 失败由后继 owner 使用既有 old-roles+reason 投影；网络未知、畸形响应或晚拒绝仍为 unresolved，不能伪装 accepted 或自动关闭保存门禁。本片不把尚未接线的 owner 行为写成已交付 UI，也不改旧 Web 语义。

## 6. Public pointer v4 与旧 owner 隔离

恢复指针 **MUST** 新增独立判别分支 `version: 4, purpose: 'story'`，保留原 product/actor/requestId/bodyHash、可选 generationId/cursor、state/updatedAt 与 battleMode；固定 delivery=stream、format=markdown、原 SSE protocolVersion，并增加 storyProtocolVersion/sessionId/operationId/inputDigest。其 bodyHash 只承载上述 clientBodyHash。

pointer **MUST NOT** 存 funding、pendingRevision 或 writeOptions；恢复从原 product 的 Native pending 读取当前 exact key 和冻结选项。仍只有原两个 public keys，序列化上限仍为 16,384 code units，不含秘密。v1/v2/v3 不升级成故事权限，普通单次 owner 不能接管或清除 v4 作品。public pointer 丢失时 **MAY** 从原 product 枚举 Native pending，generation/cursor 从 null 查找/回放，不能据指针缺失重新 create。两页故事 owner 与 Hosted 待处理作品导出入口接线留后继。

## 7. 窄 telemetry 原件与保存覆盖

pending **MAY** 新增一个 `telemetry` part，只接受 [`DesktopArenaHostedSuccessTelemetrySchema`](../../packages/contracts/src/desktop-arena-hosted.ts) 的闭合成功分支：可选 version:1、aiModel、usage、narrativeHistoryReadCount；usage 沿原数字/null 与 completionTokensIncludesReasoning 布尔域。不得接受 errorClass 分支、改用更窄 CompanionUsage/ModelId，或增加任意 metadata 口袋。

独立 part 沿原 `eventWireBytes=25,231,360 bytes`，aiModel 不额外限制为 64 KiB、200 字或 256 字；仍计入 active/upload 的原 128/384 MiB 逻辑预算。manifest 保留旧 kind 相对顺序和全部旧 parts，只封存完成时选定的一份 telemetry，不逐事件累计。

共享 `projectHostedStoryPendingContent` **MUST** 投影到既有 aiModel/aiUsage/narrativeHistoryReadCount，Native 同步验证 shape、digest、backup audit 与 content coverage，数字/null/布尔不得丢失。header 与 telemetry 同时带 readCount 时 **MUST** 相等；冲突拒绝冻结并保留两份原件，仅一方存在时投影该方。成功释放 pending 前仍须证明必要内容已经进入最终记录，不以新增 part 放宽 DESK-099 的保存覆盖和未知只查 receipt 规则。
