# Arena Room 部署边界与实时权威决策

状态：`accepted + 部分 superseded`
日期：2026-08-22
决策标识：`ADR-arena-room-deployment-realtime-authority`
新权威决策补充修订：`docs\decisions\2026-08-25_104400_ArenaRoom运行时可移植与HonoRedis首发决策.md`

## 背景

Arena 多人协作 v1 的产品目标一直是“把多人能力整合进现有竞技场”，而不是建立第二套 Arena。与此同时，多人房间需要 WebSocket、Durable Object、Hibernation、alarm、房间局部持久化、低成本 fanout 与独立资源预算；目标平台架构又已经把 Hosted/authoritative Arena generation 迁向独立的 `apps/api` / Hono。

因此需要明确区分两个容易混淆的概念：

- **产品/页面边界**：是否另建一套 Multiplayer Arena；
- **运行时/部署边界**：实时房间协调是否与 Web/OpenNext、Hono generation 使用同一个部署单元。

本 ADR 冻结第二个问题，并补齐独立部署后必须承担的协议、幂等、恢复和安全责任。

## 决定

### 1. 产品继续集成，实时协调独立部署

Arena 多人仍然使用现有 `/arena` 页面、配置组件、BattleResult 与既有生成语义，不新建独立 Multiplayer Arena 产品。

实时协调进入独立部署单元：

```text
apps/arena-room
  -> Worker ingress / room ticket verification
  -> ArenaRoom Durable Object
  -> Hibernation WebSocket
  -> room-local SQLite storage
  -> alarm scheduler
  -> room broadcast / reconnect
```

这是一条运行时和部署边界，不是新的产品边界。

Monorepo 完成前可临时使用 `workers/arena-room` 或等价目录；进入目标结构后统一为 `apps/arena-room`。

### 2. 一房间一 Durable Object

`ArenaRoom Durable Object = one logical Arena multiplayer room`。

不得把所有房间放入全局单一 DO，也不以用户作为主要协调原子。

DO 只权威维护单房间事实：

- room metadata / lifecycle；
- user-level membership 与 role；
- connection-level presence；
- Room Shared Config；
- revision；
- unresolved Proposal；
- generation reservation / mirror state；
- reconnect control cursor；
- cleanup deadlines。

D1 只承担跨房间查询所需的目录/索引事实。

### 3. 明确三个数据与执行平面

```text
Client / Arena UI plane
  - local working copy
  - host-local full content
  - UI state

Room coordination plane
  - safe Shared Config projection
  - Proposal / revision
  - membership / presence
  - generation mirror
  - no Provider secret
  - no full host-local payload

Generation plane
  - authoritative Arena generation
  - existing generation persistence / R2
  - receives only the generation input it actually needs
  - publishes safe result/delta projection back to Room
```

“房主本地内容留在设备”的规范含义是：

- 完整 host-local payload **不得进入 Room DTO、DO、D1、房间日志或成员广播**；
- authoritative generation 若确实需要该内容，可以由房主客户端按既有安全生成契约将所需 generation payload **直接临时发送给 generation service**；
- 该传输不得被解释为 Room 可以持久化、复制或广播完整本地内容；
- generation service 对敏感输入沿用既有日志脱敏、生命周期和持久化规则。

Provider/API credential 同理：不得进入 Room plane。若现有 Hosted generation 仍支持用户 Provider credential，只能沿既有 generation contract 进入 generation service，不得通过 Room 中转。

### 4. Worker 调 Room 使用 Service Binding / RPC

Cloudflare Worker 调用 `apps/arena-room` 时，优先使用 Service Binding + typed RPC：

```text
apps/web
  -> Service Binding / RPC
  -> apps/arena-room
  -> ArenaRoom DO
```

公共 HTTP 不应仅为了 Worker-to-Worker 内部调用而暴露。

调用方必须 `await` 需要完成的 RPC；不得 fire-and-forget 后假定下游继续运行。

### 5. Hono 到 Room 使用独立 Generation Bridge

`apps/api` / Hono 是 Cloudflare Workers 之外的 Node 服务，不能把 Service Binding 当作其内部调用机制。

因此定义 `GenerationBridge`：

```text
apps/api / Hono
  -> authenticated generation-scoped bridge
  -> apps/arena-room
  -> target ArenaRoom DO
```

要求：

- bridge 绑定 `roomId + generationRequestId + generationId/attempt + exp`；
- 每个 batch 带单调 `batchSeq`；
- 重复 batch 必须可幂等丢弃；
- 不允许仅凭公开 `roomId` 发布事件；
- bridge credential 不得进入浏览器或房间 snapshot；
- 不按 token 建立一次 HTTP/DO 调用。

首选基线是 **generation-scoped authenticated WebSocket publisher**：生成活跃期间保持一个发布连接，将批量 delta 发送给 Room；生成结束立即关闭。这样不会把 50–100ms 的每个 batch 变成独立跨公网 HTTP 握手。

如果 PoC 证明 batched HTTPS internal endpoint 在成本、延迟和可靠性上更合适，可以替换 publisher transport，但必须保持同一 `GenerationBridge` 契约、幂等和鉴权语义。

### 6. 房主浏览器不是流式中继

房主浏览器可以发起“开始生成”意图，也可以提交 generation service 所需的 host-local payload；但浏览器不得成为：

```text
AI stream -> host browser -> room
```

的唯一中继。

generation service 一旦接受多人 generation：

- AI 执行和 room publisher 生命周期不依赖房主 Arena WebSocket；
- 房主刷新、切换网络或关闭单个标签页不得自动导致其他成员失去已经开始的权威 generation；
- host 与 member 都从 Room view 获得同一份安全投影；
- authoritative final result 仍以既有 generation persistence / R2 为准。

是否允许用户显式“停止生成”继续由 host-only command 控制，并必须具备服务端授权和幂等语义。

### 7. Generation start 必须幂等

开始生成不是普通按钮事件，而是状态转换：

```text
idle
  -> starting(generationRequestId, frozenRevision, snapshotDigest)
  -> running(generationId)
  -> completed | failed | cancelled
```

要求：

- `generationRequestId` 在一次用户意图内稳定；
- DO 在开始前校验 host、当前 revision、room generation state；
- frozen shared config、participant snapshot、`collaborativeInfluence` 与引用版本在 reservation 时确定；
- 同一 `generationRequestId` 的浏览器重试、网络重试或 API 重试不得创建第二次权威 generation；
- generation service 也必须以该 idempotency key 去重；
- 完成/失败消息必须匹配当前 generation attempt，旧 attempt 不得覆盖新状态。

### 8. Proposal stale conflict 不能只携带 baseRevision

`baseRevision` 只能说明 Proposal 基于哪个房间版本，不能单独重建 BASE。

每个 typed semantic change 必须携带足以验证其 BASE 的 typed precondition / `expectedBase`，例如：

- 期望当前 guidance 等于某规范化值；
- 期望对象存在且引用版本匹配；
- 期望对象不存在；
- 期望 team assignment / mode 等于 Proposal 创建时的值。

服务端/DO 必须用：

```text
expectedBase(change)
vs currentSemanticValue(change.target)
```

判断同字段冲突。

不得为了 stale conflict 保存无限完整 revision 历史；可以保留有限诊断历史，但不能把它作为正确性的唯一来源。

接受所选 changes、dependency/atomic group 校验、Shared Config 更新、Proposal 状态更新和 `revision++` 必须在单房间原子状态转换中完成。

### 9. 在线 DataCard 引用必须版本化

Room Shared Config 和 Proposal 不得只保存“永远解析最新版”的 `id`。

网络发布后的引用至少包含：

```ts
type DataCardRef = {
  id: string;
  kind: 'character' | 'scenario' | 'material';
  versionToken: string;
};
```

`versionToken` 是服务器可验证的不透明版本标识，可以由 canonical `updatedAt`、revision、content digest 或未来版本系统生成。

接受 Proposal、房主 publish 和 generation reservation 时必须验证该 token：

- token 仍匹配：允许继续；
- 对象已更新/删除/权限变化：返回显式 stale/reference-changed 错误；
- 不得静默解析到新版内容而保持 room revision 不变。

### 10. Reconnect 使用 durable control cursor；story delta 是临时传输

Hibernation 会清空 DO 内存并重新运行 constructor，因此恢复协议不能依赖只存在内存中的全局 `seq`。

控制面采用：

```ts
type RoomCursor = {
  roomEpoch: string;
  seq: number;
};
```

要求：

- `roomEpoch` 与 durable room state 一起持久化；
- `seq` 只为会改变/描述 durable room state 的 control event 前进，并与相应状态写入一起提交；
- reconnect 若 epoch 不同或 replay window 不足，直接返回最新 snapshot；
- presence 可以从当前 WebSocket attachments / membership 重新构建，不要求无限 replay。

流式正文采用独立 cursor：

```text
generationId + chunkSeq
```

`story.delta` 是低延迟展示事件，不是最终权威存储。

- Room 可以保留有界内存 replay window；
- 不要求为了断线重播而逐 chunk 持久化；
- gap 无法恢复时，客户端转入 resync 状态；
- generation 完成后从权威 generation record / R2 获取完整最终结果。

### 11. 多个 deadline 共用一个 DO alarm scheduler

每个 Durable Object 同时只能设置一个 alarm。

房间可以存在多个逻辑 deadline，例如：

- `hostOfflineDeadline`；
- `roomIdleDeadline`；
- generation recovery / cleanup deadline（若未来需要）。

必须将逻辑 deadline 存储在 room state 中，并始终：

```text
setAlarm(min(active deadlines))
```

`alarm()`：

1. 重新读取 durable state；
2. 处理所有已经到期的条件；
3. 对 destructive cleanup 再次验证；
4. 计算剩余最早 deadline；
5. 重新 `setAlarm(nextDeadline)`。

Alarm 为 at-least-once；所有处理必须幂等。不能依赖 constructor 无条件重设 alarm。

### 12. D1 room directory 是派生索引，不是真相源

D1 `arena_multiplayer_rooms` 只用于：

- public/unlisted room discovery metadata；
- host 房间查询；
- 低频跨房间运维。

DO 才是单房间 lifecycle 的最终权威。

创建/销毁跨 DO 与 D1 不能获得分布式原子事务，因此：

- join 最终必须由目标 DO 验证房间状态；
- DO 已关闭时，D1 残留行不得使房间复活；
- `destroyRoom()` 先把 room durable state 进入 terminal/closed，再 best-effort 删除 D1 directory；
- directory 更新/删除必须幂等并可重试；
- 应提供低频 reconciliation 清理 orphan directory row，而不是实时轮询全部房间。

### 13. Membership 与 connection 分离

Membership 以用户为单位，presence 以连接为单位。

```text
member(userId, role)
  -> connection A
  -> connection B
```

- 多标签页/多设备不能重复计算成多个成员；
- 每个 WebSocket 使用独立 `connectionId`，并把最小 metadata 放入 WebSocket attachment；
- socket close 只影响 connection presence；
- 普通成员“退出房间”是显式 user-level command；
- 房主“显式退出/关闭房间”是 room-level close command；
- 页面 unload / 单个 socket close 不得隐式模拟上述两个命令。

kick 必须失效 user-level membership 并关闭该用户当前连接；旧 ticket 即使尚未到期，重连时也必须由 DO membership 校验拒绝。

### 14. WebSocket 鉴权区分浏览器与 Installed Client

所有连接必须使用 WSS/HTTPS 生产入口和短期 room ticket。

room ticket 至少绑定：

```text
roomId
userId
capability/role hint
exp
jti or equivalent replay identifier
protocolVersion
```

浏览器客户端：

- upgrade 时严格校验显式 Origin allowlist；
- 不使用 wildcard/substr Origin 判断；
- ticket endpoint 本身遵守现有 session/CSRF 安全边界。

Desktop/Mobile 或其他非浏览器客户端：

- `Origin` 可以作为诊断信号，但不能作为信任根；
- 权威鉴权依赖短期签名 ticket、membership 和 message-level authorization；
- 服务端不得因为客户端声称“官方 APP”而放宽权限。

所有 WS message：

- schema allowlist；
- capability check；
- message bytes / rate limit；
- oversized 使用适当的 WebSocket policy；
- 不可信正文不得提升到 system authority；
- 日志只记录必要 metadata，不记录 ticket、secret、完整 Proposal 正文或 generation 内容。

### 15. Room ID 与 DO ID 分离

对外 `roomId` 必须是服务端生成的高熵 opaque identifier，不得直接暴露 Durable Object internal ID。

只有在鉴权和 room id 基本格式检查后才解析目标 DO，以降低 object spray。

Public room list 可以显示独立的人类可读 title；不得把低熵 title/code 直接作为唯一 DO trust boundary。

### 16. 独立部署必须承担 wire compatibility

`apps/web`、`apps/arena-room` 与 `apps/api` 独立发布后会出现 version skew，因此 protocol 版本必须成为正式 contract。

至少冻结：

```text
protocolVersion
room snapshot schemaVersion
GenerationBridge version
supported peer version range
```

部署遵循 expand/contract：

1. 先部署下游/被调用方的向后兼容扩展；
2. 再部署调用方使用新字段/方法；
3. 观察稳定后再删除旧协议；
4. destructive DO storage migration 单独门禁，不与普通 Worker rollback 混为一谈。

共享 contract 改动必须有 old/new fixture compatibility test。

### 17. Backpressure 与大小上限

除现有成员数、Proposal 数等限制外，必须有：

- WebSocket inbound frame/message bytes；
- outbound batch bytes；
- per-connection / per-user message rate；
- pending outbound/backpressure budget；
- generation publisher batch rate/bytes。

推荐以 64 KiB 级别作为普通控制消息的安全起始上限，再根据 Shared Config 实测调低或拆包；具体生产常量必须在压测后冻结。

slow consumer 不能导致 Room 无限缓存：

- 优先丢弃可恢复/临时的 story delta；
- control snapshot/terminal event 必须能重新同步；
- final report 从 authoritative generation storage 恢复。

## 影响

### 正面影响

- Arena 产品保持一个页面和一套生成语义。
- Web、Room realtime 与 Hono generation 可以独立扩容、部署、回滚和观察。
- OpenNext compatibility date 不再限制 Room 使用现代 Durable Object 能力。
- idle room 可利用 Hibernation 降低 duration 成本。
- host 浏览器故障不会成为多人 generation 的单点中继故障。
- Proposal stale、generation retry 和 reconnect 都有可测试的确定语义。
- D1 不承担实时状态，减少 rows read/write。
- PVP 若后续复用，只复用 transport/lifecycle 基础设施，不污染 Arena 业务契约。

### 代价

- 需要维护版本化协议和跨部署单元 contract test。
- Hono 与 Room 之间需要额外的安全 publisher bridge。
- DO 与 D1 之间是最终一致，需要 repair/reconciliation。
- generation start、Proposal accept 和 reconnect 状态机比单机 UI 更严格。
- 需要针对 slow consumer、重试和 version skew 做故障注入测试。

## 不采用的方案

- **另建 Multiplayer Arena 页面/产品**：复制现有 Arena UI 与生成语义，增加长期漂移。
- **把 Room DO 混入 OpenNext Worker**：耦合 compatibility date、实时生命周期、部署和资源预算。
- **把多人全部放到 Hono + Redis/WebSocket**：放弃 DO 单房间强一致、Hibernation 与边缘 WebSocket 优势。
- **让房主浏览器转发 AI stream**：浏览器刷新/后台/断网会成为房间级单点故障。
- **每 token 一个 HTTP/DO publish**：增加上下文切换、请求和 CPU 成本。
- **把 D1 当实时 room state**：增加扫描、写入和协调冲突。
- **保存无限 event/revision history**：不符合 v1 成本目标；snapshot + typed precondition + bounded replay 足够。
- **首期引入 CRDT/PartyServer/复杂 pub-sub**：当前 Proposal 模型不需要。

## 实施门禁

进入 Phase B/Room Worker 实现前必须至少具备：

1. Room DTO / sensitive-field negative fixture。
2. typed Proposal + `expectedBase` conflict fixture。
3. versioned `DataCardRef` fixture。
4. `roomEpoch + seq` snapshot/reconnect fixture。
5. generation start idempotency state-machine test。
6. single-alarm scheduler unit test。
7. multi-tab membership/presence test。
8. GenerationBridge authentication/replay test。
9. D1 orphan directory recovery test。
10. old/new protocol compatibility fixture。
11. host refresh during generation fault-injection test。
12. oversized/flood/slow-consumer test。
