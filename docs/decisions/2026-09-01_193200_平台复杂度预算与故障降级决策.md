# 平台复杂度预算与故障降级决策

状态：`accepted`  
日期：2026-09-01  
决策标识：`ADR-platform-complexity-budget-and-graceful-degradation`

## 1. 背景

自 `cc217a0c711650a7501d771d7fb2aa1292fa21c9` 起的平台重整，已经完成 Hono 独立运行时、Monorepo 应用边界、可恢复 Arena 长生成、Redis 协调、D1/R2 持久化、多人 Room 等有实际价值的能力。

与此同时，平台也逐步引入了一批面向“大型商业平台 / 高合规环境”的证明型机制：source digest、源码 SHA 固定、机器化 evidence registry、迁移 inventory、GMR slice 状态机、独立复审 manifest、release gate、hardening evidence、严格 terminal finalization、完整角色 revision reconciliation 等。

这些机制中有一部分已经出现反作用：

- 低价值安全属性被升级成主业务成功的强前置条件；
- 一个行为变化需要同步源码、机器事实、证据文档、摘要和验证器；
- 为维护 gate / evidence 本身持续新增测试和兼容代码；
- 已经成功的 AI 生成可能因归档或 provenance 失败而被重新判定为失败；
- Arena 战报已经成功生成，但角色更新可能因 `baseRevisionHash` / native authority 差异整体 `409`；
- 发布与多人激活受到“证明流程是否闭合”的约束，而不是受到真实产品 blocker 的约束。

MahoShojo-Generator 是公开源码、资源有限、维护者规模较小的开源项目。项目当前优先级是：**用户主流程可靠、代码容易维护、真实高风险边界安全，而不是最大化形式化证明和防御纵深。**

本 ADR 因此重新冻结平台的复杂度预算、失败语义和发布原则。它覆盖与本决策冲突的旧平台门禁、证据链和 fail-closed 口径；旧文档仍可作为历史背景，但不得要求重新引入本 ADR 已明确撤回的证明型机制。

## 2. 总原则

### 2.1 复杂度必须购买真实风险降低或用户价值

新增持久机制至少应满足一项：

1. 防止账户、权限、秘密、付费资源或公开数据受到实质损害；
2. 防止不可逆数据破坏或明显的重复 AI Provider 调用 / 重复计费；
3. 解决已经出现或高概率出现、且用户可感知的可靠性问题；
4. 显著降低未来维护成本。

仅用于“证明某次审查发生过”“证明源码没有变化”“证明某份证据仍和历史完全一致”的机制，默认不满足复杂度预算。

### 2.2 行为测试优先于源码形态证明

用户可见契约由运行行为、类型 / schema 和必要的集成测试保护。

默认不得把以下内容长期作为 merge / release blocker：

- 任意业务源码文件的固定 SHA-256；
- 排除少量文件后的全仓 Git tree / source digest；
- 某个历史 reviewed commit 与当前 release 的源码树等价证明；
- 审计 Markdown 中固定 marker 是否存在；
- 某一测试必须由某一 evidence manifest 精确登记；
- 迁移期间生成的大型 snapshot inventory 是否仍与旧基线逐项一致。

Git 自身已经提供 commit identity 和历史；CI 应验证产品行为，而不是再造一套平行的源码身份证明系统。

### 2.3 只在因果边界上 fail closed

`fail closed` 仅用于失败后继续执行会显著增加实际风险的边界，包括：

- 身份认证与授权；
- Admin / 管理操作；
- secret、签名密钥、Provider credential；
- 严格排位、权威评分和公开治理写入；
- 会造成不可逆数据覆盖 / 删除的写操作；
- 已经 dispatch 的非幂等 AI Provider 请求发生结果不确定时，禁止自动重复 dispatch；
- 多人房间中会让普通成员获得 host / server 权威权限的操作；
- 明显资源滥用、无限队列、无界 payload / WebSocket backlog。

低风险、可降级或仅影响附加能力的失败，应优先 `fail soft` / `graceful degradation`。

### 2.4 主业务成功与附加持久化成功分离

如果用户已经得到完整、有效的 AI 输出，则默认视为**生成成功**。

Redis / D1 / R2 / telemetry / archive / replay / provenance 等附加能力失败时：

- 可以降低断线恢复、历史归档、跨设备读取或审计能力；
- 可以向用户明确提示“生成已完成，但保存 / 恢复能力暂不可用”；
- 可以在安全的前提下重试持久化；
- **不得仅因为附加持久化失败，把已经成功且已交付给用户的 AI 结果重新定义为生成失败。**

例外仅限：该写入本身就是请求的主要业务结果，例如用户明确执行“发布角色”“修改账户”“提交排位结算”。

## 3. Arena 原生性与 provenance

### 3.1 原生性是有限权威属性，不是全流程完整性证明

原生性只在它会因果性地影响当前服务器决策时验证，例如：

- 是否允许进入严格排位；
- 是否获得仅限官方原生内容的特殊规则；
- 是否对公开结果施加某项原生内容政策。

普通沙盒战报、角色成长文本、本地状态更新不应因为无法证明完整 provenance 而整体失败。

### 3.2 客户端 `isNative` 不可信，但失败默认降级

服务器不得直接信任客户端的 `isNative=true`。

需要原生性时：

1. 服务器根据自己掌握的证据验证；
2. 验证成功则视为原生；
3. 验证失败、证据缺失或历史格式无法确认时，**视为非原生并继续低风险流程**；
4. 只有“必须为原生才能执行”的高风险动作才拒绝。

这足以防止 causal attack：攻击者不能通过伪造 `isNative=true` 获得因原生性而产生的权限 / 结果；但 provenance 的非关键不一致也不会拖垮主流程。

### 3.3 撤回“完整角色快照 hash 作为战后更新许可”

Arena 战后角色更新不得再要求当前角色完整 `data + isNative + isPreset + characterGuidance` 与 generation 起点做强 hash 等价。

推荐语义：

```text
generationId
  -> 读取服务器已确认的 report / impacts
  -> 依据稳定角色身份 / 本场 roster identity 对应目标角色
  -> 对需要原生性的具体 effect 当场重新验证
  -> 将合法 effect 应用到当前角色
```

如果某一个角色发生身份冲突或不可安全匹配：

- 局部跳过该角色；
- 返回明确的 per-combatant warning / error；
- 不因单个角色冲突让全场战后更新整体失败，除非整个 roster 都无法可信对应。

`baseRevisionHash` 可以完全删除；如果后续确实需要乐观并发控制，也只能使用**最小稳定 revision / identity**，不得重新把整张角色业务对象做 hash 当作权限条件。

## 4. 错误返回与诊断信息

### 4.1 目标：可行动，而不是统一模糊化

项目允许并鼓励向用户返回足以定位问题的错误信息。

错误响应可以包含：

- 稳定错误 code；
- 人类可读 message；
- Provider 在安全清洗后的原始诊断；
- HTTP status / retryable / phase / capability 等有助于排障的低敏元信息；
- generationId / requestId 等不构成凭据、且有助于定位日志的标识；
- 在多个角色局部失败时的逐角色原因。

不要求所有服务端异常统一投影成“服务器内部错误”。

### 4.2 允许恢复“安全清洗后的错误透传”

对于第三方 AI Provider 等上游错误，优先：

```text
上游错误
  -> 清洗 secret / credential / authorization / signed URL / cookie / internal path 等敏感信息
  -> 保留 Provider 给出的有用诊断
  -> 附加项目自己的稳定 code / phase
  -> 返回用户
```

如果无法可靠判断一段原始错误是否安全，则回退为项目自己的稳定错误文案，同时把完整细节留在受保护日志。

### 4.3 永远不得直接返回的内容

- stack trace；
- 源码绝对路径 / 容器内部路径；
- SQL 文本、数据库 schema 细节、连接串；
- Redis / D1 / R2 credential；
- API Key、Bearer token、Cookie、session token；
- Cloudflare / AWS 等签名 URL 或签名 header；
- SSH key / private key；
- 其他用户的个人信息或私有内容；
- 内部仅用于授权 / 风控的敏感判定数据。

### 4.4 错误 taxonomy 不需要为了“简化”而减少信息量

本轮简化删除的是**维护成本高但用户价值低的证明体系**，不是要求错误 code 越少越好。

错误 code 可以细分，只要：

- code 由真实失败阶段自然产生；
- 不需要额外机器 evidence / manifest 才能维护；
- 不泄露秘密；
- 前端可以直接显示或映射；
- 不把每个内部状态机细节都永久冻结成公共兼容承诺。

内部错误分类可以比公共 API 更细；公共 API 不必为所有内部枚举承担永久兼容责任。

## 5. Hosted AI、DR 与长生成

### 5.1 保留可恢复长生成

以下能力具有明确用户价值，应保留：

- 稳定 `generationId`；
- 服务器端生成继续运行；
- 客户端断网后重连；
- 有界 replay / terminal result 查询；
- 用户显式取消；
- 已 dispatch Provider 请求的重复调用防护。

### 5.2 DR 规则收敛为少数因果规则

无需为每个 route 长期维护大规模 capability evidence matrix。

默认规则：

1. **safe read**：允许 fallback / retry；
2. **尚未 dispatch Provider 的新生成请求**：可以切换 placement 后执行一次；
3. **Provider 已 dispatch**：不得因为网络 / adapter 错误自动重新 dispatch；优先通过已有 `generationId` 查询或重连；
4. **明确幂等命令**：按该命令自己的 idempotency key 处理；
5. 无法判断是否已执行的非幂等动作：返回“结果不确定 / 请查询”，而不是盲目重放。

只要代码能直接表达这些规则，就不需要再用大型 capability manifest、drill evidence 或 source digest 证明它们。

## 6. CI 与发布

### 6.1 CI 的最小目标

默认 merge CI 应主要回答：

- TypeScript / typecheck 是否通过；
- lint 是否通过；
- 单元 / 关键集成测试是否通过；
- Web / Hono / 需要发布的 workspace 是否能 build；
- 是否存在少量明确的高风险安全回归。

CI 不应成为历史项目管理系统。

### 6.2 发布门禁只保护真实 release 风险

production 发布可以使用：

- GitHub Environment；
- 必要时的 manual approval；
- production branch restriction；
- deploy concurrency；
- 构建产物 digest；
- 部署后 `/health/ready`；
- 少量真实公网 smoke / canary；
- 可操作的上一版本 rollback。

不再要求 GMR source digest、审查 Markdown marker、历史 evidence manifest 或多层自定义 release gate 才能发布。

### 6.3 多人模式发布原则

Arena 多人模式不应继续被 `GMR-10Q`、`GMR-11`、sourceDigest、reviewedSourceDigest、独立审查 evidence 等证明型状态长期卡住。

只要当前候选版本：

- 核心 Room 创建 / 加入 / 退出可用；
- WebSocket ticket / membership 授权没有已知严重绕过；
- host 与 member 权限边界没有已知 Critical 问题；
- 基本生成 / Proposal / 广播主流程可完成；
- 有界 payload / send queue / 基础限流仍存在；
- production 配置、Redis 和 Hono health 正常；
- 最小线上 smoke 通过；
- 没有已知会导致严重数据破坏、凭据泄露、权限提升或重复大额 Provider 调用的 blocker；

则可以发布。

普通 bug、边缘断线恢复缺陷、缺少某个 hardening drill、没有新的独立审查证据、某份机器 evidence 过期，都不构成自动阻断发布的充分理由。

发布后发现一般问题可以正常修复和迭代；必要时使用 feature flag 关闭多人入口或回滚 release。

## 7. Monorepo 与应用边界

保留：

- `apps/web` / `apps/api` / `apps/admin` / `apps/d1-gateway` 等真实运行时边界；
- `packages/*` 的共享代码边界；
- package `exports`；
- 不把 secret 代码导入 client package 等高价值边界。

但自定义 AST / naming / source-ownership checker 只有在 TypeScript、ESLint、package exports 和普通测试无法低成本保护真实风险时才保留。

不得因为“既然已经写了 checker”而永久保留 checker。

## 8. 复杂度预算审查问题

今后新增新的 gate、manifest、digest、registry、checkpoint、reconciliation 或独立 verifier 前，应回答：

1. 它具体防止什么用户损失或安全后果？
2. 普通类型系统、测试、Git 历史、日志或简单条件判断为什么不足？
3. 如果该机制自身出错，是否会阻塞主业务？
4. 它需要同步维护几份 source of truth？
5. 能否设计成 advisory / warning / telemetry，而不是 fail-closed？
6. 删除它以后，攻击者是否真的获得新的因果能力？

如果第 6 项答案是否定的，则默认不应让它成为主流程 blocker。

## 9. 外部设计参考

本 ADR 借鉴但不机械照搬以下资料：

- OWASP Error Handling Cheat Sheet：异常响应不应泄露 stack trace、框架 / 数据库等实现细节；预期失败应使用合适 HTTP 状态并集中处理。  
  https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html
- OWASP Logging Cheat Sheet：日志应保留调查所需上下文，但 credential、token、连接串、私密数据等不得直接记录；必要时可清洗 / 去标识。  
  https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- Google SRE, Production Services Best Practices / Cascading Failures：故障与过载时应优先 graceful degradation，继续提供合理但降级的结果，并避免重试放大故障。  
  https://sre.google/sre-book/service-best-practices/  
  https://sre.google/sre-book/addressing-cascading-failures/
- GitHub Actions Environments：生产部署可以直接使用 environment、required reviewer、branch restriction、concurrency 和 environment secrets 作为部署保护，不要求项目自行再造 reviewed-source-digest 机制。  
  https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments

这些资料支持的是**风险匹配的控制与优雅降级**，并不意味着本开源项目需要复制大型组织的全部治理流程。

## 10. 与旧文档冲突时的裁决

自本 ADR 为 `accepted` 起：

- 旧文档要求完整 source digest / reviewedSourceDigest 才能发布：以本 ADR 为准；
- 旧文档要求 evidence manifest / audit marker 成为长期 CI blocker：以本 ADR 为准；
- 旧文档要求 provenance / native 不一致让普通 Arena 更新整体 fail closed：以本 ADR 为准；
- 旧文档要求 D1/R2 finalization 失败推翻已交付 AI 结果：以本 ADR 为准；
- 旧文档关于真实认证、授权、secret、严格排位、多人 host/member 权限、Provider 防重复调用的安全边界继续有效。

具体删除、迁移和验收顺序见配套实施计划。
