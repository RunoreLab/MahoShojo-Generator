# pnpm 包管理器迁移决策

状态：`accepted`
日期：2026-05-29

## 背景

仓库迁移前同时存在 `bun.lock` 与 `package-lock.json`，日常说明中以 Bun 为主、npm 为备用；`package.json` 中还存在 `preview` 调用 `npm run build:cf`、测试脚本调用 Bun 测试运行器、部分运维脚本直接调用 Bun 的混用状态。

这类混用会带来三个问题：

1. 锁文件来源不唯一，依赖解析结果难以长期对齐。
2. 本地、CI 与 Cloudflare Pages 的包管理器版本可能漂移。
3. 后续贡献者难以判断应当使用 Bun、npm 还是其他命令安装与调度脚本。

本次决策只处理“包管理器与脚本调度口径”。Bun 测试运行器和少量 Bun TS 脚本属于运行时/测试框架问题，不在第一阶段迁移范围内。

## 决定

采用 pnpm 作为项目唯一包管理器与脚本调度入口，第一阶段基线为：

- Node.js：`>=22`，本地推荐 `v24.14.0`。
- pnpm：`11.3.0`。
- `package.json` 增加 `packageManager: "pnpm@11.3.0"`。
- Cloudflare Pages 显式配置 `PNPM_VERSION=11.3.0`。
- 依赖锁文件统一为 `pnpm-lock.yaml`。
- `package-lock.json` 与 `bun.lock` 在生成并验证 `pnpm-lock.yaml` 后移除。

命令口径统一为：

```bash
pnpm install
pnpm dev
pnpm build
pnpm start
pnpm build:cf
pnpm preview
pnpm lint
pnpm test
```

`package.json` 内部脚本也应避免再调用 `npm run`。例如：

```json
{
  "preview": "pnpm run build:cf && wrangler pages dev .vercel/output/static"
}
```

## 保留边界（历史）

第一阶段继续保留 Bun 作为测试运行器。

原因是现有测试大量使用 `bun:test`，直接替换为 Node test runner、Vitest 或 Jest 会扩大为测试框架迁移。此类迁移应另开设计与验证，不与包管理器切换混在同一批完成。

第一阶段也继续保留现有直接使用 Bun 的运维脚本，特别是 `scripts/backfill-user-auth-links.ts` 这类带 `#!/usr/bin/env bun` 且依赖 TypeScript 与 `@/` 路径别名的脚本。后续若要统一为 `tsx` 或 Node 原生执行，需要单独验证路径别名、环境加载和 Cloudflare D1 调用行为。

当前状态见文末“后续状态”。上述内容仅记录第一阶段决策边界，不再代表当前命令口径。

`scripts/build-cf.mjs` 中为 `next-on-pages` 内部 `npx vercel build` 设置 npm cache 的逻辑应保留。该逻辑处理的是上游工具内部 npm/npx 调用的可写缓存目录，不代表项目继续使用 npm 作为包管理器。

## 迁移步骤

1. 确认本地 Node 版本满足 `>=22`。
2. 通过 Corepack 或全局安装方式启用 `pnpm@11.3.0`。
3. 在 `package.json` 写入 `packageManager: "pnpm@11.3.0"`。
4. 使用 `pnpm import` 从现有 `package-lock.json` 生成 `pnpm-lock.yaml`。
5. 执行 `pnpm install`，确认 `node_modules` 与锁文件可用。
6. 将项目文档、AGENTS/CLAUDE 指引和 README 中的包管理器命令改为 pnpm。
7. 将 `package.json` 内部的 `npm run` 调用替换为 `pnpm run`。
8. 在验证通过后删除 `package-lock.json` 与 `bun.lock`。
9. 在 Cloudflare Pages 环境变量中设置 `PNPM_VERSION=11.3.0`。

## 验证清单

迁移提交前至少执行：

```bash
pnpm install --frozen-lockfile
pnpm test
pnpm lint
pnpm build
pnpm build:cf
```

如果 Cloudflare Pages 预览链路需要本地确认，再执行：

```bash
pnpm preview
```

验证时需要特别关注：

- pnpm 安装后是否出现 peer dependency 或 build script 审批相关提示。
- `next build` 与 `next-on-pages` 是否仍能正常产出 `.vercel/output/static`。
- 当时保留的 Bun 测试运行器是否能在 pnpm 管理的 `node_modules` 下继续通过。
- Bun TS 运维脚本是否仍可通过 `pnpm run <script>` 间接调用。

## 影响

正向影响：

- 依赖锁文件收敛为单一来源。
- 本地与 Cloudflare Pages 的包管理器版本可显式固定。
- pnpm 的内容寻址存储与严格依赖结构有利于减少隐式依赖问题。
- 命令入口更清晰，贡献者只需记住 pnpm。

代价与风险：

- Node 18/20 不再作为推荐开发基线；贡献者需升级到 Node 22 或更高版本。
- pnpm 11 的严格依赖结构可能暴露此前 npm/Bun 扁平安装下未暴露的幽灵依赖。
- Cloudflare Pages v3 默认 pnpm 版本不是 11.3.0，必须显式配置 `PNPM_VERSION`。
- 测试仍依赖 Bun，因此“迁移到 pnpm”不等同于“移除 Bun”。

## 备选方案

### pnpm 10 + Node 20/22

优点是兼容面更宽，Cloudflare Pages v3 默认 pnpm 版本也在 10.x。缺点是项目当前本地 Node 已为 24.14.0，且维护者已确认可采用 pnpm 11，因此没有必要为了旧 Node 基线保守停留。

### 只更新文档，不切换锁文件

优点是短期风险最低。缺点是 `bun.lock` 与 `package-lock.json` 并存的问题继续存在，无法真正建立稳定包管理器口径。

### 同时移除 Bun

优点是工具链最统一。缺点是会牵涉测试框架、TS 脚本运行器、路径别名与若干运维脚本行为，风险和工作量明显超出本次目标。
