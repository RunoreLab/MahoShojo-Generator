# Monorepo 与应用边界决策

状态：`accepted`
日期：2026-08-22
决策标识：`ADR-pnpm-monorepo-app-boundaries`

## 背景

当前仓库已经同时包含 Next.js/OpenNext Web、Hono Node 服务、D1 Gateway Worker、Arena Room Worker/Durable Object 的已冻结 v1 设计、Drizzle schema、大量共享领域代码、长期分叉的 `feat/admin`，以及计划新增的 Desktop 与 Mobile。

现有单 package 结构无法准确表达运行时、部署、秘密、依赖和信任边界。

## 决定

### 1. 使用 pnpm workspace

仓库迁移为 pnpm Monorepo，根目录使用 `pnpm-workspace.yaml`。首阶段只使用 pnpm 原生 workspace 和 filter 能力，不预先引入 Turborepo/Nx。

只有在 CI 耗时、依赖图和缓存收益有可测证据后，才另行决定是否增加任务编排器。

### 2. 应用是独立部署单元

目标应用目录：

```text
apps/
  web/
  admin/
  api/
  d1-gateway/
  arena-room/
  desktop/
  mobile/
```

职责：

- `apps/web`：公共 Web、账号入口、线上卡库、社区和现有在线功能。
- `apps/admin`：独立构建和部署的管理后台。
- `apps/api`：香港 Hono、长流、Hosted 生成、签名和其他 Node 服务。
- `apps/d1-gateway`：Cloudflare Worker 内部数据库网关。
- `apps/arena-room`：Arena 多人 Room sidecar Worker、Durable Object、WebSocket、alarm 与最小房间持久化。
- `apps/desktop`：Tauri Desktop 首选实现。
- `apps/mobile`：通过 PoC 后选定的移动运行时。

应用之间禁止源码级直接导入；跨应用复用必须提取到 package 或通过版本化 API/协议完成。

`apps/arena-room` 的“独立”只指运行时、部署、秘密与资源边界。Arena 多人在产品层仍然整合进现有 `/arena`，不得因为 sidecar 独立部署而复制一套 Multiplayer Arena 页面或生成核心。

Arena 多人 v1 在 Monorepo 落地前可以临时位于 `workers/arena-room` 或现有等价目录；迁移后必须进入独立部署单元，且不得改变已冻结语义。Worker 调用 Room 优先走 Service Binding/RPC；外部 Hono generation 到 Room 的发布使用 Arena Room ADR 定义的 GenerationBridge，不把 Service Binding 错用于非 Worker 运行时。

### 3. 共享包有明确职责

目标共享包：

```text
packages/
  domain/
  contracts/
  ai-core/
  ai-direct/
  local-library/
  cloud-client/
  multiplayer-core/
  ui-web/
  config/
  test-utils/
```

约束：

- `domain`：纯 TypeScript 领域规则；不得依赖 Next、Cloudflare、Tauri、Electron、DOM、Node 数据库或应用目录。
- `contracts`：API DTO、Zod schema、错误码和协议版本；不得读取环境变量。
- `ai-core`：Prompt、结构化结果 schema、解析、修复和运行时无关的流逻辑。
- `ai-direct`：Direct Provider Profile、执行端口和共享请求模型；Native 实现在对应 APP。
- `local-library`：本地库记录、迁移、导入导出和 repository contract。
- `cloud-client`：对项目 Web/API 的版本化客户端；不得持有服务器秘密。
- `multiplayer-core`：房间共享投影、Proposal、revision、参与者、事件、幂等和恢复语义。
- `ui-web`：Web/Desktop WebView 可共享的 React DOM 组件；不得假定可直接用于 React Native。
- `config`：非秘密静态配置和工具链配置。
- `test-utils`：测试夹具和 contract harness，不得进入生产包。

禁止创建职责不清的长期 `packages/common` 或 `packages/shared` 倾倒目录。

### 4. 依赖方向

必须满足：

```text
apps -> packages
runtime adapters -> domain/contracts
server packages -> domain/contracts
packages !-> apps
client packages !-> server secret code
```

根 `package.json` 只承担 workspace 编排、统一版本和顶层命令，不继续承载所有运行时依赖。

### 5. `feat/admin` 回归主线

`feat/admin` 不直接整分支合并，也不继续作为长期部署分支。

迁移方式：

1. 盘点功能、API、数据表、危险操作和测试；
2. 以业务域为单位移植到 `apps/admin` 与共享 package；
3. 同步吸收主线安全、schema 和 API 变更；
4. 上线前补齐 Access、Origin JWT、RBAC、审计和高风险操作保护；
5. 完成后冻结并归档旧分支。

### 6. Arena 多人不中断

已冻结的 Arena 多人 v1 可以在 Monorepo 迁移期间继续实施，但必须：

- 保持 Room Shared Config 白名单；
- 不传播 Provider/API credential；
- 不把每 token 作为 DO 事件；
- 不用固定轮询替代实时能力；
- 保持服务器唯一权威生成；
- 在共享 package 成熟后迁移契约，不做无关重写。

### 7. 部署、秘密和 CI 分离

- 每个 APP 有自己的构建、运行时配置、健康检查和部署流程。
- 生产秘密按应用最小权限分配。
- 任意 branch push 不得默认触发生产部署。
- 共享 package 变更必须触发所有依赖应用的测试。
- 结构迁移阶段不得同时大规模修改业务行为。

## 影响

### 正面影响

- 运行时和部署边界可审查。
- Admin、Hono、Web、Arena Room、Desktop、Mobile 可独立发布。
- 客户端不会因为复用代码而意外打包服务器秘密。
- 可以对共享协议和 repository 做跨运行时 contract test。
- 长期分支的修复漂移成本下降。

### 代价

- 需要搬迁路径、构建脚本、别名、测试和 CI。
- 初期可能出现跨 package 类型、ESM、Edge/Node 兼容问题。
- 需要建立依赖边界 lint 和 package exports。
- 共享包拆分过细或过早会增加维护负担，因此必须按真实复用提取。

## 不采用的方案

- **继续单 package，只增加 Desktop/Mobile 子目录**：无法可靠约束依赖、部署和秘密边界。
- **每个客户端独立仓库**：当前跨仓库同步成本高于收益。
- **立即引入复杂 Monorepo 编排器**：避免把目录迁移与工具迁移叠加。
- **把 Arena Room Worker 混入 Web Worker**：Room sidecar 有独立 WebSocket、DO、alarm、资源和部署边界；产品/UI 仍保持现有 Arena 一体化。
