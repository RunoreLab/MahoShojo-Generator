# 公开数据卡众查 Phase 1A/1B 基础设施与当前案件流程 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为现有公开数据卡举报案件补齐众查 Phase 1A/1B 所需的资格、派单、投票、结果写回与最小消息入口聚合提示，先跑通巡查使的“当前案件”闭环。

**Architecture:** 继续把 `report_cases` / `reports` 作为举报事实层，再新增 `crowd_review_*` 执行层和 `crowd_review_inspectors` 资格状态层。服务端由 `lib/crowd-review/*` 与 `lib/db/repositories/crowd-review.ts` 负责资格判断、派单、投票、并发约束与结果写回；前端新增 `/investigation` 单页入口，并把“可处理案件”作为消息摘要的派生提示而不是 `user_messages` 行。该计划只覆盖总体规划中的 `Phase 1A + Phase 1B`，以及为后续 `Phase 1C` 准备最小消息入口聚合，不包含申诉 UI/API 与 `feat/admin` 后台页面。

**Tech Stack:** Next.js Pages Router、React 19、Cloudflare Edge Runtime、Cloudflare D1、Drizzle ORM、Bun test、现有消息系统与公开数据卡举报链路。

## Scope Notes

- This plan intentionally excludes `POST /api/report-appeals` and user-facing appeal UI because it is the first implementation plan for the overall spec, not the full “一期” closure. `Phase 1C` remains a required follow-up plan from the approved overall spec.
- This plan intentionally excludes `feat/admin` 后台 UI. It only prepares the schema, state machine, and API/service seams that `feat/admin` can call later.
- Before implementation starts, create a small protocol addendum doc that locks three planning-sensitive areas: result writeback mapping, minimal API contracts, and concurrency invariants. Reviewer feedback identified these as the main ambiguity risks.

- [ ] **Step 1: Write the protocol addendum**

Create `docs/specs/2026-04-08_215011_公开数据卡众查一期协议附录.md` with four sections:

1. `众查结果写回举报案件处理链路`
   - Auto-writeback mapping:
     - `crowd result = violation` -> `report_cases.status = 'resolved'`, `resolution_code = 'confirmed_violation'`, `closed_at = now`
     - `crowd result = no_violation` -> `report_cases.status = 'dismissed'`, `resolution_code = 'no_violation'`, `closed_at = now`
     - `crowd result = tie | escalated` -> keep `report_cases.status = 'under_review'`, `resolution_code = null`, `closed_at = null`
   - For this Phase 1A/1B plan, there is no persisted “requires admin confirmation” branch. Any richer admin-confirmation policy is deferred to the follow-up admin plan and must not appear as an implicit runtime branch here.
2. `最小 API 契约`
   - Exact request/response fields for:
     - `GET /api/crowd-review/summary`
     - `POST /api/crowd-review/current/assign`
     - `GET /api/crowd-review/current`
     - `POST /api/crowd-review/current/submit`
     - `GET /api/crowd-review/history`
     - `GET /api/messages/summary` crowd-review extension fields
   - Auth rules for anonymous viewer vs authenticated viewer vs eligible inspector
   - Error codes: `400`, `401`, `403`, `404`, `409`, `422`, `503`
3. `并发与一致性约束`
   - One active inspector assignment at a time
   - One crowd-review round per open report case
   - No duplicate assignment of the same round to the same inspector
   - Submission must be idempotent once assignment status is final
   - Active round statuses are `pending_dispatch | active | waiting_more_votes`
   - Active assignment statuses are `assigned`
   - Deadline and expiry progression are lazy: `summary/current/assign/current/submit` must all call the same “advance expired state” helper before reading or mutating live rows
4. `本批次范围`
   - Explicitly mark appeal UI/API and admin UI as follow-up work
