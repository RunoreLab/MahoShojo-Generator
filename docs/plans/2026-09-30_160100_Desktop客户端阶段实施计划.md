# Desktop 客户端阶段实施计划

状态：`active`
日期：2026-09-30
计划标识：`PLAN-desktop-client-v1`
约束规格：[Desktop 客户端实施规格](../specs/2026-09-30_160000_Desktop客户端实施规格.md)
约束决策：[Desktop Tauri V1 运行时与本地安全边界决策](../decisions/2026-09-30_160000_DesktopTauriV1运行时与本地安全边界决策.md)

本计划只定义 Desktop 客户端自身阶段顺序。它不改变
[平台重整分阶段实施计划](./2026-08-22_022700_平台重整分阶段实施计划.md) 的跨应用门禁优先级，也不
改变 Arena、认证、数据所有权与服务器权威语义。

## 0. 总体原则

1. **先证明平台边界，再迁业务。** 在 capability、CSP、IPC 形态和 secret 存储被真实运行验证前，
   不迁移任何 Web 业务页面。
2. **先冻结既有语义，再跨语言复制。** 本地库阶段不得顺手修改内容摘要算法。
3. **先证明最薄纵切，再做完整产品。** Direct AI 跑通后才允许进入本地库持久化。
4. **每个阶段独立可交付。** 任何阶段失败都不应让仓库处于无法构建或门禁变红的状态。

## 1. 阶段序列

```text
D0    Desktop skeleton + 安全边界 + CI 接线
  ↓
D0.5  Secret store spike（OS 凭据存储）
  ↓
D1    Direct AI 最薄纵切（Rust HTTP + SSE + Channel + cancel + 契约一致性门禁）
  ↓
D1.5  内容摘要语义下沉
      a 修订权威要求（单一 TS 实现 + 冻结 V1 语义）
      b 下沉 canonicalization / 摘要 / ID 派生
      c V1 golden fixture
  ↓
D2    Installed 本地库
      0 SQLite 本地卡存储（schema v2 + keyset 分页）
      1 Web Package ZIP blob 持久化
      2 完整性审计与孤儿 GC
        a 并发地基（单 managed state + 维护窗口 + 数据目录锁）
        b 完整性审计（只报告）
        c 孤儿 GC
      3 Portable archive（Web 与 Desktop 共用）
        a manifest V2 契约（替换 V1）
        b ZIP 流式组装 + Desktop 导出
        c Desktop 导入
        d Web 设备级页面 + 导出
      4 完整备份与恢复
        a 备份
        b 恢复（重启时交换）
  ↓
D3    第一条真实业务纵切（魔法少女生成）
  ↓
D4    Web Package 独立零 capability webview
  ↓
D5    Hosted 集成与发行（updater + 签名分层）
```

D2 的五段顺序固定，不合并：每段引入一类新的失败模式（SQL、文件系统、并发、跨运行时契约、
破坏性恢复），合并交付会让任何一类的根因被其余部分淹没。段内再切的理由写在 §2。

### D0 Desktop skeleton 与安全边界

交付物：

- `apps/desktop`：manifest、README、Vite 配置、TypeScript 配置、lint/test 配置、最小 UI shell；
- `apps/desktop/src-tauri`：`Cargo.toml`、`build.rs`、`tauri.conf.json`、`capabilities/main-ui.json`、
  入口与一个只读运行时自述 command；
- 仓库接线：`.gitignore`、workspace 边界检查忽略 `target`、`tests/workspace-structure.test.ts`
  结构门禁、root 过滤脚本、独立 Rust CI workflow；
- 显式 CSP，`withGlobalTauri=false`，无 Tauri 插件。

退出门禁：

- 前端 `build`、`test`、`lint` 通过；
- `cargo fmt --check`、`cargo clippy`、`cargo test` 通过；
- `check:workspace:boundaries` 与 `test:repo` 通过；
- `apps/desktop` 的 `build` 脚本不含 `tauri build`；
- capability 只用 `webviews` 且不含通配；
- 渲染层无 shell / fs / sql / 任意 fetch 依赖。

已知限制：GUI 交互行为无法在无头环境验证。凡涉及"实际点击后运行结果"的验证 **MUST** 记录为
未验证并附可复现步骤，**MUST NOT** 记为 PASS。

### D0.5 Secret store spike

目标是把 ADR 中"OS 凭据存储优先"的假设变成结论。

结论：**成立**。`keyring` 的 Windows Credential Manager 后端在本机完成写入、读取、删除与
幂等二次删除，全程无需交互式解锁；Stronghold 不进入 V1。ADR 第 6 条随之冻结。

已落地：

- `apps/desktop/src-tauri/src/secret.rs`：可插拔 `SecretStore` trait + `keyring` 绑定；
- command 层只有 `set` / `has` / `delete`，**没有**明文读取入口；
- secret 引用的字符集与长度上限由 `@mahoshojo/contracts/desktop-ipc` 定义，
  并以 `packages/contracts/fixtures/desktop-secret-refs.json` 作为跨运行时一致性 fixture，
  由 TypeScript 与 Rust 两侧测试同时消费（DESK-033 的最小实例）；
- `@mahoshojo/ai-direct` 的 `SecureVault` 从 `set/get/delete` 收敛为 `set/has/delete`。

未在本阶段覆盖、留待 D5 发行门禁：macOS Keychain 与 Linux Secret Service 后端的真实往返。

退出门禁：

- renderer 无任何返回明文 secret 的入口；
- secret 不出现在 SQLite、日志与导出；
- ADR 由 `proposed` 转为 `accepted`，或记录被否决的备选与理由。

### D1 Direct AI 最薄纵切

交付物：

- **SQLite 与 Provider Profile 存储**（见下方「D1/D2 职责边界修订」）：Profile 只存非秘密
  字段与 `secretRef`，明文 API Key 仍只在操作系统凭据存储里；
- Rust 侧 HTTP transport 与 OpenAI-compatible adapter；
- `streamDirectAi` / `cancelDirectAi` / 连接测试 command，`Channel<AiStreamEvent>` 流式；
- TypeScript 侧 `DesktopAiExecutionPort` 适配与最小测试面板；
- 契约一致性门禁（共享 fixture + 两侧校验）。

依赖选择（2026-09-30 确认）：`reqwest` + `rustls`（纯 Rust，无 OpenSSL，跨平台一致）、
`rusqlite` + `bundled`（不依赖系统 SQLite，代价是编译 C 源码与二进制增大）。

退出门禁：

- 至少一个 loopback OpenAI-compatible 端点与一个公网端点实测通过；
- 取消真正中止上游，并投递 exactly-once 终态；
- 契约一致性门禁在两侧均生效；
- Direct 出站路径拒绝项目自有域名；
- 出站端点只来自已保存 Profile，请求 DTO 不含 endpoint / header / secret 明文。

未验证项必须显式记录：真实 Ollama、LM Studio 与公网端点的连通性由使用者在
`pnpm --filter @mahoshojo/desktop run dev:tauri` 下自行复现；CI 内只跑进程内自建的
OpenAI-compatible SSE 服务。

#### D1 当前状态

已完成（D1a + D1b 的执行核）：

- SQLite + `provider_profile` 表 + migration journal，Rust 为 opaque 文档的 dumb store；
- Provider Profile 的保存/读取/列举/删除命令，以及保存前让 native 独立表态的双向校验；
- `stream_direct_ai` / `cancel_direct_ai`：Rust 持有 HTTP transport，
  `Channel<AiStreamEvent>` 流式，`requestId` + 取消注册表 + exactly-once 终态；
- SSE 增量解析器（含跨 chunk 边界重组、`[DONE]` 终止、多行 data、CRLF、注释行）；
- `AiStreamEvent` / `AiExecutionResult` 的 Rust 镜像，与 TypeScript 共用
  `packages/contracts/fixtures/ai-stream-events.json` 做双向断言；
- transport policy：项目自有域名拒绝、公网明文 HTTP 需显式确认、重定向缺省关闭、
  `no_proxy`、header 白名单与 secret 引用校验；
- **进程内 OpenAI-compatible SSE 测试服务**驱动的端到端测试，覆盖正常流、取消、缺终态、
  缺 secret、未知 Profile、模式拒绝；
- `AiExecutionPort` 的桌面实现：`execute()` 收集流、协议归约复用 `ai-core`、
  AbortSignal 同时中止本地消费与 native 上游；
- 最小 Provider Profile 面板：保存 / 列表 / 凭据存在性 / 生成测试，含凭据与 Profile 的
  写入顺序不变量。

端到端测试给出的三条可执行证据：

1. 事件以 `started` 开始、`sequence` 连续、**终态恰好一次**；
2. 取消**真正中止上游 body** —— 由测试服务端观察到客户端断连证明，而不是只看本地返回值；
3. 上游缺少 `[DONE]` 时报 failed，不会把半截正文当成功。

**尚未完成，因此 D1 退出门禁未闭合**：

1. 真实端点（Ollama / LM Studio / 公网）未实测。这是唯一一条必须由人在真实 Provider 上
   确认的门禁，端到端测试只能证明客户端与本地语义正确。
2. `thinking` 字段当前被 `deny_unknown_fields` 拒绝，尚未映射到 Provider 参数。
3. serde 不支持在 internally tagged enum 上使用 `deny_unknown_fields`，因此流事件的未知字段
   会被静默忽略；已用测试记录该事实并依赖 fixture 双向断言兜底，但这是一个已知弱点。
4. `anthropic` / `google` adapter 未实现，当前显式拒绝而不是按 OpenAI 语义静默发起请求。
5. 面板只覆盖 D1 所需的最小流程，不含完整设置页、连接测试分离、Profile 编辑与导入导出。

> **关于"D1 门禁未闭合却已推进到 D2.3"**：这不是治理事故，而是一条必须显式记录的迁移差距。
> 上面五条里没有一条阻断本地库工作——1 与 4 属 Provider 覆盖面，2、3 属 Direct 流语义，5 属设置页
> （计划里落在 D5）。它们各自落在别的阶段，因此"D1 门禁未闭合"与"D2.3 可以开工"同时为真。
>
> 记在这里是为了防止另一种误读：后来者看到 D2.3 已推进，可能推断 D1 的退出门禁已被默认放弃。
> 实际状态是**延期**而非放弃，第 1 条（真实 Provider 实测）尤其不能被无声地跳过。

#### D1/D2 职责边界修订

原计划把 SQLite 整体放在 D2，这会让 D1 无法满足"出站端点只来自已保存 Profile"这条安全
属性：Rust 侧必须自己持有 Profile 才能解析 endpoint 与 secret 引用。若先用 JSON 文件
承载，D2 就要写一次性迁移，属于为迁移制造临时兼容。

因此修订为：

- **D1** 引入 SQLite 与 migration journal，只建 `provider_profile` 表。Rust 是"已校验文档的
  dumb store"：只按 id 存取 opaque JSON 文档，不解释业务字段。
- **D2** 在同一个 SQLite 上增加本地卡、Web 包与 blob 相关表，并落地崩溃一致性写入顺序、
  备份/恢复与 GC。

该修订不改变 ADR 第 7 条的职责分层：Profile 的组装与校验仍在 TypeScript，Rust 仍然自己
产生路径与 SQL 选择器。

### D1.5 内容摘要语义下沉

拆成三个可独立提交的原子步骤，因为它们的风险与回滚代价不同：文档修订不改变任何运行时行为，
下沉改变代码归属，fixture 改变"什么算回归"的判定标准。

#### D1.5a 修订权威要求

按 [ADR 第 8 条的修订记录](../decisions/2026-09-30_160000_DesktopTauriV1运行时与本地安全边界决策.md)
与 `DESK-060` / `DESK-062`，把"native 侧计算同一摘要"改为"单一权威 TS 实现 + golden fixture 冻结
V1 逐字节输出"，并新增 opaque document 写入门禁条款。退出门禁：ADR、spec、plan 三处口径一致，
且文档中不再存在"native 侧需要算卡 payload 摘要"的表述。

#### D1.5b 下沉到共享包

把 canonicalization、内容摘要、本地 ID 派生与传输元数据剥离从 `apps/web` 移到
`@mahoshojo/local-library`；`apps/web` 改为直接消费，行为不变。

退出门禁：移动前后的实现在同一组输入上产出相同 canonical 文本与摘要；Web 侧既有本地库测试全部通过；
`apps/web` 不再持有摘要算法；边界检查通过。

#### D1.5c 建立 V1 golden fixture

fixture 每个用例记录 `input` / `expectedCanonicalText` / `expectedDigest` / `expectedLocalId` /
`caseDescription`，覆盖 ADR 第 8 条列出的全部类别，其中三条是与 Rust 默认行为不同的历史语义：
UTF-16 键排序、`1e-6` → `0.000001`、`-0` → `0`。

退出门禁：fixture 由下沉后的实现生成并被同一实现断言；`caseDescription` 能指明被改动的是哪一种
历史行为；孤立代理项记录 JavaScript 行为且 V1 不新增拒绝。

#### D1.5 当前状态：已完成

- **D1.5a** 已落地：ADR 第 8 条、`DESK-060` / `DESK-061` / `DESK-062` 修订完成，并新增
  `DESK-054..059` 记录 D2 范围决策。
- **D1.5b** 已落地：`@mahoshojo/local-library/digest` 成为唯一权威实现。搬运范围比原计划大
  一项：传输元数据剥离函数实测有 4 处生产消费方（竞技场选卡、竞技场房间主机对账、卡牌工坊、
  摘要算法），此前定义在 `data-card-read-mappers` 里只被摘要算法当作依赖，属于归属错位，
  因此一并下沉并更名为 `stripLocalCardTransportMeta`。
- **D1.5c** 已落地：`packages/local-library/fixtures/local-card-digest-v1.json`，28 条用例。

门禁有效性经过实测而非假设：

| 注入的改动 | 结果 |
| --- | --- |
| 比较器换成 `localeCompare` | 失败，报出 canonical 文本差异与该用例锁定的语义 |
| 比较器换成码点序 | 恰好只有 `sort-utf16-vs-codepoint-fffd-vs-emoji` 与 `sort-utf16-vs-codepoint-private-use` 两条失败 |

两条分片用例各守一条语义、互不干扰，这是 fixture 设计的直接证据。

冻结结果与调研实测一致：键序为 UTF-16 code unit（表情的 `0xD83D` 排在 `U+FFFD`、`U+E000`
之前，与码点序相反）；`1e-6` → `0.000001` 而 `1e-7` → `1e-7`；`-0` → `0`。

**已知的门禁边界**：fixture 只能探测未同步的改动，探测不到"实现改了、fixture 一起重新
生成"。后者由 `caseDescription` 与 code review 拦住，这是刻意取舍，已写入 fixture 的
`$comment` 与 `notes`。

顺带更正一处先写错的事实：孤立代理项的摘要前像不是 `U+FFFD` 的替换字节，而是
`JSON.stringify` 产出的 8 个 ASCII 字符 `"\ud800"`——转义发生在编码之前，`TextEncoder` 根本
看不到代理项。实测摘要与这串 ASCII 的 SHA-256 一致后才改正文档。

### D2 Installed 本地库

D2 拆成五段，顺序固定。理由：每一段引入一类新的失败模式（SQL、文件系统、并发、跨运行时契约、
破坏性恢复），合并成一个交付会让任何一类问题的根因都被其余部分淹没。

#### D2.0 SQLite 本地卡存储

交付物：schema v2 与 migration、`local_card` 表（opaque document + Rust 自有索引列）、
Rust 侧对索引列与 document 的一致性复核、keyset 分页、业务级卡片 IPC、桌面端 `CardRepository` adapter。

`local_card` 同时持有 opaque `document` 与 `card_type` / `updated_at` / `deleted_at` /
`content_digest` 四个索引列。这不违反 ADR 第 7 条：TypeScript 提供这些值，Rust 不解释其语义，只用
它们做 SQL 选择器；TypeScript 在调用 IPC 前完成 schema 校验，Rust 独立复核索引列与 document 一致。
该复核复用 D1 已验证的"保存前让 native 独立表态"模式。

分页使用 `(updated_at, id)` keyset 游标而非 offset，避免并发写入下的漏页与重复页。`CardRepository`
的 `cursor` 保持 opaque，使 Web IndexedDB adapter 未来可独立改进，**MUST NOT** 为 D2 顺手重写 Web 分页。

本段 **MUST** 包含一条兼容性用例：JavaScript 可产出而 `serde_json` 拒绝的 document（例如含 `\ud800`
转义）**MUST NOT** 在桌面端静默被拒（`DESK-062`）。

退出门禁：重启持久；同一 `local_card` 既有 1000 条时的分页无重复无遗漏；索引列与 document 不一致时
以可诊断错误拒绝而不是写入不一致行；上述兼容性用例通过。

#### D2.0 当前状态：已完成（含一轮 remediation）

初版落地为两个原子提交：native 存储层与 IPC，契约与渲染层 adapter。

独立审查发现三处 correctness 问题，均已修复（见下方 remediation 记录）。架构本身未变：
opaque document + 类型化索引投影 + keyset + `RawValue` 仍然成立。

`DESK-062` 的落地方式经实测确定：document 的自由载荷声明为 `Box<RawValue>`，保留原始文本
而不实例化 `String`，因此 `\ud800` 被逐字节保留（`serde_json` 的 `raw_value` 特性）。索引字段
继续用 `String` 提取——surrogate 出现在 `id` / `cardType` / 时间戳 / 摘要里是真的非法，不是
收窄可表示域。

跨运行时契约落在 `packages/contracts/src/desktop-ipc.ts` + `fixtures/desktop-local-cards.json`，
两侧读同一份 fixture 并断言各自常量与它的**具体取值**相等。线上形状放在 contracts 而非
local-library，是因为后者是前者的上游，反向引用会形成 workspace 依赖环。

#### D2.0 remediation：独立审查发现并修复的三个问题

**1. soft delete / restore 造成 document 与索引列双状态。** 初版 `delete` / `restore` 只
UPDATE 索引列而**不动 document**，而 `get()` 返回的正是 document——于是软删后 `get()` 交回一条
"看起来仍未删除"的记录，直接违反 `repository.ts:40` 的 "returns the record, including a
tombstone"；恢复方向同样分叉。改为三个写入口（`save` / `delete` / `restore`）**同形**：都接受
调用方组装好的完整记录，由 native 校验状态转移并用**单条语句**写入整行。记录组装仍在
TypeScript（ADR 第 7 条）。新增 `card_lifecycle_keeps_the_document_and_the_tombstone_in_step`
逐条对齐端口注释。

**2. migration 存在真实 crash window。** 初版在 MIGRATION_1 之后、MIGRATION_2 之前就写入
`PRAGMA user_version = SCHEMA_VERSION`，且各步骤不在同一事务里。崩溃后下次启动会认为版本 2
已完成，从而永远跳过 MIGRATION_2，得到"版本号是 2 但 `local_card` 表不存在"的库。改为每个
版本一个显式事务（建表 + journal + `user_version = N` 同进同退），并新增失败注入测试：
注入一个必然失败的 v2，断言 `user_version` 停在 1、journal 无 2、`local_card` 不存在，且
条件修好后再次启动能补完。

**3. keyset 的时间排序只在 UTC `Z` 下成立。** 契约是 `datetime({ offset: true })`，允许任意
offset，而字符串比较不是时间比较：`2026-09-30T12:00:00+14:00` 的**文本**大于
`2026-09-30T01:00:00Z`，实际却是更早的时刻。影响面包括排序、"时间戳不得回退"判定、游标边界，
以及未来带 offset 的 archive 导入顺序。新增 `updated_at_sort`（UTC epoch 毫秒）作为真正的排序
键，document 仍保留原始 RFC3339 文本。排序键由 native **自行从 document 解析**，不采信调用方
提供的值，因此不可伪造、不会与 document 分叉。引入 `time` crate 做 RFC3339 解析——不自己写
日期解析：闰年与 offset 边界这类错误极难靠肉眼保证，而排序键算错直接表现为 keyset 漏读。

三处修复的门禁有效性均经**注入验证**（改回旧写法后确认对应测试变红），不是仅在顺利路径上
断言。详见各提交的说明。

门禁已通过：Rust 77 个测试、desktop 69 个、contracts 221 个、local-library 84 个、Web 2717 个。

#### D2.1 Web Package ZIP blob 持久化

交付物：`blob` 表与 `web_package_archive_ref` 真实外键表、blob 元数据表、内容寻址 blob 区、
同目录临时文件 + flush + 原子 rename 的写入顺序、已有 blob 的去重与损坏自愈。

退出门禁：崩溃注入后只可能出现孤儿 blob 而不出现悬空记录；已有且校验通过的 blob 视为成功；
命中损坏 blob 时自愈并返回"已修复损坏"，读取时无正确内容则 fail closed。

已完成（schema v4：v3 建 `blob`，v4 建 `local_web_package` 与引用表）。三项实现期发现值得留下：

**1. `contentDigest` 与归档字节的摘要本来就不相等，不要试图把它们对齐。**
`contentDigest`（= `ref.digest`）是 **manifest** 的摘要，见
`packages/web-package/src/verify.ts` 里 `digest(canonicalize(manifest))`；它是领域身份，包 id 由它
派生。归档字节的摘要是 blob 的**存储地址与完整性校验**，两者必然不同——ZIP 里除 manifest 还有
文件。实现中一度想加"归档摘要必须等于 `contentDigest`"的校验，那会直接破坏设计。归档字节是否真的
属于这份 manifest，由 TypeScript 侧 `unpackWebPackageZip` 核对（它会重算 `ref.digest` 再比对）；
native 不重建 ZIP 与 manifest 的规范化逻辑。

**2. 记录自称的归档长度必须与实际字节数复核。** `archiveByteLength` 是"这个包多大"的唯一答复，
而详情页、进度与配额估算都建立在它上面。native 从 document 取该字段与实际字节数比对，不一致
按 `index-mismatch` 拒绝。

**3. base64 信封是两侧唯一真值的耦合点。** 载荷由 TypeScript 编码、由 native 解码，若两侧只比较
字符串，一个"声明 4 字节、实际解出 5 字节"的 fixture 会一起通过，直到用户导入时才炸。因此共享
fixture 里的载荷被**解码**后断言长度与 ZIP 魔数，且 native 用自己的解码器再跑一遍。代价是空字节
序列必须在传输层可表示——"空 archive 非法"归 ZIP 校验管，不归传输信封管。

门禁有效性经**注入验证**：去掉归档长度复核、让孤儿补记写成 0 长度、把 fixture 改回解码长度不符的
旧值，三者分别让对应测试变红。base64 编解码另有与 Node 标准实现的逐字节对照测试（含 0/1/2/3 字节
的补位边界）——自实现编码器与渲染层只有一次调用相隔，漂移的表现是"存进去读不出来"。

#### D2.1 的第二轮：跨适配器与真实 wire 修复

首轮实现完成后，外部独立审查确认了**两个会让真实 Web 包读取路径必然失败**的跨层问题。两者都
能通过全部单测，因为两侧各自 mock 了对方的形状：

1. **响应方向形状不一致**：native 返回裸 base64 字符串，渲染层按 `{b64, len}` 解析。现改为
   请求与响应共用同一个 `Base64Bytes` DTO——让读写各自定义形状正是这类 bug 的温床。共享 fixture
   新增 `readArchiveResponse`，两侧都断言它。
2. **读取入口的键用错**：共享端口 `readArchive(digest)` 与 Web 的 IndexedDB adapter 都以
   **manifest 摘要**为键，业务侧传的正是 `record.ref.digest`；而 native 把它当包 id 查。
   manifest 摘要永远不是 `wp_…` 形式，于是每次读取都落空，表现为"包打不开"。现改为
   `contentDigest → 包记录 → 引用行 → blob` 两跳解析，并补生命周期测试（软删后仍可读、
   purge 后读不到）。

这两条现在都由 fixture 的**请求与响应两个方向**以及注入验证守住——改回旧写法会让对应测试变红。

顺带收口的三项：

- **`deriveLocalWebPackageId` 下沉到 `@mahoshojo/local-library`。** 它此前住在 `apps/web` 里，
  等于把跨运行时共享数据的派生规则变成某个前端的私有细节。canonical identity 现在由**记录契约**
  强制（`LocalWebPackageRecordV1Schema.superRefine`），Web adapter 里重复的那次检查相应删除。
  Desktop 侧加 `ref_digest UNIQUE`：Web 的 IndexedDB 对 `contentDigest` 建了 unique index，
  桌面侧缺这一条时同一摘要能落进两行，而按摘要读档只命中一行。native **不**在 SQL 里重算派生
  规则——那会把权威实现复制成第二份。
- **base64 换标准 crate。** 手写解码器遇到 `=` 就 `break` 而不校验 padding，尾随垃圾会被静默
  丢弃（`UEsDBQ==garbage` 与 `UEsDBQ==` 被当成同一份载荷）；且逐字符线性查表在 64 MiB 归档上是
  10⁹ 量级的比较。改用 `base64` crate（MIT/Apache-2.0，与既有 `sha2` 同族，无 bundle 影响）。
- **metadata 在但字节丢失时重写报 `repaired` 而非 `stored`。** 报 `stored` 会把"这台设备的库已经
  不健康"说成一次正常写入，健康告警因此漏掉整整一类问题。

门禁已通过：Rust 120 个测试、desktop 89 个、contracts 232 个、local-library 85 个。

状态：**implementation complete / parity remediation 已完成**。审查提出的其余项——`DESK-065`
维护并发模型、`DESK-066` 审计分类、D2.3 大归档内存门禁与双摘要命名、D4 的 `AppManifest::commands`
首道门禁——已写入规格与本计划。D2.1 到此可以判定 CLOSED。

#### D2.2 完整性审计与孤儿 GC

**先决条件：`DESK-065`（维护并发模型）与 `DESK-066`（审计分类）已冻结。** 这两条不是实现细节，
而是 GC 正确性的定义：一次保存跨 blob 文件、blob metadata、包事务三个资源，若 GC 恰好落在
"blob 已发布、引用行未 commit"的窗口就会删掉 in-flight 的 blob。

拆成三段的理由：并发地基会改动每一个 command 签名与每一个 store，与审计混在一起时，地基的
回归无法归因——这与本计划"D2 五段不合并"是同一条原则，只是往下再切一层。

##### D2.2a 并发地基

交付物：`LocalLibrary` 单一 managed state（一条连接，四个 store 共用）、`MaintenanceGate`
（窗口内写入被拒）、数据目录 advisory lock。

**这一段修掉的是一个已经存在的缺陷，不只是为 GC 铺路。** D2.1 之后四个 store 各自持有
`Mutex<Connection>`、指向同一个文件，于是 `save_web_package` 的"写 blob"（web_package.rs:283）
与"写包事务"（web_package.rs:285）之间没有任何互斥：一条观察路径落在那里就会看到一个
"有 metadata、无引用"的 blob。`DESK-065` 把这个窗口写成"GC 引入后才成立的风险"，
实际上它在 D2.1 落地那天就可以发生。

单实例用 `fs4` 的数据目录 advisory lock，**不用** `tauri-plugin-single-instance`——后者按 app id
判定，挡不住"不同 app id、同一数据目录"，且会迫使 V1 引入第一个 Tauri 插件。`DESK-068` 记录了
这个选择与它排除的失败模式。

退出门禁：第二个进程在同一数据目录上拒绝启动并给出可诊断提示；维护窗口内 `enter_write()`
返回 `MaintenanceBusy` 且不留任何写入痕迹；四个 store 共用一条连接（外部持锁时其它路径阻塞）；
锁文件在释放后仍然存在。全部经**注入验证**（去掉维护窗口后对应断言变红）。

已落地：`maintenance.rs`、`library.rs`、`store::SharedConnection`、`LocalLibrary` 作为唯一
`State`、`maintenance-busy` 错误码进 contracts 与 fixture、两条结构门禁
（"store 只经由一个 managed state"、"写许可在变更 command 上而在读取 command 上不出现"）。

##### D2.2b 完整性审计

按 `DESK-066` 分桶并跑 `PRAGMA foreign_key_check`。只报告，不修复。

`DESK-066` 在本段补了第六桶 `record-without-reference`：外键方向是"引用行 → 包记录"，因此
数据库不约束"每个包记录都必须有引用行"，而缺引用行的包对用户表现为"打不开"。同时明确
V1 **不**纳入 `quick_check`：它回答的是"文件是否损坏"而非"不变量是否成立"，纳入会让桶的含义
从本地库语义滑向引擎健壮性。

退出门禁：六类都能报出且不误删；FK 违规通过注入一个真实的外键违反来验证可检出；审计期间
写入被拒而读取仍可用。

已落地：`audit.rs`（六桶 + 分母）、`audit_local_library` command、`test_fixture.rs`

渲染层分组与维护冲突重试。

**注入验证**（每条都真的让对应测试变红，而不是仅在顺利路径上断言）：

##### D2.2c 孤儿 GC

只删不在任何引用表中的 blob。判定**只**依据引用表，`last_referenced_at` 不参与（`DESK-065`）。
标记—再确认。删除顺序由 `DESK-072` 固定为"先 metadata 后文件"——反过来崩溃后会留下
`DESK-051` 禁止的悬空记录。

对回收收益要有正确预期：Web 包的 purge 目前**没有 UI 入口**，所以用户主动 purge 之前，
GC 基本只回收崩溃窗口的孤儿。这是符合规格的预期，不应被当作"回收站清盘"来宣传。

Web 侧**不**实现 GC：IndexedDB 的 `put` / `purge` 都在单个跨 store 事务里完成，事务原子性
意味着不会产生孤儿，`DESK-055` 的可达性规则已天然满足。

已落地：`gc.rs`、`collect_local_garbage` command、GC 结果与错误码进 contracts 与 fixture、
渲染层的 `collectLocalLibraryGarbage` 与 `gcReclaimedSomething`。

**一处必须诚实记录的取舍**：桶五（记录缺引用行）的包，其字节**会被 GC 回收**。这不是 bug，
而是 `DESK-065` 的直接后果——判定依据是引用表，而该 digest 确实不在引用表里。关键在于
**这类包在 GC 跑之前就已经打不开**（`readArchive` 找不到 digest），所以回收不额外造成损失；
真正的损失发生在引用行丢失的那一刻，而那由审计的桶五负责暴露给用户。GC 的职责是让磁盘
回到与引用表一致的状态，不是在损坏发生后做抢救。若允许 GC 参考包记录的 `deletedAt`，
它就必须开始解释那个字段的语义——那是 TypeScript 的领域知识。

**门禁形态上的一处调整**：条件 DELETE 的 `NOT EXISTS` 在维护窗口内**恒为真**（窗口已排除
并发写入），因此无法在无头环境里触发。原计划的"为它造一个并发场景"会得到依赖时序的
脆弱测试，CI 上只会偶发红。改为两层谓词一致性门禁：把候选集查询或条件 DELETE 任一处的
`NOT EXISTS` 换成恒真条件，`a_clean_library_reclaims_nothing_but_still_scans` 与
`the_delete_guard_and_the_candidate_query_agree` 就会变红（已实测）。

删除顺序同样无法用运行期测试覆盖（要在两步之间断电），因此由结构门禁钉住源码里的语句
顺序。

#### D2.3 Portable archive（Web 与 Desktop 共用）

交付物：`@mahoshojo/local-library` 持有 portable archive manifest 契约（V2，覆盖 cards、web packages
与 blobs）、Web IndexedDB adapter 与 Desktop SQLite/blob adapter 都能产出与消费、导入前展示摘要与
冲突策略、Web 侧设备级承载页面。

退出门禁：Web 导出的包可被 Desktop 导入，反向亦然；`archive.test.ts` 的"无 Provider 秘密字段"断言
对 V2 同样成立；导入全程零网络请求；**不要求登录**即可完成；**导入在真实 WebView 里复核绝对内存
与响应性**（`DESK-070` 已要求真机复核渲染层绝对值，这条把它明确为 D2.3 的退出门禁而不是可选复核）。

D2.1 踩过的坑要写进本阶段退出门禁：

- **portable manifest 里的包内容摘要与归档字节摘要 MUST 是两个明确命名、明确验证的字段**，
  **MUST NOT** 再次用一个泛化的 `digest` 混过去。`DESK-063` 说明了这两者为什么必然不同。
  具体形态由 `DESK-059b` 固定：Web 包条目 **MUST** 是独立 schema，**MUST NOT** 复用 V1 的
  asset 条目——后者的 `superRefine` 要求 `checksum === contentDigest` 且 path 由它推导，
  这两条对 Web 包全部不成立，复用会让每一条真实包都被自己的 `superRefine` 拒绝，
  而症状表现为"所有包都导入失败"。
- **大归档的内存与性能门禁**由 `DESK-070` 固定，且**拆成三个上限**：打包输入、最终归档输出、
  单次 IPC 块。归档上限 **MUST NOT** 复用 `MAX_BLOB_BYTES`（那是**单个** blob 的上限；一个含几十个
  包的归档轻松超过它，而每个包都远小于 64 MiB）。输入上限 MUST 由实测推导：合成归档上记录渲染层
  与 native 的峰值内存。本阶段要么切 Tauri raw IPC（command 返回 `tauri::ipc::Response`，前端收
  `ArrayBuffer`），要么按需流式传输；**MUST NOT** 沿用"整包 base64 过 JSON"而不给出实测数字。
- **导出 MUST 全程不持维护窗口**（`DESK-071b`，D2.3r3 修订）：自洽性由内容寻址与
  `BlobStore::read` 的摘要校验保证，而不是由锁保证；并发只能让导出**失败**，不能让清单与载荷
  错配。**MUST NOT** 整段导出持维护窗口——那会在 `zipSync` 阻塞主线程期间让用户唯一能点的
  "取消"也失败。导出的一致性是"列举时刻的快照"，**MUST NOT** 描述成强一致。
- **不可信归档的解压边界由 `DESK-074` 固定，且它不是性能优化**：manifest 优先是格式属性，
  只有先读清单才能在任何分配发生前拒绝超限输入。bounded streaming import 是 D2.3c 的 mandatory
  项，**MUST NOT** 归入 D2.3e 的"可选流式优化"。
- portable archive 的**业务语义继续归 TS 权威实现所有**，native 保持 SQLite/blob mechanism。
  **MUST NOT** 为了产出 portable archive 而让 Rust 实现 ZIP、manifest 或 canonicalization 规则。
- 导入 **MUST** 全程零网络请求，且这条 MUST 由可执行断言证明（导入路径上任何 fetch/XHR 抛错），
  **MUST NOT** 只靠代码审查声称。
- 回收站 UI（软删后的恢复入口）**不属于**本阶段退出门禁。Web 侧目前"删除即删除"，这是个
  真实缺口，但把它与导出/导入塞进同一阶段会让 D2.3 无法独立验收。

##### D2.3a manifest V2 契约（已落地）

`packages/local-library/src/archive.ts` 的 V1 由 V2 **直接替换**，不保留 V1 reader。V1 零 producer、
零 consumer，野外不存在 V1 归档；为一个永远没人产出的格式维护代码是负债。V1 的 `assets`
命名空间一并移除——`DESK-054` 已确认四种数据卡 schema 均无图片字段。`formatVersion` 因此**从
`2` 起步**而不是从 `1` 递增。理由与规范性要求见 `DESK-059c`。

容器层面的规范化要求（布局、路径可移植性、stem 派生、严格 UTF-8 与 JSON 解析、错误类型一致性）
此前只散落在 `DESK-052`/`DESK-059b` 的几句提示里，实际实现时被逐条追问出来，因此补成
`DESK-059c` 而不是留在计划里。

**实现中被测试抓出的两个真实缺陷**，两者都属于"派生规则与 schema 各自正确、合起来错"：

1. `con` 归一化后**恰好仍是 `con`**——只做字符替换与首尾修整的 stem 规则把它原样吐出，于是
   `cards/con.json` 在 Windows 上根本无法创建。首版修法是追加 `-`，**也是错的**：保留名判据
   `^con(?:\.|$)` 只看开头，`con.txt` → `con.txt-` 仍然是设备名。必须前缀。门禁因此不止断言
   "stem 形状合法"，还断言**派生出的完整路径能被 schema 接受**。
2. 记录解析漏了 `JSON.parse`，把解码出的字符串直接喂给记录 schema。这条在实现时不会立刻暴露
   ——任何失败都表现为"校验不通过"，看起来无害；但它把"语法错误"和"校验失败"分成了两类异常，
   导入侧按 `ZodError` 做的分类统计会漏掉前者。

两处修法都经注入验证：移除保留名前缀 → 2 条断言变红；移除 `parseJsonStrict` → 1 条变红。

门禁：local-library 106 个测试（新增 23 条）、repo 172。未落地部分：D2.3b ZIP 机制与 Desktop
导出、D2.3c Desktop 导入、D2.3d Web 页面。

##### D2.3r D2.3 落地前的 remediation 与 spec freeze

D2.3b1 之后的审查发现两类问题：一类是**已在生产**的缺陷（不属于 D2.3 的范围，却因 D2.3b1 才被
注意到），一类是 D2.3b2 若直接开工就会返工的协议缺口。因此在 b2 之前插入一个 checkpoint，而不是
继续写 b2。

分两段的理由是它们的风险来源完全不同：`r0` 修的是线上缺陷，`r1` 改的是规范口径。混在一个提交里
时，review 无法判断"这次改动为什么必须现在做"。

**D2.3r0（已落地）线上缺陷：ZIP 固定条目时间在 UTC 以西的时区抛错。**

两处生产打包器都把 `new Date('1980-01-01T00:00:00.000Z')` 交给 `zipSync`。ZIP 的 DOS 日期字段
无时区，而 fflate 用**本地时间 getter** 编码并校验 1980–2099，因此该字面量在
`TZ=America/Los_Angeles` 下是本地 1979-12-31 16:00，年份越界后直接抛
`date not in range 1980-2099`。

把它单列而不是并入"b2 的 remediation"，是因为它已经是**线上缺陷**：`packWebPackageZip` 被
`useWebPackagePresetDownload`、`useSoloWebPackageSection.downloadFromLibrary` 等调用，即 UTC 以西的
用户当时无法导出 Web 包。仓库自己的测试在 `TZ=America/Los_Angeles` 下实测 37 条 web-package 与
5 条 local-library 用例变红——**测试是绿的，因为 CI 跑在 UTC**。

同批修掉两处测试夹具里同样的字面量。它们模拟的是"别的工具打出来的 ZIP"，但在美洲时区下会让 30 条
导入用例变成"打包器坏了"，症状与根因完全无关。

顺带把归档确定性的表述改为诚实限定（`exportedAt` 必然进入字节，见 `DESK-070` 归档的确定性边界），
并补一条断言把这条边界钉死。门禁是 `tests/zip-epoch-timezone.test.ts`：跨时区那条**MUST 起真实
子进程**改 `TZ`（进程内改 `process.env.TZ` 不可靠，V8/ICU 缓存时区，而恒真的门禁比没有门禁更糟）。

**D2.3r3 spec 修订。** 两条口径，只改文档零代码：

- `DESK-071b` 的导出并发模型由"阶段 A 快照 + 阶段 B 搬运"改为**全程不取维护窗口**，
  命令形状由三段状态机简化为 `begin` + `append`；
- 冻结导出目标路径的命名与保留策略（见上面第五条），并把 native 备份目录与导出目录分开。

这次修订的触发点是实现前的代码核对，而不是新的设计构想：`BlobStore::read` 在返回前重算并校验
摘要这件事，把"并发会让归档自相矛盾"这个 r1 未验证的前提直接消掉了。**教训**：r1 冻结并发模型时
把"需要一致性"当成了不变量，却没有先问"不一致的症状具体是什么"。如果当时先写出症状（归档少一条
记录 / 清单与载荷错配），就会看到后者被内容寻址排除，而前者只是"失败"不是"错"。

**D2.3r1 spec freeze。** 改三处规范口径，零代码：

- `DESK-071` 的导出部分由 `DESK-071b` 取代，并把导出改写成"阶段 A 快照 + 阶段 B 搬运"
  （**该并发模型已被 D2.3r3 推翻**，见下"三次推翻"一节；此处保留 r1 当时冻结的口径作为演进记录）；
- `DESK-070` 把一个"归档级字节上限"拆成输入 / 输出 / IPC 块三个，并补上此前完全缺失的
  raw IPC 静默回退风险；
- 新增 `DESK-074` 归档输入的安全模型（manifest 优先、预算维度、existing-wins 冲突策略）。

**D2.3r2（已落地）D2.2 remediation：审计与 GC 的 fail-open。**

`audit.rs` / `gc.rs` 用 `rows.flatten()` 遍历 `rusqlite::MappedRows`，而其 `Item` 是 `Result<T>`
（`rusqlite-0.37/src/row.rs:155`）。`Result<T, E>` 实现了 `IntoIterator<Item = T>`，因此这行
**能编译**——编译器不会拦它。

两个后果方向相反，但都是错的报告：

- 审计的桶遍历跳过出错行 ⇒ 少报问题、分母变小 ⇒ UI 看起来比真实状态更健康；
- 审计的 `known` 集合跳过出错行 ⇒ 集合变短 ⇒ **每一个** blob 文件都被误报成孤儿。

另有三处把失败折叠成"看起来正常"的写法：`scalar()` 的 `unwrap_or(0)`（让"查询失败"与"库里真有
0 条"不可区分，而分母恰恰是审计用来表达"这份'0 个问题'来自多大的库"的）、孤儿字节长度的
`unwrap_or_default()`（给真实存在的文件报 `byteLength: 0`）、目录条目的 `entries.flatten()`。

修法是新增 `store::collect_rows`，它用 `collect::<rusqlite::Result<Vec<T>>>()`——`Result<T, E>`
不实现 `FromIterator`，因此**正确写法在类型上无法被误写成 `.flatten()`**。这不是靠 review 拦，
而是让类型系统替 review 拦。

另有三条门禁，全部经注入验证（分别让对应断言变红）：

| 注入 | 变红 |
| --- | --- |
| `audit_unreferenced` 改回 `.flatten()` | 结构门禁报出那一行的原文 |
| `collect_rows` 内部改回 `Ok(rows.flatten().collect())` | 行为门禁报 `Err` 与 `Ok` 不符 |
| `scalar_i64` 折叠成 0 | 行为门禁报 `left: Ok(0)` / `right: Err(Failure)` |

**为什么严重性排在 r0 / r1 之后**：`rusqlite` 的 `step()` 只在 I/O 错误或类型不匹配时失败，而
"库已损坏"本身已由 `DESK-066` 的 `foreign_key_check` 覆盖。它是真实的 fail-open，但不阻断 D2.3
的任何决策。

##### D2.3b1 ZIP 组装机制与内存实测（已落地）

新增 `packages/local-library/src/archive-pack.ts`（独立 export subpath）与
`scripts/measure-archive-memory.mjs`。

**外层 ZIP 里 Web 包以 `level: 0`（store）写入。** 它们已经是 DEFLATE 过的 ZIP，再压一遍既不省体积
又实打实烧 CPU——对几百 MiB 的库这是导出耗时里最大的一块无谓开销。记录 JSON 仍压缩。门禁用 4 MiB
的 `AAAA…` 载荷：真被压缩归档会缩到几 KiB，断言因此不会与压缩率波动纠缠。

**确定性（限定条件是 `exportedAt`）**：固定条目时间 + 固定条目顺序 + 固定的清单字节 ⇒ **在同一份
`exportedAt` 下**两次导出逐字节相同。归一化顺序**必须**在打包器里做而不是指望调用方排好数组——只排
ZIP 条目顺序并不充分，`manifest.json` 自己就把数组顺序写进了字节。这条是测试逼出来的：最初只排条目
顺序，"与清单顺序无关"那条断言变红，且原因是清单 JSON 变了。

`exportedAt` 是清单的必填字段，因此它**必然**进入字节——此前文档写成"刻意不参与字节布局"，与实现
相反，且因夹具把它钉死而从未被检验。两种用途因此必须分开：判断"库的内容变了没有"比较各记录的
`contentDigest` / `archiveDigest`，判断"打包逻辑变了没有"才在固定 `exportedAt` 下比归档字节。
两者混淆的症状是"同一份库两次导出摘要不同"，而根因是调用方问错了问题。

**实测的方法学比结论本身更值得记。** 三次返工：

1. 基线快照取在合成数据**之后** ⇒ 峰值只测到增量，得出"几百 MiB 的库只多花 1 MiB 堆"；
2. 改用 `process.memoryUsage().rss` 做差值 ⇒ V8 不及时归还内存，第二次的基线已被第一次抬高，差值
   恒为 0；
3. 换成 `setInterval` 采样 ⇒ 合成与 `zipSync` 都是**同步**工作，事件循环被占满，采样器在最危险的
   时刻从未触发。

最终形态：每档跑在**独立子进程**（基线只能来自干净进程）+ `process.resourceUsage().maxRSS`（OS 维护
的高水位，同步峰值也逃不掉）。测得 2.1–2.2×，据此把上限从拍脑袋的 512 MiB 修正为 256 MiB。

**这是架构上限而不是产品上限。** 2.1× 来自 `zipSync` 要求全体条目同时在内存（1×）加完整输出归档
（1×）。改用 fflate 流式 `Zip` 可把峰值降到 O(块大小)。是否为此增加"分块读写归档"的 native command
属于真实架构取舍，**留待 D2.3b2 决定**；`DESK-070` 与 `archive-pack.ts` 的注释都已记录数字与条件。

另：合成数据的 id 由摘要**前 32 位**派生，因此"序号只落在摘要尾部"会让所有包 id 相同、合成库被清单
唯一性检查拒绝。这个坑在实测脚本与测试夹具里各踩一次，已各自用专门辅助函数根治。

门禁：local-library 118 个测试（新增 12 条）、repo 172、lint/build/边界检查全通过。三处关键断言经
注入验证：去掉 `level: 0` → 1 条变红；去掉条目排序 → 1 条变红；去掉顺序归一化 → 1 条变红。

未落地：D2.3b2 Desktop 导出 command（依赖流式与否的取舍）、D2.3c Desktop 导入、D2.3d Web 页面。

##### D2.3b2 取舍：先 `zipSync`，字节传输切 raw IPC，流式延后

三个决定，理由分别独立。**规范性要求见 `DESK-070` 与 `DESK-071b`，本节只记取舍与理由。**

**一、保留 `zipSync`，流式组装延后。** 2.1× 的峰值是 `zipSync` 的固有代价，而消除它需要
"分块读写归档"的一整套 native command。ZIP 已经被封在 `packLocalLibraryArchive` **一个函数**
后面，机制可在不触碰导出 command、Web 页面与导入路径的前提下替换。因此流式是 D2.3e 的一处替换，
不是一处重写。代价必须诚实记下：在此之前，超过输入上限（256 MiB）的库**无法导出**。

**二、字节传输切 Tauri raw IPC，base64 债务在此偿还。** `web-package-bridge.ts` 里早已预登记了这个
决定——"等 D2.3 要搬整个 archive 时再切 raw IPC"。D2.3 已到，且 256 MiB 归档经 base64 会变成
341 MiB 外加一次解码峰值，恰好是 `DESK-070` 明令禁止的形态。

已核对 tauri 2.12 的实际 API，而不是沿用注释里的说法：

- `tauri::ipc::Response::new(Vec<u8>)` 提供 raw 响应，渲染层收到 `ArrayBuffer`。**结构化请求 + raw
  响应可以共存**——限制只在于"命令参数不能来自 raw 请求体"。因此 blob 读取不需要任何自定义封包。
- `InvokeBody::Raw` 取代整个请求体，所以 **raw 请求无法携带结构化参数**。
- **但 header 可以携带元数据**：`InvokeOptions.headers` 在官方文档里明写可通过
  `tauri::ipc::Request::headers()` 在 Rust 侧读取，`ipc/mod.rs:160` 确实有该方法。这一条把"自造
  封包"整条路排除了——原先"raw 请求带不了参数 ⇒ 只能靠不变量"的前提并不成立。

**三、导出全程不持维护窗口（`DESK-071b`）。** 这一条**两次推翻**了本节的早期设计。第一版是
`begin` / `append` / `finish` 三段单飞状态机；第二版改为"窗口内快照 + 窗口外搬运"。两者都错，
但错的方式不同，值得记下来：

第一版的问题在 UX——导出耗时由**用户在做什么**决定，而 `zipSync` 在 renderer 主线程执行，
那段时间 UI 冻结，用户唯一能点的就是"取消"，而取消恰恰要求写入被允许。

第二版的问题是**它解决的问题不存在**。为导出的一致性去申请维护窗口，前提是"并发会让归档自相
矛盾"。但核对代码后这个前提不成立：

- Web 包 id 由 manifest 摘要派生，blob 按字节摘要存储且只写不改（`BlobStore::write` 摘要不符即拒）；
- `BlobStore::read` 在返回前**重算并校验摘要**。

于是渲染层读到的任何一块字节都已被验证为"就是清单将要声明的那个摘要"，清单与载荷不可能错配
——**这与并发无关**。并发只能让导出**失败**（列举后被 purge → `blob-not-found`），不能让它产出错误
结果。keyset 分页配合 `nextLocalTimestamp` 的单调性，并发写入只把新行排到游标之后，只漏不重，
清单的唯一性检查不会被破坏。

因此最终形态是"列举时刻的快照，失败就重试"，窗口是多余的。第二版引入的 native 侧快照物化还要
多写多读 256 MiB，同样是纯浪费。

这与 `DESK-058`（备份 MUST 持窗口）不矛盾，两者 MUST NOT 互相引用为前提：备份的产物要在之后被
用来整体替换当前库，必须是单一时刻的精确快照；导出是给人搬去另一台设备的人工产物。

命令形状也随之简化为两条：`begin_local_archive_export(声明总长)` 与
`append_local_archive_export_chunk(raw, x-export-id)`。**没有 `finish`**——native 在累计字节等于
声明总长时自行核对、`fsync`、原子 rename 并清空会话。三段状态机里最容易泄漏的正是"begin 之后
renderer 崩溃、永远没人 finish"，去掉 `finish` 让"完成"成为字节计数的函数而非需要别人调的动作。

exportId **MUST** 由 native 分配（单调计数器）：它不是鉴权而是 epoch guard，让 renderer 刷新后的
迟到 append 被拒；而 renderer 自己生成的 id 无法让 native 区分"新导出"与"迟到的旧块"。`begin`
MUST 回收任何已存在的会话，使 renderer 刷新导致的泄漏自愈。

**五、命名与保留策略冻结（D2.3r3）。** `DESK-071` 只说"native 自行选择目标路径"，未定义命名与保留；
这条必须先冻结，否则 D2.4 备份会撞上同一个问题——两种语义不同的产物落在同一目录，规则不统一时
用户与排障都无从下手。

- 目录 `<data_root>/exports/`；D2.4 的 native 备份落`<data_root>/backups/`，**不混**；
- 文件名 `local-library-<YYYYMMDDTHHMMSSZ>.zip`（UTC），撞名追加 `-2`、`-3`……；
- **不覆盖**、**V1 不自动清理**、UI 回显绝对路径与所在目录。

后两条的理由不是省事，而是**自动淘汰是未经请求的数据删除**，其最坏失败模式（删掉用户唯一一份
备份）比代价（用户自己清目录）严重得多。"保留 N 个、最旧的出局"这类规则看起来能自圆其说，但
"哪些文件是导出"这个前提一旦不成立（例如用户把家人的备份拷进同一目录），规则就会静默删掉不该
删的东西。真需要清理时，只删 native 自己按上述规则命名、且超过 N 天的。

文件名 **不包含**任何用户数据或记录标题：文件名会出现在系统日志、崩溃报告与文件选择器的最近
列表里，而"记录标题"是用户内容。

**四、导入的安全模型必须与流式组装解耦（`DESK-074`）。** bounded streaming import 是 D2.3c 的
**mandatory** 项，而不是 D2.3e 那个"可选的流式优化"的一部分。理由不是"安全比性能重要"，而是
manifest 优先本身就是格式属性：只有先读清单，才能在解压其余条目之前算出期望路径集与声明总字节，
从而在任何分配发生前拒绝超限输入（OWASP ASVS 5.0 V5.2.3）。把它归到"可选优化"意味着先写出一个
违反该要求的实现。

冲突策略收敛为 existing wins / skip + report，理由见 `DESK-074`。

##### D2.3b2 导出（已落地，除两条需真机实测的门禁外）

四层，从上到下各自可独立验收：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 清单 | `packages/local-library/src/archive-export.ts` | 构造 manifest + 归档字节读取器（**成对返回**） |
| 打包 | `packages/local-library/src/archive-pack.ts` | `zipSync`，输入预算 256 MiB |
| 桥 | `apps/desktop/src/platform/local-archive-bridge.ts` | 分块 + header + 错误归一 |
| 落盘 | `apps/desktop/src-tauri/src/export.rs` | 命名、temp 追加、`sync` + 原子 rename |

**清单与读取器必须成对返回**，因为 `checksum` 是"读取器写出的那些字节"的摘要。分开构造就是允许
两者各说各话，而症状是导入侧报内容损坏——与根因完全无关。

**ExportError 手写 Serialize** 输出 `{code, message}` 而不是枚举名。枚举名会序列化成 `"TooLarge"`，
于是渲染层的 `.strict()` schema 每次都拒收，症状是"UI 拿不到错误码，只能显示无法归类的失败"。

**`includeDeleted: true` 两个来源都要有。** 少了它，导出的归档不带墓碑，下一次同步会把被删的记录
当新记录重新拉回来。门禁对卡片与 Web 包**分别**断言：只覆盖一个时，漏掉那一个的失败在测试里
看不出来（这条是注入验证才发现的——第一版门禁只查了卡片）。

**`MAX_LOCAL_LIBRARY_IPC_CHUNK_BYTES = 4 MiB`，内存侧已论证、吞吐侧未实测。** 内存是能算的：
导出期间同时存在 `zipSync` 的 1× 输入（≤ 256 MiB）+ 完整输出归档（≤ 256 MiB）+ native 侧一块，
总计约 772 MiB，与 `zipSync` 本身的 512 MiB 相比可忽略，因此 4 MiB **不是内存约束的绑定项**，
选它不会把峰值推高到需要重跑内存实测的程度。但块大小对**吞吐**与**回退阈值**的影响必须实测才能
定，而 `DESK-071b`"raw IPC 的静默回退"把它列为退出门禁。因此以下两条**仍然开放**：

- **块大小的吞吐实测**——需要一个真实运行的 Tauri 应用，桌面侧无法在测试里代劳；
- **"未发生 `postMessage` 静默回退"的运行时断言**——回退发生在 `ipc-protocol.js` 的
  `customProtocolIpcFailed`，只有真机能观测。

这两条不是可以先按"看起来合理"记为通过的。它们留在 D2.3b2 的验收清单里，直到有一次真机运行。

**`workspace-structure.test.ts` 的 command 白名单要求每个新 command 显式登记**——本次是它先拦下
了未登记的 `begin_local_archive_export` / `append_local_archive_export_chunk`。

门禁与剩余：Rust 13 条（另 12 条在 export.rs）、跨语言 3 条、桥 15 条、清单 8 条；注入验证覆盖
raw header 漏发、`includeDeleted` 漏发、`readArchive` 误按包 id、Rust 字节上限漂移与归零、
错误码枚举名回退。剩余：D2.3c Desktop 导入（纯 TS，零新增 native surface）、D2.3d Web 设备级
页面与导出、D2.3e 流式组装（可选），以及上面两条需真机实测的门禁。

> **导出目标路径的命名与保留策略已由 D2.3r3 冻结**（`DESK-071b` 末节，`<data_root>/exports/` +
> `local-library-<YYYYMMDDTHHMMSSZ>.zip` + 撞名递增 + 不覆盖 + V1 不自动清理 + native 备份
> 另落 `<data_root>/backups/`）。此前此处标记为"仍未定义"。

#### D2.4 完整备份与恢复

交付物：备份（Desktop 用 `VACUUM INTO` + blob 复制 + 逐个 digest 校验 + 最后写 manifest；Web 用
portable full-library archive）、受控维护窗口、恢复前自动备份当前库。

退出门禁：备份是一致快照（`DESK-058`）；中断的备份不会被当作可用备份；恢复失败不破坏当前库。
`VACUUM INTO` 是 live DB 的一致快照，但中断时输出文件可能不完整——因此"manifest 最后写、
未完成 manifest 不视为有效备份"正是对这一失败模型的回应。

另有一处此前记错的 SQLite 细节：原文写"`VACUUM INTO` 在目标文件已存在时直接失败"。SQLite 文档的
原文是"文件名**MUST NOT** 已存在，**否则它 MUST 是空文件**"——已存在的**空**文件是允许的。
实践上仍然必须写临时路径再 rename（因为非空文件会被拒，且临时路径保证 rename 的原子性），但把
规则写成"存在即失败"会让实现多写一段无用的删除逻辑，并在误判时删掉不该删的文件。

若将来维护窗口实测过长，再考虑 SQLite Online Backup API：它可增量复制，且只在实际读取时短暂
加锁。现在换它属于提前优化。

**备份不含 secret 明文。** native 备份 **MUST** 只备份 Provider Profile 记录与其 `secretRef`，
**MUST NOT** 导出 OS 凭据存储里的明文 secret（`DESK-040`）。恢复后若对应 secret 不存在，
**MUST** 提示用户重新录入。这与"完整备份"的字面含义有张力，因此必须显式写明——否则"完整备份"
会无意中变成一条 secret 导出通道，而备份产物的流转范围通常比用户以为的大。

**备份持维护窗口、导出不持——两者必须显式区分，不得互相引用为前提。** 差异在产物的用途：备份
的产物要在**之后**被用来整体替换当前库，它必须是单一时刻的精确快照；导出是给人搬去另一台设备
的人工产物，`BlobStore::read` 的摘要校验已经保证自洽（见 D2.3r3）。因此备份落
`<data_root>/backups/`，与 D2.3b2 的导出目录分开；两者的命名规则**共享**同一前缀约定但目录独立。

恢复采用**重启时交换**（`DESK-073`），不在运行中热替换。Tauri `manage()` 持有的 owned connection
无法在运行中换掉，而热替换还要处理渲染层的陈旧记录与在途 AI 请求，收益为零；重启时交换的
失败模型 trivially 安全——交换前什么都没动，失败即原样回滚。这条路径反过来依赖 D2.2a：
合并成单一 managed state 之后，"重启时交换"只需要动一个对象。

拆两段：D2.4a 只做备份（纯增量，无破坏性），D2.4b 才做恢复（破坏性路径）。这样备份的正确性
可以先独立验收。

### D3 第一条真实业务纵切

目标是把与服务器无关的魔法少女生成链路接到 Desktop Direct 端口，同时保持 Hosted 路径可用。

约束：**MUST NOT** 搬运 Hosted runtime。逐条判定哪些 prompt、composition、parse、repair 属于
runtime-neutral 并下沉，其余保留在 `hosted-runtime`。

退出门禁：同一业务流程可由 Hosted 或 Desktop 端口驱动；本地旅程对项目域名请求数为 0。

### D4 Web Package 隔离

交付物：独立零 capability webview、默认拒绝浏览器权限、`maho-webpkg://` resolver、overlay 与
单文件目标约束继承既有规格。

**第一道门禁是启用 `AppManifest::commands`，不是创建第二个 webview。** Tauri 的应用自注册
command 默认对**所有** window/webview 可用；要把它们纳入 ACL，必须在 `AppManifest::commands`
里声明。已在 tauri 2.12 源码核对实际判断条件（`webview/mod.rs`）：

```rust
if (plugin_command.is_some() || has_app_acl_manifest || !is_local) && invoke.acl.is_none() { /* 拒绝 */ }
```

即：**当前没有 `AppManifest` 时，自定义 command 对所有本地 webview 全开**。因此在只有 `main-ui`
的当前阶段，`build.rs` 刻意不启用它——而一旦要创建 Web Package webview，没启用就等于那个不可信
webview 也能调全部本地库命令。

**但拆分的理由不是"否则现在就有漏洞"。** 当前只有受信任的 `main-ui`，不构成现存缺陷。真正的
理由是那条**结构门禁**：把 ACL 边界变成可执行断言，在创建第二个 webview **之前**建立，比在
同一批改动里"顺手收 ACL"更容易审计，也更容易在 review 时看清 ACL 的完整形状。

拆成两段：

```text
D4a  AppManifest command ACL + 三方一致结构门禁   —— 建立可执行的边界
D4b  创建 zero-capability Web Package webview    —— 在已验证的边界之内扩张
```

结构门禁比对：

```text
generate_handler! commands  ↔  AppManifest commands  ↔  main-ui capability
```

否则以后每新增一个 native command 都会有人忘记进 ACL，而这种缺失**不会**让任何现有测试变红。

退出门禁：不可信 webview 无法进入任何 IPC；不依赖同源 iframe；新增 native command 未进 ACL
时结构门禁变红。

> `main-ui` 当前使用 `core:default`。该集合实际包含 app/event/image/menu/path/resources/tray/
> webview/window 等一组权限，并不特别小；当前 renderer 主要只用 `invoke` 与 `Channel`。按
> `DESK-011` 的文字目标，后续应做一次 core permission minimization。这不是 D2.1 的阻断项。

### D5 Hosted 集成与发行

交付物：设置页、在线能力适配（按信任级别分流）、错误诊断、Windows x64 安装包、GitHub Actions
构建、updater 签名与 OS code signing 策略记录。

退出门禁：`ACCEPT-007` 可验证；发布私钥为受保护 secret；失败发布不覆写既有资产。

## 2. 提交切分

每阶段按 `skeleton → contract → adapter → UI → tests → docs` 切分为原子提交。大量生成资产
（`Cargo.lock`、`gen/schemas/`、图标）**MUST** 与行为修改分开提交，避免把机械变更混入语义变更。

D2.2 与 D2.4 各再切一层（`D2.2a/b/c`、`D2.4a/b`），理由已写在各自小节：并发地基会改动每一个
command 签名，把它与审计混在一起时地基的回归无法归因；备份与恢复的破坏性风险量级不同。
`D2.3a/b/c/d` 的切分对应"契约 → 机制 → 消费者 → Web 侧"，让每一层都能独立验收。

## 3. 门禁与失败处理

- 任何阶段 **MUST NOT** 以降低门禁强度的方式"通过"；
- 任何阶段 **MUST NOT** 以未实际运行的检查声称 PASS；
- 阶段失败时 **MUST** 回到最近一个退出门禁已通过的状态，或显式记录新的迁移差距；
- 生产动作（发布、凭据变更、代码签名、Updater 激活）不在本计划授权范围内，需要单独授权。
