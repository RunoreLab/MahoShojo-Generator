# MahoShojo-Generator 平台重整分阶段实施计划

状态：`accepted`
日期：2026-08-22
计划标识：`PLAN-platform-restructure-v1`

## 1. 执行原则

1. 不做一次性大爆炸迁移。
2. 目录结构与业务行为分开提交。
3. 每个阶段有可验证退出门禁和可回滚点。
4. Web 生产能力在迁移期间持续可用。
5. Legacy 登录保持行为不变。
6. Client 本地能力优先，Hosted APP 能力后置。
7. 任何服务器权威语义不得下放到客户端。
8. `feat/admin` 以业务域移植，不整分支直接合并。
9. 已冻结的 Arena 多人协作 v1 可以并行推进，但必须保持平台信任与秘密边界。
10. 旧 PVP 去留不阻塞 Arena 多人协作。

## 2. 依赖顺序

```text
Phase 0 盘点与冻结
   │
Phase 1 pnpm workspace 骨架
   │
Phase 2 contracts/domain/ports 提取
   ├───────────────────────┐
   │                       │
Phase 3 Admin             Phase 4 Web 本地库
   │                       │
   └──────────┬────────────┘
              │
Phase 5 Desktop PoC/MVP
              │
Phase 6 Desktop Release/Updater
              │
Phase 7 Mobile PoC/ADR/MVP
              │
Phase 8 旧 PVP 数据决策
              │
Phase 9 可选 Hosted/Sync/iOS/Auth
```

Arena 多人 v1 是并行兼容轨：

```text
current Arena multiplayer spec/plan
   -> 可继续在现有目录实现
   -> Phase 1/2 增加边界与契约回归
   -> 适当阶段迁入 apps/arena-room + packages/multiplayer-core
```

Phase 3 与 Phase 4 在 Phase 2 后可以并行，但同一批核心 package 变更需协调。

## 3. Phase 0：盘点、基线与决策冻结

### 目标

形成重构前可比较的仓库、生产和使用基线。

### 交付物

1. 当前目录、运行时、部署和 secret inventory。
2. API 路由清单：
   - Web-only；
   - Hono migrated；
   - authoritative；
   - Direct candidate；
   - Admin；
   - Arena room/ticket/internal RPC。
3. 现有 IndexedDB/localStorage 清单。
4. `feat/admin` 功能与危险操作矩阵。
5. 90 天旧 PVP 指标查询/报告框架。
6. Legacy/Better Auth 回归测试基线。
7. 生成时长、timeout、abort 和服务器资源基线。
8. Arena 多人 v1 的 DTO/事件/敏感字段夹具清单。
9. 本权威文档集。

### 退出门禁

- 所有生产部署单元和 secret owner 可列出；
- 所有 Admin 写操作可分类；
- 当前 `pnpm test`、`pnpm lint`、`pnpm build` 基线记录；
- Hono 现有部署与回滚继续有效；
- Arena 多人 v1 与平台文档没有未解释冲突；
- 本主题页成为稳定入口。

### 回滚

无运行代码变化。

## 4. Phase 1：pnpm Workspace 骨架，保持行为

### 目标

建立 Monorepo 编排能力，不改变生产行为。

### 建议步骤

1. 新增 `pnpm-workspace.yaml`。
2. 根 package 保持现有应用，先标记为 legacy root app。
3. 新建空/最小 `apps/`、`packages/` 和 `apps/arena-room` 占位说明。
4. 增加 root filter scripts。
5. 建立 package exports 和路径解析 PoC。
6. 增加 dependency boundary 检查。
7. CI 同时运行旧命令和 workspace 命令。
8. 不移动 Arena 多人当前实现，先增加未来目标路径说明。

### 退出门禁

- lockfile 无非预期漂移；
- 原 Web/Hono build 输出等价；
- tests/lint/build 通过；
- 生产部署路径不变；
- 无跨 APP 依赖；
- 无业务 schema 迁移；
- Arena 多人规格夹具仍通过。

### 提交策略

建议单独提交：

```text
chore(repo): 建立 pnpm workspace 骨架
```

不得与 Admin、Desktop、本地库或多人业务改写混合。

## 5. Phase 2：共享协议、领域与能力端口

### 目标

为多 APP 复用建立最小稳定内核。

### 首批提取

1. `packages/contracts`
   - card schemas；
   - provider request/result；
   - error codes；
   - API version；
   - Arena room DTO/event version。
2. `packages/domain`
   - 数据卡纯校验；
   - provenance 状态；
   - 不依赖 runtime 的 Arena/Creator 逻辑。
3. `packages/ai-core`
   - Prompt；
   - stream event；
   - JSON repair；
   - result schema。
4. `packages/local-library`
   - record/migration/export contract。
5. `packages/cloud-client`
   - 当前项目 API client contract。
6. `packages/multiplayer-core`
   - shared config projection；
   - typed Proposal；
   - revision/conflict；
   - 纯函数与夹具。
7. 端口：
   - `AiExecutionPort`
   - `CardRepository`
   - `SecureVault`
   - `FilePort`
   - `UpdatePort`

### Arena 多人迁移原则

- 不要求先完成 Monorepo 才能开发 v1。
- 只提取已经稳定且两个部署单元都需要的契约。
- DO、Worker、Next/Hono runtime code 留在应用层。
- 先运行现有 v1 tests，再移动路径。
- 不能借提取扩大 Room Shared Config 或改变 host-only generation。

### 退出门禁

- Web 继续消费新 package；
- 至少有一个 in-memory contract test harness；
- 无 package 导入 app；
- contracts 可在 Node、Worker 和浏览器测试环境加载；
- current fixtures 通过；
- Arena Room DTO/事件兼容测试通过。

## 6. Phase 3：Admin 回归主线和安全上线

### 目标

结束 `feat/admin` 长期分支，同时不把本地可信假设带到公网。

### 迁移批次

按风险由低到高：

1. read-only dashboard/analytics；
2. content list/detail；
3. messages/report review；
4. user write/badge/redemption；
5. ratings/PVP/Arena room recovery；
6. data maintenance/export/system config。

每批包括 UI、route/API、repository、RBAC capability、audit、tests 和 rollback。

### 安全工作

1. Cloudflare Access Application。
2. Cloudflare Tunnel。
3. Origin JWT validation。
4. internal admin allowlist/capability。
5. CSRF/session/CORS policy。
6. high-risk reason/idempotency/version。
7. direct-origin bypass test。
8. audit retention。

### 退出门禁

- Admin 不依赖切换 Git branch；
- 未授权和错误 audience 被拒；
- browser 无 D1 credential；
- 所有写操作有 capability；
- destructive 操作有审计；
- 旧 `feat/admin` 标记只读/归档；
- 主线 tests/build 通过。

### 回滚

- Access policy 可立即 deny；
- Admin host 可下线而不影响公共 Web；
- 每个迁移域可独立 feature flag；
- 不删除旧 Admin 数据表。

## 7. Phase 4：Web 本地库

### 目标

先在现有 Web 验证本地库语义、数据模型和显式复制流程。

### 工作项

1. 独立 IndexedDB。
2. LocalCardRecord v1。
3. repository + migration。
4. 列表、搜索、详情、编辑。
5. 保存目标选择。
6. 本地 -> 线上上传副本。
7. 线上 -> 本地下载副本。
8. import/export archive。
9. storage persist/estimate UI。
10. backup warning。
11. local library 不占 slot 回归。
12. Arena 单人可选本地卡；Arena 多人只发送规格允许投影/stub。

### 退出门禁

- 断网创建/编辑/导出可用；
- 清晰标注 Local/Cloud；
- 1000 卡性能基线；
- 导出导入 round-trip；
- 升级 migration test；
- 上传失败不损坏本地；
- 无自动同步文案；
- 多人事件不泄漏本地完整 payload。

### 回滚

本地库功能可 feature flag 关闭；已有 IndexedDB 不主动删除。

## 8. Phase 5：Desktop Tauri PoC 与 MVP

### PoC 范围

用代表性切片验证，不先复制全部 Web 页面：

1. 首页/导航；
2. 卡片列表和编辑；
3. Direct Provider 设置；
4. 自定义 OpenAI-compatible Endpoint；
5. localhost 模型；
6. stream/cancel；
7. SQLite 本地库；
8. Stronghold secret；
9. import/export；
10. 在线卡库只读/登录适配；
11. Arena 单人本地卡与 Direct AI；
12. Arena 多人入口使用服务器权威链路，不传播 Provider。

### 安全实现

- 本地打包 UI，不加载远端主应用；
- capabilities 最小化；
- Native Direct Executor；
- no generic shell/fs/fetch；
- IPC payload schema；
- logs redaction；
- CSP；
- external link allow rules。

### Desktop MVP

PoC 通过后补：

- 完整本地工作流；
- APP 设置；
- update UI；
- crash-safe local migrations；
- compatibility/version handshake；
- optional online capabilities。

### Tauri 失败门禁

只有出现 ADR 中列出的核心失败并有 PoC 记录，才启动 Electron fallback spike。

### 退出门禁

- `ACCEPT-001` 至 `ACCEPT-005` 通过；
- `ACCEPT-009` 多人敏感信息检查通过；
- Windows x64 至少有可安装包；
- Direct Key 不离设备；
- local model 长流可取消；
- restart 后本地库稳定；
- no server secret in bundle。

## 9. Phase 6：Desktop GitHub Release 与 Updater

### 工作项

1. SemVer/tag policy。
2. GitHub Actions platform matrix。
3. protected release environment。
4. Tauri updater key pair。
5. private key offline backup。
6. MSI/NSIS/AppImage/macOS assets（按已支持平台）。
7. `latest.json`。
8. SHA-256。
9. artifact attestation。
10. draft -> publish release。
11. update check/download/install/rollback UX。
12. immutable releases（如仓库启用）。

### 退出门禁

- clean VM install；
- upgrade N-1 -> N；
- bad signature rejected；
- downgrade rejected或有明确策略；
- missing asset graceful failure；
- Release 指向正确 commit；
- secrets 不出现在 Actions log；
- GitHub asset 和 attestation 可验证。

### 回滚

发布问题使用新 patch version 修复，不替换已发布二进制。

## 10. Phase 7：Mobile PoC、ADR 与 MVP

### 比较候选

- Tauri Mobile；
- Capacitor。

### 同一 PoC

严格使用实施规格中的 Mobile PoC 门禁，避免两个候选使用不同标准。

### Android 优先

首个移动发行目标建议是 Android：

- signed APK；
- GitHub Release；
- version check；
- user-confirmed install；
- local library；
- Direct AI；
- file share；
- Arena 多人安全 DTO。

### iOS

独立工作流，仅在签名和分发路径确定后进入实现。

### 退出门禁

- 形成 Mobile Runtime ADR；
- Android 真机 Direct/SQLite/Vault/import/export 通过；
- stable signing key backup；
- 不宣称 Desktop updater 覆盖 mobile；
- offline first launch 可用；
- 多人 DTO 不包含本地 Provider/secret。

## 11. Phase 8：旧 PVP 使用评估与去留

### 工作项

1. 查询 90 天指标。
2. 区分打开页面、建房、开局、完成和复玩。
3. 估算 AI 与 D1 成本。
4. 盘点与 Arena 多人和未来玩法的复用。
5. 提交独立决策：
   - 保留并维护；
   - 只读归档；
   - 产品层移除、抽取 multiplayer-core。

### 如果下线

严格按 `PVP-002` 顺序，不提前 DROP schema。

### 退出门禁

- 指标与查询口径可复核；
- 用户数据归档策略明确；
- multiplayer-core 清单明确；
- 不破坏 Arena 多人 v1；
- rollback window 明确。

## 12. Phase 9：后置可选工作

仅在前述阶段稳定后考虑：

- Desktop/Mobile Hosted AI；
- local/cloud linked sync；
- conflict resolution；
- iOS 正式发行；
- native signature key ID/rotation；
- non-HMAC public verification；
- Auth/Legacy 收口；
- 多人 Direct 非权威模式；
- richer local model management。

每项应单独 ADR/spec，不自动成为本计划范围。

## 13. 测试矩阵

| 层级 | 必测 |
| --- | --- |
| packages | unit + contract + typecheck |
| Web | IndexedDB migration、upload/download、auth regression |
| Admin | Access JWT、RBAC、CSRF、audit、destructive action |
| API | auth/signature/rating/multiplayer authority |
| Arena Room | DTO allowlist、Proposal、revision、Hibernation、cleanup、single generation |
| Desktop | IPC schema、Direct stream、Vault、SQLite、updater |
| Mobile | 真机 Direct、SQLite、Vault、文件、签名安装 |
| Release | clean install、upgrade、bad signature、attestation |
| Security | secret scan、bundle scan、Direct credential isolation、room leak scan |

## 14. 首批建议 PR

1. **文档与边界**：本次文档提交。
2. **Workspace 骨架**：只建立 `pnpm-workspace.yaml`、apps/packages 空骨架和等价命令。
3. **Contracts 与 boundary check**：提取首批 schema，纳入 Arena Room DTO 兼容测试。
4. **Local library contracts**：定义记录、repository、migration 和 archive format，不做 UI。
5. **Web local library MVP**：IndexedDB 和显式复制。
6. **Desktop Tauri PoC**：只做代表性垂直切片。

Admin 工作可在 PR 3 后按业务域并行；Arena 多人 v1 可继续按其领域计划推进。
