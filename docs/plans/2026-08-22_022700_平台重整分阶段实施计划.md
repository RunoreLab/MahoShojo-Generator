# MahoShojo-Generator 平台重整分阶段实施计划

状态：`accepted`
日期：2026-08-22
最近修订：2026-08-23（补充 Phase 2.5 Hosted 主执行面/Cloudflare DR 容灾门禁，并保留既定应用边界顺序）
计划标识：`PLAN-platform-restructure-v1`

## 1. 执行原则

1. 不做一次性大爆炸迁移。
2. 目录结构与业务行为分开提交。
3. 每个阶段有可验证退出门禁和可回滚点。
4. Web 生产能力在迁移期间持续可用。
5. Legacy 登录保持行为不变。
6. Client 本地能力优先，Hosted APP 能力后置。
7. 任何服务器权威语义不得下放到客户端。
8. `feat/admin` 以业务域移植，不整分支直接合并。
9. 已冻结的 Arena 多人协作 v1 保持为兼容业务轨；在 Phase 2.5 退出前，只继续共享契约、纯逻辑、真实 consumer 接入、兼容/安全测试和阻断性修复，不继续展开 Durable Object、WebSocket、D1 directory、ticket/auth、GenerationBridge runtime 或多人 UI 等重运行时工作。
10. 旧 PVP 去留不阻塞 Arena 多人语义冻结，但不得借 PVP 或多人功能轨延后平台关键路径。
11. 平台关键路径优先于单一功能纵向深挖：当领域计划与本计划争用同一重构分支、共享 package 或运行时边界时，先满足当前平台 Phase 的退出门禁，再恢复领域 runtime 阶段。
12. `apps/*` 的 README、空目录或仅有占位 manifest 不计为 MONO-002 完成；只有形成真实源码所有权、独立 manifest、命令、环境/部署入口及适用的 health/readiness，才视为应用边界已激活。
13. 不以“迁移覆盖率”作为继续扩大 Hono 路由面的目标。新增迁移必须有明确的运行时、成本、可靠性、安全或平台解耦收益；否则保持现有双轨回滚面并优先完成应用边界。
14. Hono HK 是 Hosted 默认主执行面；Cloudflare Next/OpenNext 对显式 DR manifest 能力保留长期灾备 adapter。必须删除 legacy app-to-app import/wrapper，但不得把这与删除 DR adapter 混为一谈。
15. Hosted failover 先服从业务幂等/重放语义：safe/read 可自动切换；generation/stream/settlement 不允许在“可能已执行”后盲目跨 runtime 重放。


## 4. Phase 1：pnpm Workspace 骨架，保持行为

### 目标

建立 Monorepo 编排能力，不改变生产行为。

### 建议步骤

1. 新增 `pnpm-workspace.yaml`。
2. 根 package 保持现有应用，先标记为 legacy root app。
3. 新建空/最小 `apps/`、`packages/` 和 `apps/arena-room` 占位说明。
4. 增加 root filter scripts。
5. 建立 package exports 和路径解析 PoC。
6. 增加 dependency boundary 检查。
7. CI 同时运行旧命令和 workspace 命令。
8. 不移动 Arena 多人当前实现，先增加未来目标路径说明。

### 退出门禁

- lockfile 无非预期漂移；
- 原 Web/Hono build 输出等价；
- tests/lint/build 通过；
- 生产部署路径不变；
- 无跨 APP 依赖；
- 无业务 schema 迁移；
- Arena 多人规格夹具仍通过。

### 提交策略

建议单独提交：

```text
chore(repo): 建立 pnpm workspace 骨架
```

不得与 Admin、Desktop、本地库或多人业务改写混合。

## 5. Phase 2：共享协议、领域与能力端口

### 目标

为多 APP 复用建立最小稳定内核。

### 首批提取

1. `packages/contracts`
   - card schemas；
   - provider request/result；
   - error codes；
   - API version；
   - Arena room DTO/event version。
2. `packages/domain`
   - 数据卡纯校验；
   - provenance 状态；
   - 不依赖 runtime 的 Arena/Creator 逻辑。
3. `packages/ai-core`
   - Prompt；
   - stream event；
   - JSON repair；
   - result schema。
4. `packages/local-library`
   - record/migration/export contract。
5. `packages/cloud-client`
   - 当前项目 API client contract。
6. `packages/multiplayer-core`
   - shared config projection；
   - typed Proposal；
   - revision/conflict；
   - 纯函数与夹具。
7. 端口：
   - `AiExecutionPort`
   - `CardRepository`
   - `SecureVault`
   - `FilePort`
   - `UpdatePort`

### Arena 多人迁移原则

- 不要求等待整个 Monorepo 最终形态才保留和验证 v1 契约，但领域 runtime 开工必须服从本计划的平台阶段门禁。
- 只提取已经稳定且存在真实跨运行时消费者的契约/纯逻辑；不得为了多人单一功能把 Phase 2 扩张成 Room runtime 实现阶段。
- Phase 2.5 退出前，允许完成 `BattleStoreState -> ArenaRoomNormalizedSource` 等真实 Web consumer adapter、兼容夹具、安全负向测试和阻断性修复。
- DO、Worker、WebSocket、D1 directory、alarm、ticket/auth、GenerationBridge ingress、多人 UI 等 runtime code 在 Phase 2.5 后恢复，并直接落到目标 app/runtime 边界。
- 先运行现有 v1 tests，再移动路径；不能借提取扩大 Room Shared Config 或改变 host-only generation。

### Phase 2 收口优先级

Phase 2 不要求机械创建所有目标 package 的空壳；只提取下一阶段真实需要且可以证明有两个以上消费者、跨运行时复用需求或依赖倒置价值的最小公共面。当前优先级为：

1. 补齐 `packages/contracts` 的通用 card/provider/API/error 契约，避免其长期退化为 Arena-only package；
2. 建立最小 `packages/domain`，先容纳 Web/API/Desktop 都需要的纯领域校验与状态语义；
3. 建立 `packages/ai-core` / Direct 请求模型与 `AiExecutionPort`，让 Hosted adapter 与 Native Direct adapter 共享结果/流契约而不共享秘密；
4. 建立 `packages/local-library` 的 record/migration/archive contract 与 `CardRepository`；
5. 按真实调用需要建立最小 `packages/cloud-client` 和 `SecureVault` / `FilePort` / `UpdatePort` 等端口；
6. 让至少一个现有 Web 路径真实消费上述 package，避免 package 只被测试夹具消费。

若某个目标 package 暂无真实消费者，应记录延期而不是创建职责不清的空 package。

### 退出门禁

- Web 至少有一个真实生产路径消费新 package，而不只是测试或多人专用夹具；
- 至少有一个 in-memory contract test harness；
- 无 package 导入 app；
- contracts 可在 Node、Worker 和浏览器测试环境加载；
- Direct/local-library 所需的最小跨运行时 contract/port 已存在，足以支持 Phase 4 与 Phase 5A；
- current fixtures 通过；
- Arena Room DTO/事件兼容测试通过。

## 5.1 Phase 2.5：真实应用边界激活

### 目标

把当前“workspace 骨架 + legacy root app”推进为真实多应用仓库，使后续 Admin、Desktop 与 Arena Room 都建立在已经验证的部署/依赖边界上，而不是继续在根单体中增加功能后再二次搬迁。

本阶段仍遵循行为等价迁移：不借目录搬迁重写产品流程、认证语义、数据库 schema 或 Arena v1 协议。

### 激活顺序

1. **`apps/d1-gateway`**
   - 优先迁移当前相对自洽的 `server/d1-gateway` Worker；
   - 保持 D1 binding、HMAC/Access、Wrangler 配置、部署与 health 行为等价；
   - 以该应用验证真实 workspace app 的 manifest、filter、CI 与独立部署入口。
2. **Hono 运行时解耦，不扩大路由面**
   - 先停止让迁移架构继续依赖“`apps/api` 动态导入未来 `apps/web/app/api/*`”这一结构；
   - 将现有 Hono 白名单所复用的业务逻辑逐步下沉到共享 service/domain/ai-core 边界，由 Next Route Adapter 与 Hono Adapter 分别调用；
   - 允许短期 legacy import/wrapper 共存以保持搬迁回滚，但必须有明确删除门禁，不能把 app-to-app 源码导入作为目标架构；删除 legacy 层后，按 DR ADR 经过 contract test 的 Next 灾备 adapter 继续长期保留。
   - 2026-08-24 Phase 2.5B 已完成这一结构退出：保留 10 条 shared-service capability，明确退出 14 条继续由 Next 承载的 capability，Hono 生成链不再拥有 legacy Next route 动态导入能力；这不等于 `apps/api` 已激活。
3. **`apps/api`**
   - 在 Hono 的核心入口不需要导入另一个 app 内部源码后，迁移 `server/` 的 Node runtime、配置、Redis middleware、health、build/deploy 到独立 workspace app；
   - 现有 Hosted 生成路由集合保持兼容，不以本阶段为由新增一批普通 CRUD API。
4. **`apps/web`**
   - 将 legacy root Next 应用做行为等价搬迁；
   - 同步迁移 Next/OpenNext config、测试、别名、静态资产和 Cloudflare 部署入口；
   - 为后续 Hosted DR 保留显式 runtime adapter seam，但不在目录搬迁 PR 中同时上线自动切流；
   - 搬迁 PR 不同时实现 Web 本地库、Admin 或大规模 UI 重构。
5. **根目录收口**
   - 当 Web/API/D1 Gateway 已拥有真实 app manifest 后，根 `package.json` 向 workspace 编排、统一工具和顶层验证收口；
   - runtime 依赖应归属实际 app/package，不继续因为历史原因全部堆在根 manifest。

`apps/admin`、`apps/desktop`、`apps/arena-room` 应在其实际实现阶段建立真实 manifest/runtime；不得为了让目录看起来完整而提前创建无真实职责的应用空壳。

### Hono 路由扩张门禁

Phase 2.5 退出前，`config/hono-api-routes.json` 默认冻结新增迁移。只有满足以下至少一项时才例外，并在变更说明中记录理由和回滚：

- 必须使用 Node/Hono runtime 才能满足长流、Hosted 生成、签名或其他已接受的服务器能力；
- 有可测量的 Cloudflare 资源、延迟、可靠性或限流收益；
- 为 `apps/api` 独立化或 Arena 权威 GenerationBridge 提供必要边界；
- 修复生产安全/可靠性问题。

“该 handler 也能在 Hono 运行”本身不是迁移理由。

### Hosted DR 激活与故障门禁

Phase 2.5 同时把已有“双轨回滚”收口为可长期维护的 DR seam，但不要求在一个 PR 内购买/启用具体 Cloudflare Load Balancing 产品：

1. **路由语义盘点**
   - 以当前 Hono route manifest 为 source of truth，逐项标记 `safe-read`、`durably-idempotent-command`、`non-idempotent/stream`；
   - 新增长期 DR capability/route manifest，默认只收录已经共享 core、具备 contract test 的能力；
   - 不复制完整动态路由表到文档。
2. **稳定逻辑入口**
   - 去除“客户端必须知道物理 Hono origin 才能使用 Hosted”的目标耦合；
   - 切流控制面独立于 Hono 主机，切换 DR 不要求重新发布前端/APP；
   - 选择 Cloudflare Load Balancing、等价边缘路由或其他方案前，必须评估是否会把 SSE/长流重新变成 Workers CPU 热点。
3. **跨 runtime 数据与 secret**
   - Hono 使用 D1 Gateway；Cloudflare DR 尽量使用独立 D1 binding/Sessions provider；
   - 两边运行同一 consistency contract/bookmark 规则；
   - DR secret 只按 capability 最小复制，缺失 capability fail closed。
4. **非幂等保护与 active-passive**
   - DR 默认 active-passive，不把权威/非幂等写流量随机分摊到 Hono/Next；
   - generation/stream/settlement 在请求开始前选择 runtime；
   - 请求可能已经到达 Hono/Provider 后，连接失败不得触发透明第二次 POST；
   - 使用稳定 `generationRequestId`/operation ID、attempt、状态查询和结果恢复。
5. **Standby freshness / version skew**
   - DR adapter 随 shared core 持续 build/contract test，并保持当前可接管 artifact；
   - schema/contract 变更按 expand -> Hono/DR rollout -> contract 清理，禁止先做破坏性变更再等待备用端追赶；
   - synthetic probe/版本信息能够证明 DR 仍兼容当前 public contract。
6. **主执行面 telemetry**
   - 补齐 CPU、RSS/heap、event-loop、active request/stream/socket、AI upstream、D1、Redis 和 runtime/failover 指标；
   - 先记录基线，再冻结容量告警；readiness 不只看单一 CPU。
7. **故障演练**
   - Hono down；Redis down/flush；D1 Gateway down；generation mid-flight disconnect；D1 down；DR secret missing；Hono/DR version skew；
   - 记录实际恢复时间和人工步骤，不在没有测量时虚构 RTO/SLA。

### 退出门禁

- `apps/d1-gateway`、`apps/api`、`apps/web` 均为真实 workspace project，并拥有各自 manifest、build/test/lint、环境说明和部署入口；
- `apps/api` 不直接导入 `apps/web` 内部源码；现有 Hono/Next 双轨通过 adapter/shared package 复用业务逻辑；
- 根 manifest 不再是 Web + Hono + D1 Gateway 三个 runtime 的共同所有者；
- workspace boundary gate 覆盖新增 app，依赖图无 app-to-app 和 package-to-app 违规；
- 原 Web、Hono、D1 Gateway 的生产构建/健康检查/回滚语义保持等价；
- 没有借路径迁移改变 Legacy 登录、数据库 schema、Arena v1 wire contract 或线上数据所有权；
- 形成可独立回退的三个迁移提交/批次，不要求一次性切换全部部署；
- Hono 与 Next DR adapter 对至少一组代表 capability 运行同一 contract suite；
- Hono 不可达演练证明 DR eligible safe/read 能力无需客户端重新发布即可切换；
- generation mid-flight 故障演练证明不会创建第二次 AI generation；
- Redis 清空、D1 Gateway 故障与 D1 故障演练分别满足 `DR-006`、`DR-007`、`DR-011`；
- Hono Node 资源指标满足 `RESOURCE-005` 的最小集合；
- DR 当前 artifact/version 与生产 schema/client contract 的 compatibility probe 满足 `DR-014` / `ACCEPT-017`。

### 回滚

- 每个 app relocation 独立回滚，不依赖回退其他已通过阶段；
- legacy Hono/Next import/wrapper 只保留到搬迁回滚窗口结束；长期 DR adapter 按 accepted DR ADR 保留，不作为迁移垃圾删除；
- 目录迁移失败时回到 legacy root 路径，不通过放宽依赖边界检查维持失败结构。

## 6. Phase 3：Admin 回归主线和安全上线

### 前置条件

- Phase 2.5 已通过；`apps/admin` 可以依赖共享 package/API，但不得通过相对路径或别名读取 `apps/web` 内部源码。
- `feat/admin` 继续作为迁移来源和行为参考，不整分支 merge；以业务域重新落到当前 schema、鉴权与安全边界。

### 目标

结束 `feat/admin` 长期分支，同时不把本地可信假设带到公网。

### 迁移批次

按风险由低到高：

1. read-only dashboard/analytics；
2. content list/detail；
3. messages/report review；
4. user write/badge/redemption；
5. ratings/PVP/Arena room recovery；
6. data maintenance/export/system config。

每批包括 UI、route/API、repository、RBAC capability、audit、tests 和 rollback。

### 安全工作

1. Cloudflare Access Application。
2. Cloudflare Tunnel。
3. Origin JWT validation。
4. internal admin allowlist/capability。
5. CSRF/session/CORS policy。
6. high-risk reason/idempotency/version。
7. direct-origin bypass test。
8. audit retention。

### 退出门禁

- Admin 不依赖切换 Git branch；
- 未授权和错误 audience 被拒；
- browser 无 D1 credential；
- 所有写操作有 capability；
- destructive 操作有审计；
- 旧 `feat/admin` 标记只读/归档；
- 主线 tests/build 通过。

### 回滚

- Access policy 可立即 deny；
- Admin host 可下线而不影响公共 Web；
- 每个迁移域可独立 feature flag；
- 不删除旧 Admin 数据表。

## 7. Phase 4：Web 本地库

### 前置条件

- Phase 2.5 已通过，Web 已位于真实 `apps/web` 边界；
- `CardRepository`、本地库 record/migration/archive contract 与 Direct 所需最小共享契约已经在 Phase 2 收口。

### 目标

在 `apps/web` 验证本地库语义、数据模型和显式复制流程，为 Desktop MVP 提供已经跑过真实用户路径的数据语义，而不是把 Web legacy root 当成第二套临时实现。

### 工作项

1. 独立 IndexedDB。
2. LocalCardRecord v1。
3. repository + migration。
4. 列表、搜索、详情、编辑。
5. 保存目标选择。
6. 本地 -> 线上上传副本。
7. 线上 -> 本地下载副本。
8. import/export archive。
9. storage persist/estimate UI。
10. backup warning。
11. local library 不占 slot 回归。
12. Arena 单人可选本地卡；Arena 多人只发送规格允许投影/stub。

### 退出门禁

- 断网创建/编辑/导出可用；
- 清晰标注 Local/Cloud；
- 1000 卡性能基线；
- 导出导入 round-trip；
- 升级 migration test；

### 回滚

本地库功能可 feature flag 关闭；已有 IndexedDB 不主动删除。

## 8. Phase 5：Desktop Tauri PoC 与 MVP

### 启动时序

- **Phase 5A 薄 PoC**：Phase 2.5 退出且所需 `ai-core` / Direct / local-library / port 契约可用后即可启动，可与 Phase 3、Phase 4 并行；目标是尽早验证 runtime-neutral 设计，而不是复制完整 Web。
- **Phase 5B MVP**：必须等待 Phase 4 的本地记录、迁移、显式复制和失败恢复语义稳定，再扩展为完整本地工作流。
- PoC 若暴露 shared package 仍依赖 DOM、Next、Node server secret 或 Web-only storage，应回到 package 边界修正，不在 Tauri adapter 中复制业务逻辑绕过问题。

### PoC 范围

用代表性切片验证，不先复制全部 Web 页面：

1. 首页/导航；
2. 卡片列表和编辑；

4. 自定义 OpenAI-compatible Endpoint；
5. localhost 模型；
6. stream/cancel；
7. SQLite 本地库；
8. Stronghold secret；
9. import/export；
10. 在线卡库只读/登录适配；
11. Arena 单人本地卡与 Direct AI；
12. Arena 多人入口使用服务器权威链路，不传播 Provider。

### 安全实现

- 本地打包 UI，不加载远端主应用；
- capabilities 最小化；
- Native Direct Executor；
- no generic shell/fs/fetch；
- IPC payload schema；
- logs redaction；
- CSP；
- external link allow rules。

### Desktop MVP

PoC 通过后补：

- 完整本地工作流；
- APP 设置；
- update UI；
- crash-safe local migrations；
- compatibility/version handshake；
- optional online capabilities。

### Tauri 失败门禁

只有出现 ADR 中列出的核心失败并有 PoC 记录，才启动 Electron fallback spike。

### 退出门禁

- `ACCEPT-001` 至 `ACCEPT-005` 通过；

## 14. 下一批建议交付

当前 workspace 骨架、Arena wire contract 与 `multiplayer-core` 已有实施成果；后续不再按最初“首批 PR”清单机械推进，而按以下关键路径交付：

1. **Phase 2 收口：通用共享内核**：补通用 contracts、最小 domain、ai-core/Direct contract、local-library contract/ports，并让 Web 真实路径消费；不继续增加 Room runtime。
2. **Phase 2.5A：`apps/d1-gateway`**：行为等价迁移最自洽的 Worker 部署单元，验证真实 workspace app lifecycle。
3. **Phase 2.5B/C：Hono seam + `apps/api`**：先把 Hono 对 legacy Next route module 的复用转成 shared service/adapter，再迁 Node runtime；默认不增加新的 Hono 路由，并补齐 Hono 资源 telemetry。
4. **Phase 2.5D：`apps/web`**：纯目录/构建/部署边界搬迁，保持 Web 行为等价，同时建立长期 DR adapter seam。
5. **Phase 2.5E：Hosted DR contract/drill**：建立 DR manifest、稳定逻辑入口 seam、独立 D1 provider、跨 runtime contract tests 与 Hono/Redis/Gateway/mid-flight 故障演练；具体自动切流产品可以在保持语义的前提下单独启用。
6. **平台 gate 后并行**：
   - `apps/admin` read-only dashboard/analytics/content list 第一批；
   - Web local-library/Direct-first；
   - Desktop 薄 PoC。
7. **Arena runtime 恢复**：Phase 2.5 退出后再进入 `apps/arena-room` 的 Durable Object/WebSocket/ticket/reconnect/GenerationBridge/UI 阶段。

每批只完成一个可解释迁移目标。若某批需要同时大改业务逻辑、schema 与部署边界，应继续拆分，而不是扩大单个 PR。

## 16. 外部设计指南（非规范性）

以下资料用于解释本计划的迁移方法和工具选择，不覆盖仓库 accepted ADR/spec；外部文档如更新，以其官方最新版本为准：

- pnpm Workspace：<https://pnpm.io/workspaces>。采用原生 workspace 与 `workspace:` 本地依赖约束，避免把额外编排器作为迁移前置条件。
- AWS Prescriptive Guidance — Strangler Fig：<https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/strangler-fig.html>。参考渐进替换、旧新共存与逐单元回滚，避免 big-bang migration。
- AWS Prescriptive Guidance — Decomposing monoliths：<https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-decomposing-monoliths/introduction.html>。参考按边界逐步解耦和 branch-by-abstraction 思路；不照搬其云产品实现。
- Tauri 2 Capabilities：<https://v2.tauri.app/security/capabilities/>。Desktop PoC/MVP 继续以最小 capability 和显式 Native command 边界作为安全设计指南。
- Cloudflare Load Balancing common configurations / Monitors / Adaptive routing：<https://developers.cloudflare.com/load-balancing/load-balancers/common-configurations/>、<https://developers.cloudflare.com/load-balancing/monitors/>、<https://developers.cloudflare.com/load-balancing/understand-basics/adaptive-routing/>。参考 active-passive health routing；对 request-level retry 单独检查非幂等重放风险。
- Cloudflare D1 Global read replication / Time Travel：<https://developers.cloudflare.com/d1/best-practices/read-replication/>、<https://developers.cloudflare.com/d1/reference/time-travel/>。参考 Sessions/bookmark 一致性与 point-in-time recovery；不把 Redis 作为数据库恢复源。
- RFC 9110 §9.2.2：<https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2>。HTTP 方法幂等性只作为 transport retry 的基础，业务生成仍需自己的 operation ID/幂等契约。
- Node.js 24 `perf_hooks`：<https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html>。使用 event-loop utilization/delay 等指标补足 Hono process telemetry。
