# Arena 多人 GMR-10P 产品一致性整改实施计划

日期：2026-08-31
状态：`READY / implementation-plan`
计划标识：`PLAN-arena-multiplayer-product-parity-remediation-v1`
对应规格：`SPEC-arena-multiplayer-product-parity-amendment-v1`
审查基线：默认分支 `feature/v0.2.0_Battle_Growth_MahoShojo`，远端 HEAD `da88fa7f1c939346d564597101f987f85696bc47`

## 1. 目标

在不推翻现有 Hono + Redis Room runtime 的前提下，修复 Arena 多人当前的产品一致性和真实生成输入正确性问题，使实现重新满足最初 v1 的核心产品模型：

- `/arena` 是唯一竞技场产品面；
- member Proposal 使用现有 Arena UI/UX，而不是残缺 mini editor；
- Room Shared Config 是多人 generation 的唯一共享语义权威；
- accepted Proposal 必须真实进入 frozen snapshot 和 AI generation semantic input；
- Room 战报和结果复用现有 BattleResult / battle report card presentation；
- room shell 收纳发现、提案、成员、管理，不挤占主要 Arena 工作区。

本计划定义新的 `GMR-10P`，插入当前 `GMR-10 DONE` 与 `GMR-11 production activation` 之间。

在 `GMR-10P = DONE` 前，GMR-11 已完成的 release/ingress/rollback 工作保留，但 production activation 的**有效状态为 `BLOCKED`**；旧 Goal 指南中的 `IN_PROGRESS` 在本计划/配套修订接受后仅作为历史记录，不再授权继续上线。

## 3. 总体顺序

```text
GMR-10P-A  authority + coverage audit
    -> GMR-10P-B  authoritative materialization / start preflight
    -> GMR-10P-C  scoped Arena editor reuse foundation
    -> GMR-10P-D  full Proposal surface + host reconciliation
    -> GMR-10P-E  shared BattleResult + room result projection
    -> GMR-10P-F  room shell / management / discovery UX
    -> GMR-10P-G  product parity E2E + exit audit
    -> resume GMR-11 production activation review
```

P0 correctness 优先于视觉整理。不得先把 mini editor 做得更漂亮再继续保留错误 authority 路径。

## 4. GMR-10P-A：Authority 与 coverage re-baseline

状态：`READY`

### Objective

把当前真实 Arena generation inputs、Room Shared Config、Proposal typed changes、host-only inputs 与 forbidden inputs 建立一张可执行覆盖矩阵，并加入 production activation blocker。

### Scope

- 枚举 `useBattleEngine` 当前真正进入 generation request 的语义字段；
- 枚举 `ArenaRoomSharedConfig`；
- 枚举 `ArenaProposalChange`；
- 枚举现有 Arena UI 可编辑项；
- 为每项标记：
  - `shared/proposable`；
  - `shared/host-only`；
  - `host-runtime-only`；
  - `local-only`；
  - `forbidden`；
  - `deferred-with-reason`；
- 明确 selectedLanguage、questionnaire/lore、adjudication、team display name 等当前缺口；
- 为 coverage matrix 建 test fixture，防止新增 generation semantic 后忘记 Room 分类；
- 将 GMR-11 production readiness test/docs 绑定 `GMR-10P` 未完成即 fail/blocked 的事实（不执行 production action）。

### Forbidden

- 不顺手开始大规模 UI 重构；
- 不部署 production；
- 不改变 Redis Room runtime 架构。

### Done

- coverage matrix 没有未分类的当前 generation semantic；
- 旧 mini editor 的三字段范围不再被当作产品 contract；
- targeted contracts/core/Web/API tests 通过；
- `git diff --check` 通过。

## 5. GMR-10P-B：Frozen authority materialization 与 generation preflight

状态：`BLOCKED`（依赖 A）

### Objective

先关闭 P0：accepted Proposal / Room authority 必须成为真实 AI 输入，host local store 不能在 start 时静默覆盖。

### Scope

#### Server

- 引入/抽取 `ArenaRoomGenerationMaterializer` 或等价 narrow port；
- online DataCard exact version 内容解析；
- server-known preset ref 解析；
- host-local stub -> request-scoped payload map 对齐；
- frozen Shared Config 重建 generation semantic payload；
- semantic hash 在 materialization 后绑定；
- client `generation` 中与 Room-shared semantic 同名字段不得拥有 authority；
- stale/deleted/permission drift/missing host-local payload fail closed。

#### Web / host start

- generation start 不再自动把 `useBattleStore` safe projection 静默 publish；
- 增加 host dirty-vs-room preflight state；
- clean：直接开始；
- dirty：显式选择 `更新房间配置并开始` / `按当前房间配置开始` / `取消`；
- request 只携带 materializer 确实需要的 host-local payload 和 host-only runtime/provider 信息。

### Required tests

- accepted addCombatant 进入 materialized request；
- accepted guidance/scenario/material/history setting 进入 request；
- host stale local state 不覆盖；
- explicit host republish 可以产生新 revision 并覆盖；
- online ref stale 阻止 provider start；
- host-local payload 缺失阻止 provider start；
- duplicate start 仍 one provider execution；
- secret 仍不进 Room checkpoint/WSS/log。

### Done

P0 generation authority tests 全通过；旧 single-producer/recovery/idempotency 无回归。

## 6. GMR-10P-C：Scoped Arena Editor reuse foundation

状态：`BLOCKED`（依赖 B）

### Objective

建立可以让 single / room-host / room-proposal 共用 Arena 编辑组件的 scoped session/adapter 基础，而不污染全局单人状态。

### Scope

- 抽象 `ArenaEditorSession` / provider / scoped store；
- single adapter 兼容当前 `useBattleStore` 行为；
- room-host adapter 带 room baseline/revision/dirty capability；
- room-proposal adapter 从 safe snapshot 初始化 detached store；
- 建立 capability map；
- 优先迁移将被 Proposal 直接复用的组件：
  - roster/Combatant list；
  - online DataCard selection；
  - battle mode；
  - scenario / aux scenario；
  - material；
  - story guidance / story length / language；
  - history settings。

### Implementation preference

如果继续使用 Zustand，优先 vanilla `createStore` + React Context 建 scoped store；避免临时替换 singleton store。

### Forbidden

- 不复制第二套 Proposal JSX；
- 不通过 member snapshot 伪造完整 `CombatantData`；
- 不把 host-local/private payload 填入 proposal store。

### Done

- single UI 行为/测试不变；
- proposal session 与 single session 可同时存在且互不污染；
- shared component smoke/interaction tests 证明同组件被两种 adapter 使用。

## 7. GMR-10P-D：完整 Proposal surface 与 host reconciliation

状态：`BLOCKED`（依赖 C）

### Objective

移除最终产品路径中的 mini Shared Config editor，使 member 在既有 Arena UI 中创建 Proposal；补齐 host accept 后的 workspace reconciliation。

### Scope

#### member

- `[同步房间配置]` 建立 proposal editor session；
- Arena 主编辑区域显示 proposal mode；
- online public/approved DataCard 通过既有 Modal 选择；
- server-verifiable preset 若可稳定引用则可提案；
- host-local stub 可做安全 guidance/team/remove proposal；
- 复用 scenario/material/settings UI；
- `[预览提案]` Modal 展示 typed diff；
- submit/withdraw 继续使用现有 authority contract。

#### host

- 增加 `[更新房间配置]`；
- Proposal Review 迁移到 Modal；
- 显示 author display name、BASE/CURRENT/PROPOSED、conflict/dependency/atomic group；
- accepted config 更新后：
  - host working clean -> 自动确定性同步；
  - host working dirty -> `hostWorkspaceStale/conflicted`，不自动覆盖；
- 提供 `同步房间配置` / `查看差异` / `保留本地并重新发布`。

### Required tests

至少覆盖 add/remove combatant、character guidance、team、scenario、aux scenario、material、language/story/history 中可共享项；不能只测原来的三个字段。

### Done

- `ArenaProposalPanel` 不再承担完整配置编辑器职责；
- 不存在另一套与 Arena controls 重复的三字段/小型配置表单；
- accepted Proposal 可在 host UI 明确看到并进入下一次生成。

## 10. GMR-10P-G：Product parity E2E 与退出审计

状态：`BLOCKED`（依赖 A-F）

### Objective

重新以最初产品需求而不是单个 runtime Goal 的 stopping condition 做一次端到端验收。

### Mandatory golden flow

```text
host create room
member join
member sync room config
member edit using existing Arena UI
  -> add public online character
  -> set character guidance
  -> edit another shared semantic (scenario/material/team/history etc.)
preview typed diff
submit Proposal
host review modal
accept selected
Room revision update
host workspace reconcile
host start
frozen snapshot contains accepted changes
server materializer resolves exact payload
one provider execution
host/member receive same authoritative stream/final
shared battle report card renders
member save image works
safe character result projection visible
no private/full local payload leaks
```

### Additional audit

- product parity matrix 全部分类；
- no mini editor duplication；
- no silent host overwrite；
- no second report presentation；
- member local/private restrictions；
- room management；
- discovery pagination；
- reconnect/gap/recovery regression；
- load/security/secret regression；
- single-player / feature-off regression。

### Validation

至少执行：

- contracts/core/API/Web targeted suites；
- 新 product-parity interaction/E2E suites；
- relevant real Redis/WSS verifier；
- typecheck/lint/build；
- workspace boundary/generated checks；
- `pnpm ci:verify`；
- `git diff --check`；
- architecture/security/test-adequacy 独立复审。

### Exit

只有 GMR-10P-G 全部通过后：

- `GMR-10P = DONE`；
- 恢复 GMR-11 production activation review；
- 重新执行 production readiness，而不是沿用 product-remediation 前的 go/no-go 结论。

## 11. Stop-and-escalate

以下情况才需要用户/架构决策：

1. 为实现 product parity 必须改变 Hono + Redis 单 Room 单写者主架构；
2. 必须新增 member private/local payload sharing；
3. 必须改变现有账户/auth 信任根；
4. 必须执行 production migration/DNS/Access/secret 改动；
5. materialization 无法在现有 data-card/preset repository 上实现 exact-version authority，需要新的长期数据模型；
6. 为复用 Arena UI 唯一可行方案会导致 member 获得 host-only action/secret；
7. 发现新的 accepted spec 之间不可同时满足的实质冲突。

通常不需要升级决策：

- scoped store/context 的具体文件名；
- presentation/view-model 的内部命名；
- Modal vs responsive Drawer 的组件实现；
- adapter/helper 的拆分；
- 测试 fixture 组织；
- 在保持 wire 向后兼容前提下增加 allowlist result fields。

## 12. 回滚与发布边界

- GMR-10P 开发阶段不得执行 production activation。
- 每个子 Goal 使用可独立解释/回滚的 atomic commits。
- 优先 additive/refactor-compatible 方式；删除 mini editor / room report 复制实现应在共享替代路径测试绿色后完成。
- 若新增 wire field，优先 reader-first / optional-compatible，再启用 writer。
- 不把 UI feature flag 当作修复 authority bug 的长期替代品。
- 已完成的 GMR-11 ingress/release/rollback 代码若不与整改冲突可以保留；最终 production readiness 必须在 GMR-10P 后重新验证。
