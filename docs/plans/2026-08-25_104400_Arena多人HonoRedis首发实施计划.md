# Arena 多人 Hono + Redis 首发实施计划

状态：`accepted`
日期：2026-08-25
计划标识：`PLAN-arena-multiplayer-hono-redis-v1`
依据 ADR：`ADR-arena-room-portable-runtime-hono-redis-first`
依据规格：`SPEC-arena-multiplayer-hono-redis-runtime-amendment-v1`
基线分支：`refactor/platform-rearchitecture`
基线提交：`73e51e1e18e27eee7d09e36ff0ff8010e56e5d88`

## 1. 计划关系

本计划保留 `docs/plans/2026-08-21_arena-multiplayer-v1-implementation-plan.md` 的：

- Phase A 已完成/已形成的 contracts 与 `packages/multiplayer-core` 基础；
- Arena 产品/UI 不复制；
- Proposal / generation / security 产品语义；
- “平台 Phase 2.5 退出前不展开重运行时”的时序门禁。

从旧计划 Phase B 开始，本计划取代其：

- Room sidecar Worker；
- Durable Object；
- Hibernation；
- DO SQLite/alarm；
- Service Binding；
- Hono -> DO GenerationBridge；

等具体首发实现。

## 2. 当前执行状态与启动门禁

基线 `73e51e1e18e27eee7d09e36ff0ff8010e56e5d88` 对应平台重整当前入口为 **Phase 2.5D `apps/web`**。

因此本计划的 runtime Phase B **尚未获得启动许可**。

在平台 Phase 2.5 完整退出前：

允许：

- 继续维护 contracts / multiplayer-core pure logic；
- existing Arena state -> normalized source adapter；
- compatibility/security fixture；
- 本轮 ADR/spec/plan 文档收口；
- 会阻塞平台阶段的缺陷修复。

不允许：

- 新增 Room WebSocket runtime；
- 把 Redis Room checkpoint 接入生产路径；
- 实现 room ticket/join lifecycle；
- 上多人 UI；
- 改 generation runtime 以发布 Room delta；
- 因为“不做 DO 了”就把 Arena 业务轨插到 G25D/G25E 前面。

平台阶段退出门禁决定“何时做”，本计划决定“到时怎么做”。

## 3. 首发目标架构

```text
apps/web existing /arena
        │
        │ room HTTPS/WSS
        ▼
apps/api / Hono
  ├─ arena-room/ws + command ingress
  ├─ RoomActorRegistry
  │    └─ one active writer per room
  ├─ RedisRoomStore
  │    ├─ semantic checkpoint + TTL
  │    ├─ transient presence/index
  │    ├─ optional Pub/Sub
  │    └─ optional Stream only if proven needed
  └─ RoomGenerationPublisher
       └─ existing authoritative Arena generation

packages/contracts
  └─ wire schemas / snapshot / event / ticket payload

packages/multiplayer-core
  └─ pure projection / diff / conflict / apply / room transition helpers

D1
  └─ derived room directory + existing durable business facts

R2 / generation persistence
  └─ final authoritative generation output
```

首发不建立 `apps/arena-room`。若未来通过 DO/Cloudflare Room adapter 评估，再单独激活该 app boundary。

## 4. Phase B1：Room runtime contract 与状态机收口

> 启动条件：平台 Phase 2.5 已退出。

### 4.1 目标

把已经存在的多人 pure logic 组织成 Hono runtime 可以安全调用、未来 DO adapter 也能复用的明确边界。

### 4.2 工作项

1. 盘点当前 `packages/contracts` Room DTO/event，保留 wire compatibility。
2. 盘点 `packages/multiplayer-core` 当前 `projection/diff/conflicts/apply/selection`，避免重写已验证逻辑。
3. 只补真实 runtime 所需的 pure transition helper，例如：
   - room create/close transition；
   - membership transition；
   - host publish / Proposal resolve atomic transition；
   - generation reservation/mirror transition；
   - epoch validation。
4. 定义 server-side runtime port，但不得把 Redis/Hono 类型放进 shared core。
5. 明确 `roomEpoch` fencing 与 `revision` 同 epoch 比较规则。
6. 补 old/new protocol fixture，不随部署简化而改 wire 名称。

### 4.3 建议边界

示意，不要求逐字采用：

```ts
interface RoomCheckpointStore {
  load(roomId: string): Promise<RoomCheckpoint | null>;
  save(checkpoint: RoomCheckpoint): Promise<void>;
  delete(roomId: string): Promise<void>;
}

interface RoomGenerationPublisher {
  publish(event: SafeRoomGenerationEvent): Promise<void>;
}
```

上述 server port 可以位于合适的 server-neutral package 或 `apps/api` 内部边界；不得为了“看起来抽象”把尚无第二消费者的实现代码过度 package 化。

### 4.4 退出门禁

- current multiplayer-core tests 全绿；
- no framework/runtime import in multiplayer-core；
- epoch + transition fixtures 存在；
- DTO 敏感字段负向 fixture 全绿；
- 未新增生产 WebSocket 路由。

## 5. Phase B2：单实例 Hono RoomActor + Redis checkpoint

### 5.1 目标

先证明最小单写者 Room runtime，不提前解决多实例分布式协调。

### 5.2 建议源码归属

示意：

```text
apps/api/src/arena-room/
  room-actor.ts
  room-registry.ts
  redis-room-store.ts
  lifecycle.ts
  errors.ts
```

不要创建第二套业务 schema；使用 packages 中的 contract/core。

### 5.3 RoomActorRegistry

实现：

- `roomId -> RoomActor`；
- 每 Room command 串行队列；
- bounded queue；
- idle actor eviction；
- process shutdown 时停止接收新 authority-changing command；
- 不用 per-room `setInterval`。

### 5.4 RedisRoomStore

实现：

- versioned snapshot/checkpoint；
- semantic mutation success 前 checkpoint；
- TTL；
- schema version；
- delete/expire 幂等；
- Redis error 显式上浮。

首发优先单 snapshot key；如 Shared Config 大小/写放大实测不合适，再基于数据拆分，不提前优化。

### 5.5 Redis 故障策略

测试并冻结：

```text
Redis healthy
  -> normal authority-changing commands

Redis unavailable
  -> new authority-changing command fail closed
  -> temporary existing stream MAY continue while safe
  -> no fake-success memory-only write
```

### 5.6 退出门禁

- create/load/mutate/close checkpoint test；
- Redis restart after acknowledged mutation recovers latest checkpoint；
- Redis unavailable fail-closed fixture；
- TTL expiry test；
- command queue/backpressure test；
- no distributed lock dependency；
- no D1 presence write。

## 6. Phase B3：WSS、ticket、membership、reconnect 与 lifecycle

### 6.1 WebSocket ingress

在 `apps/api` 提供版本化 Room WSS 入口。

要求：

- HTTPS/WSS only in production；
- short-lived signed ticket；
- browser Origin exact allowlist；
- installed client 不以 Origin 为 trust root；
- message schema/capability/bytes/rate limit；
- connection-level backpressure。

### 6.2 Membership / connection

继续使用：

```text
membership(userId, role)
  -> connection A
  -> connection B
```

- 多 tab 不重复计 member；
- socket close 只改变 presence；
- explicit member leave 与 host close 是 command；
- kick 后旧 ticket 不能重建 membership。

### 6.3 reconnect

实现：

- reconnect backoff；
- same epoch snapshot/replay；
- new epoch full snapshot；
- presence rebuild；
- story gap -> generation resync。

v1 不要求在 Node process restart 后保留旧 epoch；优先用新 epoch fencing。

### 6.4 lifecycle / deadline

实现：

- host-offline grace；
- room idle TTL；
- Redis TTL；
- process-level deadline scheduler 或 lazy validation；
- D1 directory low-frequency cleanup/reconciliation。

禁止固定频率 room polling。

### 6.5 D1 directory

继续只存 discovery 需要的低频 metadata。

必须验证：

- Redis checkpoint absent + D1 row present -> join not-found/stale；
- stale D1 row 不创建 Room；
- cleanup/reconciliation 可重复执行。

### 6.6 退出门禁

- refresh/reconnect 不等于 leave；
- multi-tab test；
- kick/replay ticket test；
- old epoch command rejected；
- process restart + Redis warm recovery；
- expired checkpoint + orphan D1 row 不复活；
- oversized/flood/slow-consumer fault injection。

## 7. Phase C：现有 Arena 页面多人入口

继续旧计划产品设计，不新增独立多人 Arena route。

支持：

- create room；
- public/unlisted find/join；
- room status；
- members；
- leave/host close；
- reconnect/degraded UI。

UI 必须显示可理解的恢复状态，例如：

- 正在重新连接；
- 房间已由服务器恢复，需要重新同步；
- 房间运行时不可用；
- 原房间无法恢复，请房主创建新房间。

不得伪装为透明无缝 failover。

## 8. Phase D：Proposal 完整闭环

复用既有 typed Proposal / expectedBase / versionToken 设计。

实现：

1. member sync snapshot；
2. local working copy；
3. local diff；
4. submit Proposal；
5. host review partial accept/reject；
6. RoomActor 串行执行 schema/capability/precondition/dependency/atomic group；
7. apply + proposal state + revision increment；
8. Redis checkpoint；
9. success ack + broadcast。

关键要求：**成功 ack 不早于 checkpoint 成功**。

## 9. Phase E：Authoritative generation 与 Room broadcast

### 9.1 reservation

Host start：

1. 验证 host membership/epoch；
2. 发布尚未同步 host config；
3. 稳定 `generationRequestId`；
4. RoomActor reserve；
5. freeze revision/shared config/ref versions/participant snapshot；
6. Redis checkpoint reservation；
7. 调 existing generation service。

### 9.2 RoomGenerationPublisher

在 Hono 进程内建立内部 publisher：

- started；
- batched story delta；
- metadata；
- completed/failed/cancelled。

首发不走跨公网 GenerationBridge。

批量继续以时间 + bytes 双阈值，初始可沿用 50–100ms 量级假设，再根据真实压测调整；不得按 token fan-out。

### 9.3 crash / unknown

Hono process/socket 异常时：

- 不自动重新发起 AI；
- 先以 `generationRequestId` 查询/对账 durable generation state；
- completed -> 从权威存储恢复 final；
- running/unknown -> 显示 recovery/unknown；
- failed -> 显式失败；
- 显式 retry 必须遵循 generation idempotency contract。

### 9.4 host browser

host browser 不是 AI stream relay。

host tab close：

- MAY 变 offline presence；
- MUST NOT 自动产生第二次 generation；
- 其他成员仍从 Room runtime 接收已有安全投影，只要服务端 execution 仍在。

### 9.5 退出门禁

- duplicate start only one AI execution；
- old epoch/attempt terminal rejected；
- host refresh fault injection；
- story delta gap -> resync；
- final report from authoritative storage；
- host-local/provider secret never enters Room checkpoint/broadcast。

## 10. Phase F：个人页多人战报关联（可选）

延续旧计划：只新增 generation <-> participant 轻量关系；不复制 generation row/R2 report，不重复生成。

该阶段不阻塞多人基础能力上线。

## 11. Phase G：资源、安全与恢复 hardening

### 11.1 资源指标

接入现有 Hono telemetry，并增加：

- active rooms；
- active Room sockets；
- RoomActor queue/latency；
- checkpoint bytes/latency/error；
- Redis room key count/memory/eviction；
- reconnect/snapshot/resync；
- publisher backlog/drop；
- recovery/replacement-room incident。

### 11.2 故障演练

至少演练：

1. 单 WebSocket 断线；
2. host tab refresh；
3. Redis 短暂不可用；
4. Hono process restart + Redis survives；
5. Redis flush / checkpoint loss；
6. D1 orphan directory；
7. generation stream 中途 Hono process failure；
8. slow consumer；
9. oversized/flood；
10. VPS 整体不可达。

验收重点不是“房间永不掉”，而是：

- 可恢复时恢复；
- 不可恢复时明确终止/rebuild；
- 不 duplicate generation/rating/settlement；
- final durable facts 保持正确。

### 11.3 容量门禁

在没有生产基线前不设虚构 SLA。

当 active socket、event-loop delay、RSS/heap、Redis latency 或 RoomActor queue 显示单实例瓶颈时，再进入 Phase H 评估。

## 12. Phase H：多实例 / Durable Object 评估（条件触发，不是 v1 必做）

只在真实指标或可用性目标触发时执行。

比较至少三类方案：

1. Hono multi-instance + room routing + lease/fencing；
2. 独立 self-hosted room runtime；
3. Cloudflare Durable Object adapter。

评估维度：

- 实现复杂度；
- split-brain 风险；
- fault recovery；
- global RTT；
- socket capacity；
- CPU/RSS/event-loop；
- Redis/Cloudflare 成本；
- deploy/version skew；
- DR 演练成本。

若选 DO：

- 建立 `apps/arena-room`；
- 一逻辑 room 一 coordination atom；
- 实现同一 Room contract；
- 再引入 Hibernation/alarm/DO storage 等平台优化；
- generation 侧实现 `RoomGenerationPublisher` 的 DO bridge adapter；
- 先支持新 room traffic，禁止未设计协议时与 Hono 对同一 epoch 双写。

## 13. Cloudflare DR 实施顺序

多人首发不阻塞当前 Hosted DR G25E，也不要求 G25E 顺带实现 Room DR。

顺序应为：

```text
current platform Phase 2.5D apps/web
  -> Phase 2.5E Hosted DR
  -> Phase 2.5 exit audit
  -> 本计划 Phase B-G
  -> only if triggered: Phase H / Cloudflare RoomRuntime DR
```

如果 Hono 在 Phase H 之前故障：

- 已纳入 Hosted DR manifest 的 HTTP capability 按现有 DR 计划切换；
- Arena Room realtime 明确 degraded/unavailable；
- 不用 D1 polling/client host state 伪造 Room takeover。

## 14. 提交与回滚建议

建议把实施拆成原子提交：

```text
refactor(multiplayer): 冻结 runtime-neutral room authority contract
feat(api): 增加 Redis room checkpoint store
feat(api): 增加 single-writer Arena RoomActor runtime
feat(api): 增加 Arena Room WebSocket 与 ticket
feat(arena): 接入多人房间 UI 与 reconnect
feat(multiplayer): 完成 Proposal server workflow
feat(api): 接入 in-process Room generation publisher
test(multiplayer): 增加 room recovery 与 failure drills
```

每一阶段必须能够回滚而不改变既有单人 Arena。

不得把：

- 平台 Phase 2.5D/E；
- Room runtime；
- 多人 UI；
- DO 未来 adapter；

混成一个无法独立验证的大提交。

## 15. 完成定义

Arena 多人 Hono + Redis v1 达到首发条件时，应满足：

- 现有 Arena 单人功能行为不变；
- Room realtime 在 Hono 提供；
- 一 room 一活动 writer；
- authority-changing ack 有 Redis checkpoint；
- Redis outage fail closed；
- reconnect/snapshot/epoch fencing 正确；
- Proposal 语义保持原规格；
- AI 每个 generation intent 只执行一次；
- host browser 不是 stream relay；
- final result 从权威 generation storage 恢复；
- host-local/provider secrets 不进入 Room plane；
- D1 orphan 不复活 Room；
- Hono process restart + Redis warm recovery 通过；
- VPS 整体丢失允许 Room rebuild，但无永久业务事实错误；
- telemetry 能支持后续是否引入 DO 的数据化决策。
