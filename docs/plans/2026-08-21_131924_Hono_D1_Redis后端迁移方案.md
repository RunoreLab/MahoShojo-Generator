# Hono + D1 + Redis 后端独立部署迁移方案

> 基线分支：`feature/v0.2.0_Battle_Growth_MahoShojo`
> 基线提交：`c123fbbb`
> 设计时间：2026-08-21 13:19:24 +08:00
> 决策状态：采用 Hono Node，继续使用 D1，引入 Redis；本文覆盖此前方案中的 PostgreSQL 目标态部分。

## 1. 结论摘要

本阶段建议采用以下目标架构：

```text
浏览器 / App
  |
  | HTTPS / WSS（保持公开同源或同站点）
  v
Cloudflare DNS + WAF + Tunnel
  |
  v
Hono Node（首批仅选定的生成型 HTTP API）
  |-- Redis（同区域、私网 TLS）
  |     |-- 限流、冷却、租约、幂等
  |     |-- 查询结果缓存、热点快照
  |     |-- PvP 在线状态、匹配队列
  |     +-- Pub/Sub / 短期 Stream
  |
  +-- 内部 D1 Gateway Worker
  |     +-- D1 binding + Sessions/bookmark + batch
  |
  +-- R2 / AI Provider / Resend 等外部服务
```

关键决策：

1. **首阶段只把白名单内的生成型 HTTP API 迁到 Hono Node**，其余 API 继续由 Next.js 承载；WebSocket 延后到 PvP 实时层阶段。
2. **D1 继续作为权威持久化数据库**，Redis 不替代用户、卡牌、对局、结算、审计等事实数据。
3. **Node 不直接使用 D1 内置管理 REST API 作为生产数据通道**。现有 `lib/db/d1-http-client.ts` 改造成访问内部 D1 Gateway 的兼容客户端。
4. **新增轻量 D1 Gateway Worker**，通过原生 D1 binding 执行参数化查询、事务 batch 和 Sessions/bookmark。
5. **Redis 第一优先迁移现有进程内限流和缓存**；第二优先承载 PvP 实时分发、在线状态、匹配队列和防重锁。
6. **Redis 故障不能破坏核心数据正确性**：缓存故障回源 D1，Pub/Sub 故障回退轮询，锁故障仍由 D1 `version` CAS/唯一约束兜底。
7. 第一阶段不引入消息队列语义，不把关键写入改成异步最终一致；只对允许少量丢失的统计数据采用 Redis 聚合后回写。

## 2. 当前系统基线

### 2.1 API 与运行时

- `app/api` 当前有 133 个 `route.ts` 和 132 个独立 `handler.ts`。
- PvP 是最大的 API 领域，共 27 个 handler；Arena 14 个，个人中心 13 个。
- 现有多数业务入口已经是 Web 标准 `Request` / `Response`，适合直接挂到 Hono。
- 有 13 条流式接口，依赖 `ReadableStream`、SSE、`AbortSignal` 和后台收尾任务。
- 约 41 个 handler 仍导入 `NextRequest`；约 11 处逻辑读取 Cloudflare `waitUntil`。
- 当前 `lib/db/drizzle.ts` 已能从 Cloudflare binding 或 HTTP D1 client 创建同一种 `DrizzleD1Database`。

### 2.2 数据库

- Drizzle schema 使用 SQLite/D1 dialect，约 56 张表。
- D1 已包含账号、会话、数据卡、卡组、收藏、消息、众查、徽章、PvP、竞技场、战报和 AI 可用性统计等数据。
- PvP 房间已有 `version` 字段并使用 CAS 更新，这是并发正确性的核心，必须保留。
- 数据卡互动使用唯一记录去重，再更新计数；不能改成单纯 Redis 计数。
- Better Auth 当前将会话持久化到 `ba_session`，同时启用 5 分钟 cookie cache。

### 2.3 已发现的进程内状态

以下状态在多实例 Hono 下会失效，必须优先统一：

| 代码位置 | 当前实现 | 问题 |
| --- | --- | --- |
| `lib/auth/attempt-rate-limit.ts` | 进程内 token bucket | 多实例绕过，重启清空 |
| `lib/ai/public-rate-limit.ts` | 进程内冷却 Map | 官方密钥额度无法全局保护 |
| `lib/ai-session/rate-limit.ts` | 会话租约 + IP bucket Map | 无法跨实例阻止并发生成 |
| `lib/data-card-stats/rate-limit.ts` | 固定窗口 Map | 多实例下限流放大 |
| `app/api/arena/leaderboard/search/handler.ts` | 搜索 bucket Map | 多实例下限流不一致 |
| `lib/arena/generation-ranking-rate-limit.ts` | Cloudflare Rate Limit binding | Node 环境无 binding 时降级放行 |
| `lib/edge-cache.ts` | `caches.default` + 进程内 LRU | Node 多实例缓存不共享 |
| `lib/arena/tier.ts`、`lib/db/repositories/data-card-meta.ts` | 女王实体 Map 缓存 | 多实例可能短时不一致 |
| `lib/ai/availability/rebuild-snapshot.ts` | isolate 内 single-flight + D1 快照 | 并发实例仍会重复重建 |

客户端的 IndexedDB/localStorage 缓存，例如 `lib/public-card-cache/*`、`lib/arena/rank-cache.ts`、AI 会话和茶会本地存档，不迁移到服务端 Redis。

## 3. 为什么需要 D1 Gateway Worker

仓库现有 HTTP client 直接请求：

```text
https://api.cloudflare.com/client/v4/accounts/{accountId}/d1/database/{databaseId}/query
```

该接口可以用于开发、脚本和故障工具，但不应成为正式 Node API 的主数据通道：

- Cloudflare 将内置 D1 REST API 定位为偏管理用途，并受 Cloudflare 全局 API 限流影响。
- 当前全局 API 限制为每个用户 5 分钟 1,200 次；复杂 PvP 请求自身就可能产生多次 SQL，无法支持正式流量。
- D1 Sessions API 只通过 Worker binding 提供，REST Query API 不能使用 Sessions/bookmark，因而无法利用读副本并保证顺序一致性。
- Node 保存的是 Cloudflare D1 管理 API Token；若泄漏，权限面大于一个受控的业务网关凭据。

因此新增 `apps/d1-gateway`：

```text
Hono Node
  | POST /internal/d1/v1/query|batch|raw
  v
D1 Gateway Worker
  | env.DB.withSession(bookmark)
  v
D1
```

### 3.1 Gateway 契约

Gateway 只提供以下能力：

- `POST /internal/d1/v1/query`：单条参数化语句。
- `POST /internal/d1/v1/batch`：多条参数化语句，调用原生 `session.batch()`。
- `POST /internal/d1/v1/raw`：仅兼容确有矩阵返回需求的旧代码；逐步收敛。
- `GET /health`：不执行写入，只返回 Worker 与 binding 就绪状态。

每次请求限制：

- body 不超过 512 KiB；
- batch 最多 50 条语句；
- 每条 SQL 不超过 D1 平台限制，应用侧再限制为 64 KiB；
- 每条最多 100 个绑定参数；
- 只允许参数化 `SELECT`、`INSERT`、`UPDATE`、`DELETE`、`WITH`；
- 拒绝 `ATTACH`、`DETACH`、`PRAGMA`、`VACUUM` 和 DDL；迁移继续使用 Wrangler；
- 请求带 trace ID、调用服务版本和超时预算；日志不得打印完整参数或隐私数据。

### 3.2 Gateway 鉴权

优先采用两层保护：

1. Cloudflare Access Service Token 保护内部 hostname；
2. 请求体 HMAC 签名：`method + path + timestamp + nonce + sha256(body)`。

Gateway 校验 60 秒时间窗，并对 Node 出口来源与每服务速率设置限制。关键写请求另外携带业务 request ID，由 D1 CAS/唯一约束和 Redis 短期幂等记录防重。Gateway 域名不提供浏览器 CORS，也不写入前端配置。

### 3.3 请求级一致性

Node 为每个 HTTP/WS 命令创建 `RequestContext`，保存当前 D1 bookmark：

- 公开、允许短时陈旧的只读请求：从 `first-unconstrained` 开始，可命中读副本；
- 登录态写请求、PvP 命令、写后读：从 `first-primary` 开始；
- Gateway 每次响应返回最新 `x-d1-bookmark`；Node 后续查询继续携带该 bookmark；
- 同一个 Hono 请求内按需要串行执行依赖查询，互不依赖的读取可组成一个 `batch()`；
- 多条必须原子成功的 SQL 必须放在同一次 `batch()`，不能靠多次 HTTP 调用模拟事务。

D1 `batch()` 会按顺序执行，任一语句失败则整批回滚。现有 `HttpD1DatabaseClient.batch()` 可以继续作为 Drizzle 兼容边界。

### 3.4 适配现有代码

保留 `AppDrizzleDb` 和现有 repository，调整初始化链路：

```text
当前：getCloudflareContext() / global / Cloudflare REST fallback
目标：显式 DatabaseProvider -> GatewayD1Client -> drizzle(client, schema)
```

建议新增：

```ts
interface DatabaseProvider {
  getDb(): AppDrizzleDb;
  runInConsistencyScope<T>(
    mode: 'replica-ok' | 'primary',
    callback: () => Promise<T>,
  ): Promise<T>;
}
```

Node 运行时不再探测 `getCloudflareContext()`；Cloudflare Web 旧入口在过渡期仍使用 binding provider。

### 3.5 D1 容量边界

Redis 能减少读取、轮询和临时状态写入，但不会改变单个 D1 数据库的写入上限：

- 单个 D1 数据库本质上仍按单线程顺序处理查询；
- 所有写入最终仍到 primary；读副本不能分担写入；
- 高频写必须使用索引、短事务和 batch，禁止在请求内循环发出大量独立 Gateway 调用；
- 持续观察 `overloaded`、SQL duration、rows read/written 和单请求 Gateway 往返次数；
- 当数据库容量达到上限的 70%，或经过索引与 batch 优化后仍持续出现写入排队，再按领域拆分新 D1，例如将可用性/统计和战报历史从核心账号/PvP 数据库中拆出。

分库是容量措施，不纳入首批迁移；当前所有业务仍使用现有 `DB`，避免同时承担跨库一致性改造。

## 4. 数据归属原则

### 4.1 必须继续由 D1 权威持久化

- 用户、Better Auth 账号、账号映射、密码恢复 token；
- 数据卡、卡组、标签、收藏、点赞/使用互动明细；
- 举报、众查、申诉、管理员操作和审计日志；
- 徽章、用户消息和已读状态；
- PvP 房间规则、成员、提交、手牌、卡牌快照、比赛、回合、选择、聊天和结算；
- Arena rating、rating event、赛季归档和战报；
- 兑换码、唯一约束、幂等事实与需要恢复的数据；
- R2/大对象的元数据引用。

### 4.2 可以只存在 Redis

- 限流 bucket、冷却时间、短期租约；
- WebSocket 在线状态和连接所在实例；
- Redis Pub/Sub 实时通知；
- 可重建的热点查询结果；
- PvP 匹配等待队列；用户断线后可重新入队；
- 短期事件 replay Stream；完整快照仍由 D1 恢复；
- 可丢弃的负缓存、single-flight 标记和防缓存击穿锁。

### 4.3 Redis 加速，但 D1 仍兜底

- PvP 房间公开快照；
- 排行榜、女王实体、公开卡详情、用户公开摘要；
- 未读消息数、徽章列表；
- AI 渠道可用性实时窗口；
- 用户最后活跃时间和非计费统计；
- API 幂等响应缓存、昂贵 AI 任务的防重复租约。

## 5. Redis 迁移清单

### 5.1 P0：首批必须迁移

| 能力 | 当前来源 | Redis 结构 | TTL/策略 | 降级行为 |
| --- | --- | --- | --- | --- |
| 登录/注册限流 | `lib/auth/attempt-rate-limit.ts` | Lua token bucket 或 GCRA | 2 小时 | Redis 短故障用本机紧缩 bucket；持续故障对注册和密码接口保护性拒绝 |
| 邮件发送风控 | `lib/auth/mail-send-guard.ts` | 用户/IP 滑动窗口 | 最长业务窗口 + 60 秒 | Redis 异常时保留 D1 审计查询兜底 |
| 公共 AI 冷却 | `lib/ai/public-rate-limit.ts` | `SET NX EX` / Lua | 冷却时间 + 60 秒 | 系统密钥请求保护性拒绝；用户自带密钥可本机限流 |
| AI 会话并发租约 | `lib/ai-session/rate-limit.ts` | 带随机 token 的 lease | 上游总超时 + 30 秒 | 无法取得 Redis 时拒绝系统密钥并发生成，避免重复扣费 |
| 数据卡统计限流 | `lib/data-card-stats/rate-limit.ts` | 固定窗口计数 | 2 分钟 | 本机 fallback，D1 唯一约束继续兜底 |
| 排行榜搜索限流 | `app/api/arena/leaderboard/search/handler.ts` | token bucket | 30 秒 | 本机 fallback |
| 生成排名限流 | `lib/arena/generation-ranking-rate-limit.ts` | 3 组 Redis limiter | 60～120 秒 | 不再因 Cloudflare binding 不存在而无条件放行 |
| 服务端响应缓存 | `lib/edge-cache.ts` | string/json cache | 按接口 10 秒～10 分钟 | Redis miss/故障直接查 D1 |
| 女王实体缓存 | 两处进程内 Map | JSON cache | 30 秒 | 回源 D1 |

限流 key 中不得保存原始邮箱、Cookie、Authorization 或完整 IP。统一使用带服务端 pepper 的 HMAC-SHA256 摘要。

### 5.2 P1：D1 读优化

| 场景 | 建议 | 建议 TTL | 失效方式 |
| --- | --- | ---: | --- |
| 公开数据卡详情 | 正缓存 + 负缓存 | 300 秒 / 15 秒 | 卡片更新、删除、审核状态改变后 delete |
| 数据卡 metadata batch | 按卡 ID/版本缓存 | 120 秒 | 更新卡片或指标后 delete |
| 标签列表 | 共享 JSON | 300～600 秒 | 标签管理/seed 后提升 namespace version |
| Arena 排行榜 | 规范化 query hash -> JSON | 10～20 秒 | rating 写入后可只依赖短 TTL；赛季切换主动清空 namespace |
| 排行榜搜索 | query hash -> JSON | 10 秒 | 短 TTL，不做复杂精准失效 |
| PvP 房间浏览列表 | query hash -> JSON | 3～5 秒 | 房间创建/加入/离开/关闭时递增 browse epoch |
| PvP 房间公开快照 | room ID + version -> JSON | 15～30 秒 | D1 CAS 成功后写新版本并发布事件 |
| 用户公开摘要/徽章 | user ID -> JSON | 60 秒 | 用户、徽章变更后 delete |
| 消息未读数 | user ID -> count | 15～30 秒 | 新消息、read/read-all 后 delete |
| AI 渠道快照 | 单一 JSON | 45～120 秒 | 聚合器更新后覆盖 |

缓存统一采用 cache-aside：

1. 读 Redis；
2. miss 后读 D1；
3. 写 Redis，加入 0～10% TTL 抖动；
4. 业务写必须先成功提交 D1，再删除或覆盖 Redis；
5. Redis 写失败只记录指标，不回滚 D1 业务写。

对热点 key 使用 3～10 秒 single-flight 锁，未获得锁的请求等待短时间后重读缓存，避免缓存击穿。

Cloudflare CDN 仍是公开 GET 的第一层缓存；Redis 只作为服务端共享 L2，减少 D1 查询和响应组装。Redis 优先缓存经过 schema 校验的业务 payload，再由 handler 重建 Response；禁止缓存带 `Set-Cookie`、用户身份、私有权限或动态安全 header 的完整响应。

### 5.3 P1：PvP 实时能力

#### 在线状态

```text
maho:v1:prod:presence:room:{roomId}:user:{userId}
```

- value：`instanceId、connectionId、role、lastSeenAt`；
- 心跳约 20 秒，TTL 60 秒；
- 在线状态不写 D1；`last_activity_at` 仍只在有效业务动作时更新；
- Socket 对象保存在所属 Node 进程内，Redis 只存索引，不能序列化 Socket。

#### 实时广播

```text
maho:v1:prod:pubsub:room:{roomId}
```

D1 写入成功后发布轻量事件：

```json
{
  "eventId": "uuid",
  "type": "room.updated",
  "roomId": "...",
  "version": 42,
  "occurredAt": "..."
}
```

所有 Node 实例订阅并推送给本机 Socket。事件只通知“有新版本”，客户端收到后可请求最新快照；不把完整私有手牌或密钥放到 Pub/Sub。

Pub/Sub 不保证离线重放。需要短期补帧时，同时写入：

```text
maho:v1:prod:stream:room:{roomId}
```

- `MAXLEN ~ 500`；
- key TTL 2 小时；
- 客户端携带最后 `eventId`；无法补齐时回退 D1 快照。

#### 匹配队列

快速匹配从“扫描 D1 开放房间”逐步改成 Redis 队列：

- ZSET 保存可匹配玩家或房间；
- HASH 保存模式、人数、rating 区间、入队时间；
- Lua 原子完成“检查仍在队列 -> 选取 -> 移除”；
- 匹配成功后必须在 D1 创建/加入房间，D1 失败则重新入队；
- 断线、取消、超时均移除；后台定期清理过期成员；
- Redis 丢失只导致等待队列清空，玩家重连即可恢复，不影响已建立房间。

#### 分布式租约与幂等

以下昂贵动作增加 Redis 租约：

- `room:start:{roomId}`；
- `round:resolve:{roundId}`；
- `round:settle:{roundId}`；
- AI generation request id；
- 自动审核和重复统计任务。

租约必须使用唯一 token，释放时通过 Lua 比较 token 后删除，不能直接 `DEL`。租约只防止重复工作，不替代 D1 CAS、唯一索引或业务幂等。

### 5.4 P2：可写回聚合的统计

以下数据允许先在 Redis 聚合，再周期性回写 D1：

| 数据 | Redis 做法 | D1 做法 | 可接受损失 |
| --- | --- | --- | --- |
| AI 渠道 outcome bucket | HASH `HINCRBY` | 每 1～5 分钟 batch upsert | 宕机时少量监控样本 |
| 用户最后活跃 | ZSET/HASH 保留每用户最大时间 | 每分钟批量 upsert | 少量活跃时间不精确 |
| 非计费 telemetry | counters/histogram | 聚合或外部观测系统 | 允许 |

点赞、收藏、使用互动去重、排位分数、战斗结算、兑换码和审计日志不进入这种 write-behind 模式。

### 5.5 Better Auth 会话

Better Auth 1.4.19 支持 `secondaryStorage`，并可将 session/rate-limit 存入 Redis。但是本项目第一阶段不直接切换：

- 当前 5 分钟 cookie cache 已经减少大量会话查询；
- 配置 secondary storage 后，会话读取默认总是走 secondary storage；Redis 故障会直接影响全部登录态；
- 会话切换和旧 Cookie 兼容需要专项演练。

建议顺序：

1. 第一阶段：`ba_session` 继续在 D1，保留 cookie cache；删除当前 `/api/auth/verify` HTTP 自请求，Hono 内直接调用 Better Auth session API。
2. Redis 高可用稳定后：增加 `secondaryStorage`，同时设置 `session.storeSessionInDatabase: true`，让 D1 保留会话记录。
3. 验证登录、退出、全端注销、封禁和密码重置后，再决定是否将 Redis 设为会话主读路径。

## 6. Redis 键空间

统一格式：

```text
maho:{schemaVersion}:{environment}:{domain}:{kind}:{identity}
```

示例：

```text
maho:v1:prod:rl:auth:login:ip:{hash}
maho:v1:prod:lease:ai-session:{sessionId}
maho:v1:prod:cache:card:{cardId}:{updatedAtHash}
maho:v1:prod:cache:leaderboard:{queryHash}
maho:v1:prod:cache:pvp-room:{roomId}:{version}
maho:v1:prod:presence:room:{roomId}:user:{userId}
maho:v1:prod:pubsub:room:{roomId}
maho:v1:prod:stream:room:{roomId}
maho:v1:prod:idem:{routeId}:{actorHash}:{requestId}
```

若未来使用 Redis Cluster，多 key Lua 的相关 key 使用相同 hash tag，例如 `{roomId}`，保证落在同一 slot。

约束：

- 所有 cache、limiter、lease、presence 和 idempotency key 都必须有 TTL；
- value 默认不超过 256 KiB，房间公开快照最大 512 KiB；
- 不缓存原始 Authorization、Cookie、API Key、密码 reset token、完整私有手牌；
- 业务对象包含 `schemaVersion` 和 `sourceVersion`，解析失败直接删除并回源；
- 大 JSON 先评估字段裁剪，不默认开启 Redis 压缩，避免 Node CPU/GC 开销。

## 7. Hono 服务设计

### 7.1 过渡目录

```text
apps/
  api/
    package.json
    src/
      app.ts
      server.ts
      routes/
      middleware/
      runtime/
      websocket/                 # 阶段 5 再引入
  d1-gateway/
    wrangler.jsonc
    src/index.ts
app/api/                         # 旧 Next 入口，灰度期保留
lib/                             # 现有业务与 repository，先共享
packages/
  contracts/                     # 新增/变更 API 的 Zod DTO
  runtime/                       # DatabaseProvider、Cache、Limiter、TaskDispatcher
```

### 7.2 依赖注入

```ts
type AppDependencies = {
  database: DatabaseProvider;
  redis: RedisServices;
  tasks: TaskDispatcher;
  logger: AppLogger;
  clock: Clock;
};

type RedisServices = {
  cache: CacheStore;
  rateLimit: RateLimitStore;
  lease: LeaseStore;
  pubSub: RoomEventBus;
  presence: PresenceStore;
};
```

业务 core 不 import Hono Context、`next/*`、`getCloudflareContext()` 或具体 Redis client。Hono middleware 负责把 trace、真实 IP、用户、依赖和 abort signal 放入请求上下文。

### 7.3 路由迁移

- 自动扫描 `app/api/**/handler.ts` 生成 route manifest；
- `[roomId]` 转换为 `:roomId`，参数显式传给新 handler；
- 旧 handler 可先通过 `c.req.raw` 直接复用；
- Better Auth 路由直接挂 `auth.handler`，不再经过 Next adapter；
- 公开 URL 保持不变，由 Cloudflare 路由切换 `/api/*`；
- WebSocket 延后到阶段 5；首阶段不注册 `/ws`，也不安装直接 `ws` 依赖。

### 7.4 Redis 客户端

Node 侧建议采用一个成熟的 Redis client，并建立独立连接：

- command/cache 连接；
- publisher 连接；
- subscriber 连接；
- 后续若引入 BullMQ，再创建独立的 blocking connection。

请求链路上的 Redis 命令超时建议 50～100 ms；缓存最多重试一次，避免 Redis 故障拖垮 API。Pub/Sub 和后台连接使用独立的重连退避策略。

## 8. 写入顺序与一致性

### 8.1 普通业务写

```text
校验请求
  -> D1 batch/CAS 提交
  -> Redis 删除/覆盖缓存
  -> Redis 发布事件
  -> 返回响应
```

D1 成功但 Redis 失败时仍返回业务成功，同时记录 `cache_invalidation_failed` 指标。短 TTL 保证错误缓存最终自动消失。

### 8.2 防止删除缓存竞态

对高风险对象使用版本化 key：

```text
cache:pvp-room:{roomId}:{d1Version}
```

读路径先获得 D1/轻量版本号或 Redis current-version，再读取对应快照。旧版本 key 无需同步删除，可由 TTL 回收，避免旧查询在新写入后重新填充旧值。

### 8.3 Redis 不可用

| 能力 | 故障策略 |
| --- | --- |
| 普通查询缓存 | 直接回源 D1，增加本机短 TTL L1 和请求合并 |
| 排行榜/公开列表 | 回源 D1，并启用并发上限防止雪崩 |
| Pub/Sub | 客户端回退 2～5 秒带抖动轮询 |
| Presence | 显示“状态未知”，不把用户判定为退出 |
| Matchmaking | 暂停快速匹配，仍允许房间码加入 |
| 幂等缓存 | D1 CAS/唯一约束兜底 |
| AI 系统密钥限流/租约 | 保护性拒绝，避免重复费用 |
| 普通读限流 | 本机紧缩 fallback |

### 8.4 D1 Gateway 不可用

- `/health/ready` 返回失败，实例停止接收新流量；
- 后续 WebSocket 客户端应在连接中断后重连，必要时回退 HTTP 轮询；
- 只允许无需 D1 的心跳/静态能力；
- 不把 Redis 缓存提升成权威写库；
- 使用指数退避和熔断，避免所有请求不断重试 Gateway；
- D1 写请求最多由应用层重试一次，且必须具备 request ID/幂等约束。

## 9. 部署建议

### 9.1 起步规格

- Hono Node：2 vCPU / 4 GiB RAM，Node.js 24 LTS；
- Redis：同区域托管实例，1 GiB 起步，TLS、私网、自动故障转移；
- D1 Gateway：Cloudflare Worker Paid，D1 native binding；
- `cloudflared`：与 Hono 同机或同私网，公网不开放 API 端口；
- Hono 仅监听 `127.0.0.1:3001`，通过 Tunnel 暴露；
- Redis 不配置公网 allow-all，禁止直接从浏览器访问。

MVP 可先使用一套 Redis，但必须设置所有 key TTL、内存告警和写失败监控。用户规模扩大后拆成：

1. control Redis：限流、租约、幂等、presence、Pub/Sub；
2. cache Redis：查询缓存，允许 LFU 淘汰。

控制实例不应因为大量缓存 value 被驱逐。单实例阶段建议将 Redis 使用量长期控制在 60% 以下，达到 70% 告警，80% 停止写入非关键缓存。

### 9.2 环境变量

Hono Node：

```text
PORT=3001
PUBLIC_ORIGIN=https://example.com
D1_GATEWAY_URL=https://d1-internal.example.com
D1_GATEWAY_ACCESS_CLIENT_ID=...
D1_GATEWAY_ACCESS_CLIENT_SECRET=...
D1_GATEWAY_HMAC_SECRET=...
REDIS_URL=rediss://...
REDIS_KEY_PREFIX=maho:v1:prod
INSTANCE_ID=...
```

D1 的 Cloudflare Account API Token 不再放进 Hono 生产容器。迁移/运维脚本可继续在受控 CI 环境使用它。

## 10. 分阶段实施

### 阶段 0：基线与契约冻结（1～2 天）

- 导出 133 条路由清单、method、认证方式、body 限制和响应样例；
- 记录各 API 的 D1 query 次数、rows read/written、p50/p95/p99；
- 建立公开 GET、登录 CRUD、PvP CAS、AI stream 四类 contract test；
- 明确 Redis 缓存命中率和故障目标。

验收：迁移前行为和性能基线可重复。

### 阶段 1：运行时抽象（3～5 天）

- 新增 `DatabaseProvider`、`CacheStore`、`RateLimitStore`、`LeaseStore`、`TaskDispatcher`；
- 将约 41 个 `NextRequest` 收敛为标准 `Request`；
- 将 `waitUntil` 收口到 `TaskDispatcher`；
- 保持原 Cloudflare 部署行为不变，先补单元测试。

验收：`pnpm test`、`pnpm lint`、`pnpm build`、`pnpm build:cf` 通过。

### 阶段 2：D1 Gateway 与 Node 数据适配（3～6 天）

- 新建 `apps/d1-gateway`；
- 改造 `lib/db/d1-http-client.ts` 支持 Gateway URL、Access/HMAC、bookmark 和 abort；
- 将独立查询合并为 D1 batch；
- 对 Gateway 做权限、重放、超时、batch rollback 和故障测试；
- 先迁 tags、presets、公开 stats 等只读路由。

验收：生产候选环境不再调用 Cloudflare D1 管理 Query REST；读请求能观察到 `served_by_region`，写后读保持一致。

### 阶段 3：Redis P0（3～5 天）

- 迁移 6 组限流/冷却；
- 替换 `withEdgeCache` 的服务端共享缓存；
- 迁移女王实体与 AI snapshot single-flight；
- 添加 Redis outage fallback、指标和 key cardinality 测试。

验收：双实例压测下限流总量不放大；Redis 断开不会导致普通读接口不可用。

### 阶段 4：Hono API 与鉴权/流式路由（5～8 天）

- 建立 Hono route manifest、middleware、错误边界和结构化日志；
- Better Auth 直接挂载，删除 session verify 自请求；
- 迁移 13 条流式接口，验证断流和 backpressure；
- Cloudflare 先灰度只读，再灰度登录写和 AI。

验收：Cookie、Set-Cookie、多值 header、SSE、abort 和旧接口一致。

### 阶段 5：PvP Redis 实时层（5～10 天）

- 加入 WebSocket 鉴权、presence 和 room Pub/Sub；
- 房间公开快照使用版本化 cache；
- 引入快速匹配队列和昂贵动作租约；
- 保留轮询 fallback；所有状态转换仍先提交 D1 CAS。

验收：两个 Node 实例之间广播正常；关闭任一实例后客户端能重连并从 D1 快照恢复；重复 resolve/settle 不产生重复结果。

### 阶段 6：统计写合并与全量切流（3～7 天）

- AI outcome、user activity 改成 Redis 聚合 + D1 batch flush；
- 按 1% -> 10% -> 50% -> 100% 切流；
- 旧 Next API 保留至少两个发布周期；
- 稳定后删除 Cloudflare runtime discovery 和旧 Route wrappers。

## 11. 测试与发布门槛

### 11.1 功能

- 133 条路由 contract 覆盖状态码、body、header、Cookie；
- D1 batch 中任一语句失败时无部分提交；
- PvP `version` 冲突稳定返回 409/业务冲突，不被 Redis 锁掩盖；
- Redis 缓存失效后不会返回私有或旧权限数据；
- Better Auth 登录、退出、注销、封禁和密码重置完整通过；
- SSE/流式生成断开后能取消上游并释放 Redis lease。

### 11.2 性能

- 单个普通 API 的 Gateway 往返次数目标不超过 2；复杂 PvP snapshot 不超过 3；
- 非 AI API p95 不劣于旧服务 10%；
- 热点公开 GET Redis 命中率目标 > 80%；
- D1 Gateway 429 为 0，overloaded 错误率 < 0.1%；
- Redis 命令 p95 < 10 ms（同区域目标）；
- WebSocket 广播端到端 p95 < 200 ms（大陆网络另行分运营商观测）。

### 11.3 故障演练

- Redis 断网 5 分钟；
- D1 Gateway 返回 429/5xx/超时；
- Node 收到 SIGTERM；
- Pub/Sub 中断和恢复；
- 重复提交相同 request ID；
- 两实例同时 resolve 同一 round；
- Cloudflare/Tunnel 主动断开 WebSocket。

## 12. 观测指标

至少采集：

- `http_requests_total`、`http_duration_ms`、流式 TTFB；
- `d1_gateway_requests_total`、round trips/request、rows read/written、served region/primary；
- `redis_command_duration_ms`、hit/miss、errors、memory、evictions、connected clients；
- limiter allowed/denied/fallback；lease acquired/conflict/expired；
- WebSocket active connections、room fanout、send buffer、reconnect；
- PvP CAS conflict、duplicate command、snapshot rebuild；
- AI upstream active、abort、token usage和系统密钥拒绝次数。

日志关联字段：`traceId`、`requestId`、`instanceId`、`userIdHash`、`roomId`、`d1BookmarkHash`；不得记录原始 token、Cookie、HMAC secret 或完整私有卡牌内容。

## 13. 首个实现 PR 建议

首个 PR 只建立边界，不切正式流量：

1. 新增 `apps/api` Hono skeleton、health 和 route adapter；
2. 新增 `apps/d1-gateway`，只支持参数化 query/batch；
3. 新增 `DatabaseProvider`、`CacheStore`、`RateLimitStore` 接口及内存测试实现；
4. 改造 HTTP D1 client，使目标从 Cloudflare 管理 REST 可切换到 Gateway；
5. 接入 Redis client，但只迁登录限流、公共 AI 冷却和一个公开 GET cache；
6. 选择三条代表路由做端到端验证：`tags`、登录/会话、PvP room GET；
7. 增加 Gateway batch rollback、bookmark、Redis outage 和双实例限流测试。

这个 PR 不迁全部路由、不启用 WebSocket、不改变 D1 schema，也不删除旧 Next API。验证通过后再按领域拆分迁移，降低一次性回归面。
