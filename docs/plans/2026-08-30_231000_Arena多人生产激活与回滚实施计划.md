# Arena 多人生产激活与回滚实施计划

**Goal:** 在不改变 Hono + Redis single-writer、Room v1 排除 Cloudflare DR 与默认关闭边界的前提下，按
reader-first 顺序安全启用 production Arena 多人，并保留可验证的三层回滚路径。

**Architecture（2026-08-31 re-baseline）：** Arena Room production HTTPS/WSS 复用 Hosted 现有 Hono primary origin；
当前为 `https://homura.colanns.me`。不再为 Room provision `api.mahoshojo.colanns.me`、独立 DNS/Caddy/TLS 或第二套
service-origin source of truth。Hono release tuple 决定 writer 能力，`.env.hono` request flag 决定运行时是否公开，Web
build flag 最后决定客户端曝光；任一层未就绪都保持 fail closed。

**Tech Stack:** GitHub Actions、Hono/Node、Redis、Caddy、Cloudflare Workers、Vitest、curl。

## 2. 角色与 go/no-go

- **执行人：** 用户指定的平台管理员，负责 GitHub Environment、`.env.hono` 与 workflow dispatch；现有 Hono primary
  DNS/TLS/Caddy 只做健康核验，不新增 Room 专属入口；
- **观察与回滚人：** 执行人在每个阶段同时承担观察和回滚，不在无人观察时开启 Web flag；
- **变更授权：** 每次 production mutation 前由用户单独确认；“准备完成”不等于 deploy 授权；
- **可接受降级：** 任一 Room 门禁失败时，多人入口保持关闭，现有单人 Arena 与其他 Hosted API 必须继续可用。

## 8. 观察、停止与回滚

公开后至少观察一轮真实操作，关注 Hono CPU/RSS/event-loop、Redis latency/memory/eviction、Room actor queue、snapshot
bytes/latency、socket close、reconnect/resync 与 publisher backlog。没有生产 SLA 时只记录基线，不伪造阈值。

命中以下任一项立即停止：readiness 非 200、HTTP/WSS 认证/CORS contract 不符、Redis/D1 required dependency degraded、
出现第二个 room-capable writer、rollback target 不兼容、terminal/finalization 重复或用户出现整包延迟。

先做曝光收缩，再按需做代码回滚：

1. 把 Web public flag 改为 false 并发布隐藏 UI；
2. 原子把 Hono `ARENA_MULTIPLAYER_ENABLED` 改为 false，并重跑当前 enabled tuple确认 backend 不再公开；
3. 手工 dispatch Hono `arena_room_writer_activation=disabled`；部署脚本会拒绝 request 仍开启时回退；
4. 若问题来自新代码而非开关，按通用部署指南把 Worker 回退到记录的 version，并把 Hono 回退到
   记录的 immutable writer-disabled reader release；
5. 不执行 Redis flush，不删除 D1 审计事实；现有 Hono primary DNS/TLS/Caddy 保持平台通用配置；
6. 验证单人 Arena、retained Hosted routes、Hono readiness 与 production Web 均恢复正常。
