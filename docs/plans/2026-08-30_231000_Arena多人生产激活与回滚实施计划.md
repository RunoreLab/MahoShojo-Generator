# Arena 多人生产激活与回滚实施计划

状态：`ACCEPTED / READY_FOR_PRODUCTION_ACTIVATION`

日期：2026-08-31

## 1. 目标与判断

Arena Room production HTTP/WSS 已直接复用 Hosted Hono primary，不再需要独立 Room hostname。多人模式的生产发布应回到
PR #55 合并前、Hono 初次上线时的主干自动发布模型：一次默认分支 push 完成一次 CI、Hono 发布和 Cloudflare 发布；
不得再要求 operator 重复填写相同事实、重复跑 CI，或手工完成 reader attestation、go/no-go token 和两次相同 Hono
dispatch。

简化不改变下列安全边界：Hono + Redis single-writer、不可变 release tuple、精确 Origin、Room realtime 排除
Cloudflare DR、部署事务与回滚 baseline、HTTP/WSS contract probe，以及 Redis/D1/R2 authority。

## 2. 冻结发布模型

```text
default-branch push
  -> ci:verify（一次）
  -> 构建 writer-enabled Hono immutable release tuple
  -> Hono production deploy transaction
  -> readiness + retained route + Room HTTP/WSS/CORS probe
  -> 调用 Cloudflare reusable workflow
  -> Web build（NEXT_PUBLIC_ARENA_MULTIPLAYER_ENABLED=true）
  -> Worker deploy --keep-vars
  -> /arena + Hono readiness smoke
```

以上步骤必须串行。Hono deploy 或 backend probe 失败时不得发布 Web；Cloudflare workflow 不再单独监听 push，也不重复
`ci:verify`。Preview 使用同一合同，但保持独立部署根、Redis prefix、public origin 和 feature flag。

生产激活只保留两个有独立语义的控制：

1. Hono `.env.hono` 的 `ARENA_MULTIPLAYER_ENABLED`：服务端 request kill switch；
2. Web build 的 `NEXT_PUBLIC_ARENA_MULTIPLAYER_ENABLED`：用户入口 exposure switch。

immutable release tuple 的 `writerActivation=enabled` 继续证明 binary 具备 writer 能力，但不再由 operator 在日常发布时
选择；正常发布固定生成 enabled tuple。request flag 关闭时，enabled binary 仍不得公开 Room HTTP/WSS。

## 3. 一次性生产前置核对

执行人只核对“存在性、权限、非秘密枚举值和一致性”，不得把 secret 值输出到终端、日志、仓库或交付说明。

- `/opt/mahoshojo-hono/.env.hono` 是部署用户所有的普通文件、非符号链接且 mode 为 `0600`；
- `ARENA_ROOM_ALLOWED_ORIGINS=https://mahoshojo.colanns.me`；`ARENA_MULTIPLAYER_ENABLED` 在普通 v2 发布前为
  `true`，从历史 v1 baseline 首次迁移时按第 4 节的一次性桥接保持 `false`；
- Hono 所需 Redis、D1 Gateway、R2、auth、generation finalization 等配置存在，readiness 的 required dependencies 均 ready；
- GitHub `hono-production` Environment 的 VPS host/user/key/host-key 配置存在；
- Cloudflare production deploy credentials 与 generation finalization secret 已配置；
- Hosted Hono primary `https://homura.colanns.me` 的 readiness、TLS 与 Caddy proxy 健康；
- production current immutable tuple、manifest、container 与 Redis healthy，且没有悬挂 deployment transaction。

缺少秘密配置时由平台管理员补齐；不得以临时弱化鉴权、CORS、manifest 或 deploy validator 的方式通过发布。

## 4. 首次激活

1. 若 production current 已是 schema v2，直接对 `.env.hono` 做保留 owner/mode 的原子更新，只把
   `ARENA_MULTIPLAYER_ENABLED` 设为 `true`；不得改写或打印其他值。
2. 若 current 仍是历史 schema v1 writer-disabled tuple，旧 binary 可能拒绝在 request=true 环境下充当回滚 baseline。
   这时必须完成一次性桥接：保持 request=false，以手工 Hono dispatch 的 `arena_multiplayer=disabled` 发布 v2 tuple；确认
   v2 已成为 current 后再原子设为 true，并发布同一或更新的 v2 tuple。两个阶段都必须经过 transaction/probes，第一阶段
   Cloudflare exposure 保持 false。完成桥接后永久回到普通单流水线，不再重复这项迁移。
3. 合并并 push 已通过 review 与 `ci:verify` 的提交到默认分支。普通 push 固定生成 writer-enabled tuple并启动第 2 节的
   单流水线，不需要额外 workflow dispatch。
4. 记录 Hono 输出的 candidate release ID、`ROLLBACK_BASELINE_RELEASE_ID`、GitHub workflow run 和 Cloudflare version。
5. 验证 Hono readiness、Room 未认证 HTTP 401/stable error/exact ACAO、合法 WSS handshake 无 ticket 401，以及 production
   `/arena` 可达并出现 `[data-arena-multiplayer="v1"]`。
   `@hono/node-server` 的 upgrade rejection wire body 为空，因此公网 WSS gate 固定状态码 401；内部
   `ROOM_TICKET_REQUIRED` 由 authority 单元合同固定。
6. 只有在具备测试账号和明确业务写入窗口时才执行真实双成员 canary；无授权时公开 wire contract smoke已足够完成发布，
   不伪造业务 canary 证据。

首次激活以后，默认分支 push 沿用相同自动流程，不再维持一次性激活仪式。

## 5. 紧急关闭与回滚

优先收缩 exposure，再停止 request，最后才切换 immutable code：

1. 手工运行 `Deploy to Cloudflare Workers` 的 emergency disable 入口。该入口只允许构建
   `NEXT_PUBLIC_ARENA_MULTIPLAYER_ENABLED=false`，不能误用于开启多人；它隐藏 Web 入口但不宣称后端已关闭。
2. 原子把 production `.env.hono` 的 `ARENA_MULTIPLAYER_ENABLED` 改为 `false`，保留 owner/mode，并通过当前或后续安全
   Hono release 让 request kill switch 生效。验证 Room HTTP/WSS 不出现 2xx/101。
3. 若问题来自 Hono code，使用当前 immutable release-local `deploy-bundle.sh rollback <baseline-id> <origin>`。从
   writer-enabled release 回退前必须已关闭 generation start；脚本继续验证 target checkpoint contract、完整 tuple、事务恢复和
   公网 probe。
4. 若问题来自 Web/Worker code，回退到发布前记录的明确 Cloudflare version；若旧 version 可能重新曝光多人，优先使用第 1
   步的新 disabled build。

不得 flush Redis、删除 D1/R2 business facts、手改 `current` symlink、删除 deployment journal、把 Room realtime 切入
Cloudflare DR，或以重新引入独立 hostname 绕过 gate。

## 6. 保留与删除的流程

| 保留 | 删除 |
| --- | --- |
| 一次 `ci:verify` | Hono 与 Cloudflare 重复 CI |
| immutable tuple、manifest、single-writer | operator 选择日常 writer tuple |
| exact Origin 与 HTTP/WSS/CORS probes | reader rollout attestation env |
| Hono transaction、baseline 与 compatible rollback | production go/no-go token env |
| 服务端 request kill switch | Web writer/reader/go-no-go 三个派生公共变量 |
| Web exposure switch 与 emergency disable | 正常发布的两次 Hono dispatch |
| Environment protection、SSH host key、secret 隔离 | 独立 Room DNS/Caddy/TLS provision |

## 7. 完成条件

- 默认分支 push 只跑一次 CI，并严格按 Hono 成功后再发布 Cloudflare；
- production Room HTTP/WSS 只使用 Hosted Hono primary；
- Web 只公开一个多人 feature flag，不承载服务器 writer/reader/授权证明；
- request off、认证失败、Origin 不匹配、Redis/required dependency 不健康时继续 fail closed；
- 记录实际 release/version/baseline，公开 smoke 通过，无 secret 泄漏；
- rollback drill 或静态/fault-injection 覆盖仍证明可恢复，不以生产数据破坏测试回滚；
- Room authority、generation/finalization 与 Cloudflare DR exclusion 均未改变。
