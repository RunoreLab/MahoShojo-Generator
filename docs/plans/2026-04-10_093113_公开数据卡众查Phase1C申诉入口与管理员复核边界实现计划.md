# 公开数据卡众查 Phase 1C 申诉入口与管理员复核边界 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为公开数据卡举报案件补齐被处理用户的申诉入口、申诉数据层、用户侧申诉页，以及管理员复核与结果写回 API 边界，完成众查一期剩余的 Phase 1C 闭环。

**Architecture:** 继续保持“举报事实层 `report_cases/reports` + 众查执行层 `crowd_review_*` + 新增申诉子域 `report_appeals/*`”的分层。处理结果通知与创作者入口复用现有消息系统和 `DataCardDetailsModal`；申诉正文与状态使用独立表承载；管理员侧先暴露无 UI 的 API/service 边界，由后续 `feat/admin` 页面直接复用。众查历史事实不回写，管理员复核只更新 `report_cases` 与 `report_appeals`。

**Tech Stack:** Next.js Pages Router、React 19、Cloudflare Edge Runtime、Cloudflare D1、Drizzle ORM、Bun test、现有消息系统、现有公开数据卡举报与众查服务。

## Scope Notes

- This plan includes user-facing appeal submission, appeal history viewing, result-notification messages, and admin review API boundaries.
- This plan intentionally excludes `feat/admin` 后台页面、文件上传、举报人通知回流和巡查使自动扣分。
- This plan keeps the implementation data-card-specific. Do not introduce a multi-object “generic moderation appeals platform”.
- Reuse existing public data card / encyclopedia structured reference rules; do not add arbitrary URL or image attachments.

Implementation rules:

- Require `report_cases.status = 'resolved'` plus adverse `resolutionCode` for entry/submit.
- Treat `confirmed_violation`, `content_removed`, and `self_remediated` as appealable adverse final outcomes.
- Compare `caseUpdatedAtSnapshot` against the live case before create.
- Allow one `submitted/under_review` appeal per `report_case` at a time.
- Treat an existing `submitted/under_review/resolved` appeal for the same snapshot as the canonical record and return it instead of creating a duplicate.
- If the same snapshot only has `withdrawn` history, allow submit to create a brand-new row instead of reopening the withdrawn one.
- Generate `evidence_summary_json` from normalized references on write, and only fall back to dynamic reconstruction when reading legacy or incomplete rows.
- On `reviewReportAppeal`, write both `report_appeals` and `report_cases` in the same logical flow.
- After `reviewReportAppeal` commits a final resolution, emit exactly one `user.moderation.report_appeal_resolved` message with `actionUrl = /report-appeals?appealId=<id>`; repeated review retries must not duplicate this notification.
