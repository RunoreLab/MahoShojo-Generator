# 竞技场战报流式中断复盘与排障建议（2026-02-08）

## 1) 背景与现象

近期用户反馈包含两类看似矛盾的现象：

- 现象 A：移动端小窗/切后台后，流式战报“半截结束”，且未明显报错。
- 现象 B：也有用户在类似机型上正常，说明并非“必现的前端 bug”。
- 现象 C：新增反馈指出“正常前台使用也会中断”，排除“仅后台冻结”这一单一解释。

综合看，这是**多因素叠加**问题，而不是单点故障。

---

## 2) 代码链路与关键观察

### 2.1 前端读取 SSE 的完成判定存在“假阳性成功”窗口

文件：`components/arena/hooks/useBattleEngine.ts`

- 前端在 SSE 读取时维护 `sawDoneEvent`（`event: done`）状态。
- 但当底层 `reader.read()` 返回 `done=true` 时，会直接结束读取流程。
- 结束后未强制要求 `sawDoneEvent === true` 才算成功。
- 结果：若连接提前关闭（但没有抛错），可能出现“半截内容 + 无错误提示”。

这会解释“看起来像正常完成，但实际被截断”的用户体感。

### 2.2 服务端把“上游 EOF”当作可完成流

文件：`pages/api/arena/generate-stream.ts`

- 服务端将上游流读到 `done=true` 后执行 `finalizeSseAndClose(...)`。
- 只要已有“非空正文”就会发送 `event: done`，并记录 `completed`。
- 目前并没有“语义完整性”校验（例如必需段落、结束标记、finishReason 校验）。

这意味着：即便上游因为不明原因提前结束，只要有一些正文，仍可能被判为完成。

### 2.3 上游 `streamText` 的 finishReason 未被利用

文件：`lib/stream/raw-ai.ts`

- 当前调用 `streamText(...)`，但未将 `result.finishReason` 持久化或透传到业务判定层。
- 因此无法区分：
  - 正常 `stop`
  - 长度截断 `length`
  - 内容拦截 `content-filter`
  - 其他异常结束 `error/unknown`

这使“上游模型主动/被动提早停止”与“传输中断”在观测上混在一起。

---

## 3) 结论：当前最可能是“上游 + 链路 + 判定策略”三者叠加

结合新增反馈“正常前台也会中断”，我建议将根因从“移动端焦点切换”升级为：

1. **上游生成提早停止（概率高）**  
   可能由模型侧长度/安全/网关策略触发；当前未记录 finishReason，难以直接证伪。

2. **SSE 传输中途关闭（概率中高）**  
   包括运营商网络抖动、浏览器连接回收、边缘链路波动；不一定抛异常，可能直接 EOF。

3. **前后端“完成判定偏宽松”（确定存在）**  
   导致部分“异常结束”被误判为成功完成，进而出现“截断但无报错”。

> 换句话说：即使真实起因在上游，当前产品层也缺少足够强的“异常识别与提示”。

---

## 4) 建议的排障优先级（按收益排序）

### P0（建议优先本周落地）

1. **明确三态语义：成功 / 中断 / 失败**
   - 中断不是失败，也不是成功。
   - 前端提示语与业务动作分离：  
     - 失败：允许 0 冷却重试  
     - 中断：计入正常冷却（不可 0 冷却）

2. **前端把“无 done 的 EOF”归类为中断**
   - SSE 模式下：若流结束时 `sawDoneEvent=false`，前端标记为“中断”。
   - 不走“失败文案”，但会触发冷却。

3. **服务端 D1 状态映射保持可审计**
   - `failed`：明确业务失败（上游报错、空输出等）。
   - `aborted`：传输/读取中断（超时、连接中断、取消）。
   - 保证后台统计可区分“真失败率”和“中断率”。

4. **SSE error 事件携带状态字段**
   - 透传 `status=aborted|failed` 与 `interrupted=true/false`，前端可直接按三态处理。

### P1（建议下个迭代）

5. **补齐 finishReason 可观测性**
   - 从 `streamText` 提取并记录 `finishReason`，用于区分 length/content-filter/stop。

6. **SSE 心跳与链路保活**
   - 服务器每 10~15 秒发送心跳，降低中间链路空闲断开概率。

7. **异常后恢复入口**
   - 基于 `generationId` 提供“从记录恢复/继续查看”入口，减少用户感知损耗。

## 5) 快速判因矩阵（运营/开发可直接使用）

### 场景 A：客户端 `sawDoneEvent=false`，但有部分正文
- 判断：大概率传输中断（客户端-边缘链路）。
- 动作：记为“中断”（`aborted`），并计入冷却，不归类失败。

### 场景 B：`sawDoneEvent=true`，`finishReason=length`
- 判断：上游输出长度受限导致提早停止。
- 动作：按产品策略决定计为“中断”或“成功（长度截断）”，但不应混入失败。

### 场景 C：`sawDoneEvent=true`，`finishReason=content-filter`
- 判断：上游安全策略截断。
- 动作：按“中断”处理更贴近用户体感（非系统失败）。

### 场景 D：`sawDoneEvent=true`，`finishReason=stop` 但内容明显半截
- 判断：提示词约束不足或模型过早收束。
- 动作：优先通过日志观测和提示词调优处理，不必引入结束哨兵。

---

## 6) 建议采集的最小证据集（用于后续复盘）

每次用户反馈“流式中断”时，建议采集：

1. `generationId`
2. 是否 SSE（当前是 `format=sse`）
3. 客户端日志：
   - `SSE 调试：响应信息`
   - `SSE 调试：读取结束`（重点看 `sawDoneEvent`）
4. 服务端记录：
   - generation status（completed/failed/aborted）
   - finishReason（待补采）
   - outputChars / usage（尤其 completion tokens）

---

## 7) 立即可执行的临时缓解建议（无需改代码）

1. 降低上下文长度（减少叙事历史/历战记录读取）。
2. 出现中断后按冷却窗口再重试，连续复现时换模型。
3. 移动端关闭浏览器节电/后台冻结策略（仍有帮助，但已不是唯一根因）。
4. 开启 `debugSse=1` 收集日志后再判断是上游截断还是链路中断。

---

## 8) SSE 与“无 SSE”方案评估

### 8.1 直接回退到无 SSE（plain text stream）的优点

- 实现更简单，事件解析链路更短。
- 少一层 `event/data` 组包与解析，调试门槛略低。

### 8.2 直接回退的代价

- 丢失结构化事件通道（`reasoning` / `meta` / `telemetry` / `error status`）。
- 错误与中断语义更难表达，最终又会退回“正文猜测”。
- 现有 Arena/PVP 已围绕 SSE 事件构建，回退会带来较多兼容改造。

### 8.3 推荐策略（折中）

- **不建议全量回退**，建议保留 SSE 为主链路。
- 增加“传输策略开关”：
  - `sse`（默认）
  - `plain-stream`（兼容/排障模式）
- 通过灰度和埋点比较两种策略的 `aborted` 与 `failed` 比例，再决定是否扩大 plain-stream 覆盖。

---

## 9) 实施备注

- 本文档结论不否认“移动端后台策略”影响，但将其从“唯一根因”降级为“触发因子之一”。
- 当前最确定且可立即改进的点是：**三态语义 + 状态可观测性**。
- 先把“中断/失败”边界与冷却策略落稳，再评估是否做传输层灰度切换。
