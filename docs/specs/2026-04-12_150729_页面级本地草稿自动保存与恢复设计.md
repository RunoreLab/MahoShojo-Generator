# 页面级本地草稿自动保存与恢复设计

日期：2026-04-12  
状态：已完成设计讨论，待人工评审  
范围：为输入密集型页面补齐“刷新后可恢复”的本地草稿能力，首期覆盖 [`pages/scenario.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/scenario.tsx) 与 [`pages/character-manager.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/character-manager.tsx)，并沉淀轻量通用存储边界  
核心参考：[`pages/details.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/details.tsx)、[`pages/free.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/free.tsx)

## 1. 背景

当前仓库已经存在多处浏览器本地存储逻辑，但职责不一致：

- [`pages/details.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/details.tsx) 已具备问卷答案自动保存与恢复能力。
- [`pages/free.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/free.tsx) 会保存创作输入与部分偏好。
- [`pages/scenario.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/scenario.tsx) 目前只保存偏好项，不保存正文输入或生成后继续编辑的草稿。
- [`pages/character-manager.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/character-manager.tsx) 目前不保存编辑中的数据本体，刷新后会直接丢失当前编辑内容。

这导致用户在情景页、角色管理页等输入密集型页面里，一旦误触刷新，就会失去已经填写的大量内容。

问题的核心不是“如何拦截刷新”，而是“刷新之后能否恢复用户刚才的工作”。因此本次设计将“页面级本地草稿”视为输入密集页的基础能力，而不是额外增强项。

---

## 2. 目标

### 2.1 本次目标

- 为 [`pages/scenario.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/scenario.tsx) 补齐正文输入与可编辑结果的自动保存、自动恢复能力。
- 为 [`pages/character-manager.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/character-manager.tsx) 补齐粘贴态与编辑态草稿恢复能力。
- 新增一层轻量通用草稿存储边界，统一处理 `localStorage` 读写、版本、过期、损坏兜底与清空。
- 页面打开时默认自动恢复未过期草稿，不要求用户二次确认。
- 页面提供清晰但不打扰的 UI 提示，让用户知道浏览器已自动保存，并可显式清空草稿。

### 2.2 明确非目标

- 本次不引入全局“离开页面确认”弹窗。
- 本次不把所有页面的本地存储逻辑一次性重构为统一框架。
- 本次不持久化 API Key、推理流、加载态、报错提示、弹窗开关等瞬时状态。
- 本次不做跨设备同步，仍限定为“当前浏览器本地恢复”。
- 本次不把非结构化结果全部长期缓存到浏览器，只保存明确属于“用户可继续编辑的草稿”。

---

## 3. 设计原则

### 3.1 自动恢复优先

用户已经明确偏好“打开页面就自动恢复草稿”。因此首期产品策略为：

- 检测到未过期草稿时，页面初始化阶段直接恢复。
- 不额外弹确认框，不增加一次点击成本。
- 仅在草稿损坏、过期或本地存储不可用时跳过恢复。

### 3.2 轻通用层，重页面边界

本次不追求抽象出庞大的全局状态系统，而是采用：

- 通用层只负责安全读写、版本、TTL、清空与时间戳。
- 每个页面自行定义“草稿 payload”结构与恢复策略。

这样可以避免过度抽象，同时收敛已经分散在多个页面内的重复存储逻辑。

### 3.3 只保存高价值状态

草稿持久化只覆盖以下状态：

- 用户重新输入成本高
- 刷新后丢失会明显伤害体验
- 恢复后不会制造大量脏 UI

与之相对，报错文本、流式推理内容、扫描结果、弹窗开关等状态恢复价值低，且容易制造误导，因此不纳入草稿。

### 3.4 明确清空边界

保存成功不等于用户“工作结束”。因此：

- 导出、复制、保存到云端后默认不自动清空草稿。
- 只有用户明确执行“清空本地草稿”或“加载其他数据”等重置型动作时，才清空对应草稿。

## 5. 通用草稿存储层设计

### 5.1 新增位置

建议新增：

- [`lib/page-draft-storage.ts`](/home/notuhao/code/MahoShojo-Generator/lib/page-draft-storage.ts)

必要时可再补一个轻量 hook，例如：

- [`lib/usePageDraft.ts`](/home/notuhao/code/MahoShojo-Generator/lib/usePageDraft.ts)

若 hook 不能明显降低复杂度，则允许仅保留 `storage` 工具函数，由页面自行组织 `useEffect`。

### 5.2 通用层职责

通用层统一提供：

- `readPageDraft`
- `writePageDraft`
- `clearPageDraft`
- 过期判断
- 版本校验
- 损坏 JSON 兜底
- `updatedAt` 记录

建议通用存储格式：

```ts
type StoredPageDraft<T> = {
  version: number;
  updatedAt: number;
  payload: T;
};
```

### 5.3 Key 规范

建议为每个页面使用独立 key，例如：

- `mahoshojo.scenario.page-draft.v1`
- `mahoshojo.character-manager.page-draft.v1`

禁止把多个页面的草稿混存到同一 key 下，避免恢复边界混乱。

### 5.4 TTL 策略

建议统一设置 TTL，例如 14 天或 30 天。

要求：

- 超过 TTL 的草稿不再恢复。
- 发现过期草稿时自动删除。
- TTL 判断统一由通用层负责，页面不重复实现。

### 5.5 异常与降级策略

通用层需要保证：

- `window` 不存在时安全返回，不在服务端渲染阶段报错。
- `localStorage` 不可用时静默失败。
- JSON 解析失败时返回空结果，并清理损坏草稿。
- 所有异常最多 `console.warn`，不能阻塞页面正常使用。

### 5.6 写入节流

建议页面侧以轻度防抖方式写入本地存储，推荐 400 到 800ms。

目标：

- 避免每次按键都同步写盘。
- 又不至于让刷新窗口过长，导致用户刚输入的内容来不及落盘。

## 6. `/scenario` 页面设计

### 6.1 保存范围

[`pages/scenario.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/scenario.tsx) 建议保存以下字段：

- `answers`
- `scenarioTitleHint`
- `fieldsToKeepEmpty`
- `isAdvancedVisible`
- `selectedLanguage`
- `generationMode`
- `generalScenarioDraft`
- `generalScenarioDraftEdited`

其中：

- `answers` 用于恢复问卷输入。
- `generalScenarioDraft` 用于恢复流式生成后仍在手动修改的通用情景卡。
- `generalScenarioDraftEdited` 用于标记用户是否真的手动改过流式结果。

### 6.2 不保存范围

以下状态不写入本地草稿：

- `isGenerating`
- `error`
- `streamingReasoning`
- `nonStreamReasoning`
- `resultData`
- `userProviderConfig`

特别说明：

- `resultData` 属于非流式最终结果，更接近“生成产物”，而不是“页面草稿”。本次默认不持久化。
- `userProviderConfig` 不能保存到页面草稿里，尤其不能落地 `apiKey`。

### 6.3 恢复策略

- 页面初始化时，如检测到未过期草稿，直接恢复 `answers` 与相关偏好字段。
- 如果存在 `generalScenarioDraft`，也直接恢复。
- `generalScenarioDraftEdited === true` 时，视为高优先级用户草稿。
- 对“纯流式生成中间态但用户未手改”的内容，不强制长期恢复，以免把半成品长期滞留在本地。

### 6.4 UI 设计

建议在现有页面中新增：

- 自动保存时间提示
  - 文案示例：`已自动保存于 15:07:29`
- 清空本地草稿按钮
  - 清除 `answers`、`generalScenarioDraft` 及本页草稿 key
  - 不清除与草稿无关的页面临时状态

### 6.5 用户收益

这样设计后：

- 用户填写问卷时误刷新，不丢。
- 用户在流式生成后继续修改通用情景卡时误刷新，不丢。
- 页面不会恢复 API Key、错误信息、推理流等不该恢复的状态。

## 7. `/character-manager` 页面设计

### 7.1 草稿分层

[`pages/character-manager.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/character-manager.tsx) 建议将草稿拆成两层：

- `pasteDraft`
  - 表示用户还停留在粘贴 JSON、但尚未点击加载的阶段。
- `editorDraft`
  - 表示用户已经加载并进入编辑态，正在修改数据卡本体。

实现上可以仍写入同一个页面 key，但 payload 结构中需明确区分这两类状态。

### 7.2 保存范围

建议保存以下字段：

- `pastedJson`
- `characterData`
- `originalData`
- `isNative`
- `selectedTemplate`

必要时允许增加：

- `isPasteAreaVisible`
  - 仅当恢复 `pastedJson` 需要自动展开粘贴区时可保留
  - 若页面初始化逻辑可根据 `pastedJson` 自动展开，则无需单独存储

### 7.3 不保存范围

以下状态不纳入草稿：

- `message`
- `validationResult`
- `sensitiveIssues`
- `isSensitiveScanning`
- `lastScanTime`
- `manualCheckText`
- `manualCheckResult`
- 各类弹窗开关
- 登录态、云端卡片列表、徽章列表
- `characterPortraitAsset`

原因：

- 上述状态要么可重新计算，要么属于瞬时 UI，要么恢复价值低。
- 强行恢复这些状态容易造成“页面像停留在半途”的脏体验。

### 7.4 恢复策略

- 若存在 `editorDraft.characterData`，优先恢复编辑态。
- 若不存在编辑态，但存在 `pastedJson`，则恢复粘贴区内容，并自动展开粘贴区域。
- 恢复编辑态时必须同时恢复 `originalData` 与 `isNative`，以保证原生性丧失判断逻辑继续成立。
- `selectedTemplate` 可以从恢复后的数据重新推导；如推导失败，再回退到草稿内兜底值。

### 7.5 关键清空时机

以下动作应显式清空本地草稿：

- 用户点击“加载其他数据”
- 用户明确点击“清空本地草稿”

以下动作应覆盖旧草稿，而不是保留并存：

- 用户成功上传并加载新文件
- 用户通过模板切换创建新的空白数据卡

以下动作默认不清空草稿：

- 保存修改并下载
- 复制到剪贴板
- 保存到云端

原因是这些动作之后，用户仍可能继续编辑。

### 7.6 用户收益

这样设计后：

- 用户在粘贴大量 JSON 后误刷新，不丢。
- 用户在角色/情景数据卡编辑过程中误刷新，不丢。
- 恢复后原生性判断仍具备正确上下文，不会因为只恢复一半状态而误判。

## 8. 恢复优先级与冲突边界

本次产品策略为“默认自动恢复”，因此需要控制自动恢复的优先级，避免覆盖更明确的新输入来源。

首期建议如下：

- 页面初始挂载时执行一次恢复。
- 一旦用户通过上传、模板创建、显式清空等操作进入新的页面状态，应以新的显式输入来源覆盖草稿。
- 不在用户已经明确开始新一轮操作后，再次反向套用旧草稿。

对于本次首期范围：

- `/scenario` 基本不存在复杂外部来源冲突，自动恢复风险较低。
- `/character-manager` 则必须保证“新上传文件”与“新建空白模板”能够覆盖旧草稿。

## 9. UI 与交互文案

### 9.1 通用展示建议

所有接入草稿恢复的页面建议统一提供：

- 自动保存时间提示
- 清空本地草稿按钮

文案建议：

- 自动保存提示：`已自动保存于 HH:mm:ss`
- 恢复提示：`已恢复本地草稿`
- 清空按钮：`清空本地草稿`

### 9.2 交互原则

- 提示应轻量，不打断当前操作。
- 不使用模态框或确认弹窗强行打断用户。
- 清空本地草稿属于显式破坏性操作，可在按钮点击时做一次确认。

## 10. 错误处理

### 10.1 读取失败

- 草稿读取失败时静默兜底，不阻塞页面渲染。
- 记录 `console.warn`，便于排查。
- 如果确认是损坏 JSON，则自动删除损坏项。

### 10.2 过期草稿

- 过期草稿不再恢复。
- 在检测到过期时直接删除。
- 不向用户展示干扰性错误提示。

### 10.3 浏览器存储不可用

- 若 `localStorage` 不可用，页面仍可正常使用。
- 自动保存与恢复能力静默失效，但不影响核心业务流程。

### 10.4 不恢复瞬时状态

恢复草稿时不恢复以下状态：

- 错误提示
- 加载态
- 推理流
- 敏感词扫描结果
- 弹窗开关

这样可以避免用户打开页面时看到一个看似“停留在故障中途”的界面。

## 13. 风险与控制

- 风险：不同页面再次各写一套 `localStorage` 逻辑，形成新的分叉。
  - 控制：本次先收敛通用层，至少统一基础读写、版本、TTL 与异常处理。

- 风险：恢复过多 UI 状态，导致页面看起来像“半卡死”。
  - 控制：只恢复高价值输入，不恢复瞬时状态。

- 风险：`/character-manager` 只恢复 `characterData`，未恢复 `originalData` 与 `isNative`，造成原生性误判。
  - 控制：将其视为同一恢复单元，禁止只恢复部分上下文。

- 风险：用户已经开始新一轮上传或建卡，却又被旧草稿覆盖。
  - 控制：新上传、新建空白模板、显式清空等动作均视为新输入来源，应覆盖或清除旧草稿。

## 14. 结论

本次最合适的实现路径，不是继续在各页面里补散落的 `useEffect + localStorage`，而是先补一层轻量通用草稿存储边界，再优先接入最易造成高成本输入丢失的两个页面：

- [`pages/scenario.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/scenario.tsx)
- [`pages/character-manager.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/character-manager.tsx)

该方案能够在不引入复杂全局框架的前提下，稳定解决“手滑刷新导致内容全部消失”的核心体验问题，并为后续其他输入密集页提供可复用的本地草稿模式。
