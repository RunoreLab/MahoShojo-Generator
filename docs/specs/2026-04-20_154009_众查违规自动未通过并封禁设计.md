# 众查违规自动未通过并封禁设计

更新时间：2026-04-20 15:40:09

## 1. 背景

当前众查 `violation` 结论只会写回 `report_cases`，不会同步把目标数据卡切换到“未通过 + 封禁”状态。结果是社区已经形成违规共识，但卡片仍可能继续以公开可见状态存在。

本设计用于补齐这条治理闭环，但只覆盖**未来新增**的不利最终结论，不回补历史案件。

## 2. 目标

- 当举报案件进入不利最终结论时，自动把目标数据卡设为：
  - `review_status = 'rejected'`
  - `is_public = -1`
- 保留现有 `report_cases` / `report_appeals` 状态机，不重构案件领域。
- 只发送一条处理结果通知，并在通知中明确“系统已自动设为未通过并封禁”。
- 通知失败不回滚案件结论与卡片治理结果。

## 3. 适用范围

### 3.1 当前分支实际接线

当前仓库内只有众查 `violation -> resolved + confirmed_violation` 这条不利结论链路可直接接入，因此本分支只在该链路上启用自动处置。

### 3.2 Helper 预留范围

为了兼容 `feat/admin` 分支，自动处置 helper 的结论口径统一定义为：

- `confirmed_violation`
- `content_removed`
- `self_remediated`

未来管理员入口只需要在写入上述结论后调用同一个 helper，不再复制规则。

### 3.3 明确排除

- 不处理历史已结案案件。
- 不在本分支对 `feat/admin` 做跨分支接线。
- 不在申诉改判后自动恢复卡片。
- 不新增数据库触发器、定时巡检或隐式后台任务。

## 4. 领域规则

### 4.1 不利最终结论

当 `report_cases` 已经被写成以下状态组合时，视为应自动治理卡片：

- `status = 'resolved'`
- `resolution_code IN ('confirmed_violation', 'content_removed', 'self_remediated')`

### 4.2 卡片治理动作

系统侧对目标 `data_cards` 执行以下写入：

- `review_status = 'rejected'`
- `is_public = -1`
- `public_since = null`
- `updated_at = now`

不修改：

- `deleted_at`
- 内容 JSON
- 点赞、收藏、使用计数

### 4.3 幂等语义

helper 必须幂等：

- 若卡不存在：返回“未处理”，不回滚案件结论。
- 若卡已是 `review_status='rejected'` 且 `is_public=-1`：直接 no-op。
- 若卡是私有或待审核，但尚未封禁：仍然强制写成 `rejected + -1`。

### 4.4 申诉后的语义

当申诉结果为：

- `overturned_no_violation`
- `reopened_under_review`

只允许更新 `report_cases` / `report_appeals`，**不得自动恢复**卡片状态；后续恢复由管理员处理。

## 5. 架构设计

### 5.1 新增模块

新增一个小型治理 helper，建议放在：

- `lib/data-card-reports/outcome-enforcement.ts`

职责：

- 接收 `reportCaseId`、`resolutionCode`、`now`
- 判断是否属于不利最终结论
- 拉取目标卡
- 对目标卡执行系统侧治理更新

该模块不负责：

- 写 `report_cases`
- 发通知
- 处理申诉状态

### 5.2 仓储层扩展

在数据卡仓储层新增一个系统侧更新入口，建议放在：

- `lib/db/repositories/data-cards-core.ts`

职责：

- 按 `cardId` 更新 `reviewStatus / isPublic / publicSince / updatedAt`
- 不要求 `userId`
- 供服务层治理逻辑复用

原因：

- 现有 `updateDataCardByIdAndUser` 是用户侧接口，不适合作为系统治理写入口。

### 5.3 现有链路接线

当前分支只在众查写回点调用 helper：

- `lib/crowd-review/service.ts`

顺序固定为：

1. 先写 `report_cases`
2. 再执行卡片自动治理
3. 最后发送 `report_case_resolved` 通知

## 6. 通知设计

继续复用：

- `user.moderation.report_case_resolved`

扩展 payload：

- `cardAutoRejected: boolean`
- `cardAutoBanned: boolean`

当自动治理已执行时，正文要明确体现：

- 当前处理结果
- 系统已自动将该数据卡设为未通过并封禁
- 如有异议可前往申诉页

不新增第二条“未通过”或“封禁”消息，避免多条治理消息并发。

## 7. 失败处理

### 7.1 治理优先

若通知发送失败：

- 保留 `report_cases` 已写入的最终结论
- 保留 `data_cards` 已写入的 `rejected + -1`
- 只回退通知去重标记或重试通知

### 7.2 卡片治理失败

若案件已写回，但卡片自动治理失败：

- 当前请求应视为失败并抛错
- 这样不会产生“案件结论成功、但代码无感知地漏掉卡片治理”的静默坏状态

本设计不尝试跨表分布式事务，只要求服务层明确暴露失败。

## 8. 测试要求

至少覆盖以下行为：

- 众查 `violation` 结案后，案件写回为 `resolved + confirmed_violation`
- 同一流程会把目标卡写成 `review_status='rejected'`、`is_public=-1`
- 已经被封禁的卡重复执行时保持幂等
- 非不利结论不会触发卡片治理
- `report_case_resolved` 模板在自动治理场景下包含“已自动设为未通过并封禁”的正文
- 申诉改判路径不会自动恢复卡片

## 9. 风险与兼容性

- 当前 `listAssignableCases` 只会选择 `reviewStatus='approved'` 的公开卡，因此一旦卡被自动封禁，不会再次进入可众查池。
- PVP 等其他读取路径已把 `review_status='rejected'` 与 `is_public=-1` 视为不可用状态，本设计与现有消费方语义一致。
- 由于本次不补历史数据，线上仍会暂时保留一批旧的“案件已违规、卡仍公开”的历史脏状态；这属于显式接受的范围外问题。
