# 公开数据卡举报机制设计规格

更新时间：2026-04-08 09:40:56

## 1. 目标

本设计用于落地公开数据卡举报机制首版：

- 允许登录用户对公开数据卡发起举报。
- 支持预设举报理由，并允许填写补充说明。
- 支持结构化引用公开数据卡与百科条目，满足抄袭举报与守则依据引用场景。
- 支持同一卡聚合为单个开放案件，但保留多用户、多条举报记录。
- 在基础风控与去重通过后，向被举报卡创作者发送匿名化站内通知，帮助其自查与自整改。
- 为 `feat/admin` 管理后台预留案件处理、结案口径、自整改复核与后续仲裁扩展边界。

## 2. 非目标

- 不处理私有数据卡、本地卡、未公开草稿或已删除卡的举报。
- 不在本分支开发 `feat/admin` 后台页面。
- 不实现申诉流、用户仲裁流、自动处罚流。
- 不支持任意 URL、任意附件或富文本证据包。
- 不把举报系统做成用户私信/讨论线程系统。
- 不实现黑盒风控模型或自动机器审核结案。

## 3. 术语和边界

### 公开数据卡举报

首版仅允许举报满足以下条件的目标：

- `data_cards.is_public = true`
- `review_status = approved`
- 当前未被删除
- 举报发起者可正常读取

不支持举报：

- 私有卡
- 待审核公开卡
- 本地未上传数据
- 已删除或不可见卡

### 案件与举报记录

本设计采用“单卡单开放案件 + 多条举报记录”模型：

- `report_case` 表示“某张公开数据卡当前存在一个活跃治理事件”。
- `report` 表示“某位举报人对该案件提交的一条实名举报记录”。

同一张公开数据卡在案件未关闭前只有一个开放案件，但允许多个不同用户将举报挂到同一案件下。这样可以避免后台重复处理同一个目标，同时保留不同举报人的理由、说明、证据与时间线。

### 举报人身份可见性

首版采用“对创作者匿名、对管理员实名”的口径：

- 创作者收到举报通知时，看不到举报人身份。
- `feat/admin` 后台可见实名举报人信息。
- 后续如接入用户仲裁，仲裁侧默认也只能看到匿名化举报材料。

### 自整改

创作者在收到通知后修改数据卡，不自动撤销案件。

系统会：

- 保留举报提交时的数据卡快照。
- 记录“创作者通知后该卡已更新”状态。
- 交由后台优先按“已自整改，可轻量结案”口径复核。

这意味着首版鼓励自我纠正，但不允许通过“被举报后秒改卡”直接抹除案件证据。

## 4. 方案比较与取舍

### 方案 A：单表轻量举报

做法：

- 所有举报信息直接存入单张 `data_card_reports` 表。
- 每条举报记录同时承担案件、举报人、理由、引用与通知状态。

优点：

- 首版开发成本最低。

缺点：

- 同一卡多用户举报时难以聚合。
- 引用能力只能塞 JSON，后台后续处理不稳定。
- 后续扩展到申诉、仲裁、结案口径时模型会迅速失衡。

### 方案 B：精简案件制

做法：

- `report_cases` 承担目标卡与案件生命周期。
- `reports` 承担每位举报人的举报记录。
- `report_references` 承担结构化引用。

优点：

- 兼顾首版可控复杂度与后续治理扩展。
- 能清晰处理“同一卡多用户举报”的真实场景。
- 便于 `feat/admin` 后台按案件而不是按散乱举报处理。

缺点：

- 比单表多一层聚合逻辑。

### 方案 C：治理大系统

做法：

- 现在就加入申诉、仲裁、案件事件流、处罚审计和用户投票。

优点：

- 未来完整。

缺点：

- 明显超出本分支范围，且后台未开发时会形成大量空壳结构。

### 结论

本设计采用方案 B：精简案件制。

## 5. 数据模型

SQL 层使用 `snake_case`，TypeScript DTO 与组件状态使用 `camelCase`，跨层转换集中在 repository / service 边界。

### 5.1 `report_cases`

```sql
CREATE TABLE IF NOT EXISTS report_cases (
  id TEXT PRIMARY KEY,
  target_entity_type TEXT NOT NULL,
  target_entity_id TEXT NOT NULL,
  target_user_id INTEGER NOT NULL,
  status TEXT NOT NULL,
  resolution_code TEXT,
  risk_state TEXT NOT NULL,
  creator_notified_at TEXT,
  creator_notified_report_count INTEGER NOT NULL DEFAULT 0,
  latest_reported_at TEXT NOT NULL,
  target_card_updated_at_at_notice TEXT,
  closed_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (target_user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_report_cases_target_open
  ON report_cases(target_entity_type, target_entity_id)
  WHERE status IN ('open', 'under_review');

CREATE INDEX IF NOT EXISTS idx_report_cases_status_latest
  ON report_cases(status, latest_reported_at DESC);
```

字段说明：

- `target_entity_type`：首版固定为 `data_card`，为后续扩展保留边界。
- `target_entity_id`：目标数据卡 ID。
- `target_user_id`：目标卡创作者。
- `status`：`open | under_review | resolved | dismissed`。
- `resolution_code`：结案口径，首版预留给后台填写。
- `risk_state`：案件聚合风控状态，`pending_screen | accepted | suppressed`。
- `creator_notified_at`：首次向创作者发送匿名通知的时间。
- `creator_notified_report_count`：发送通知时已接受举报数。
- `target_card_updated_at_at_notice`：通知时的目标卡 `updated_at` 快照，用于判断是否通知后已更新。
- `latest_reported_at`：最近一条有效举报时间。

### 5.2 `reports`

```sql
CREATE TABLE IF NOT EXISTS reports (
  id TEXT PRIMARY KEY,
  case_id TEXT NOT NULL,
  reporter_user_id INTEGER NOT NULL,
  reason_code TEXT NOT NULL,
  details TEXT,
  status TEXT NOT NULL,
  screening_status TEXT NOT NULL,
  evidence_summary_json TEXT NOT NULL DEFAULT '{}',
  target_name_snapshot TEXT NOT NULL,
  target_description_snapshot TEXT,
  target_data_snapshot TEXT NOT NULL,
  target_updated_at_snapshot TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  withdrawn_at TEXT,
  FOREIGN KEY (case_id) REFERENCES report_cases(id) ON DELETE CASCADE,
  FOREIGN KEY (reporter_user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_reports_case_reporter_active
  ON reports(case_id, reporter_user_id)
  WHERE status = 'active';

CREATE INDEX IF NOT EXISTS idx_reports_case_status_created
  ON reports(case_id, status, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_reports_reporter_status_created
  ON reports(reporter_user_id, status, created_at DESC);
```

字段说明：

- `status`：`active | withdrawn`。
- `screening_status`：`accepted | suppressed`。
- `evidence_summary_json`：引用摘要与服务端聚合信息，便于消息模板与后台摘要复用。
- `target_*_snapshot`：举报提交时的目标卡快照，用于后续复核和自整改判定。

### 5.3 `report_references`

```sql
CREATE TABLE IF NOT EXISTS report_references (
  id TEXT PRIMARY KEY,
  report_id TEXT NOT NULL,
  reference_type TEXT NOT NULL,
  reference_id TEXT NOT NULL,
  label_snapshot TEXT NOT NULL,
  url_snapshot TEXT,
  note TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (report_id) REFERENCES reports(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_report_references_report_sort
  ON report_references(report_id, sort_order, created_at);
```

首版允许的 `reference_type`：

- `public_data_card`
- `encyclopedia_entry`

### 5.4 可选扩展字段

首版不强制落库，但 service 层应按扩展友好方式设计：

- 案件聚合理由计数
- 创作者通知载荷快照
- 风控命中原因
- 后续仲裁资格与投票状态

## 6. 举报理由与引用规则

### 6.1 举报理由

首版使用配置驱动的理由白名单，建议默认值：

- `plagiarism`：疑似抄袭或高度近似搬运
- `harassment_or_hate`：辱骂、仇恨、攻击性内容
- `sexual_or_excessive_gore`：露骨性内容或过度血腥猎奇
- `illegal_or_dangerous`：违法、危险、鼓动现实伤害
- `spam_or_malicious_noise`：刷屏、污染、恶意噪声内容
- `rule_violation_other`：其他守则违规

理由配置应与前端选项、后端校验、后台展示共享，避免前后端各自维护。

### 6.2 引用规则

首版支持两类结构化引用：

#### 公开数据卡引用

适用场景：

- 举报抄袭
- 举报高度近似设定
- 引用对照卡作为上下文

约束：

- 只能引用当前公开且可读的数据卡
- 不能引用被举报目标自身
- 保存标题快照和可访问链接快照

#### 百科条目引用

适用场景：

- 引用社区守则
- 引用百科说明
- 引用术语或处理口径

约束：

- `reference_id` 必须来自现有 `encyclopediaEntries.slug`
- 保存条目标题和 `/encyclopedia/[slug]` 链接快照

### 6.3 引用数量

首版每条举报建议最多 5 条引用，防止把用户侧举报模态膨胀成复杂案件工作台。

## 7. 案件生命周期

### 7.1 创建或更新举报

1. 登录用户打开公开数据卡详情。
2. 用户通过“更多 -> 举报此卡”进入举报模态。
3. 提交时服务端校验目标卡、理由、说明与引用。
4. 服务端执行基础风控。
5. 若当前卡没有开放案件，则创建 `report_case`。
6. 若已有开放案件，则复用原案件。
7. 创建或更新当前用户在该案件下的 `report`。
8. 重建该 `report` 对应的 `report_references`。
9. 更新案件聚合时间与有效举报统计。
10. 必要时向创作者发送匿名化通知。

### 7.2 多用户举报同一卡

同一卡多用户举报的处理口径：

- 归入同一个开放案件。
- 每位用户保留自己的举报记录、理由、说明和引用。
- 案件层只负责聚合视图，不覆盖单条举报细节。

这样后台能看到：

- 当前案件有多少条有效举报
- 有多少个不同举报人
- 他们的理由与证据是否一致
- 是否存在明显重复、跟风或恶意滥用

### 7.3 撤回举报

首版建议支持服务端撤回能力：

- 举报人可将自己的 `report.status` 标记为 `withdrawn`
- 若案件下已无任何 `accepted + active` 举报，则案件可自动转为 `dismissed`

前台入口可以首版隐藏或延后接入，但后端能力建议一次设计完整。

### 7.4 结案

案件 `status` 预留：

- `open`
- `under_review`
- `resolved`
- `dismissed`

后台结案口径 `resolution_code` 建议预留：

- `self_remediated`
- `content_removed`
- `confirmed_violation`
- `no_violation`
- `malicious_report`

## 8. 创作者通知与自整改

### 8.1 通知时机

创作者通知口径：

- 不是举报一提交就通知。
- 只有基础风控/去重通过后才通知。
- 同一开放案件只做首次正式通知，后续新增举报不重复轰炸创作者。

### 8.2 通知内容

创作者收到的通知应包含匿名化但可操作的信息：

- 被举报的数据卡名称
- 匿名化理由汇总
- 引用摘要
- 补充说明摘录
- 当前已接受举报数
- 引导其自查和修改

通知不包含：

- 举报人身份
- 管理员内部风控结论
- 其他实名治理信息

### 8.3 自整改处理

自整改口径采用：

- 不自动撤案
- 标记“通知后目标卡已更新”
- 后台默认优先按轻量结案口径复核

判定方式建议为：

- 若 `data_cards.updated_at > creator_notified_at` 或大于 `target_card_updated_at_at_notice`，则视为“通知后已更新”
- 后台复核时同时读取举报时快照和当前最新版

这样能兼顾：

- 鼓励自我修正
- 保留证据链
- 避免“改卡即免审”

## 9. 风控规则

首版只实现确定性、可解释风控。

### 9.1 硬校验

- 仅登录用户可举报
- 禁止自举报
- 仅允许举报公开、已审核通过、未删除且当前可读的数据卡
- `reason_code` 必须来自配置白名单
- `details` 做长度限制
- `references` 类型、数量和目标合法性必须通过校验

### 9.2 频率限制

建议首版做轻量频率限制，例如：

- 单用户 1 小时最多 3 次有效提交
- 单用户 24 小时最多 10 次有效提交

命中频率限制时直接返回明确错误，不静默吞掉请求。

### 9.3 风控结果

每条举报记录独立拥有 `screening_status`：

- `accepted`
- `suppressed`

只有 `accepted + active` 的举报会：

- 进入案件聚合计数
- 触发创作者通知
- 进入后台主处理视图

`suppressed` 记录仍保留，便于后续审计与风控调参。

## 10. 前台交互设计

### 10.1 入口位置

举报入口放在 [DataCardDetailsModal.tsx](/home/notuhao/code/MahoShojo-Generator/components/DataCardDetailsModal.tsx) 内。

建议在模态右上角关闭按钮左侧增加“更多”入口，再在菜单中放置：

- `举报此卡`

原因：

- 详情模态当前动作较多，直接裸露主按钮会打断已有层级。
- “更多” 入口更适合未来扩展其他次级动作。

### 10.2 举报模态

点击 `举报此卡` 后，在当前页面内弹出二级举报模态，不新开标签页。

字段：

- 理由单选
- 补充说明文本框
- 引用公开数据卡
- 引用百科条目
- 提交按钮

若当前用户对该案件已有活跃举报，则模态应回填现有内容，语义变为“编辑我的举报”。

### 10.3 引用交互

首版避免复杂证据工作台，采用轻量交互：

- 公开数据卡引用：粘贴公开卡链接或卡 ID，服务端校验后回显标题
- 百科条目引用：基于现有 `encyclopediaEntries` 做本地搜索选择

## 11. API 设计

首版建议只暴露用户侧最小闭环 API。

### 11.1 `GET /api/data-card-reports?dataCardId=...`

返回：

- 当前用户是否可举报
- 当前卡是否已有开放案件
- 当前用户是否已有活跃举报
- 当前用户已有举报内容
- 可选举报理由配置
- 是否存在“通知后目标卡已更新”标记

### 11.2 `POST /api/data-card-reports`

语义：

- 创建或更新“我对这张公开数据卡的举报”

服务端行为：

- 鉴权
- 校验目标卡、理由、说明、引用
- 基础风控
- 创建或复用案件
- 创建或更新当前用户举报
- 重建引用
- 更新案件聚合字段
- 必要时发送创作者通知

### 11.3 `POST /api/data-card-reports/withdraw`

语义：

- 举报人撤回自己的活跃举报

首版前端可延后暴露该入口，但后端建议预留。

### 12.1 模板

- 不泄露举报人身份
- 能引导创作者进入目标数据卡自查

## 13. `feat/admin` 分支边界

本分支负责：

- schema / migration
- repository / service
- 用户侧 API
- 举报入口与举报模态
- 创作者通知模板与消息写入

`feat/admin` 后续应负责：

- 案件列表页
- 单案件详情页
- 举报人实名信息展示
- 举报时快照与当前版本对比
- 自整改标记展示
- 结案与处罚动作
- 申诉与仲裁能力扩展

建议后台读取视图至少包含：

- 案件摘要
- 有效举报数
- 举报明细列表
- 举报时目标卡快照
- 当前目标卡版本
- 是否通知后已更新
- 推荐结案口径

## 14. 测试与验收标准

### 14.1 Repository / Service

- 同一卡多用户举报聚合为同一开放案件
- 同用户再次提交时更新原举报而不是创建并行活跃举报
- 引用校验与重建正确
- `accepted` / `suppressed` 只按有效举报计入口径
- 仅首次有效案件通知创作者
- 创作者通知后卡更新能正确标记

### 14.2 API

- 未登录拒绝
- 自举报拒绝
- 非公开卡拒绝
- 理由或引用非法时拒绝
- 频率限制生效
- 已有举报时返回更新成功而不是重复创建

### 14.3 前端

- 详情模态渲染“更多 -> 举报此卡”
- 举报模态可选择理由、填写说明、添加引用
- 已有举报时可回填编辑
- 不可举报时正确隐藏或禁用

### 14.4 消息

- 新模板能正确渲染理由、引用摘要和说明摘录
- 不泄露举报人身份

## 15. 风险与后续

风险：

- 创作者通知过于频繁会造成打扰，因此必须坚持“基础风控后再通知”与“案件级只通知一次”。
- 若理由配置与百科条目选择器缺少统一源，后续会出现前后端不一致。
- 若不保存举报时快照，创作者自整改后后台将难以复原原始问题。

后续可扩展方向：

- 申诉能力
- 用户仲裁资格与案件分流
