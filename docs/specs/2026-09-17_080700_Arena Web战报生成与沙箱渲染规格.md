## 1. 背景与目标

当前 Arena 战报已经通过 Markdown、GFM、KaTeX、表格、图片、音视频等能力提供较丰富的内容呈现，但 Markdown 的表达能力仍不足以覆盖更复杂的视觉与交互需求。

用户希望 AI 可以直接创作具有下列能力的战报：

* 自定义 HTML 与 CSS；
* 更自由的排版、色彩与视觉组件；
* inline / external SVG；
* CSS / SVG 动画；
* Canvas；
* JavaScript 交互；
* 选项卡、折叠区域、悬浮提示、时间线、关系图、战况面板等 Web UI；
* 必要时加载第三方 JavaScript、CSS、字体、图片、音视频或其他 Web 资源。

本功能的目标不是“先生成普通战报，再给战报套一个网页皮肤”，而是：

> **允许 AI 从一开始就以 Web/HTML 作为战报的第一等生成介质。**

Markdown 和 Web 应作为两种并列的战报内容格式。

---

## 2. 核心设计裁决

Arena 将“生成传输方式”与“战报内容格式”拆成两个独立维度：

```ts
type GenerationMode = 'stream' | 'non-stream';

type ArenaReportFormat =
  | 'markdown'
  | 'web';
```

用户界面分别展示：

```text
生成方式
[ 非流式 ] [ 流式 ]

战报格式
[ Markdown ] [ Web（实验性） ]
```

`reportFormat` 默认 MUST 为 `markdown`，因此现有用户、旧草稿、旧房间与旧战报行为保持不变。

### 2.1 单人 Arena

首版支持完整组合：

| Generation mode | Markdown               | Web                   |
| --------------- | ---------------------- | --------------------- |
| Stream          | 现有 `stream-markdown`   | 新增 Web document 流式输出  |
| Non-stream      | 现有 `structured-report` | 新增 Web document 非流式输出 |

Web 的 stream / non-stream 使用相同的 Web 文档语义，区别仅在传输方式：

* stream：模型 token 按现有流式机制持续传输；
* non-stream：完整模型输出一次性返回。

### 2.2 Arena 多人房间

多人房间保持当前**服务器权威流式生成**机制，不为本功能额外引入多人 non-stream producer。

房间 Shared Config 新增：

```ts
reportFormat: 'markdown' | 'web';
```

因此房主决定：

> 这个房间下一场生成 Markdown 战报还是 Web 战报。

但每一名房间成员独立决定：

> 是否在自己的浏览器中执行和渲染这份 AI Web 内容。

该本地执行决定 MUST NOT 写入 Room Shared Config、WebSocket 状态、Redis、D1 或其他服务器状态。

---

# 3. V1 范围与 YAGNI 边界

V1 Web 战报采用：

> **一个 AI response = 一个完整 HTML5 document。**

它可以包含或引用标准浏览器能够直接处理的资源，包括：

* HTML；
* CSS；
* SVG；
* Canvas；
* JavaScript；
* browser-native ES Module；
* CSS / SVG / JS 动画；
* HTTPS JavaScript / CSS CDN；
* Web Fonts；
* 图片；
* 音频；
* 视频；
* 浏览器允许的其他普通 Web 资源；
* `fetch()` 等普通 Web API，但实际能否访问由浏览器 CORS、sandbox 等机制决定。

应用不提供：

* npm 安装；
* Node.js runtime；
* bundler；
* Vite / Webpack；
* TypeScript build pipeline；
* 多文件虚拟项目；
* WebContainer；
* React/Vue/Svelte 专用运行环境。

如果 AI 自己通过普通浏览器能力加载某个 runtime compiler 或第三方框架，属于生成页面自身的行为，应用不需要专门支持或保证其可用。

核心原则是：

> Web V1 支持“标准浏览器可以直接运行的一个 HTML 文档”，而不是建设浏览器 IDE。

# 4. Web 输出契约

## 4.1 Web document

模型 MUST 直接输出 HTML，不得用 Markdown fenced code block 包裹，不得在 HTML 前后附加解释性文本。

期望形式：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>战报标题</title>
  <style>
    ...
  </style>
</head>
<body>
  ...
  <script>
    ...
  </script>
</body>
</html>

<!-- MAHOSHOJO_ARENA_META {...} -->
```

HTML DOM 的结构、class、id、样式、交互实现均由 AI 自由决定。

应用 MUST NOT：

* 根据某个固定 DOM selector 提取胜利者；
* 根据 `<h1>` / `<div>` / `<script>` 等任意 HTML 结构推测游戏状态；
* 将页面运行后的 DOM 作为权威 Arena 数据来源。

---

## 4.2 机器元数据继续使用 `MAHOSHOJO_ARENA_META`

Web 战报 MUST 在输出最后追加现有 Arena 机器元数据 marker：

```html
<!-- MAHOSHOJO_ARENA_META {
  "version": 1,
  "report": {
    "headline": "……",
    "winner": "……"
  },
  "impacts": [...]
} -->
```

原则上继续复用现有 Arena Stream Meta payload，而不是为 Web 发明第二套角色更新协议。

Web 模式下：

* `MAHOSHOJO_ARENA_META` MUST 始终要求输出；
* 是否写 Arena History / Current State 继续决定 `impacts` 等字段是否需要；
* Web 本身负责向用户展示完整故事、胜负与结果；
* Meta 负责向应用提供机器可读事实。

Server projector / parser MUST 在生成完成时把 Meta 从用户内容中分离。

发送到 Web iframe 的 HTML MUST NOT 包含系统使用的 Meta comment。

现有 metadata parse / repair / diagnostics 语义继续适用；本功能 MUST NOT 为了修复 malformed meta 自动重新调用一次模型，也 MUST NOT 增加“解析 DOM 猜胜者”的 fallback。

# 5. Prompt 设计

现有 Arena 世界观、角色、情景、随机裁定、引导和故事规则继续作为共享 Prompt。

仅将当前固定的 Markdown output requirement 抽成 presentation/output contract，例如：

```ts
buildArenaOutputInstructions({
  reportFormat,
  deliveryMode,
  metaRequirements,
});
```

Markdown 使用现有 Prompt。

Web 模式追加独立要求。

## 5.1 Web Prompt 应告诉模型

模型正在制作一份可以直接在现代浏览器中运行的完整 HTML5 战报。

允许自由使用 HTML、CSS、SVG、Canvas、JavaScript 和外部 Web 资源。

模型 SHOULD：

* 优先制作适合桌面与移动端阅读的响应式布局；
* 根据实际故事设计视觉与交互，而不是机械套固定模板；
* 可以使用动画、时间线、状态面板、互动按钮、Tab、折叠内容、图表等；
* 优先使用内联 `<style>` / `<script>` 与 `addEventListener`，避免依赖被主站 CSP 阻止的外部库、字体和内联事件属性；
* 可访问的外部资源优先使用完整 HTTPS URL；
* 对 CDN / API 加载失败保持基本可读性；
* 不依赖宿主页面 React 组件、变量或函数；
* 不假设能够访问宿主页面 cookie、localStorage 或 DOM；
* 在最终 HTML 后按要求输出 `MAHOSHOJO_ARENA_META`。

Prompt SHOULD 提醒模型：

`iframe srcdoc` 中的相对 URL 可能基于宿主页面 URL 解析，因此外部资源建议使用绝对 URL。

## 5.2 故事事实与表现分离

Web 格式只改变**表现方式**，不得改变既有 Arena 游戏规则。

随机裁定结果、角色资料、房间共享配置、引导信息等对故事事实的约束，与 Markdown 模式保持一致。

AI 可以使用页面互动来：

* 展开内容；
* 切换视角；
* 浏览人物状态；
* 播放动画；
* 控制图表；
* 显示附加叙事信息。

但这些互动不得成为服务器权威状态输入。

例如页面中的一个按钮显示“让角色 B 获胜”，不会改变 Arena 系统记录的实际 winner。

# 6. Stream Web 行为

Web Stream 的 Provider 输出从第一个 token 开始就是 HTML。

但是 V1 MUST NOT 尝试边接收 token 边运行不断变化的 HTML document。

流式阶段：

```text
Provider
   ↓
HTML token stream
   ↓
现有 stream/replay/reconnect 管线
   ↓
普通战报卡内容区域
```

流式过程中直接把当前累计 Web source 交给现有 Markdown fallback renderer。

不增加：

* incremental DOM parser；
* `document.write()`；
* iframe 不断 reload；
* live DOM patch protocol；
* Web-specific token parser。

生成完成并取得 authoritative final content 后，才允许 mount Web iframe。

这样仍属于真正的 Web generation：

> AI 从开始到结束生成的都是 HTML，只是完整文档完成之前暂不执行它。

Room replay / reconnect 同样只恢复同一份 Web source bytes，不重新调用模型。

---

# 7. 普通显示 / Markdown fallback

用户没有同意 Web 执行时，不新增一套 Web source renderer。

直接复用当前 Battle Report Markdown presentation：

```text
raw Web source
       ↓
现有 ReactMarkdown
       ↓
现有战报卡
```

现有 GFM、KaTeX、表格、图片、音视频等插件保持原样。

V1 MUST NOT 为此加入 `rehype-raw` 或其他新的 raw HTML executor。

因此：

* ReactMarkdown 当前能够正常处理的内容继续正常处理；
* 原始 HTML 的行为继续遵循现有 ReactMarkdown 行为；
* 不承诺 fallback 后仍然具有良好的 Web 页面排版；
* fallback 的主要目标是“内容仍然可查看”，而不是复制完整 Web 体验。

这一设计避免维护：

* HTML → Markdown 转换；
* Web AST sanitizer；
* 第二套源码 viewer；
* Web fallback allowlist。

# 8. Web Viewer 与安全边界

Web 内容视为 AI 生成的不可信页面，但 V1 不试图证明 Web 页面自身安全。

安全目标仅为：

> **把可能不安全或有错误的 Web 页面与魔法少女生成器主应用隔离。**

渲染使用独立 iframe：

```html
<iframe
  sandbox="allow-scripts"
  referrerpolicy="no-referrer"
/>
```

通过 `srcdoc` 写入最终 HTML。

V1 MUST NOT 添加：

```text
allow-same-origin
allow-forms
allow-popups
allow-top-navigation
allow-downloads
allow-modals
allow-pointer-lock
allow-presentation
```

除非未来有独立需求与设计。

特别是 MUST NOT 同时启用：

```text
allow-scripts + allow-same-origin
```

V1 不增加额外 CSP allowlist，也不放宽现有主站 CSP。

**2026-09-17 实施裁决：** `srcdoc` 会继承主站的 CSP。现有策略允许内联 `<script>` / `<style>`，但限制第三方 JavaScript、CSS、字体及内联事件属性（如 `onclick`）；不能把「标准浏览器资源」解释成绕过现有策略的保证。V1 保留这一边界，不新增独立响应入口。Prompt 必须优先使用自包含 CSS/JavaScript，并以 `addEventListener` 绑定交互；外部图片、音视频和 API 仍受现有 CSP、CORS 等规则约束。

因此 AI Web 可以尝试访问外部：

* JavaScript；
* CSS；
* fonts；
* images；
* media；
* APIs。

实际请求仍受继承的主站 CSP、浏览器 sandbox、Same-Origin Policy、CORS、第三方服务配置等标准 Web 规则影响。

浏览器规则核验（2026-09-17）：[MDN iframe / srcdoc 与 sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)。本地 Chromium smoke 已验证内联脚本绑定的按钮交互可运行，同时父页面 DOM 与 localStorage 访问被拒绝。

V1 明确认可下列剩余风险：

* 页面 JavaScript 死循环；
* 浏览器 tab 卡顿；
* 高 CPU / 内存占用；
* 极端 DOM 数量；
* 动画影响性能；
* 页面内部显示误导性 UI；
* 第三方资源未来变化或失效；
* 第三方服务收到网络请求及其能够观察到的相关信息；
* 外部 API 因 CORS 等原因无法使用。

这些均不作为首版阻塞条件。

用户可通过关闭/刷新页面恢复。

---

# 9. 不建立 Host Bridge

V1 不建立 iframe → React host 的业务通信协议。

因此暂不提供：

* iframe 自动报告高度；
* Web 页面直接触发 Arena 操作；
* Web 页面修改角色；
* Web 页面写入房间配置；
* Web 页面调用宿主下载；
* Web 页面请求新的 AI generation；
* Web 页面向宿主发送任意 command。

iframe 使用固定/响应式容器并允许内部滚动。

如果未来确实需要交互宿主，再独立设计严格 typed `postMessage` bridge。

# 10. 用户确认与 UX

## 10.1 单人

用户首次在当前浏览器选择：

```text
战报格式
[ Markdown ] [ Web（实验性） ]
```

时弹出确认。

建议说明：

> Web 战报会运行 AI 生成的 HTML、CSS 和 JavaScript，并可能加载第三方脚本、样式、图片或其他网络资源。生成页面可能出现显示异常、页面卡顿、外部资源失效，第三方资源也可能接收到相关网络请求或页面发送的信息。请仅在了解这些风险后启用。

操作：

```text
[取消]
[继续使用 Web]

☐ 此浏览器不再提示
```

取消时保持 `reportFormat = markdown`。

确认可以在浏览器本地记录：

```text
arena.web-report-consent.v1
```

不得同步服务器。

---

## 10.2 多人房间

`reportFormat` 是 Room Shared Config，由房间权威配置决定。

每名成员第一次在某一房间需要执行 Web 内容时独立确认。

建议本地 key：

```text
arena.web-report-consent.v1.room.<roomId>
```

即使用户曾在单人 Arena 中勾选“不再提示”，多人房间仍按房间首次确认。

普通成员拒绝时：

* 不改变 Room Shared Config；
* 不影响其他成员；
* 不请求重新生成；
* 不影响房间权威结果；
* 当前成员使用现有普通战报卡显示同一份 raw Web source。

战报界面保留：

```text
[普通显示] [Web 显示]
```

未同意用户之后点击“Web 显示”时可以再次弹出确认。

# 11. Room Shared Config 与兼容

当前 `ArenaRoomSharedConfig` 是 strict schema，因此新字段必须明确处理旧 Room / fixture / replay 兼容。

新增：

```ts
reportFormat: 'markdown' | 'web';
```

解析旧数据时：

```text
missing reportFormat
        ↓
normalize to "markdown"
```

新客户端创建或发布 Shared Config 时 SHOULD 始终显式写出 `reportFormat`。

因此：

* 旧 Room 默认为 Markdown；
* 旧 generation snapshot 语义不变；
* 旧 fixture 不要求批量手工迁移；
* `reportFormat` 进入 config revision / snapshot digest；为兼容旧 Markdown generation 的重试，digest 规范化将缺失字段与显式 `markdown` 视为同一语义，仅 `web` 保留在 canonical digest 输入中；
* generation 开始后使用被冻结 snapshot 的 format；
* 生成过程中本地切换 format 不改变已经开始的请求。

`reportFormat` 是 Room semantic，应像其他共享标量配置一样参与现有 diff / proposal / host reconciliation 体系；不得作为 request-scoped host-local override 绕过 Room authority。

# 12. Multiplayer wire / result contract

当前多人结果使用：

```ts
format: 'stream-markdown'
```

Web V1 扩展为：

```ts
format:
  | 'stream-markdown'
  | 'stream-web';
```

Room authoritative producer 仍只有 streaming producer。

现有 HTTP / replay contract 中的 `markdown` 字段属于历史命名。

为避免仅为字段重命名就升级整套 Room protocol，V1 允许该字段继续承载“模型生成的可见文本内容”：

```text
result.format = stream-markdown
markdown = Markdown

result.format = stream-web
markdown = raw HTML source
```

所有新代码 MUST 先判断 `result.format` 再解释该字符串。

实现内部 SHOULD 使用 `content` / `generatedContent` 等中性变量名，不继续扩散 `markdown` 语义。

字段本身的正式 wire rename 留到未来 Room protocol version bump 一并处理。

---

# 13. Single-player response contract

现有 Markdown 行为保持完全不变。

Web 模式新增统一 Web document output contract。

逻辑关系为：

```text
reportFormat=markdown + stream
→ stream-markdown

reportFormat=markdown + non-stream
→ structured-report

reportFormat=web + stream
→ web-document, SSE transport

reportFormat=web + non-stream
→ web-document, ordinary response transport
```

Web non-stream 不强制模型把完整 HTML encode 成 structured JSON string。

模型仍直接输出：

```text
HTML document
+
MAHOSHOJO_ARENA_META
```

服务器负责：

* 提取 meta；
* 保存 raw Web content；
* 构造现有客户端需要的可信 generation metadata；
* 返回 Web content。

这样避免 HTML 中大量引号、换行、script 内容经过 JSON-string generation contract。

---

# 14. Persistence 与历史记录

持久化层 MUST 保存报告格式，使 replay 能确定该内容应该解释成 Markdown 还是 Web。

优先复用现有 generation metadata / extra JSON / render snapshot，不为单一 enum 字段新增 D1 migration，除非实现阶段证明现有持久化无法表达。

Web raw source 与 Markdown content 继续受现有 Arena generation output byte budget 保护。

V1 不另外引入 Web 专属极小尺寸限制。

对于 R2 / object storage：

* Web source 是持久化数据；
* 浏览器执行发生在应用 iframe 中；
* R2 object 本身不应成为“绕过 sandbox 直接访问 Web 页”的产品入口。

如果现有存储 API 支持选择 MIME，Web raw source SHOULD 以非主动执行语义保存，例如 `text/plain; charset=utf-8`；渲染时应用再显式把字符串传给 iframe `srcdoc`。

# 15. Safety / sensitive-content pipeline

现有输入、输出 safety / shield word / redirect 流程继续适用。

但是 Web source 不应经过会破坏 JavaScript/CSS/HTML 语法的逐文本替换后再执行。

实现阶段必须明确区分：

```text
safety decision
```

与：

```text
HTML source mutation
```

如果当前 `sanitizeTextByShieldWords()` 等函数会直接改写 Provider Web bytes，则 Web 路径 MUST 避免把经过语法破坏的字符串作为 executable artifact。

Safety 可以：

* 拒绝整个输出；
* 标记输出；
* 阻止展示；

但不得悄悄把 HTML/JS 任意字符串替换后仍假设页面可执行。

# 16. Existing battle-report features

### AI model / usage / reasoning

这些属于宿主 Arena UI metadata，不要求 AI 写进 Web document。

Web viewer 外层仍可以显示：

* model；
* prompt/reasoning/completion tokens；
* AI reasoning panel；
* generation status。

### adjudication results

AI 可以自行把裁定结果设计进 Web 页面。

宿主现有随机判定记录仍可保留，避免把游戏权威数据完全委托给 HTML。

### battle report illustration

Web 自身已经可以使用 `<img>`、SVG 等。

现有 battle-report illustration feature 暂不要求与 Web DOM 深度整合；宿主可以继续在 iframe 外展示现有 illustration，或后续再决定是否把其 URL 注入 Web Prompt。

### 保存图片

现有 DOM screenshot 工具不保证能够捕获 opaque-origin sandbox iframe。

因此 V1 不把“Web 战报保存为 PNG”列为验收条件。

普通显示模式仍保持现有截图能力。

### 导出 HTML

V1 已提供「🌐 下载 HTML」按钮：仅 authoritative final 完整战报可下载，普通显示与 Web 显示均可使用，下载不要求同意在本站执行。

导出保留生成 HTML 的样式和脚本，移除机器 Meta comment，以 UTF-8 单文件保存；不打包外部资源，也不保存页面运行后的交互状态。Web 图片保存暂不提供，用户可使用浏览器截图，或切换普通显示沿用现有截图能力。

如增加“导出 HTML”，必须明确提示：在浏览器直接打开导出的 HTML 时，不再处于应用 iframe sandbox 中。

# 17. Error 与降级

Web 模式属于实验性能力。

以下情况不得破坏 Arena 主页面：

* HTML malformed；
* CSS malformed；
* JS throw；
* external script 404；
* CDN 不可用；
* CORS failure；
* iframe 页面空白；
* 页面内部导航；
* Web runtime error。

宿主只需要始终保留：

```text
普通显示
```

作为降级入口。

V1 不需要检测 iframe 内 JS exception，也不需要自动判断页面“是否正常工作”。

如果用户认为 Web 页面有问题，可以：

* 切换普通显示；
* reload Web view；
* 重新生成整场战报。

本规格不授权下列工作：

1. Markdown 战报完成后再次调用模型生成 Web 版；

3. 原 Web V1 中的多文件 Web Package 解析与 rendering（后续 first-party Phase 1 由独立 Package 规格扩展）；
4. npm / bundler / TypeScript toolchain；
5. WebContainer；
6. 边生成边执行增量 HTML；
7. iframe watchdog / CPU timeout；
8. HTML sanitizer / JS AST validator；
9. CSP URL allowlist；
10. CDN allowlist；
11. 单独 sandbox origin/domain；
12. `allow-same-origin`；
13. iframe → Arena Host Bridge；
14. Web 页面直接修改角色/房间状态；
15. Web 页面直接调用宿主 AI；

17. 旧 PVP Web 化；

19. Web report PNG capture；
20. Web package 分享/市场。

这些能力未来根据实际使用反馈单独评估，不提前建设。

# 19. 实现结构建议

实现阶段优先形成以下窄 seam：

```text
ArenaReportFormat
        │
        ├── markdown
        │     ├── stream-markdown
        │     └── structured-report
        │
        └── web
              └── web-document
                    ├── stream transport
                    └── non-stream transport
```

展示层：

```text
BattleResultPresentation
        │
        ├── Markdown report presentation
        │
        └── Web report presentation
                 │
                 ├── ordinary fallback
                 │      └── existing ReactMarkdown card
                 │
                 └── consented
                        └── SandboxedWebReport iframe
```

尽量不要分别在：

* `BattleReportCard`
* `StreamingBattleReportCard`
* Arena Room result

中复制完整的 consent / iframe 逻辑。

Web viewer 应成为一个共享 presentation component。

# 20. 测试与验收门禁

实现至少需要覆盖：

### Contract

* `reportFormat` 接受 `markdown | web`；
* 缺失旧 Room `reportFormat` 正确归一化为 `markdown`；
* Room snapshot digest 包含 format；
* Room result 接受 `stream-markdown | stream-web`；
* 旧 Markdown fixture / replay 继续通过。

### Prompt

* Markdown Prompt 与当前行为保持回归一致；
* Web Prompt 不要求 Markdown；
* Web Prompt 要求完整 HTML；
* Web Prompt 要求最后 Meta；
* stream / non-stream Web 都使用同一 Web document 语义；
* 四种 Arena mode 均覆盖 Web format。

### Provider / runtime

* Web stream 不走 structured output；
* Web non-stream 不错误进入现有 Battle Report JSON schema；
* stream reconnect / replay 可以恢复 HTML bytes；
* abort / timeout / no-replay 规则与现有 generation 一致；
* Meta extraction 不把 marker 发送到 iframe。

### UI

* Markdown 默认；
* 选择 Web 首次出现风险确认；
* remembered consent 生效；
* Room consent 按 roomId 隔离；
* 拒绝 Room Web 不改变房间状态；
* 普通显示复用现有 Markdown renderer；
* Web render 使用 sandbox iframe；
* sandbox 只包含 `allow-scripts`；
* 不存在 `allow-same-origin`；
* generation 进行中不执行 incomplete HTML；
* final 后才 mount iframe。

### Regression

* 原有 stream Markdown；
* 原有 non-stream structured report；
* Arena History / Current State；
* combatant updates；
* room single-producer；
* room recovery / replay；
* room host reconciliation；
* historical battle reports；
* AI reasoning / usage；
  -现有 Markdown multimedia renderer。

最终要求 workspace 相关 test / lint / typecheck / build 与 `ci:verify` 通过。

# 21. 兼容与迁移策略

V1 默认行为为：

```text
reportFormat = markdown
```

因此功能上线后：

* 旧用户无行为变化；
* 旧本地 draft 无行为变化；
* 旧 Room 无行为变化；
* 旧 replay 无行为变化；
* 旧 generation record 无行为变化；
* 未主动选择 Web 的用户不会执行 AI JavaScript。

如果未来 Web 功能风险边界发生实质变化，例如：

* 新增 `allow-same-origin`；
* 开放宿主 bridge；
* 开放宿主文件系统；
* 开放敏感浏览器权限；

则 MUST 提升 consent version，并要求用户重新确认。

单纯增加可用 CDN、Prompt 调整、样式增强等不需要重置 consent。

# 22. 后续可能增强

以下仅保留方向，不进入 V1：

### Web 再创作

对历史 Markdown / Web 战报进行：

```text
现有战报
   ↓
重新生成 Web 版
```

不重新判定战斗，不修改 Arena 状态。

### Live Web

设计真正增量可运行的 Web protocol，而不是完整 document 重载。

### Web Experience Package

2026-09-22 的独立 Package 规格已将此方向明确为“不可变 Base Package + AI 单文件 Overlay”。Package 承载 Runtime、样式、依赖、媒体、schema 与 AI instructions，AI 仍只生成 manifest 中唯一 `generation.target`。`entry` 与 target 可以相同或不同；Phase 1 仅提供内置 Package，任意用户导入和 AI 多文件生成继续延后。

### Host interaction

如果未来需要 Web 战报触发游戏交互，再设计最小 typed `postMessage` bridge。

上述能力均以实际用户需求为前提。
