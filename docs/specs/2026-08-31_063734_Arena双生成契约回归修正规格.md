# Arena 双生成契约回归修正规格

状态：accepted / implemented  
日期：2026-08-31  
实现提交：`b9a8aed2`  
适用范围：Arena 单人、session 与多人权威生成所复用的 shared generation producer，以及
`/api/arena/generate`、`/api/generate-battle-story` companion response

## 1. 背景与裁决

平台重整后的 G25H-1 整改把流式与非流式战报误合并为单一 Markdown 内容契约。为了让 non-stream
companion 能填充 `report.article.analysis`，共享流式 Prompt 被加入必需的“记者点评”，同时两个
non-stream route 从 schema 驱动的 structured generation 变为 Markdown 生成后按固定标题解析。

这不是重整前的产品契约。重整前两类生成有意不同：

- 流式战报面向阅读过程，输出自由、纯粹的 Markdown；
- 非流式战报面向稳定 JSON consumer，输出带 `headline`、`article`、`officialReport` 与条件性
  `impacts` 的结构化报告。

因此，本规格取代
[G25H-1 审查整改设计](./2026-08-26_112538_G25H-1审查整改设计.md)中“单一可见内容契约”、
“流式必需记者点评”与“不恢复 structured Provider pipeline”的要求。该旧文档的 PVP 可审计拒绝和
legacy stats 退休裁决不受影响。

## 2. 规范性输出契约

### 2.1 Stream Markdown

用户可见的 stream producer，包括 `/api/arena/generate-stream`、session next 与多人权威生成复用的
producer，MUST 使用 `stream-markdown` 契约：

- Prompt MUST NOT 要求 `记者点评` 或 `article.analysis`；
- 可见结果保持标题、自由正文、胜利者和最终结果的 Markdown 结构；
- 为历战记录或当前状态追加的 `MAHOSHOJO_ARENA_META` 是隐藏的系统元数据，不得变成可见文章模板；
- 网络可恢复、typed replay、reasoning event、取消和 single-producer 机制继续有效，不因恢复内容契约
  而退回不可恢复的直接传流。

### 2.2 Non-stream structured report

只有服务器写入且同时满足以下条件的 route context 才能选择 `structured-report`：

- `deliveryMode=non-stream`；
- endpoint 为 `api/arena/generate` 或 `api/generate-battle-story`。

客户端 body 自报的 context MUST 被服务器覆盖，不能借此切换 Provider 调用形态。两个 route MUST 使用
structured runtime、Battle Report schema 和本地终态校验，结果至少包含：

- `headline`；
- `article.body` 与 `article.analysis`；
- `officialReport.winner` 与 `officialReport.conclusion`；
- 在写入历战记录或当前状态时，按开关要求输出对应字段的 `impacts`。

缺少必需字段、类型不符或 malformed structured snapshot MUST fail closed，不能再按本地化 Markdown
标题正则静默投影为空字段并返回 200。旧持久 Markdown replay 仍可走兼容 parser；当前 structured
producer 通过受信 `outputContract` metadata 与旧记录区分。

### 2.3 Legacy 输入与响应兼容

- non-stream `userGuidance` 在 safety、Prompt、响应和历史投影前保持 200 字上限；stream 不套用该上限；
- `characterGuidance` 进入 Prompt、safety metadata 与历史投影时保持 100 字上限；
- structured runtime 的 `model`、`usage` 与 reasoning envelope 继续投影到 `aiModel`、`aiUsage` 与
  `aiReasoning`；
- R2/D1 snapshot、terminal index、local reconciliation 与 companion response 必须从 structured JSON
  读取 headline、winner 与 impacts，不依赖 Markdown heading；对象内容类型标记为
  `application/json; charset=utf-8`。

## 3. 不支持 structured output 模型的兼容策略

non-stream structured contract MUST 保留重整前的兼容降级：

1. 对已知不支持 JSON mode 的模型族，可预判直达“文本 JSON + 本地 repair + schema 校验”，避免一次必败
   的 structured 请求；
2. 对未预判、但上游明确以 `response_format`、`json_schema`、JSON mode 或 structured output
   capability rejection 拒绝的请求，可在同一 Provider、同一 model 上降级一次文本 JSON；
3. capability rejection 必须来自原错误或经过安全提取的上游错误，不得把普通网络错误、5xx、限流、鉴权
   或 schema 内容不合格解释为“不支持”；
4. 请求已 dispatch 后的普通错误、可能已产生内容的解析失败和跨 Provider failover 继续遵守 no-replay
   边界，MUST NOT 为提高成功率而盲目二次计费；abort 后也不得重放。

上述第 2 条是 no-replay 的窄例外：明确能力拒绝表示 structured 调用未开始生成内容，恢复文本 JSON
调用不会重放一份不确定的生成结果。

## 4. 保留的有意平台变化

本次修复不回滚下列平台重整成果，但它们必须作为用户可感知差异登记，不能继续笼统宣称全量等价：

- client preflight 和 Hosted fail-closed routing 会在 Provider 前增加 readiness 依赖与一个网络往返；
- Redis rate limit、single-producer reservation、replay 持久化与批量 flush 扩大了 Provider 之外的运行链路；
- `done` 前的 R2/D1 durable finalization 是权威终态门禁；存储失败可能让已经生成正文的请求最终失败；
- request body、角色、裁定事件、问卷和叙事历史存在服务器资源上限；materials 与 aux scenarios 的上限在
  重整前已经存在，不应误列为本轮新增；
- `isNative` 由服务器验签重算，不再信任客户端声明；
- 空输出 fail closed、Provider redirect 拒绝和默认 300 秒 idle / 600 秒 total stream timeout 保持现状；
- `NEXT_PUBLIC_ENABLE_AI_SAFETY_CHECK=true` 时会增加一次生成前 AI safety call；默认关闭，但启用环境需
  独立观测其延迟与拒绝率。

这些变化有可靠性、安全或资源治理依据，但正常路径的延迟主因不能只凭静态代码归因。观测 SHOULD 区分
client preflight、Provider TTFB/total、Redis replay flush 与 R2/D1 finalization，避免把平台终态失败误报为
模型失败。每请求渲染后的 Prompt 不应作为高基数或含敏感指纹的 telemetry；需要版本识别时使用低基数
`outputContract` / contract ID 与构建期模板 hash。

## 5. 验收与回归证据

实现至少满足以下证据：

- stream Prompt 负向断言不含记者点评，四种 Arena mode 与 legacy builder 保持 parity；
- trusted non-stream route 的完整 Prompt、schema、model override 与 structured runtime boundary 有测试；
- structured JSON 正文可自由包含类似 Markdown heading 的文本而不被 parser 截断；
- malformed current structured snapshot fail closed；
- known text-only model、已 dispatch 的明确 capability rejection 和普通已 dispatch 5xx 分别覆盖直达、
  兼容回退和禁止重放；
- structured reasoning/usage/model、R2 content type、D1 terminal 与 impacts reconciliation 有测试；
- hosted-runtime test/lint/build、Web 全量测试、workspace boundary 与最终 `ci:verify` 通过。

机器可读证据入口为 `config/user-visible-contracts.json`。本规格未授权或执行 production deploy、数据迁移、
切流、secret 变更、release 或远程生产写操作。

## 6. 仍需运行态核实的事项

- 生产/Preview 分段 telemetry 是否证实 client preflight、Redis replay 或 durable finalization 是尾延迟主因；
- 18 条 shared generation route 的完整 Provider-boundary differential 仍未全部自动化；
- 资源上限是否需要按 system channel 与 BYOK 分层，必须结合本方内存、Redis/D1/R2 与 safety 成本另行决策，
  不能仅因 BYOK 不消耗系统模型额度就无条件放开。
