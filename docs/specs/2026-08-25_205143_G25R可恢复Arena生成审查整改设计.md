# G25R 可恢复 Arena 生成审查整改设计

状态：`accepted`
日期：2026-08-25
设计标识：`DESIGN-G25R-review-remediation-v1`
依据规格：`SPEC-hosted-resumable-generation-stream-v1`
依据 ADR：`ADR-hosted-runtime-resilience-cloudflare-dr`
审查基线：`f100413ebdd74cf576c2379a15aa854f7aa86088`

## 1. 背景与结论

G25R 已建立 server-owned generation、Redis reservation/replay、D1/R2 terminal fallback 与 Web resume，
但复审确认了四个必须在 production cutover 前闭合的问题：

1. post-claim finalization 耗尽重试后会把真实 Provider terminal 改写成 `failed`，并提前设置
   `finalizationCompleted=true`；
2. Web 在 initial generation POST 结果未知时会自动重放同一个 POST，无法保证仍由原 runtime 处理；
3. 客户端命中敏感输出后只取消 subscriber reader，没有显式取消 server-owned producer；
4. reused create 会重新生成 adjudication 与 reporter metadata，可能与实际 Provider prompt 不一致。

四项问题均不改变现有 “Hono primary + Next/OpenNext DR、Redis transient lifecycle、D1/R2 durable terminal”
方向。本设计只修复 lifecycle、recovery、cancel 与 generation metadata 边界，不引入新的业务事实存储，
也不恢复 legacy Next handler。

## 2. 目标与非目标

目标：

- durable finalization 失败时保留真实 Provider terminal，并允许 expired-lease reaper 收口；
- initial POST 状态未知时围绕稳定 `generationRequestId` 查询并恢复，不透明重放 create；
- 明确区分 subscriber disconnect、用户 Stop 与 content-policy cancel；
- 同一 generation 的随机裁定、记者信息和 Provider prompt 使用同一份服务器冻结随机性；
- 通过 fault injection 证明无第二 Provider、无伪终态、无错误 metadata 与无重复副作用。

非目标：

- 不改变 Hono/Next active-passive placement 或生产入口；
- 不新增 D1 lifecycle/job 表、Durable Object、Queue 或 Workflow；
- 不持久化完整 prompt、BYOK secret、Provider header、私有卡或完整 generation input；
- 不改变 rating、R2 key、local-card reconciliation 或 Room runtime；
- 不在本次整改中建立完整 server-owned output safety gate；该能力应单独设计流中截断、误伤、持久化、
  telemetry 与资源预算；
- 不重新裁决首次 terminal claim 前 R2 连续失败时的产品终态。

## 3. 必须保持的不变量

1. 同一 `(actor, generationRequestId, semanticPayloadHash)` 同时最多有一个 Provider producer。
2. subscriber disconnect 只结束当前订阅，不取消 producer。
3. 用户 Stop 与 content-policy 命中是显式、幂等的 generation cancel。
4. Provider terminal 与 durable finalization 状态正交；finalization 失败不能伪造新的 logical terminal。
5. initial POST 一旦可能到达 runtime，不得因 ambiguous failure 自动再次 POST。
6. 随机 metadata 不进入 semantic hash，但必须绑定到 generation 并在其生命周期内稳定。
7. Redis 只保存有界、非敏感 transient state；D1/R2 继续持有 durable terminal/output。
8. Next/OpenNext 没有共享 active Redis capability 时继续在 Provider 前 fail closed。

## 4. Durable finalization

R2 已成功、D1 terminal claim 已保存真实 terminal，但 combatant/history/rating/complete 等 post-claim 步骤
在 bounded retry 后仍失败时，状态必须保持为：

```text
D1:    generationTerminalStatus = 原 Provider terminal
       finalizationCompleted = false
Redis: status = finalizing, terminal = null, lease = producer lease
```

finalizer 抛出原始错误，runtime 表现为 `ArenaGenerationFinalizationPendingError`。service 不调用
`replayWriter.finish(failed)`，也不把 Redis 标记为 terminal。lease 到期后，只有取得 expired-lease CAS 的 reaper
可以运行既有 reconciliation；全部幂等副作用成功后才设置 `finalizationCompleted=true`，并保留原 terminal。

实现只删除 post-claim retry exhausted 路径对 `failTerminal()` 的调用，不修改 Redis claim/heartbeat/fencing、
reaper CAS 或 `readOwnedTerminal(requireFinalized=true)`。`failTerminal()` 在首次 claim 前的 R2 failure 兼容路径暂时保留。

## 5. Initial POST unknown recovery

新增 shared、actor-authenticated endpoint：

```http
GET /api/arena/generation-requests/{generationRequestId}
```

服务端使用 create/cancel 相同的 actor resolver，由 `(actorKey, generationRequestId)` 派生 `generationId`，
再复用 owned-state、D1 pending 与 D1/R2 terminal fallback。最小成功响应为：

```json
{
  "generationRequestId": "request-id",
  "generationId": "arena_...",
  "status": "running",
  "resumable": true,
  "lastEventId": "123-0",
  "updatedAt": "2026-08-25T12:00:00.000Z"
}
```

响应语义：Redis active 或 finalized terminal 返回 `200`；D1 pending 返回
`503 GENERATION_FINALIZATION_PENDING`；actor 不匹配或无法证明 ownership 返回统一
`404 GENERATION_REQUEST_NOT_FOUND`；Redis/D1 均不能证明状态返回 `503 GENERATION_STATE_UNAVAILABLE`；
格式错误返回 `400 GENERATION_REQUEST_ID_INVALID`。Hono 与 Next/OpenNext adapter 调用同一 hosted service，
无需 D1 migration。

create POST 只发送一次。network exception、incomplete `200`、`502/504` 与无明确 pre-execution contract 的
`429/503` 都进入 `recovering_initial`：保留 request ID/body-scoped state/actor token，以有界 backoff 调用 lookup；
找到 generation 后只 GET resume；预算耗尽进入 `unknown` 并明确提示，不再 POST。刷新或再次打开同一 intent 继续
lookup，不把 `generationId=null` 当作 create 许可。

明确的 pre-execution 业务错误直接返回调用方并遵守 `Retry-After`，本次不自动重试 create。旧 server 不支持 lookup
时也不得回退为 blind POST。`unknown` 不静默生成新 request ID；未来若增加“放弃未知任务并建立新 intent”的 UI，
必须显式告知旧任务可能仍在运行，该 UI 不属于本次整改。

## 6. Cancel reason 分层

新增固定 cancel reason：`user | content_policy`。

| 事件 | subscriber | producer | terminal |
| --- | --- | --- | --- |
| 网络断线、reader 普通 cancel | 结束 | 继续 | 不变 |
| 用户 Stop | 结束 | 显式 cancel | `cancelled / USER_CANCELLED` |
| 客户端 content-policy 命中 | 结束 | 显式 cancel | `cancelled / CONTENT_POLICY_CANCELLED` |

generation-ID 与 request-ID cancel 接受可选 allowlisted reason；缺省及旧客户端回退 `user`，其他值返回 `400`。
Redis active state 增加可选 `cancelReason`，request-cancel mutation、heartbeat 与 finalization claim 传播该值，旧 entry
缺失时回退 `user`。observer 只记录固定低基数 reason，不记录命中文本。

Web 保留现有本地截断、逮捕令与备份，但命中时改为 abort generation controller，reason 为 `content_policy`，
不得只取消 reader。这恢复受信客户端的主动阻断语义，但不把客户端检测提升为服务器权威；完整 server-owned
output gate 继续作为独立后续事项。

## 7. Generation-scoped 随机 metadata

preparation 拆为：

1. deterministic preflight：authority normalization、schema、资源上限、input safety、semantic payload；
2. reservation：原子比较 semantic hash，并冻结服务器 CSPRNG 生成的 `preparationSeed`；
3. materialization：用 reservation 返回 seed 计算 adjudication、reporter metadata 与 Provider prompt；
4. execution：只有 `reservation.kind=created` 的 owner 可以启动 Provider。

seed 由服务端生成，客户端不可选择；seed 不进入 semantic hash，也不返回客户端。adjudication resolver、reporter
selector 与其他影响公开 execution metadata 的随机选择使用同一可注入 seeded random source，不再直接调用全局
`Math.random()`。

`created` 原子保存 candidate seed并启动一次 Provider；`reused` 返回首次 seed，重建相同 response metadata 但不启动
Provider；`conflict` 保持 `409`。reservation 成功但 materialization 在 Provider 前失败时，只在仍持有 reserved token
时释放；释放结果未知则 fail closed。旧 Redis entry 没有 seed 时允许 resume，但 omit 随机 presentation metadata，
不得 reroll。

为覆盖 Hono/DR 滚动部署期间的短暂版本偏差，seeded reservation 的 payload hash 使用固定协议域与旧 hash 隔离：
旧实例读取新 reservation 时只能得到 conflict，不能把 reservation 前重新生成的 metadata 当作 reused 响应返回；
新实例遇到旧 hash conflict 时，仅在 actor-owned state 同时证明 legacy hash 相同且 seed/version 均缺失后，将其识别为
seedless reused 并省略 metadata。客户端已采用 create-once + request lookup，因此版本偏差下通过 lookup/resume 恢复，
不得用旧 create 路径绕过该 fail-closed 边界。durable terminal 的 legacy hash 也只作为同一 semantic payload 的兼容值读取。

Redis 只新增有界 seed/version，不保存 execution payload、prompt 或 secret。D1 terminal fallback 没有 frozen presentation
metadata 时允许缺省展示，但不得重新掷骰。parser 采用 optional expand 字段；response header 保持现有 wire；semantic
hash 继续只覆盖授权后的请求语义和固定协议域，不包含 seed 或随机结果。

## 8. 测试与交付

所有行为修复按 test-first 实施，并实际观察新增测试在修复前以预期原因失败。

- finalization：completed/cancelled/failed pending 不被改写；lease reaper 保留原 terminal；副作用最多一次；
- recovery：ambiguous handshake 严格一次 POST；refresh/跨 runtime 只 lookup/resume；wrong actor 与 unavailable fail closed；
- cancel：普通 reader cancel 不触发 explicit cancel；user/content-policy reason 幂等且可跨实例传播；
- metadata：重复/并发 create 的 header、roll 与 Provider prompt 一致；旧无 seed entry 不 reroll；无 secret 泄漏。

实现按四个原子工作单元提交：finalization、content-policy cancel、request-ID recovery、reservation seed。
每个单元运行 targeted tests、类型检查与 lint。全部完成后至少运行 `pnpm ci:verify`、根 Next build、严格 naming、
生成物/route manifest 检查、`git diff --check` 与 G25R fault-injection 专项测试。既有 warning 必须区分本次引入与
无关历史项，不得隐藏。

本设计不授权 production deploy、DNS/LB 切流、remote D1 migration、Cloudflare secret 变更或 Docker 管理端写操作。
