# 模态框页签窄屏承载规格

状态：`accepted`

日期：2026-09-30
规格标识：`SPEC-modal-tabs-narrow-viewport-v1`

适用范围：`apps/web` 模态框内的页签栏（tab bar）与弹窗外壳视口定量。

本文件不改变任何数据、协议或持久化语义，也不改变 `BattleDataModal` 的调用契约。
与 [本地库 Web 落地与 BattleDataModal 一等数据源规格](./2026-09-29_200500_本地库Web落地与BattleDataModal一等数据源规格.md)
一致；两者冲突时以该规格为准（它管数据源，本文件管承载方式）。

---

## 1. 背景：故障与根因

窄屏下 `BattleDataModal` 的页签互相挤压：`管理员推荐` 被压成竖排单字，
`我的角色 (167)` 被挤成一列，界面看起来像坏了。

根因不是「少了一个响应式断点」，而是页签容器是裸 `flex gap-2`，同时缺三条约束：

| 缺失 | 后果 |
| --- | --- |
| 容器无 `overflow-x-auto` | 放不下时无处可去，只能压缩 |
| 子项无 `shrink-0` | flex 子项默认 `min-width: auto`，**允许收缩** |
| 标签无 `whitespace-nowrap` | 中文可在任意字符间断行 |

三者叠加：flex 收缩 + CJK 逐字换行。`DecksModal` 与 `WebPackagePickerModal`
是同一套写法的副本，同样中招。

同时暴露的可访问性欠账：这两个页签栏此前**完全没有 ARIA**——`BattleDataModal`
的 6 个页签各自是独立 Tab 停靠点，读屏无法得知哪一项选中，也没有方向键导航；
触控目标 `py-2` 约 36px，低于 Apple HIG 的 44pt 与 WCAG 2.5.5 的 44×44。

弹窗外壳另有两处独立的移动端缺陷，与页签无直接因果，但同属本轮范围（见 §5）。

---

## 2. 方案选型：为什么是横向滚动

窄屏页签有四种候选。本轮选择**横向滚动**，依据如下。

### 2.1 被否决的方案

**换行堆叠（`flex-wrap`）**
W3C ARIA APG 议题 #2438（tablist 窄屏 reflow）任务组的评估原文：
「simple to implement and remains accessible, but visually **inelegant** and somewhat crude
design because the connection between a tab and its content panel is often broken if the
active tab is on an upper row」。在高度受限的模态框里，换行还会进一步挤压内容区。
换言之：它正是当前故障形态的另一种写法。

**方向切换（窄屏改竖排）**
同议题列为次选，需要同步改 `aria-orientation` 与方向键绑定，复杂度显著高于收益。

**「更多」溢出菜单**
同议题明确否掉：「button is **not an allowed child of tablist** and making a tab element
behave as a menu button both violates the intent of the tab role and is confusing to AT users」。

**图标小按钮 + 角标数字**
不是上述议题的候选，但对本项目也不成立：3–5 字中文标签退化为 16px 图标后语义丢失，
而移动端没有 hover tooltip 可依赖；角标数字在此语义下表达的是「通知数」而非
「结果集大小」（`本地库 (0)` / `我的收藏 (—)`），会误导。

### 2.2 被采纳的方案

同议题任务组结论原文：「The most preferred solution with current ARIA 1.2 features is
**horizontal tablist scrolling**. Horizontal scrolling can readily meet the needs of all
users and is a good match for a wide variety of design systems. It is **more elegant than
wrapping** and avoids the substantial complexities inherent in the orientation switching and
overflow button solutions.」

Material Design 3 同向：
- 「When a set of tabs cannot fit on screen, **scrollable tabs** are used. They are best used
  for browsing on touch interfaces.」
- 「On mobile and desktop, offset the first tab on the left to signal that tabs are scrollable.」
- 「It's **not recommended to loop** a tab set where it scrolls infinitely. This can trap users
  who are navigating linearly with a screen reader.」

WCAG 1.4.10 Reflow（320 CSS px 宽下不出现二维滚动）对单个单行控件的横向滚动是认可的出路，
APG 与 MD3 都把它作为合规路径采用。

## 3. 规范要求

### 3.1 页签栏（`shared/ModalTabs`）

模态框内的页签栏 MUST 使用 `apps/web/components/shared/ModalTabs`。

- 滚动容器 MUST 常开 `overflow-x-auto`，MUST NOT 挂在某个断点下。
  理由：断点方案要赌「标签总宽度」这个变量，而标签里含调用方传入的
  `titleOverride`／类型名／数量，长度不可控，断点一定会被某些组合穿透。
- 每个页签 MUST 同时具备 `shrink-0` 与 `whitespace-nowrap`。
  缺任一条，中文都会在窄屏被逐字拆开。
- 触控目标 MUST NOT 低于 `min-h-11`（44px，Apple HIG / WCAG 2.5.5）。
  MD3 明确要求不要为了紧凑把 tab 目标压到 48dp 以下。
- 滚动条 MUST 隐藏但滚动能力 MUST 保留；容器 MUST `overscroll-x-contain`，
  避免横向滚动手势连带滚动祖先。
- `role="tablist"` / `role="tab"` / `role="tabpanel"` 与 `aria-selected` /
  `aria-controls` / `aria-labelledby` MUST 齐备；页签 MUST 使用 roving `tabIndex`
  （整条 rail 只占一个 Tab 停靠点）。
- 键盘契约：MUST 消费 `ArrowLeft` / `ArrowRight` / `Home` / `End`；
  MUST NOT 消费 `ArrowUp` / `ArrowDown`（APG 对 horizontal tablist 的要求，上下键留给页面滚动）；
  到达首尾 MUST 硬停，MUST NOT 循环。
- 选中页签变化时 MUST 自动进入视野，且 MUST 只改 rail 自身的 `scrollLeft`。
  MUST NOT 使用 `scrollIntoView`：它会连带滚动所有祖先滚动容器，而模态框是
  portal 到 `document.body` 的 `fixed` 元素，会把整个文档拽动。
- 数量等变长信息 MUST 作为独立 `tabular-nums` 片段渲染，MUST NOT 拼进 label 参与宽度计算。

### 3.2 非页签控件

非页签的动作按钮（如 `BattleDataModal` 的「卡组导入」）MUST 留在滚动 rail 之外。
进入 rail 就意味着它会随横向滚动被卷走，窄屏下等于消失。

### 3.3 页签行位置

页签行位于纵向滚动容器内时 SHOULD sticky，且底色 MUST 不透明
（否则列表内容会从页签行底下透出），并 MUST 为 focus ring 预留溢出空间
（`ring-offset-2` + `ring-2` 共 4px）。

## 4. 收敛范围

本轮收敛 `BattleDataModal`、`WebPackagePickerModal`、`DecksModal` 三处。
`MeTabs`、`BadgeManagerPage`、`magic-tea-party/CharacterPanel` 尚未接入，
但新增页签栏 MUST 使用 `ModalTabs`，不再新增裸 `flex` + 手写按钮的写法。

## 4.1 视觉口径变化

`BattleDataModal` / `DecksModal` 的未选中页签底色由 `bg-gray-200` 收敛到
`bg-gray-100` + `text-gray-700`，即对齐此前已在用的 `WebPackagePickerModal` 配色。
`BattleDataModal` 17 处调用点不涉及 props 变更。

## 5. 弹窗外壳的视口定量

与页签无因果关系，但同属窄屏可用性，本轮一并修正。

- 弹窗外壳 MUST NOT 用 `vw` 定量宽度。仓库现有写法 `w-[96vw]` 与遮罩层自带的
  `p-4` 叠加：375px 视口下 96vw = 360px + 32px 内边距 = 392px，必然产生横向滚动。
  MUST 用 `w-full` + `max-w-[…]`，由遮罩 padding 留边。
- 弹窗高度 MUST 使用 `dvh`，MUST NOT 使用 `vh`。`vh` 不含移动端浏览器地址栏与工具栏，
  浏览器 UI 收起时可视区小于 `vh`，弹窗底部会被切掉。`BaseModal` 已采用
  `max-h-[calc(100dvh-2rem)]`，本轮与之对齐。

本轮修正的四处：`BattleDataModal`、`PvpRoomBrowserModal`、`NarrativeHistoryModal`、
`NarrativeHistoryPickerModal`。

## 6. 未决：完整迁移到 `BaseModal`

`BattleDataModal` 仍保留手写的 focus trap 与 document 级 Escape 处理，未迁到 `BaseModal`。

阻塞点：`BaseModal` 通过模块级 `openModalStack` 保证「只有栈顶对话框响应 Escape/Tab」。
`DataCardDetailsModal` 尚未接入该栈——一旦 `BattleDataModal` 迁入，它就会重新成为栈顶，
当前「详情弹窗打开时 Escape 只关详情」的既有保护会回归，两个 focus trap 也会互相抢焦点。
`DataCardDetailsModal` 自带一套手写焦点逻辑并嵌套 `DataCardReportModal`（后者已接入该栈），
改造它属于独立改动，不夹带在本次视口修正内。

`BattleDataModal` 与嵌套的本地库删除二次确认之间也存在同类问题：
`BattleDataModal` 的 document 级处理在确认框打开时仍会响应 Escape，
一次按键会把整个选择弹窗一起关掉。该缺陷与 `DataCardDetailsModal` 同源，一并归入上述改造。
