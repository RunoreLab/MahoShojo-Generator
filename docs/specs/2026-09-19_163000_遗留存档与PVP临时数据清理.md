# 遗留存档与 PVP 临时数据清理

状态：已接受；2026-09-19 用户授权按核验结果清理，生产执行以备份验证完成为前提。

## 范围与边界

- 退休无产品消费者的 `shojo` 旧生成存档、`player_data` 测试表及其专用 helper；从当前初始化 schema 移除测试表。
- 保留共享 D1 transport、UUID、用户数据卡、卡组、Arena 排位与战报。
- 不新增 D1 表、付费观测、后台任务或新依赖。
- `characters` / `battles` 延续 G25H-1 的历史保留规则，不随本次清理删除。
- 旧 PVP 低活跃不等于无人使用。本轮保留产品入口和生成能力；用户进一步明确授权终止长期过期会话，再清理临时数据。
- 当前代码变更不会自动部署，也不把生产清理夹带进全量 migration 执行。

## 存档退休

`saveToD1` 已标记 deprecated，运行代码没有消费者；`createWithCustomId`、`updateById`、`getRecordById` 及专用随机 ID helper 也只剩兼容导出和测试引用，一并移除。通用 transport 的不确定提交结果与禁止隐式重放测试继续保留。

删除生产表前，先在用户指定的仓库外目录建立包含 schema、原始行和 rowid 的 SQLite 备份，并核验分页读入与本地读回的 SHA-256、行数、文件校验和及 `integrity_check`。备份只覆盖待清理的遗留表和 PVP 相关表，不宣称为全库备份。备份内容和生产凭据不得提交到公开仓库。

执行前重新核对源表未变化。仅对已备份、无当前消费者的 `shojo` 与 `player_data` 做定向退休；不执行无关 pending migrations。删除后查询表清单和数据库大小，实际容量变化以读回为准。

## PVP 临时数据

旧脚本 `apps/web/scripts/pvp-prune-ephemeral.ts` 仅凭过期时间取候选，且不提供并发版本保护，不能直接用作本轮生产清理入口。

本轮固定陈旧阈值为 `2026-09-12T00:00:00Z`。房间必须已过期，且房间、临时子表、对局、回合和关联生成均无该时刻之后的活动；缺失或无法解析的必要时间不能自动视为陈旧。通过 room ID 和 round 的 generation ID 两种关联检查已存在的生成记录，非终态、损坏 metadata 或明确未完成 finalization 时跳过。

用户授权的行政终止是本次有界维护操作：将符合冻结条件的 room 关闭并清空当前 match 指针，将仍为 active 的 match、pending/resolving 的 round 标记 aborted；保留既有结果，不补造胜负，不创建或修改 generation 终态，不重放 AI。无 generation 证据的陈旧 resolving 可以被维护者放弃，但不能被描述为已证明生成正常完成。既有 Admin runtime 的未知生成保护保持不变。

房间关闭、版本递增、状态终止、临时字段压缩和临时行删除在同一原子 batch 中执行。事务内复核冻结房间状态和子表新活动；CAS 零行须让整个 batch 回滚，不继续删除。目标清单、原因、操作时刻、备份摘要和实际结果保存在仓库外的备份目录，供恢复和审计。

可清理项：手牌、投稿、卡片快照、聊天、回合出牌选择，以及共享 `clearPvpRoomRuntimeFromRulesJson` 定义的临时规则字段。保留房间、参与者、matches、match players、rounds、generation 及战报历史，不能影响参与者访问历史战报的授权。

## 核验与后续

修改后执行受影响的 transport 测试、workspace 边界检查、测试、lint 和构建。PVP 失败记录中存在模型地区限制、空正文和未细分错误；本次不把它们统一归因于项目回归，不做推测性修复。当前流量权限不足的功能也不增加付费观测。

2026-09-19 的代码验证已完成 workspace 与仓库级 lint、构建、边界检查及 Cloudflare/OpenNext 构建。默认并发测试出现 Admin 本地夹具与 Web 认证首例超时；不改断言或超时阈值，Admin 用 `--maxWorkers=1` 全部 148 个测试通过，Web 用 `--maxWorkers=2` 全部 2,345 个测试通过，其余 workspace 与仓库级测试通过。不能把首次 `ci:verify` 描述为零退出码；这里记录的是各阶段及受限并发复验结果。

构建仍有环境代理提示和依赖触发的 Node `punycode` 弃用提示，不在本次退休工作中通过改代理或升级无关依赖消除。PVP 流式结算在签名/fetch 早期异常后的状态恢复路径仍可单独加固；这不是已证明的历史失败根因，也不影响本次有明确授权、备份和 CAS 的行政终止。
