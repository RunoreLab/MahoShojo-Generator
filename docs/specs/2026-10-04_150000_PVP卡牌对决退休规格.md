# PVP 卡牌对决退休规格

状态：accepted
日期：2026-10-04
接受依据：维护者明确授权移除 `/pvp` 卡牌对决及其专属功能，降低维护、服务器资源和 Desktop 开发成本。

## 范围与取代关系

退休对象是 `/pvp` 房间制卡牌对决，包括创建、匹配、选牌、机器人、聊天、表情包、投票、回合推进、结算以及专属管理操作、导航和百科。删除活跃实现，不以隐藏入口或 feature flag 代替退休。

本规格取代[遗留存档与 PVP 临时数据清理](./2026-09-19_163000_遗留存档与PVP临时数据清理.md)中“保留 PVP 产品入口和生成能力”的范围限定，以及[Desktop 产品共源决策](../decisions/2026-10-02_184000_Desktop产品架构与Web共源决策.md)中“Web PVP 功能保留”的口径。既有生产清理记录仍是历史事实。

`/battle`、`/arena` 和 Arena 多人不属于此次退休。较早 Desktop 文档将 `/battle`、`/arena` 称作旧 PVP 的表述不能用于扩大本次删除范围；本轮也不重新决定这些功能的 Desktop 实施阶段。

## 共享能力与兼容边界

- PVP 目录内被账号、消息、举报等模块使用的 HTTP 响应、认证及错误处理先提取为中性模块，保持认证授权与错误响应语义。
- Arena 多人仍使用的 generation authority、签名 header/purpose、`pvpContext` 以及 `battle_report_generations.pvp_*` 字段继续兼容。它们不是活跃 PVP 产品的保留理由，也不能按名称批量删除。
- 保留历史战报、排位结果、用户数据卡、卡组及其访问授权。历史 PVP 参与关系有真实读取消费者时，只保留必要的只读查询；不得将参与者权限扩大为 owner 权限。
- 不删除历史 migration，不自动 DROP 生产表，不新增数据库或外部服务。休眠表和旧字段可以为历史读取、回滚及旧部署共存保留。
- 移除 PVP 专属 Admin capability、查询及写操作时同步清理消费者和契约；Arena 管理功能继续保留。
- 已退休的 PVP Admin capability 不再可授予、不注册任何 resource/action；但存量 principal 的 `capabilities_json` 中允许保留这些条目用于身份解析，解析时必须从有效权限中过滤，不得据此授予任何操作。

个人资料卡 `/api/me/profile-card` 同步移除专属 `pvp` 摘要字段及前端消费；这是随产品退休进行的有意契约收缩。Admin 的 PVP read/action 和专属 cleanup target 同步退出，既有审计记录不重写。

## 退出行为

删除专属页面和 API 后，旧 `/pvp` 链接及 API 使用框架的未找到行为，不重定向到语义不同的 Arena，不允许旧客户端继续创建或推进卡牌对决。清理个人页专属入口、首页、共享导航、百科及仅供 PVP 使用的静态资产；历史设计文档保留，并链接此规格说明退休关系。

## 验证与交付

按完整主题原子化提交。验证共享 API helper 的鉴权/错误处理、Arena 生成与历史权限、Admin capability 退出、导航与百科完整性；执行受影响 workspace 测试、静态检查和构建，再执行仓库边界检查。全量验证可按资源限制拆分并记录实际结果，不把未执行项写成通过。

代码交付不等于线上退休完成：本轮不推送、不部署、不切流、不清理生产数据库或 Redis。旧版本进程停止前，不能宣称服务器资源开支已经下降；生产数据清理需要单独确定备份、活跃请求处理、授权和恢复策略。
