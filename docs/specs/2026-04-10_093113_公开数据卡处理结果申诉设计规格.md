# 公开数据卡处理结果申诉设计规格

更新时间：2026-04-10 09:31:13

## 1. 目标

本设计用于补齐公开数据卡众查一期中尚未落地的 `申诉入口 + 管理员复核边界`：

- 为被处理的公开数据卡创作者提供明确、可回看的申诉入口，而不是隐式要求用户自行联系管理员。
- 在 `report_cases` 事实层之外建立独立的 `report_appeals` 子域，用于承载申诉提交、状态跟踪、补充材料与复核结论。
- 复用现有消息系统与公开数据卡详情视图，形成“处理结果通知 -> 申诉页 -> 管理员复核边界”的最小闭环。
- 在当前分支补齐用户侧页面/API、管理员复核 API 边界与结果写回规则，为后续 `feat/admin` 后台页面直接复用。

## 2. 非目标

- 不在本分支开发 `feat/admin` 后台 UI。
- 不支持任意文件上传、富文本编辑器、外链附件或聊天式申诉线程。
- 不实现举报人通知回流、巡查使自动扣分、准确率权重或处罚引擎。
- 不扩展到评论、私聊、动态等其他对象。
- 不重做消息中心、调查院或公开数据卡管理页的整体信息架构。

## 3. 现状与核心缺口

当前仓库已经具备众查一期前半段所需的大部分基础设施，但申诉链路仍然缺失两个关键环节：

- `lib/crowd-review/service.ts` 已能将众查结果写回 `report_cases`，但只更新案件状态，不会向被处理用户发出“处理结果 + 申诉入口”通知。
- `user_messages` 适合做入口通知，不适合直接承载申诉正文、复核状态和结构化补充材料。
- `components/DataCardDetailsModal.tsx` 已经是用户查看自有公开卡详情的稳定入口，适合补一个创作者可见的申诉状态摘要，作为消息之外的第二入口。

因此，本阶段不应把申诉继续塞进 `report_cases` 或消息 payload，而应新增一个面向“被处理结果”的独立子域。

## 4. 方案比较与结论

### 4.1 方案 A：把申诉直接塞进 `report_cases`

做法：

- 在 `report_cases` 上直接追加 `appeal_text`、`appeal_status`、`appeal_admin_note` 等字段。
- 消息只负责跳回原案件。

优点：

- 表面上改动最少。

缺点：

- 举报案件主实体和申诉生命周期耦合，后续很难支持多轮不同结果快照下的申诉。
- 无法干净表达“申诉材料”“申诉状态”“管理员复核结论”这三类独立信息。
- 会让 `report_cases` 同时承担事实层、治理层和申诉层职责。

### 4.2 方案 B：独立 `report_appeals` 子域

做法：

- `report_cases` 继续作为举报案件事实层。
- 新增 `report_appeals` 与 `report_appeal_references`，专门承载申诉提交、补充引用与复核结果。
- 用户入口复用现有消息系统和数据卡详情页；管理员只先定义 API / service 边界，不做 UI。

优点：

- 与现有“举报事实层 + 众查执行层”的分层策略一致。
- 既能满足一期最小闭环，又不会阻塞后续 `feat/admin` 扩展。
- 允许按“结果快照”而不是按“案件永恒单例”管理申诉，边界更清晰。

缺点：

- 比直接往 `report_cases` 加字段多一层 repository / service / API 设计。

### 4.3 方案 C：现在就做通用申诉平台

做法：

- 一开始就抽象评论、私聊、动态、公开卡等所有对象的通用申诉系统。

优点：

- 长期形态更完整。

缺点：

- 明显超出当前阶段范围。
- 会把当前目标从“公开数据卡众查一期收口”拖向“治理平台化重构”。

### 4.4 结论

本设计采用方案 B：独立 `report_appeals` 子域。

## 5. 申诉适用范围与资格

### 5.1 哪些案件可以进入申诉

本批次只允许对以下案件结果发起申诉：

- `report_cases.target_entity_type = 'data_card'`
- 当前访问者 `viewerUserId = report_cases.target_user_id`
- `report_cases.status = 'resolved'`
- `report_cases.resolution_code IN ('confirmed_violation', 'content_removed', 'self_remediated')`

说明：

- `dismissed + no_violation` 不属于被处理结果，不提供申诉入口。
- `malicious_report` 针对的是举报人治理，不属于被举报创作者的申诉范围。
- `open / under_review` 代表案件尚未形成可申诉的终局处理结果。

### 5.2 结果快照口径

申诉不是绑定到“案件永远只能申诉一次”，而是绑定到“某次终局处理结果快照”。

本批次以 `report_cases.updated_at` 作为结果快照版本号，并采用以下规则：

- 用户打开申诉入口时，服务端返回当前 `caseUpdatedAtSnapshot`。
- 用户提交申诉时，必须回传该快照值。
- 同一 `report_case` 在任一时刻最多只允许 `1` 条活跃申诉（`submitted / under_review`）。
- 同一 `(report_case_id, case_updated_at_snapshot)` 只允许存在一条 `非 withdrawn` 的申诉记录。
- 若同一快照下的旧申诉已 `withdrawn`，用户允许重新提交一条新的申诉记录；旧记录仅保留历史，不做复活或覆盖。
- 如果管理员后续改判、重新进入 `under_review`，再形成新的终局处理结果，则新的 `updated_at` 会允许产生新的申诉记录。

### 5.3 用户可执行动作

- 满足资格时：可以提交申诉。
- 申诉未结案前：可以查看状态；若仍为 `submitted / under_review`，允许撤回一次。
- 撤回后的记录固定保留为历史记录；首批不做撤回冷却、草稿恢复或“复用原记录再次提交”。
- 申诉已结案后：只能查看记录，不允许对同一结果快照重复申诉。

## 6. 数据模型

SQL 层使用 `snake_case`，TypeScript DTO 与组件状态使用 `camelCase`，跨层映射集中放在 repository / service 边界。

本批次所有新增申诉域时间字段统一采用 `UTC ISO8601` 字符串并带尾部 `Z`，例如 `2026-04-10T01:30:00.000Z`。`case_updated_at_snapshot`、`resolution_notified_case_updated_at` 等快照字段在服务层只做字符串全等比较，不做本地化格式转换或宽松解析。

说明：

- DDL 中保留 `DEFAULT CURRENT_TIMESTAMP` 仅作为极端情况下的兜底，不作为业务时间格式来源。
- 实际实现时，`report_appeals`、`report_appeal_references` 与新增 `report_cases` 通知字段涉及的所有时间写入，都必须由服务层显式传入 ISO8601 UTC 字符串。

### 6.1 `report_cases` 扩展字段

为结果通知与入口幂等新增两个字段：

```sql
ALTER TABLE report_cases ADD COLUMN resolution_notified_at TEXT;
ALTER TABLE report_cases ADD COLUMN resolution_notified_case_updated_at TEXT;
```

字段说明：

- `resolution_notified_at`：最近一次向被处理用户发送“处理结果/申诉入口”消息的时间。
- `resolution_notified_case_updated_at`：发送通知时对应的 `report_cases.updated_at` 快照。

该设计的目的不是记录所有历史通知，而是保证：

- 同一个结果快照不会重复发消息。
- 若案件后续再次被管理员改判并形成新的终局结果，即使 `resolution_code` 未变化，也能重新生成新的申诉入口消息。

### 6.2 `report_appeals`

```sql
CREATE TABLE IF NOT EXISTS report_appeals (
  id TEXT PRIMARY KEY,
  report_case_id TEXT NOT NULL,
  appellant_user_id INTEGER NOT NULL,
  target_user_id INTEGER NOT NULL,
  target_entity_type TEXT NOT NULL,
  target_entity_id TEXT NOT NULL,
  appeal_reason_code TEXT NOT NULL,
  details TEXT NOT NULL,
  evidence_summary_json TEXT NOT NULL DEFAULT '{}',
  status TEXT NOT NULL,
  resolution_code TEXT,
  resolution_note TEXT,
  case_status_snapshot TEXT NOT NULL,
  case_resolution_code_snapshot TEXT,
  case_updated_at_snapshot TEXT NOT NULL,
  reviewed_by_user_id INTEGER,
  reviewed_at TEXT,
  withdrawn_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (report_case_id) REFERENCES report_cases(id) ON DELETE CASCADE,
  FOREIGN KEY (appellant_user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (target_user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (reviewed_by_user_id) REFERENCES users(id) ON DELETE SET NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_report_appeals_case_active
  ON report_appeals(report_case_id)
  WHERE status IN ('submitted', 'under_review');

CREATE UNIQUE INDEX IF NOT EXISTS idx_report_appeals_case_snapshot_unique
  ON report_appeals(report_case_id, case_updated_at_snapshot)
  WHERE status IN ('submitted', 'under_review', 'resolved');

CREATE INDEX IF NOT EXISTS idx_report_appeals_appellant_created
  ON report_appeals(appellant_user_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_report_appeals_status_created
  ON report_appeals(status, created_at DESC);
```

字段说明：

- `appeal_reason_code`：结构化申诉理由，固定枚举：
  - `factual_error`
  - `missing_context`
  - `already_fixed`
  - `misidentified_target`
  - `other`
- `details`：用户的申诉说明，首批为必填纯文本。
- `evidence_summary_json`：结构化引用摘要，供列表页、消息模板与后台预览复用。
- `status`：`submitted | under_review | resolved | withdrawn`
- `resolution_code`：`upheld | overturned_no_violation | reopened_under_review`
- `case_*_snapshot`：用户发起申诉时看到的案件终局结果快照，用于后续判断“这条申诉到底在挑战哪一次处理结果”。

约束说明：

- `idx_report_appeals_case_active` 用于表达“每个案件同时最多 1 条活跃申诉”。
- `idx_report_appeals_case_snapshot_unique` 用于表达“同一结果快照在未撤回或已结案后不可重复提交”。
- 两个索引叠加后，`withdrawn` 是唯一允许同一快照重新提交的例外状态。

### 6.3 `report_appeal_references`

```sql
CREATE TABLE IF NOT EXISTS report_appeal_references (
  id TEXT PRIMARY KEY,
  appeal_id TEXT NOT NULL,
  reference_type TEXT NOT NULL,
  reference_id TEXT NOT NULL,
  label_snapshot TEXT NOT NULL,
  url_snapshot TEXT,
  note TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (appeal_id) REFERENCES report_appeals(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_report_appeal_references_sort
  ON report_appeal_references(appeal_id, sort_order, created_at);

CREATE UNIQUE INDEX IF NOT EXISTS idx_report_appeal_references_target_unique
  ON report_appeal_references(appeal_id, reference_type, reference_id);
```

首批仍只支持与举报侧一致的两类引用：

- `public_data_card`
- `encyclopedia_entry`

不支持任意 URL、图片或附件上传。

`evidence_summary_json` 的写入策略固定为：服务端在创建或重提申诉时，根据标准化后的 `report_appeal_references` 生成并落库；读取列表时优先使用该摘要，只有在摘要缺失时才回退动态组装。

## 7. 产品与交互

### 7.1 入口 1：处理结果消息

当案件首次进入“可申诉的被处理结果快照”时，系统应向 `report_cases.target_user_id` 发送高优先级定向消息：

- `messageType = 'moderation'`
- `templateKey = 'user.moderation.report_case_resolved'`
- `actionUrl = '/report-appeals?reportCaseId=<caseId>'`
- `sourceEntityType = 'report_case'`
- `sourceEntityId = <caseId>`

消息文案需说明：

- 哪张公开数据卡被处理
- 当前处理口径
- 可前往申诉页提交说明

### 7.2 入口 2：创作者卡片管理视图

扩展 `GET /api/data-card-reports?dataCardId=...` 响应，在创作者查看自己的公开卡详情时增加 `ownerModerationSummary`：

```json
{
  "ownerModerationSummary": {
    "latestCaseId": "case_123",
    "status": "resolved",
    "resolutionCode": "confirmed_violation",
    "canAppeal": true,
    "activeAppealId": null,
    "activeAppealStatus": null,
    "appealEntryUrl": "/report-appeals?reportCaseId=case_123",
    "statusSummary": "该卡因举报处理结果被判定为违规，可提交申诉。"
  }
}
```

`components/DataCardDetailsModal.tsx` 在 `isOwner === true` 时：

- 若 `canAppeal = true`，展示申诉 CTA banner。
- 若存在 `activeAppealId`，展示“申诉处理中 / 已结案”状态摘要并链接到详情页。

### 7.3 申诉页

首批新增独立页面：`/report-appeals`

页面职责：

- 展示当前用户自己的申诉记录列表。
- 当 URL 带 `reportCaseId` 时，优先展示该案件对应的申诉入口卡片。
- 当 URL 带 `appealId` 时，优先展示该申诉详情卡片。
- 若该案件已经存在活跃或已结案申诉，则直接展示该记录，不再重复渲染空表单。

首批表单字段：

- `appealReasonCode`：单选
- `details`：必填文本
- `references`：可选，与举报侧相同的结构化引用输入

## 8. API 契约

### 8.1 `GET /api/report-appeals/entry?reportCaseId=<id>`

- 仅允许已登录访问。
- 仅目标创作者本人可查看。
- 成功返回 `200`。

响应字段：

```json
{
  "reportCaseId": "case_123",
  "eligible": true,
  "caseUpdatedAtSnapshot": "2026-04-10T01:20:00.000Z",
  "caseStatus": "resolved",
  "caseResolutionCode": "confirmed_violation",
  "targetCard": {
    "id": "card_123",
    "name": "公开卡示例"
  },
  "reasonOptions": [
    { "code": "factual_error", "label": "事实有误" }
  ],
  "existingAppeal": null
}
```

若当前已有申诉记录，`existingAppeal` 返回完整摘要，前端直接进入查看态。

### 8.2 `POST /api/report-appeals`

请求体：

```json
{
  "reportCaseId": "case_123",
  "caseUpdatedAtSnapshot": "2026-04-10T01:20:00.000Z",
  "appealReasonCode": "missing_context",
  "details": "该卡被判定时缺少前后文，补充说明如下……",
  "references": [
    {
      "referenceType": "public_data_card",
      "referenceId": "card_456",
      "note": "补充对照"
    }
  ]
}
```

成功返回 `200`：

```json
{
  "appealId": "appeal_123",
  "status": "submitted",
  "entryUrl": "/report-appeals?appealId=appeal_123"
}
```

若同一快照下已存在 `submitted / under_review / resolved` 申诉，则接口直接返回该记录，不再创建新行；若仅存在 `withdrawn` 记录，则允许新建一条新的申诉记录。

### 8.3 `GET /api/report-appeals`

- 仅允许已登录访问。
- 返回当前用户自己的申诉记录。

响应字段：

```json
{
  "items": [
    {
      "appealId": "appeal_123",
      "reportCaseId": "case_123",
      "targetCardName": "公开卡示例",
      "appealReasonCode": "missing_context",
      "status": "submitted",
      "resolutionCode": null,
      "createdAt": "2026-04-10T01:30:00.000Z",
      "updatedAt": "2026-04-10T01:30:00.000Z"
    }
  ],
  "fetchedAt": "2026-04-10T01:31:00.000Z"
}
```

### 8.4 `GET /api/report-appeals/detail?appealId=<id>`

- 仅允许已登录访问。
- 仅申诉发起者本人可查看。
- 成功返回单条申诉详情，包含引用材料、案件快照与当前状态。

响应字段至少包括：

```json
{
  "appealId": "appeal_123",
  "reportCaseId": "case_123",
  "appealReasonCode": "missing_context",
  "details": "补充说明……",
  "status": "resolved",
  "resolutionCode": "upheld",
  "resolutionNote": "管理员复核说明",
  "caseSnapshot": {
    "status": "resolved",
    "resolutionCode": "confirmed_violation",
    "updatedAt": "2026-04-10T01:20:00.000Z"
  },
  "references": [],
  "createdAt": "2026-04-10T01:30:00.000Z",
  "updatedAt": "2026-04-10T02:00:00.000Z"
}
```

### 8.5 `POST /api/report-appeals/withdraw`

请求体：

```json
{
  "appealId": "appeal_123"
}
```

- 仅允许申诉发起者本人操作。
- 仅 `submitted / under_review` 可撤回。
- 成功返回 `200`，并把 `status` 置为 `withdrawn`。
- 撤回后如该快照下不存在其他 `非 withdrawn` 记录，允许用户再次新建一条新的申诉。

### 8.6 `GET /api/data-card-reports?dataCardId=<id>` 扩展字段

保留现有举报能力字段，同时新增：

- `ownerModerationSummary: DataCardOwnerModerationSummaryDto | null`

非创作者访问时固定返回 `null`。

### 8.7 管理员复核 API 边界

当前分支只定义 API / service 边界，不做后台页面。

#### `GET /api/report-appeals/admin?status=submitted`

- 仅管理员可访问。
- 返回待复核申诉列表。
- 首批支持可选 `limit` 参数，默认 `50`，最大 `100`。

#### `GET /api/report-appeals/admin/[appealId]`

- 仅管理员可访问。
- 返回申诉详情、引用材料、案件快照和当前 `report_cases` 最新状态。

#### `POST /api/report-appeals/admin/[appealId]/review`

请求体：

```json
{
  "resolutionCode": "upheld | overturned_no_violation | reopened_under_review",
  "resolutionNote": "管理员复核说明"
}
```

本批次允许两种管理员状态流转：

- `submitted -> resolved`
- `submitted -> under_review -> resolved`

是否显式进入 `under_review` 由后台交互决定，不强制要求“打开详情即自动占用”。

### 8.8 错误码约定

- `400`
  - 缺少 `reportCaseId`
  - `appealReasonCode` 非法
  - `details` 为空
- `401`
  - 未登录
- `403`
  - 不是案件目标创作者
  - 非管理员访问管理员接口
- `404`
  - 案件不存在
  - 申诉不存在
- `409`
  - 同一结果快照已存在 `submitted / under_review / resolved` 申诉
  - 管理员试图复核已结案申诉
- `422`
  - 当前案件结果不可申诉
  - `caseUpdatedAtSnapshot` 与当前案件快照不一致，需要用户刷新后重新确认
- `503`
  - D1 / 服务层不可用

## 9. 状态流转与结果写回

### 9.1 处理结果通知

当举报案件进入“可申诉的终局结果”时：

- 如果 `report_cases.resolution_notified_case_updated_at !== report_cases.updated_at`
- 且结果满足 5.1 的申诉资格

则系统发送一次处理结果消息，并将：

- `resolution_notified_at = now`
- `resolution_notified_case_updated_at = report_cases.updated_at`

### 9.2 管理员复核结论

管理员复核 `report_appeals` 时允许三种结论：

- `upheld`
  - 维持原判
  - `report_cases` 不变
- `overturned_no_violation`
  - 改判为不违规
  - `report_cases.status = 'dismissed'`
  - `report_cases.resolution_code = 'no_violation'`
  - `report_cases.closed_at = reviewedAt`
- `reopened_under_review`
  - 发回继续人工处理
  - `report_cases.status = 'under_review'`
  - `report_cases.resolution_code = null`
  - `report_cases.closed_at = null`

### 9.3 与众查结果的关系

申诉复核不会篡改历史众查轮次事实：

- 不回写 `crowd_review_rounds.result_code`
- 不重写巡查使投票记录
- 社区结论与管理员最终处理结果的差异，保留在 `report_appeals` 与 `report_cases` 的对照关系中

这样后续若要做“众查结果与复核结果一致性统计”，仍能基于原始事实计算。

### 9.4 申诉结果通知

管理员复核完成后，系统向申诉人发送：

- `templateKey = 'user.moderation.report_appeal_resolved'`
- `actionUrl = '/report-appeals?appealId=<appealId>'`

通知文案需说明：

- 申诉已处理
- 复核结论为何
- 若被发回 `under_review`，当前仍属人工处理中的中间态

## 10. 验收口径

本批次完成后，应至少满足以下条件：

- 被处理用户在消息页或公开卡管理视图中能够看到明确申诉入口。
- 只有案件目标创作者本人可以打开并提交该案件的申诉。
- 同一结果快照不会被重复申诉。
- 管理员复核 API 能返回待处理列表、详情与三类标准结论。
- `upheld / overturned_no_violation / reopened_under_review` 三种复核结论都能正确写回 `report_cases`。
- 申诉结果会以消息形式回告给申诉人。
- `feat/admin` 后台 UI、自动扣分和多对象平台化扩展仍保持在后续阶段。

## 11. 后续保留问题

以下问题不阻塞本批次启动，但需在后续阶段继续演进：

- 是否允许在申诉中上传图片、文本附件或更多证据类型。
- 是否向举报人或巡查使同步申诉改判结果。
- 是否在后台补充更细粒度的申诉事件流与审计账本。
- 申诉成功后是否对巡查使准确率、冷却或治理事件进行回流处理。
