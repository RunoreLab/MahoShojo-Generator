# 魔法少女竞技场肉鸽首版设计规格

日期：2026-04-03 23:33:57
范围：定义“魔法少女竞技场”作为首发世界的本地路径式叙事肉鸽 MVP，并同时定义未来多世界扩展所需的稳定接口与覆写点，但不展开第二世界的具体玩法设计。
参考依据：`docs/reports/2026-04-03_193555_肉鸽玩法调研与基础方案建议.md`

---

## 1. 设计目标

本轮设计目标是做出一个可直接进入后续计划拆分的首版规格，解决以下问题：

1. 在当前项目内，为“路径式叙事肉鸽”确定首发世界、首版范围与非目标。
2. 在不把结构写死在竞技场语义里的前提下，定义未来多世界扩展需要的稳定接口。
3. 明确“系统约束下的 AI 裁定”如何用于战斗与事件，而不是退回纯数值硬算，也不是放任纯 AI 放飞。
4. 明确本地存档、挑战快照、敌人来源、UI 主流程与验证边界。

---

## 2. 结论先行

首版产品定位收敛为：

> 在本地浏览器中运行的、以魔法少女竞技场为首发世界的路径式叙事肉鸽 MVP。

用户界面文案中，`run` 统一翻译为：

- `挑战`
- 需要更完整语气时使用 `本轮挑战`

系统内部、代码与 schema 仍保留 `run` 语义，不强行中文化内部命名。

---

## 3. 范围与非目标

### 3.1 首版范围

首版明确包含：

1. 只实现 `1` 个世界：
   - `魔法少女竞技场`
2. 只实现 `1` 套完整可玩的挑战循环：
   - 进入世界
   - 选择角色
   - 生成竞技场快照
   - 跑图
   - 结算节点
   - 通关或失败
3. 挑战长度先控制在：
   - `8-12` 个节点
4. 节点类型固定为：
   - 普通战斗
   - 精英战斗
   - 事件
   - 休整
   - 商店
   - Boss
5. 允许任意角色卡进入挑战。
6. 开局自动补全并冻结一份“竞技场战斗快照”。
7. 地图整张基本公开，但节点细节半隐藏。
8. 战斗采用“系统约束下的 AI 裁定”，不做细回合制。
9. 事件采用分级输入模式，默认 `choice-plus-note`。
10. 存档只保存在本地浏览器 IndexedDB。
11. 默认失败语义为：
   - 失败即结束挑战
   - 生成失败战报
   - 给予少量长期内容型收益

### 3.2 首版非目标

首版明确不做：

1. 第二世界的具体玩法设计与实现。
2. 完整 deckbuilder 或细回合制战斗系统。
3. 完整小队制玩法。
4. 云存档、跨设备同步、线上挑战持久化。
5. 强永久数值成长。
6. 开局快照的完整手工编辑器。
7. 由 AI 动态生成世界预设、动作池或事件池。
8. 多世界平衡与统一内容平台。

### 3.3 多世界接口边界

本规格会定义未来多世界扩展所需的：

1. schema
2. resolver 插槽
3. UI 扩展点
4. world override points

但不会定义：

1. 第二世界的具体内容池
2. 第二世界的具体 UI
3. 第二世界的具体数值与平衡参数

## 4. 方案选择

### 4.1 不选“纯数值硬算”

若战斗和事件都采用纯数值硬算：

- 会过度削弱项目已有的“角色设定 + 用户意图 + AI 演出”特色
- 很容易把玩法滑向普通规则引擎
- 无法充分利用现有竞技场战报资产

### 4.2 不选“纯 AI 自由生成”

若完全交给 AI 判定胜负、掉血、掉落与状态变化：

- 长期一致性难控
- 平衡难以验证
- 存档恢复与后续扩展都会变得脆弱

### 4.3 采用“系统约束下的 AI 裁定”

首版采用：

1. 系统先生成合法结果带宽
2. AI 在带宽内生成结构化裁定结果与战报
3. 系统校验结果是否合法后写回状态

这是当前项目最稳妥、也最能发挥特色的方案。

## 5. 稳定接口设计

本节定义未来多世界共用的稳定对象，不写竞技场专属参数。

### 5.1 `worldPreset`

定义一个世界如何运行，至少包含：

- `id`
- `title`
- `resourceModel`
- `mapProfile`
- `nodeGenerationRules`
- `actionCatalogs`
- `eventCatalogs`
- `enemySourcePolicy`
- `failurePolicy`
- `aiPromptPack`

职责：

- 声明“这个世界里的挑战如何构成”
- 不是只提供一层文案皮肤

### 5.2 `runState`

定义一轮挑战的当前真相，至少包含：

- `runId`
- `worldPresetId`
- `seed`
- `playerSnapshot`
- `resources`
- `statuses`
- `inventory`
- `relics`
- `skillProgress`
- `currentNodeId`
- `mapState`
- `historyDigest`
- `failureState`
- `startedAt`
- `updatedAt`

职责：

- 所有节点判定都以 `runState` 为准
- 不直接回头读取原始角色卡

### 5.3 `mapNode`

定义地图节点，至少包含：

- `nodeId`
- `layer`
- `nodeType`
- `visibility`
- `riskHint`
- `rewardHint`
- `encounterRef`

职责：

- 支持“整图公开、细节半隐藏”的默认规则

### 5.4 `encounterTemplate`

统一描述战斗、事件、休整、商店、Boss 等节点，至少包含：

- `templateId`
- `kind`
- `inputMode`
- `requirements`
- `actionOverrides`
- `rewardProfile`
- `aiContextPack`

### 5.5 `actionDefinition`

定义玩家在节点里可采取的动作，至少包含：

- `actionId`
- `label`
- `source`
- `intentType`
- `requirements`
- `riskTag`
- `aiHint`

其中 `source` 至少支持：

- `world`
- `encounter`
- `character`
- `free-intent-derived`

### 5.6 `enemySnapshot`

定义敌人在本次挑战中的冻结快照，至少包含：

- `sourceType`
- `sourceId`
- `displayName`
- `strengthTier`
- `combatProfile`
- `tags`
- `promptSummary`

职责：

- 不管敌人来源于预设、公开库还是排行，一旦进入挑战，都必须先冻结为统一快照

### 5.7 `saveModel`

定义本地存档结构，至少拆成：

1. `run record`
2. `node records`
3. `checkpoints`
4. `unlock records`

### 5.8 世界覆写点

未来世界允许覆写：

1. 资源模型
2. 地图节点权重
3. 动作池
4. 事件池与默认 `inputMode`
5. 敌人来源策略
6. 失败语义
7. AI 风格包

## 6. 魔法少女竞技场世界 MVP 实例化

### 6.1 世界定位

竞技场世界首版是：

- 一轮连续挑战
- 以战斗节点为主
- 以强敌遭遇、战后成长、事件变化和战报生成推动节奏

它不是：

- 传统 deckbuilder
- 细回合制 RPG
- 单次普通竞技场战报的简单外壳

### 6.2 玩家入口

玩家可从任意角色卡开始挑战。

开局时系统生成“竞技场战斗快照”：

1. 若角色已有 `buildState / 角色参数`，优先复用
2. 若没有，则按下列信号自动补全：
   - 角色文本设定
   - 标签
   - `powerLevel` 或强度描述
   - 公开排位信息（若有）
   - 世界默认模板

补全后的竞技场快照在本轮挑战内冻结，不回写原始角色卡。

### 6.3 开局补全交互

开局不采用：

- 完全静默生成
- 完整手工微调

首版采用：

1. 生成竞技场快照摘要
2. 展示给玩家
3. 玩家可：
   - 接受并开始挑战
   - 免费重掷一次
4. 不开放逐字段编辑

摘要建议展示：

- 力量层级
- 战斗定位
- 关键属性倾向
- 关键动作倾向
- 初始风险/稳定性提示

### 6.4 资源模型

竞技场世界首版资源建议收敛为：

- `hpBand` 或粗粒度 HP
- `radiance`
- `currency`
- `consumables`
- `relics`
- `temporaryStatus`
- `runFlags`

外显层主要显示：

- `完好 / 受创 / 重伤 / 濒危`
- 关键资源变化

不显示逐回合精细扣血流水。

### 6.5 地图与节点

默认挑战规模：

- `8-12` 个节点
- `1` 个最终 Boss

地图可见性：

- 整张图基本公开
- 节点细节半隐藏

公开：

- 拓扑
- 节点类型
- 精英/Boss 分布
- 风险/收益倾向

不完全公开：

- 敌人具体身份
- 事件正文
- 商店详细售卖内容
- 奖励精确落点

### 6.6 节点类型分工

1. 普通战斗
   - 主体节奏节点
2. 精英战斗
   - 高风险高收益节点
3. 事件
   - 节奏变化与分支节点
4. 休整
   - 修复与资源整理
5. 商店
   - 结构化资源交换
6. Boss
   - 本轮挑战终局节点

### 6.7 敌人来源策略

#### 普通敌人

普通敌人不以公开库纯随机作为主来源。

首版主来源应为：

1. 当前 / 历史赛季的低中位公开角色段
2. 本地预设角色池补位
3. 公开库随机作为补充与兜底

理由：

- 强度更稳定
- 不容易在普通战斗里直接抽出榜首角色
- 更适合做分带控制

#### 精英敌人

精英敌人建议来自：

1. 当前赛季中高位角色段
2. 手工标记的高压预设角色

#### Boss

Boss 建议来自：

1. 当前或历史赛季高位代表角色
2. 竞技场代表性预设角色

#### 强度分层

首版先粗分为：

- `common`
- `elite`
- `boss`

预设角色若自带明显强度描述或 `powerLevel` 描述，可作为强度映射参考。

### 6.8 战斗流程

战斗节点默认流程：

1. 读取本场 `enemySnapshot`
2. 生成推荐动作
3. 玩家可：
   - 选择推荐动作
   - 输入一句自由战术意图
   - 或两者结合
4. resolver 先生成 `resolverEnvelope`
5. AI 在 envelope 内产出：
   - 胜负
   - 损伤
   - 资源消耗
   - 特殊后果
   - 战报文本
6. 系统校验结果是否合法
7. 写回 `runState`
8. 发奖励并进入下一节点

首版不处理：

- 逐回合行动顺序
- 精确逐击扣血
- 复杂技能 CD

### 6.9 事件输入模式

事件节点采用分级输入模式。

支持三档：

1. `choice-only`
2. `choice-plus-note`
3. `free-intent`

首版默认：

- 全局默认 `choice-plus-note`
- 简单事件显式写为 `choice-only`
- 少数关键事件使用 `free-intent`

### 6.10 默认失败语义

首版默认：

- 失败即结束挑战
- 生成失败战报
- 给予少量内容型长期收益

未来允许竞技场世界扩展特殊败北分支，但不纳入首版核心。

### 6.11 长期成长方向

首版长期成长以内容解锁为主：

- 图鉴
- 事件解锁
- 敌人记录
- 起始动作候选
- 起始物候选
- 特殊路线或文案解锁

不建议首版做强永久数值成长。

## 7. UI 主流程与页面结构

### 7.1 入口策略

首版建议为肉鸽玩法提供独立入口页，而不是直接塞进 `/battle` 作为附加开关。

原因：

- 状态模型明显不同
- 需要地图、挑战存档、节点结算与长期解锁层
- 可避免继续做胖普通竞技场页

但入口关系应与现有竞技场保持强连接：

- 可从竞技场页或百科页跳入
- 可从挑战页返回普通竞技场

### 7.2 首版用户主流程

1. 世界选择
2. 角色选择
3. 竞技场快照确认
4. 挑战地图页
5. 节点结算页
6. 挑战结算页

### 7.3 推荐页面骨架

建议最少拆成：

1. `WorldRunLobby`
2. `RunBootstrapPanel`
3. `RunMapPage`
4. `NodeResolutionPanel`
5. `RunSummaryPage`

### 7.4 地图页常驻信息

地图页至少常驻三类摘要：

1. 玩家状态
2. 路线信息
3. 最近节点结果摘要

### 7.5 节点页常驻信息

战斗节点建议展示：

- 敌人名或代号
- 危险等级
- 风险提示
- 推荐动作
- 自由意图输入框
- 可能的重要代价提示

事件节点建议展示：

- 事件标题/概述
- 可选项
- 是否支持补充说明
- 可能影响的资源或状态提示

### 7.6 本地存档入口

首版即提供：

- 继续未完成挑战
- 查看最近挑战
- 删除本地挑战
- 查看本地解锁摘要

## 8. 存档、快照与裁定数据流

### 8.1 存档对象

本地至少维护：

1. `challengeRecord`
2. `challengeNodeRecord`
3. `challengeCheckpoint`
4. `challengeUnlockRecord`

### 8.2 玩家快照冻结

挑战开始时生成并冻结 `playerSnapshot`。

它不等于原始角色卡，而是本轮挑战专用的竞技场化投影。

挑战内所有判定只读取：

- `playerSnapshot`
- `runState`

不直接回读原始角色卡。

### 8.3 敌人快照冻结

任何被抽入挑战的敌人，一旦进入节点，也必须先冻结为统一 `enemySnapshot`。

### 8.4 裁定数据流

建议严格按以下顺序：

1. 读取 `challengeRecord`
2. 读取当前节点与 `encounterTemplate`
3. 汇总玩家快照、敌人快照、当前状态、资源与动作候选
4. 接收玩家输入
5. resolver 生成 `resolverEnvelope`
6. AI 基于 envelope 产出结构化裁定结果与战报
7. 系统校验结构化结果是否合法
8. 写回节点记录、checkpoint 与挑战主记录

### 8.5 `resolverEnvelope`

这是系统与 AI 的边界层，至少定义：

- 允许的胜负集合
- 允许的损伤区间
- 允许的资源消耗范围
- 允许的特殊状态
- 不允许发生的结果
- 推荐结果倾向

AI 不直接创造结果边界，只在边界内落点并叙述。

### 8.6 中断恢复

建议恢复策略：

1. 若中断发生在节点结算前：
   - 回到上一个 checkpoint
2. 若发生在 AI 裁定后、写盘前：
   - 丢弃未提交结果，回到节点入口
3. 若写盘已完成：
   - 直接恢复到最新 checkpoint

### 8.7 存储技术选择

首版直接使用 IndexedDB，不采用 `localStorage` 顶替挑战主存档。

`localStorage` 仅继续承担：

- UI 偏好
- 轻量筛选状态
- 最近选择

## 9. 验证、测试与实现拆分

### 9.1 首版要验证的核心问题

只聚焦 4 个问题：

1. 任意角色是否能顺畅开始挑战
2. 路径选择是否真的有规划价值
3. 系统约束下的 AI 裁定是否稳定
4. 失败是否既有张力又不显得白跑

### 9.2 推荐实现顺序

建议按以下顺序推进：

1. 世界与挑战骨架
2. 角色与敌人快照
3. 无 AI 的占位结算
4. 接入 AI 裁定
5. 失败结算与长期解锁

### 9.3 测试层次

建议至少覆盖：

1. schema / mapper 测试
2. resolver 测试
3. storage 测试
4. UI 主流程测试

### 9.4 推荐实现阶段

#### Phase 1：数据骨架

- world preset
- challenge schema
- IndexedDB stores
- 地图生成

#### Phase 2：无 AI 可玩闭环

- 快照补全
- 敌人抽取
- resolver 占位结算
- 地图推进
- 挑战结束

#### Phase 3：AI 节点裁定

- 战斗节点 AI 裁定
- 事件节点 AI 裁定
- 失败战报与总结

#### Phase 4：打磨

- 解锁记录
- 继续挑战入口
- 更多事件/敌人池
- UI 体验整理

### 9.5 成功标准

若上线前满足以下条件，即可视为首版成立：

1. 能从任意角色卡开始一轮竞技场挑战
2. 能完整跑完一轮挑战
3. 普通/精英/Boss 强度分层基本成立
4. AI 裁定能稳定产出可接受的战斗与事件结果
5. 本地存档、继续挑战、失败结算可用

## 10. 与现有仓库关系

本设计优先复用：

1. `/creator` 角色参数与 build rule 体系
2. 竞技场与连续战报已有的 AI 提示链路经验
3. 现有 IndexedDB 存储经验
4. 公开数据卡库
5. 排行榜与赛季快照数据

但首版不直接要求：

1. 把挑战状态写回原始角色卡
2. 把挑战系统硬并入普通竞技场页
3. 与线上数据库实时双向同步挑战进度
