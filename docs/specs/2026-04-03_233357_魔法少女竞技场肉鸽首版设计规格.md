# 魔法少女竞技场肉鸽首版设计规格

日期：2026-04-03 23:33:57
范围：定义“魔法少女竞技场”作为首发世界的本地路径式叙事肉鸽 MVP，并同时定义未来多世界扩展所需的稳定接口与覆写点，但不展开第二世界的具体玩法设计。
参考依据：`docs/reports/2026-04-03_193555_肉鸽玩法调研与基础方案建议.md`

---

## 1. 设计目标

本轮设计目标是做出一个可直接进入后续计划拆分的首版规格，解决以下问题：

1. 在当前项目内，为“路径式叙事肉鸽”确定首发世界、首版范围与非目标。
2. 在不把结构写死在竞技场语义里的前提下，定义未来多世界扩展需要的稳定接口。
3. 明确“系统约束下的 AI 裁定”如何用于战斗与事件，而不是退回纯数值硬算，也不是放任纯 AI 放飞。
4. 明确本地存档、挑战快照、敌人来源、UI 主流程与验证边界。

---

## 2. 结论先行

首版产品定位收敛为：

> 在本地浏览器中运行的、以魔法少女竞技场为首发世界的路径式叙事肉鸽 MVP。

用户界面文案中，`run` 统一翻译为：

- `挑战`
- 需要更完整语气时使用 `本轮挑战`

系统内部、代码与 schema 仍保留 `run` 语义，不强行中文化内部命名。

---

## 3. 范围与非目标

### 3.1 首版范围

首版明确包含：

1. 只实现 `1` 个世界：
   - `魔法少女竞技场`
2. 只实现 `1` 套完整可玩的挑战循环：
   - 进入世界
   - 选择角色
   - 生成竞技场快照
   - 跑图
   - 结算节点
   - 通关或失败
3. 挑战长度按“已访问节点数”定义。
   - 稳定接口支持未来世界扩展到 `8-12` 个已访问节点
   - 竞技场世界首版默认固定为 `8` 个已访问节点（含 Boss，不含虚拟起点）
4. 节点类型固定为：
   - 普通战斗
   - 精英战斗
   - 事件
   - 休整
   - 商店
   - Boss
5. 允许任意角色卡进入挑战。
6. 开局自动补全并冻结一份“竞技场战斗快照”。
7. 地图整张基本公开，但节点细节半隐藏。
8. 战斗采用“系统约束下的 AI 裁定”，不做细回合制。
9. 事件采用分级输入模式，默认 `choice-plus-note`。
10. 存档只保存在本地浏览器 IndexedDB。
11. 默认失败语义为：
   - 失败即结束挑战
   - 生成失败战报
   - 给予少量长期内容型收益

### 3.2 首版非目标

首版明确不做：

1. 第二世界的具体玩法设计与实现。
2. 完整 deckbuilder 或细回合制战斗系统。
3. 完整小队制玩法。
4. 云存档、跨设备同步、线上挑战持久化。
5. 强永久数值成长。
6. 开局快照的完整手工编辑器。
7. 由 AI 动态生成世界预设、动作池或事件池。
8. 多世界平衡与统一内容平台。

### 3.3 多世界接口边界

本规格会定义未来多世界扩展所需的：

1. schema
2. resolver 插槽
3. UI 扩展点
4. world override points

但不会定义：

1. 第二世界的具体内容池
2. 第二世界的具体 UI
3. 第二世界的具体数值与平衡参数

---

## 4. 方案选择

### 4.1 不选“纯数值硬算”

若战斗和事件都采用纯数值硬算：

- 会过度削弱项目已有的“角色设定 + 用户意图 + AI 演出”特色
- 很容易把玩法滑向普通规则引擎
- 无法充分利用现有竞技场战报资产

### 4.2 不选“纯 AI 自由生成”

若完全交给 AI 判定胜负、掉血、掉落与状态变化：

- 长期一致性难控
- 平衡难以验证
- 存档恢复与后续扩展都会变得脆弱

### 4.3 采用“系统约束下的 AI 裁定”

首版采用：

1. 系统先生成合法结果带宽
2. AI 在带宽内生成结构化裁定结果与战报
3. 系统校验结果是否合法后写回状态

这是当前项目最稳妥、也最能发挥特色的方案。

## 5. 稳定接口设计

本节定义未来多世界共用的稳定对象，不写竞技场专属参数。

### 5.1 `worldPreset`

定义一个世界如何运行，至少包含：

- `id`
- `title`
- `resourceModel`
- `mapProfile`
- `nodeGenerationRules`
- `actionCatalogs`
- `eventCatalogs`
- `enemySourcePolicy`
- `failurePolicy`
- `aiPromptPack`

职责：

- 声明“这个世界里的挑战如何构成”
- 不是只提供一层文案皮肤

### 5.2 `runState`

定义一轮挑战的当前真相，至少包含：

- `runId`
- `worldPresetId`
- `seed`
- `playerSnapshot`
- `resources`
- `statuses`
- `inventory`
- `relics`
- `skillProgress`
- `currentNodeId`
- `mapState`
- `historyDigest`
- `failureState`
- `startedAt`
- `updatedAt`

职责：

- 所有节点判定都以 `runState` 为准
- 不直接回头读取原始角色卡

### 5.3 `mapNode`

定义地图节点，至少包含：

- `nodeId`
- `layer`
- `nodeType`
- `visibility`
- `riskHint`
- `rewardHint`
- `encounterRef`

职责：

- 支持“整图公开、细节半隐藏”的默认规则

### 5.4 `encounterTemplate`

统一描述战斗、事件、休整、商店、Boss 等节点，至少包含：

- `templateId`
- `kind`
- `inputMode`
- `requirements`
- `actionOverrides`
- `rewardProfile`
- `aiContextPack`

### 5.5 `actionDefinition`

定义玩家在节点里可采取的动作，至少包含：

- `actionId`
- `label`
- `source`
- `intentType`
- `requirements`
- `riskTag`
- `aiHint`

其中 `source` 至少支持：

- `world`
- `encounter`
- `character`
- `free-intent-derived`

### 5.6 `enemySnapshot`

定义敌人在本次挑战中的冻结快照，至少包含：

- `sourceType`
- `sourceId`
- `displayName`
- `strengthTier`
- `combatProfile`
- `tags`
- `promptSummary`

职责：

- 不管敌人来源于预设、公开库还是排行，一旦进入挑战，都必须先冻结为统一快照

### 5.7 `saveModel`

定义本地存档结构，至少拆成：

1. `run record`
2. `node records`
3. `checkpoints`
4. `unlock records`

### 5.8 世界覆写点

未来世界允许覆写：

1. 资源模型
2. 地图节点权重
3. 动作池
4. 事件池与默认 `inputMode`
5. 敌人来源策略
6. 失败语义
7. AI 风格包

### 5.9 首版字段级接口草案

以下接口以 TypeScript 语义表达首版最小闭包，供后续实施计划直接拆分。

## 6. 魔法少女竞技场世界 MVP 实例化

### 6.1 世界定位

竞技场世界首版是：

- 一轮连续挑战
- 以战斗节点为主
- 以强敌遭遇、战后成长、事件变化和战报生成推动节奏

它不是：

- 传统 deckbuilder
- 细回合制 RPG
- 单次普通竞技场战报的简单外壳

### 6.2 玩家入口

玩家可从任意角色卡开始挑战。

开局时系统生成“竞技场战斗快照”：

1. 若角色已有 `buildState / 角色参数`，优先复用
2. 若没有，则按下列信号自动补全：
   - 角色文本设定
   - 标签
   - `powerLevel` 或强度描述
   - 公开排位信息（若有）
   - 世界默认模板

补全后的竞技场快照在本轮挑战内冻结，不回写原始角色卡。

此阶段只有在玩家接受快照后，系统才生成正式 `runSeed` 与地图；在此之前只存在 `snapshotSeed`。

### 6.3 开局补全交互

开局不采用：

- 完全静默生成
- 完整手工微调

首版采用：

1. 生成竞技场快照摘要
2. 展示给玩家
3. 玩家可：
   - 接受并开始挑战
   - 免费重掷一次
4. 不开放逐字段编辑

“免费重掷一次”的精确定义如下：

1. 每轮新挑战仅限 `1` 次
2. 仅发生在 `bootstrapping` 阶段
3. 重掷只替换 `snapshotSeed` 并重生成：
   - 玩家竞技场快照
   - 初始推荐动作倾向
4. 地图与正式 `runSeed` 在玩家接受快照前不会生成
5. 首版不保留前一版快照做对比或回退
6. 玩家一旦接受快照，`usedBootstrapReroll` 固化写入 challenge record

摘要建议展示：

- 力量层级
- 战斗定位
- 关键属性倾向
- 关键动作倾向
- 初始风险/稳定性提示

### 6.4 资源模型

竞技场世界首版资源建议收敛为：

- 规范化 HP：`hpCurrent/hpMax`，整数范围 `0-100`
- 规范化光辉：`radianceCurrent/radianceMax`，整数范围 `0-100`
- 货币：`currency`，整数范围 `0-999`
- 消耗品：`consumableIds`，首版上限 `3`
- 遗物：`relicIds`，首版上限 `3`
- 临时状态：`temporaryStatuses`
- 运行标记：`runFlags`

外显层主要显示：

- `完好 / 受创 / 重伤 / 濒危`
- 关键资源变化

不显示逐回合精细扣血流水。

HP 外显状态层级固定为：

- `76-100`: 完好
- `51-75`: 受创
- `26-50`: 重伤
- `1-25`: 濒危
- `0`: 败北

首版允许的临时状态集合固定为：

- 正向：`steady`、`empowered`
- 负向：`shaken`、`exposed`、`fatigued`

`runFlags` 在首版中定义为 `string[]`，只承载世界内的离散进度标记，不承载数值成长。

首版允许写入的 `runFlags` 仅限“对后续节点有条件影响”的标记，例如：

- `preset_only_enemy_mode`
- `elite_defeated`
- `boss_gate_unlocked`

### 6.5 地图与节点

默认挑战规模：

- 竞技场世界首版默认 `8` 个已访问节点（含 Boss，不含虚拟起点）
- `1` 个最终 Boss
- 稳定接口允许未来世界扩展到 `8-12`

地图拓扑规则：

1. 使用虚拟起点 `S`，不计入已访问节点数
2. 首版固定为 `8` 层可访问层：
   - `L1-L6`: 常规层
   - `L7`: Boss 前层
   - `L8`: Boss 层
3. 节点生成数量固定为：
   - `L1-L6`: 每层 `2` 个候选节点
   - `L7`: `1` 个节点
   - `L8`: `1` 个 Boss 节点
4. 总图节点数（不含虚拟起点）固定为 `14`
5. 连线约束：
   - 仅允许连接到下一层
   - 不允许跳层
   - `L1-L5` 内至少出现 `1` 次分叉与 `1` 次合流
   - `L8` Boss 节点接受来自 `L7` 的全部入边

节点类型配比固定为：

1. `Boss`: 恰好 `1` 个，固定在 `L8`
2. `Elite`: 恰好 `1` 个，固定在 `L6` 或 `L7`
3. `Rest`: 恰好 `1` 个，固定在 `L3-L5`
4. `Shop`: 恰好 `1` 个，固定在 `L3-L6`
5. `Event`: 恰好 `2` 个，分布于 `L1-L6`
6. 其余节点为 `Battle`

地图可见性：

- 整张图基本公开
- 节点细节半隐藏

公开：

- 拓扑
- 节点类型
- 精英/Boss 分布
- 风险/收益倾向

不完全公开：

- 敌人具体身份
- 事件正文
- 商店详细售卖内容
- 奖励精确落点

可见性状态机固定为：

1. `summary`
   - 所有未到达节点的默认状态
   - 只显示：节点类型、层数、粗风险/收益提示、拓扑连线
2. `focused`
   - 当前节点的后续两层节点进入该状态
   - 额外显示：更强的风险提示、强度档提示或事件倾向提示
3. `resolved`
   - 玩家实际完成的节点
   - 显示节点结算结果与摘要

进入节点瞬间，系统才揭示本场具体 `enemySnapshot`、事件标题、商店库存或奖励选项。

### 6.5.a 地图承载与持久化策略

首版地图图结构以 `MapStateV1` 承载：

- `nodes: MapNodeV1[]` 保存 `14` 个正式节点的静态定义与当前可见性
- `edges: MapEdgeV1[]` 以显式有向边保存拓扑，只允许 `fromNodeId -> toNodeId` 的跨一层连接
- `rootNodeId` 固定指向虚拟起点 `S`

首版额外硬规则为：

1. `MapEdgeV1.fromNodeId` 允许等于 `S`，且仅允许出现在起始出边
2. `MapEdgeV1.toNodeId` 不允许等于 `S`
3. `MapStateV1.totalLayers = 8`，只统计 `L1-L8`，不含虚拟起点层

持久化策略固定为：

1. 玩家接受 bootstrap 快照后，客户端生成正式 `runSeed`
2. 由 `runSeed + worldPresetId` 一次性生成完整 `MapStateV1`
3. 生成后的 `mapState` 立即写入 `challenge_runs.runState.mapState`
4. 之后恢复挑战时，优先读取已持久化的 `mapState`，不依赖重新推导
5. `runSeed` 仍保留，用于调试、复核与必要时的只读重建比对，但不是恢复的唯一真相来源

### 6.6 节点类型分工

1. 普通战斗
  - 主体节奏节点
2. 精英战斗
   - 高风险高收益节点
3. 事件
   - 节奏变化与分支节点
4. 休整
   - 修复与资源整理
5. 商店
  - 结构化资源交换
6. Boss
  - 本轮挑战终局节点

### 6.6.a 首版节点结算矩阵

#### 战斗 / 精英 / Boss

- 输入模式：`recommended-action-plus-free-intent`
- 是否走 AI：是
- 是否生成 `resolverEnvelope`：是
- 允许修改的 `runState` 字段：
  - `status`
  - `resources.hpCurrent`
  - `resources.radianceCurrent`
  - `resources.currency`
  - `temporaryStatuses`
  - `pendingRewardChoice`
  - `currentNodeId`
  - `visitedNodeCount`
- 说明：
  - `consumableIds / relicIds` 不由裁定结果直接写入，只能通过奖励应用阶段修改

#### 事件

- 输入模式：
  - 模板显式指定 `choice-only / choice-plus-note / free-intent`
- 是否走 AI：
  - `choice-only`：否，走纯系统结算
  - `choice-plus-note / free-intent`：是
- 是否生成 `resolverEnvelope`：
  - `choice-only`：否
  - `choice-plus-note / free-intent`：是
- 允许修改的 `runState` 字段：
  - `status`
  - `resources.hpCurrent`
  - `resources.radianceCurrent`
  - `resources.currency`
  - `temporaryStatuses`
  - `pendingRewardChoice`
  - `currentNodeId`
  - `visitedNodeCount`
- 说明：
  - 纯系统事件通过 `encounterSnapshot.eventOptions[].effectPatch` 直接结算
  - AI 事件沿用同一结构化输出契约，其中 `victory / costly_victory / defeat` 分别解释为“顺利解决 / 付出代价解决 / 处理失手”
  - `consumableIds / relicIds` 若要改动，仍只通过奖励应用阶段完成

#### 休整

- 输入模式：`choice-only`
- 是否走 AI：否
- 是否生成 `resolverEnvelope`：否
- 节点入场时固定给出 `3` 个系统选项：
  1. 静养：`hpCurrent +20`，封顶 `hpMax`
  2. 调律：`radianceCurrent +20`，封顶 `radianceMax`
  3. 稳态整理：按 `fatigued > exposed > shaken` 的固定优先级移除 `1` 个负面状态；若当前没有负面状态则该选项禁用
- 允许修改的 `runState` 字段：
  - `status`
  - `resources.hpCurrent`
  - `resources.radianceCurrent`
  - `temporaryStatuses`
  - `currentNodeId`
  - `visitedNodeCount`

#### 商店

- 输入模式：`choice-only`
- 是否走 AI：否
- 是否生成 `resolverEnvelope`：否
- 节点入场时生成 `3` 个手工配置来源的商店货品，并冻结到 `encounterSnapshot.shopOffers`
- 首版规则固定为：
  - 每个货品带明确价格
  - 玩家可选择购买 `0` 或 `1` 个后离开
  - 仅当 `currency >= price` 时允许购买
  - 若对应背包/遗物槽已满，则该货品在本次商店中禁用
  - 商店货品的 `reward.kind` 仅允许：`add_consumable / add_relic / add_status / clear_negative_status`
  - 首版商店不直接售卖 `heal_hp / heal_radiance / gain_currency` 类资源改写货品
- 允许修改的 `runState` 字段：
  - `status`
  - `resources.currency`
  - `consumableIds`
  - `relicIds`
  - `temporaryStatuses`
  - `currentNodeId`
  - `visitedNodeCount`

### 6.6.b `runFlags` 写入规则

首版 `runFlags` 不进入 AI 结构化输出契约。

`runFlags` 只允许由系统 progression layer 写入，固定写入点如下：

1. 挑战初始化完成且敌人来源已降级为本地预设模式时：
   - 写入 `preset_only_enemy_mode`
2. 精英节点以 `victory` 或 `costly_victory` 结算后：
   - 写入 `elite_defeated`
3. 当 `elite_defeated` 已存在且玩家推进到 `L7` 或更后层时：
   - 写入 `boss_gate_unlocked`

首版不允许：

- AI 直接输出 `runFlagsDelta`
- 事件模板直接写任意自定义 flag
- 同一 flag 在单轮挑战中被反复加删

### 6.6.c `choice-only` 事件的 `EffectPatchV1` 规则

首版 `choice-only` 事件不走 AI，也不走 `resolverEnvelope`，只执行 `encounterSnapshot.eventOptions[].effectPatch`。

`EffectPatchV1` 的执行语义固定为：

1. `hpDelta / radianceDelta / currencyDelta`
   - 分别修改 `resources.hpCurrent / resources.radianceCurrent / resources.currency`
   - clamp 规则与战斗/奖励结算保持一致
2. `addStatuses / removeStatuses`
   - 仅允许操作首版白名单内的 `TemporaryStatus`
3. `rewardSelectionMode / rewardOptionIds`
   - 仅允许引用当前节点 `encounterSnapshot.rewardOptions`
   - `none / auto / choose-one` 的长度规则与 6.8.b 完全一致
4. 不允许直接修改：
   - `relicIds`
   - `consumableIds`
   - `runFlags`

若 `choice-only` 事件需要发放遗物、消耗品或状态型收益，必须通过 `rewardOptionIds` 进入后续奖励应用流程，而不是在 effect patch 内直接写值。

### 6.7 敌人来源策略

#### 普通敌人

普通敌人不以公开库纯随机作为主来源。

首版主来源应为：

1. 当前 / 历史赛季的低中位公开角色段
2. 本地预设角色池补位
3. 公开库随机作为补充与兜底

理由：

- 强度更稳定
- 不容易在普通战斗里直接抽出榜首角色
- 更适合做分带控制

#### 精英敌人

精英敌人建议来自：

1. 当前赛季中高位角色段
2. 手工标记的高压预设角色

#### Boss

Boss 建议来自：

1. 当前或历史赛季高位代表角色
2. 竞技场代表性预设角色

#### 强度分层

首版先粗分为：

- `common`
- `elite`
- `boss`

预设角色若自带明显强度描述或 `powerLevel` 描述，可作为强度映射参考。

#### 降级与兜底策略

由于挑战存档在本地浏览器，但敌人来源可能依赖在线接口，因此首版必须定义降级路径：

1. 普通/精英/Boss 候选池的解析顺序：
   - 优先：在线 leaderboard / data-card-meta / public-data-cards 接口
   - 次优：静态赛季归档文件（如 `public/data/seasons/archive_*.json`）
   - 最后：本地预设角色池
2. 若在线来源不可用：
   - 当前挑战直接切换为 `preset-only` 敌人来源模式
   - 该模式对整轮挑战保持稳定，不中途来回切换
3. 若某个候选角色详情读取失败或不再公开：
   - 在同强度档内重抽，最多 `3` 次
   - 超过后回退到同强度档的本地预设角色
4. 预设池必须按 `common / elite / boss` 三档预先手工分层，不能临时硬猜

### 6.8 战斗流程

战斗节点默认流程：

1. 读取本场 `enemySnapshot`
2. 生成推荐动作
3. 玩家可：
   - 选择推荐动作
   - 输入一句自由战术意图
   - 或两者结合
4. resolver 先生成 `resolverEnvelope`
5. AI 在 envelope 内产出：
   - 胜负
   - 损伤
   - 资源消耗
   - 特殊后果
   - 战报文本
6. 系统校验结果是否合法
7. 写回 `runState`
8. 发奖励并进入下一节点

首版不处理：

- 逐回合行动顺序
- 精确逐击扣血
- 复杂技能 CD

### 6.8.a `resolverEnvelope` 与资源带宽对齐

为避免 AI 输出与资源系统脱节，首版 battle resolver 必须产出如下 envelope：

```ts
interface ResolverEnvelopeV1 {
  outcomeSet: Array<'victory' | 'costly_victory' | 'defeat'>;
  recommendedOutcome: 'victory' | 'costly_victory' | 'defeat';
  hpDeltaRange: { min: number; max: number };          // 负数表示损失
  radianceDeltaRange: { min: number; max: number };    // 负数表示损失
  currencyDeltaRange: { min: number; max: number };
  allowedAddStatuses: TemporaryStatus[];
  allowedRemoveStatuses: TemporaryStatus[];
  rewardSelectionMode: RewardSelectionModeV1;
  rewardOptionIds: string[];
  forbiddenFlags: Array<'one_shot' | 'full_heal' | 'free_relic' | 'out_of_band_status'>;
}
```

首版校验规则固定为：

1. AI 输出的 `hpDelta`、`radianceDelta`、`currencyDelta` 必须落在 envelope 区间内
2. AI 输出的新增/移除状态必须属于 allowlist
3. AI 不得生成 envelope 外的奖励
4. 若输出违反 envelope：
   - 首次自动重裁定一次
   - 再失败则降级为系统模板结算文本

### 6.8.b 奖励选项模型与应用规则

`rewardOptionIds` 引用 `RewardOptionV1.rewardOptionId`。首版奖励只允许以下类型：

- `heal_hp`
- `heal_radiance`
- `gain_currency`
- `add_consumable`
- `add_relic`
- `add_status`
- `clear_negative_status`

首版奖励选择模式固定为：

1. `none`
   - `rewardOptionIds` 必须为空
2. `auto`
   - `rewardOptionIds` 必须恰好为 `1`
   - 节点裁定通过后自动应用该奖励
3. `choose-one`
   - `rewardOptionIds` 必须恰好为 `2`
   - 节点先完成裁定，再由玩家二选一
   - 首版不支持多选，不支持超过 `2` 选 `1`

奖励选项实例的来源与持久化规则固定为：

1. 节点进入时，系统生成该节点的 `EncounterSnapshotV1`
2. 若该节点存在奖励分支，则对应的 `RewardOptionV1[]` 必须直接写入 `encounterSnapshot.rewardOptions`
3. `resolverEnvelope.rewardOptionIds` 只能引用当前节点 `encounterSnapshot.rewardOptions` 中已冻结的选项
4. UI 展示奖励标题、效果摘要与后续选择时，一律以 `challenge_nodes.encounterSnapshot.rewardOptions` 为准，不回查世界级动态 catalog
5. 中断恢复后，奖励选择也继续读取该节点已落库的 `encounterSnapshot.rewardOptions`

各奖励类型的写回规则固定为：

1. `heal_hp`
   - `resources.hpCurrent = clamp(hpCurrent + amount, 0, hpMax)`
2. `heal_radiance`
   - `resources.radianceCurrent = clamp(radianceCurrent + amount, 0, radianceMax)`
3. `gain_currency`
   - `resources.currency = clamp(currency + amount, 0, 999)`
4. `add_consumable`
   - 当 `consumableIds.length < 3` 时追加唯一 `itemId`
   - 若背包已满，该选项视为非法，不得出现在 envelope 中
5. `add_relic`
   - 当 `relicIds.length < 3` 时追加唯一 `itemId`
   - 若遗物槽已满，该选项视为非法，不得出现在 envelope 中
6. `add_status`
   - 仅当该状态当前不存在时加入 `temporaryStatuses`
7. `clear_negative_status`
   - 若 `payload.statusId` 存在，则只移除该负面状态
   - 若未指定，则按 `fatigued > exposed > shaken` 的固定优先级移除首个可移除目标

奖励应用完成后，必须写入一次 `reward_applied` checkpoint。

### 6.9 事件输入模式

事件节点采用分级输入模式。

支持三档：

1. `choice-only`
2. `choice-plus-note`
3. `free-intent`

首版默认：

- 全局默认 `choice-plus-note`
- 简单事件显式写为 `choice-only`
- 少数关键事件使用 `free-intent`

### 6.10 默认失败语义

首版默认：

- 失败即结束挑战
- 生成失败战报
- 给予少量内容型长期收益

未来允许竞技场世界扩展特殊败北分支，但不纳入首版核心。

### 6.11 长期成长方向

首版长期成长以内容解锁为主：

- 图鉴
- 事件解锁
- 敌人记录
- 起始动作候选
- 起始物候选
- 特殊路线或文案解锁

不建议首版做强永久数值成长。

### 6.11.a MVP 解锁闭包

为使“失败也有收益”具备可实现的最小闭包，首版必须落地以下解锁类型：

1. `enemy-log`
   - 首次完成与某个唯一敌人来源键的遭遇时解锁
2. `event-log`
   - 首次完成某个唯一事件模板时解锁
3. `start-action-option`
   - 固定解锁 `2` 个候选：
     - 首次失败一轮挑战时解锁 `1` 个
     - 首次击败精英时解锁 `1` 个
4. `start-relic-option`
   - 首次完成整轮挑战时解锁 `1` 个固定候选

首版不做：

- 永久加 HP
- 永久加伤害
- 无限堆叠式长期属性成长

挑战结算页必须展示“本轮新解锁”列表；本地解锁页必须能展示以上四类内容。

## 8. 存档、快照与裁定数据流

### 8.1 存档对象

本地至少维护：

1. `challengeRecord`
2. `challengeNodeRecord`
3. `challengeCheckpoint`
4. `challengeUnlockRecord`

首版 IndexedDB store 与索引要求如下：

#### `challenge_runs`

- `keyPath`: `id`
- 索引：
  - `by_status_updatedAt`: `[status, updatedAt]`
  - `by_world_startedAt`: `[worldPresetId, startedAt]`

最小字段：

- `id`
- `worldPresetId`
- `status`
- `snapshotSeed`
- `runSeed`
- `usedBootstrapReroll`
- `playerSnapshot`
- `runState`
- `currentStateDigest`
- `currentNodeId`
- `visitedNodeCount`
- `lastResolvedNodeId`
- `lastCheckpointId`
- `startedAt`
- `updatedAt`
- `finishedAt`

#### `challenge_nodes`

- `keyPath`: `id`
- 索引：
  - `by_run_visitIndex`: `[runId, visitIndex]`（唯一）
  - `by_run_createdAt`: `[runId, createdAt]`

最小字段：

- `id`
- `runId`
- `nodeId`
- `visitIndex`
- `nodeType`
- `status`（`entered | resolved`）
- `encounterSnapshot`（最少为 `EncounterSnapshotV1`，并按节点类型冻结 `rewardOptions / eventOptions / shopOffers`）
- `playerInput`
- `resolverEnvelope`（AI 裁定节点必填，纯系统节点为 `null`）
- `adjudicationResultDigest`
- `storyText`
- `createdAt`
- `resolvedAt`

#### `challenge_checkpoints`

- `keyPath`: `id`
- 索引：
  - `by_run_seq`: `[runId, seq]`（唯一）
  - `by_run_kind_createdAt`: `[runId, kind, createdAt]`

最小字段：

- `id`
- `runId`
- `seq`
- `kind`
  - `bootstrap_accepted`
  - `node_resolved`
  - `reward_applied`
  - `finished`
- `snapshot`
  - 至少包含：`runState`、`playerSnapshot`、`lastResolvedNodeId`
- `createdAt`

#### `challenge_unlocks`

- `keyPath`: `id`
- 索引：
  - `by_world_createdAt`: `[worldPresetId, createdAt]`
  - `by_unlock_key`: `[worldPresetId, unlockType, unlockKey]`（唯一）
  - `by_run_createdAt`: `[runId, createdAt]`

最小字段：

- `id`
- `worldPresetId`
- `runId`
- `unlockType`
- `unlockKey`
- `title`
- `description`
- `sourceNodeId`
- `createdAt`

### 8.1.a 地图持久化与 checkpoint 快照

首版地图持久化策略固定为“生成一次，持久化一次”：

1. `bootstrap_accepted` 时生成正式 `runSeed`
2. 同步生成完整 `MapStateV1`
3. 将完整 `runState` 写入 `challenge_runs.runState`
4. 其中 `runState.mapState` 作为当前挑战地图的唯一可恢复真相
5. `runSeed` 仅作为重建校验依据，不作为恢复时的必需输入

`challenge_checkpoints.snapshot` 的最小结构固定为：

- `runState`
- `playerSnapshot`
- `lastResolvedNodeId`
- `pendingRewardChoice`

其中：

1. `runState.mapState` 是 checkpoint 内唯一权威的地图快照
2. checkpoint 不再平行单列 `mapState`
3. 恢复逻辑与一致性测试一律以 `snapshot.runState.mapState` 为准

恢复流程一律优先读取最新 checkpoint，其次再回退 `challenge_runs.runState`。

### 8.2 玩家快照冻结

挑战开始时生成并冻结 `playerSnapshot`。

它不等于原始角色卡，而是本轮挑战专用的竞技场化投影。

挑战内所有判定只读取：

- `playerSnapshot`
- `runState`

不直接回读原始角色卡。

### 8.3 敌人快照冻结

任何被抽入挑战的敌人，一旦进入节点，也必须先冻结为统一 `enemySnapshot`。

### 8.4 裁定数据流

建议严格按以下顺序：

1. 读取 `challengeRecord`
2. 读取当前节点与 `encounterTemplate`
3. 汇总玩家快照、敌人快照、当前状态、资源与动作候选
4. 接收玩家输入
5. resolver 生成 `resolverEnvelope`
6. AI 基于 envelope 产出结构化裁定结果与战报
7. 系统校验结构化结果是否合法
8. 写回节点记录、checkpoint 与挑战主记录

### 8.5 `resolverEnvelope`

这是系统与 AI 的边界层，至少定义：

- 允许的胜负集合
- 允许的损伤区间
- 允许的资源消耗范围
- 允许的特殊状态
- 不允许发生的结果
- 推荐结果倾向

AI 不直接创造结果边界，只在边界内落点并叙述。

首版仅 `battle / elite / boss` 与需要 AI 的 `event` 节点生成 `resolverEnvelope`；`rest / shop / choice-only event` 直接走系统 effect patch，不生成 envelope。

### 8.5.a AI 结构化输出契约

首版战斗/事件裁定的 AI 输出必须可被解析为结构化 JSON。最小契约如下：

```ts
interface AdjudicationResultV1 {
  outcome: 'victory' | 'costly_victory' | 'defeat';
  hpDelta: number;
  radianceDelta: number;
  currencyDelta: number;
  addStatuses: TemporaryStatus[];
  removeStatuses: TemporaryStatus[];
  rewardOptionId: string | null;  // `choose-one` 模式下固定为 null，等待玩家选择
  summary: string;        // 1-2 句短摘要
  storyMarkdown: string;  // 节点正文
}
```

首版不定义 `runFlagsDelta`；所有 flag 改写都在 AI 结果校验通过后，由系统层按固定规则写入。

校验顺序固定为：

1. JSON 结构可解析
2. 枚举值合法
3. 数值落在 envelope 区间内
4. 状态与奖励落在 allowlist 内
5. `rewardSelectionMode = auto` 时，`rewardOptionId` 必须等于唯一候选奖励；其余模式下必须为 `null`
6. 通过后才允许写盘

### 8.6 中断恢复

建议恢复策略：

1. 若中断发生在节点结算前：
   - 回到上一个 checkpoint
2. 若发生在 AI 裁定后、写盘前：
   - 丢弃未提交结果，回到节点入口
3. 若写盘已完成：
   - 直接恢复到最新 checkpoint

### 8.7 存储技术选择

首版直接使用 IndexedDB，不采用 `localStorage` 顶替挑战主存档。

`localStorage` 仅继续承担：

- UI 偏好
- 轻量筛选状态
- 最近选择

## 8.8 执行边界

为便于后续按仓库现实约束拆任务，首版执行边界固定如下：

### 客户端负责

1. 世界选择与角色选择 UI
2. 本地 IndexedDB 挑战存档
3. 地图渲染与节点可见性状态机
4. bootstrap 快照确认与一次性重掷
5. 纯本地 map generation
6. 纯本地 resolver precheck / envelope 校验
7. 挑战恢复、继续挑战、本地解锁展示

### `pages/api/*` 负责

1. 需要数据库读能力的公开角色/排行/赛季数据查询
2. 敌人来源的远端候选归一化
3. AI prompt 构建与模型调用
4. 返回结构化裁定结果与战报文本

### 首版不做

1. 直接从客户端访问线上数据库
2. 在客户端执行模型调用密钥逻辑
3. 挑战进度的线上回写
4. 跨设备同步挑战存档

## 9. 验证、测试与实现拆分

### 9.1 首版要验证的核心问题

只聚焦 4 个问题：

1. 任意角色是否能顺畅开始挑战
2. 路径选择是否真的有规划价值
3. 系统约束下的 AI 裁定是否稳定
4. 失败是否既有张力又不显得白跑

### 9.2 推荐实现顺序

建议按以下顺序推进：

1. 世界与挑战骨架
2. 角色与敌人快照
3. 无 AI 的占位结算
4. 接入 AI 裁定
5. 失败结算与长期解锁

### 9.3 测试层次

建议至少覆盖：

1. schema / mapper 测试
2. resolver 测试
3. storage 测试
4. UI 主流程测试

### 9.4 推荐实现阶段

#### Phase 1：数据骨架

- world preset
- challenge schema
- IndexedDB stores
- 地图生成

#### Phase 2：无 AI 可玩闭环

- 快照补全
- 敌人抽取
- resolver 占位结算
- 地图推进
- 挑战结束

#### Phase 3：AI 节点裁定

- 战斗节点 AI 裁定
- 事件节点 AI 裁定
- 失败战报与总结

#### Phase 4：打磨

- 解锁记录
- 继续挑战入口
- 更多事件/敌人池
- UI 体验整理

### 9.5 成功标准

若上线前满足以下条件，即可视为首版成立：

1. 能从任意角色卡开始一轮竞技场挑战
2. 能完整跑完一轮挑战
3. 普通/精英/Boss 强度分层基本成立
4. AI 裁定能稳定产出可接受的战斗与事件结果
5. 本地存档、继续挑战、失败结算可用
