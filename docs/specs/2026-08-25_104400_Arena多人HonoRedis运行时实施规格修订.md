## 1. 规范语言

本文中的“必须 / MUST”“不得 / MUST NOT”“应 / SHOULD”“可以 / MAY”具有规范性，其解释遵循 RFC 2119 与 RFC 8174。

本文是 **增量规格修订**。未被本文明确覆盖的既有 Arena 多人业务、Proposal、安全、generation、排位和平台重整要求继续有效。

## 2. 优先级与被覆盖条款

### 2.1 Arena 多人 v1 规格

本文覆盖 `docs/specs/2026-08-21_arena-multiplayer-v1-spec.md` 中所有把以下实现作为 v1 强制条件的条款：

- `apps/arena-room` sidecar Worker；
- one-room-one-Durable-Object；
- Durable Object Hibernation；
- Durable Object SQLite/storage；
- Durable Object alarm；
- `apps/web -> apps/arena-room` Service Binding；
- Hono -> DO `GenerationBridge`；
- D1 directory 必须以 DO 为单房间 lifecycle truth；
- DO internal id / DO storage cleanup / DO migration 等实现专属要求。

尤其包括原规格 §10 中 DO-specific lifecycle/TTL 实现、§14、§15 中 Hibernation-specific 恢复说明、§17 中 DO authority 绑定、§18、§20 中 DO-specific security wording、§23/§24/§25 中 DO-specific 不变量/成本/原则。

以下业务语义 **不被覆盖**：

- 单一 Room Shared Config；
- member local working copy + Proposal；
- typed `expectedBase`；
- versioned DataCard ref；
- host-only authoritative generation；
- stable `generationRequestId`；
- host-local/provider secret isolation；
- membership 与 connection 分离；
- strict/collaborativeInfluence 规则；
- WebSocket 安全、消息限制、backpressure；
- generation final result 仍以既有权威持久层为准。

### 2.2 平台重整实施规格

- **Development Gate**：在用户可感知 blocker 已关闭、`apps/api` / `apps/web` 真实边界已激活后可以 `PASS`。允许在 `refactor/platform-rearchitecture` 的隔离工作树/功能分支、本地 CI 与非生产测试环境继续 B1–G，包括 RoomActor、Redis Room checkpoint、WebSocket、ticket、reconnect、多人 UI、Proposal 与 generation publisher；实现必须默认不改变生产公开能力。

## 3. Runtime contract

### ROOMRT-001 平台无关 core

Room Shared Config、Proposal、conflict、revision、epoch、snapshot、generation reservation 等业务语义 MUST 由平台无关 contract/pure logic 表达。

`packages/multiplayer-core` MUST NOT 导入：

- Hono；
- Node HTTP/WebSocket server；
- Redis client；
- Cloudflare Durable Object；
- Cloudflare binding；
- 环境变量或 server secret。

### ROOMRT-002 v1 主运行时

Arena 多人 v1 的 Room realtime MUST 首先由 `apps/api` / Hono 提供。

v1 MUST NOT 以实现以下内容作为上线前置条件：

- `apps/arena-room`；
- Durable Object；
- Hibernation；
- DO alarm；
- DO SQLite storage；
- 跨部署 GenerationBridge。

未来 adapter MAY 实现这些能力，但 MUST 复用同一 wire/domain contract。

### ROOMRT-003 单房间单写者

任一活动 `roomId` MUST 在任一时刻只有一个可改变 Room session authority 的 RoomActor/owner。

Room 创建 MUST 通过 server-owned creation entry 签发新的不可预测 `roomId`、`roomEpoch` 与服务端时间；通用
Room command 通道 MUST NOT 接受客户端选择这些标识的 `create`。客户端提供的 host/member 字段仍必须由
当前服务器鉴权上下文覆盖或验证，不得把“能提交 create JSON”解释为创建能力。

v1 初始部署 SHOULD 只有一个 room-capable Hono 实例。

在允许多个 room-capable 实例前，MUST 有经过故障测试的 ownership + fencing 方案，或迁移到能够天然提供单协调原子的 runtime。

普通 `SETNX` / sticky session / 短 TTL MUST NOT 单独作为该正确性证明。

## 4. Redis session store

### ROOMRT-004 checkpoint

Authority-changing control transition MUST 产生版本化 Redis Room checkpoint。

至少包括：

```text
schemaVersion
roomId
roomEpoch
revision
room metadata / lifecycle
members / roles
shared config
unresolved proposals
generation reservation / mirror
logical deadlines
updatedAt
```

首发 authority checkpoint 当前使用 `authorityStateVersion = 2`，把 host-offline / room-idle logical deadline 与
member authority sidecar 一起纳入 predecessor CAS。严格解析的 active v1 checkpoint 由 Redis adapter 使用 exact raw
compare-and-set + `KEEPTTL` 原位迁移；由于 v1 没有可证明的 presence 连续性，迁移后的 open Room 使用其可信
`lifecycle.updatedAt` 作为已到期 deadline，并在 recovery/lazy validation 时 fail closed。malformed、并发变化或迁移
结果不确定时 MUST NOT 伪装为可用 v2 state。

对于已经向客户端返回成功的以下操作，Redis checkpoint MUST 在 success ack 前完成，除非具体操作被规格明确标为 lossy：

- create/close；
- membership mutation；
- host publish；
- Proposal submit/resolve/withdraw；
- generation reservation；
- generation terminal mirror。

Authority-changing transition 的提交顺序 MUST 保持为：

```text
读取并验证当前 checkpoint / actor state
  -> 纯逻辑推导 next state
  -> 以 predecessor 条件提交 Redis checkpoint
  -> 提交成功后安装 actor next state
  -> success ack / broadcast
```

不得先向客户端确认成功、再异步补 checkpoint；也不得在 Redis 提交失败后继续把仅存在内存的 next state 宣称为已提交。

### ROOMRT-005 原子观察与条件写

Redis Room store MUST 提供可原子观察的 checkpoint 版本，并 MUST 防止 stale actor / restart recovery / 迟到 callback 无条件覆盖较新的 room incarnation。

首发 SHOULD 优先使用单一版本化 snapshot 或具有等价原子性的有限事务结构，而不是把一份 room state 分散为大量不能一致读取的 key。每次 authority-changing save MUST 带可验证的 predecessor 条件，至少覆盖当前 `roomEpoch` 与 `revision`（或等价 `checkpointVersion`）。

实现 MAY 使用 Redis `WATCH` + transaction、Lua CAS 或具有等价原子条件语义的机制；MUST NOT 仅以普通无条件 `SET` 覆盖当前 checkpoint。

CAS/precondition 冲突时：

- 当前 command MUST NOT 被伪装为成功；
- runtime MUST reload/reconcile 当前 checkpoint，或返回显式 conflict/recovery；
- 不得在未知外部副作用可能已经发生时盲目重放非幂等操作。

首发 `RedisRoomStore` 使用单一 versioned checkpoint envelope 与同一 Lua 内的完整 predecessor snapshot CAS。只有
runtime-neutral state machine 的真实 `applied` transition 能签发一次性 checkpoint receipt；receipt 一经发起 Redis
提交即消费，Redis timeout / unknown result 后不得复用它盲目重放。

为防止 checkpoint 经 `delete` 或 TTL 消失后，迟到 create receipt 在同一 `roomEpoch` 上复活已经结束的
incarnation，首发实现还为每个 `roomId` 保存独立负向 incarnation ledger：

- ledger 不随 checkpoint TTL 删除；这里的“持久”只表示没有 Redis key TTL，不把 Redis 提升为永久业务数据库；
- 已记录 `roomEpoch` 的 absent-create MUST 返回 conflict，未记录的新 `roomEpoch` MAY 显式建立新 incarnation；
- ledger 每个 `roomId` 最多记录 16 个 epoch；满额后该 `roomId` 的新 incarnation MUST fail closed，用户改用新 Room；
- ledger 是内部 Redis replay schema，不进入公开 Room wire、snapshot、广播或 D1 directory；
- Redis 数据整体丢失或连续性无法证明时，后续 RoomActor recovery MUST 终止旧 actor/receipt 并签发新
  `roomEpoch`，不得把空 Redis 当成同 epoch incarnation 可恢复的证据。

首发兼容读取会在严格解析 active v1 checkpoint 后补种其 epoch ledger；checkpoint 在读取与补种之间到期时，
补种脚本仍必须记录已验证旧 epoch 并让 load 返回 absent。这个 lazy bootstrap 不能证明从未被新 runtime 观察、
且已经到期的历史数据；因此 production activation 前若发现任何由旧 runtime 写入且未带 ledger 的 Room key，
MUST 停止激活并先执行可审计迁移。当前 Arena Room 尚未在 production 暴露或写入，没有此类 production 数据，
故本轮不执行 migration；不得把这一事实泛化为后续环境也无需迁移。

### ROOMRT-006 TTL

每个非 terminal Room checkpoint MUST 有 TTL/expiry 机制。

TTL MUST NOT 被解释为永久数据保留保证；Redis key 过期后 D1 directory 残留 MUST NOT 复活房间。

### ROOMRT-006A bounded Room incarnation / exact replay fence

同一 `roomEpoch` 内，为阻止旧 membership、Proposal、`generationRequestId`、`generationId` 或 generation attempt 复活，Room Authority MUST 保留足以进行精确判定的 replay fence；不得为了释放容量而在同一 Room incarnation 内静默遗忘或复用这些标识。

该状态同时 MUST 有界。首发实现 MAY 为 member authority history、terminal Proposal ID、generation history 与 collaborative provenance 设定内部 Room-incarnation 配额。达到配额时：

- 对应的新 authority-changing command MUST 以稳定 `capability-denied` 语义 fail closed；
- 已提交 checkpoint、既有 generation mirror 与 host `close` 能力 MUST 保持可用；
- runtime MUST 关闭当前 Room，并由用户显式创建新 Room / 新 `roomEpoch` 后恢复对应能力；
- 不得把 rollover 实现成同 epoch ledger 清空、ID 重用或旧 callback 可重新命中的隐式重置。

这些配额是 active Room incarnation 的安全/资源边界，不是公开 wire 的产品数量承诺。Redis TTL/expiry 结束 incarnation 后，旧 D1 directory 仍不得复活它。

### ROOMRT-007 Redis failure

Redis 不可用时，authority-changing command MUST fail closed 或返回明确 `degraded`/`503` 等价状态；不得继续只写内存却仍向客户端承诺正常可恢复成功。

临时 `story.delta` / presence MAY 在内存安全且 backpressure 有界时继续，但不得改变持久业务事实。

### ROOMRT-008 Redis 不是持久业务权威

即使 Redis 保存活跃 Room checkpoint，以下事实仍 MUST NOT 只存在 Redis：

- final generation record/artifact；
- rating；
- settlement；
- durable provenance；
- account/authorization；
- online card ownership；
- audit / governance facts。

`FLUSHALL` 或 VPS 丢失 MAY 终止 Room session，但 MUST NOT 改写上述事实。

## 5. Fan-out 与 replay

### ROOMRT-009 Pub/Sub

Redis Pub/Sub MAY 用于跨连接/跨实例实时 fan-out，但 MUST NOT 成为：

- Room state truth；
- durable event history；
- reconnect replay 的唯一来源。

客户端漏掉 Pub/Sub event 后 MUST 能通过 snapshot/resync 恢复。

v1 只有一个 room-capable Hono 实例时 SHOULD 直接使用 RoomActor 的有界内存 fan-out，不应为了预期未来扩容提前引入 Pub/Sub。只有出现真实跨进程消费者后才增加 Pub/Sub，并继续以 checkpoint/snapshot 为恢复基线。

### ROOMRT-010 Streams

Redis Streams 或等价 bounded log 只在存在真实 replay/跨实例需求时 MAY 引入。

v1 MUST NOT 为了预期未来扩展而要求无限 event sourcing。

story delta 不要求逐 chunk 持久化；final report MUST 从既有 authoritative generation storage 恢复。

## 6. Epoch、revision 与 reconnect

### ROOMRT-011 `roomEpoch`

`roomEpoch` MUST 标识 Room Authority incarnation，并充当 fencing boundary。

以下情况 MUST 使用新 epoch，除非实现能够严格证明旧 owner/callback 已不可能继续写：

- Hono RoomActor ownership 重建；
- Hono process restart 后重新加载 checkpoint；
- Room runtime failover；
- 灾难恢复/replace。

### ROOMRT-012 stale writer 拒绝

Mutable command、generation publisher/callback 和 terminal event MUST 被绑定或校验到当前 room epoch / generation attempt。

旧 epoch 的迟到 command/callback MUST NOT 覆盖新 epoch 状态。

### ROOMRT-013 reconnect

Reconnect MUST 支持：

```text
same epoch + replay available -> bounded replay
same epoch + replay unavailable -> current snapshot
epoch changed -> full snapshot / rejoin / recovery
story gap -> generation resync
```

`revision` MUST 仅在同一 epoch 语境中比较；较大的旧 revision 不得压过新的 epoch。

首发单进程 RoomActor 为同 epoch control event 保留有界内存 replay；cursor 连续时返回 replay，窗口缺失时返回当前
snapshot。process recovery 会切换新 epoch，因此旧 epoch ticket/cursor 只能得到 stale/rejoin 语义，新 ticket 进入后
返回 full snapshot。ticket 中的 reconnect cursor 只用于选择 replay/snapshot，不构成 authority，也不得覆盖当前
checkpoint membership 或 epoch。

## 7. Generation

### ROOMRT-014 RoomGenerationPublisher

Hono 主路径 MUST 使用 runtime-neutral `RoomGenerationPublisher` 或等价端口连接 authoritative generation 与 Room runtime。

当 generation 与 Room 位于同一 `apps/api` runtime 时，SHOULD 使用进程内/服务内调用，不得仅为了未来可分拆而强制跨公网 bridge。

future DO/independent runtime MAY 为同一 publisher contract 实现 authenticated bridge。

### ROOMRT-015 generation idempotency

以下要求保持 MUST：

- stable `generationRequestId`；
- frozen revision / snapshot digest / participant snapshot / ref versions；
- generation service idempotency；
- terminal event 匹配 current attempt + room epoch；
- client reconnect/process failure 不得透明触发第二次 AI generation；
- unknown execution state 必须先查询/对账服务器持久记录。

### ROOMRT-016 host browser 不是中继

Host browser MUST NOT 成为：

```text
AI stream -> host browser -> members
```

的唯一传输路径。

关闭 host tab/socket MAY 改变 presence，但 MUST NOT 因此自动生成第二次权威 generation。

## 8. Lifecycle 与 deadline

### ROOMRT-017 deadline scheduler

v1 MAY 使用 Redis TTL、进程级 scheduler、lazy validation 和低频 reconciliation 的组合。

MUST NOT：

- 为每个 room 建永久高频 `setInterval`；
- 通过固定频率 D1 polling 维持 lifecycle；
- 依赖 timer 永不丢失来保证 destructive correctness。

cleanup 前 MUST 重新验证 room epoch/state/deadline，并保证幂等。

首发实现把 deadline 同时放在 authority state v2、进程级 scheduler 与 lazy validation 路径中。任何 queued command
在 `RoomActor.apply` 的实际线性化边界都 MUST 先用 server clock 复核已安装 state 的 deadline；一旦到期，先以 scoped
deadline-close capability 完成 checkpoint CAS、安装 terminal state 与 fan-out，再拒绝原 command。客户端 command
timestamp 或排队中的 presence update MUST NOT 清除已经到期的 deadline。

### ROOMRT-018 D1 directory

D1 room directory 继续是 derived index。

- public listing MAY 依赖 D1；
- join MUST 最终验证当前 Room runtime/checkpoint；
- Redis checkpoint 不存在时，D1 orphan row MUST NOT 自动创建 Room；
- close/expiry 对 directory 的更新/删除 MUST 幂等且可低频 reconciliation。

v1 不保证 VPS 丢失后同 roomId 恢复；如需该能力，MUST 另立 durable registration/ownership 设计。

GMR-06 首发实现使用 server-owned Redis registration sidecar 补偿 D1 派生投影，不把 D1 提升为
Room authority。registration v2 显式区分 `pending-create` / `projecting` / `active` / `closing`，并同时
保留 `targetRoomEpoch` 与已确认的 `projectedRoomEpoch`。create MUST 先准备 registration，再在同一
Redis Lua checkpoint CAS 中验证 exact pending registration 并切换到 `projecting`；不得以准备完成代替
checkpoint commit。

清理一个 registration 前 MUST 在同一 Redis Lua 线性化边界内验证 authority：先前观察为 absent 时
checkpoint key MUST 仍然 absent；先前严格解析为 terminal 时，只允许 checkpoint raw 已 absent 或与严格
parser 生成的 canonical terminal raw exact-equal。任何 open、malformed、old/new epoch 或并发替换 raw
MUST fail closed，不得删除 D1 投影或 registration。`closing` tombstone MUST 保留到 D1 exact-epoch
删除并确认 absent 后才可删除；D1/Redis 失败后必须可低频重试。

rolling upgrade 期间的 registration v1 只能在 strict parse 与 exact-CAS 成功后迁移为 v2
`pending-create`；旧 target 在 recovery 前进时先保留为 predecessor，D1 读写或 confirm 失败不得丢失
可恢复状态。除 registration reconciler 外，还 MUST 有独立、低频、有界的 D1 reconciliation，以清理
registration 已丢失的 orphan row；两者均不得轮询维持 Room lifecycle。

## 9. DR 与可用性

### ROOMRT-019 v1 不承诺活动房间热迁移

Hono + Redis / VPS 整体不可用时，v1 MAY 中断当前房间并要求 replacement room/rejoin。

v1 MUST 保证该中断不造成：

- duplicate generation；
- duplicate settlement/rating；
- final generation artifact 丢失；
- 客户端伪造旧服务器权威状态。

### ROOMRT-020 Cloudflare DR 范围显式化

Arena Room realtime MUST 只有在实现并验证 Cloudflare RoomRuntime adapter 后才进入对应 DR capability manifest。

在 adapter 不存在时，Hono outage 下多人能力 MUST 明确 degraded/unavailable；不得用无状态 Worker、D1 polling 或客户端房主状态拼装出看似成功但不满足原权威语义的“灾备”。

Future Cloudflare adapter SHOULD 优先重新评估 Durable Object。

## 10. Security

### ROOMRT-021 ticket

Room WebSocket MUST 使用短期签名 ticket，至少绑定：

```text
roomId
userId
capability/role hint
exp
jti or equivalent
protocolVersion
```

role hint MUST NOT 覆盖服务器当前 membership。

首发 ticket 使用 `arena-room-ticket-v1` 独立签名 purpose，默认 45 秒且硬上限 60 秒；签名能力复用既有
server-owned signature service，但 purpose domain separation MUST 保留。每个 `jti` 在 upgrade authorization 阶段通过
Redis 原子消费；replay store 不可用、ticket replay、epoch stale、membership revoked 或 current role 与 hint 不一致时
均 fail closed。ticket 验签成功不等于连接授权成功。

Development Gate 可以先存在 WSS transport/security skeleton，但在 signed ticket 与 membership authority 接入前，
runtime MUST 使用空 browser Origin allowlist 与 default-deny authorizer，使所有真实客户端无法成功 upgrade。测试可以
注入 scoped authorizer 验证 transport；该测试 seam MUST NOT 形成公开 bypass endpoint，也不得被描述为 ROOMRT-021 已完成
或 production WSS 已激活。

GMR-05 后 Development Gate runtime 已可在显式本地 feature flag 下组合上述 authority，但
`ARENA_MULTIPLAYER_ENABLED` MUST 默认关闭，production/preview 配置 MUST 拒绝开启；在 GMR-07 提供受鉴权的
create/join/ticket 产品入口前，不得把仅完成 WSS authority composition 描述为公开可用能力。

### ROOMRT-022 browser Origin

浏览器 WebSocket upgrade MUST 使用显式 Origin allowlist。

Desktop/Mobile 等非浏览器客户端 MUST NOT 把 Origin 当作信任根。

### ROOMRT-023 message validation

所有 Room message MUST 有：

- schema allowlist；
- authorization/capability check；
- message/frame byte limit；
- per-user/per-connection rate limit；
- per-user connection cap；
- bounded outbound backlog/backpressure；
- idle/dead connection cleanup；
- ping/pong 或等价 heartbeat，用于识别半开连接；
- 明确的 slow-consumer close/resync policy。

### ROOMRT-024 secret / host-local isolation

Redis checkpoint、Room log、snapshot、broadcast MUST NOT 包含：

- API Key；
- Provider secret header；
- Better Auth/Legacy credential；
- Cloudflare service credential；
- 完整 host-local payload；
- 不需要共享的 generation sensitive input。

## 11. Observability

### ROOMRT-025 metrics

首发 MUST 至少可观察：

- active rooms；
- active Room WebSockets；
- RoomActor command latency/queue；
- checkpoint bytes/latency/error；
- Redis latency/error/memory/eviction；
- reconnect / snapshot / resync；
- generation publisher backlog/error；
- process CPU/RSS/heap/event-loop delay；
- room recovery/replacement incidents。

指标/日志 MUST NOT 记录完整用户正文、API Key 或完整 Proposal payload。

### ROOMRT-026 scale trigger

在出现以下任一信号后，MUST 重新评估 multi-instance ownership 或 DO adapter，而不是无门禁扩容 Room runtime：

- 单实例容量压力；
- 多地域延迟需求；
- 活动房间连续性要求提高；
- ownership/lease/fencing 代码复杂化；
- Cloudflare Room DR 获得明确业务价值。

## 12. Compatibility 与测试门禁

### ROOMRT-027 wire compatibility

即使 v1 Room 与 generation 同处 `apps/api`，Web/Installed Client 与 Hono 仍可能 version skew。

MUST 保留：

```text
protocolVersion
room snapshot schemaVersion
supported peer version range
```

跨版本改动 MUST 使用 expand/contract，并有 old/new fixture。

### ROOMRT-028 Node WebSocket runtime bootstrap

v1 的 Node WebSocket ingress MUST 使用 `@hono/node-server` 当前支持的 WebSocket server 集成方式，并显式管理底层 WebSocket server 生命周期；实现时 SHOULD 使用 `ws` / `WebSocketServer` 或官方文档中等价的当前方案，不得继续采用已弃用的 `@hono/node-ws` 作为新基线。

WebSocket upgrade route MUST 单独审计 middleware chain。会修改 response headers 的通用 middleware（例如全局 CORS/header middleware）不得在未验证 upgrade 行为的情况下套用到 Room upgrade path。

upgrade policy MUST 使用 adapter 提供的原始 Node method，而不是依赖重建后的 Fetch `Request.method`。method、
`Sec-WebSocket-Key` / version、subprotocol grammar、canonical protocol 与 browser Origin MUST 在 authorizer 前校验；
malformed/aborted handshake MUST NOT 留下 per-user pending occupancy。若 transport 在握手前生成 authorization grant，
grant MUST 不可由客户端伪造、只可消费一次，并在成功 `onOpen` 时原子检查及占用 active connection cap。

浏览器/Installed Client MUST 连接逻辑 Hosted WSS 入口；`homura` 等物理 Hono origin 不得成为长期 public wire contract。生产 WSS routing/hostname 的实际激活继续受 Production / Integration Gate 约束。

### ROOMRT-029 必测场景

进入多人 runtime 上线前至少 MUST 覆盖：

1. sensitive-field negative fixture；
2. typed Proposal + expectedBase conflict；
3. DataCard versionToken stale；
4. roomEpoch fencing；
5. same-epoch snapshot/reconnect；
6. process restart + Redis checkpoint warm recovery；
7. Redis outage authority-changing command fail closed；
8. Redis checkpoint expiry + D1 orphan row 不复活 Room；
9. generationRequestId duplicate start；
10. old epoch/attempt terminal event rejected；
11. host tab refresh during generation；
12. story gap -> generation resync；
13. multi-tab membership/presence；
14. ticket replay/kick/reconnect；
15. oversized/flood/slow-consumer；
16. Hono/VPS loss drill：允许 Room 中断，但无 duplicate generation/settlement；
17. old/new protocol compatibility fixture。

## 13. 开发与生产双门禁

自 2026-08-27 起，不再把“Phase 2.5 所有 acceptance 均 PASS”作为 Arena Room **开发启动**的单一前置条件。

### 13.1 Development Gate

当前允许继续：

- contracts / `packages/multiplayer-core`；
- existing Arena -> normalized source adapter；
- Room runtime state machine、RoomActor 与 Redis conditional checkpoint；
- Room WebSocket / ticket / membership / reconnect；
- feature-flagged 多人 UI 与 Proposal；
- authoritative generation 的 Room publisher；
- 本地、CI、隔离 Redis/D1 与 fault-injection 验证。

必须保持：

- production feature 默认关闭/不可达；
- 不修改 stable control plane、DNS/LB/Access 或生产 credential；
- 不执行 production migration/write/drill；
- 不降低现有 Hosted fail-closed guard；
- 每个切片在自己的验收与验证失败时停止，不把失败债务带入下一切片。

### 13.2 Production / Integration Gate

以下事项在当前平台 blocker 关闭和相应生产 runbook/授权完成前仍不得发生：

- 将多人 realtime 宣称为 production-ready；
- 暴露生产 Room WSS / ticket 入口；
- 以多人开发完成代替完整 `ACCEPT-018` / `ACCEPT-014`；
- 为多人功能放宽 production Web build / DR activation gate；
- 在没有 RoomRuntime adapter 与 fencing protocol 时宣称 Cloudflare 可热接管活动房间。

具体 `/goal` 切片顺序与停止条件由配套 Goal 执行指南约束；该指南不得覆盖本文规范语义。
