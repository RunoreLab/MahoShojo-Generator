# Arena 多人 Hono + Redis 运行时实施规格修订

状态：`accepted`
日期：2026-08-25
规格标识：`SPEC-arena-multiplayer-hono-redis-runtime-amendment-v1`
依据 ADR：`ADR-arena-room-portable-runtime-hono-redis-first`
基线分支：`refactor/platform-rearchitecture`
基线提交：`73e51e1e18e27eee7d09e36ff0ff8010e56e5d88`

## 1. 规范语言

本文中的“必须 / MUST”“不得 / MUST NOT”“应 / SHOULD”“可以 / MAY”具有规范性，其解释遵循 RFC 2119 与 RFC 8174。

本文是 **增量规格修订**。未被本文明确覆盖的既有 Arena 多人业务、Proposal、安全、generation、排位和平台重整要求继续有效。

## 2. 优先级与被覆盖条款

### 2.1 Arena 多人 v1 规格

本文覆盖 `docs/specs/2026-08-21_arena-multiplayer-v1-spec.md` 中所有把以下实现作为 v1 强制条件的条款：

- `apps/arena-room` sidecar Worker；
- one-room-one-Durable-Object；
- Durable Object Hibernation；
- Durable Object SQLite/storage；
- Durable Object alarm；
- `apps/web -> apps/arena-room` Service Binding；
- Hono -> DO `GenerationBridge`；
- D1 directory 必须以 DO 为单房间 lifecycle truth；
- DO internal id / DO storage cleanup / DO migration 等实现专属要求。

尤其包括原规格 §10 中 DO-specific lifecycle/TTL 实现、§14、§15 中 Hibernation-specific 恢复说明、§17 中 DO authority 绑定、§18、§20 中 DO-specific security wording、§23/§24/§25 中 DO-specific 不变量/成本/原则。

以下业务语义 **不被覆盖**：

- 单一 Room Shared Config；
- member local working copy + Proposal；
- typed `expectedBase`；
- versioned DataCard ref；
- host-only authoritative generation；
- stable `generationRequestId`；
- host-local/provider secret isolation；
- membership 与 connection 分离；
- strict/collaborativeInfluence 规则；
- WebSocket 安全、消息限制、backpressure；
- generation final result 仍以既有权威持久层为准。

### 2.2 平台重整实施规格

本文覆盖 `docs/specs/2026-08-22_022600_平台重整实施规格.md` 的以下 Arena-specific 要求：

- `MONO-002` 中“当前目标态必须无条件建立独立 `apps/arena-room`”这一项；
- `MONO-008 Arena Room 迁移` 中 Worker/DO/Service Binding/GenerationBridge 的固定映射。

修订后：

- v1 Room runtime MUST 位于 `apps/api` / Hono；
- `apps/arena-room` MAY 在未来 Cloudflare/DO adapter 被批准时建立；
- 共享协议/纯逻辑仍 MUST 位于 `packages/contracts` / `packages/multiplayer-core`；
- 不得通过 app-to-app 源码导入实现未来 adapter。

### 2.3 其他平台文档

以下既有文档中的 Arena-specific DO 图示/措辞按本修订解释，但其其他内容继续有效：

- `docs/architecture/2026-08-22_022500_平台重整目标架构.md`；
- `docs/topics/2026-08-22_022000_平台重整与本地优先架构.md`；

## 3. Runtime contract

### ROOMRT-001 平台无关 core

Room Shared Config、Proposal、conflict、revision、epoch、snapshot、generation reservation 等业务语义 MUST 由平台无关 contract/pure logic 表达。

`packages/multiplayer-core` MUST NOT 导入：

- Hono；
- Node HTTP/WebSocket server；
- Redis client；
- Cloudflare Durable Object；
- Cloudflare binding；
- 环境变量或 server secret。

### ROOMRT-002 v1 主运行时

Arena 多人 v1 的 Room realtime MUST 首先由 `apps/api` / Hono 提供。

v1 MUST NOT 以实现以下内容作为上线前置条件：

- `apps/arena-room`；
- Durable Object；
- Hibernation；
- DO alarm；
- DO SQLite storage；
- 跨部署 GenerationBridge。

未来 adapter MAY 实现这些能力，但 MUST 复用同一 wire/domain contract。

### ROOMRT-003 单房间单写者

任一活动 `roomId` MUST 在任一时刻只有一个可改变 Room session authority 的 RoomActor/owner。

v1 初始部署 SHOULD 只有一个 room-capable Hono 实例。

在允许多个 room-capable 实例前，MUST 有经过故障测试的 ownership + fencing 方案，或迁移到能够天然提供单协调原子的 runtime。

普通 `SETNX` / sticky session / 短 TTL MUST NOT 单独作为该正确性证明。

## 4. Redis session store

### ROOMRT-004 checkpoint

Authority-changing control transition MUST 产生版本化 Redis Room checkpoint。

至少包括：

```text
schemaVersion
roomId
roomEpoch
revision
room metadata / lifecycle
members / roles
shared config
unresolved proposals
generation reservation / mirror
logical deadlines
updatedAt
```

对于已经向客户端返回成功的以下操作，Redis checkpoint MUST 在 success ack 前完成，除非具体操作被规格明确标为 lossy：

- create/close；
- membership mutation；
- host publish；
- Proposal submit/resolve/withdraw；
- generation reservation；
- generation terminal mirror。

### ROOMRT-005 原子观察

Redis Room store MUST 提供可原子观察的 checkpoint 版本。

首发 SHOULD 优先使用单一版本化 snapshot 或具有等价原子性的有限事务结构，而不是把一份 room state 分散为大量不能一致读取的 key。

### ROOMRT-006 TTL

每个非 terminal Room checkpoint MUST 有 TTL/expiry 机制。

TTL MUST NOT 被解释为永久数据保留保证；Redis key 过期后 D1 directory 残留 MUST NOT 复活房间。

### ROOMRT-007 Redis failure

Redis 不可用时，authority-changing command MUST fail closed 或返回明确 `degraded`/`503` 等价状态；不得继续只写内存却仍向客户端承诺正常可恢复成功。

临时 `story.delta` / presence MAY 在内存安全且 backpressure 有界时继续，但不得改变持久业务事实。

### ROOMRT-008 Redis 不是持久业务权威

即使 Redis 保存活跃 Room checkpoint，以下事实仍 MUST NOT 只存在 Redis：

- final generation record/artifact；
- rating；
- settlement；
- durable provenance；
- account/authorization；
- online card ownership；
- audit / governance facts。

`FLUSHALL` 或 VPS 丢失 MAY 终止 Room session，但 MUST NOT 改写上述事实。

## 5. Fan-out 与 replay

### ROOMRT-009 Pub/Sub

Redis Pub/Sub MAY 用于跨连接/跨实例实时 fan-out，但 MUST NOT 成为：

- Room state truth；
- durable event history；
- reconnect replay 的唯一来源。

客户端漏掉 Pub/Sub event 后 MUST 能通过 snapshot/resync 恢复。

### ROOMRT-010 Streams

Redis Streams 或等价 bounded log 只在存在真实 replay/跨实例需求时 MAY 引入。

v1 MUST NOT 为了预期未来扩展而要求无限 event sourcing。

story delta 不要求逐 chunk 持久化；final report MUST 从既有 authoritative generation storage 恢复。

## 6. Epoch、revision 与 reconnect

### ROOMRT-011 `roomEpoch`

`roomEpoch` MUST 标识 Room Authority incarnation，并充当 fencing boundary。

以下情况 MUST 使用新 epoch，除非实现能够严格证明旧 owner/callback 已不可能继续写：

- Hono RoomActor ownership 重建；
- Hono process restart 后重新加载 checkpoint；
- Room runtime failover；
- 灾难恢复/replace。

### ROOMRT-012 stale writer 拒绝

Mutable command、generation publisher/callback 和 terminal event MUST 被绑定或校验到当前 room epoch / generation attempt。

旧 epoch 的迟到 command/callback MUST NOT 覆盖新 epoch 状态。

### ROOMRT-013 reconnect

Reconnect MUST 支持：

```text
same epoch + replay available -> bounded replay
same epoch + replay unavailable -> current snapshot
epoch changed -> full snapshot / rejoin / recovery
story gap -> generation resync
```

`revision` MUST 仅在同一 epoch 语境中比较；较大的旧 revision 不得压过新的 epoch。

## 7. Generation

### ROOMRT-014 RoomGenerationPublisher

Hono 主路径 MUST 使用 runtime-neutral `RoomGenerationPublisher` 或等价端口连接 authoritative generation 与 Room runtime。

当 generation 与 Room 位于同一 `apps/api` runtime 时，SHOULD 使用进程内/服务内调用，不得仅为了未来可分拆而强制跨公网 bridge。

future DO/independent runtime MAY 为同一 publisher contract 实现 authenticated bridge。

### ROOMRT-015 generation idempotency

以下要求保持 MUST：

- stable `generationRequestId`；
- frozen revision / snapshot digest / participant snapshot / ref versions；
- generation service idempotency；
- terminal event 匹配 current attempt + room epoch；
- client reconnect/process failure 不得透明触发第二次 AI generation；
- unknown execution state 必须先查询/对账服务器持久记录。

### ROOMRT-016 host browser 不是中继

Host browser MUST NOT 成为：

```text
AI stream -> host browser -> members
```

的唯一传输路径。

关闭 host tab/socket MAY 改变 presence，但 MUST NOT 因此自动生成第二次权威 generation。

## 8. Lifecycle 与 deadline

### ROOMRT-017 deadline scheduler

v1 MAY 使用 Redis TTL、进程级 scheduler、lazy validation 和低频 reconciliation 的组合。

MUST NOT：

- 为每个 room 建永久高频 `setInterval`；
- 通过固定频率 D1 polling 维持 lifecycle；
- 依赖 timer 永不丢失来保证 destructive correctness。

cleanup 前 MUST 重新验证 room epoch/state/deadline，并保证幂等。

### ROOMRT-018 D1 directory

D1 room directory 继续是 derived index。

- public listing MAY 依赖 D1；
- join MUST 最终验证当前 Room runtime/checkpoint；
- Redis checkpoint 不存在时，D1 orphan row MUST NOT 自动创建 Room；
- close/expiry 对 directory 的更新/删除 MUST 幂等且可低频 reconciliation。

v1 不保证 VPS 丢失后同 roomId 恢复；如需该能力，MUST 另立 durable registration/ownership 设计。

## 9. DR 与可用性

### ROOMRT-019 v1 不承诺活动房间热迁移

Hono + Redis / VPS 整体不可用时，v1 MAY 中断当前房间并要求 replacement room/rejoin。

v1 MUST 保证该中断不造成：

- duplicate generation；
- duplicate settlement/rating；
- final generation artifact 丢失；
- 客户端伪造旧服务器权威状态。

### ROOMRT-020 Cloudflare DR 范围显式化

Arena Room realtime MUST 只有在实现并验证 Cloudflare RoomRuntime adapter 后才进入对应 DR capability manifest。

在 adapter 不存在时，Hono outage 下多人能力 MUST 明确 degraded/unavailable；不得用无状态 Worker、D1 polling 或客户端房主状态拼装出看似成功但不满足原权威语义的“灾备”。

Future Cloudflare adapter SHOULD 优先重新评估 Durable Object。

## 10. Security

### ROOMRT-021 ticket

Room WebSocket MUST 使用短期签名 ticket，至少绑定：

```text
roomId
userId
capability/role hint
exp
jti or equivalent
protocolVersion
```

role hint MUST NOT 覆盖服务器当前 membership。

### ROOMRT-022 browser Origin

浏览器 WebSocket upgrade MUST 使用显式 Origin allowlist。

Desktop/Mobile 等非浏览器客户端 MUST NOT 把 Origin 当作信任根。

### ROOMRT-023 message validation

所有 Room message MUST 有：

- schema allowlist；
- authorization/capability check；
- message/frame byte limit；
- per-user/per-connection rate limit；
- bounded outbound backlog/backpressure。

### ROOMRT-024 secret / host-local isolation

Redis checkpoint、Room log、snapshot、broadcast MUST NOT 包含：

- API Key；
- Provider secret header；
- Better Auth/Legacy credential；
- Cloudflare service credential；
- 完整 host-local payload；
- 不需要共享的 generation sensitive input。

## 11. Observability

### ROOMRT-025 metrics

首发 MUST 至少可观察：

- active rooms；
- active Room WebSockets；
- RoomActor command latency/queue；
- checkpoint bytes/latency/error；
- Redis latency/error/memory/eviction；
- reconnect / snapshot / resync；
- generation publisher backlog/error；
- process CPU/RSS/heap/event-loop delay；
- room recovery/replacement incidents。

指标/日志 MUST NOT 记录完整用户正文、API Key 或完整 Proposal payload。

### ROOMRT-026 scale trigger

在出现以下任一信号后，MUST 重新评估 multi-instance ownership 或 DO adapter，而不是无门禁扩容 Room runtime：

- 单实例容量压力；
- 多地域延迟需求；
- 活动房间连续性要求提高；
- ownership/lease/fencing 代码复杂化；
- Cloudflare Room DR 获得明确业务价值。

## 12. Compatibility 与测试门禁

### ROOMRT-027 wire compatibility

即使 v1 Room 与 generation 同处 `apps/api`，Web/Installed Client 与 Hono 仍可能 version skew。

MUST 保留：

```text
protocolVersion
room snapshot schemaVersion
supported peer version range
```

跨版本改动 MUST 使用 expand/contract，并有 old/new fixture。

### ROOMRT-028 必测场景

进入多人 runtime 上线前至少 MUST 覆盖：

1. sensitive-field negative fixture；
2. typed Proposal + expectedBase conflict；
3. DataCard versionToken stale；
4. roomEpoch fencing；
5. same-epoch snapshot/reconnect；
6. process restart + Redis checkpoint warm recovery；
7. Redis outage authority-changing command fail closed；
8. Redis checkpoint expiry + D1 orphan row 不复活 Room；
9. generationRequestId duplicate start；
10. old epoch/attempt terminal event rejected；
11. host tab refresh during generation；
12. story gap -> generation resync；
13. multi-tab membership/presence；
14. ticket replay/kick/reconnect；
15. oversized/flood/slow-consumer；
16. Hono/VPS loss drill：允许 Room 中断，但无 duplicate generation/settlement；
17. old/new protocol compatibility fixture。

## 13. 对旧实施门禁的解释

平台 `Phase 2.5` 门禁仍决定 **何时开始** Room runtime；本规格决定 **开始后做成什么样**。

在 Phase 2.5 退出前，只允许继续：

- contracts；
- `packages/multiplayer-core` 纯逻辑；
- existing Arena -> normalized source adapter；
- compatibility/security fixture；
- 阻塞平台迁移的缺陷修复。

不得因为 Hono + Redis 方案更简单，就提前插入当前 G25D 平台关键路径。
