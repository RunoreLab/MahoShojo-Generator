# Arena 多人生成眼—手一致与 preflight 收敛修订

日期：2026-09-04
状态：`accepted`
规格标识：`SPEC-arena-multiplayer-generation-eyehand-convergence-v1`
修订对象：`docs/specs/2026-08-31_150000_Arena多人产品一致性与既有Arena复用修订.md` 第 7.2、7.3 节

## 1. 目的

本修订关闭 Arena 多人在「接受 Proposal → 房主本地落地 → 开始生成」链路上残余的眼—手不一致问题，并把近期实现中膨胀的客户端收敛复杂度收敛回成熟模型：

> **房主在 Arena 编辑区看见的配置，就是下一次生成实际使用的配置；任何不一致都必须先由房主显式解决，不允许用看不见的配置开始生成。**

本修订不改变以下既有权威边界：

- Room Shared Config 仍是多人共享状态的服务器权威（Redis / RoomActor，checkpoint-before-ack）；
- INV-PARITY-003～005（Room 权威、显式覆盖、单次 frozen snapshot）继续有效；
- host 的最终控制权与显式覆盖要求（INV-PARITY-004）继续有效。

## 2. 第 7.2 节补充：命令响应收敛（command-response convergence）

对产品一致性修订 7.2 节「Room 接受 Proposal 后」补充确定性落地路径：

1. host 或 member 自己发起的 Room HTTP mutation（`publish-config`、proposal `resolve`）的响应 MUST 携带 mutation 完成后的权威状态（`publish-config` 返回完整 session；`resolve` 携带 post-mutation 完整权威 `snapshot`，含 members/proposals/sharedConfig/activeGeneration 与 revision/controlSeq）。
2. 客户端 MUST 以该命令响应作为本次操作的**主收敛路径**：resolve 成功后立即把权威 revision/config 安装进本地 session 视图，并触发 host workspace reconciliation materialize 到 Arena 编辑区。
3. WebSocket 控制事件降级为**复制/恢复通道**：向其他成员与并行会话广播变更、支持断线重连与结果未知对账；后续到达的 `room.config.updated` / `proposal.resolved` 与已安装状态幂等。
4. 命令响应安装 MUST 带 fence：房间/纪元/身份一致、本地 revision 与 controlSeq 不回退、同 revision 时配置必须一致；任一不满足则跳过安装，退回 WSS / 快照对账路径。
5. 客户端安装完整 snapshot 时 MUST 同步推进本地 control 复制游标到 `snapshot.controlSeq`，保证「controlSeq 表示已见过的控制事件」这一去重语义与已安装内容一致。禁止只安装部分字段却把整个 snapshot 的 controlSeq 宣布到响应值：否则尚未送达的中间控制事件（如另一成员的 `proposal.submitted`）会被 WSS 的 `controlSeq <= current` 去重规则永久丢弃。

实现注记：`resolve` 响应的权威状态直接取自服务端 transition 后已在内存中的 `nextState`，无额外读取成本。仅携带 `sharedConfig` 的旧版响应由客户端保留部分安装回退，仅收敛 revision/config/proposal，供滚动发布期间的旧服务器使用。

## 3. 第 7.3 节覆盖：generation preflight 选项收敛

产品一致性修订 7.3 节中 host 可选择的 `按当前房间配置开始` 选项**自本修订起移除**，不得继续实现或使用。

原因：该选项允许「房主眼前是本地配置 A，生成却使用看不见的房间配置 B」，违背眼—手一致；且其可用性依赖一套复杂的本地 baseline/`startFromRoom` 分支，成本高、收益低。

### 3.1 新的 preflight 决策集

host 点击生成时：

- 本地 working copy 与 Room authority 一致：直接冻结并开始；
- 本地有未发布修改（dirty 或 working copy 无法投影）：显示 preflight，不得隐式 publish，host 可选择：
  - `更新房间配置并开始`：把本地 working copy 显式发布为新 Room revision，并开始生成（仅当本地草稿可安全投影且同步状态已落定）；
  - `同步房间配置`：放弃本地未发布修改，把当前 Room authority materialize 到 Arena 编辑区；**不得自动开始生成**，由房主确认眼前配置后再次点击生成；
  - `取消`；
- 本地与房间权威一致但仍有待处理提案：允许在醒目提示「继续生成不会应用这些提案」后确认开始（此场景下本地所见即房间权威，不存在眼—手分离）。

### 3.2 硬不变量

> 多人生成开始时，用于冻结的 `sharedConfig` MUST 等于房主当时在 Arena 编辑区可见的配置投影；二者不一致的任何分支都 MUST 先通过显式 publish 或显式同步解决。

## 4. 依据（外部经验，非规范）

- 客户端数据管理成熟实践推荐直接用 mutation response 更新客户端状态，而不是再等一条异步同步链（TanStack Query "Updates from Mutation Responses"，访问日期 2026-09-04）。
- 多人共享对象由服务器维护权威、客户端以命令响应 + 复制通道收敛是游戏网络架构的常见做法（Unity 网络系统概念文档，访问日期 2026-09-04）。
- 读写/命令链路过度分离会引入不必要的状态机复杂度（Fowler, CQRS, martinfowler.com，访问日期 2026-09-04）。

## 5. 影响范围

- `apps/web` generation preflight dialog / useBattleEngine 房间生成流程：移除 `use-room` 分支，新增 `sync-room`（不自动开始）与 `confirm-start`（干净 + 待处理提案确认）。
- `apps/web` arena-room controller：resolve 响应安装 fence（本修订第 2 节）。
- `packages/contracts`、`apps/api`：proposal resolve 响应携带 post-mutation 权威状态。
- 产品一致性修订 7.3 节的 `按当前房间配置开始` 选项按第 3 节废止；其余章节不受影响。

## 6. wire 兼容与发布顺序

`resolve` 响应新增 `snapshot` 字段属于 wire 变更：本仓库 schema 为 `.strict()`，仍在浏览器中运行旧版 Web 的页签无法解析携带新字段的响应，会落入 `ROOM_RESULT_UNKNOWN`（“请求可能已提交，请先确认房间状态”）路径，可通过 session 对账自行恢复，不会造成状态破坏。

部署管线（API/Hono 先于 Web 触发部署）不构成原子切换，因此拆分为两个可独立发布的原子提交：

- Release A（客户端就绪）：contracts schema 允许解析可选 `snapshot` + 客户端安装逻辑；旧 API 不发送该字段时行为完全不变。
- Release B（服务端启用）：API resolve 响应开始携带完整 `snapshot`。

推荐先推送 Release A 并确认 Web 部署完成，再推送 Release B，使暴露窗口收窄到「未刷新的旧页签」。若一次性推送，接受上述可恢复的短暂失败窗口。后续新增响应字段应默认沿用此「客户端先接受、服务端后发送」顺序。
