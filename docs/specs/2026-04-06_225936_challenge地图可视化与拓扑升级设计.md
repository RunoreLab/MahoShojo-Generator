# /challenge 地图可视化与拓扑升级设计

## 背景

当前 `/challenge` 已经具备一套可推进的挑战地图数据结构：

1. `lib/challenge/map.ts` 会生成带分叉与汇合的 `nodes + edges` 图。
2. `RunStateV1.mapState` 已经保存了层数、节点、边与可见状态。
3. 节点可进入逻辑由边关系驱动，而不是纯粹按列表顺序推进。

但当前地图页 `components/challenge/ChallengeMapPage.tsx` 仍然把这些信息主要渲染成“节点卡片列表”：

1. 玩家需要逐卡阅读才能理解路线。
2. 分叉、汇合、路径形状几乎不可感知。
3. 节点类型、当前可进入状态与路线前瞻没有建立一眼可读的视觉层次。
4. 地图区域整体更像信息面板，而不是冒险界面。

因此，本次工作不应只理解为“改一张更好看的地图皮肤”，而应当同时解决两类问题：

1. 地图可视化表达不足。
2. 地图拓扑虽然可用，但视觉骨架仍然过于朴素，难以支撑成熟的路线规划感。

## 目标

1. 让玩家在进入 `/challenge` 地图页后，能够一眼看懂路线的分叉、汇合、前进方向与当前所在位置。
2. 让不同节点类型与节点状态在 1 秒内可识别，不再依赖阅读整块卡片文本。
3. 保留当前站点主视觉基调，但把地图主区域升级成独立的“挑战沙盘 / 冒险界面”。
4. 在不破坏现有 challenge 推进契约的前提下，升级地图拓扑生成，使路线形状更成熟、更接近肉鸽游戏的规划体验。
5. 保证桌面端与移动端表达的是同一张地图，不引入两套不同的地图语义。

## 非目标

1. 本次不重写 challenge 的核心节奏系统，不调整结算、奖励、失败或 boss 判定的大规则。
2. 本次不把 `/challenge` 整页改造成完全不同的视觉主题，外层页面继续沿用当前项目风格。
3. 本次不新增大型自由缩放画布、复杂拖拽编辑或地图编辑器能力。
4. 本次不把地图节点扩展成大段富文本卡片，节点本体仍以“快速识别”优先。
5. 本次不引入与桌面端完全不同的移动端轨道视图或简化版地图语义。

## 现状调研结论

## 1. 当前数据层并非列表，而是图

`MapStateV1` 已经包含：

1. `nodes`
2. `edges`
3. `totalLayers`
4. `bossNodeId`
5. `rootNodeId`

这意味着：

1. 地图视觉表达完全可以升级为真实的路径图。
2. 前端不必继续依赖“平铺卡片”去表达地图。
3. 本轮改造没有必要重写存档模型。

## 2. 当前推进契约依赖 layer 语义

以下逻辑都与 `layer` 有耦合：

1. 地图可见范围推进。
2. 精英、休整、商店、Boss 的分布节奏。
3. `writeRunFlagsAfterNode` 中的部分 run flag 判定。
4. 现有测试中对层数、节点数与特殊节点落位的断言。

这说明本轮可以升级拓扑，但不应把“层级推进”本身推翻为完全自由图。

## 3. 当前问题主要出在表达层与拓扑成熟度不足

当前 `generateChallengeMap` 虽然已经有分叉与汇合，但由于：

1. 每层节点数量少；
2. 边关系较固定；
3. 前端没有显式绘制路径；

最终玩家感知不到“地图是一张图”，而只会感知到“这是 14 张按层数标注的卡片”。

## 方案比较

## 方案 A：只重做地图页渲染，不改拓扑生成

### 做法

1. 保留现有 8 层 14 节点与固定边结构。
2. 只在前端增加路径绘制、节点徽记、状态高亮与详情面板。

### 优点

1. 风险最低。
2. 交付最快。
3. 不需要改动地图生成测试。

### 问题

1. 底层路线形状仍然偏朴素。
2. 即使视觉画得更好，长期也容易暴露“骨架不够像成熟肉鸽地图”的问题。

### 结论

可作为第一阶段兼容目标，但不作为本次最终目标。

## 方案 B：地图渲染升级 + 受约束拓扑升级

### 做法

1. 重做地图主舞台与节点视觉表达。
2. 保留现有 layer 推进契约与大部分数据结构。
3. 把拓扑从“固定骨架”升级成“受约束生成”，让分叉、汇合与路径可读性更成熟。

### 优点

1. 能同时解决“看不懂路线”和“路线骨架不够成熟”两类问题。
2. 不需要重写 challenge 结算与存档主契约。
3. 适合以 TDD 方式分两阶段落地。

### 问题

1. 需要补充布局信息或布局计算逻辑。
2. 需要更新地图生成测试与展示测试。

### 结论

推荐采用。

## 方案 C：连 challenge 节奏系统一起重写

### 做法

1. 同时改地图生成、节点配比、奖励曲线、Boss 门槛与 run flag 判定。

### 优点

1. 理论上自由度最高。

### 问题

1. 范围已超出“地图体验升级”。
2. 会把本轮工作从地图改造扩大成挑战系统重设计。
3. 测试与回归风险明显提高。

### 结论

本次不采用。

## 设计结论

本次采用方案 B：在保留现有 challenge 推进契约的前提下，同时升级地图可视化与地图拓扑。

## 视觉与交互设计

## 总体视觉方向

地图页采用“站点主视觉延续 + 地图区域独立强化”的折中方向：

1. 页面外层继续沿用当前白底、玫瑰色、暖色渐变的站点语言。
2. 地图主区域单独强化为“挑战沙盘”，通过背景层次、路径线、节点发光与状态区分建立冒险感。
3. 不直接照搬《Slay the Spire》的旧纸卷轴风格，但借鉴其“一眼看懂路线”的信息组织方式。

## 页面结构

页面分为两个主要区域：

1. 左侧挑战侧栏
2. 右侧地图主舞台

### 左侧挑战侧栏

保留但收紧现有信息卡职责，仅包含：

1. 当前挑战状态
2. 主资源轨摘要
3. 最近节点结果摘要
4. 地图图例

其作用是辅助阅读地图，而不是继续与地图主区域争夺视觉重心。

### 右侧地图主舞台

替代当前的节点卡片网格，承担以下职责：

1. 渲染整张地图的节点与连线。
2. 强调当前可进入节点。
3. 区分已完成、可进入、前方可见、未接触节点。
4. 支持节点选中与详情查看。

### 节点详情区

节点详情不再常驻在每个节点本体上，而是在地图主舞台内以独立情报区呈现。该区域展示：

1. 节点类型
2. 层数
3. 风险 / 收益提示
4. 节点状态
5. 操作按钮

桌面端可与地图同屏；移动端可位于地图下方。

## 地图表达规则

## 方向与层级

地图采用自上而下的层级推进表达：

1. 起点位于顶部。
2. Boss 位于底部终层。
3. 每层在纵向上保持稳定节奏。
4. 分叉与汇合通过显式连线表达。

这样既符合现有 `layer` 语义，也更符合用户对肉鸽路线图的理解。

## 节点本体

节点采用统一的“徽记式按钮”，而非完整卡片。节点本体包括：

1. 中心图标，用于表达节点类型。
2. 外圈描边与底色，用于表达状态。
3. 必要时的小型辅助点缀，用于表达风险 / 奖励倾向。

节点本体不承载大段说明文本，避免再次退化为小卡片网格。

## 节点状态规则

### 可进入节点

1. 使用最高亮的暖色渐变与柔和外发光。
2. 支持轻微呼吸感或脉冲感。
3. 在键盘聚焦与屏幕阅读器语义上都应被识别为可操作按钮。

### 已完成节点

1. 保持实心节点。
2. 路径与节点以“完成态”高亮保留历史轨迹。
3. 不继续展示为主要操作目标。

### 前方可见节点

1. 可见但降饱和。
2. 仍保留节点类型图标，方便规划。
3. 默认不可直接进入。

### 未接触节点

1. 默认不展示完整实体信息。
2. 可只保留弱化轮廓或完全隐藏。
3. 目标是降低噪声，让当前规划范围更清楚。

## 连线状态规则

连线至少区分三层语义：

1. 已走过路径
2. 当前可走路径
3. 尚未开放路径

这样玩家能直观看到自己已经走到哪条分支，以及下一步有哪些选择。

## 节点交互规则

1. 点击或聚焦节点进入“选中态”，在详情区展示完整信息。
2. `进入节点` 操作由详情区按钮触发，而不是点击节点即直接进入，避免误触。
3. 桌面端可提供 hover 预览，但 hover 只做辅助，不承载唯一信息。
4. 移动端以 tap 选中为主。

## 移动端策略

移动端选择“保留完整地图形状”的方案，而不是改成另一套轨道视图。具体策略为：

1. 保持与桌面端相同的地图语义。
2. 压缩节点本体的信息密度。
3. 允许轻量横向溢出或拖动，以保留路线形状。
4. 把详细说明收纳到地图下方的详情区，而不是塞回节点本体。

这保证了桌面端与移动端表达的是同一张地图，只是信息密度不同。

## 拓扑升级设计

## 设计原则

拓扑升级遵循“兼容 layer 契约、提升路线可读性”的原则：

1. 保留 layer 作为推进主轴。
2. 保留由 `edges` 决定下一步可选节点的机制。
3. 保留 Boss 终层、Elite 后段、Rest / Shop 中段、Event 分散在前中段的节奏约束。
4. 提升分叉与汇合的清晰度，避免地图继续看起来像列表。

## 受约束生成

新地图生成不采用完全自由随机图，而采用“受约束图谱生成”：

1. 总层数先维持在 8 层左右。
2. 节点总量先维持在 14 个左右，控制改造范围。
3. 至少保证 2 次明确分叉。
4. 至少保证 1 次明显汇合。
5. 避免过多视觉交叉边。
6. 避免连续多层都退化成单线。

## 轨道位概念

当前层内节点可以继续使用 `index` 标识，但视觉布局需要稳定的“轨道位”概念，用于控制同层节点的横向位置。轨道位可以通过以下两种方式实现：

1. 直接在地图数据中增加布局字段。
2. 基于拓扑结果在前端或共享 helper 中稳定计算布局坐标。

本次优先选择“共享 helper 计算布局”：

1. 避免立即修改存档主结构。
2. 先把布局作为渲染逻辑能力引入。
3. 若后续发现布局需要跨端持久化，再升级 `MapNodeV1` 契约。

## 特殊节点分配规则

本轮仍保留以下约束：

1. `boss` 固定终点。
2. `elite` 位于后段。
3. `rest` 位于中段。
4. `shop` 位于中后段。
5. `event` 分散在前中段。

但需要确保这些特殊节点落在视觉上更有意义的路径位置，而不是只满足层数约束。

## 实现架构

## 组件拆分

建议将当前 `ChallengeMapPage` 拆分为以下职责单元：

1. `ChallengeMapPage`
   - 页面容器，组织侧栏、地图舞台与详情区。
2. `ChallengeMapStage`
   - 地图主舞台，负责节点与路径的整体布局。
3. `ChallengeMapNode`
   - 单个节点按钮与状态展示。
4. `ChallengeMapLegend`
   - 地图图例。
5. `ChallengeMapNodeDetail`
   - 节点详情区。
6. `ChallengeMapSidebar`
   - 当前状态、资源轨与最近节点摘要。

## 渲染技术选择

采用“HTML 节点 + SVG 连线”的混合方案：

1. 节点使用 DOM / button 渲染，保留语义、可访问性与样式灵活性。
2. 连线与辅助高亮使用单独 SVG 层绘制，便于表达分叉、汇合与状态线。
3. 地图背景与装饰层保持轻量，不引入复杂画布系统。

## 数据层改造

`lib/challenge/map.ts` 中的逻辑需要拆成更清晰的阶段：

1. 基础节点生成
2. 特殊节点分配
3. 拓扑边生成
4. 布局计算
5. 可见范围推进

这样可以分别对“地图长什么样”和“地图怎么显示”进行测试。

## 与现有推进逻辑的边界

本次尽量不改动以下契约：

1. `acceptBootstrapSnapshot` 仍然在接受快照后生成地图。
2. `getSelectableNodeIdsForMap` 仍按边关系返回当前可进入节点。
3. `finalizeNodeResolution` 与 `writeRunFlagsAfterNode` 仍按 `layer` 与 `nodeType` 工作。

也就是说，本轮地图升级应尽量被约束在：

1. `lib/challenge/map.ts`
2. `components/challenge/ChallengeMapPage.tsx`
3. 新增地图子组件
4. 相应测试

## 测试设计

## 地图生成测试

需要扩展 `tests/challenge-map.test.ts`，验证：

1. 新拓扑仍满足层级递进。
2. 至少存在规定数量的分叉与汇合。
3. 特殊节点仍落在预期层区间。
4. 图中不存在非法跳层边。
5. 地图在相同 seed 下仍保持稳定输出。

## 地图布局测试

新增布局级测试，验证：

1. 同层节点会被分配到稳定轨道位。
2. 汇合与分叉在布局上可区分。
3. 不会出现显著不可读的节点重叠。

## 地图页面渲染测试

扩展 `tests/challenge-page.test.tsx` 或新增专门测试，验证：

1. 地图页不再以节点卡片网格作为核心表达。
2. 可进入节点数量与按钮语义正确。
3. `focused` 但不可选节点不会被标成可进入。
4. 节点详情区能根据选中节点显示正确信息。

## 响应式测试

至少通过 SSR / 静态渲染测试确认：

1. 桌面端与移动端都能渲染同一套地图结构。
2. 图例、详情区与主要操作按钮在小屏下不会丢失。

## 分阶段落地建议

为降低风险，建议按两阶段执行：

### 阶段 1：新地图舞台兼容旧拓扑

1. 先完成新的地图舞台、节点视觉、详情区与连线渲染。
2. 先兼容现有拓扑输出，确认交互与信息架构成立。

### 阶段 2：切换到受约束拓扑生成

1. 再升级 `generateChallengeMap` 的拓扑与布局逻辑。
2. 更新生成测试与页面测试。

这种顺序能避免在同一轮里同时调“拓扑”和“渲染”导致问题难以定位。

## 风险与控制

## 风险 1：地图样式做成另一套产品

控制方式：

1. 页面外层继续沿用现有主视觉。
2. 仅强化地图区域，而不是整页换皮。

## 风险 2：拓扑升级牵动 challenge 规则层

控制方式：

1. 保留 `layer` 契约。
2. 不在本轮重写 `progression` 规则。

## 风险 3：移动端地图变成难以操作的大画布

控制方式：

1. 控制节点规模与横向展开范围。
2. 使用详情区承接文本信息。
3. 只允许轻量滚动或拖动，不引入复杂缩放交互。

## 最终结论

本次 `/challenge` 地图升级应被定义为一次“兼容式架构升级”：

1. 表现层上，把地图从节点卡片列表升级为真实的路线图。
2. 数据层上，把固定骨架升级为受约束拓扑生成。
3. 契约层上，继续保留 challenge 当前的 layer 推进与结算规则。

这样可以在一轮改造里显著提升地图的成熟度、直观性与可规划性，同时把系统性风险控制在可验证范围内。
