# 数据卡列表加载可靠性与真分页修订

> 状态：已接受设计；本次实现口径见 §12  
> 日期：2026-09-23  
> 关联背景：2026-09-22 用户集中反馈“我的数据卡/情景卡长期加载不出、切换网络瞬间显示数量但列表为空、搜索后偶尔恢复、云端刷新不及时”。

## 1. 背景与问题定性

2026-09-20 的性能优化提交 `52f5f22` 将 `GET /api/data-cards` 与非 `idsOnly` 的 `GET /api/favorites` 改为 `limit/offset` 分页，默认及最大单页为 8；客户端为维持旧的“完整数组”消费方式，在 `lib/auth.ts` 的 `fetchCardListPages()` 中顺序拉取全部页面，直到 `nextOffset=null`。

这一改动降低了单次 Worker 读取峰值，但形成了新的可靠性薄弱点：

1. 一个完整列表可能需要串行执行很多 HTTP 请求；
2. 任意中间页网络错误、5xx、超时或解析失败都会使整次完整列表读取失败；
3. `dataCardApi.getCards()` 只返回 `result.cards`，上层通常无法区分“真实空列表”和“加载失败”；
4. 多个页面/模态框直接把 `[]` 渲染为“暂无数据卡”，因此瞬时网络故障会被伪装成云端卡库为空；
5. Arena 的搜索会缩小结果规模，减少分页次数，所以用户可能观察到“默认列表加载不出，但搜索后能读出”的现象；
6. `BattleDataModal` 目前多个来源共用 `isLoading`，并发请求还可能产生 loading 提前结束、旧请求覆盖新请求等状态竞争。

本修订不认定历史上所有类似反馈均由 `52f5f22` 引起。历史网络链路、Cloudflare/D1 瞬时故障可能一直存在；本次重点是避免客户端把可恢复的传输失败放大成“数据消失”。

## 2. 设计目标

### 2.1 必须达到

- **失败不等于空。** 只有一次成功完成的列表请求返回 0 条时，UI 才允许显示“暂无数据卡”。
- **刷新失败不清空已有结果。** 已经存在上一次成功数据时，刷新失败保留旧结果并提示“刷新失败”。
- **初次加载失败可恢复。** 显示明确错误和“重试”入口，不要求用户通过切网络、搜索、刷新整页来碰运气。
- **控制瞬时故障影响。** 对可重试的 GET 失败做有界重试；禁止无限重试。
- **避免请求竞态。** 网络切换、搜索、Tab 切换产生的新请求必须能够取消/淘汰旧请求，旧响应不得覆盖新状态。
- **最终改为真正的服务端分页。** 列表首屏只读取当前页所需摘要；完整卡片正文按用户动作读取，不再为了展示第 1 页而串行拉取全部正文。
- **不增加不必要的付费基础设施。** 本轮不引入新的 KV/R2/DO/第三方监控依赖，不修改数据卡业务真相源。

### 2.2 非目标

- 不重做数据卡数据库模型。
- 不借本次问题重构审核、可见性、收藏、卡槽计费或账号迁移逻辑。
- 不建设复杂离线同步系统。
- 不保证在网络完全不可用时仍可第一次打开未缓存的云端数据。
- 不把 IndexedDB 离线缓存作为本轮前置条件；如未来确有收益再单独设计。

## 3. 总体方案

采用两阶段落地：

1. **阶段 A：可靠性止血。** 保持现有 API 与“完整数组”兼容路径，先修复错误语义、重试、保留旧数据和请求竞态。
2. **阶段 B：真分页与摘要列表。** 让“我的数据卡/收藏”像公开库一样按当前页服务端查询；列表只返回展示所需摘要，详情/选择/编辑/下载时再读取完整正文。

阶段 A 应可单独上线，不依赖阶段 B。阶段 B 完成后，阶段 A 的错误语义与重试仍继续生效。

## 4. 阶段 A：可靠性止血

### 4.1 统一列表结果语义

`DataCardsListResult` 继续作为完整列表兼容层的显式结果：

```ts
type DataCardsListResult = {
  success: boolean;
  cards: any[];
  error?: string;
  status?: number;
};
```

UI 入口不得再通过 `dataCardApi.getCards()` 的裸数组结果判断空状态。需要展示云端列表的主要消费者应改用可感知失败的接口，例如：

- `CharacterManagerPage`
- `QuestionnaireEditorPage`
- `SaveToCloudButton` 的“替换已有”
- `BattleDataModal` 的“我的”来源
- 其他实际展示“我的数据卡”列表的入口

`getCards()` 可暂时保留给未迁移的兼容调用方，但不得新增 UI 消费者。

### 4.2 UI 状态机

每个列表来源至少区分：

```ts
type ListLoadState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success' }
  | { status: 'error'; message: string };
```

渲染规则固定为：

- 初次 `loading`：显示加载状态；
- 初次 `error`：显示“数据卡加载失败” + 错误摘要 + “重试”；
- `success && cards.length === 0`：才显示“暂无数据卡”；
- 已有成功数据后的 refresh `error`：继续显示旧卡片，在列表上方显示非阻断提示“刷新失败，当前显示上次成功结果”；
- retry 成功后清除错误。

禁止用 `cards=[]` 兼任“尚未加载 / 加载失败 / 真实为空”三种语义。

### 4.3 有界重试

`fetchCardListPages()` 对**幂等 GET** 增加页级有界重试。

可重试：

- 网络层异常（如 `TypeError` / 连接中断）；
- 408；
- 429；
- 5xx。

不可自动重试：

- 400/401/403/404 等明确业务/权限错误；
- 响应契约非法且重复请求无明显恢复价值的错误。

首轮建议每页最多 **2 次尝试（1 次自动重试）**。如生产观测表明瞬时失败仍较多，可再评估提高到 3 次；本轮不做无限或长时间后台重试。

退避保持简单有界，例如首次失败后等待约 300–800ms 再试。无需引入通用重试框架。

### 4.4 超时与取消

列表请求应支持 `AbortSignal`：

- 模态框关闭时取消未完成请求；
- Tab 切换时取消旧来源请求；
- 搜索词/排序/筛选发生新请求时淘汰旧请求；
- 新请求发起后，即使旧请求晚到，也不得写回状态。

实现可使用 `AbortController` + request generation/token；不要求引入新的状态管理库。

如增加请求超时，必须是有界保护而不是极短超时。超时应被归为可重试传输错误，并在最终失败后展示真实错误状态。

### 4.5 保留已经成功的数据

刷新动作采用 stale-while-error 语义：

1. 保留当前成功数组；
2. 标记 refreshing；
3. 新请求成功后原子替换；
4. 新请求失败则保留原数组并显示刷新错误。

不得在请求开始时先 `setCards([])`。

完整分页兼容层在某个中间页最终失败时，仍然不得把已读部分伪装成“完整成功列表”。阶段 A 保持当前“整次请求失败”的一致性语义，但 UI 必须保留**上一次完整成功结果**。

### 4.6 BattleDataModal 拆分来源状态

`BattleDataModal` 不再让 `my/public/favorites` 共用一个布尔 `isLoading` 作为唯一真相。

建议最小化拆分为：

```ts
type SourceState = {
  loading: boolean;
  error: string | null;
};

type DataSource = 'my' | 'public' | 'favorites';
```

每个来源只更新自己的状态。当前激活 Tab 的 UI 只读取对应来源状态。

公开库已有 `AbortController` 逻辑，应将相同的“新请求淘汰旧请求”原则补到 `my` 与 `favorites`，而不是另造一套不同模型。

## 5. 阶段 B：真分页与摘要列表

### 5.1 原则

当前“服务端 8 条一页 → 客户端把所有页串行拉完 → 客户端再切成 12 条一页”的方式只降低单请求峰值，并没有降低首屏总请求量与总正文传输量。

阶段 B 后：

> UI 第 1 页 = 服务端第 1 页。  
> UI 翻页/搜索/筛选 = 发起对应服务端查询。  
> 列表展示 = 摘要数据。  
> 用户真正打开/选择/编辑/下载 = 再读取完整正文。

### 5.2 兼容 API

不要求立即删除现有完整列表契约。优先在现有 `GET /api/data-cards` 上增加兼容的摘要查询模式，例如：

```text
GET /api/data-cards?view=summary&limit=12&offset=0...
```

默认行为在迁移期间保持兼容；新的 UI 明确请求 `view=summary`。

收藏接口采用相同原则：

```text
GET /api/favorites?view=summary&limit=12&offset=0...
```

如实现时发现共享 repository 更适合不同字段选择，可在内部拆分 summary/full 查询；不要求新建另一套公开 URL。

### 5.3 摘要字段

摘要只返回列表展示、排序、筛选、权限提示所需字段，原则上包括：

- `id`
- `type`
- `name`
- `description`
- 可见性 / `review_status`
- `created_at` / `updated_at`
- `usage_count` / `like_count` / `favorite_count`
- `is_recommended`
- 列表所需 tag 信息
- 若 UI 必需，提供服务端归一化的角色类别/模板摘要
- 是否存在待审核更新等列表状态字段

摘要响应**不返回完整 `data` / `pending_data` 正文**。

如果角色类别等兼容信息仍需要读取 JSON 才能推断，可以在服务端当前页查询内部计算后只返回归一化结果；不要为了前端推断而把正文传回浏览器。

### 5.4 单卡完整读取

阶段 B 需要一个经过鉴权的“我的单卡完整内容”读取路径，用于：

- 打开详情；
- 载入编辑器；
- Arena/其他选择器真正选择某卡；
- 下载；
- 替换已有卡。

优先复用现有 `/api/data-cards` 路由并增加精确 ID 的 GET 模式：

```text
GET /api/data-cards?id=<uuid>
```

语义：

- 必须鉴权；
- 仅允许读取当前用户有权访问的完整卡；
- 返回单卡正文及现有必要元信息；
- `Cache-Control: private, no-store`；
- 不因“公开”状态绕过当前用户/权限校验。

若代码审查发现已有更合适的 authorized single-card loader，应复用而不是复制 SQL。

### 5.5 服务端筛选

真分页后，任何会影响“这一页应该有哪些卡”的条件都不能只在当前页客户端过滤，否则会出现假空页/页数错误。

因此“我的数据卡”摘要查询至少应覆盖实际 UI 使用的：

- `search`
- `sortBy`
- `type` / `types`
- 可见性
- 点赞/使用/收藏区间（若该入口保留这些筛选）
- 角色类别（若该入口保留）
- 其他当前 DataCardsModal 会改变集合边界的筛选

不影响集合边界的纯展示转换可以继续留在客户端。

### 5.6 页大小

阶段 B 不再把“8”视为产品层固定值。页大小应围绕 UI 当前每页展示数选择，例如 12；服务端保留合理最大值防止滥用。

不要通过把页大小简单提高到几十/几百来代替真分页。阶段 A 如临时调整 8 只能作为短期缓解措施。

## 6. 网络切换与自动恢复

网络从 offline/异常恢复为 online 时：

- 如果当前激活来源处于 `error`，可以触发一次 best-effort 重试；
- 如果当前已有成功数据且没有 error，不需要因为每次 `online` 事件都强制刷新；
- 自动恢复不得形成循环重试。

网络切换本身不是成功信号，UI 仍以对应请求的真实结果为准。

## 7. 可观测性

本轮不引入新的付费监控基础设施，但应增加足够的结构化信息，让生产故障可以定位。

### 7.1 服务端

数据卡列表请求至少记录或可关联：

- route / source；
- request id / trace id（如已有则复用）；
- `limit` / `offset`；
- 是否 summary；
- DB/handler 总耗时；
- 返回条数；
- HTTP 状态；
- 错误类别。

不得记录卡片正文、认证密钥或用户敏感内容。

### 7.2 客户端

最终失败时可记录：

- source：`my/public/favorites`
- query/offset 的非敏感摘要；
- attempt 次数；
- HTTP 状态或 network/timeout/abort 分类；
- 当前是否保留 stale data。

不要把普通用户搜索文本、卡片正文直接写入遥测。

## 8. 测试要求

### 8.1 API / client helper

必须覆盖：

1. 多页读取全部成功；
2. 中间页第一次 503、重试后成功；
3. 中间页持续 503，最终返回显式失败而不是 `success + partial cards`；
4. 400/401/403 不自动重试；
5. 非法 `nextOffset` 防止无限循环；
6. Abort 后不继续后续分页；
7. 真分页 summary 不返回完整正文；
8. 精确单卡 GET 的 ownership/auth 边界。

### 8.2 UI

必须覆盖：

1. 初次失败显示“加载失败/重试”，不显示“暂无数据卡”；
2. 成功返回空数组才显示“暂无数据卡”；
3. 已有卡片时刷新失败，旧列表仍在；
4. 重试成功后错误状态消失；
5. 旧请求晚于新请求完成时，旧响应不能覆盖新数据；
6. `BattleDataModal` 一个来源完成不得错误清除另一个来源的 loading；
7. 搜索/Tab 切换/模态框关闭能取消或淘汰旧请求；
8. 200 张级别的用户卡库打开首屏时，不再产生 O(N/pageSize) 个正文列表请求。

### 8.3 手工验收

至少在移动端浏览器验证：

- Wi-Fi 正常加载；
- 加载过程中 Wi-Fi → 蜂窝网络切换；
- 加载过程中短暂断网再恢复；
- Arena“我的卡”默认列表与搜索；
- 档案馆“我的数据卡”；
- 创建/替换/删除后列表刷新；
- 收藏列表翻页与刷新。

## 9. 验收标准

满足以下条件才视为本修订完成：

- 任意列表 GET 最终失败时，产品不会把失败显示成“0 张/暂无数据卡”；
- 已成功显示的卡片不会因为一次刷新失败而瞬间消失；
- 用户可以在错误界面直接重试；
- 网络切换后不会被旧请求结果覆盖；
- `BattleDataModal` 的 `my/public/favorites` 加载状态相互独立；
- “我的卡/收藏”首屏已经改为服务端真分页，不需要先把全部卡正文拉完；
- 列表响应不携带完整正文，用户操作单卡时再精确读取；
- 现有公开库、审核、权限、卡槽计费、收藏语义不发生业务回归；
- 不新增数据库迁移或新的付费基础设施，除非实现过程中出现独立且经确认的必要性。

## 10. 建议实施顺序

1. **P0-A1**：迁移关键 UI 到显式 `success/error` 结果，修复“失败=空列表”。
2. **P0-A2**：增加页级一次重试、Abort/竞态保护、stale-on-error。
3. **P0-A3**：拆分 `BattleDataModal` 各来源 loading/error。
4. **P1-B1**：增加 owned/favorites summary 真分页查询与服务端筛选。
5. **P1-B2**：增加/复用鉴权单卡完整读取，并把详情/选择/编辑/下载改为按需读取。
6. **P1-B3**：补观测、全量回归和移动网络切换手工验收。
7. 所有消费者迁移完成后，再评估是否废弃“自动顺序拉完整列表”的 `fetchCardListPages()` 兼容路径；不要在仍有调用方时抢先删除。

## 11. YAGNI 边界

本次优先解决已发生且能解释用户痛点的问题：

- 错误语义；
- 瞬时失败恢复；
- 请求竞态；
- 全量串行分页；
- 正文过度传输。

除非后续数据证明有必要，本轮不加入：

- 复杂多级私有卡离线缓存；
- WebSocket/SSE 实时推送卡库变更；
- 跨设备实时同步协议；
- 无限/长时间后台重试；
- 为列表单独建设新的存储服务。

如果将来“实时同步”仍有可复现问题，应先基于本修订新增的 request/refresh 观测确认是写后读、缓存、路由还是客户端状态问题，再单独立项。


## 12. 本次实现与兼容边界

- `packages/contracts/src/data-cards.ts` 定义摘要查询与响应。`view=summary` 对自有卡和收藏均返回 `cards/total/nextOffset`，并提供筛选集合的 `stats`（私有、公开、待审计数）；默认 12 条、最多 24 条。
- 未指定 `view=summary` 的完整列表与 `favorites?idsOnly=1` 保持兼容。客户端兼容路径仍禁止把部分成功页面返回为完整成功列表。
- `GET /api/data-cards?id=...` 只返回当前用户未删除的自有卡，包含编辑需要的待审内容；他人卡统一返回 404，包括公开卡。收藏正文复用现有公开单卡读取入口并重新检查公开/审核状态。
- 角色管理、问卷库、替换已有、Arena 我的卡/收藏和卡组添加候选均接入摘要分页。问卷页面的统计只读取一条摘要及服务端聚合计数；回收站沿用现有有限容量接口。
- 所有影响摘要集合的搜索、类型、可见性、角色类别、互动数区间、标签、作者、原生许可等条件在数据库分页之前执行。摘要中不含 `data/pending_data`；角色类别与原生许可通过数据库 JSON 表达式推断，无新增字段或索引。
- 问卷库通过 `includeLegacyQuestionnaires` 保留旧误标问卷的发现入口：以 kind/title/questions/loreMarkdown 结构提示识别候选；操作单卡时仍执行既有问卷 schema 校验，类型恢复仍调用现有受控接口，不在列表读取时写库。
