# 最近严格排位对局记录设计

## 背景

严格排位的分数变化来自公开角色卡之间的已计分对局。当前用户能看到卡片分数与排行榜状态，但当一张卡被其他用户发起对局后发生涨分或掉分时，缺少一个轻量入口回答以下问题：

- 最近跟哪个角色打过？
- 这局是谁发起的？
- 本卡是胜、负还是平？
- 本卡分数发生了多少变化？

这个功能用于提升排位透明度，降低“分数变化来源不明”的挫败感。它不是完整审计页，也不承担风控调查功能。

## 目标

新增一个公开可见的“最近严格排位”二级查看能力。

- 所有人都可以查看某个排位实体最近的严格排位已计分记录。
- 卡详情主体只展示入口，不直接塞入历史列表。
- 历史记录在用户点击入口后单独加载，避免打开卡详情时增加默认 D1 查询。
- 第一版只展示最近 10 条 `strict + applied` 记录。

## 非目标

- 不展示自由排位历史。
- 不展示跳过计分、失败结算或 pending 记录。
- 不展示 IP、邮箱、模型、请求头、风控细节、完整战报内容。
- 不做全站审计流、分页历史归档或高级筛选。
- 不改变排位结算规则。

## 交互设计

### 入口

在卡详情弹窗中靠近排位/评分信息的位置增加一个轻量按钮：

```text
最近严格排位
```

点击后打开独立二级弹窗。

### 二级弹窗

弹窗标题为“最近严格排位”。内容独立加载，包含加载中、空状态、错误重试和记录列表。

每条记录展示：

- 对局时间
- 对手角色名
- 本卡结果：胜 / 负 / 平
- 本卡分数变化，例如 `+18`、`-12`、`0`
- 本卡赛后分
- 发起者用户名

推荐文案：

- 空状态：`暂无严格排位记录`
- 加载失败：`无法加载最近严格排位记录`
- 发起者缺失：`未知用户`

## 数据口径

查询对象是一个排位实体：

- `entityType`: `data_card` 或 `preset`
- `entityId`: 数据卡 ID 或预设文件名

第一版只返回：

- `queue = strict`
- `status = applied`
- 最近 10 条
- 与该实体作为 A 方或 B 方有关的事件

结果从 `arena_rating_events` 读取分数变化和双方实体，从 `battle_report_generations` 读取发起用户，从 `battle_report_generation_combatants` 读取参战者展示名。

本卡视角需要根据实体在事件中的位置映射：

- 本卡为 A 方：使用 `a_delta`、`a_after_rating`
- 本卡为 B 方：使用 `b_delta`、`b_after_rating`
- 对手为另一方
- `winner_slot = 0` 表示平局；否则根据本卡对应 slot 判断胜负

## API 设计

新增 Edge API：

```text
GET /api/arena/entity-rating-history?entityType=data_card&entityId=...&queue=strict
```

第一版 `queue` 只接受 `strict`，缺省也按 `strict` 处理。

成功响应：

```ts
type EntityRatingHistoryResponse = {
  success: true;
  entityType: 'data_card' | 'preset';
  entityId: string;
  queue: 'strict';
  items: Array<{
    generationId: string;
    createdAt: string;
    appliedAt: string | null;
    opponent: {
      entityType: 'data_card' | 'preset';
      entityId: string;
      displayName: string;
    };
    result: 'win' | 'loss' | 'draw';
    delta: number;
    afterRating: number;
    initiator: {
      userId: number | null;
      username: string | null;
    };
  }>;
};
```

错误响应沿用项目现有 API 风格：

```ts
type ApiErrorResponse = {
  success: false;
  error: string;
};
```

## 数据库与性能

现有 `arena_rating_events` 有 `queue, created_at` 等索引，但实体维度查询需要同时覆盖 A/B 两侧。第一版可以先用受限 limit 查询实现，但建议同步补实体侧索引，避免数据量增长后 D1 rows read 不稳定。

建议新增索引：

```sql
CREATE INDEX IF NOT EXISTS idx_arena_rating_events_a_entity_queue_status_created_at
  ON arena_rating_events(a_entity_type, a_entity_id, queue, status, created_at);

CREATE INDEX IF NOT EXISTS idx_arena_rating_events_b_entity_queue_status_created_at
  ON arena_rating_events(b_entity_type, b_entity_id, queue, status, created_at);
```

查询时分别查 A 侧和 B 侧最近记录，合并后按 `created_at` 倒序取前 10 条。

## 隐私与安全

该记录公开可见，但只展示排位透明度需要的最小字段。

允许展示：

- 发起者公开用户名
- 对手角色名
- 对局时间
- 胜负平结果
- 本卡分数变化与赛后分

禁止展示：

- IP / 匿名 IP
- 邮箱
- user agent / referer / cf 元数据
- 模型、供应商、token 统计
- 风控 skip reason
- 完整输入、完整输出、完整战报正文

## 前端结构

建议新增独立组件：

- `components/ranking/EntityRatingHistoryButton.tsx`
- `components/ranking/EntityRatingHistoryModal.tsx`

卡详情相关组件只负责放入口和传递实体信息；历史弹窗自行请求 API、管理加载状态和错误状态。

## 测试计划

建议覆盖：

- repository 查询能同时返回实体作为 A/B 方的记录。
- API 只返回 `strict + applied`，并按时间倒序限制 10 条。
- 本卡作为 A/B 方时，`delta`、`afterRating`、`opponent`、`result` 映射正确。
- 发起用户缺失时返回 `username: null`，前端显示“未知用户”。
- 前端入口不会在卡详情打开时预加载历史。
- 空记录、加载失败、重试按钮渲染正确。

## 开放问题

当前确认口径是公开可见、二级弹窗、最近 10 条、只看 strict 已计分记录。暂不做分页和完整战报跳转。
