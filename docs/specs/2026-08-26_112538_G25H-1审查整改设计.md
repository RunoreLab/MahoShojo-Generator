# G25H-1 审查整改设计

状态：accepted
日期：2026-08-26
适用范围：`G25H-1 Arena companion AI routes re-entry` 审查整改

## 1. 背景与裁决

本设计处理 `.tmp/G25H-1审查.md` 提出的三个问题。它服从现有平台重整与 Hosted
长生成 accepted 口径；当旧口径之间存在冲突时，本设计只为本次整改建立窄范围例外，不扩大到
其他 Hosted generation family。

审查裁决如下：

1. `report.article.analysis` 永久为空属实，是两条 non-stream companion route 的用户可见
   contract 语义回归，定级 Important；同根的持久记录 Markdown 被按旧 non-stream JSON
   恢复也必须一并修复。
2. 可信 PVP 请求在 Provider 前被拒绝时不再产生 failed generation、也没有同步
   `generationId` 属实，破坏 round 与风控/失败审计的关联，定级 Important；但不得把所有
   preflight `Response` 都解释为 generation，也不得把安全检查移到 reservation 之后。
3. legacy Arena stats 写入被切断属实；默认构建中 `SHOW_STAT_DATA` 关闭，所以不是默认界面的
   无条件退化。项目没有既有退休决定，而现有 writer 又不具备 generation-id 幂等性。本次明确
   退休该 dormant feature，保留历史表和数据，不做删除迁移。

G25H-1 原设计与实施日志中关于 contract、side-effect parity 和无 Important open 的结论，在本设计
完成前视为尚未闭合；不得继续将现有通过测试当作这些行为已被证明的证据。

## 2. 目标与非目标

目标：

- 恢复两条 companion JSON response 中 `report.article.analysis` 的既有记者点评语义；
- 让即时响应、typed replay、持久 terminal 恢复得到一致的正文和点评；
- 恢复可信 PVP 可审计拒绝的 durable failed terminal 与同步稳定 ID；
- 保持 safety/validation 早于 reservation，拒绝路径不得启动 Provider；
- 正式退出 legacy Arena stats 的 UI、配置、API 与写入代码，同时保留历史数据；
- 以回归测试固定 producer、projector、consumer、D1 identity/fencing 与负面安全边界。

非目标：

- 不恢复旧 structured Provider pipeline，不增加第二次 AI 调用；
- 不把任意 4xx/5xx、非法请求或临时基础设施故障写成 generation terminal；
- 不新增 PVP attempt/security audit 表，不改变 round 胜负、重试或逮捕令规则；
- 不统计 stream/session generation，不以非幂等方式恢复 legacy stats writer；
- 不删除 `characters`、`battles` 等历史表或历史行，不执行生产 migration/deploy；
- 不迁移或重定义现有 Arena rating/ranking 事实。

## 3. 文章 contract 与投影

### 3.1 单一可见内容契约

共享 Arena Markdown prompt 固定以下可见顺序：

1. 标题；
2. 正文；
3. `## 记者点评`，保持旧 structured schema 约 100–150 字的语义；
4. `## 胜利者`；
5. `## 最终结果`。

记者点评属于公开内容，不复制到隐藏 meta，也不按 delivery mode 分叉 prompt。stream projector
继续只负责逐字透传可见 Markdown、处理 chunk 边界并剥离隐藏 meta，不理解业务 section。

### 3.2 Companion projector

non-stream companion projector 从完整 Markdown 提取记者点评写入
`report.article.analysis`，正文在点评 heading 前结束。两条 route 使用同一 projector，delta、snapshot
和 terminal replay 必须产生相同 JSON。旧存量 Markdown 缺少点评时保留空字符串兼容，不从正文猜测或
伪造内容。

UI 对空点评做防御性隐藏，避免旧存量记录出现空白卡块；这不是 producer 可以继续返回空值的理由。

### 3.3 持久记录恢复

`generationMode` 表示 delivery mode，不再被当作内容格式。恢复卡片时先识别实际内容：JSON preview
按旧 structured JSON 解析，Markdown preview 按 section 解析。由 companion route 生成但标记为
`non-stream` 的 Markdown terminal 因而能恢复正文、点评、胜者和结论，同时旧 JSON 记录保持兼容。

## 4. PVP 可审计拒绝状态机

### 4.1 Typed rejection

preflight/materialization 不再只返回无法分类的 opaque `Response`。共享 generation core 引入窄范围
typed rejection，至少携带：

- 原始 HTTP response；
- 稳定的 machine-readable stage/code；
- 是否允许 durable audit；
- 已确认的 actor、`generationRequestId` 与受信 route context；
- 已脱敏、可用于 identity fencing 的请求指纹；
- 通过服务器 authority 验证的 PVP context。

只有显式标为 auditable 且具有可信 PVP authority 的拒绝才能进入下述 terminal recorder。不得通过
解析任意 `Response` 文本来推断 audit policy。

### 4.2 Auditable 分类

本次恢复以下 Provider 前拒绝：

- 本地或 AI safety policy rejection；
- 已确认 actor、稳定 request ID 和可信 PVP context 后的既有业务校验失败，包括参与者、aux/material
  限制与 custom Provider 配置校验；
- 同类 materialization rejection 在释放已创建 reservation 后使用相同 recorder，避免只修复
  preflight 而留下同一历史关联缺口。

以下情况不创建 generation terminal：method、非法 JSON、超大 body、未授权、非法 request ID、非法或
不可信 PVP context、readiness/安全服务不可用等临时 503、reservation unavailable。它们只进入现有
结构化 telemetry。

### 4.3 Failed terminal recorder

对 auditable rejection：

1. 使用既有 actor-scoped `(actorKey, generationRequestId)` 规则派生稳定 `generationId`；
2. 不创建 active reservation，不启动 Provider；materialization 已有 reservation 时先按既有规则释放；
3. 通过 generation-owned D1 terminal recorder 以确定性 ID `INSERT OR IGNORE`，并复用 request、owner、
   payload fingerprint 的 duplicate reconciliation/fencing；
4. terminal 记录为 logical `failed` 且 finalization 已完成，不写 R2、combatant、rating、history 或其他
   成功副作用；
5. 只保存安全 error code/stage、受信 endpoint/delivery context、必要的 PVP 关联 ID 和 identity
   metadata；不得保存 prompt、原敏感文本、custom Provider key、authority signature 或完整请求体；
6. 只有 D1 insert 或 identical-existing 已确认后，才在兼容 JSON body 中加入 `generationId`，并设置
   标准 generation ID response header。保留原状态码、redirect 字段、reason 与其他 header；
7. recorder 失败时 fail-soft 返回原拒绝且不返回 ID，避免写入 `pvp_rounds` 的悬空指针。

同 actor/request/fingerprint 重试返回同一 ID且最多一条 terminal；同 request 的冲突 fingerprint
fail closed，不复用错误记录。该窄例外修订旧规格中“D1 generation 行只在 durable success/failure
finalization 阶段创建”的绝对表述：可信、可审计的 PVP Provider 前拒绝也是 generation terminal，但
绝不代表 active producer 已开始。

### 4.4 Consumer 兼容

PVP resolve 继续兼容 JSON body 的 `generationId`，并可读取标准 header；只有取得已确认 durable ID
才更新 round 的 `battle_generation_id`。敏感拒绝仍按原规则生成逮捕令和平局，普通失败仍按原规则
重试或回退；本设计只恢复关联与审计，不改变控制流。

## 5. Legacy Arena stats 退休

本次把 `SHOW_STAT_DATA`、`updateBattleStats`、legacy stats repository 的活跃调用能力、Arena 统计 UI
fetch/render 及 `/api/get-stats` 公开能力视为同一 dormant feature 一并退休。实现时先检查真实消费者，
删除只服务于该功能的组件、类型和 route registration；不得误删仍服务于新 rating/ranking 的代码。

退休规则：

- 不在 companion、subscriber、replay 或 finalizer 恢复 stats writer；
- 不新增 stats schema/migration，不 DROP/DELETE 历史表和数据；
- 移除或明确失效所有仓库内可配置入口，不能保留“开关可开但数据永远不更新”的半退休状态；
- accepted G25H-1 文档与实施日志记录这是经确认的 compatibility exception，而不是把切断写入继续描述为
  side-effect parity；
- `arena_ratings` 与现有严格/自由榜保持原状，不声称它们迁移或替代了 legacy stats 历史口径。

## 6. 安全、数据与依赖边界

- `packages/*` 不导入 `apps/*`。Markdown 业务投影留在 hosted-runtime 内部；Web 只维护自己的持久卡片
  hydrate/呈现逻辑。
- PVP authority 必须由 Node/server composition 验证，body 自报的 PVP IDs 不足以启用 audit。
- 拒绝审计不降低 safety、auth、rate limit 或 reservation fail-closed 门禁。
- generation ID 必须在 D1 记录确认后才暴露给 PVP consumer；D1 仍是 durable terminal authority。
- telemetry 和 terminal extra 只记录低基数 code/stage 与必要 ID，不记录用户正文、敏感原文或 secret。
- legacy stats 退休不改变数据库中的历史事实，不需要 production migration、Cloudflare 或 Hono 人工操作。

## 7. 测试与验证门禁

实现采用测试驱动，至少覆盖：

1. prompt 冻结 reporter section 的存在、顺序和字数语义；
2. 两条 companion route 在 delta、跨 chunk、snapshot/terminal replay 下得到一致非空 analysis，正文不吞
   点评；缺 section 的旧记录安全降级；
3. stream projector 逐字保留 reporter section 且只剥离隐藏 meta；
4. Web 对旧 JSON、non-stream Markdown、stream Markdown 的内容格式识别，以及空/非空点评渲染；
5. auditable PVP rejection 不 reserve/不启动 Provider，幂等写一条 failed terminal并返回稳定 ID；
6. invalid/untrusted/operational rejection 不审计、不返回 ID；custom key、签名和敏感原文不进入 D1；
7. duplicate、transport timeout、identity mismatch、recorder failure、materialization reservation release；
8. PVP sensitive/ordinary failure 维持既有控制流，且只在 durable ID 存在时关联 round；
9. failed rejection 不写 R2、combatant、rating、history 或 retired legacy stats；
10. `SHOW_STAT_DATA`、旧 stats fetch/render、公开 route 与 writer 不再有活跃源引用，历史 schema 不被删除；
11. hosted-runtime、hosted-api、Web targeted tests、typecheck/lint、workspace boundary、build 与最终
    `ci:verify`；无法运行的外部验证必须单列，不能以未执行命令声称通过。

现有基线共 389 个 test files、2,089 tests 全部通过，只证明当前行为与现有测试一致，不构成上述整改
已完成的证据。

## 8. 实施分组、回滚与 stopping condition

实现计划应保持以下原子边界：

1. 文章 contract/projector/hydrate/UI 与回归测试；
2. typed rejection、failed terminal recorder、PVP consumer 与安全/幂等测试；
3. legacy stats 退休及 accepted 文档校准；
4. 全局验证、独立复审与实施日志收口。

每组完成最小但充分验证后独立提交。代码回滚使用普通 `git revert` 按逆序执行；没有 schema/data
rollback。若回滚 PVP recorder，必须同时回滚 typed audit classification 与 consumer header/body 读取，
不能留下 durable 记录和 wire projection 不一致。

只有同时满足以下条件才可再次宣告 G25H-1 审查闭合：

1. 三项裁决均有实现或明确退休证据；
2. contract、authority、identity、side-effect、replay、data-retention 与 dependency boundary 测试通过；
3. targeted、workspace、Web/OpenNext/Hono 必要构建和 `ci:verify` 无新增 warning/error；
4. accepted 设计、插入计划、topic 和实施日志不再声称与仓库事实冲突的 parity；
5. 独立 architecture/security/compatibility-data/replay/test review 无 Critical/Important open；
6. 未执行 production deploy/migration、secret 变更、切流或其他未经授权的高风险操作。
