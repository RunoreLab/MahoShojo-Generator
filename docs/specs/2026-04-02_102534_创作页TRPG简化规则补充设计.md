## 3. `arena-trpg-lite` 预设定位

### 3.1 目标

`arena-trpg-lite` 用于在创作页中提供“TRPG 简化角色卡”规则输入层，只覆盖：

1. 力量层级
2. 七维核心属性
3. 基于基础能力模块的 `specialties`
4. 由属性推导出的 `HP / MP / Radiance`

### 3.2 第一阶段明确不做

第一阶段不纳入以下完整 TRPG 子系统：

1. 技能树与技能点分配
2. PCP
3. 魔装构筑
4. 羁绊预算
5. 奇境 / 繁开专用编辑器
6. 完整角色卡编辑器式交互

### 3.3 模板支持边界

`arena-trpg-lite` 第一阶段只服务角色卡模板：

- `general`
- `magical-girl`

不支持：

- `canshou`
- `scenario`
- `general-scenario`

## 4. `arena-trpg-lite` 预设定义

### 4.1 顶层字段

预设顶层建议固定包含：

```json
{
  "id": "arena-trpg-lite",
  "version": "1.0.0",
  "title": "魔法少女竞技场 TRPG 简化角色卡",
  "description": "基于《魔法少女竞技场 TRPG》核心属性、力量层级与基础能力模块的轻量车卡规则。",
  "supportedTemplates": ["general", "magical-girl"],
  "allowStandalone": true,
  "mainRuleEligible": true,
  "projectionPolicy": "primary-structured",
  "blocks": []
}
```

### 4.2 blocks

第一阶段 blocks 固定为：

1. `powerLevel`
2. `coreAttributes`
3. `specialties`
4. `derivedStats`
5. `ruleNotice`

各 block 含义：

- `powerLevel`
  - 选择力量层级
- `coreAttributes`
  - 分配七维属性点
- `specialties`
  - 选择基础能力模块中的简化专长，并消耗专长预算
- `derivedStats`
  - 只读展示 `HP / MP / Radiance`
- `ruleNotice`
  - 展示简化规则边界与“本版未覆盖内容”

## 5. 力量层级与预算

### 5.1 力量层级选项

预设中的 `powerLevel` 选项固定为：

- `seed`
- `sprout`
- `leaf`
- `bud`
- `flower`
- `gemScepter`
- `unlimited`

### 5.2 属性预算

属性预算直接采用 Helper 项目中的层级配置：

| 层级 | 属性点预算 |
| --- | ---: |
| `seed` | 280 |
| `sprout` | 285 |
| `leaf` | 290 |
| `bud` | 300 |
| `flower` | 310 |
| `gemScepter` | 325 |
| `unlimited` | 不限制 |

说明：

- `unlimited` 仅取消总点数限制。
- 第一阶段默认仍保留单项属性 `10-80` 的上下限约束。
- 若未来需要放开单项限制，应通过预设字段显式声明，不在第一阶段隐式处理。

### 5.3 核心属性

核心属性固定为：

- 力量 `STR`
- 体质 `CON`
- 敏捷 `AGI`
- 魔力 `MAG`
- 意志 `WILL`
- 感知 `PER`
- 魅力 `CHM`

第一阶段不允许增删字段，也不允许按模板差异切换属性组。

---

## 6. 衍生值公式

第一阶段只计算并展示用户明确要求的三项：

- `HP = ceil((STR + CON) / 10)`
- `MP = ceil(MAG / 4)`
- `Radiance = ceil(WILL / 5)`

补充说明：

- 这些值由运行时自动计算。
- 页面不允许手工输入。
- 结果卡中应保存最终派生值快照，但不把公式文本写进正文。

## 7. `specialties` 设计

### 7.1 设计来源

`specialties` 的条目来源于“设定卡（原作）：心之花体系与能力边界（留空规则）”中列出的基础能力模块：

- 魔力放出：魔弹、魔力冲击、魔炮
- 防御：魔力护盾
- 强化：身体强化、魔力附着
- 飞行与机动：悬浮、魔力受身、炮弹起射、永动飞行、超速闪现
- 魔力感知：感知强化、环境魔力侦测

### 7.2 分组

为兼顾 UI 展示与 prompt 解释，`specialties` 需保留分组信息：

- `magic-output`
  - 魔弹
  - 魔力冲击
  - 魔炮
- `defense`
  - 魔力护盾
- `enhancement`
  - 身体强化
  - 魔力附着
- `mobility`
  - 悬浮
  - 魔力受身
  - 炮弹起射
  - 永动飞行
  - 超速闪现
- `sensing`
  - 感知强化
  - 环境魔力侦测

### 7.3 成本

`specialties` 第一阶段采用“有预算的点数池 / 成本制”，成本定义如下：

| 条目 | 成本 |
| --- | ---: |
| 魔弹 | 1 |
| 魔力冲击 | 1 |
| 身体强化 | 1 |
| 悬浮 | 1 |
| 感知强化 | 1 |
| 魔炮 | 2 |
| 魔力护盾 | 2 |
| 魔力附着 | 2 |
| 魔力受身 | 2 |
| 环境魔力侦测 | 2 |
| 炮弹起射 | 3 |
| 永动飞行 | 3 |
| 超速闪现 | 3 |

说明：

- 该成本表是基于规则书中的基础能力模块强弱层次做的产品化压缩映射。
- 它不是规则书的直接条文，而是本项目创作页为第一阶段可用性所做的推导。
- 因此该表应写入规则预设，而不是散落在页面逻辑里。

### 7.4 专长预算

`specialties` 预算随 `powerLevel` 变化：

| 层级 | `specialtyPoints` |
| --- | ---: |
| `seed` | 4 |
| `sprout` | 5 |
| `leaf` | 6 |
| `bud` | 8 |
| `flower` | 10 |
| `gemScepter` | 13 |
| `unlimited` | 不限制 |

说明：

- `specialties` 使用独立预算，不挤占属性预算。
- 第一阶段采用“随力量层级增长”的方案，而不是统一固定预算。
- `unlimited` 跳过专长总成本校验，但不跳过字段合法性校验。

## 8. 运行时结构

### 8.1 运行时职责

规则运行时建议固定为三段：

1. `loadBuildRulePresetById(ruleId)`
2. `evaluateBuildRuleState({ ruleId, inputs })`
3. `projectBuildRulesForPrompt(...)`

### 8.2 `evaluateBuildRuleState` 输出

运行时返回值应至少包含：

```ts
{
  ruleId: 'arena-trpg-lite',
  version: '1.0.0',
  blockResults: {
    powerLevel: 'seed',
    coreAttributes: {
      STR: 40,
      CON: 40,
      AGI: 40,
      MAG: 40,
      WILL: 40,
      PER: 40,
      CHM: 40
    },
    specialties: ['magic-bullet', 'body-enhancement']
  },
  derived: {
    HP: 8,
    MP: 10,
    Radiance: 8
  },
  validationSummary: {
    valid: true,
    issues: [],
    missingRequiredBlockKeys: [],
    budget: {
      attributePointsUsed: 280,
      attributePointsLimit: 280,
      specialtyPointsUsed: 2,
      specialtyPointsLimit: 4
    }
  }
}
```

约束：

- `blockResults` 只保存规范化后的用户输入结果。
- `derived` 必须全部由运行时重算。
- `validationSummary` 必须全部由运行时重算。
- 页面只维护输入态，不手写派生值和最终预算结论。

### 8.3 校验规则

第一阶段校验策略：

1. 缺少必填 block
   - `invalid`
2. 属性预算超限
   - `invalid`
3. 专长预算超限
   - `invalid`
4. 属性字段非法或缺失
   - `invalid`
5. `unlimited`
   - 仅跳过预算总量校验
   - 不跳过字段必填和数值合法性校验

第一阶段不做自动修正，不做自动均分，不做静默容错。

## 9. 存储与留痕

### 9.1 分层原则

规则相关数据必须保留两层：

- `creationInputs.buildRules[]`
  - 代表“本次生成请求送入 AI 的快照”
- `buildState.rules[]`
  - 代表“当前卡片/页面上的权威规则状态”

主规则字段保持同名：

- `creationInputs.primaryRuleId`
- `buildState.primaryRuleId`

### 9.2 第一阶段语义

第一阶段中，两层结构可以在形状上高度接近，但语义必须分开：

- `creationInputs`
  - 记录生成时发生了什么
- `buildState`
  - 记录当前状态是什么

这样做的目的：

1. 避免后续编辑器接入时混淆“历史快照”和“当前权威状态”
2. 允许未来出现“重新编辑 buildState，但保留旧 creationInputs”的场景
3. 保证 canonical source 始终是结构化 JSON，而不是正文中的描述文本

## 10. AI 投影策略

### 10.1 主规则投影

`arena-trpg-lite` 使用：

- `projectionPolicy = "primary-structured"`

主规则投影时，必须把以下事实作为结构化输入注入 prompt：

1. `powerLevel`
2. 七维属性
3. `specialties`
4. `derived.HP / MP / Radiance`

### 10.2 问卷、自由文本与规则的优先级

建议优先级：

1. 结构化规则事实
2. `freeformBrief`
3. 问卷与设定卡内容

解释：

- `freeformBrief` 可以改变风格、口吻、叙事偏向、强调点。
- 但 `freeformBrief` 不能推翻结构化规则事实。
- 问卷继续负责背景、性格、关系、世界观补充。
- `specialties` 既要以原始条目列表进入 prompt，也要附带中文解释，方便模型理解战斗与能力方向。

### 10.3 模板约束

- 若模板为 `magical-girl`
  - 规则事实用于约束角色数值、战斗风格、魔装与能力边界
- 若模板为 `general`
  - 规则事实用于约束正文中角色的能力与数值设定

第一阶段不尝试把 `arena-trpg-lite` 直接映射成完整的 TRPG 专用角色卡 schema。

## 11. 页面与组件边界

页面分层固定为：

1. 模板选择
2. 自由文本补充
3. 问卷 / 设定卡选择与回答

5. 规则摘要与错误提示

- `TemplateSelector`
- `FreeformBriefPanel`
- `BuildRulePicker`
- `BuildRulePanel`

原则：

- 问卷展示继续复用现有问卷组件树
- 不把规则输入塞回问卷系统
- 不在 `pages/creator.tsx` 中硬写全部规则 UI

## 13. 结论

本轮已确认的关键结论如下：

1. 继续开发前，除了保留现有 `/details` 复制底座外，还必须先补入 `/free` 的“模板选择 + 结果分流”能力。
2. `arena-trpg-lite` 应重做为中文、结构化、可校验的轻量规则预设，而不是把 TRPG 规则硬塞进问卷。
3. `specialties` 第一阶段采用“随力量层级变化的预算池 + 成本制”，并保留 `unlimited` 选项。
4. 规则事实由运行时统一计算，页面不手工维护派生值和预算结论。
5. `creationInputs` 与 `buildState` 必须继续分层保存，避免后续扩展时语义混乱。

本补充设计通过后，再进入实现计划与代码落地阶段。
