# 前端完整卡缓存与低请求优化设计

## 背景

上一轮 challenge 对手链路已经完成两件关键事情：

1. `/challenge` 进入战斗节点时，主选敌链路改为服务端 `selectionSeed` 选敌。
2. 服务端会在选中 `public-card` 时返回 `resolvedSourceCardLite` sidecar，展示层优先消费 sidecar。

这已经显著降低了 challenge 主链路中“逐张请求 `/api/public-data-cards?id=...`”的频率，但前端仍存在以下优化空间：

1. 同一个浏览器会在 `/challenge`、`/ranking` 详情弹窗、排行榜快捷加入等多个入口重复读取同一张公开角色卡。
2. 当前重复读取的缓存粒度主要停留在“组件实例内 memory cache”或“15 秒 edge cache”，跨刷新、跨页面复用仍然不足。
3. `/ranking` 现有本地缓存 `lib/arena/rank-cache.ts` 只缓存 rank/rating/games/tier，不缓存完整卡 payload，因此不能直接承担完整卡缓存职责。

用户目标是继续降低：

1. 前端首屏和详情打开时的等待时间。
2. 向服务器重复发起的单卡请求数。
3. 间接带来的数据库查询流量与 D1 Rows Read 消耗。

## 目标

1. 为“按 ID 读取完整公开卡”的前端热路径提供统一共享缓存。
2. `/challenge` 与 `/ranking` 至少共享同一份完整卡缓存，不再各自重复请求相同数据。
3. 缓存命中时应优先提升前端响应速度，避免等待网络。
4. 缓存 miss 时仍维持当前 API 契约，不新增新的服务端热路径。
5. 缓存设计必须有明确 TTL、容量上限与淘汰策略，避免无限增长。
6. 不把现有 `rank-cache` 设计污染成“轻量榜单缓存 + 大体积完整卡仓库”的混合体。

## 非目标

1. 本次不缓存完整排行榜列表。
2. 本次不缓存 `/api/public-data-cards` 的搜索结果、分页结果或过滤结果。
3. 本次不引入 Service Worker 或浏览器 HTTP Cache Hack。
4. 本次不把完整敌方原卡写入 challenge 存档、`runState` 或 `encounterSnapshot`。
5. 本次不做“预热整榜 Top N 全量角色卡”。

## 现状调研

## 1. `/ranking` 的本地 rank cache 不是完整卡缓存

`lib/arena/rank-cache.ts` 当前只保存：

1. `rank`
2. `rating`
3. `games`
4. `tier`
5. `updatedAtMs`
6. `source`

它的职责是名次信息回填，不是完整卡缓存。若把完整卡 JSON 直接塞进去，会同时带来：

1. 数据体积暴涨
2. `localStorage` 容量与序列化成本问题
3. 职责边界混乱

因此本次设计不复用 `rank-cache` 作为完整卡缓存容器。

## 2. 当前已有局部 memory cache，但没有跨页面共享

`components/ranking/LeaderboardEntityDetailsModal.tsx` 内部已经有 `Map<string, CacheEntry>`，但它只在当前组件实例内生效：

1. 关闭弹窗或离开页面后，缓存上下文就丢失
2. `/challenge` 无法复用这份缓存
3. 刷新页面后仍会重新发请求

这说明当前项目已经验证“按 ID 缓存完整卡”是有效方向，但还缺一个跨页面、跨刷新、共享的正式实现。

## 3. 项目已经具备 IndexedDB 基础设施

当前项目已有统一的 `ai-continuous-dialogue:v1` IndexedDB：

1. `lib/ai-session/types.ts`
2. `lib/ai-session/storage.ts`

并已经承载 challenge run / node / checkpoint / unlock 等 store。说明：

1. 浏览器端结构化持久缓存已有成熟接入方式
2. 无需重新发明另一套 IndexedDB 打开与错误处理逻辑
3. 对“中等体积、按 ID 精确读写”的完整卡缓存而言，IndexedDB 比 `localStorage` 更合适

## 4. `/challenge` 主链路已具备最佳写缓存时机

当前 `/challenge` 在 `selectionSeed` 模式下拿到的 `resolvedSourceCardLite` 已经是服务端验证成功的最小 DTO：

```ts
type ChallengeResolvedSourceCardLite = {
  id: string;
  name: string;
  data: string;
  updatedAt: string | null;
};
```

这意味着 challenge 进入节点时已经天然拥有：

1. 一次“零额外请求”的完整卡写缓存时机
2. 一份已通过服务端验证的最小可信 payload

如果不把它写入客户端共享缓存，这份 sidecar 的价值只停留在当前 controller 会话内，跨刷新就丢失。

## 方案比较

## 方案 A：只做当前 challenge 会话内 memory cache

### 做法

1. 只在 `useChallengeController` 或 challenge 页面内维护 `Map`
2. 当前 tab 命中时复用
3. 刷新后全部失效

### 优点

1. 实现简单
2. 风险最低

### 问题

1. `/ranking` 无法复用
2. 刷新后收益归零
3. 对降低服务器请求和数据库流量帮助有限

### 结论

不采用，单独作为 L1 memory cache 的一部分保留。

## 方案 B：独立的“两级完整卡缓存”

### 做法

1. L1：tab 内 memory cache
2. L2：IndexedDB 持久缓存
3. 统一由共享 loader 负责读写与淘汰

### 优点

1. 兼顾命中速度与跨刷新复用
2. 可供 `/challenge` 与 `/ranking` 共用
3. 不污染现有 `rank-cache`

### 问题

1. 需要新增 store 与迁移
2. 需要定义 TTL、容量与负缓存边界

### 结论

推荐采用。

## 方案 C：直接扩展 `rank-cache` 为完整卡缓存

### 做法

1. 在 `localStorage` 的 leaderboard cache 中追加完整卡 payload

### 问题

1. `localStorage` 体积与同步序列化成本不适合完整卡 JSON
2. `rank-cache` 的 key 语义、淘汰策略和完整卡缓存并不一致
3. 容易把排行榜排序元数据与完整卡详情耦死

### 结论

不采用。

## 推荐方案

采用方案 B：引入独立的“前端完整公开卡共享缓存”，架构为：

1. `L1 memory cache`
2. `L2 IndexedDB persistent cache`
3. 统一共享 loader

并且坚持以下原则：

1. 完整卡缓存与 rank cache 分离。
2. 只缓存“按 ID 成功读取到的单卡详情”和“challenge sidecar”。
3. 不缓存列表搜索结果。
4. 只做精确 ID 读写，不做任何扫表式前端操作。

## 设计细节

## 一、存储模型

### 1. IndexedDB 复用现有 `ai-continuous-dialogue:v1`

不新开第二个数据库，直接在现有 DB 上新增 store：

1. `AI_SESSION_DB_VERSION` 从 `3` 升到 `4`
2. 新增 `AI_SESSION_STORE_NAMES.publicCardCache = 'public_card_cache'`

这样做的好处：

1. 浏览器端存储入口统一
2. 迁移逻辑集中在 `lib/ai-session/storage.ts`
3. 复用现有测试与错误处理模式

### 2. Store 记录结构

正缓存记录推荐如下：

```ts
type PublicCardCacheRecord = {
  id: string;
  cacheKind: 'card';
  name: string;
  data: string;
  updatedAt: string | null;
  fetchedAtMs: number;
  lastAccessedAtMs: number;
  expiresAtMs: number;
  renderableTemplate: 'magical-girl' | 'canshou' | 'general' | null;
  isRenderable: boolean;
  source: 'challenge-sidecar' | 'public-data-card-api';
};
```

负缓存记录推荐如下：

```ts
type PublicCardNegativeCacheRecord = {
  id: string;
  cacheKind: 'negative';
  statusCode: 404;
  fetchedAtMs: number;
  lastAccessedAtMs: number;
  expiresAtMs: number;
  reason: 'not-found';
};
```

约束：

1. `data` 必须保持 JSON 字符串，不提前 parse 后再写入 IndexedDB。
2. `updatedAt` 继续使用 camelCase。
3. `renderableTemplate / isRenderable` 只是派生元数据，不是权威真相；真相仍是 `data`。

### 3. Index 设计

新增以下索引即可：

1. `by_expiresAt`：用于批量清理过期项
2. `by_lastAccessedAt`：用于 LRU/最近最少使用淘汰
3. `by_cacheKind_lastAccessedAt`：用于分别控制正缓存与负缓存上限

不新增任何全文检索、模糊搜索或按作者/标签查询索引。

## 二、缓存层级

### 1. L1：memory cache

使用模块级 `Map<string, PublicCardCacheRecord | PublicCardNegativeCacheRecord>`：

1. 当前 tab 读写最快
2. 不需要异步等待 IndexedDB
3. 页面切换后自动释放

L1 主要解决“同一页面或同一会话内重复打开详情”的延迟问题。

### 2. L2：IndexedDB cache

用于：

1. 跨刷新保留
2. challenge 与 ranking 跨页面共享
3. 降低跨页面重复请求

推荐容量上限：

1. 正缓存最多 `256` 条
2. 负缓存最多 `128` 条

理由：

1. 公开角色卡 JSON 体积明显大于 rank cache
2. 256 条已足够覆盖多数“最近浏览 / 最近遭遇 / 最近查看榜单详情”的热集合
3. 上限固定后，不会无限膨胀

## 三、TTL 与淘汰策略

### 1. 正缓存 TTL

采用“双阈值”：

1. `FRESH_TTL = 1 小时`
2. `HARD_TTL = 24 小时`

语义：

1. `<= 1 小时`：直接命中
2. `> 1 小时 && <= 24 小时`：允许 stale hit，并在后台异步 revalidate
3. `> 24 小时`：视为过期，必须重新走网络

这样既能显著降低重复请求，又不会把潜在过时的公开卡长期保留太久。

### 2. 负缓存 TTL

仅缓存 `404`，不缓存 `500`、超时、网络错误：

1. `NEGATIVE_TTL = 3 分钟`

原因：

1. 404 对同一坏 ID 的重复点击没有价值
2. 500/网络错误通常是暂时问题，不适合写入负缓存

### 3. 淘汰策略

每次写入后执行轻量维护：

1. 优先清理 `expiresAtMs <= now`
2. 若正缓存超上限，按 `lastAccessedAtMs` 从旧到新裁剪
3. 若负缓存超上限，同样按 `lastAccessedAtMs` 裁剪

只在写入后做有限清理，不做启动时全库扫描。

## 四、统一读写链路

### 1. 统一公共入口

新增共享 loader，例如：

```ts
getCachedPublicCardById(id, options?)
putCachedPublicCard(record)
putCachedPublicCardFromSidecar(sidecar)
fetchPublicCardByIdWithSharedCache(id, options?)
```

## 2. 统一读取顺序

读取顺序必须固定为：

1. challenge 当前会话 sidecar
2. L1 memory cache
3. L2 IndexedDB cache
4. `/api/public-data-cards?id=...`

其中：

1. 如果 L1/L2 命中负缓存，直接短路返回 `null`
2. 如果命中 stale 正缓存，先返回缓存值，再后台 revalidate

## 3. 统一写入时机

以下来源都应写入共享缓存：

1. `resolvedSourceCardLite`
2. `/api/public-data-cards?id=...` 成功返回的单卡结果
3. `/ranking` 详情弹窗成功读取到的公开卡
4. 其它显式按 ID 读取公开卡的 UI 入口

写入规则：

1. `sidecar` 命中时直接 write-through 到 L1 + L2
2. 网络请求成功时也 write-through 到 L1 + L2
3. `404` 时写入负缓存

## 五、页面接入范围

### Phase 1：优先接入 challenge 与 ranking 详情

必须接入：

1. `components/challenge/hooks/useChallengeController.ts`
2. `components/ranking/LeaderboardEntityDetailsModal.tsx`

原因：

1. 这是当前最明确的重复读取热点
2. challenge 已经天然拥有 sidecar 写缓存时机
3. ranking 详情已有局部 memory cache，改造成共享缓存收益明确

### Phase 2：接入其它按 ID 读取公开卡的入口

可选扩展：

1. `components/arena/components/ArenaRankingModal.tsx`
2. `components/BattleDataModal.tsx`

这些入口也在按 ID 请求 `/api/public-data-cards`，后续应逐步改到同一共享 loader，避免再次出现“每个组件都各写一份 fetch + cache”。

## 六、与 challenge 的边界

1. 缓存只服务于“展示完整卡”和“详情打开速度”，不参与服务端选敌决策。
2. challenge 当前会话中的 `resolvedSourceCardLite` 仍然是第一优先级。
3. 即使本地缓存命中，也不能反向影响 `selectionSeed` 主链路。
4. 不把完整卡写进 `runState`、`ChallengeNodeRecord` 或 checkpoint。

## 七、与权限/时效性的边界

这套缓存的设计前提是：

1. 缓存对象本质上是“此前已经成功公开读取过的数据”
2. 允许短时间的前端陈旧读取
3. 不允许长期无上限地保留

因此约束如下：

1. 只允许 `1h fresh + 24h hard TTL`
2. 不对 500/网络错误做负缓存
3. 一旦后台 revalidate 返回 404，必须立即删除正缓存并写入短 TTL 负缓存

## 八、测试要求

至少覆盖以下测试：

1. `sidecar` 写入缓存后，刷新前后的 challenge fallback 可命中本地缓存，不再请求单卡 API
2. ranking 详情同一张卡二次打开时优先命中共享缓存
3. 命中 stale 正缓存时会立即返回缓存并后台 revalidate
4. 404 负缓存生效期间不会重复请求同一坏 ID
5. 500/网络错误不会写入负缓存
6. 超容量后会按 `lastAccessedAtMs` 淘汰旧项
7. IndexedDB 不可用时安全降级到 L1 memory cache，不影响主流程

## 九、埋点与观测

建议增加最小埋点：

1. `public_card_cache_hit_memory`
2. `public_card_cache_hit_idb`
3. `public_card_cache_hit_stale`
4. `public_card_cache_miss_network`
5. `public_card_cache_negative_hit`
6. `public_card_cache_write_sidecar`
7. `public_card_cache_write_api`

目标不是精细 BI，而是验证：

1. 是否真的减少了 `/api/public-data-cards?id=...` 请求数
2. challenge/ranking 是否共享命中了同一批热卡

## 十、实施建议

推荐拆成两步：

1. 先落基础设施
   - 新增 store、类型、shared loader、TTL/淘汰
2. 再接入页面
   - challenge
   - ranking details

原因：

1. 基础设施更容易单测
2. challenge 与 ranking 页面接入可以逐步扩展
3. 避免一次性把所有读取入口都重写

## 最终结论

本次优化应采用“独立的两级完整卡共享缓存”，而不是修改现有 `rank-cache`：

1. L1 `Map`
2. L2 IndexedDB
3. `sidecar -> memory -> IndexedDB -> network` 的固定读取顺序
4. `1h fresh + 24h hard TTL + 3min 404 负缓存`
5. 先接入 challenge 与 ranking 详情，再逐步扩到其它按 ID 读取入口

这样可以在不改动服务端选敌真相源、不增加新的数据库热路径的前提下，同时提升前端响应速度并减少重复请求。
