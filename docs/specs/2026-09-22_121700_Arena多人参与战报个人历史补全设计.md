# Arena 多人参与战报个人历史补全设计

- 日期：2026-09-22
- 状态：accepted / 实施中
- 来源：用户确认的“核查多人战报落地情况”会话设计及本次实施授权。
- 关系：细化 [Arena 多人 v1 §12.3](./2026-08-21_arena-multiplayer-v1-spec.md#123-个人页战报)，参与者历史权限遵守该规格的房间共享边界。

## 1. 背景

Arena 多人模式现已具备：

- generation 开始时冻结 `participantUserIds`；
- 单次权威 generation 与断线恢复；
- D1 `battle_report_generations` 终态持久化；
- R2 战报正文持久化；
- Room 内近期历史战报浏览；
- 个人页战报列表、详情与“重生/还原战报”能力。

但现有个人页战报查询仍主要依赖：

```sql
battle_report_generations.user_id = current_user
```

该模型适用于单人 Arena，但无法表达：

> 一次多人 Arena generation 同时属于多名用户的历史记录。

原多人规格已经提出建立 `generation <-> participant` 长期关系，但当前实现尚未落地。因此普通房间成员离开房间或 Room TTL 清理后，无法依赖个人页长期回顾其实际参与的多人战报。

本规格补齐这一纵切，同时保持现有 Arena Room、generation、D1/R2 和个人页体系，不建立第二套战报系统。

---

## 2. 目标

本次实现应满足：

1. Arena 多人 generation 开始时冻结的全部 active members 获得长期战报参与关系。
2. 用户退出房间、断线、被移除或 Room runtime 清理后，该历史关系仍然存在。
3. 用户可在个人页看到自己实际参与的多人 generation。
4. 区分用户当时是：
   - `host`
   - `member`
5. participant 查询具有普通索引能力，不依赖扫描 `extra_json` JSON 数组。
6. participant 关系不复制战报正文。
7. participant 权限不自动等价于 generation owner 权限；普通成员只能获得符合多人共享边界的历史投影。
8. 不扩大 PVP、Proposal 历史、Room membership 历史等无关范围。

---

## 3. 非目标

本次明确不做：

- 完整 Room membership 历史数据库；
- 保存 join / leave 时间；
- 保存 presence / 在线状态；
- 保存成员 display name / username snapshot；
- 保存完整 Proposal 历史；
- 保存每个 contributor 的 Proposal 贡献详情；
- host transfer；
- 将旧 PVP participant 全量迁移到新关系表；
- 对历史 Arena Room generation 进行不可靠 participant 回填；
- 真正重新调用 AI 复现历史 generation；
- 建立通用 ACL / RBAC 系统。

---

## 4. 核心语义

### 4.1 Participant 的定义

某用户属于 generation 的长期 participant，当且仅当：

> 该用户在 generation reservation 时位于服务端冻结的 active membership snapshot 中。

判断基于：

```text
membershipState === active
```

而不是：

```text
当前是否在线
最终是否仍在房间
是否提交过 Proposal
是否贡献过配置修改
```

例如：

```text
generation 开始：
A host
B member
C member，暂时离线但 membership 仍 active

=> participant = A, B, C
```

如果 D 在 generation 开始后加入：

```text
D 不属于该 generation 的长期 participant
```

即使 D 在房间内临时看到了该战报。

### 4.2 Participant snapshot 不可事后修改

generation 开始后：

- 用户断线；
- 用户重新连接；
- 用户主动退出；
- 用户被移除；
- 房间成员发生变化；

均不得修改已经冻结的 generation participant 集合。

## 5. 数据模型

新增窄关联表：

```sql
CREATE TABLE battle_report_generation_participants (
  generation_id TEXT NOT NULL,
  user_id INTEGER NOT NULL,
  role TEXT,

  PRIMARY KEY (generation_id, user_id),

  FOREIGN KEY (generation_id)
    REFERENCES battle_report_generations(id)
    ON DELETE CASCADE,

  FOREIGN KEY (user_id)
    REFERENCES users(id)
    ON DELETE CASCADE
);

CREATE INDEX idx_battle_report_generation_participants_user_generation
ON battle_report_generation_participants(user_id, generation_id);
```

对应 Drizzle schema 应同步定义。

### 5.1 字段语义

#### `generation_id`

指向唯一 `battle_report_generations.id`。

#### `user_id`

实际账户用户 ID。

#### `role`

允许：

```text
host
member
NULL
```

正常新 generation 必须保存 `host` 或 `member`。

`NULL` 仅用于兼容无法证明历史角色的旧 snapshot / 跨版本在途任务，不得用于正常新 reservation。

## 6. YAGNI 取舍

### 6.1 为什么新增关系表，而不是写入 `extra_json`

技术上可以把：

```json
{
  "participantUserIds": [101, 202, 303]
}
```

写入 `battle_report_generations.extra_json`。

但个人页和授权的核心访问方向为：

```text
user_id -> generations
```

JSON array 更适合：

```text
generation -> participants
```

若以 JSON 作为长期查询权威，则个人页列表、count、授权和统计需要依赖 `json_each()` 或类似 JSON 扫描。

因此本关系属于真实、稳定且高频反向查询的多对多关系，独立索引表的长期收益明显超过一次 migration 和少量 D1 存储成本。

### 6.2 为什么保留 `role`

`role` 的持久化成本很低，但可以支持：

- `[多人 · 房主]`
- `[多人 · 成员]`
- “我主持的战报”
- “我参与的战报”
- 后续 host-specific 历史操作
- 行为统计和 provenance 审计

而历史 role 一旦未保存，Room runtime 清理后无法可靠恢复。

因此 `role` 属于：

> 当前保存成本低，但未来恢复成本高且具有明确产品价值

的字段，应一并持久化。

### 6.3 本次不保存以下字段

不增加：

```text
room_id
created_at
username
display_name
joined_at
left_at
presence
proposal_count
contributor_user_id
```

理由：

- `room_id` 已属于 generation provenance，不应在 participant 表重复形成第二权威；
- generation 时间可从 `battle_report_generations` 获取；
- display/username 会产生名称变化和冗余问题；
- membership 生命周期不是本功能需求；
- contributor provenance 当前模型没有可靠冻结 author 信息，扩展收益不足以覆盖复杂度。

## 7. Frozen generation provenance 扩展

当前 `ArenaMultiplayerGenerationSnapshot` 已包含：

```ts
participantUserIds: number[];
```

新增：

```ts
hostAccountUserId: number;
```

目标结构：

```ts
type ArenaMultiplayerGenerationSnapshot = {
  roomId: string;
  generationRequestId: string;
  configRevision: number;
  snapshotDigest: string;
  collaborativeInfluence: boolean;

  participantUserIds: number[];
  hostAccountUserId: number;

  sharedConfig: ArenaRoomSharedConfig;
};
```

### 7.1 `hostAccountUserId` 来源

必须在 generation reservation 前，从同一个 authority state 中确定：

```text
member.role === host
&& member.membershipState === active
```

不得在 generation 结束时重新查询当前 Room。

### 7.2 GenerationMirror / durable ledger

所有需要重新构造 frozen generation snapshot 的 durable state 也必须保留：

```text
hostAccountUserId
```

尤其 historical retry / recovery 不得通过当前 membership 猜测原 host。

`GenerationMirror` 与 started/completed/failed event 的解析边界同样验证：有
`hostAccountUserId` 时，该用户必须位于 `participantUserIds`。旧 checkpoint / event 缺少
host 字段时仍可读取，不改变 wire version。

---

## 8. Role 派生

participant relation 写入时：

```ts
role =
  participantUserId === snapshot.hostAccountUserId
    ? 'host'
    : 'member';
```

正常 snapshot 必须满足：

```text
hostAccountUserId ∈ participantUserIds
```

否则 reservation 应 fail closed。

当前 v1 不支持 host transfer，因此一个 generation 应恰好拥有：

```text
1 host
0..N members
```

---

## 9. collaborativeInfluence

当前 multiplayer snapshot 已冻结：

```ts
collaborativeInfluence: boolean;
```

该信息具有长期 provenance 价值，应在 D1 generation terminal manifest 中保存。

建议进入已有 bounded `extra_json`：

```json
{
  "arenaMultiplayer": {
    "collaborativeInfluence": true
  }
}
```

暂不保存：

```text
contributorUserIds
acceptedProposalCount
per-user contribution
```

因为当前 `collaborativeChanges` 只维护仍有效的 semantic effects，并未保留可靠 author provenance。

---

## 10. Participant 写入时机

Participant relation 应作为 generation terminal finalization 的幂等持久化 effect，而不是浏览器回调。

当前流程：

```text
claimTerminal
  -> persistCombatants
  -> applyStoryImpacts
  -> settleRatings
  -> completeTerminal
```

修改为：

```text
claimTerminal
  -> persistCombatants
  -> persistParticipants
  -> applyStoryImpacts
  -> settleRatings
  -> completeTerminal
```

### 10.1 数据源

唯一数据源：

```ts
input.payload.multiplayerGenerationSnapshot
```

若 payload 不包含合法 multiplayer snapshot：

```text
persistParticipants = no-op
```

不得重新访问：

```text
Redis current members
Room current snapshot
客户端提供 participant IDs
```

---

## 11. 幂等性

新增 terminal effect，例如：

```text
arena-terminal:<generationId>:participants
```

Participant 表使用：

```text
PRIMARY KEY (generation_id, user_id)
```

并使用幂等 insert。

写入前按 generation 主键读取已有参与关系，核验它们属于本次 frozen participant set；若新旧证据
都含非空角色，则角色必须一致。发现冲突时拒绝继续补写，不静默覆盖已知角色。
中断后缺少的 participant 可以重试补齐；旧 `NULL` role 保留，新证据不在本次修复中补填旧角色。

建议每批最多 16 participants：

```text
16 × 3 bindings = 48 bindings
```

避免依赖接近 D1 单语句绑定参数上限的 32 × 3 = 96 bindings。

最大 32 人时最多执行两批。

---

## 12. Terminal 状态语义

participant relation 描述的是：

> 谁参与了这个 durable generation attempt

而不是：

> 谁参与了一个成功的 AI 输出。

因此：

| Generation 终态 | Participant relation |
| --- | --- |
| `completed` | 保存 |
| `failed` | 保存 |
| `cancelled` / D1 `aborted` | 保存 |
| `producer_lost` / D1 `failed` | 保存 |

前提是该任务已经形成合法 frozen multiplayer snapshot / durable generation reservation。

### 12.1 Provider 前 rejected request

对于尚未形成正常 generation runtime、在 Provider dispatch 前即被拒绝的 auditable rejection：

```text
v1 不创建 participant relation
```

原因：

当前 `ArenaGenerationRejectedTerminalRecordInput` 没有 multiplayer participant snapshot。

仅为无效生成尝试扩大 rejected-terminal contract 的产品收益较低，本次不增加该复杂度。

---

## 13. Finalization failure 与 reconciliation

Participant persistence 属于 durable finalization completeness，但不得反向改变已经成立的 AI generation 逻辑结果。

例如：

```text
AI completed
R2 archived
participant D1 write timeout
```

不得向用户呈现为：

```text
AI generation failed
```

应延续当前 finalization pending / reconciliation 模型。

因此以下路径均需覆盖 `persistParticipants`：

- 正常 finalization；
- retry；
- expired lease reconciliation；
- interrupted finalization recovery。

`finalizationCompleted=true` 之前必须确保要求执行的 participant effect 已成功或已通过幂等证据确认完成。

---

## 14. 查询模型

现有：

```sql
WHERE battle_report_generations.user_id = :userId
```

以两个 user 索引先求可访问 generation IDs，再按主键读取 generation：

```sql
WHERE battle_report_generations.id IN (
  SELECT id FROM battle_report_generations WHERE user_id = :userId
  UNION
  SELECT generation_id FROM battle_report_generation_participants WHERE user_id = :userId
)
```

列表、count、profile card 等个人战报统计应复用同一个 repository predicate。

避免各 API 自己拼不同访问条件。

`UNION` 去重 owner 与 participant 重叠的记录；列表通过一次当前用户 relation 的 `LEFT JOIN`
读取参与角色。列表、总数及时间范围统计都不应从完整 generation 表开始扫描，回归测试使用实际
repository SQL 的 `EXPLAIN QUERY PLAN` 验证 owner user 索引和 participant user 索引。

来源判定统一为：存在任意该 generation 的 participant relation → `arena-multiplayer`，否则
`pvp_match_id` 非空 → `pvp`，其余 → `solo`。Arena Room 复用 generation authority 时也会写入
`pvp_*`，因此不能先按 PVP 字段分类，也不能仅凭当前查看者是否拥有 relation 判定来源。
`pvpOnly` 需要同时满足 `pvp_match_id IS NOT NULL` 和不存在该 generation 的 participant relation。

## 15. Access Scope

新增统一的访问语义：

```ts
type BattleReportAccessScope =
  | 'owner'
  | 'arena-participant'
  | 'pvp-participant';
```

建议提供类似：

```ts
resolveBattleReportAccessScope({
  userId,
  generationId,
})
```

统一处理：

1. generation owner；
2. Arena multiplayer frozen participant；
3. legacy PVP participant。

本次不建立通用 ACL 框架。

---

## 16. Participant 不等价于 Owner

新增 participant entitlement 后，不得直接把现有 owner detail DTO 原样开放给普通 Arena participant。

当前 generation detail 中可能包含：

- `templateId`
- `dataCardId`
- `dataCardUpdatedAt`
- `characterGuidance`
- combatant provenance

而多人 Room 原安全边界只承诺成员获得：

> room-safe shared projection

尤其 host-local 内容不得因为退出 Room 后访问个人页，而获得比当时房间内更大的信息范围。

因此：

### owner

继续允许现有 owner-safe detail。

### arena-participant

返回：

> multiplayer-safe historical detail projection

不得因 participant relation 暴露 host-local 完整来源信息。

### pvp-participant

保持当前 PVP 兼容行为，并在后续独立重构时再考虑统一。

---

## 17. Role 与 ACL 分离

虽然 participant 表保存：

```text
host
member
```

本次不要立即定义：

```text
host participant > member participant
```

即：

```text
role 是 provenance
不自动等于新的权限等级
```

Arena participant 无论 host / member，在本次历史详情路径均使用多人安全投影。

未来如果增加：

> 房主以历史配置重新创建房间

再单独设计 host-specific capability。

## 19. “重生战报”文案

现有：

```text
重生战报
```

实际上不会重新调用 AI，而是：

- 读取已保存正文；
- 加载 render snapshot；
- 重新 hydrate 战报卡 / Web 战报。

因此建议：

### 方案 A

改名：

```text
还原战报
```

### 方案 B

继续保留：

```text
重生战报
```

但 tooltip 明确：

> 使用已保存的战报正文重新还原战报展示，不会再次调用 AI。

本次 participant 历史实现不得增加“以原模型重新生成”的隐式能力。

## 20. 数据保留

participant relation 本身非常轻量，不需要和 R2 正文采用同一生命周期。

建议长期允许：

```text
generation metadata 存在
participant relation 存在
R2 正文已过期
```

个人页此时可继续显示：

```text
标题
时间
模式
角色身份
生成状态
```

正文不可用时：

```text
战报正文已超过保留期
```

不得把“R2 正文过期”等同于“用户从未参与过该 generation”。

## 21. Cleanup

Participant 表使用：

```sql
ON DELETE CASCADE
```

因此：

```text
删除 generation
=> 自动删除 participant relations
```

已有 generation cleanup eligibility 需要识别新 dependent table。

不得出现：

```text
generation 被删除
participant relation orphan
```

也不得因存在 participant row 导致 generation 永久无法执行正常 retention cleanup。

具体 cleanup 应按现有 dependency cleanup 顺序：

```text
dependent rows
-> generation
```

或依赖确认可用的 FK cascade。

## 22. Backward compatibility

### 22.1 历史数据

不做历史 Arena multiplayer participant backfill。

旧 Room 已清理后无法可靠证明：

```text
谁在 generation reservation 时属于 active participant snapshot
```

不得通过以下信息猜测：

- 谁后来查看过战报；
- 谁曾经提交 Proposal；
- 当前 Room members；
- generation title / metadata。

### 22.2 跨版本在途 generation

升级期间可能存在旧 checkpoint：

```text
participantUserIds 已存在
hostAccountUserId 缺失
```

因此 wire / recovery compatibility 可以暂时允许：

```ts
hostAccountUserId?: number
```

但所有新 generation reservation 必须生成该字段。

如果能证明：

```text
participantUserIds
```

但无法证明 role：

```text
participant relation 正常写入
role = NULL
```

不得猜测 host。

UI 显示：

```text
多人参与
```

### 22.3 Migration-first 发布前置条件

本纵切的 writer 和 reader 都依赖
[`0017_battle_report_generation_participants.sql`](../../drizzle/0017_battle_report_generation_participants.sql)。
现有 Preview / Hono 自动发布不执行 D1 migration，且 Preview 复用 production D1，
因此在激活任何包含本纵切的 Preview 或 production 版本之前，先完成以下顺序：

1. 经明确生产迁移授权后，使用根 `package.json` 的 `db:migrate:remote:prod` 应用 additive migration 0017。
   新表不改变旧 writer / reader，迁移期间可以继续运行旧版本。
2. 使用既有 `db:status:remote:prod:ready` 确认 migration history 无遗漏，并只读核验表和索引：

   ```sql
   SELECT name, type FROM sqlite_master
   WHERE name IN (
     'battle_report_generation_participants',
     'idx_battle_report_generation_participants_user_generation'
   );
   PRAGMA foreign_key_list(battle_report_generation_participants);
   ```

   应返回该表及 `(user_id, generation_id)` 索引，外键保持 generation/user 删除级联；
   migration 状态缺失或表、索引未就绪时，不部署依赖它们的新代码。
3. 部署 Hosted Hono writer，再部署 Web reader（含同版本 DR writer）。
4. 以 host/member 双账号完成一次真实多人 generation smoke：双方个人历史、详情与名片来源为多人，
   “仅 PVP”排除该记录，普通成员仍只能读取共享投影；检查旧单人与旧 PVP 历史正常。

回滚只回滚应用版本，保留 additive 表及已经落地的关系，不做破坏性回迁。
本地 SQLite 集成测试覆盖应用真实 0017 后旧 owner 查询/写入、参与关系读写与删除级联；
这不代替生产 D1 migration、远端 schema 核验或双账号线上 smoke。

## 23. 数据完整性约束

新 reservation 至少验证：

```text
participantUserIds 非空
participantUserIds 无重复
hostAccountUserId 为正整数
hostAccountUserId ∈ participantUserIds
participant 数量 <= MAX_ROOM_MEMBERS
```

Participant relation 持久化时：

```text
generationId 与 terminal generation 相同
只信任 frozen snapshot
role 只能为 host/member
```

## 24. 安全约束

不得：

- 接受客户端单独提交 participant IDs；
- 在 terminal 时重新查询 Room 作为历史 participant 权威；
- 将完整 Room membership snapshot 写入 generation D1；
- 将 participant IDs 暴露给不需要它们的 API；
- 因 participant relation 扩大 host-local 数据访问；
- 将 `role` 自动升级为新的 write permission。

---

## 25. 测试要求

至少新增以下回归覆盖。

### 25.1 Snapshot

- host + members 正确冻结；
- 离线但 active member 被包含；
- revoked member 不被包含；
- hostAccountUserId 必须位于 participantUserIds；
- participant 顺序规范化；
- historical retry 保持相同 participant/host snapshot。

### 25.2 Persistence

- completed generation 写入全部 participants；
- failed generation 写入全部 participants；
- cancelled/aborted 写入全部 participants；
- producer_lost 可恢复 participant relation；
- 非 multiplayer generation 不产生 participant rows；
- retry 不重复写入；
- finalization 中断后 reconciliation 可补齐；
- role 正确派生；
- legacy 无 host 信息写 `NULL`；
- 已有非空 role / participant 冲突被拒绝，partial retry 与 legacy `NULL` 保持兼容；
- 最大 32 人正常写入且不触发 D1 binding ceiling。

### 25.3 Query

- owner 可以看到单人 generation；
- Arena member 可以看到本人参与 generation；
- 非 participant 看不到；
- 后加入成员看不到历史 generation；
- generation 开始后退出的 participant 仍能看到；
- count 与 list 结果一致；
- pagination/filter/sort 保持正确。
- Arena 真实 `pvp_match_id` / `pvp_room_id` 与 participant relation 并存时仍标记多人，且被 PVP-only 排除；
- owner/participant 重叠不重复计数，列表及 count 的 query plan 使用 user 索引，不扫描完整 generation 表。

### 25.4 Authorization

- participant 能读取 multiplayer-safe detail；
- participant 不能读取 owner-only host-local provenance；
- unrelated user 返回 403/404，遵守现有 anti-enumeration 语义；
- PVP participant 既有路径不回归；
- regenerate/restore 使用相同 access scope。

### 25.5 Cleanup

- generation 删除后 participant rows 被删除；
- cleanup 不产生 orphan；
- participant relation 不导致 generation retention 永久失效。

## 27. 验收标准

本功能视为完成，当且仅当：

1. 多人 generation reservation 冻结完整 participant + host provenance；
2. terminal D1 中存在幂等 participant relation；
3. Room 被关闭或 TTL 清理后，参与用户仍可在个人页找到该 generation；
4. 后加入用户无法获得此前 generation 的长期归属；
5. generation 中途退出的原 participant 不丢失历史；
6. host/member 可被准确展示；
7. participant 不获得超出 Room-safe 边界的敏感 provenance；
8. completed / failed / aborted / producer_lost 生命周期均有测试；
9. finalization retry/reconciliation 不产生缺失或重复关系；
10. 旧单人 Arena、PVP、ranking、Room history 和 generation recovery 无行为回归。

## 28. 最终决策摘要

采用：

```text
独立 battle_report_generation_participants 窄关联表
+
frozen hostAccountUserId
+
participant role provenance
+
terminal idempotent persistence
+
统一 access scope
```

不采用：

```text
extra_json participant array 作为查询权威
完整 membership history
participant metadata 扩张
Proposal contributor 历史
旧数据猜测回填
```

该方案以很低的 D1 存储和维护增量，补齐 Arena multiplayer 的长期个人历史闭环，同时为 host/member 展示和未来有限权限能力保留高价值 provenance，但不扩张为通用多人历史系统。
