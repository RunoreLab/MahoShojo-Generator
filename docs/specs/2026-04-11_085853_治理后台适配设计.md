# 治理后台适配设计

更新时间：2026-04-11 08:58:53

## 1. 背景

自提交 `43a1ced0dea8998b07dc1fc134de996d3c5cc16a` 以来，生产分支 `feature/v0.2.0_Battle_Growth_MahoShojo` 已陆续落地以下治理相关能力：

- 站内消息系统
- 公开数据卡举报案件
- 巡查使与众查执行层
- 处理结果申诉
- 创作器元数据与角色参数展示能力

这些能力已经在用户侧 service、repository、表结构和部分页面中落地，但 `feat/admin` 分支的后台导航、仪表盘、`/api/admin/*` 接口与管理页尚未完成承接。当前后台仍主要覆盖用户、内容、竞技场、PVP、存储等传统模块，导致治理链路在后台缺少统一入口、运营看板和处理动作。

本设计用于定义本分支后台需要补齐的治理域页面、共享读模型、动作接口以及与现有内容管理页/仪表盘的联动方式，并据此指导后续开发。

## 2. 目标

- 为后台新增独立的“治理”模块组，正式接入消息、举报案件、众查、申诉四个子域。
- 让管理员能够在后台完成最小可用的治理闭环，而不是只依赖用户侧页面或直接改数据库。
- 保持“治理子域拆页 + 共享后台读模型/动作层”的结构，不把所有治理能力都塞回现有内容页。
- 为现有内容管理页补足必要联动：
  - 展示举报/众查/申诉状态
  - 在审核拒绝、封禁或处理时可选向作者发送消息
  - AI 辅助审查理由可自动回填到发送消息的原因输入中
- 为仪表盘补齐治理指标，避免后台入口继续失焦。

## 3. 非目标

- 本次不重构整个后台框架，不引入新的全局管理布局系统。
- 本次不补管理员严格鉴权；继续沿用“当前分支可暂不严格鉴权”的约定。
- 本次不做完整的治理平台化重构，例如统一 action log 总线、通用 case engine、审批工作流引擎。
- 本次不单独给 challenge / battle lite / beta access 开辟独立后台域，只补指标或信息展示入口。

## 4. 现状与缺口

### 4.1 已有基础

- 消息服务已支持：
  - 全站消息创建 `createSiteMessageEntry`
  - 定向消息创建 `createUserMessageEntry`
  - 全站消息立即失效 `expireSiteMessageNowEntry`
- 申诉服务已支持：
  - 管理员列表 `listReportAppealsForAdmin`
  - 管理员详情 `getReportAppealForAdmin`
  - 管理员复核 `reviewReportAppeal`
- 举报服务已支持：
  - 用户侧举报能力查询、提交、撤回
  - 创作者通知与处理结果通知
  - 自整改候选判定逻辑
- 众查服务已支持：
  - 巡查使资格判定
  - 派单、投票、过期推进、结果写回
  - 消息摘要中的众查红点聚合
- 创作器/角色参数已经可以通过共享组件展示。

### 4.2 后台当前缺口

- `pages/admin/index.tsx` 还没有治理模块组入口。
- `pages/api/admin/dashboard-stats.ts` / `lib/database/admin.ts` 尚未暴露治理统计。
- 后台缺少以下核心页面与 API：
  - `/admin/messages`
  - `/admin/report-cases`
  - `/admin/report-appeals`
  - `/admin/crowd-review/inspectors`
  - `/admin/crowd-review/cases`
- `pages/admin/content-management.tsx` 还无法：
  - 展示最新案件/众查/申诉联动状态
  - 在审核动作中选择“发送消息”
  - 复用 AI 审查理由填充消息原因
- 现有后台数据卡查询没有带出治理摘要字段，也没有作者用户 ID，无法稳定接入“给作者发消息”动作。

## 5. 方案比较

### 方案 A：只在现有内容管理页和仪表盘里打补丁

做法：

- 不新增治理子域页面
- 只在内容管理页加几列、几个弹窗和若干批处理按钮
- 仪表盘补几张统计卡

优点：

- 改动面最小
- 交付速度最快

缺点：

- 消息、举报、众查、申诉会被硬塞进“内容审核”语义里，后续继续膨胀
- 与现有 service / repository 的自然边界不一致
- 众查案件、巡查使资格、申诉复核都不是“内容页附属功能”

结论：

- 不推荐，只适合临时排障，不适合作为本分支正式后台方案。

### 方案 B：按治理子域拆页，补共享后台读模型与动作层

做法：

- 新增治理模块组和独立页面
- 后端为各子域补 `/api/admin/*` 和共享读模型
- 内容管理页只保留必要联动信息与“发送消息”入口

优点：

- 与现有消息 / 举报 / 众查 / 申诉的数据边界一致
- 页面职责清晰，后续迭代不会继续堆到一个页面
- 可以逐域演进，避免一次性平台化过度设计

缺点：

- 首次接入需要补多张页面和多组 API
- 需要在后台建立一层新的治理读模型

结论：

- 推荐方案。本次实现按此方案推进。

### 方案 C：直接做统一“治理中台”

做法：

- 一次性抽象统一 case / appeal / message / inspector / action log 平台
- 所有治理动作经统一流程编排

优点：

- 理论上的长期扩展性最好

缺点：

- 超出当前分支目标
- 会把已有 service 边界推倒重来
- 当前后台缺口是“尚未接入”，不是“架构无法承载”

结论：

- 当前不做。

## 6. 最终设计

### 6.1 后台信息架构

后台首页新增一个治理模块组，包含：

- `消息管理` `/admin/messages`
- `举报案件` `/admin/report-cases`
- `申诉复核` `/admin/report-appeals`
- `巡查使管理` `/admin/crowd-review/inspectors`
- `众查案件` `/admin/crowd-review/cases`

同时保留现有“内容与审核”模块，但其描述和跳转语义要调整为“治理联动入口”，而不是治理主入口。

### 6.2 仪表盘与统计 API

仪表盘需新增治理统计区块，建议包含：

- `openReportCasesTotal`
- `underReviewReportCasesTotal`
- `activeCrowdReviewRoundsTotal`
- `submittedReportAppealsTotal`
- `activeInspectorsTotal`
- `recentSiteMessagesTotal`
- `recentDirectMessagesTotal`

这些统计通过 `lib/database/admin.ts` 新增治理 section 计算，并在首页显示治理总览卡与治理模块入口卡。

### 6.3 消息管理后台

#### 页面职责

`/admin/messages` 提供三类能力：

- 发送全站消息
- 发送定向消息
- 查看最近运营消息状态

#### API 设计

- `GET /api/admin/messages`
  - 返回最近 `site_messages` 与 `user_messages`
  - 支持按 scope、templateKey、messageType、recipientUserId 过滤
- `POST /api/admin/messages/site`
  - 创建全站消息
- `POST /api/admin/messages/direct`
  - 向一个或多个用户发送定向消息
- `POST /api/admin/messages/site/[id]/expire`
  - 让全站消息立即失效

#### 交互要求

- 支持模板键选择、标题/正文兜底、优先级、过期时间
- 支持直接输入用户 ID 列表发送定向消息
- 首版不做复杂的“按筛选条件批量圈选用户”界面，而是保留手工 userId 列表和后续其他页面联动入口
- 需要显示消息是否已过期、来源实体、最近发送时间

### 6.4 举报案件后台

#### 页面职责

`/admin/report-cases` 是治理中枢，负责展示和处理案件事实层状态。

#### 后台列表必须展示

- 案件 ID、状态、结案口径
- 目标卡 ID / 名称 / 作者
- 有效举报数
- 理由摘要、引用摘要、补充说明摘要
- 是否已通知创作者
- 是否为自整改候选
- 是否存在活跃众查轮次
- 是否存在活跃申诉
- 最新举报时间 / 更新时间

#### 详情页必须展示

- 举报时目标卡快照
- 当前目标卡版本
- 活跃举报明细与引用
- 处理通知状态
- 众查轮次摘要
- 申诉摘要

#### 动作边界

首批后台动作至少包含：

- 进入详情查看
- 给作者发送处理说明消息
- 作为内容管理联动的跳转目标

更重的结案、改判、处罚动作可在读模型稳定后继续补，但本次结构上要为这些动作预留独立 action API。

### 6.5 申诉复核后台

`/admin/report-appeals` 直接复用现有 service。

#### 页面能力

- 列表筛选 `submitted / under_review / resolved`
- 详情查看：
  - 申诉原因
  - 申诉材料引用
  - 案件快照 vs 当前案件状态
  - 目标卡 / 发起人 / 被处理人
- 复核动作：
  - `upheld`
  - `overturned_no_violation`
  - `reopened_under_review`

#### API 设计

- `GET /api/admin/report-appeals`
- `GET /api/admin/report-appeals/[appealId]`
- `POST /api/admin/report-appeals/[appealId]/review`

### 6.6 巡查使与众查后台

拆成两个页面：

- `/admin/crowd-review/inspectors`
- `/admin/crowd-review/cases`

#### 巡查使管理

页面能力：

- 查看资格状态、暂停截止时间、原因码、原因说明、最近更新时间
- 执行授予、暂停、撤销、恢复
- 写入纪律事件

数据层要求：

- 基于 `crowd_review_inspectors`
- 新增纪律事件 repository/service 边界

#### 众查案件管理

页面能力：

- 查看轮次状态、截止时间、票型摘要、有效票数、结果码
- 查看派单与投票详情
- 查看是否升级管理员处理

首批动作边界：

- 管理员接管
- 撤销轮次
- 平票升级
- 改判留痕

本次开发至少要把列表/详情与 action API 骨架建立出来，后续动作可在此基础上继续扩展。

### 6.7 内容管理页联动

现有 `pages/admin/content-management.tsx` 不是治理主页，但必须补四类联动。

#### 联动一：治理状态列/徽标

数据卡列表新增治理摘要徽标：

- 最新举报案件状态
- 是否众查冻结
- 是否有活跃申诉
- 是否自整改候选

点击后跳转到对应案件或申诉页。

#### 联动二：审核/封禁时可选发送作者消息

在以下动作中提供“发送消息”选项：

- 审核拒绝
- 设为封禁

消息默认使用：

- 审核拒绝：`user.moderation.data_card_rejected`
- 数据卡封禁：`user.moderation.data_card_banned`

消息发送必须是可选动作，不勾选时只更新状态，不写 `user_messages`。

#### 联动三：AI 审查理由自动回填

AI 审查结果与外部 AI 解析结果都已经有 `reason` 字段。本次要求：

- 当管理员从 AI 审查弹窗执行“拒绝”动作时，若勾选发送消息，默认把该 `reason` 填入消息原因
- 当管理员在主列表里手动对选中项执行“拒绝并发送消息”时，若这些项刚刚来自 AI 解析结果，也优先回填对应理由

这样管理员不用在“AI 已经给出理由”的情况下重复手打。

#### 联动四：内容详情里展示新元数据

在详情对话框或摘要区展示：

- creator 相关元数据
- 角色参数摘要

避免管理员只能读原始 JSON 判断。

### 6.8 数据卡管理页面与作者消息联动

后台数据卡查询需要补齐以下字段：

- `userId`
- `latestReportCaseId`
- `latestReportCaseStatus`
- `latestReportCaseResolutionCode`
- `hasActiveCrowdReview`
- `hasActiveAppeal`
- `isSelfRemediationCandidate`

这些字段既用于列表显示，也用于“给数据卡作者发消息”。

### 6.9 共享后台数据层

本次新增一层治理后台读模型/动作层，避免页面直接拼 repository：

- `lib/admin/messages.ts`
- `lib/admin/report-cases.ts`
- `lib/admin/crowd-review.ts`

职责：

- 组合多个 repository / service 输出后台 DTO
- 在 mapper / adapter 边界完成命名转换
- 屏蔽页面对底层表结构的了解

### 6.10 命名与边界约束

- SQL / schema 继续使用 `snake_case`
- admin DTO / 页面状态统一 `camelCase`
- 跨层字段由后台 adapter 集中映射
- 不允许在页面层直接零散兼容 `snake_case`

## 7. 实施顺序

推荐顺序如下：

1. 先补仪表盘治理入口和统计，建立导航可达性
2. 先实现 `report-appeals` 后台，因为 service 已完备、交付最快
3. 再实现 `messages` 后台，复用现有 service 并为内容管理联动打基础
4. 再扩展内容管理页，加入治理摘要与“发送消息”动作，接通 AI 理由回填
5. 再实现 `report-cases` 后台读模型与基础详情页
6. 最后实现 `crowd-review inspectors/cases` 后台基础页与动作骨架

## 9. 风险与取舍

- `report-cases` 和 `crowd-review` 管理动作目前在用户侧 service 之外，首批需要补 action 层，容易出现“只读先行、写操作后补”的阶段性不均衡；本次优先保证后台可观察和可联动。
- 内容管理页会继续承担“快速审核入口”职责，但不应让它取代治理主页；因此只补摘要与消息联动，不堆叠完整案件处理流程。
- 消息后台首版不做复杂人群筛选器，优先保证与治理联动、全站消息和定向消息的基础能力。
- 后台暂不严格鉴权符合当前分支约定，但上线前必须补强。
