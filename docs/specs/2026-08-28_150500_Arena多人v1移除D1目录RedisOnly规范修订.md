# Arena 多人 v1 移除 D1 Room Directory / Redis-only 规范修订

状态：`accepted`
日期：2026-08-28
修订标识：`SPEC-arena-multiplayer-redis-only-directory-amendment-v1`
适用分支：`feat/arena-multiplayer-hono-redis` 及后续并轨分支
决策基线观察：`ad2c9328d2300c854ee44f37b542df04e5374b3f`

## 1. 目的与结论

Arena 多人 v1 撤出 D1 Room Directory。首发房间运行时、活动房间发现与加入校验统一以 Redis 为运行时数据边界。

本修订的核心结论：

1. `drizzle/0014_arena_multiplayer_rooms.sql` 不进入 v1 生产迁移链，不得在 production/preview/其他共享远程环境执行。
2. `arena_multiplayer_rooms` 不再是 v1 目标 schema。
3. Redis Room checkpoint 继续是活动 Room authority；活动房间 discovery index 也改为 Redis 派生索引。
4. 删除 GMR-06 为 Redis -> D1 派生投影引入的 registration compensation、D1 tombstone、D1 reconciliation 等跨存储一致性机制。
5. 保留存储无关的 Room directory 产品契约和 UI/API 语义；“发现房间”功能不因移除 D1 而取消。
6. 未来只有在有可测量的新增价值时，才通过新的 ADR / spec 重新决定是否引入 D1 或其他目录存储；不得把 GMR-06 历史实现自动恢复为当前设计。

该调整不否定项目已有 D1 用途。账户、线上数据卡、排位、治理、generation durable facts 等既有持久业务数据不在本修订范围内。

## 3. 为什么移除 D1 directory

### 3.1 D1 没有增加 Room authority 或恢复能力

当前设计中，即使存在 D1 row：

- join 仍必须重新读取并验证 Redis checkpoint；
- Redis checkpoint absent / expired 时 D1 不得复活 Room；
- Redis/VPS 整体丢失时 v1 本就允许活动 Room 中断并创建 replacement Room；
- D1 row 不能证明 current `roomEpoch` authority，也不能恢复 membership、Proposal、generation reservation 或 replay fence。

因此 D1 directory 在 v1 中只提供第二份发现元数据，而没有提供独立的正确性或恢复价值。

### 3.2 主要成本来自跨存储一致性，而不是表本身

GMR-06 为保持 Redis authority 与 D1 derived index 一致，已经需要：

- `pending-create -> projecting -> active -> closing` registration 状态；
- exact epoch / host / checkpoint fence；
- create 与 cleanup 的 Redis Lua 线性化保护；
- D1 write 成功但 confirm 失败的补偿；
- closing tombstone；
- registration reconciler；
- 独立 D1 orphan reconciler；
- v1 registration rolling migration；
- 多种 malformed / absent / terminal / concurrent replacement 竞态验证。

这些机制本身实现正确，但其复杂度是“双存储派生索引”的附加成本，不是 Arena 多人业务本身的必要复杂度。

### 3.3 Redis 足以承担首发 discovery

活动 Room 本来就是 Redis TTL 生命周期数据。Redis sorted set 可以提供有界排序与分页，Room checkpoint 又能作为最终验证来源。

v1 不需要为“以后可能跨运行时发现”预先承担 D1 schema、补偿状态机和 reconciliation 维护成本。

## 4. Redis-only directory contract

### ROOMDIR-R001 authority

Redis Room checkpoint 仍是活动 Room 的唯一 session authority。

任何 directory index 都是 derived index，不能：

- 创建或恢复 Room；
- 覆盖 checkpoint 中的 `roomEpoch`、host、membership、lifecycle；
- 让 absent/expired Room 重新可加入。

### ROOMDIR-R002 public discovery index

v1 SHOULD 使用一个有界 Redis sorted set 维护 public Room 候选，例如：

```text
arena:room-directory:public:v1
  member = roomId
  score  = directoryActivityAt / lastActivityAt epoch milliseconds
```

具体 key prefix 必须继续服从现有 `ROOM_REDIS_*` namespace 配置，不得把上述示例字符串硬编码为新的跨环境公共契约。

查询 SHOULD 使用 Redis `ZRANGE ... REV ... LIMIT` 或等价 API，并对候选 Room 做批量/pipeline checkpoint load。

返回 public item 前 MUST 验证：

- checkpoint 存在且严格可解析；
- lifecycle 为 open；
- visibility 为 public；
- `roomId` 与 checkpoint 一致；
- 当前 checkpoint 未因 deadline/TTL 失效。

发现 stale candidate 时 MAY lazy `ZREM`。stale index member 不能产生成功 join。

### ROOMDIR-R003 host discovery index

若产品需要“我的活动房间”列表，v1 MAY 使用 per-host sorted set，例如：

```text
arena:room-directory:host:<userId>:v1
```

返回前仍必须验证 current checkpoint host 与 lifecycle。

如果实际产品没有 host list 需求，不得仅为了结构对称新增该索引。

### ROOMDIR-R004 unlisted join

unlisted Room 不依赖 public directory。

已知 `roomId` 的 join/session/ticket 流程 MUST 直接进入当前 server authority + Redis checkpoint 校验，不得要求 Room 先出现在 public index。

### ROOMDIR-R005 index update

影响发现语义的 authority transition SHOULD 在与 checkpoint 提交同一 Redis 原子边界内更新/删除必要 index member，优先复用现有 Lua / transaction，而不是再建立异步跨系统补偿协议。

至少包括：

- create：public Room 加入 public index；
- visibility change（若 v1 暴露）：按新 visibility add/remove；
- close / terminal cleanup：移除 public/host index；
- activity ordering：只在已经发生的低频 authority-changing checkpoint 上更新；presence/chunk 等高频 lossy 事件不得为了排序额外写 directory。

如果未来证明“每个 authority checkpoint 都更新 score”产生不必要写放大，可以降低 activity score 更新频率；这不改变 checkpoint authority。

### ROOMDIR-R006 stale / Redis loss

Redis index 与 Redis checkpoint 同故障域是 v1 有意接受的约束：

- checkpoint TTL/删除后，index stale member只可被过滤/清理；
- Redis 整体数据丢失时，活动 Room 和 directory 一并丢失；
- v1 可要求用户创建 replacement Room；
- final generation / settlement / account 等 durable facts 仍由既有持久层保证。

不得为了掩盖该 v1 可用性边界而恢复 D1 row 并把它解释成 Room 恢复依据。

## 5. v1 明确删除的 GMR-06 机制

以下机制从当前 v1 目标态删除：

- D1 `arena_multiplayer_rooms` table；
- `D1RoomDirectoryStore`；
- Redis `RoomDirectoryRegistrationStore` 及其 `pending-create/projecting/active/closing` 状态机；
- Redis -> D1 projection confirm；
- D1 exact-epoch delete；
- D1 closing tombstone；
- registration reconciler；
- 独立 D1 orphan reconciler；
- registration v1 -> v2 migration；
- production/preview D1 Room directory migration / rollback runbook 要求；
- 为上述机制专门增加的 physical D1 probe / SQLite migration contract。

以下内容应保留：

- `RoomDirectoryEntry/Page/Query` 等存储无关 contract；
- public/unlisted 产品语义；
- bounded pagination、cursor/limit hard cap；
- return 前对 current Redis authority 的严格验证；
- stale candidate 不得复活 Room；
- API 鉴权、Origin、rate-limit、ticket、membership、epoch fence；
- GMR-06 中发现的竞态与安全经验，作为未来重引入 D1 时的参考。

## 7. Migration 处理

根据 GMR-06 验收记录：

- `0014` 只在隔离 SQLite 测试执行；
- 未执行 production/preview remote migration/write；
- 未创建需要清理的生产 Room directory data。

因此当前预期处理是：**在并轨/发布前从迁移链删除 `0014`，无需生产 down migration。**

但是实现清理时仍 MUST 做一次 fail-closed 检查：

1. 确认目标 production/preview migration history 中不存在 `0014`；
2. 确认没有人为或外部流程提前创建 `arena_multiplayer_rooms`；
3. 若发现共享/远程环境已经应用，不得按本文直接 `DROP TABLE`；另立带备份/回滚的 schema cleanup 操作记录。

不得因为当前日志显示“未远程执行”而把“删除 migration 文件”泛化为任何环境都可无审计删除 schema。

## 8. 测试与退出门禁

D1 directory 清理完成后至少必须通过：

1. create public Room -> Redis checkpoint + public index 可发现；
2. unlisted Room 不进入 public index，但已知 roomId 可 join；
3. list candidate checkpoint absent -> 不返回并 lazy cleanup；
4. list candidate closed/expired -> 不返回；
5. stale/wrong epoch index 信息不能覆盖 current checkpoint；
6. close -> index remove；
7. Redis restart/AOF 后已确认 checkpoint 与必要 directory index 行为符合现有恢复口径；
8. Redis unavailable 时 authority-changing command 继续 fail closed；
9. public list 有硬 limit/cursor/bounded work；
10. GMR-07 create/list/join/session/ticket/leave/close 与 Web UI tests 不回归；
11. Proposal/generation 后续切片不依赖 D1 directory side effects；
12. repository 不再包含 `arena_multiplayer_rooms` schema/migration/runtime D1 write；
13. production/preview 不新增 D1 Room migration；
14. `pnpm ci:verify` 与 `git diff --check` 通过。

## 9. 未来重新评估 D1 的触发条件

只有出现至少一个可量化需求，才重新立项评估 D1 / Durable Object / 其他目录后端：

1. public Room 数量或 Redis directory 内存/查询延迟达到已定义容量阈值；
2. 需要跨多个 Redis cluster、VPS 或 RoomRuntime backend 的统一发现面；
3. 需要 Room runtime 故障后仍保留“可发现但明确不可加入/可恢复”的 durable registration，并且该信息本身有产品价值；
4. 需要 SQL 型复杂筛选、搜索、运营审核或历史目录，而 Redis index 明显不适合；
5. Cloudflare DR / multi-region 方案要求一个独立目录控制面，并能证明其在故障时提供真实恢复或路由价值；
6. Redis-only directory 的实际故障或维护数据证明第二存储可以降低而不是增加系统复杂度。

重新引入时必须回答：

- D1 保存的事实是什么，为什么不能只从 current Room authority 推导？
- 它是 authority、durable registration 还是 derived index？
- Redis/D1 双写失败的用户可见语义是什么？
- 是否真的需要 compensation/reconciliation？
- Room runtime 丢失时 D1 row 能做什么，不能做什么？
- migration、DR、成本和删除策略是什么？

没有这些答案，不得仅因“以前已经实现过”恢复 GMR-06。
