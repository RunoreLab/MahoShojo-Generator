## 1. 背景

当前仓库已经具备两类成熟能力：

1. 以 [`pages/details.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/details.tsx) 为代表的问卷生成链路
   - 支持多问卷叠加
   - 支持跳题、条件显示、草稿保存与恢复
   - 支持问卷导入、数据库加载、问卷保存为数据卡
2. 以 [`pages/free.tsx`](/home/notuhao/code/MahoShojo-Generator/pages/free.tsx) 为代表的模板选择与通用卡生成链路
   - 支持角色卡/情景卡
   - 支持通用 Markdown 卡与结构化模板
   - 已形成稳定的流式/非流式能力边界

新增创作生成页的目标，不是重新发明一套全新页面，而是把“问卷输入”升级为“多输入源创作工作台”：

- 问卷仍然负责叙事、背景、人格与世界观补充
- 新增车卡规则输入负责点数、专长、预算、派生值等结构化规则信息
- 保留独立的自由文本补充输入，承载风格偏好、禁忌、附加要求

## 2. 设计目标

### 2.1 本次目标

1. 新增创作生成页 `/creator`
2. 在复用 `/details` 的前提下，引入可扩展的车卡规则输入层
3. 支持多问卷、多规则、自由文本补充同时参与一次生成
4. 结果卡中区分：
   - 生成留痕
   - 当前规则状态
5. 第一阶段接入第一套规则预设 `arena-trpg-lite`

### 2.2 明确非目标

1. **第一阶段不新增 TRPG 专用角色卡模板**
   - 输出模板继续复用现有体系
2. **第一阶段不把规则数据写进卡正文**
   - 规则数据只由程序维护
3. **第一阶段不实现用户自定义规则编辑器**
   - 仅为未来预留规则模型与存储边界
4. **第一阶段不把 `arena-trpg-lite` 扩展成完整 TRPG 编辑器**
   - 不做技能树、PCP、魔装构筑、羁绊预算等复杂模块

## 4. 页面结构

创作生成页在 `/details` 现有结构上新增下列区块：

1. 输出模板区
   - 选择本次最终生成的模板
2. 自由文本补充区
   - 输入创作要求、风格偏好、禁忌、额外说明
3. 问卷区
   - 继续使用现有多问卷与题目流能力
4. 车卡规则区
   - 选择多套规则
   - 指定主规则
   - 填写各规则 block 输入
5. 输入摘要区
   - 汇总模板、问卷、主规则、补充规则、关键派生值
6. 生成结果区
   - 展示卡正文结果
   - 单独展示程序维护的规则摘要面板，不混入正文

## 5. 输入模型

创作页输入统一分为 4 层：

1. `generationTemplate`
2. `questionnaires`
3. `buildRules`
4. `freeformBrief`

### 5.1 `generationTemplate`

决定本次最终输出什么卡，不承担输入留痕职责。

### 5.2 `questionnaires`

- 继续沿用现有问卷定义与答案模型
- 负责叙事、背景、人格、世界观补充
- 不承载规则点数、预算与程序派生值

### 5.3 `buildRules`

- 新增规则输入层
- 支持多规则并行启用
- 用户必须在已选规则中指定一套主规则
- 规则数据的权威来源只能是程序，不是 AI

### 5.4 `freeformBrief`

- 独立输入源
- 用于承载：
  - 创作要求
  - 人物气质
  - 风格偏好
  - 禁忌/避雷
  - 其他无法被问卷或规则块自然表达的说明
- 不伪装成问卷答案
- 不拆进规则 block
- 在 prompt 中优先于问卷与规则解释层，但不覆盖结构化规则结果

## 6. 规则预设模型

### 6.1 规则预设目录

建议新增独立目录：

- `public/build-rules/presets/index.json`
- `public/build-rules/presets/*.json`

不与问卷目录混用。

### 6.2 规则预设顶层字段

规则预设至少需要声明：

- `id`
- `title`
- `description`
- `version`
- `supportedTemplates`
- `allowStandalone`
- `mainRuleEligible`
- `projectionPolicy`
- `aiPromptHint`
- `uiSummary`
- `blocks`
- 可选 `budgets`
- 可选 `derivedStats`

其中：

- `supportedTemplates` 为必要字段
  - 创作页本身支持角色卡与情景卡
  - 每套规则必须自己声明它能服务哪些模板
- `mainRuleEligible`
  - 决定该规则能否被选为主规则
- `projectionPolicy`
  - 第一阶段仅支持：
    - `primary-structured`
    - `reference-only`

### 6.3 类型化规则块

第一阶段采用“类型化规则块”路线，不走固定字段模型，也不引入过重通用 DSL。

第一阶段要求 block 至少支持：

- `section`
- `select`
- `multi-select`
- `number`
- `point-buy`
- `derived`

后续预留：

- `repeatable-list`
- `tree-select`

### 6.4 `multi-select` 的预算能力

`multi-select` 不应只支持“纯多选”，还应支持可选预算机制，例如：

- 每个选项声明 `cost`
- block 自身声明 `selectionBudget`
- 程序负责校验总花费是否超限

这样未来出现“专长需要花费点数”的规则时，不需要再发明新的 block 类型。

## 7. 多规则模型

### 7.1 多规则并存

- 允许用户同时启用多套规则
- 允许不同规则中出现同名字段，例如不同世界观下都存在 `STR`
- 这些字段默认不视为冲突，因为它们属于不同规则上下文

### 7.2 主规则与补充规则

- 用户必须指定 `primaryRuleId`
- 主规则作为主要结构化投影来源
- 其他规则作为补充参考输入

### 7.3 规则结果标识

第一阶段采用最小标识模型：

- `ruleId`：必有
- `version`：建议保留
- `ruleInstanceId`：可选，第一阶段不强制

第一阶段不引入额外 `namespace` 字段。

原因：

- `rules[]` 数组项本身就是天然隔离空间
- 多规则但不重复时，`ruleId` 已足够引用
- 额外 `namespace` 成本高于收益

## 8. 投影模型

规则预设与输出模板之间通过“投影”连接，而不是直接绑定。

投影的定义：

- 是程序在“生成时”或“页面预览时”根据 `buildState` 计算出的模板消费视图
- 不是原始持久化数据
- 不是卡正文内容

### 8.1 `primary-structured`

含义：

- 可作为主规则
- 程序会把该规则整理成高优先级、结构化、稳定的模板输入视图
- AI 必须尊重其中规则事实，但不得修改数值

处理方式：

1. 找到 `primaryRuleId` 对应规则
2. 提取核心 `blockResults`、`derived` 与必要校验摘要
3. 组装成面向当前模板的一份结构化摘要
4. 在 prompt 中作为固定事实提供给 AI

### 8.2 `reference-only`

含义：

- 只作为补充参考
- 可提供世界观、风格、附加限制或辅助灵感
- 不覆盖主规则的结构化事实

处理方式：

1. 提取适合展示的参考摘要
2. 在 prompt 中以较低优先级提供给 AI
3. 不强制映射到目标模板主体字段

## 9. 留痕与规则状态

### 9.1 `creationInputs`

职责：

- 只表示生成留痕
- 保存生成时使用过的输入快照

建议保存：

- `template`
- `freeformBrief`
- `questionnaires`
- `questionnaireAnswers`
- `buildRules`
- `primaryBuildRuleId`

粒度约束：

- 默认不内嵌完整问卷定义快照
- 默认不内嵌完整规则预设定义快照
- 只保留：
  - `questionnaireId` / 可选 `version`
  - 答案结果
  - `ruleId` / `version`
  - 规则输入结果与派生值

### 9.2 `buildState`

职责：

- 保存当前附着在卡上的、由程序维护的权威规则状态
- 用于后续程序化修改、重新计算派生值、故事生成输入

若本次生成未选择任何车卡规则，则结果中不写 `buildState`。

最小结构：

```json
{
  "buildState": {
    "primaryRuleId": "arena-trpg-lite",
    "rules": [
      {
        "ruleId": "arena-trpg-lite",
        "version": "1.0.0",
        "blockResults": {},
        "derived": {},
        "validationSummary": {}
      }
    ]
  }
}
```

约束：

- `primaryRuleId` 只引用 `rules[]` 中的一条
- `rules[]` 保存当前权威规则状态，不是生成时快照
- `blockResults` 只存用户输入或程序维护的原始结果
- `derived` 只存程序计算出的派生值
- `validationSummary` 只存程序校验摘要
- 第一阶段不持久化运行态字段，例如：
  - `dirty`
  - `disabled`
  - `source`

## 11. 程序职责边界

### 11.1 前端负责

- 规则 block 输入状态维护
- 主规则选择
- 派生值实时计算
- 预算与上下限校验
- 草稿保存与恢复

### 11.2 后端负责

- 统一整理 prompt 输入
- 最终一次规则数据合法性校验
- 生成结果并正确落盘：
  - 正文模板结果
  - `creationInputs`
  - `buildState`

### 11.3 AI 负责

- 基于程序整理好的输入生成卡正文内容

AI 明确不负责：

- 决定规则值
- 修改规则值
- 重算派生值
- 自动修复程序校验失败的数据

---

## 12. 提交流程

1. 用户点击生成前，前端先做本地校验
2. 若存在以下情况，则不发请求：
   - 主规则未选
   - 规则预算校验失败
   - 必填 block 缺失
3. 请求发出时，提交统一输入包
4. 后端再次做兜底校验
5. 若规则数据非法，直接返回结构化错误，不让 AI 猜修复
6. 若 AI 生成失败：
   - 保留问卷、规则、自由文本输入
   - 不清空 `buildState`
   - 不回滚草稿
7. 若生成成功：
   - 写入正文模板结果
   - 写入 `creationInputs`
   - 写入 `buildState`

错误反馈约束：

- 明确区分：
  - 规则校验失败
  - AI 生成失败

## 13. 流式与非流式边界

第一阶段沿用现有成熟能力边界：

- `non-stream` 支持所有创作页输出模板
- `stream` 只支持：
  - 通用角色卡
  - 通用情景卡

原因：

- 可最大化复用现有流式 Markdown 输出与卡片转换链路
- 避免第一阶段在结构化模板上同时推进流式协议、模板约束与复杂输入拼装

## 14. 第一套规则预设：`arena-trpg-lite`

### 14.1 模板支持边界

虽然创作页本身支持情景卡，但 `arena-trpg-lite` 第一阶段只服务角色卡模板。

对应设置：

- `supportedTemplates = ["general", "magical-girl"]`

### 14.2 第一阶段 block 范围

1. `powerLevel`
   - `select`
   - 选项：
     - `seed`
     - `sprout`
     - `leaf`
     - `bud`
     - `flower`
     - `gemScepter`
2. `coreAttributes`
   - `point-buy`
   - 字段：
     - `STR`
     - `CON`
     - `AGI`
     - `MAG`
     - `WILL`
     - `PER`
     - `CHM`
   - 受力量层级预算限制
3. `specialties`
   - `multi-select`
   - 支持可选 `cost + selectionBudget`
   - 第一阶段内容参考原作“心之花体系与能力边界（留空规则）”中的基础能力模块：
     - 魔力放出：魔弹、魔力冲击、魔炮
     - 防御：魔力护盾
     - 强化：身体强化、魔力附着
     - 飞行与机动：悬浮、魔力受身、炮弹起射、永动飞行、超速闪现
     - 魔力感知：感知强化、环境魔力侦测
   - 第一阶段主要作为 AI 参考输入，不做复杂联动
4. `derivedStats`
   - `derived`
   - 展示：
     - `HP`
     - `MP`
     - `Radiance`
5. `ruleNotice`
   - `section`
   - 展示简化规则说明与边界提示

### 14.3 第一阶段明确不做

- 技能树
- 技能点分配
- PCP
- 魔装构筑
- 羁绊预算
- `repeatable-list`
- `tree-select`

## 15. 兼容策略

若未来卡中引用的 `questionnaireId` 或 `ruleId` 已不存在、下线或版本不兼容：

- 保留已有答案与规则结果
- 允许继续查看
- 页面提示“原预设缺失”
- 缺失部分输入区改为只读
- 若用户想继续编辑该部分，需手动重新选择新预设

## 17. 当前结论

本次设计已经明确：

1. `/creator` 是基于 `/details` 复制后增量改造的创作工作台
2. 问卷、车卡规则、自由文本补充是并列输入层
3. 规则数据只由程序维护，不进入正文
4. `creationInputs` 与 `buildState` 分离，分别承担“生成留痕”和“当前规则状态”
5. 第一阶段以独立 API、现有模板复用、`arena-trpg-lite` 轻量接入为主

后续若进入实现规划，应以本规格为基准拆解：

- 页面状态
- 规则预设加载
- 规则 block 校验
- 新 API
- 结果落盘
- 回归测试
