# 举报流引用公开卡查看态设计规格

更新时间：2026-04-08 12:00:00

## 1. 目标

在“公开数据卡举报”流程内，为“引用公开数据卡”提供可查看能力，方便用户在填写举报时核对被引用卡的当前公开内容。

本次只解决举报流程内的查看问题，不扩展为站内通用公开详情页能力。

## 2. 非目标

- 不新增通用公开数据卡详情页面。
- 不在查看态内提供“更多”“举报此卡”“标签编辑”等无关动作。
- 不实现多引用卡的上一张 / 下一张切换。
- 不展示引用添加当时的历史快照；查看内容以当前最新公开版本为准。

## 3. 方案选择

### 方案 A：举报流内切换到引用卡查看态

做法：

- 在举报模态中点击某条公开卡引用后，进入“引用卡查看态”。
- 查看态与举报表单属于同一流程，不新开页面，不额外叠第三层模态。
- 返回举报后完整保留草稿状态。

优点：

- 范围最小。
- 可复用现有数据卡详情展示能力。
- 避免三层模态导致的焦点、滚动和关闭路径复杂化。

缺点：

- 不是通用详情页能力。
- 多张引用卡时需要返回列表重新选择。

### 方案 B：再叠一层详情模态

不采用。会把当前链路变成“详情模态 -> 举报模态 -> 引用卡详情模态”，交互过重。

### 方案 C：新建公开详情页

不采用。已超出本次“只解决举报流查看入口”的范围。

### 结论

采用方案 A。

## 4. 用户流程

1. 用户在数据卡详情中打开举报模态。
2. 用户填写理由、说明，并添加一个或多个“公开数据卡引用”。
3. 用户点击某条引用旁的“查看”。
4. 举报模态切换到“引用卡查看态”。
5. 用户查看该公开卡的当前最新公开内容，必要时下载 JSON。
6. 用户点击“返回举报”。
7. 返回原举报表单，已填写草稿全部保留。

补充关闭语义：

- 查看态中的“返回举报”仅切回举报表单，不关闭整个举报流程。
- 查看态右上角关闭按钮、遮罩点击和 `Esc` 行为与举报模态本身保持一致：直接关闭整个举报模态。
- 直接关闭整个举报模态后，本次内存态草稿一并释放；仅“返回举报”保证草稿保留。

## 5. 查看态展示范围

查看态应展示：

- 卡名
- 简介
- 作者
- 当前最新公开内容
- 下载按钮

查看态不展示：

- 更多
- 举报此卡
- 标签编辑
- 其他与“核对引用证据”无关的次要动作

## 6. 数据口径

### 6.1 内容版本

查看态展示的是被引用公开卡的当前最新公开版本。

### 6.2 权限边界

仅允许查看当前仍然公开、可读、未删除且审核通过的数据卡。

若用户点击查看时，该引用目标已不再可访问，则查看态显示明确错误提示，不影响已填写的举报草稿。

### 6.3 下载

允许在查看态中保留下载按钮，下载内容为当前最新公开版本的 JSON。

## 7. 组件边界

### 7.1 `DataCardReportModal`

保持举报表单状态拥有者身份，负责：

- 举报理由、说明、引用草稿状态
- 当前是否处于“表单态 / 引用卡查看态”
- 当前正在查看哪一条公开卡引用

### 7.2 新的只读详情展示层

从现有 `DataCardDetailsModal` 中抽出可复用的只读展示能力，形成一个更小的展示组件，负责：

- 渲染卡片的只读详情内容体
- 只消费稳定输入字段，不自行决定场景动作
- 支持在举报查看态内复用
- 不携带举报、标签编辑等业务动作

建议拆成两层：

- 共享只读内容体：负责展示卡名、简介、作者、主体内容与基础只读元信息。
- 场景容器动作区：由外层容器决定是否显示下载、返回举报、关闭等按钮。

共享只读内容体的最小输入字段应明确为：

- `card.id`
- `card.name`
- `card.description`
- `card.author`
- `card.type`
- `card.data`
- `card.isPublic`
- `card.createdAt`
- `card.updatedAt`
- `mode = 'full-details' | 'report-reference-preview'`

### 7.3 `DataCardDetailsModal`

继续保留现有完整详情能力，但应尽量复用抽出的“共享只读内容体”，由 `DataCardDetailsModal` 自己保留原有外层动作区，避免两套详情渲染逻辑长期分叉。

## 8. 状态设计

举报模态至少维护以下状态：

- `viewMode = 'form' | 'reference-preview'`
- `draft`
- `selectedReference`
- `previewLoading`
- `previewError`
- `previewRequestId`
- `lastFocusedReferenceKey`

切换到查看态时：

- 不清空 `draft`
- 不重置引用列表
- 不清除当前已选理由与说明
- 记录当前点击的引用项 key，供返回后恢复焦点或滚动定位

返回举报时：

- 仅切回 `form`
- 保留全部草稿
- 尽量将焦点恢复到刚才点击“查看”的那条引用项

竞态约束：

- 若用户快速连续点击不同引用项，只允许最后一次点击返回的结果进入查看态。
- 旧请求完成后不得覆盖较新的 `selectedReference` 和预览内容。
- 查看态加载中必须有明确的 loading 反馈，不得出现空白态冒充成功。

## 9. API 与取数

首版不新增通用详情页 API。

可优先复用现有公开数据卡详情所需的取数方式；若现有接口返回字段不足，则只补满足“举报查看态”所需的最小字段，不扩展成通用公开详情能力。

### 9.1 最小请求标识

查看引用卡时，前端至少应提交：

- `dataCardId`

该值来自举报草稿中公开卡引用的规范化 `referenceId`。

### 9.2 最小响应字段

举报查看态所需最小 DTO 应至少包含：

```ts
type ReportReferencePreviewDto = {
  card: {
    id: string;
    name: string;
    description: string;
    author: string | null;
    type: 'character' | 'scenario' | 'history' | 'questionnaire';
    data: string;
    isPublic: true;
    createdAt: string | null;
    updatedAt: string | null;
  };
  download: {
    mode: 'client-json';
  };
};
```

说明：

- `download.mode = 'client-json'` 表示下载按钮继续沿用客户端基于 `card.data` 生成 JSON 文件的方式，不新增专门下载接口。

### 9.3 错误语义

查看失败时，前端至少区分以下错误语义：

- `not_found_or_inaccessible`：目标卡不存在或当前不可访问
- `invalid_reference`：引用 ID 非法或无法解析
- `request_failed`：请求失败或返回异常

首版 UI 可以统一文案展示，但测试中应锁定上述错误分支被正确映射。

## 10. 测试要求

至少补充：

- 举报模态在存在公开卡引用时可进入查看态。
- 查看态可显示当前引用卡的只读内容。
- 查看态加载中存在明确反馈。
- 查看态保留下载按钮。
- 返回举报后草稿状态完整保留。
- 返回举报后焦点或滚动尽量恢复到原引用项。
- 引用目标不可访问时展示错误提示且不丢草稿。
- 快速切换不同引用项时，仅最后一次点击结果生效。
- `DataCardDetailsModal` 与举报查看态共用只读详情展示层后，原有详情测试不回归。

## 11. 风险

- 若直接复制 `DataCardDetailsModal` 的现有渲染逻辑而不抽层，后续两个详情入口会快速分叉。
- 若查看态继续保留过多动作，容易从“核对证据”膨胀成新的通用详情入口。
- 若在切换查看态时卸载举报表单，会导致草稿丢失或重置，破坏主要流程。
- 若不处理快速切换引用项时的异步竞态，查看态可能展示过期结果。
- 若不定义关闭语义和焦点恢复规则，举报流在多层模态内会出现状态不一致。
