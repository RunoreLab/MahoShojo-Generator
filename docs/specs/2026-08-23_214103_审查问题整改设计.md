日期：2026-08-23
状态：`approved`

## 1. 目标与范围

本设计处理两份审查中经当前代码、提交历史和 accepted 文档核验后仍成立的问题：

- D1 HTTP transport 透明重放可能已经执行的 mutation/batch；
- Direct Provider Profile 的 HTTP header 大小写冲突；
- Local Card provenance 的状态与签名证据组合未冻结；
- `contracts` 公共面的跨 runtime 可移植性门禁不完整；
- D1 mutation helper 把“可能已提交”错误吞成确定失败，safe-read 重试复用同一组 Gateway 鉴权元数据；
- Hono Docker workspace 安装层失配；
- CI 没有同时执行 legacy root 与 workspace 验证；
- Hono 部署说明和本地库实施日志的事实错误。

本设计不推翻 Phase 2、Phase 2.5A、D1 Gateway 行为等价搬迁或 Arena Proposal 的 typed `expectedBase` 冲突模型，也不把 Phase 2.5 描述为已经完成。

## 2. 审查裁决

### 2.1 直接成立

- D1 transport 对所有 POST 固定重试 5 次，写操作存在重复副作用风险；该问题早于被审查提交，但与 Hosted DR ADR 的非幂等重放约束冲突。
- `Dockerfile.hono` 在 workspace manifest 不完整时运行 `pnpm install`，支持的 Compose 构建路径无法解析根包的 `workspace:*` 依赖。
- 两条部署 workflow 只执行 workspace 验证或部分根测试，没有统一运行根 `pnpm test` 与 `pnpm lint`。
- Provider Profile 没有按 HTTP header 的大小写不敏感语义检查单集合或跨集合冲突。
- `contracts` 当前源码没有 runtime 污染，但静态 gate 和 bundle test 不能阻止未来未被选中 symbol 引入 Node/framework/database runtime。
- esbuild 的 `node`、`browser`、`neutral` target 只证明可编译，不会拒绝顶层 `window` 等在 Node 中不可用的 global；需要更窄的 contracts browser-only global gate 和实际 Node load smoke。
- `server/README.md` 把任意分支的 artifact build 误写成任意分支上传 VPS。
- 本地库实施日志记录的 source commit SHA 正确，但提交标题错误。

### 2.2 部分成立：Local Card provenance

当前 schema 确实允许 `official-signed` 没有签名以及 `unsigned` 携带签名证据等矛盾组合；但 accepted architecture 当前把 `signatureVersion`、`signatureKeyId` 定义为 optional，legacy HMAC 卡也没有这两个字段。因此不直接采用审查中“所有 signed 状态必须同时携带 signature + version”的建议。

本设计冻结以下兼容口径：

- `official-signed`：必须保留非空 `signature`；`signatureVersion`、`signatureKeyId` 可选，以兼容 legacy 签名。
- `signature-invalid`：表示曾有签名证据但签名覆盖字段已经改变或验证失败，必须保留非空 `signature`；版本与 Key ID 继续可选。
- `unsigned`：provenance 层不得携带 `signature`、`signatureVersion` 或 `signatureKeyId`。
- legacy 卡 payload 内已有的 `data.signature` 不因本次 contract 收紧而被改写；进入本地库 adapter 时应显式映射到 provenance 证据。
- schema 只验证结构一致性，不能证明签名有效；导入、上传、服务器权威入口仍必须按各自信任边界重新验证或降级状态。

### 2.3 部分成立：`apiKeyRef` 与受管认证 Header

Profile 同时存在 `apiKeyRef`、`secretHeaderRefs` 与 `publicHeaders`，未来 Native Executor 确实必须防止 adapter-managed credential 和用户自定义 Header 生成同名的 effective request header。但当前 accepted architecture/spec 没有冻结三种 adapter 的 credential placement，现有正例还允许 `openai-compatible` 同时持有 `apiKeyRef` 与 `secretHeaderRefs.Authorization`。

因此本批不猜测 `openai-compatible -> Authorization`、`anthropic -> x-api-key` 或 `google -> x-goog-api-key`，也不以此收紧 v1 schema。实施规格只冻结未来要求：每个 adapter 在激活前必须显式定义 `apiKeyRef` 的 credential placement；Executor 必须对 adapter-managed credential、`publicHeaders` 和 `secretHeaderRefs` 合并后的 canonical effective header 做 fail-closed collision 检查，不定义覆盖优先级。

## 3. 设计决策

### 3.1 D1 重试采用显式语义，默认不重放

D1 HTTP transport primitive 本身默认只发送一次请求。`queryD1Payload`、`queryD1RawPayload`、`queryD1BatchPayload`、兼容别名，以及直接调用私有 transport 的 `createWithCustomId`、`updateById`、`saveToD1` 等 helper 都不得默认进入 retry loop。调用方只有在能够证明请求为 safe/read 时，才通过显式 retry option 选择现有退避重试。

本次不通过 SQL 文本猜测幂等性，也不新增没有权威去重记录支持的 `durably-idempotent` 模式。当前只有明确的健康读取等调用方可以 opt in；普通 mutation、混合 batch、HTTP D1 adapter 的通用执行入口均保持不重放。未来 command 若拥有稳定 operation ID、D1 唯一约束/CAS 或权威幂等记录，再单独扩展并补 contract test。

失败语义：mutation/未分类请求在已尝试 dispatch 后遇到 408、425、429、5xx 或可重试网络错误时，transport 抛出带稳定 error code 的 `D1IndeterminateOutcomeError`。该错误表示权威层可能已经执行 SQL，不是确定失败；`createWithCustomId`、`updateById`、`saveToD1` 必须继续向上抛出，不得转换为 `null`/`false`。其他明确的本地配置失败、4xx 或权威响应中的业务拒绝保持既有兼容语义。

调用方遇到 indeterminate outcome 后只能通过业务查询、稳定 operation ID、唯一约束/CAS 或权威幂等记录恢复，不能把它当作普通失败再发一次。该行为优先保证 correctness，允许暂时牺牲无语义标注读取的透明重试可用性。

safe-read 每次实际 HTTP attempt 都重新构建 request authentication metadata；Gateway HMAC 的 timestamp、nonce 和 signature 不跨 attempt 复用。这保持当前鉴权语义，并为未来 Gateway 增加 nonce replay protection 保留正确边界。

### 3.2 Provider Header 保留输入形式，只拒绝 canonical 冲突

Profile schema 使用 lowercase header name 做比较，但不改写持久化键名：

- 单个 `publicHeaders` 或 `secretHeaderRefs` 内不得同时出现 `X-Foo` 与 `x-foo`；
- 两个集合之间不得出现大小写等价名称；
- 现有敏感 header、transport-controlled header、数量、值和总字节限制继续生效；
- 不定义 public/secret 覆盖优先级，冲突输入直接校验失败。

对应 accepted spec 补充 header 名大小写不敏感和冲突必须拒绝的规范性要求。

`apiKeyRef` 不在本批参与 schema collision，因为 adapter-managed credential header 映射尚未被 accepted contract 定义。本批只在 accepted spec 中补上 2.3 节的 future executor fail-closed 要求。

### 3.3 Provenance 使用 discriminated union

`LocalCardProvenanceSchema` 改为以 `kind` 为 discriminator 的 strict union。三个分支共享可选 `execution`，signed/invalid 分支共享签名证据字段，unsigned 分支显式禁止这些字段。

对应 accepted architecture 与实施规格同步记录第 2.2 节兼容口径。由于真实 IndexedDB/SQLite adapter 尚未落地，本次无需数据库 migration；测试夹具覆盖 legacy 无 version/key ID 的 signed card，避免把未来字段错误升级为 v1 必填。

### 3.4 `contracts` gate 覆盖所有公共入口

复用当前 AST dependency scanner，为 `contracts` 增加 Node/framework/database runtime import 禁令，并建立独立、更窄的 browser-only global denylist。该 denylist 至少覆盖 `window`、`document`、`localStorage`、`sessionStorage`、`indexedDB` 与明确的 DOM UI global，同时检测未解析的裸 identifier 和 `globalThis.<name>`；影子变量、普通对象属性与字符串不误报。

该规则不机械复制 `domain` 的全部 DOM global 禁令，也不禁止 `URL`、`Blob`、`Headers`、`Request`、`Response`、`ReadableStream`、`TextEncoder` 等已在目标 runtime 共享的 Web Standards。

`packages/contracts/tests/bundle.test.ts` 从 `package.json.exports` 枚举所有公共入口，并让整个 namespace 在 bundle 中可观察，分别验证 `node`、`browser`、`neutral` target，防止 tree-shaking 隐藏未选中 export 的 runtime 依赖。Node target 产物还必须被实际 `import()` 一次；esbuild 成功不能代替 loadability 证据。真实 browser/Worker harness 等对应 adapter 和测试 runtime 建立后再增强，不在本批引入新 runtime 依赖。

### 3.5 Docker 与 CI 关闭相同回归路径

Docker dependency layer 在 `pnpm install --frozen-lockfile` 前按原目录结构复制所有当前 workspace `package.json`，保留依赖层缓存。根回归测试动态枚举 `apps/*/package.json` 与 `packages/*/package.json`，要求每个 manifest 均在 install 前出现；新增 workspace 时若遗漏 Dockerfile，测试立即失败。

这是 legacy-root Hono 阶段的迁移期策略，不是长期要求。`apps/api` 成为真实 server build/manifest 所有者后，Docker install context 必须收窄到 `apps/api` 及其实际 workspace 依赖闭包，同时删除“所有未来 workspace 都必须进入 Hono image”的动态门禁。Dockerfile 中留下这一删除条件，防止 Desktop/Admin 等无关 app 长期耦合进 Hono build。

根 `package.json` 新增统一 CI 验证入口，顺序执行：

1. `workspace:verify`；
2. legacy root `pnpm test`；
3. legacy root `pnpm lint`。

Hono 与 Cloudflare 两条部署 workflow 都调用该入口。Hono workflow 额外运行 `docker build -f Dockerfile.hono .` smoke，确保 README/Compose 支持路径不是只靠文本测试。现有 runtime-specific build、artifact 与生产分支 deploy gate 保持不变。

## 5. 测试策略

所有行为修复遵循 RED -> GREEN：

1. 先增加 mutation 在第一次可能执行后收到 retryable failure 时不得发第二次请求，且必须向上传播 indeterminate outcome 的失败测试；再实现默认 no-replay 与稳定错误类型。
2. 增加显式 safe-read 仍会重试且每个 attempt 刷新 Gateway timestamp/nonce/signature 的失败测试，证明修复没有删除受控重试能力。
3. 增加 Provider 单集合 casing duplicate、跨 public/secret collision 负例。
4. 增加 provenance 三态正负矩阵和 legacy 无 version/key ID 正例。
5. 增加 contracts runtime import、browser-only global（含 `globalThis` 成员）fixture，以及自动 exports bundle + Node import 枚举。
6. 增加 Docker manifest ordering、统一 CI command、两条 workflow 调用及生产 deploy gate 测试。

每个原子批次先运行 targeted test/lint/build；最终运行统一 CI 验证、Hono/Cloudflare build、server runtime 验证、workspace boundary、全仓 diff/告警检查。由于当前环境没有 Docker CLI，实际 Docker build 若仍不可用，将明确记录为未验证项；GitHub Actions smoke 会成为持续门禁。

## 6. 原子提交边界

1. `fix(database): 禁止 D1 写操作透明重放`
2. `fix(contracts): 拒绝 Provider Header canonical 冲突`
3. `fix(local-library): 冻结 provenance 状态不变量`
4. `test(contracts): 加固跨 runtime 可移植性门禁`
5. `chore(ci): 恢复根应用与 Hono 容器门禁`
6. `docs(platform): 校正部署说明与实施证据`

设计文档与后续实施计划各自作为独立、可解释的文档提交，不与生产行为修改混合。

## 7. 非目标与影响

- 不新增生产依赖。
- 不新增数据库 schema、远端 migration、数据回填或生产写操作。
- 不实现 operation ID 去重存储、Redis correctness 去重或完整 DatabaseProvider 重构。
- 不在没有 adapter contract 时猜测 `apiKeyRef` 的有效 Header 映射，也不实现尚未存在的 Native Provider Executor。
- 不实现 IndexedDB/SQLite adapter、签名算法升级或 Key ID 轮换。
- 不改变 Cloudflare/Hono 生产分支、secret、发布凭据、切流或部署目标。
- 不执行生产 deploy、remote D1 操作、release/tag 或历史重写。

本设计的 wire/持久化影响限于尚无真实 adapter consumer 的 Local Card provenance v1 结构收紧；legacy payload 签名通过明确兼容规则保留。其余修改属于 transport correctness、验证门禁和文档事实校正。
