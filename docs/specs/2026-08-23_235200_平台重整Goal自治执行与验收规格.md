# MahoShojo-Generator 平台重整 `/goal` 自治执行与验收规格

状态：`accepted`
日期：2026-08-23
规格标识：`SPEC-platform-restructure-goal-execution-v1`
适用范围：`platform-restructure-local-first` 主题下采用 Codex `/goal` 的长时自治开发、审查、修复与验收工作

## 1. 目的

本规格定义平台重整工作采用 Codex `/goal` 时的**执行治理、自治边界、Goal 尺寸、完成条件与证据要求**。

本规格不改变产品架构、信任边界、数据所有权、协议语义或阶段顺序。相关语义继续由平台主题页、accepted ADR、目标架构、实施规格和阶段计划定义。

`/goal` 的作用是把既有 Phase/规格转换为 Agent 可以持续数小时自主推进并可靠停止的执行单元，而不是创建第二套平台路线图。

## 2. 规范优先级

Agent 在 `/goal` 中必须按以下优先级解释约束：

1. 适用的 accepted ADR、领域规格与平台实施规格中的安全、权威、数据、兼容和协议不变量；
2. 平台重整目标架构与分阶段实施计划；
3. 本 `/goal` 自治执行与验收规格；
4. 当前 `/goal` 纵切实施计划；
5. 实施日志、历史报告、旧计划与一次性工作笔记；
6. Agent 自行选择的实现细节。

若低层材料与高层 accepted 口径冲突，必须先按高层口径处理；不得为了使当前 Goal 更容易完成而降低高层约束。

## 3. Goal 尺寸

### GOAL-001 默认约五小时

平台重整的单个 `/goal` 默认按**约 5 小时的有效自治开发工作量**规划。

这是任务切分尺度，不是硬性运行时 watchdog：

- 目标应明显大于一次普通 prompt 或一个短小代码任务；
- 共享同一业务目标、上下文、验证链和回滚面的相邻工作应优先放在同一 Goal 内；
- 不因为内部某个 checkpoint 只需要几十分钟就另开 Goal；
- 若预计整个候选范围在约 5 小时内能够完成，应保持为一个 Goal；
- 只有在预检后预计明显超过约 5 小时，或出现独立的高风险/不可逆/外部授权边界时，才拆成后续 Goal；
- 若实际运行接近 5 小时时已经接近 stopping condition，不得仅因时间到点中断；应完成当前闭环；
- 若实际运行中发现新增的大块工作会使目标显著越界，应完成当前安全 checkpoint，记录证据并把新增范围移入下一 Goal；
- 若因复用已有实现而提前完成，不得为了“凑满五小时”扩张范围。

时间估计必须基于当前代码、测试规模、运行时数量、迁移复杂度和已有同类实施日志，而不是机械按文件数或 route 数平均分配。

### GOAL-002 一个 Durable Objective

一个 Goal 必须只有一个可以用一句话表达的 durable objective，以及一个明确 stopping condition。

允许 Goal 内包含多次：

```text
调研 -> 设计 -> 原子实现 -> 测试 -> 审查 -> 修复 -> 再验证
```

但不得把互不相关的 backlog 项拼接成 Goal，只因为它们各自很短。

### GOAL-003 Checkpoint 不等于 Goal

Goal 内部可以按风险和依赖形成 20–90 分钟级的 checkpoint/atomic batch。checkpoint 用于：

- 限制 diff；
- 形成可回滚点；
- 快速运行 targeted validation；
- 给下一批提供稳定基线。

checkpoint 默认不需要用户介入，也不自动产生新的 `/goal`。

## 4. 启动预检

### GOAL-010 必读顺序

每个 Goal 启动后，Agent 必须先自行核对当前仓库事实，不得只按启动 prompt 中的静态描述工作。至少读取：

1. 根 `AGENTS.md`；
2. `docs/AGENTS.md` 与 `docs/README.md`；
3. `docs/topics/2026-08-22_022000_平台重整与本地优先架构.md`；
4. 主题页链接的适用 accepted ADR、architecture、spec 和主实施计划；
5. `docs/plans/2026-08-23_235300_平台重整Goal纵切实施计划.md`；
6. 与当前阶段最接近的实施日志、退出审计和审查整改材料；
7. 当前代码、manifest、machine-readable config、tests 和 CI/deploy workflow。

代码、manifest、配置与测试代表“当前实现事实”；accepted 文档代表“必须达到或保持的目标口径”。二者不一致时按迁移差距处理。

### GOAL-011 启动时重新估算

Goal 计划中的工时范围只是制定时估计。Agent 必须依据启动时最新仓库状态重新评估：

- 若已有后续提交显著完成了计划工作，应缩小到剩余 stopping condition，不重复实现；
- 若发现候选目标明显超过约 5 小时，应在开始大规模编码前自行切出下一 Goal，并在当前 Goal 的工作记录中写明理由；
- 若只是存在若干可在同一验证链内消化的小型未知项，不应因此提前拆 Goal。

Agent 可以自行调整当前 Goal 的内部 checkpoint、route 分组和实现顺序，无需逐项请求用户确认。

## 5. Agent 自治权限

### GOAL-020 可自行决定

在不违反高层不变量的前提下，Agent 可以自行：

- 调研代码、历史、官方文档与可用最佳实践；
- 选择实现方式、内部抽象、package/service/adapter 边界；
- 重排当前 Goal 内部实施顺序；
- 增加、修改或删除当前 Goal 所需的代码、测试、脚本、CI 与非秘密配置；
- 增加或修订 architecture/spec/plan/topic，使权威文档与经过验证的新事实一致；
- 根据证据决定某条 Hono 能力继续保留、退出 Hono 或通过共享 service 重构；
- 修复自行审查或其他 Agent 审查发现的范围内问题；
- 为反复出现的验证工作增加 repo-local script、test harness 或 skill。

Agent 应优先选择可逆、可测试、可机械约束的方案，而不是依赖口头约定。

### GOAL-021 accepted ADR 的演进

Agent 被授权基于新证据演进 accepted 技术决策，但必须保持设计历史可追溯：

- 解释性补充、事实校正和不改变决定本身的收紧可以直接更新原 ADR，并记录理由；
- 实质推翻已有 accepted 决定时，应新增 superseding ADR，并把旧 ADR 标记为 `superseded` 或链接到新决定；
- 不应通过删除旧 ADR、旧实施日志或改写历史来隐藏决策变化。

### GOAL-022 不得移动终点线

Agent 不得为了让 Goal 宣布完成而自行弱化或删除：

- 客户端不可信与服务器权威边界；
- secret/credential 隔离；
- 数据所有权与 authority；
- Legacy/Better Auth 兼容要求；
- Arena v1 已冻结 wire/authority 语义；
- 非幂等请求不盲目重放要求；
- 适用的 `MUST` / `MUST NOT`；
- 当前 Goal 明确引用的 acceptance criterion。

若新证据表明其中某项确实应改变，Agent 必须形成决策提案、替代方案、风险和迁移影响，并把该事项标为需要人工判断的 blocker；除非启动 Goal 时用户已明确授权这一类高后果决策。

### GOAL-023 历史与日志

`docs/logs/` 原则上视为实施证据记录：

- 新实施应新增日志或退出审计，而不是回写旧日志制造“当时已经完成”的假象；
- 旧日志存在明确事实错误时可以修正，但必须保留修正原因，不能删除对理解演进仍有价值的证据；
- 当前结论应进入 topic/ADR/spec/plan，不依赖日志作为唯一事实源。

## 6. 高风险操作与外部授权

### GOAL-030 默认禁止

除非当前用户明确授权，Goal 不得执行：

- production deploy 或正式流量切换；
- 远程生产数据库 migration/write/restore；
- 生产 Redis flush 或破坏性故障注入；
- secret、Access policy、生产 credential 或签名私钥变更；
- release/tag 发布；
- force push、历史重写或其他根 `AGENTS.md` 禁止的操作。

Agent 应优先使用 local、test、preview、mock/fake、fault injection、dry-run 或隔离副本完成可验证验收。

### GOAL-031 BLOCKED 不等于 PASS

如果 Goal 的某个必要 acceptance 只能通过未获授权的生产操作完成：

- 可先完成代码与隔离环境验收；
- 必须把剩余项标为 `BLOCKED`，写明需要的授权与安全执行方案；
- 不得将其假定为已通过；
- 若该项是 durable objective 的必要组成部分，Goal 不能以完全完成状态报告。

## 7. 实施循环

### GOAL-040 原子推进

Agent 应在 Goal 内自行形成可审查、可回滚的 atomic batches。每批至少遵循：

```text
确认当前行为/失败
-> 实现最小充分修改
-> targeted test / lint / typecheck / build
-> 检查 diff 与边界
-> 进入下一批
```

结构迁移、业务语义修改、数据库 schema 和部署切换应尽量分离；若必须同批发生，应说明为什么无法安全拆分。

### GOAL-041 证据优先

任何“已完成”“兼容”“无回归”“性能改善”“故障可恢复”的结论都必须有实际运行的测试、构建、检查、测量或可复核代码证据。

不得：

- 把未运行的命令写成通过；
- 用编译成功代替 contract/runtime 行为验证；
- 用 mock-only happy path 证明高风险故障语义；
- 用历史日志替代当前代码验证。

### GOAL-042 已知债务 no-new-regression

全仓既有 warning、audit finding、naming debt 或非 canonical check 失败，默认采用**冻结基线 + no new regression**，而不是在每个 Goal 中顺手清零。

只有当既有债务：

- 阻塞当前 Goal；
- 由当前改动显著放大；
- 或修复成本很小且与当前根因高度相关；

才应纳入当前范围。否则记录为已知债务或后续工作，不扩张 Goal。

## 8. Review 与修复闭环

### GOAL-050 Builder self-review

实现完成后，Builder 必须先审查自己的完整 diff，至少检查：

- accepted ADR/spec 是否被破坏；
- app/package/runtime 依赖方向；
- auth、secret、authority、idempotency、data ownership；
- producer/consumer/contract/schema 兼容；
- rollback 与失败语义；
- 测试是否真正覆盖风险。

### GOAL-051 Independent review

最终验收前至少进行一轮与 Builder 视角分离的独立 review；可以使用独立 subagent、Codex review 能力或等价独立审查上下文。

对平台重整 Goal，review 至少覆盖：

- architecture/dependency；
- security/authority；
- compatibility/data/replay；
- test adequacy。

### GOAL-052 Finding 关闭规则

- `Critical` / `Important`：必须修复并重新验证，否则 Goal 不得完成；
- `Minor`：应修复；若明确不影响 stopping condition，可记录理由和后续入口后关闭；
- 纯格式/自动工具可确定的问题交由 formatter/linter，不占用人工式设计讨论。

修复 review finding 后必须重跑受影响的 targeted validation；高影响修改还需重新执行最终验收集合。

## 9. 完成契约

### GOAL-060 状态模型

最终验收项只允许以下状态：

- `PASS`：实际执行并通过；
- `FAIL`：实际执行且失败；
- `BLOCKED`：因明确外部能力/授权无法安全执行；
- `NOT_APPLICABLE`：经说明后不适用；
- `DEFERRED`：明确不属于本 Goal，且不阻塞当前 stopping condition。

不得用“应该没问题”“理论上通过”“基本完成”替代这些状态。

### GOAL-061 Done 条件

只有同时满足以下条件，Agent 才能报告 Goal 完成：

1. durable objective 已真实满足；
2. stopping condition 的机械/行为证据全部为 `PASS` 或合理 `NOT_APPLICABLE`；
3. 没有会阻塞目标的 `FAIL` / `BLOCKED`；
4. 无未解决 `Critical` / `Important` review finding；
5. 适用的 targeted + integration/contract + build/boundary 验证已实际运行；
6. 没有通过放宽安全、权威、兼容或 acceptance 要求来获得通过；
7. rollback/revert 路径明确；
8. 当前 topic/plan/spec 与实现事实没有未解释冲突；
9. 最终实施日志或退出审计记录 source commit、规格 ID、测试、未完成项、临时兼容、风险和下一入口。

### GOAL-062 不做时间填充

若 stopping condition 提前满足，应结束 Goal 并报告实际完成，不为达到估计工时继续加入无关功能、重构或债务清理。

## 10. 进度记录与最终报告

### GOAL-070 Goal 内进度

长时间运行中 Agent 应维护简短工作状态，至少能够回答：

- 当前 checkpoint；
- 已验证什么；
- 还剩什么；
- 是否出现 blocker；
- 当前范围是否仍符合约 5 小时尺寸。

工作中临时笔记可以位于 Agent 工作上下文或 `.tmp/`，不要求每个 checkpoint 都形成永久文档。

### GOAL-071 最终持久化

Goal 结束前将真正具有长期价值的信息写回仓库：

- current-state 变化 -> topic/README；
- 稳定技术决定 -> ADR；
- 可测试要求 -> spec；
- 顺序/后续纵切 -> plan；
- 本次证据 -> log/exit audit。

不要把同一信息复制到所有文档；保持 progressive disclosure。

### GOAL-072 最终报告

向用户报告时至少包含：

- Goal 结论与实际达到的 stopping condition；
- 关键设计/决策变化及理由；
- 主要实现；
- 实际运行的验证与结果；
- review finding 及关闭状态；
- 未完成/blocked/deferred；
- 生产、schema、secret、release 影响；
- 下一 Goal 建议及重新估算。

## 11. 与主平台规格的追踪

每个 Goal 应在工作记录/实施日志中使用已有规格 ID，例如：

```text
Goal: G25B-1
Implements: MONO-003, MONO-009
Validates: ACCEPT-008
Preserves: AI-006, DR-008, MULTI-001..MULTI-018
Goal governance: GOAL-001, GOAL-010, GOAL-050, GOAL-061
Deferred: ACCEPT-012..017
```

`GOAL-*` 只描述执行与验收治理，不替代 `MONO-*`、`AI-*`、`DR-*`、`MULTI-*`、`ACCEPT-*` 等产品/架构要求。
