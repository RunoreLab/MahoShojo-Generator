# 创作页角色卡车卡规则展示设计

日期：2026-04-03 11:26:22  
状态：已完成设计，待人工确认  
范围：为 `/creator` 结果区内可保存为图片的角色卡增加“角色参数”展示与 `初始 / 当前` 来源切换能力，并确保展示逻辑不硬绑定现有规则 ID，而是面向通用 `blocks` 扩展。

---

## 1. 目标

本轮目标有四个：

1. 让 `/creator` 生成出的可保存长图角色卡，能够直接在卡面上展示角色参数相关内容。
2. 支持在卡面上切换查看两类数据来源：
   - `初始`：生成时输入快照
   - `当前`：当前权威规则状态
3. 展示逻辑不绑定 `arena-trpg-lite / dnd-5e-lite / coc-7e-lite` 三套现有规则，而是按预设 `blocks` 通用渲染。
4. 导出长图时隐藏交互切换控件，但仍在图片中明确标注当前显示的是 `初始` 还是 `当前`。

---

## 2. 非目标

本轮明确不做以下内容：

1. 不修改数据卡详情弹窗、档案馆详情页或其他非长图查看入口。
2. 不修复 `/creator` 当前“残兽（结构化）”结果未接入 [`CanshouCard.tsx`](/home/notuhao/code/MahoShojo-Generator/components/CanshouCard.tsx) 的链路问题。
3. 不为某套规则写专属卡面逻辑。
4. 不重写 build rule runtime、prompt projection 或 creator API 协议。
5. 不把 `/creator` 扩展成完整 TRPG 编辑器。

说明：

- 虽然本轮不修复残兽输出链路，但 [`CanshouCard.tsx`](/home/notuhao/code/MahoShojo-Generator/components/CanshouCard.tsx) 仍会同步具备相同规则展示能力，避免未来修链路时再次返工。

## 3. 已确认的事实边界

- `creationInputs.buildRules[]`
  - 表示生成时使用的规则输入快照
  - 对应用户要求中的 `初始`
- `buildState.rules[]`
  - 表示当前附着在卡上的权威规则状态
  - 对应用户要求中的 `当前`

## 4. 方案选择

本轮采用“通用卡面区块型”方案。

### 4.1 为什么不选最小硬写方案

若直接在三张卡里分别硬写“规则展示”：

- 会重复实现 `初始 / 当前` 切换与导出隐藏逻辑
- 会把展示逻辑绑定到现有规则字段名
- 新增 block 类型或新规则时会继续复制粘贴

这与本轮“支持未来可能出现的其他车卡规则”的目标冲突。

### 4.2 为什么不做更重的协议升级

更进一步的做法是为每个 block 增加专门的 card-display 元数据，例如：

- 卡面显示优先级
- 卡面摘要模式
- 是否默认折叠

这类协议升级长期有价值，但本轮不是必要条件。首版优先复用现有 `blocks` 信息，只有在通用展示确实不够时，才补最小必要字段。

## 5. 核心设计

### 5.1 新增通用“角色卡规则展示区块”

新增一个可复用的角色卡参数展示组件，供三张角色卡共用。它负责：

1. 从卡数据中读取 `初始 / 当前` 两套规则来源
2. 判定是否需要展示切换控件
3. 按规则预设的 `blocks` 顺序渲染内容
4. 在导出长图时切换为“静态标识模式”

组件输入应以“卡上已有元数据”为准，不再依赖 creator 页面本地 state。

### 5.2 卡面显示模式

展示区块支持两种模式：

1. 页面浏览模式
   - 可显示 `初始 / 当前` 切换控件
   - 用户可主动切换
2. 导出图片模式
   - 不显示交互控件
   - 保留静态来源标识，例如：`角色参数 · 当前`

这样导出的长图仍然能看出当前显示的是什么来源，但不会把按钮截图进去。

### 5.3 何时显示切换

1. 同时存在 `初始` 与 `当前` 两套规则数据时，显示切换。
2. 只有一套数据时，不显示切换，只显示静态来源标识。
3. 两套数据都不存在时，不显示整个规则区块。

首版默认优先显示：

- 有 `当前` 时默认显示 `当前`
- 否则回退到 `初始`

## 6. 通用 block 渲染策略

展示必须按规则预设 `blocks` 定义驱动，而不是按规则 ID 驱动。

### 6.1 `select`

- 从当前 block 值映射到 option `label`
- 卡面展示标签，不展示底层 `value`

### 6.2 `multi-select`

- 按 group/item 定义映射为标签
- 展示已选择项列表

### 6.3 `point-buy` / `stat-array` / `number-group`

- 统一按字段列表渲染为“字段标签：值”
- 不在卡面重现编辑态输入框，只展示结果值

### 6.4 `derived`

- 优先按预设 `fields` 顺序展示
- 若预设未提供字段列表，则从运行时 `derived` 对象回退渲染

### 6.5 `section`

- 作为说明文本块展示
- 仅在 description 存在时显示

### 6.6 未知 block

若未来出现新 block 类型：

1. 优先尝试从 `blockResults[block.id]` 或 `derived` 中做保守键值展示
2. 无法安全展示时直接跳过
3. 不让未知 block 导致整张卡崩溃

这保证系统对未来规则扩展保持前向兼容。

## 7. 卡面结构建议

角色参数区块建议放在角色核心内容之后、`CurrentStatePanel` 之前或之后的固定位置，三张卡保持一致。

推荐结构：

1. 区块标题：`角色参数`
2. 来源标识：
   - 页面态：`初始 / 当前` 可切换
   - 导出态：只保留当前来源文字
3. 每条规则以“规则标题 + 内容区块”展示
4. 尾部轻量展示规则状态：
   - `规则校验通过`
   - 或 `存在 N 条规则问题`

不在卡面复刻 creator 侧栏里的完整预算提示和大段错误说明，只保留轻量摘要，避免长图过度膨胀。

---

## 8. 需要的最小类型与协议扩展

首版预计可直接复用现有协议，但允许做以下最小扩展：

1. 为展示层补一个内部 ViewModel 类型
   - 描述来源标签、规则标题、展示项列表、校验状态
2. 若发现某类 block 在卡面层缺少必要展示信息，可只补最小的辅助解析函数或内部元数据，不修改对外 API 协议

本轮不主动扩展公开 JSON 预设结构；只有在现有字段无法支撑通用展示时，才增加最小必要字段。

## 9. 实现拆分

### 9.1 解析层

新增一层面向卡面展示的解析逻辑，负责：

- 从角色卡数据读取 `creationInputs` / `buildState`
- 加载对应规则预设
- 生成可展示的规则区块数据

该层应独立于卡组件，避免三张卡各自复制解析逻辑。

### 9.2 展示层

新增可复用的角色卡规则区块组件，负责：

- 来源切换
- block 列表展示
- 导出态静态标识

### 9.3 接入层

把该展示区块接到：

- [`components/GeneralCharacterCard.tsx`](/home/notuhao/code/MahoShojo-Generator/components/GeneralCharacterCard.tsx)
- [`components/MagicalGirlCard.tsx`](/home/notuhao/code/MahoShojo-Generator/components/MagicalGirlCard.tsx)
- [`components/CanshouCard.tsx`](/home/notuhao/code/MahoShojo-Generator/components/CanshouCard.tsx)

其中 `CanshouCard` 只做预接入，不负责修通 creator 页面结果分支。

## 11. 风险与处理

### 11.1 风险：规则区块导致卡面过长

处理：

- 只展示卡面友好的摘要形态
- 避免把 creator 工作台里的完整说明和预算 UI 原样搬过来

### 11.2 风险：未来 block 类型扩展导致展示缺口

处理：

- 采用“已知类型精确渲染 + 未知类型保守降级”的双层策略

### 11.3 风险：`初始` 与 `当前` 数据结构不完全对齐

处理：

- 统一以规则快照结构为准解析
- 缺字段时按单来源或缺省渲染处理，不强行假设两者完全一致

---

## 12. 最终结论

本轮不应把“角色参数展示”实现成针对三套现有规则写死的卡面 patch，而应实现为：

- 基于 `creationInputs.buildRules` 与 `buildState.rules` 的双来源展示
- 基于预设 `blocks` 的通用渲染
- 支持导出图片时隐藏控件、保留 `初始 / 当前` 静态标识

这样既满足本轮 `/creator` 角色卡长图的展示需求，也为未来新增规则与修复残兽结果链路保留稳定复用面。
