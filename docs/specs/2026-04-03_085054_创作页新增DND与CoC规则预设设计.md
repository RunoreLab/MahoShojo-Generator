# 创作页新增 DND 与 CoC 规则预设设计

日期：2026-04-03 08:50:54  
状态：已完成设计讨论，待人工评审  
范围：为 [`/creator`](/home/notuhao/code/MahoShojo-Generator/pages/creator.tsx) 新增经典 TRPG 车卡规则预设 `dnd-5e-lite` 与 `coc-7e-lite`，并顺手把现有 `arena-trpg-lite` 对齐到更通用的规则底座

---

## 1. 本轮目标

本轮设计聚焦三个结果：

1. 在创作页已有“规则预设 + 主规则投影”架构上，新增两套经典 TRPG 规则预设：
   - `dnd-5e-lite`
   - `coc-7e-lite`
2. 为现有规则系统补齐少量通用能力，使“等级 / 职业 / 年代 / 职业倾向 / 数值组”这类经典车卡结构可以复用，而不是为单个系统写死。
3. 顺手整理现有 `arena-trpg-lite` 的声明方式与摘要逻辑，让三套预设运行在同一套运行时与 UI 抽象上。

本轮不是要把 `/creator` 做成完整 TRPG 角色编辑器，而是要让 AI 创作链路能稳定接收“经典、结构化、可校验”的车卡事实。

---

## 2. 核心设计结论

### 2.1 总体方向

- `/creator` 继续保持“多规则预设 + 单主规则投影”的架构，不新增专用路由或专用页面。
- 新增两个预设：
  - `dnd-5e-lite`
  - `coc-7e-lite`
- 联动优先放在预设声明层，通过 block 配置和 `select` 选项元数据驱动。
- 真正的派生计算、预算校验和摘要生成，统一收敛在运行时模块中处理，不散落到组件层。

### 2.2 本轮推荐方案

本轮采用“中等扩展型”而非“最小兼容”或“完整编辑器”路线：

- 不只增加静态 JSON 预设。
- 也不直接把 DND / CoC 做成接近完整桌游编辑器的复杂页面。
- 而是在现有预设系统上补少量通用能力，使：
  - DND 能表达等级、职业、六维、熟练、派生摘要。
  - CoC 能表达年代、职业、八维、SAN/HP/MP/Build/伤害加值摘要。

这样既能满足经典规则预设的基本表达力，也能为未来新增其他车卡规则预设保留复用空间。

## 3. 规则系统方向

### 3.1 保持统一的创作页规则架构

- 所有规则继续通过 [`public/build-rules/presets/`](/home/notuhao/code/MahoShojo-Generator/public/build-rules/presets) 下的静态预设声明。
- 规则选择仍通过 [`BuildRulePicker`](/home/notuhao/code/MahoShojo-Generator/components/creator/BuildRulePicker.tsx) 进入。
- 规则编辑仍通过 [`BuildRulePanel`](/home/notuhao/code/MahoShojo-Generator/components/creator/BuildRulePanel.tsx) 承载。
- 主规则摘要与派生值仍通过 [`BuildSummaryPanel`](/home/notuhao/code/MahoShojo-Generator/components/creator/BuildSummaryPanel.tsx) 展示。
- prompt 侧继续沿用“主规则结构化投影 + 其他规则 reference”模式，不改变主规则优先级。

### 3.2 规则系统要补的通用能力

本轮需要把规则系统从“主要面向 `arena-trpg-lite` 的单一模型”扩展成“能承载多套经典车卡规则”的通用模型。

应补齐的通用能力包括：

1. `select` block 选项级元数据
   - 例如职业的 `hitDie`、施法类型、推荐主属性、职业倾向说明。
2. 新的固定数值字段组 block
   - 例如 DND 六维、CoC 八维、AC/HP/速度、Luck/Credit Rating/Age。
3. 更通用的摘要生成逻辑
   - 摘要不再默认绑定 `arena-trpg-lite` 的固定字段名，而是根据预设与运行时结果生成。
4. 更清晰的运行时上下文
   - 运行时在派生计算前，先统一拿到当前已选择的 block 结果与 `select` 元数据，再进行规则专属计算。

## 4. 新增 block 类型与声明扩展

### 4.1 `select` block 扩展

现有 `select` block 在保留 `value` / `label` 的同时，补充可选 `meta` 字段：

```json
{
  "value": "wizard",
  "label": "法师",
  "meta": {
    "hitDie": "d6",
    "spellcastingKind": "full",
    "primaryAbilities": ["INT"]
  }
}
```

该元数据用于：

- UI 说明展示
- 运行时派生计算
- prompt 摘要构建

组件本身不解释业务含义，只负责展示；业务含义由运行时消费。

### 4.2 新增 `stat-array`

新增通用 block 类型 `stat-array`，用于渲染固定字段组的数值录入。

适用场景：

- DND 六维属性
- CoC 八维属性
- 未来其他规则中的固定属性组

能力要求：

- 支持字段列表、标签、说明
- 支持可选最小值 / 最大值
- 支持只记录“最终值”，不强制用户走点买法或骰点过程

### 4.3 新增 `number-group`

新增通用 block 类型 `number-group`，用于渲染少量独立数字字段。

适用场景：

- DND 的 `AC / HP / Speed / Passive Perception`
- CoC 的 `Luck / Credit Rating / Age`

能力要求：

- 字段数量较少
- 字段间不共享预算
- 更强调最终录入值，而不是推导过程

## 5. `dnd-5e-lite` 预设设计

### 5.1 设计目标

`dnd-5e-lite` 用于在创作页中表达 DND 5e 语境下最经典、最稳定的一组角色卡事实，让 AI 能理解角色处于什么职业、什么等级、拥有什么基础能力结构。

本预设不追求完整 RAW 角色编辑器，而是提供一套足够典型、可读、可投影的轻量车卡骨架。

### 5.2 建议 block 结构

#### `level`

- 类型：`select`
- 选项：`1-20`
- 用途：
  - 决定熟练加值
  - 作为职业派生摘要的重要上下文

#### `class`

- 类型：`select`
- 首版职业范围至少包含：
  - `fighter`
  - `wizard`
  - `rogue`
  - `cleric`
  - `bard`
  - `ranger`
  - `paladin`
  - `warlock`
  - `sorcerer`
  - `druid`
  - `monk`
  - `barbarian`
- 每个职业选项通过 `meta` 补充：
  - `hitDie`
  - `spellcastingKind`
  - `primaryAbilities`
  - `savingThrowProficiencies`

#### `lineage`

- 类型：`select`
- 用途：
  - 提供角色叙事语境和风格倾向
  - 提供默认速度或气质提示
- 首版不把族裔属性加值规则强绑定到运行时校验中。

#### `abilityScores`

- 类型：`stat-array`
- 字段：
  - `STR`
  - `DEX`
  - `CON`
  - `INT`
  - `WIS`
  - `CHA`
- 规则：
  - 首版录入“最终属性值”
  - 不强制模拟 `point-buy`、`standard array` 或掷骰流程
  - 可选附带 `generationMethod` 作为记录信息，但不做严格预算校验

#### `combatProfile`

- 类型：`number-group`
- 字段建议：
  - `armorClass`
  - `hitPoints`
  - `speed`
  - `passivePerception`（可选）
- 规则：
  - 作为最终值录入
  - 首版不尝试精确硬算 `AC` 和 `HP`

#### `derivedStats`

- 类型：`derived`
- 运行时计算：
  - 六维调整值
  - 熟练加值
  - 命中骰摘要
  - 施法类型摘要

#### `ruleNotice`

- 类型：`section`
- 用于明确首版不覆盖内容。

### 5.3 首版明确不做

`dnd-5e-lite` 首版不覆盖：

1. 子职业
2. 完整技能熟练矩阵
3. 专长（Feat）
4. 装备栏
5. 完整法术位 / 法术列表编辑器
6. 升级成长记录

## 6. `coc-7e-lite` 预设设计

### 6.1 设计目标

`coc-7e-lite` 用于在创作页中表达 CoC 7 版语境下最常见的一组调查员卡面事实，让 AI 能理解人物的时代气质、职业背景、基础属性以及理智与生存相关的核心数值。

本预设优先提供“经典调查员画像”，不尝试实现完整技能点分配器。

### 6.2 建议 block 结构

#### `eraTone`

- 类型：`select`
- 选项建议：
  - `classic-1920s`
  - `modern`
  - `pulp`
  - `occult-heavy`
- 用途：
  - 主要服务于叙事语境
  - 不强绑定复杂数值规则

#### `occupation`

- 类型：`select`
- 首版职业范围建议包含：
  - `detective`
  - `journalist`
  - `doctor`
  - `professor`
  - `antiquarian`
  - `artist`
  - `criminal`
  - `dilettante`
  - `occultist`
- 每个职业选项通过 `meta` 补充：
  - 推荐技能倾向
  - 推荐信用评级区间
  - 职业气质摘要

#### `coreAttributes`

- 类型：`stat-array`
- 字段：
  - `STR`
  - `CON`
  - `SIZ`
  - `DEX`
  - `APP`
  - `INT`
  - `POW`
  - `EDU`
- 规则：
  - 直接录入最终属性值
  - 不强制模拟 `3D6×5` / `2D6+6×5` 的原始掷骰过程

#### `secondaryInputs`

- 类型：`number-group`
- 字段建议：
  - `luck`
  - `creditRating`
  - `age`

#### `signatureSkills`

- 类型：`multi-select`
- 首版用于表达“代表性技能倾向”，而非完整技能树
- 选项建议包含：
  - `library-use`
  - `spot-hidden`
  - `psychology`
  - `persuade`
  - `firearms`
  - `fighting`
  - `stealth`
  - `occult`
  - `medicine`
  - `mechanical-repair`

#### `derivedStats`

- 类型：`derived`
- 运行时计算：
  - `SAN = POW`
  - `HP = floor((CON + SIZ) / 10)`
  - `MP = floor(POW / 5)`
  - `Build`
  - `Damage Bonus`

#### `ruleNotice`

- 类型：`section`
- 用于声明首版能力边界。

### 6.3 首版明确不做

`coc-7e-lite` 首版不覆盖：

1. 完整技能点分配器
2. 职业技能 / 兴趣技能精确预算
3. 武器与战斗明细
4. 法术与神话书管理
5. 疯狂症状与长期精神状态追踪器

## 7. 运行时与联动策略

### 7.1 联动原则

联动采用“预设声明元数据 + 运行时统一消费”的模式：

- 组件负责渲染与收集输入
- 运行时负责解释规则语义
- 预设负责声明每个选项和字段意味着什么

不采用“在组件里根据具体规则 ID 写死联动”的方式。

### 7.2 运行时的统一处理流程

[`evaluateBuildRuleState`](/home/notuhao/code/MahoShojo-Generator/lib/creator/build-rule-runtime.ts) 应按以下流程处理：

1. 按 block 类型规范化输入
2. 提取所有 `select` block 当前选项与其 `meta`
3. 构造统一运行时上下文
4. 按 `ruleId` 进入对应规则计算器
5. 生成：
   - `blockResults`
   - `derived`
   - `validationSummary`

### 7.3 DND 运行时边界

`dnd-5e-lite` 运行时强算：

- 六维调整值
- 熟练加值
- 命中骰摘要
- 施法类型摘要

`dnd-5e-lite` 首版只校验、不精确硬算：

- `AC`
- `HP`
- 速度

原因是这些值高度依赖护甲、装备、职业实现、取平均还是掷骰、桌规差异等上下文，不适合在首版伪装成“精确规则计算”。

### 7.4 CoC 运行时边界

`coc-7e-lite` 运行时强算：

- `SAN = POW`
- `HP = floor((CON + SIZ) / 10)`
- `MP = floor(POW / 5)`
- `Build`
- `Damage Bonus`

`luck` 首版保留手填，因为不同桌面流程与导入来源可能直接保存最终值。

## 8. 现有 `arena-trpg-lite` 的顺手改进范围

本轮允许顺手改进现有 `arena-trpg-lite`，但只做“对齐抽象”，不做“改写规则”。

### 8.1 应该顺手做的事

1. 让 `powerLevel` 等选择项也能复用更清晰的 `select` 元数据结构
2. 让摘要生成逻辑少依赖 `arena-trpg-lite` 专属字段名
3. 让三套规则在 [`BuildSummaryPanel`](/home/notuhao/code/MahoShojo-Generator/components/creator/BuildSummaryPanel.tsx) 中遵循一致的展示节奏
4. 让运行时上下文构造方式统一，不再只针对当前这一个预设优化

### 8.2 不应该顺手做的事

1. 不重写 `arena-trpg-lite` 的规则定义
2. 不改变既有预算与派生值公式
3. 不把它扩成完整 TRPG 编辑器
4. 不把本轮时间消耗在与 DND / CoC 无关的 UI 打磨上

## 9. UI 与摘要展示原则

### 9.1 `BuildRulePanel`

`BuildRulePanel` 继续作为通用规则面板，不为单个规则新增专用页面。

本轮只扩展它对新 block 类型的渲染能力：

- `stat-array`
- `number-group`
- 带 `meta` 的 `select`

### 9.2 `BuildSummaryPanel`

`BuildSummaryPanel` 统一展示三层信息：

1. 已选择的经典规则身份信息
   - 例如等级、职业、年代、职业倾向
2. 用户明确录入的关键数值
   - 例如属性值、AC、HP、Luck
3. 运行时推导结果
   - 例如熟练加值、能力调整值、SAN、Build、Damage Bonus

这样三个预设的摘要结构保持一致，用户不需要为每一套规则学习不同的阅读方式。

### 9.3 Prompt 投影原则

主规则始终投影为：

- 已选项标签
- 关键手填字段
- 派生值
- 校验状态

AI 读取的是统一结构化事实，而不是每套规则各自拼接一套完全不同的描述方式。

## 12. 结论

本轮设计的核心不是“给 `/creator` 强塞两套新 JSON”，而是把现有规则预设体系扩成一套可持续复用的车卡规则底座。

在这个前提下：

- `dnd-5e-lite` 负责表达经典 DND 角色骨架
- `coc-7e-lite` 负责表达经典 CoC 调查员骨架
- `arena-trpg-lite` 顺手对齐通用抽象而不改动其规则含义

最终目标是让创作页能够稳定接纳“经典、结构化、可校验”的车卡事实，并把这些事实可靠地投影给 AI，而不是把 `/creator` 迅速膨胀成完整的 TRPG 编辑器。
