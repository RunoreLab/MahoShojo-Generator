# 治理后台剩余工作调研与实施设计

更新时间：2026-04-11 10:18:08

## 1. 背景

`feat/admin` 分支在提交 `75f039a0` 已经补上了治理后台的第一轮接入：

- `messages` 后台已可发送和查看消息
- `report-cases` 已可读列表、详情并通知作者
- `crowd-review/inspectors` 已可管理巡查使状态
- `crowd-review/cases` 已可读列表和详情
- `report-appeals` 已形成较完整的后台写操作样板

但面向正式运营使用，仍有四类关键缺口：

1. `admin/messages` 的交互仍偏“开发者后台”，模板与优先级直接暴露原始枚举和值
2. `report-cases` 仍缺正式结案、改判、数据卡处罚动作
3. `crowd-review/cases` 仍缺管理员接管、撤销轮次、改判写操作
4. `report-cases` / `crowd-review` 仍缺后台页面级测试

本设计文档用于在不扩大范围的前提下，为上述剩余工作给出可直接落地的实施方案。

## 2. 本轮范围确认

### 2.1 本轮纳入

- `admin/messages` 的可用性改造与中文文案收口
- `report-cases` 的正式结案、改判、数据卡处罚动作
- `crowd-review/cases` 的接管、撤销轮次、改判动作
- 治理后台剩余模块的 API / 服务测试补齐
- 为未来的管理员动作留痕预留结构边界，但本轮不新建数据表

### 2.2 本轮明确不做

- 账号处罚入口
- 后台鉴权体系重构
- 通用治理工作流引擎
- 将所有治理逻辑继续堆叠进内容管理页
- 新建治理管理员动作表
- `report-cases` / `crowd-review` 页面级测试

说明：数据卡处罚能力优先复用现有内容管理后台的 `batchUpdateDataCards` / `sendDataCardModerationMessages` 链路，不新增账号处罚分支。

## 3. 调研结论

### 3.1 `admin/messages` 的问题主要在交互层，不在后端能力

现状：

- 页面直接让管理员输入 `messageType` 与 `templateKey`
- `priority` 仍展示 `low / normal / high`
- 最近消息表格也直接显示原始 `templateKey`

对应文件：

- `components/admin/messages/AdminMessagesPage.tsx`
- `lib/admin/messages.ts`
- `lib/messages/templates.ts`
- `components/messages/messageUi.ts`

判断：

- 当前 `GET /api/admin/messages`、`POST /api/admin/messages/site`、`POST /api/admin/messages/direct` 已足够支撑本轮
- 不需要再为消息后台增加新的服务端写接口
- 应新增“模板目录 + 中文标签 + 表单提示”这一层前端/共享配置，而不是继续让管理员手输模板键

### 3.2 `report-cases` 缺的是“正式动作层”，不是读模型

现状：

- 列表、详情、通知作者已可用
- 页面状态筛选仍直接暴露 `open / under_review / resolved / dismissed`
- 后端只有：
  - `GET /api/admin/report-cases`
  - `GET /api/admin/report-cases/[caseId]`
  - `POST /api/admin/report-cases/[caseId]/notify-creator`

对应文件：

- `pages/admin/report-cases.tsx`
- `pages/api/admin/report-cases/index.ts`
- `pages/api/admin/report-cases/[caseId].ts`
- `pages/api/admin/report-cases/[caseId]/notify-creator.ts`
- `lib/admin/governance.ts`

关键缺口：

- `report_cases` 当前只有 `status / resolution_code / closed_at`，没有管理员动作备注或留痕表
- `report-appeals` 与 `crowd-review` 内部都各自写了一份“更新举报案件结论”的逻辑，缺共享抽象
- 若直接在页面上补按钮而不补 action 层和审计结构，后续无法稳定支撑改判与处罚回放

### 3.3 `crowd-review/cases` 缺的是管理员动作编排，不是底层能力空白

现状：

- 页面上已预留“接管轮次 / 撤销轮次 / 改判留痕（待接入）”
- API 仍只有列表和详情
- 底层其实已有以下可复用能力：
  - `crowd_review_rounds.result_code` 已支持 `admin_override`
  - repo 已有 `updateRound`
  - service 已有 `applyCrowdReviewRoundResultToReportCase`
  - schema 已有 `inspector_discipline_events` 作为纪律留痕参考

对应文件：

- `pages/admin/crowd-review/cases.tsx`
- `pages/api/admin/crowd-review/cases/index.ts`
- `pages/api/admin/crowd-review/cases/[roundId].ts`
- `lib/crowd-review/service.ts`
- `lib/db/repositories/crowd-review.ts`

判断：

- 本轮不需要推翻众查 service
- 应在 admin 层补“接管 / 撤销 / 改判”三个语义化动作
- 动作必须同时处理：
  - 轮次状态
  - 必要的案件回写
  - 管理员留痕
  - 对现有派单/投票记录的保留或撤销策略

### 3.4 测试目前偏 API 读写，页面级覆盖明显不足

现状：

- 已有：
  - `tests/admin-messages-api.test.ts`
  - `tests/admin-report-cases-api.test.ts`
  - `tests/admin-crowd-review-api.test.ts`
  - `tests/admin-governance-read-api.test.ts`
- 缺少：
  - `admin/messages` 页面测试
  - `admin/report-cases` 页面测试
  - `admin/crowd-review/cases` 页面测试

对比样板：

- `components/admin/report-appeals/AdminReportAppealsPage.tsx`
- `tests/report-appeals-page.test.tsx`

判断：

- 后续治理后台页面应向 `report-appeals` 的“页面交互 + 中文枚举 + API 测试”风格对齐
- 若直接拿当前页面硬测，测试价值有限；需要先把纯展示和标签映射提取出来

## 4. 方案比较

### 方案 A：继续在现有页面上直接补按钮和弹窗

做法：

- 不新增共享标签/目录层
- 不新增治理动作留痕表
- 在 `governance.ts` 和页面中直接追加逻辑

优点：

- 上线最快

缺点：

- 英文枚举和中文文案会继续分散
- `governance.ts` 会继续膨胀
- 正式结案/改判没有可靠审计基础

结论：

- 不推荐

### 方案 B：先补共享配置与动作层，再接页面和测试

做法：

- 新增消息模板目录和治理标签映射
- 为 `report-cases` / `crowd-review` 增加 admin action 层
- 增加轻量治理管理员动作留痕表
- 页面只消费 DTO、标签和动作接口

优点：

- 范围可控
- 能复用现有 repo/service
- 后续继续扩展时不会再把原始枚举和写逻辑散落在页面里

缺点：

- 首轮会多出一层共享配置和留痕结构

结论：

- 推荐方案

### 方案 C：直接重做统一治理平台

做法：

- 一次性抽象统一 case engine、治理工作流和 action log

结论：

- 明显超出本轮范围，不做

## 5. 推荐设计

### 5.1 先补共享展示与目录层

新增或抽取以下共享文件：

- `lib/messages/display.ts`
  - 从 `components/messages/messageUi.ts` 提取 `getMessagePriorityLabel` 等无 UI 依赖方法
- `lib/admin/message-catalog.ts`
  - 定义后台可选消息模板目录
  - 每项至少包含：
    - `scope`
    - `messageType`
    - `templateKey`
    - `label`
    - `description`
    - `defaultActionUrl`
    - `payloadHint`
- `lib/admin/governance-labels.ts`
  - 统一输出以下中文标签：
    - `ReportCaseStatus`
    - `ReportResolutionCode`
    - `CrowdReviewRoundStatus`
    - `CrowdReviewResultCode`
    - `CrowdReviewInspectorStatus`
    - `InspectorDisciplineEventType`

目标：

- 页面层不再直接手写 `open / pending_dispatch / normal`
- 原始 code 只作为次级调试信息保留
- 后续页面测试可直接锁定这些 label helper 的输出

### 5.2 `admin/messages` 交互改造

#### 目标

- 模板必须可选，不再手输
- 优先级、消息类型、模板说明必须中文化
- 管理员仍可看到真实 `templateKey`，但不再以其作为主交互

#### 交互调整

- 将“消息类型 + 模板键”改为两级选择：
  - 一级：消息场景/分类
  - 二级：模板
- `messageType` 改为派生字段，不让管理员自由输入
- `templateKey` 显示为只读说明行
- `priority` 使用中文标签：
  - `low` -> `低优先级`
  - `normal` -> `普通优先级`
  - `high` -> `高优先级`
- 最近消息列表中增加：
  - 模板中文名
  - 原始 `templateKey` 次级展示
  - 优先级中文标签

#### API 范围

- 维持现有接口不变
- 若需要筛选模板，前端仍传 raw `templateKey`

#### 建议影响文件

- `components/admin/messages/AdminMessagesPage.tsx`
- `lib/admin/message-catalog.ts`
- `lib/messages/display.ts`
- `components/messages/MessageCard.tsx`

### 5.3 `report-cases` 正式动作设计

#### 目标

- 支持管理员在后台正式结案
- 支持对已结案案件进行改判
- 支持在结案时顺手执行数据卡处罚
- 保留最小可审计留痕

#### 关键前提

数据卡处罚不重新发明一套逻辑，直接复用现有内容管理后台能力：

- `batchUpdateDataCards`
- `getDataCardNotificationTargets`
- `sendDataCardModerationMessages`

#### 留痕策略

本轮不新增治理管理员动作表。

替代策略：

- 先在 admin action 层保留统一的 `note / reason / payload` 结构
- 众查改判信息优先写入 `crowd_review_rounds.result_summary_json`
- 举报案件的管理员备注优先作为本次动作请求参数参与消息、状态回写和测试断言，不额外持久化到新表
- 在 service / handler / DTO 命名上预留未来迁移到统一动作留痕表的空间

说明：

- 这意味着本轮留痕是“结构预留优先，持久化后补”
- 后续若动作继续增多，再补 `governance_admin_actions` 会更稳妥

#### 建议新增共享 repo/helper

- 从 `report-appeals` 与 `crowd-review` 的重复逻辑中抽出共享 helper
- 建议位置：
  - `lib/db/repositories/data-card-reports.ts`
  - 新增 `updateReportCaseDecision(...)`

职责：

- 更新 `status`
- 更新 `resolutionCode`
- 更新 `closedAt`
- 更新时间戳

后续三处复用：

- `report-appeals`
- `crowd-review`
- `admin/report-cases`

#### 建议新增 API

- `POST /api/admin/report-cases/[caseId]/decision`

建议 payload：

```json
{
  "nextStatus": "resolved",
  "resolutionCode": "confirmed_violation",
  "resolutionNote": "管理员复核后确认违规。",
  "notifyCreator": true,
  "creatorMessageReason": "请按说明整改",
  "cardModerationAction": {
    "action": "set_public_status",
    "value": -1,
    "messageOptions": {
      "send": true,
      "defaultReason": "公开卡违规封禁"
    }
  }
}
```

#### 合法状态组合

- `resolved`:
  - `confirmed_violation`
  - `content_removed`
  - `self_remediated`
- `dismissed`:
  - `no_violation`
  - `malicious_report`
- `under_review`:
  - `null`

其中：

- `under_review + null` 表示重新打开或改回人工复核
- `resolved` / `dismissed` 同时承担“首次正式结案”和“改判”两种语义

#### 数据卡处罚策略

首版只复用已有内容管理动作，不发明新的处罚枚举：

- `reject`
  - 复用 `review_status = rejected`
- `set_public_status = 0`
  - 下架为私有
- `set_public_status = -1`
  - 封禁公开卡

说明：

- `content_removed` / `self_remediated` 不强制伴随处罚动作
- `no_violation` / `malicious_report` 不允许附带数据卡处罚

#### 页面交互

`/admin/report-cases` 详情区新增“正式处理”卡片：

- 处理结论选择
- 管理员备注
- 可选作者通知
- 可选数据卡处罚
- 提交后刷新详情与列表

同时保留现有“仅通知作者”动作，但其定位从“主要处理动作”降为“补充通知动作”。

#### 建议拆分文件

- `lib/admin/report-cases.ts`
- `pages/api/admin/report-cases/[caseId]/decision.ts`

当前 `lib/admin/governance.ts` 保留读模型，动作逐步迁出，避免继续膨胀。

### 5.4 `crowd-review/cases` 管理员动作设计

#### 目标

- 管理员可接管轮次
- 管理员可撤销轮次
- 管理员可对轮次作出改判
- 所有管理员动作均有留痕

#### 建议新增 API

- `POST /api/admin/crowd-review/cases/[roundId]/take-over`
- `POST /api/admin/crowd-review/cases/[roundId]/cancel`
- `POST /api/admin/crowd-review/cases/[roundId]/override`

#### 动作语义

##### 1. 接管轮次

用途：

- 当轮次存在争议、票型异常、需要管理员直接处理时，将轮次升级给后台

处理：

- `crowd_review_rounds.status = escalated`
- `crowd_review_rounds.result_code = escalated`
- `report_case` 回到 `under_review + null`
- 在 `result_summary_json` 中补充管理员接管元数据，便于详情页直接展示

##### 2. 撤销轮次

用途：

- 当前轮次数据无效、派单错误、需要废弃当前轮次重新处理

处理：

- 将仍处于 `assigned` 的派单批量改为 `revoked`
- `crowd_review_rounds.status = cancelled`
- `crowd_review_rounds.result_code = null`
- `report_case` 回到 `under_review + null`

说明：

- 已完成的投票记录保留，不硬删除
- 详情页可继续查看历史投票，但需要标注“此轮已撤销”

##### 3. 改判

用途：

- 管理员基于现有投票与案件材料，覆盖轮次结论

建议 payload：

```json
{
  "caseDecision": "violation",
  "reasonCode": "admin_override",
  "reasonDetail": "管理员认定该轮结果不足，改判为确认违规。"
}
```

允许值：

- `violation`
- `no_violation`
- `reopen_under_review`

处理：

- 轮次 `result_code = admin_override`
- `status = concluded`
- `result_summary_json` 写入：
  - 原始结果
  - 覆盖目标结果
  - 管理员 ID
  - 理由
  - 时间
- 案件回写：
  - `violation` -> `resolved + confirmed_violation`
  - `no_violation` -> `dismissed + no_violation`
  - `reopen_under_review` -> `under_review + null`

#### 建议新增 repo/helper

- `revokeActiveAssignmentsByRound(roundId, now)`
- `appendRoundAdminSummary(roundId, payload)`

建议文件：

- `lib/admin/crowd-review.ts`
- `pages/api/admin/crowd-review/cases/[roundId]/take-over.ts`
- `pages/api/admin/crowd-review/cases/[roundId]/cancel.ts`
- `pages/api/admin/crowd-review/cases/[roundId]/override.ts`

## 6. 推荐实施顺序

1. 提取共享标签与消息目录层
2. 完成 `admin/messages` 交互改造与中文文案替换
3. 抽出共享 `updateReportCaseDecision(...)`
4. 完成 `report-cases` 的正式处理 API 与页面
5. 完成 `crowd-review/cases` 的接管 / 撤销 / 改判 API 与页面
6. 补齐 API 测试、服务测试
7. 复核是否存在需要 cherry-pick 到 `feature/v0.2.0_Battle_Growth_MahoShojo` 的共享修复
8. 最后执行：
   - `bun test`
   - `bun run lint`
   - `bun run build`

## 7. 风险与注意事项

- `lib/admin/governance.ts` 当前同时承担读模型与部分动作，继续堆功能会明显失控；本轮应开始拆分动作文件
- `crowd-review` 的管理员撤销/改判不能破坏现有派单与投票历史，必须以“标记状态 + 留痕”替代删除
- `report-case` 的正式处理本轮不引入新表留痕，后续若需要严格审计需补专门动作表
- 本轮仍未处理后台严格鉴权，上线前必须补强
- 管理员相关页面与 `pages/api/admin/*` 只能留在 `feat/admin`，不得 pick 到生产分支
- 如有需要 pick 到 `feature/v0.2.0_Battle_Growth_MahoShojo` 的内容，只能是共享 helper、非后台 bugfix 或通用 service 修复

## 8. 本文结论

本轮剩余工作不需要重做治理域，只需要在现有能力之上补三层：

1. 共享目录与中文标签
2. 管理员正式动作层
3. API 与服务测试

其中最关键的结构性补丁不是按钮本身，而是：

- 把 `messages` 的模板选择从“手填 code”改成“目录化选择”
- 把 `report-cases` / `crowd-review` 的正式写操作从“页面占位”升级成“有统一请求结构、可后续接审计的后台动作”
- 在本分支内完成后台能力，同时对潜在生产分支共享修复保持可 cherry-pick 边界

在此基础上，后续即可进入实现计划和分批开发。
