# Arena 战后角色更新双信任通道规格

日期：2026-09-01
状态：`PARTIALLY-SUPERSEDED`
规格标识：`SPEC-arena-post-battle-dual-trust-v1`

2026-09-01 取代说明：[平台复杂度预算与故障降级决策](../decisions/2026-09-01_193200_平台复杂度预算与故障降级决策.md)
撤回了完整角色 `baseRevisionHash`、完整 roster 等价与 provenance 连续性作为普通战后更新许可的要求。
本规格的 generation owner、completed terminal、服务器冻结 effect、原生性因果校验、非权威 repair 和
Room 权限边界继续有效；与上述取代说明冲突的正文只作历史背景。

## 1. 适用关系

本规格补充 `SPEC-hosted-resumable-generation-stream-v1` 的 `RESUME-STORAGE-005`。服务器权威角色对账以
上述 2026-09-01 决策修订后的稳定身份和局部降级语义为准；非权威修复只生成用户本地角色派生版本，
不改变 generation、战报、排位或 Room authority。

多人结果动作继续受 Arena 多人产品一致性规格约束：member 只能查看安全投影，不获得 host 私有角色的 repair、保存或写回权限。

## 2. 问题与目标

当前 `/api/arena/update-combatants-after-stream` 通过 generation owner、completed/finalized terminal、
冻结的 `localCardReconciliation` effect 和稳定 roster identity 防止浏览器伪造 `report`、`impacts`
或写入开关。原生性只在当次 effect 需要重签时按服务器冻结签名或 exact canonical preset 当场校验；
校验失败降级为非原生，不阻塞低风险更新。

现状同时移除了 AI 重做尾部 metadata 和用户手工修复 impact/current state 的能力。目标是在权威通道旁新增一条职责独立的非权威修复通道：允许用户编辑自己的角色结果，但该通道不产生、恢复或继承服务器原生签名。

## 3. 通道 A：Authoritative Reconciliation

现有权威端点继续负责 generation 正常结束后的自动写入、刷新恢复、网络失败重试与原生角色重签。

端点 MUST：

- 验证 generation owner、completed terminal、`finalizationCompleted` 和冻结 manifest；
- 只采用服务器冻结的 report、impacts、guidance、scenario authority 与 write flags；
- 按 room combatant key、DataCard ID、exact preset template 或无稳定 claim 时的唯一 `type + name`
  对应当前角色；歧义或缺失角色局部跳过并返回 warning；
- 不信任客户端 `isNative`；只在当前合法签名与本次冻结签名一致，或 exact canonical
  preset 与冻结 template 一致时重签；其余按 non-native 继续；
- 保持同 `generationId` 的服务器冻结 effect 幂等，重试不调用 Provider。

浏览器提交的同名 effect 字段不得覆盖服务器数据。新增 repair 能力不得削弱上述门禁。

## 4. 通道 B：Non-Authoritative Repair

非权威修复用于 AI 重新生成或用户手工修正本次 generation 的 `impact` 和 `currentStateSummary`。它只改变当前用户持有的角色工作副本，不写 D1 generation terminal、battle report、rating、ranking evidence、season、leaderboard 或 Room authority。

### 4.1 精确目标与原子性

- repair patch 必须同时携带 roster index 与展示名称；index 是定位依据，名称只用于一致性校验和 UI。
- 同名角色不得通过 `.find(name)` 或模糊名称匹配定位。
- 同一角色在一次 repair 中最多出现一个 patch。
- 所有目标先完成校验，再原子应用；任一目标无效时不得产生半更新。
- patch 与现值完全相同时返回 no-op，不得让角色无意义失去原生身份。

### 4.2 同 generation PATCH

- history 只允许修改 `entry.metadata.generation_id === generationId` 的唯一 entry；长度保持不变。
- 找到多条同 generation history 时 MUST fail closed，返回 `ambiguous-generation-effect`。
- current state 只允许在 `current_state.generation_id === generationId` 时修改 summary；不得覆盖后续 generation 或猜测 legacy state。
- 未找到目标 effect 时先返回 `generation-effect-not-found`。UI MAY 在明确二次确认后创建本次 generation 的自定义 effect；不得静默追加。
- repair 不使用 generation `baseRevisionHash` 作为编辑权限门禁。

### 4.3 信任与 canonical identity 降级

任何真实修改后的角色数据 MUST：

- 删除顶层 `signature` 与 legacy `metadata.signature`；
- 在活动 combatant wrapper 上设置 `isValid=false`、`isPreset=false`；
- 清除 `sourceDataCardId`、`sourceDataCardUpdatedAt`、`arenaRoomKey`、`adjudicationSourceKey` 等可执行 canonical identity；
- 在后续内容安全与排位判断中作为 non-native、non-canonical derivative；
- 不调用 `applyPostBattleUpdates()`、`generateSignature()` 或其他 authoritative projector。

未修改角色保持原样。混合 roster 按角色处理，不得因一个角色被修复而整体降级。

原生角色或 canonical preset/DataCard 被修复前，UI MUST 明示将创建当前会话中的非原生可编辑版本；源 preset、源文件或云端卡不会被自动覆盖。保存或替换继续使用现有显式用户操作。

### 4.4 权威重试与 repair

repair 与权威重试仍是两个显式动作。repair 会产生 unsigned、non-canonical 本地派生版本；
稳定 roster identity 仍能对应时，旧 generation 的服务器冻结 effect 可局部重试，但不得因此
恢复或继承旧原生签名。

## 5. AI repair contract

新增语义明确的 repair endpoint。旧 `/api/arena/redo-combatant-updates` 继续返回 `410 ARENA_REDO_RETIRED`。

新 endpoint 只负责：

- 在 Hosted/Hono 权威链路校验 generation actor owner、completed terminal、`finalizationCompleted`、Provider provenance 与资源上限；
- 把角色内容按服务端验签结果交给现有内容安全策略；
- 根据 battle report 和当前 state 生成经过 schema 校验的 repair patch；
- 返回带 roster index 的 `impacts` 草稿。

AI repair MUST 使用原 generation 实际执行并写入 D1 的同一 Provider 与模型，不得根据修复时 UI 当前选项重新选择、负载均衡或静默回退：

- 系统通道必须按 `ai_provider_name + ai_provider_type + ai_model` 精确钉住当前服务器配置中的实例；原实例或模型不可用时返回稳定 `503`，不得改用其它系统 Provider；
- BYOK 必须由客户端在 generation dispatch 时创建仅驻留当前页面进程的完整请求快照，repair 时原样提交该快照；服务端必须用 D1 中的 `custom_provider_id + custom_model_id` 和实际执行 provenance 双重核对后才可调用；
- 用户在战报生成后切换 Provider、model 或 Key 不得改变这次 repair；生成时快照缺失、页面刷新丢失、身份不匹配或 provenance 不完整时必须 fail closed，并提示用户重新生成战报，不得使用当前 UI 配置代替；
- BYOK API Key 不得进入 Zustand/localStorage/sessionStorage、D1、generation manifest、日志、遥测或公开错误；只允许存在于 Provider 请求边界和本次页面进程内存；
- 匿名 actor 必须沿用 generation actor token；已登录用户必须沿用既有 owner identity，不能仅凭 generationId 调用。

Provider timeout、Provider 输出校验失败，以及 authority/safety/D1 不可用必须投影为稳定的 `504`、`502` 或 `503` 错误 wire；不得让预期故障坠落为无分类 HTTP 500。repair schema、战报 precheck 与 prompt contract 必须由 runtime-neutral `@mahoshojo/ai-core` 公共入口提供，Web 手工修复与 Hosted AI repair 不得各自维护漂移副本。

它 MUST NOT 返回更新后角色、调用角色更新/签名实现、修改 generation authority 或结算排位。客户端收到 patch 后仍需经过第 4 节的确认与 unsigned domain primitive。

## 6. UX

结果页把操作明确分成：

- “重试角色更新”：重入同 generation 的服务器冻结 effect，不调用 AI，不受 Provider cooldown 影响；
- “AI 重新生成”：只生成修复草稿，受对应 Provider cooldown 约束；
- “手动编辑”：允许导入/修正 impacts 子集，再显式应用 unsigned repair。

AI 草稿不得自动应用。手工输入可复用现有 `MAHOSHOJO_ARENA_META` 解析能力，但只读取 repair 允许字段。

## 7. 验收

- reconciliation 的 owner/finalization/frozen effect/稳定 identity/原生因果签名回归通过；
- 非原生与原生角色均可手工、AI 修复，真实修改结果不含两种 signature；
- modified preset/DataCard/Room combatant 不再携带 canonical identity；
- mixed roster 只改变被修复角色，重名通过 index 精确定位；
- 同 generation history replace 且长度不变，ambiguous/missing 明确失败；
- current state 不覆盖其它 generation；
- AI endpoint 只返回 patch，旧 redo 继续 410；
- AI endpoint 校验 owner/terminal/finalization，并精确复用原 generation 的实际 Provider/model；BYOK 使用生成时内存快照且不持久化 Key；
- Provider timeout/失败/无效输出与依赖不可用返回稳定非 500 wire，不泄漏凭据或上游错误细节；
- repair 后不会借 authoritative retry 恢复原生签名；
- Room member 仍无 host 私有角色写回能力；
- 云端保存 repair derivative 后按 unsigned 数据重新计算原生性。

## 8. 非目标

- 不改变 generation、rating、ranking、season、leaderboard 或 Room authority；
- 不恢复旧 redo endpoint 的 apply/sign 行为；
- 不在首版引入跨页面 repair 草稿持久化；
- 不为 repair 复用 generation base hash 作为 optimistic concurrency token。
