# Arena 多人产品一致性与既有 Arena 复用修订

日期：2026-08-31
状态：`accepted / remediation baseline`
规格标识：`SPEC-arena-multiplayer-product-parity-amendment-v1`
审查基线：默认分支 `feature/v0.2.0_Battle_Growth_MahoShojo`，远端 HEAD `da88fa7f1c939346d564597101f987f85696bc47`

## 1. 目的与权威关系

本修订用于关闭 Arena 多人当前实现与最初已接受产品规格之间的差距，重点恢复以下原则：

> **多人模式不是第二套竞技场。Room 只提供实时协调、权威配置、Proposal 与单次权威生成；配置编辑、数据卡选择、战报展示、角色结果展示等产品能力应尽量复用现有 `/arena` UI/UX 与业务组件。**

本修订不推翻已经完成的 Hono + Redis Room runtime、RoomActor、checkpoint-before-ack、ticket/WSS、reconnect、typed Proposal、single-producer generation、Redis-only directory、安全投影和故障恢复设计。

本修订对以下既有文档做**后续澄清/覆盖**：

- `docs/specs/2026-08-21_arena-multiplayer-v1-spec.md`：继续作为业务基线；本修订细化其中“继续使用现有 Arena UI”“房间权威配置”“战报与角色更新沿用现有语义”的落地方式。
- `docs/specs/2026-08-28_143000_Arena多人GMR-08Proposal端到端设计.md`：其中为了阶段闭环而采用“受限 Shared Config editor”的实现策略，不得再解释为最终产品形态。独立的小型 Proposal 配置编辑器属于待淘汰过渡实现。
- `docs/specs/2026-08-28_190500_Arena多人GMR-09权威生成发布设计.md`：其中“generation start 时若 host local sharedConfig 不同就先 publish-config”的路径不得继续产生**静默覆盖 Room authority**的效果；生成前必须执行本文定义的显式 reconciliation / preflight。
- `docs/plans/2026-08-27_Arena多人Goal切片执行指南.md`：其中 `GMR-11 = IN_PROGRESS` 只代表本次产品一致性审查前的历史执行状态。**自本修订接受起，GMR-11 的有效状态规范性覆盖为 `BLOCKED`，直到 `GMR-10P = DONE` 后才可恢复。** 在该指南未来被物理更新前，以本文和配套 GMR-10P 计划作为状态 overlay。

若后续切片文档、测试或实现与本文及上位 Arena v1 业务规格冲突，应停止当前切片并以本文和上位规格为准，不得为了保持旧 GMR 的 `DONE` / `IN_PROGRESS` 状态继续保留产品背离。

## 2. 本次审查确认的产品缺口

当前实现至少存在以下需要整改的差距：

1. member Proposal UI 只暴露 `battleMode`、`storyLength`、`userGuidance` 三类编辑；但 contract/core 已能表达新增/删除角色、角色引导、队伍、主/辅情景、素材、历史设置等 typed change。
2. member 没有“同步 Room Config 后继续使用现有 Arena UI 编辑 working copy”的产品体验，而是在多人面板内出现第二套残缺编辑器。
3. host 接受 Proposal 后，Room Shared Config 与 host 本地 `useBattleStore` 可能继续分叉；host 点击生成时又会从本地 store 构建 `sharedConfig`，并可能重新覆盖已接受 Proposal。
4. Proposal 可以表达新增 online DataCard ref，但当前真实 generation payload 的完整角色/情景/素材内容仍主要来自 host 本地 BattleStore，缺少“frozen Room config -> 权威生成输入”的完整 materialization 层。
5. 房间战报在多人面板中自建纯文本区域，没有复用 `StreamingBattleReportCard` / `BattleReportCard` / `BattleResult` 的 presentation 能力，因此丢失元数据显示、保存图片等既有能力，并形成长期双实现风险。
6. Room result projection 过度收窄，只提供正文/状态等信息，尚未满足原始规格中的判定结果、角色变化/当前状态安全投影和适合共享的生成 metadata。
7. 原始 host 权限中的“更新房间配置”“移除成员”“停止生成”没有完整产品入口。
8. public room discovery 直接占据 Arena 主页面纵向空间，且 Web controller 当前只消费第一页结果，未形成完整 cursor UX。
9. 部分真实 Arena 生成语义输入仍未纳入 Shared Config / Proposal 覆盖审计，例如语言、questionnaire/lore、安全可共享的 adjudication 配置等；任何遗漏都应被显式分类，而不是静默丢失。

上述问题属于 **product integration / correctness remediation**，不应以 runtime 已通过 fault/load audit 为理由跳过。

## 3. 核心不变量

### INV-PARITY-001：单一 Arena 产品面

- 保持单一路由 `/arena`。
- 不建立 `MultiplayerArena`、`RoomArenaEditor` 等第二套完整竞技场页面。
- 多人面板只负责 room shell：状态、成员、Proposal 状态、room actions、连接/错误恢复。
- 角色、情景、素材、故事选项、读写设置、战报与结果展示继续出现在既有 Arena 产品区域。

### INV-PARITY-002：同一套 UI/UX，不等于共享同一个全局 store

“复用现有 Arena UI”定义为：

- 复用同一套 presentation / editor component、选择器、数据卡 Modal、校验、交互和可访问性语义；
- 允许通过 store/context/adapter 注入不同编辑会话；
- 禁止为了避免重构而复制一套缩水控件。

member Proposal working copy 必须与用户单人 Arena 状态隔离，不能通过临时覆盖全局 `useBattleStore` 实现复用。

推荐将现有 Arena 编辑状态逐步抽象为 scoped store / editor adapter。项目当前使用 Zustand；需要独立作用域/依赖注入时，优先使用 Zustand vanilla `createStore` + React Context，再由共享 selector/action hooks 接入 UI。

参考：

- Zustand scoped/initialized store guide: https://zustand.docs.pmnd.rs/learn/guides/initialize-state-with-props
- Zustand `createStore`: https://zustand.docs.pmnd.rs/reference/apis/create-store.html
- React state architecture: https://react.dev/learn/managing-state

### INV-PARITY-003：Room Shared Config 是多人生成的唯一语义权威

在已加入多人房间时：

- `ArenaRoomSharedConfig` 表示下一次多人生成的权威共享语义；
- host 本地 Arena 编辑状态是 working copy，不是可绕过 Room authority 的第二权威源；
- accepted Proposal 一旦进入 Room revision，就必须进入后续 generation preflight 所观察的权威配置，除非 host **显式**再次修改并发布；
- generation start 不得因为 host local store 与 Room config 不同而静默执行 `publish-config` 并覆盖已接受 Proposal。

### INV-PARITY-004：host 仍拥有最终控制权，但覆盖必须显式

host 可以最终否决/覆盖成员 Proposal，但必须通过可见动作完成：

- 接受/拒绝 Proposal；
- 编辑现有 Arena UI 后点击“更新房间配置”；
- generation preflight 检测到 host working copy 与 Room authority 不一致时，由 host 明确选择如何处理。

不得把“点击生成”解释为对所有当前 Room 配置的隐式覆盖授权。

### INV-PARITY-005：一次多人生成只消费一个 frozen authority snapshot

开始多人生成时：

1. 确认 room/epoch/revision；
2. 解决 host working copy 与 Room authority 的显式 reconciliation；
3. 冻结最终 `ArenaRoomSharedConfig`；
4. 验证/解析其中所有引用；
5. materialize 成权威 generation semantic input；
6. reservation checkpoint；
7. 单次 provider execution；
8. Room safe fan-out / authoritative terminal。

客户端提交的完整 generation payload 不得覆盖 frozen Room config 的同名语义字段。

### INV-PARITY-006：多人结果复用现有 BattleResult presentation

- 禁止继续维护独立的 `ArenaRoomGenerationReport` 文本展示体系作为最终产品路径。
- streaming 和 final report 应进入现有战报卡 presentation layer。
- 多人来源可以有独立的 result adapter / view model，但不能复制卡片 UI。
- 用户在多人战报中应继续获得适用的元数据显示、保存图片等既有展示能力。

### INV-PARITY-007：安全边界不因 UI 复用而放宽

- member 不能上传/粘贴本地 JSON 作为 Proposal 内容。
- member 不能读取 host-local 完整 payload。
- member 不能枚举或借 Room membership 读取他人 private DataCard。
- Provider/API credential 永不进入 Room Shared Config、Room checkpoint、WSS、member result DTO 或日志。
- 复用组件时必须通过 capability 禁用 host-only / local-only action，而不是依赖“用户应该不会点”。

## 4. Arena Editor Session / Adapter

### 4.1 目标

将当前大量直接依赖全局 `useBattleStore` 的编辑组件逐步收敛到一个可注入的 Arena editor session。

建议概念接口：

```ts
type ArenaEditorMode = 'single' | 'room-host' | 'room-proposal';

type ArenaEditorCapabilities = {
  canUploadLocalPayload: boolean;
  canPasteLocalPayload: boolean;
  canBrowsePrivateCards: boolean;
  canAddPresetRefs: boolean;
  canEditSharedConfig: boolean;
  canPublishRoomConfig: boolean;
  canStartGeneration: boolean;
  canPersistCharacterUpdate: boolean;
  canUseHostOnlyGenerationOptions: boolean;
};

type ArenaEditorSession = {
  mode: ArenaEditorMode;
  capabilities: ArenaEditorCapabilities;
  store: ArenaEditorStoreApi;
};
```

具体命名可由实现阶段调整，但必须保持“同组件 + 不同 session/adapter”的架构目标。

### 4.2 single

- 默认连接现有完整 Arena state/action。
- 行为应保持兼容，避免为了多人整改破坏单人。

### 4.3 room-host

- 继续使用完整 Arena UI 和 host 可用本地 payload。
- 额外维护 Room authority baseline / revision / dirty 状态。
- host 本地编辑不会逐键联网。
- “更新房间配置”才将安全投影发布到 Room。
- accepted Proposal 到达后必须触发 host workspace reconciliation，见第 7 节。

### 4.4 room-proposal

- 从 projected `ArenaRoomSharedConfig` 创建 detached scoped store。
- 只包含可安全共享的编辑 view model；host-local 项显示 stub，不伪装成完整角色对象。
- 编辑过程不联网。
- 提交时继续使用 `diffArenaSharedConfig(baseline, working)` 和 typed Proposal。
- 退出/丢弃 Proposal editor 不影响用户原来的单人 Arena 配置。

### 4.5 共享组件重构原则

优先重构现有组件为 presentation + adapter，而不是复制 JSX。例如：

- 角色列表：共享 roster presentation；single/host adapter 提供完整角色详情，proposal adapter 提供安全 stub/ref view。
- `BattleDataModal`：继续作为 online DataCard 选择体验；proposal mode 通过过滤器/回调只产生可提案 ref。
- 情景/素材选择：复用现有 Modal/列表/计数/容量提示。
- StoryOptions / BattleSettings：共享同一控件，capability 决定哪些字段可编辑。
- host-only 排位、provider、generation runtime 设置不进入 member Proposal session。

禁止通过 `if (multiplayer) ...` 在大量组件中复制另一套业务逻辑；模式差异应尽量集中到 adapter/capability。

## 5. Shared Config / Proposal 产品覆盖面

### 5.1 v1 应支持的共享语义

后续实现必须对当前真实 Arena generation inputs 建立一张 machine-readable 或 test-bound coverage matrix。至少覆盖：

- battle mode；
- combatant add/remove；
- team assignment；
- team display name（若现有 Arena UI 可编辑且影响生成）；
- per-character guidance；
- main scenario；
- auxiliary scenarios；
- materials；
- global user guidance；
- story length / custom story length；
- selected language；
- arena history/current state/narrative history 的安全读写设置；
- questionnaire/lore references 中可安全引用的部分；
- adjudication 配置中适合共享且不包含 host-only secret/runtime state 的部分。

任何当前 Arena generation semantic input 若暂不支持 Proposal，必须：

1. 在 coverage matrix 中显式标为 `host-only`、`not-shared-by-design` 或 `deferred-with-reason`；
2. 有测试保证它不会被 member UI 假装支持后静默丢弃；
3. 不得因为当前 mini editor 没有控件就反向宣称它不属于需求。

### 5.2 member 可新增内容来源

member v1 可：

- 从公开且 approved 的 online DataCard 选择角色/情景/素材；
- 添加具备稳定 canonical ID + version token 的允许引用；
- 添加 server-verifiable 的内置 preset ref（若 preset registry 能稳定解析并验证 digest）；
- 对 Room 中已有 host-local stub 提交不需要完整 payload 的安全修改，例如角色引导、队伍调整、移除建议。

member v1 不可：

- 上传/粘贴本地 JSON；
- 把自己的 private card 借 Room 临时共享给 host；
- 枚举 host private card；
- 创建任意伪造 ref/version token。

如果某 private card 已由 host 合法加入 Room，则 member 只能看到规格允许的安全 stub/ref projection，不能因为它已在 Room 中获得正文读取权限。

## 6. 权威 Generation Materialization

### 6.1 当前问题

仅验证 `DataCardRef` metadata 不足以保证 accepted Proposal 真正进入 AI 输入。真实 generation semantic payload 必须由 frozen Room config 构造，而不是继续信任 host local BattleStore 提交的同名对象数组。

### 6.2 建议增加 server-side materializer

建议引入窄化的 `ArenaRoomGenerationMaterializer`（名称可调整）：

```text
frozen ArenaRoomSharedConfig
  + request-scoped host-local payload map
  + host-only runtime/provider options
  -> verify exact refs
  -> resolve canonical payloads
  -> rebuild generation semantic input
  -> canonicalize/hash
  -> existing generation service
```

解析规则：

#### online DataCard ref

- 以 exact `id + kind + versionToken` 读取 canonical 数据；
- 权限/审核状态/删除状态/版本变化任一不满足即 fail closed；
- 不静默解析 latest。

#### preset ref

- 由 server-known preset registry 按 stable ID 解析；
- digest/version 不匹配即 stale；
- 不接受 member 任意提交的 preset payload。

#### host-local stub

- Room 只保存 stub；
- host 在 generation request 中只提交**当前 frozen config 实际引用到的** host-local payload map；
- payload 以 room-local opaque key 对齐；缺失、重复、key/type 不匹配即阻止生成；
- 完整 payload 仅在 request/generation plane 内存在，不写 Room checkpoint/WSS/member response。

### 6.3 semantic authority overwrite

进入 generation service 前，server 必须用 materialized frozen config 覆盖/重建以下语义，不信任客户端同名字段：

- combatants / team assignments / character guidance；
- scenario / aux scenarios / materials；
- shared guidance；
- language / story length；
- shared history settings；
- shared questionnaire/lore/adjudication selection；
- 其他 coverage matrix 中定义为 Room-shared 的 generation semantics。

host-only 的 provider credential、generation transport mode、允许的本地 runtime option 可继续 request-scoped，但不得改变 Room-shared semantic selection。

## 7. Host Working Copy 与 Proposal Reconciliation

### 7.1 host publish

恢复原始 UI 入口：

`[更新房间配置]`

点击后：

1. 从 room-host editor session 构造 safe Shared Config；
2. preflight refs / schema / limits；
3. 使用 exact room epoch/revision 发布；
4. Redis checkpoint 成功后更新 Room revision；
5. host workspace 记录新的 published baseline。

### 7.2 accepted Proposal

Room 接受 Proposal 后：

- Room Shared Config 立即成为新 authority revision；
- host UI 必须看见“房间配置已更新”；
- 若 host working copy 对相关字段没有未发布修改，应自动/确定性地 materialize 并同步到 host workspace；
- 若 host working copy 有未发布修改，不得静默覆盖任一方向，应进入 `hostWorkspaceStale/conflicted` 状态。

冲突状态至少提供：

- `同步房间配置`：放弃本地冲突修改，采用当前 Room authority；
- `查看差异`；
- `保留本地修改并重新发布`：由 host 明确覆盖 Room authority，产生新的 revision。

最后一项是 host 最终控制权的体现，但必须是显式动作。

### 7.3 generation preflight

host 点击生成时：

- workspace 与 Room authority 一致：直接冻结并开始；
- host 有未发布修改：显示 preflight，不得隐式 publish；
- host 可选择：
  - `更新房间配置并开始`；
  - `按当前房间配置开始`；
  - `取消`。
- 任何 unresolved materialization/stale ref/host-local payload 缺失都必须阻止生成并明确指出目标。

## 8. Proposal UX

### 8.1 member

多人房间控制区不再显示独立的三字段 mini editor。

推荐体验：

1. `[同步房间配置]`；
2. Arena 主编辑区切换/提示为“Proposal 草稿模式”；
3. 用户仍在熟悉的角色、情景、素材、设置区域编辑；
4. `[预览提案]` 打开 Proposal Modal；
5. Modal 展示 typed diff 后提交。

Proposal Modal 至少显示：

- baseline revision；
- change 分类；
- BASE -> PROPOSED；
- 默认勾选真实新修改；
- dependency / atomic group；
- stale/conflict/unsupported 原因；
- 最终提交项数。

### 8.2 host review

恢复原始的“待处理提案”Modal，而不是把技术审阅列表永久铺在多人面板。

至少显示：

- 提交者 display name；
- 提交时间 / proposal ID（ID 可作为次要诊断信息）；
- base revision；
- BASE / CURRENT / PROPOSED；
- same-target conflict；
- dependency / atomic group；
- 接受所选 / 拒绝全部。

host 接受后必须触发第 7 节 reconciliation。

## 9. BattleResult / 房间战报复用

### 9.1 presentation architecture

建议将当前 `BattleResult` 中“数据来源/host-only actions”和“结果呈现”进一步拆分：

```text
local generation adapter ----\
                             -> ArenaBattleResultViewModel
room generation adapter -----/          |
                                        v
                         shared BattleResultPresentation
                           -> StreamingBattleReportCard
                           -> BattleReportCard (when structured)
                           -> adjudication/result sections
                           -> safe character updates
```

具体组件名可调整，但必须做到：

- Room 不再自行渲染战报正文卡片；
- 本地和远端结果共享同一 presentation component；
- capability 决定哪些 action 可显示。

### 9.2 room-safe result projection

Room result DTO 应按 allowlist 扩展，而不是广播完整 generation record。至少评估并支持：

- authoritative markdown / structured report presentation data；
- reporter info；
- battle mode / scenario display name；
- shared global/character guidance（本就属于 Room safe config）；
- adjudication results；
- safe AI model/usage metadata（不得含 credential/provider diagnostic）；
- narrative-history read count 等适合展示的非敏感 metadata；
- per-combatant safe update projection：`combatantKey/displayName + impact + currentStateSummary` 等；
- authoritative generation ID/record identity 的安全展示字段。

默认不得向 member 投影：

- 完整 host-local character JSON；
- private card 正文；
- provider diagnostic / credential；
- server internal prompt/signature；
- 可能泄露隐藏 authority/system 信息的 raw reasoning；
- 可用于越权写回他人数据卡的内部 payload。

### 9.3 actions

- 所有 viewer：保存战报图片、普通复制/查看等纯 presentation action可复用。
- member：角色更新默认只读；不能执行 host-only redo/manual apply，也不能自动写回 host 的角色卡。
- host：在权限允许时继续使用现有显式保存/替换/另存能力。
- Room generation 仍不自动持久化角色更新到 DataCard。

## 10. Room Shell / 公开房间 / 管理 UI

### 10.1 常驻区域最小化

未加入房间：只保留紧凑“多人模式”入口。
已加入房间：只保留紧凑状态条，例如：

```text
房间 ABCD · 房主 Alice · 3 人
[同步/更新配置] [提案] [成员] [房间管理/退出]
```

不要把 room browser、完整 Proposal editor、完整成员管理、房间战报都永久堆在 Arena 配置区顶部。

### 10.2 public room browser

采用 Modal；窄屏可采用 full-screen Drawer/Sheet。

必须：

- 首批有界加载（现有 20 条可继续作为初始值）；
- 保留 server cursor；
- `加载更多` 或等价分页；
- 固定/有界可滚动内容区；
- loading/empty/error/retry；
- 不依赖精确高频在线人数。

若增加 title/search，必须使用有界/索引友好方案；不得为了搜索公开房间退化为 Redis 全量 scan。搜索不是本次 correctness blocker，cursor pagination 是。

### 10.3 room management

host 房间管理至少提供：

- 更新房间配置；
- 成员列表；
- 移除成员/kick；
- 停止当前 generation；
- 关闭房间。

member 提供：

- 同步配置；
- Proposal 状态/撤回；
- 成员查看；
- 离开房间。

## 11. 测试与验收

### 11.1 Product parity matrix

必须新增一份可执行/受测试约束的映射：

```text
Arena control / generation semantic
-> single
-> room-host
-> room-proposal
-> shared? host-only? forbidden? deferred?
-> contract change type
-> test id
```

没有分类的 Arena generation semantic input 视为审查缺口。

### 11.2 P0 golden E2E

至少建立以下真实交互路径：

1. host 创建房间；
2. member 同步 Room config；
3. member 使用复用 Arena UI 从公开在线库新增角色；
4. member 修改该角色 guidance，并再修改至少一个非三字段旧 mini-editor 能力（例如情景/素材/队伍）；
5. preview typed diff；
6. submit；
7. host 在 Review Modal 接受；
8. Room revision 更新；
9. host workspace reconciliation 完成；
10. host 点击生成；
11. frozen Room snapshot 精确包含 accepted changes；
12. materialized generation semantic payload 精确包含 accepted 角色/引导/其他字段；
13. host 原有 stale local state 不得静默覆盖；
14. provider 只执行一次；
15. host/member 都在共享 BattleResult presentation 中看到同一权威战报；
16. member 可使用保存图片；
17. member 看到安全角色变化摘要但拿不到 host-local/private full payload。

这条 E2E 未通过时，不得宣称多人 v1 product-ready。

### 11.3 必测负向

- member local upload/paste 在 proposal mode 不可用；
- member private card 不可通过 Room 获得访问；
- forged/stale DataCard ref fail closed；
- accepted Proposal + host dirty conflicting local edit 不被静默覆盖；
- generation start 不允许 client semantic payload 覆盖 frozen Room config；
- host-local payload key 缺失/错配阻止生成；
- room result DTO 不包含 secret/private full data；
- room report 不存在第二套正文 presentation implementation；
- public room cursor 第二页可访问；
- host kick / cancel 由 server authority 再校验；
- feature flag off / single-player 无回归。

## 12. Production Gate

在本修订定义的 P0 correctness 与 product parity 验收完成前：

> **暂停 Arena 多人 production activation。已完成的 GMR-11 ingress/release/rollback 基础设施可以保留，但不能把多人产品标记为 production-ready。**

自本修订起，逻辑执行总账新增 `GMR-10P`（Product parity remediation）；`GMR-11` 的有效依赖增加 `GMR-10P = DONE`，在此之前保持 `BLOCKED`。后续若物理更新旧 Goal 指南，应同步这一状态，不得恢复旧的无条件 `IN_PROGRESS`。

本修订本身不要求：

- production Redis/D1 migration；
- DNS/LB/Access/credential 修改；
- Room runtime 切回 Durable Object；
- multi-instance；
- 新聊天/CRDT/投票系统。

## 13. 明确非目标

继续不做：

- member 本地/私有 payload 临时共享；
- CRDT/Yjs 实时共同编辑；
- 聊天；
- host transfer；
- anonymous multiplayer；
- 大房间分片；
- 为了 UI 复用而把 secret/full local payload 写进 Room store；
- 为了“代码复用”强行让 member proposal 使用 host/single-player 的危险 action。

## 14. 完成定义

只有以下条件同时满足，才能认为本修订闭合：

- mini Shared Config editor 从最终产品路径移除；
- member 可通过复用 Arena UI 编辑完整 v1 safe proposal surface；
- host 有显式 publish 与 reconciliation；
- accepted Proposal 确实进入 frozen snapshot 和真实 generation semantic payload；
- generation start 不静默覆盖 Room authority；
- online/preset/host-local materialization 有 authority-bound 实现；
- Room 战报/结果复用现有 BattleResult presentation；
- safe metadata/角色更新 projection 恢复；
- kick/stop-generation/room management 闭环；
- public room browser 收纳并支持 cursor pagination；
- product parity matrix 与 P0 E2E 通过；
- targeted + package + workspace CI 通过；
- production activation 再次独立审查通过。
