# Admin 回归安全与迁移规格

状态：`active`
日期：2026-08-29
规格标识：`SPEC-admin-reintegration-v1`
适用阶段：Phase 3 Admin；其中 §4 定义 Phase 3 正式启动前允许的 `pre-work`

## 1. 定位与目标

本规格约束从长期分支 `feat/admin` 抽取管理后台能力、迁入当前 Monorepo `apps/admin` 并最终安全上线的全过程。

它不重新设计平台架构，也不放宽 Phase 2.5 的退出门禁。它把既有高层决定细化为 Agent 可执行、可审查、可回滚的迁移与安全契约，重点回答：

- `feat/admin` 中哪些资产可以迁、如何迁、哪些本地可信假设必须淘汰；
- Admin 浏览器、Admin 服务端、项目 API/数据库之间的信任边界；
- Cloudflare Access 与应用内管理员授权如何组合，而不是相互替代；
- 写操作、批量操作、导出、维护和系统配置如何获得幂等、并发控制、审计和回滚保护；
- 在 Phase 2.5 PR 已通过 CI、仍等待核心维护者 Review 时，哪些低耦合工作可以安全并行；
- 每一批迁移必须提供哪些机械证据，才能进入下一批或生产上线。

本规格所说的 Admin 是项目业务管理后台，包括 dashboard/analytics、内容、举报与复核、用户与徽章/兑换、Ratings/PVP/Arena 恢复、数据维护、导出和系统配置等能力；**不是**另造一套部署控制平面，也不得承担 Hosted DR runtime selection 等已有平台控制面职责。

## 2. 权威来源与冲突规则

执行时按下列优先级解释要求：

1. accepted ADR 与冻结产品/安全语义；
2. `docs/specs/2026-08-22_022600_平台重整实施规格.md`；
3. `docs/plans/2026-08-22_022700_平台重整分阶段实施计划.md`；
4. 本规格；
5. `docs/specs/2026-08-23_235200_平台重整Goal自治执行与验收规格.md`；
6. `docs/plans/2026-08-29_Admin回归Goal自治执行计划.md`；
7. 实施日志、迁移清单和测试证据。

若低优先级文件与高优先级文件冲突，Agent 必须服从高优先级文件并记录冲突，不得自行“折中”降低安全或兼容要求。若冲突会阻断 Goal，按通用 Goal 自治规格停止并报告。

`feat/admin` 只是一份历史实现与行为参考，**不是**当前安全、Schema、API、部署或依赖边界的权威来源。

## 3. 分支与迁移来源

### 3.1 新开发基线

Admin 回归必须从执行时最新、被项目接受为平台重整实现基线的提交建立新分支；不得直接在 `feat/admin` 上继续开发。

每次 Goal 启动至少记录：

- 当前实现基线分支和 commit SHA；
- PR #54 或其后继集成 PR 的状态；
- `feat/admin` 当时解析到的 source SHA；
- 相比上一次 Admin Goal 的上游变化摘要。

2026-08-29 本规格制定时，PR #54 的 head 是 `0b3d9f28f6b05700fac083d15653e3436dfc62d9`。该 SHA 只是制定时证据，不是永久 pin；Agent 启动时必须重新解析远端事实。

### 3.2 `feat/admin` 的使用方式

允许：

- 读取页面、组件、handler、repository、测试和历史文档；
- 以业务域为单位重建行为；
- 对单个文件或小片段做人工审查后的选择性移植；
- 用旧实现帮助识别遗漏的字段、状态、用户流程和运维能力。

禁止：

- merge 整个 `feat/admin`；
- 把 `feat/admin` rebase 成新的长期开发基线；
- 为了省事把旧 branch 的 app/API 目录结构、鉴权、数据库访问或秘密处理假设一并搬回；
- 用兼容旧 Admin 的方式反向污染已经收口的 `apps/web`、`apps/api`、shared package 或 Hosted DR 边界；
- 在没有重新授权、重新测试的情况下直接启用旧 mutating/destructive handler。

发生冲突时，以当前平台边界和当前业务事实为准；“旧 Admin 曾经这样做”不能作为绕过新约束的理由。

## 4. Admin downstream `pre-work`（不计入正式 Phase 3）

### 4.1 不改变正式 Phase 3 前置条件

现有计划中“Phase 2.5 已通过”仍是正式 Phase 3 和生产上线的前置条件。本规格只定义一类可并行的 **Admin downstream pre-work**；它是上游 Review 等待期的可逆准备工作，既不计入正式 Phase 3，也不改变 Phase 顺序，更不把“CI green”偷换为“Phase 2.5 已正式通过”。

### 4.2 `pre-work` 进入条件

同时满足以下条件时可以启动：

- Phase 2.5 当前实现已进入正式 Review，而不是仍处于大范围探索；
- 当前 head 的仓库级 CI 通过，或仅存在与本 Goal 无关且已明确记录的外部/生产 blocker；
- Admin pre-work 不依赖仍未接受的 production control-plane、DR drill 或其他未闭合能力；
- 新工作建立在当前平台分支，而不是 `feat/admin`；
- Goal 的每项改动可在不触碰生产数据和不可逆状态的情况下回滚。

### 4.3 `pre-work` 允许范围

- 完整 Admin 资产盘点与迁移分类；
- `apps/admin` 独立 app shell、build/lint/typecheck/test/CI 边界；
- contracts、client/BFF boundary、RBAC capability evaluator、audit envelope 等安全基座；
- Access JWT 验证抽象与隔离 fixture/negative tests，但不把未授权的生产配置写成已验证；
- CSRF/session/CORS/XSS/export safety 的通用中间件和测试；
- 只依赖已稳定 shared contract 的低耦合 read model/repository adapter 准备；
- 文档、威胁模型、runbook 草案和回滚方案。

### 4.4 `pre-work` 禁止范围

- 宣称 Phase 3 已正式进入或完成；
- 生产 Admin hostname 切流、生产 Access/Tunnel 策略变更或其他需外部授权的动作；
- 删除旧 Admin 表、不可逆 schema migration 或批量生产数据修复；
- 启用封禁、删除、恢复、维护、导出、系统配置等高风险生产写操作；
- 归档/删除 `feat/admin`；
- 为 Admin 需要而放宽 Phase 2.5 的 accepted contract、边界检查、secret policy 或 DR 语义；
- 把 Reviewer 尚未接受的上游行为当成长期兼容承诺。

上游 Review 若改变 Admin 所依赖的 contract，pre-work 分支应优先 rebase/适配，不得要求上游保留仅为临时 Admin 实现服务的兼容层。

## 5. 迁移资产清单

在迁移任何业务域之前，必须建立并持续维护迁移清单。格式可由 Agent 选择 Markdown 表、JSON、YAML 或其他仓库友好形式，但必须可审查，且至少包含：

```text
sourceRef
sourcePath
sourceKind            # page/component/route/handler/repository/table/test/job/config
businessDomain
dataTouched
riskClass
legacyTrustAssumptions
disposition           # keep/adapt/rewrite/drop/defer
newDestination
apiOrServiceContract
requiredCapability
auditRequirement
concurrencyOrIdempotency
migrationRequirement
testEvidence
rollback
status
notes
```

### 5.1 风险分类

至少使用以下风险维度；可以再增加更细标签：

- `R0 read-only`：读取统计、列表、详情；仍需处理越权、隐私与 XSS；
- `R1 mutating`：普通业务写入，可恢复且影响范围有限；
- `R2 privileged`：封禁、重置、恢复、评分修正、批量变更等高权限操作；
- `R3 destructive/export/maintenance/config`：删除、维护、导出、系统配置及可能跨大量数据或影响运行态的操作。

风险分类只影响迁移顺序，不影响“每个请求都必须鉴权”的原则。read-only 不等于 trusted。

### 5.2 `legacyTrustAssumptions` 必填

每个从旧分支迁移的 handler/repository 都必须明确旧实现依赖了哪些假设，例如：

- 只在 localhost 使用；
- 只有维护者能访问；
- 浏览器可直接持有数据库/平台 token；
- route 隐藏即视为授权；
- email 等同永久管理员 ID；
- 单管理员、无并发；
- mutation 不会重试；
- 页面不会渲染恶意用户内容。

无法解释旧信任假设的高风险资产不得上线。

## 6. Admin 信任与传输边界

目标调用路径原则上是：

```text
Admin browser
  -> same-origin apps/admin HTTP/BFF boundary
  -> application authorization + domain/service contract
  -> server-side repository / internal service
  -> data/runtime resource
```

### 6.1 浏览器边界

- Admin renderer/browser 不得获得 D1 管理 API Token、Gateway HMAC secret、数据库连接凭据、Cloudflare 管理 token 或其他服务器秘密；
- 浏览器不得直接调用特权 D1/Gateway/Hono 管理接口来绕过 Admin 应用授权层；
- 默认使用 Admin 同源 API/BFF，避免为了“前后端分离”制造一个新的公网特权 CORS surface；
- 若经事实证明必须跨 Origin，必须显式 allowlist、最小化允许方法/headers、正确处理 credential，并提供与同源方案等价的 CSRF、Access、RBAC 和 direct-origin 防护证据；不得使用 `*` 与 credential 组合。

### 6.2 应用间复用

`apps/admin` 不得源码级导入 `apps/web` 或 `apps/api` 内部实现。跨 app 复用必须下沉到职责清晰的 package，或通过版本化 service/API contract 完成。

不得为了迁移 Admin 创建新的长期 `packages/common` / `packages/shared` 倾倒目录。

## 7. Cloudflare Access 与 Origin 验证

Cloudflare Access 是公网 Admin 的外层身份门，不是应用授权系统本身。

### 7.1 Origin 必须验证 Access token

对需要 Access 保护的请求，origin/Worker 必须验证 `Cf-Access-Jwt-Assertion` 或平台提供的等价已验证上下文，至少验证：

- 签名和 JWKS/key rotation；
- `iss`；
- 应用 `aud`；
- `exp`，以及库默认覆盖的其他必要 JWT validity 条件；
- 请求所需的人类/服务身份 claim。

不得只检查 header 是否存在，也不得只因为流量经过 Cloudflare 就跳过应用侧/受信代理侧 token 验证。

如果使用 Cloudflare Tunnel 的 “Protect with Access” 等受支持能力代为做 origin token validation，必须有测试/配置证据证明实际生效；应用仍需执行内部管理员身份与 capability 授权。

### 7.2 Direct-origin bypass

- 自托管 origin 应优先通过 Tunnel 或等价方案避免暴露可绕过 Access 的直接入口；
- 若保留其他网络入口，必须有等价身份与网络控制；
- 上线验收必须包含无 Access / 错误 audience / 直接 origin 的负向测试；
- “Cloudflare Dashboard 中看起来配置了 Access”不是验收证据。

## 8. 管理员主体、角色与 capability

### 8.1 稳定主体

内部管理员主体必须使用稳定、不可由普通用户随意改变的外部身份键。推荐以经过验证的 `issuer + subject`（或 IdP 提供的等价 stable immutable ID）作为 canonical external key。

- email 可以作为显示字段、通知地址或受控属性，但不得单独作为永久管理员主键；
- service token 的主体语义必须与人类管理员分开；若 `sub` 为空或不代表人类，不得自动映射成人类管理员；
- 身份映射变化必须可审计。

### 8.2 Capability-first

授权模型保持：

```text
verified identity
  -> internal admin principal
  -> roles / policy attributes
  -> capabilities
  -> per-request action authorization
```

角色只是 capability bundle，不得在业务 handler 中散落 `role === 'admin'` / `isSuperAdmin` 作为唯一安全边界。

至少延续已有 capability：

- `users.read`
- `users.write`
- `multiplayer.recover`
- `data.maintenance`
- `system.config`
- `exports.read`

Agent 可按实际业务增加更细 capability；应优先最小权限，不得用一个过宽 capability 覆盖所有后续批次。

### 8.3 Deny by default

- 未匹配策略时拒绝；
- 每个请求/动作都在服务端验证权限；
- UI 隐藏按钮只改善 UX，不构成授权；
- 新增 route/action 未显式声明 capability 时必须 fail closed；
- capability 授权应有集中式可测试入口，不依赖开发者记得在每个 handler 手写一段容易遗漏的条件。

### 8.4 Bootstrap、撤销与 break-glass

生产上线前必须有明确方案回答：

- 第一个管理员如何建立且如何验证身份；
- 管理员离职/设备丢失/账号失陷如何同时从 Access 和应用 RBAC 撤销；
- 内部 RBAC 数据损坏时如何恢复；
- break-glass 是否存在、谁能使用、如何限时、如何记录、如何恢复到正常状态。

不得以隐藏 URL、硬编码邮箱、共享万能密码或浏览器中的“超级管理员开关”作为恢复机制。

## 9. Session、CSRF 与 CORS

对使用浏览器 cookie/session 的 Admin：

- mutation 不得使用 GET；
- session cookie 必须使用适当的 `Secure`、`HttpOnly`、`SameSite` 与最小 scope；
- state-changing 请求必须使用框架成熟 CSRF 机制、synchronizer token、signed double-submit、受信 custom header 或等价强度方案之一；
- 应结合 `Origin`/`Referer` 验证与 Fetch Metadata (`Sec-Fetch-Site` 等) 拒绝明显 cross-site 请求，并为不发送 Fetch Metadata 的合法客户端提供明确兼容策略；
- SameSite 是 defense-in-depth，不得单独当成完整 CSRF 方案；
- CORS 不能替代 CSRF 或授权；
- 对敏感 mutation，缺失/错误 CSRF 信号必须 fail closed。

如果最终 Admin 使用不依赖浏览器 ambient credential 的不同认证模型，Agent 可以调整 CSRF 机制，但必须在实施日志中说明威胁模型为什么等价或更强。

## 10. Mutation contract

每个 mutating / privileged / destructive action 必须有明确 server-side contract。按风险适用以下字段/语义：

- `actor`：从已验证身份映射，不接受客户端自报；
- `capability`：服务端动作到 capability 的显式映射；
- `target`：稳定资源 ID 与允许的目标类型；
- `requestId` / correlation ID；
- `reason`：高风险、人工裁决、批量、恢复、维护、导出、配置操作必须填写并审计；
- `expectedVersion` / `If-Match` / 等价乐观锁：用于会因并发覆盖造成错误的操作；
- `idempotencyKey` / stable operation ID：用于客户端/代理/任务可能安全重试且重复副作用不可接受的动作；
- confirmation：destructive/high-impact 操作提供清晰二次确认，必要时增加 fresh/step-up authentication；
- bounded scope：批量操作必须有显式选择范围、数量上限或可审计 job scope，不允许无界“全部执行”。

同一 action 的 UI、API、service、repository 和 audit 语义必须一致。不得只在前端实现 reason/confirmation/version 检查。

## 11. Audit contract

### 11.1 必须审计的事件

至少审计：

- 管理员身份/角色/capability 映射变更；
- 所有 R1–R3 mutation；
- 用户封禁/恢复、评分修正、Arena 恢复；
- 批量操作；
- 敏感数据导出；
- 数据维护和系统配置变更；
- break-glass 使用；
- 影响审计本身保留期、sink、过滤规则的配置变更。

高敏感 read（例如导出前预览、敏感用户详情）是否全部审计可由实际数据分类细化，但不得因“只读”自动排除。

### 11.2 审计最小字段

至少包含：

```text
eventId
timestamp
actorPrincipalId
authnContextSafeRef
capability
action
targetType
targetIdOrSafeScope
requestId
reason             # when required
expectedVersion    # when applicable
result             # success/denied/conflict/failed
errorCodeSafe
sourceContextSafe
```

可额外记录 before/after digest、变更字段名等安全元数据；默认不记录完整敏感业务内容。

### 11.3 不得进入日志/审计的秘密

不得直接记录：

- Access JWT / session token / API token；
- 密码；
- D1/Gateway/数据库凭据和连接串；
- encryption/private keys；
- 不必要的敏感个人数据；
- 原始导出内容。

需要关联 session/token 时使用安全摘要或不可逆引用，不写明文。

### 11.4 失败语义

对于规范要求必须审计的 mutation，**不能在业务 mutation 已成功但审计完全丢失的情况下仍返回成功**。

实现可以选择同事务写入、outbox、具备持久确认的审计管线等方式；具体机制由 Agent 根据当前存储边界决定。但必须有故障测试证明：审计持久化不可用时，受保护操作要么不发生，要么拥有不会静默丢审计的可证明恢复协议。

生产上线前必须明确 audit retention、访问权限、备份/导出和删除策略；本规格不预先指定固定天数。

## 12. 不可信内容与 Admin XSS

Admin 会主动查看昵称、举报文本、卡片内容、富文本、错误详情等攻击者可控内容，因此它是高价值 XSS 目标。

- 默认依赖框架的文本 escaping，不使用“不可信字符串直接成为 HTML”的 escape hatch；
- 必须显示受控 HTML/富文本时使用持续维护的 sanitizer，并在 sanitize 后避免重新拼接出危险 DOM；
- URL 进入 `href`/`src` 等上下文前必须解析、规范化并按允许 scheme/policy 验证；禁止 `javascript:` 等可执行 scheme；
- React `dangerouslySetInnerHTML`、类似 unsafe HTML API、动态 script/style/event handler 等必须有显式安全审查；
- CSP/Trusted Types 等可以作为 defense-in-depth，但不能替代正确的 output encoding/sanitization；
- 恶意 payload 必须进入 Admin UI security test fixture，而不是只测试正常文本。

## 13. 导出、批量与维护安全

### 13.1 导出

- 使用独立 capability；
- 明确导出对象、字段和数量/时间范围；
- 敏感字段默认最小化/脱敏；
- 生成行为和下载行为均可审计；
- 大导出优先使用受限异步 job 与短期 artifact，不通过超长同步请求或 raw database dump；
- artifact 下载必须重新授权或使用短期、最小权限、不可猜测且可撤销的访问机制；
- 面向 CSV/电子表格的格式必须防止用户提供值被解释为公式或主动内容。

### 13.2 批量/维护

- 预览/计划与真正执行应可区分；
- 明确 bounded scope、目标数量和失败策略；
- destructive maintenance 需要高风险确认、reason、审计与独立回滚/恢复方案；
- 不允许浏览器提交任意 SQL、shell、脚本或“万能维护 payload”；
- Admin 不得变成通用远程 shell/数据库 console。

## 14. Schema、数据和旧表处理

- pre-work 不执行不可逆生产 migration；
- 正式 Phase 3 数据变化遵循 expand -> caller rollout -> contract；
- 每个 domain 先证明新 reader/writer 与当前线上事实兼容，再删除旧路径；
- 迁移完成前不删除旧 Admin 数据表；
- 任何 backfill/repair 必须可重入、有范围、有进度/校验和失败恢复；
- Admin 自身数据（principal/RBAC/audit 等）也要有 migration/backup/restore contract，不能因为是“内部工具”就无版本管理。

## 15. 必需负向测试矩阵

除正常 happy path 外，至少覆盖：

1. 缺少 Access token；
2. JWT 签名无效；
3. `iss` 错误；
4. `aud` 错误；
5. token 过期；
6. Access 合法但没有 internal admin principal；
7. 有 `*.read` 但没有对应 write capability；
8. route 未声明 capability 时 deny by default；
9. cross-site / 缺失 CSRF 防护信号的 mutation；
10. stale `expectedVersion` 不覆盖新状态；
11. 重复 idempotency key 不产生重复副作用；
12. required audit sink 故障时不静默成功；
13. direct-origin bypass 被拒；
14. 恶意 HTML/URL/富文本不能在 Admin 页面执行脚本；
15. 无 `exports.read` 的身份不能导出；
16. browser bundle/runtime response/log 中无服务器秘密；
17. batch scope 超限被拒；
18. 用户输入无法变成任意 SQL/shell/通用管理命令。

生产 Access/Tunnel/direct-origin 的真实验证必须在获得授权的环境执行；若当前 Goal 无生产权限，应明确标为 `DEFERRED/BLOCKED`，不得用本地 mock 冒充生产 PASS。

## 16. 分批迁移与退出门禁

继续采用低风险到高风险顺序：

1. read-only dashboard/analytics；
2. content list/detail；
3. messages/report review；
4. user write/badge/redemption；
5. ratings/PVP/Arena room recovery；
6. data maintenance/export/system config。

Agent 可以按当前代码事实合并相邻低风险能力或拆分过大的业务域，但不得把后批次高风险操作提前塞进前一 Goal 以“顺手完成”。

每批完成前必须有：

- UI + service/API + repository/adapter 的端到端证据；
- capability 与 negative authorization tests；
- 适用 mutation/audit/concurrency/idempotency tests；
- secret/boundary 检查；
- migration/feature flag/rollback；
- 独立 review 或等价第二遍审查；
- 无未关闭 Critical/Important finding。

正式 Phase 3 最终退出仍要求：

- Admin 独立构建部署且不依赖切换 Git branch；
- Access/origin 与应用 RBAC 两层防护真实可验证；
- direct-origin bypass 闭合；
- browser 无服务器数据库/平台秘密；
- 所有写操作有 capability；
- 高风险操作具备 reason/version/idempotency/confirmation/audit 的适用组合；
- audit retention 与恢复 runbook 已明确；
- production rollback/deny-all 路径真实演练或在获得权限后完成；
- 旧 `feat/admin` 只读归档；
- 主线 tests/build/CI 通过。
