# Cloudflare Workers CPU 异常修复与降耗方案

## 1. 文档信息

- 状态：第一、二阶段已实施，第三阶段待实施
- 编写时间：2026-07-30
- 适用项目：Mahoshojo Generator
- 部署平台：Cloudflare Workers
- 运行框架：Next.js 15 + `@opennextjs/cloudflare`
- 主要数据服务：Cloudflare D1、R2

## 2. 背景

当前账期的 Workers CPU 使用量约为 `522.02M CPU ms`。Cloudflare Workers Paid 每个账期包含 `30M CPU ms`，超出部分按 `$0.02 / 1M CPU ms` 计费。

通过 Cloudflare GraphQL Analytics、Pages 部署记录及 D1 业务数据对照，已确认：

1. 账单统计是账号级统计，包含旧 Pages Functions 与新 `mahoshojo-next` Worker。
2. 当前账期约有 `6.63M` 次 Worker 调用，平均 CPU 约为 `78.4ms/次`。
3. CPU 首次持续性异常发生在北京时间 2026-06-24 02:00 左右。
4. 异常发生时没有新的生产部署；旧 Pages 最后一次成功生产部署发生在 2026-06-05。
5. 业务生成量没有同步增长，但 Worker 调用量从约 `20K～28K/天` 增长至约 `240K～330K/天`。
6. `/api/arena/generation-ranking` 存在无硬性上限的 1.5 秒轮询。
7. 该 GET 接口在发现结算事件缺失或 pending 时，可能主动执行排位结算，形成“轮询触发写操作”的放大链路。
8. `mahoshojo-next` 的单次调用平均 CPU 高于旧 Pages，迁移进一步放大了总 CPU。

当前主要异常链路为：

```text
流式生成建立连接
→ 客户端提前获得 generationId
→ 每 1.5 秒查询 generation-ranking
→ GET 发现 pending/missing
→ GET 尝试执行排位结算
→ 状态未及时收敛
→ 客户端继续轮询
```

## 3. 目标

### 3.1 核心目标

1. 消除流式生成阶段的无意义排位轮询。
2. 禁止公共 GET 接口触发排位写入或自愈结算。
3. 将正常情况下每次生成产生的排位查询从约 `30～60` 次降低至 `0～3` 次。
4. 降低流式生成中断、敏感词扫描和重复序列化造成的 CPU 消耗。
5. 建立限流、CPU 熔断、日志和预算告警，防止再次出现 denial-of-wallet。

### 3.2 量化目标

| 阶段 | Worker 调用目标 | CPU 目标 |
| --- | ---: | ---: |
| 48 小时止损 | ≤100K/天 | ≤8M CPU ms/天 |
| 一周内 | ≤40K/天 | ≤3M CPU ms/天 |
| 理想状态 | ≤20K/天 | ≤1M CPU ms/天 |

如需稳定控制在每账期 `30M CPU ms` 的包含额度内，滚动平均 CPU 应保持在约 `1M CPU ms/天` 以下。

## 4. 第一阶段：立即止损

预计工期：半天至一天。

### 4.1 流式生成期间禁止排位轮询

涉及文件：

- `components/arena/components/CombatantList.tsx`
- `components/arena/hooks/useBattleEngine.ts`

当前 `generationId` 在流式响应刚建立时就写入 store，导致战报尚未生成完成时轮询已经开始。

建议保留提前保存 `generationId` 的行为，但将查询启用条件改为：

```tsx
enabled: Boolean(lastGenerationId) && !isGenerating
```

轮询状态机调整为：

```text
生成结束
→ 立即查询一次
→ pending：2 秒后查询
→ pending：5 秒后查询
→ pending：10 秒后查询
→ pending：20 秒后查询
→ 最长 60 秒或最多 6～8 次
→ 超时后停止，并提供手动刷新
```

TanStack Query 推荐配置：

```tsx
retry: 1,
refetchOnWindowFocus: false,
refetchIntervalInBackground: false,
```

`queryFn` 应接收 TanStack Query 提供的 `AbortSignal` 并传给 `fetch`，以便在组件卸载、generationId 变化或查询取消时立即终止旧请求。

预期效果：

- 流式生成期间的排位查询降为 0。
- 正常情况下每局排位查询降低至 1～3 次。
- `/api/arena/generation-ranking` 调用量预计从约 `91K/天` 降低至 `3K～9K/天`。

### 4.2 增加服务器端限流

旧页面或已打开的浏览器标签页仍可能运行原有 1.5 秒轮询，因此必须增加服务器端保护。

建议限流规则：

| 维度 | 建议阈值 |
| --- | ---: |
| `userId + generationId` | 12 次/分钟 |
| `IP + generationId` | 12 次/分钟 |
| 单 IP 全局 | 120 次/分钟 |

实现要求：

1. 已登录用户优先使用 `userId`，匿名用户使用 IP。
2. generationId 与 IP 在作为限流键前应哈希。
3. 超限时返回 HTTP `429`。
4. 返回 `Retry-After: 10`。
5. 可采用 Cloudflare Rate Limiting binding，并按需要叠加 Zone WAF Rate Limiting。
6. 限流应在 D1 查询及业务处理之前执行。

### 4.3 配置单次 CPU 熔断

当前 `wrangler.jsonc` 未配置自定义 CPU 上限。

建议生产环境先设置：

```jsonc
{
  "limits": {
    "cpu_ms": 10000
  }
}
```

当前 P999 约为 5 秒，10 秒能够保留一定正常业务余量，同时拦截真正失控的单次调用。运行一周并确认错误率后，可评估是否下调至 5 秒。

CPU limit 只用于防止单次请求失控，无法解决大量短请求造成的总量问题。

### 4.4 临时提高可观测性采样

当前生产环境：

```jsonc
"head_sampling_rate": 0.01
```

建议临时提高至：

```jsonc
"head_sampling_rate": 0.1
```

持续 3～7 天，完成定位后恢复。

热点接口建议记录以下结构化字段：

```text
route
responseState
durationMs
generationIdHash
settleAttempted
requestAborted
inputChars
outputChars
d1Stage
```

禁止记录：

- 原始战报正文
- API Key 或其他密钥
- 完整 generationId
- 完整 IP
- 用户原始输入

## 5. 第二阶段：消除设计层面的循环

预计工期：1～2 天。

实施状态：已于 2026-07-30 落地。

### 5.1 将 generation-ranking GET 改为纯读取

涉及文件：

- `app/api/arena/generation-ranking/handler.ts`

当前 GET handler 中存在：

```ts
await settleArenaRatingsForGeneration(generationId);
```

该行为必须从公共 GET 接口移除。

GET 接口应仅返回状态：

```text
generation 不存在 → pending
generation 已存在但尚未结算 → pending
结算完成 → ready
结算失败 → failed
```

排位结算应只在以下位置执行：

1. 战报生成完成的主链路中执行一次。
2. 独立、受保护且带幂等锁的 reconcile 任务中执行。

D1 已有 `(generation_id, queue)` 唯一约束。建议进一步增加结算租约或尝试状态，确保并发条件下只有一个执行者进入结算逻辑。

### 5.2 通过 SSE 直接下发排位结果

推荐的最终链路：

```text
AI 流结束
→ 写入 generation
→ 写入 combatants
→ 执行一次排位结算
→ SSE 发送 ranking 事件
→ SSE 发送 done
→ 客户端通过 queryClient.setQueryData 写入缓存
```

正常生成流程不再请求 `/api/arena/generation-ranking`。该 GET 只用于：

- 页面刷新后的恢复
- SSE 断线恢复
- 旧客户端兼容
- 用户手动刷新

服务端应将收尾拆分为：

```text
finalizeCritical
  - generation 记录
  - combatants 记录
  - 排位结算
  - 构造安全的 ranking DTO

发送 ranking 和 done

finalizeBackground
  - R2 索引
  - 非关键统计
  - 其他可通过 waitUntil 完成的任务
```

### 5.3 缓存终态结果

建议缓存策略：

| 状态 | 缓存策略 |
| --- | --- |
| `pending` | `Cache-Control: no-store` |
| `ready` | 按 generationId 缓存 1 小时至 1 天 |
| `failed/skipped` | 短期缓存，避免重复读取 |

项目已有 `lib/edge-cache.ts`，可用于缓存终态响应。

### 5.4 收紧 API DTO

当前 generation-ranking API 返回完整的 `ArenaEligibilitySnapshot`，其中包含：

- `userId`
- `ipAnonymized`
- `userGuidancePreview`
- `extraJson`

这些字段不应返回给客户端，也不适合进入公共 Edge Cache。

API 应显式映射为：

```ts
snapshot: {
  status: string | null;
  combatantCount: number | null;
}
```

业务层完整快照与对外 DTO 必须在 mapper 边界显式转换。

### 5.5 实际实施说明

1. `/api/arena/generation-ranking` 已改为纯读取，公共 GET 不再导入或调用排位结算函数。
2. 流式生成完成后，关键收尾依次执行 generation 写入、combatants 写入和一次排位结算；随后通过 `ranking` SSE 事件下发安全 DTO，再发送 `done`。
3. 客户端收到 `ranking` 后写入 `['arenaGenerationRanking', generationId]` Query 缓存；终态缓存命中时不再发起恢复查询。页面刷新、SSE 断线、旧客户端和 pending 状态仍使用有上限的 GET 轮询。
4. `pending` 响应使用 `Cache-Control: no-store`；正常 `ready` 使用 `s-maxage=3600`；失败或跳过终态使用 `s-maxage=60`。4xx、429 和 5xx 不缓存。
5. 公共 snapshot 仅包含 `status` 与 `combatantCount`，不再返回用户标识、匿名 IP、引导预览或 `extraJson`。
6. 本阶段未新增 D1 租约字段。当前结算继续依赖 `(generation_id, queue)` 唯一约束、事件状态和评分 CAS 更新保证幂等；未来独立 reconcile 任务必须保持受保护、显式触发且不得由公共 GET 调用。
7. R2 索引和对象清理进入 background 收尾；ranking 与 done 只等待数据库关键收尾，不等待 R2 索引完成。

## 6. 第三阶段：降低 generate-stream 单次 CPU

当前 `/api/arena/generate-stream` 约占新 Worker CPU 的 52.5%，是请求量修复后的主要优化对象。

### 6.1 客户端断开采用轻量收尾

当前客户端断开后仍可能执行：

- 战报摘要解析
- 屏蔽词和敏感词扫描
- combatants 写入
- 排位结算
- R2 索引

建议改为：

```text
客户端断开
→ 取消上游 AI 请求
→ 取消 R2 tee
→ 只写最小 aborted 记录
→ 不生成摘要
→ 不进行排位结算
→ 不创建完整 R2 索引
```

验收目标：将 `client disconnect` CPU 占比从约 12% 降至 2% 以下。

### 6.2 为敏感词检测增加布尔快速路径

当前 `quickCheck()` 会执行：

- 繁简转换
- 正则扫描
- Aho-Corasick 搜索
- 字符插入变体扫描
- 拼音转换与扫描
- 完整匹配详情构造
- 完整过滤文本构造

但生成接口在大多数场景只需要判断是否命中。

建议新增：

```ts
containsSensitiveWord(text: string): Promise<boolean>
```

要求：

1. 首次命中后立即返回。
2. 不构造 `filteredText`。
3. 不生成上下文和完整 `matchDetails`。
4. 同一文本只执行一次规范化。
5. 仅扫描未签名、用户可控制的字段。
6. 所有用户输入字段必须设置字符和字节上限。
7. 超限时直接拒绝，不能通过静默截断绕过安全检测。

同时禁止记录完整待检测文本：

```ts
// 不允许
log.warn('检测到敏感词', { text: combinedText });
```

替换为：

```ts
log.warn('检测到敏感词', {
  inputChars,
  inputHash,
  matchType,
});
```

### 6.3 减少重复序列化

重点检查并优化：

1. 同一 combatant、scenario、material 被多次 `JSON.stringify`。
2. 为计算字节数再次编码整个输入。
3. output preview 被重复执行过滤、摘要和 JSON 解析。
4. generation、combatants、写入结果等 D1 操作串行执行。

建议：

- 对输入对象只序列化一次并复用。
- 在读取请求体时累计字节数。
- 将可并行 D1 操作合并为 batch。
- 将不影响响应正确性的写入放入 `waitUntil`。
- 使用 Cloudflare DevTools CPU Profiler，以真实大小的请求定位最热函数后再做针对性优化。

### 6.4 实际实施说明

第三阶段已于 2026-07-30 落地：

1. `generate-stream` 的客户端中止路径默认启用轻量收尾。它会取消上游 reader，并通过 `AbortSignal` 取消进行中的 R2 PUT；随后只写一条最小 `aborted` generation 记录，不再等待 usage、finish reason、摘要、赛季规则、输出安全扫描、combatants、排位结算或 R2 索引。
2. `ARENA_ABORT_FAST_PATH=false` 可临时恢复原完整中止收尾；未配置或其他值均视为启用。
3. 敏感词过滤器新增 `containsSensitiveWord()` 布尔快速路径。它与完整扫描共享正则、Aho-Corasick、插入字符变体和拼音规则，但首次命中立即返回，不生成过滤文本、上下文或匹配详情。arena 的输入与输出布尔判断均使用该路径。
4. 敏感词拒绝日志不再记录原始输入，只记录字符数、SHA-256 和布尔快速路径类型。
5. `generate-stream` 不设置应用层请求字节数、引导文本、叙事历史或序列化字段硬上限，也不再静默截断用户内容。无效 JSON 或不可序列化值仍返回 HTTP 400；可接受的客观大小仍受 Cloudflare、Next.js 运行时及上游 AI 提供商约束。
6. generation 输入统计复用一次生成的 `inputJson`；安全扫描和预览通过 `WeakMap` 按实际对象惰性缓存 `JSON.stringify` 结果，避免重复序列化，并避免规范化过滤或重排后按数组索引取错内容。
7. 本阶段没有将关键 D1 写入改成 batch。generation、combatants 与排位之间存在顺序和可恢复性要求，待 CPU Profile 证明其为剩余热点后再单独设计事务边界。
8. “CPU 降低 30%”“client disconnect CPU 占比低于 2%”属于部署后指标，必须在 Cloudflare 生产观测至少 24 小时后验收，单元测试和本地构建不能替代该数据。

## 7. 测试方案

### 7.1 前端轮询测试

需要覆盖：

1. `isGenerating=true` 时 generation-ranking 请求数为 0。
2. 生成结束后立即请求一次。
3. pending 按 2、5、10、20 秒退避。
4. 单 generation 最多请求 6～8 次。
5. 超过 60 秒后停止。
6. 页面隐藏时不轮询。
7. 窗口重新获得焦点时不自动制造额外请求。
8. generationId 变化时取消旧请求。
9. 组件卸载时触发 AbortSignal。

### 7.2 API 测试

需要覆盖：

1. generation-ranking GET 永远不会调用 `settleArenaRatingsForGeneration`。
2. pending 响应不缓存。
3. ready/failed 终态响应可缓存。
4. API 不返回 `userId`、IP、预览或 `extraJson`。
5. 限流正确返回 `429` 与 `Retry-After`。
6. 100 个并发查询不会触发重复结算。
7. generationId 缺失或无效时快速返回。

### 7.3 流式生成测试

需要覆盖：

1. 客户端主动断开后取消上游请求。
2. aborted 路径不执行摘要。
3. aborted 路径不执行排位结算。
4. aborted 路径不创建完整 R2 索引。
5. 正常完成时先完成关键写入与结算，再发送 ranking/done。
6. 过大输入在进入敏感词扫描和 AI 请求前被拒绝。
7. 快速敏感词检测与现有安全规则结果一致。

### 7.4 性能测试

建议基准场景：

- 10KB、50KB、200KB 用户输入
- 2 人、10 人和最大人数战报
- 含/不含情景、素材、历史记录
- 正常完成、用户中止、上游中断
- 100 个客户端同时查询同一 generationId

记录指标：

```text
route
requests
cpuTimeMs
wallTimeMs
p50
p90
p99
p999
d1RowsRead
d1RowsWritten
abortOutcome
```

## 8. 发布与回滚

### 8.1 发布顺序

1. 部署服务器限流、纯读取兼容和结构化日志。
2. 部署新版前端有界轮询。
3. 启用 SSE ranking 事件。
4. 启用 aborted 轻量收尾。
5. 优化敏感词扫描和 D1 查询。
6. 每个阶段至少观察 24 小时。

### 8.2 功能开关

建议增加独立开关：

```text
ARENA_RANKING_READ_ONLY
ARENA_RANKING_SSE_RESULT
ARENA_ABORT_FAST_PATH
ARENA_RANKING_RATE_LIMIT
```

各项应可独立关闭，避免只能整体回滚 Worker。

### 8.3 回滚条件

出现以下任一情况应暂停扩大流量或回滚：

- 正常排位结果缺失率超过 1%。
- SSE 完成事件错误率明显上升。
- generate-stream 中断率上升超过 2 个百分点。
- D1 写入冲突或重复结算增加。
- CPU P99 或异常 outcome 不降反升。

## 9. 验收指标

第一阶段验收：

- 流式生成期间 generation-ranking 请求为 0。
- generation-ranking 调用量降低至少 80%。
- Worker 总调用量降低至少 40%。
- 无新增显著的 429 用户投诉。

第二阶段验收：

- generation-ranking GET 不再包含任何写操作。
- 正常 SSE 流程不需要额外 GET。
- 单 generation 排位查询 P95 ≤ 2 次。
- API 响应中不存在内部快照敏感字段。

第三阶段验收：

- client disconnect CPU 占比低于 2%。
- generate-stream CPU 至少降低 30%。
- 账号 CPU 使用量控制在 3M CPU ms/天以内。
- 稳态目标为接近或低于 1M CPU ms/天。

## 10. 不建议采用的单独措施

以下措施不能单独解决问题：

1. 只设置 CPU limit：无法解决大量短请求。
2. 只增加 Edge Cache：pending 状态不可长期缓存，且缓存查找本身仍可能调用 Worker。
3. 只使用客户端节流：旧客户端和机器人不会立即更新。
4. 只使用 WAF IP 限流：共享出口 IP 可能误伤正常用户。
5. 单纯提高 Workers 套餐或额度：只能掩盖请求放大，不能消除异常。

## 11. 预期效果

预期第一、二阶段可将 Worker 调用量降低约 40%～60%。

第三阶段如果 CPU profiling 证实敏感词扫描、重复序列化和中断收尾是主要热点，总 CPU 有机会降低 60%～80%。

是否能稳定降低到每账期 `30M CPU ms` 以内，必须以优化后每次生成的实际 CPU 为准，不能仅依据请求数推算。
