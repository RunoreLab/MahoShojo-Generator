# 消息系统设计规格

更新时间：2026-04-07 17:00:19

## 1. 目标

本设计用于落地站内消息系统首版：

- 支持全站通知，例如上游故障、维护、活动、临时运营提醒、Bug/问题处理进展。
- 支持定向通知，例如数据卡审核未通过、数据卡封禁、账号封禁、获得徽章、公开卡上热门/被推荐。
- 替换顶部栏“消息功能敬请期待”占位，提供真实消息入口、未读数和独立 `/messages` 页面。
- 保持低 D1 Rows Read：首版采用页面进入/可见性恢复时低频拉取，不做 SSE、WebSocket、Web Push。
- 为 `feat/admin` 后台预留发送和管理边界，但本分支不开发后台 UI。

## 2. 非目标

- 不改造现有 Git 仓库内更新公告机制。
- 不把 `public/announcements.json` 纳入消息系统未读数或 `/messages` 主列表。
- 不开发管理员后台页面。
- 不开发用户私信、会话、投诉系统。
- 不开发实时推送、离线推送或移动端原生推送。
- 不把通知表作为审核/封禁/投诉的完整审计账本。

## 3. 术语和边界

### 更新公告

现有 `public/announcements.json` 与 `AnnouncementTicker` 保持原定位：版本更新、功能说明、文档导览等随代码发布的公告。

更新公告不进入本消息系统：

- 不计入顶部栏未读。
- 不进入 `/messages` 主列表。
- 不通过新增消息 API 读取。

如未来希望在 `/messages` 页面展示更新公告，也只能作为独立区块，不进入消息未读口径。

### 全站通知

全站通知是新消息系统的一部分，独立于 Git 公告。适合：

- 上游故障、模型供应商异常。
- 临时维护、服务降级、预计恢复时间。
- 活动、征集、运营提醒。
- Bug/问题处理进展、已知问题说明。
- 规则或政策提示。

全站通知不做 fan-out：一条全站通知只在 `site_messages` 中存一行。

### 定向通知

定向通知面向单个用户，每条通知在 `user_messages` 中存一行。适合：

- 数据卡审核未通过与原因。
- 数据卡封禁与原因。
- 账号封禁与原因或说明。
- 获得徽章。
- 公开卡上热门或被推荐。

投诉相关模板首版不实现，因为投诉系统尚未落地。

## 4. 读取与已读模型

### 全站通知已读模型

全站通知采用“单记录 + 用户游标”：

- `site_messages` 保存通知正文和元信息。
- `user_message_state.last_read_site_message_id` 保存用户已读到的全站通知最大 ID。
- 未读全站通知定义为：有效期内且 `site_messages.id > last_read_site_message_id`。

这会牺牲“单独标记某一条全站通知已读、保留前后未读”的能力，但能避免 `user_id x site_message_id` 明细表导致的存储与写入放大。

### 定向通知已读模型

定向通知读状态内嵌在 `user_messages`：

- `read_at`：已读时间。
- `archived_at`：归档/移出 inbox 时间。
- `expires_at`：时效性截止时间。

未读定向通知定义为：当前用户、未归档、未过期、`read_at IS NULL`。

## 5. 数据模型

SQL 层使用 `snake_case`，TypeScript DTO 和组件状态使用 `camelCase`，跨层转换集中在 mapper / repository 边界。

### site_messages

```sql
CREATE TABLE IF NOT EXISTS site_messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  message_type TEXT NOT NULL,
  template_key TEXT NOT NULL,
  payload_json TEXT NOT NULL DEFAULT '{}',
  title_text TEXT,
  body_text TEXT,
  action_url TEXT,
  priority TEXT NOT NULL DEFAULT 'normal',
  starts_at TEXT,
  expires_at TEXT,
  created_by_user_id INTEGER,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (created_by_user_id) REFERENCES users(id) ON DELETE SET NULL
);

CREATE INDEX IF NOT EXISTS idx_site_messages_active_id
  ON site_messages(id, starts_at, expires_at);

CREATE INDEX IF NOT EXISTS idx_site_messages_created_at
  ON site_messages(created_at);
```

字段说明：

- `message_type`：全站通知类型，例如 `service`、`maintenance`、`activity`、`policy`、`issue`、`generic`。
- `template_key`：模板键，例如 `site.issue.update`。
- `payload_json`：轻量模板载荷，默认 `{}`。
- `title_text/body_text`：手工文案或模板兜底，不承载版本更新公告。
- `action_url`：可选跳转链接。
- `priority`：`low`、`normal`、`high`。
- `starts_at/expires_at`：可见窗口。

### user_messages

```sql
CREATE TABLE IF NOT EXISTS user_messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  recipient_user_id INTEGER NOT NULL,
  actor_user_id INTEGER,
  channel TEXT NOT NULL DEFAULT 'system',
  message_type TEXT NOT NULL,
  template_key TEXT NOT NULL,
  payload_json TEXT NOT NULL DEFAULT '{}',
  title_text TEXT,
  body_text TEXT,
  action_url TEXT,
  source_entity_type TEXT,
  source_entity_id TEXT,
  priority TEXT NOT NULL DEFAULT 'normal',
  read_at TEXT,
  archived_at TEXT,
  expires_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (recipient_user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (actor_user_id) REFERENCES users(id) ON DELETE SET NULL
);

CREATE INDEX IF NOT EXISTS idx_user_messages_recipient_inbox
  ON user_messages(recipient_user_id, archived_at, read_at, id DESC);

CREATE INDEX IF NOT EXISTS idx_user_messages_recipient_created_at
  ON user_messages(recipient_user_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_user_messages_recipient_source
  ON user_messages(recipient_user_id, source_entity_type, source_entity_id);

CREATE INDEX IF NOT EXISTS idx_user_messages_expires_at
  ON user_messages(expires_at);
```

字段说明：

- `recipient_user_id`：接收者。
- `actor_user_id`：触发者或管理员，系统自动通知可为空。
- `channel`：首版支持 `system`、`admin`，未来可扩 `social`，但私信会话不建议直接复用此表。
- `message_type`：业务类型，例如 `moderation`、`reputation`、`account`、`generic`。
- `template_key`：模板键，例如 `user.moderation.data_card_rejected`。
- `payload_json`：轻量模板载荷。
- `source_entity_type/source_entity_id`：来源实体，例如 `data_card`、`badge`、`user`。
- `priority`：`low`、`normal`、`high`。

可选增强：如需要更强幂等，可增加 `dedupe_key TEXT` 并建立 `recipient_user_id + dedupe_key` 唯一索引。首版可先在 service 层定义幂等规则。

### user_message_state

```sql
CREATE TABLE IF NOT EXISTS user_message_state (
  user_id INTEGER PRIMARY KEY,
  last_read_site_message_id INTEGER NOT NULL DEFAULT 0,
  last_summary_read_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

字段说明：

- `last_read_site_message_id`：已读到的全站通知最大 ID。
- `last_summary_read_at`：服务端可选摘要读取记录，首版不依赖它做限频；前端仍应做本地限频。

## 6. 通知模板

### 全站通知模板

首版定义：

- `site.service.degraded`：上游服务异常、服务降级。
- `site.maintenance.notice`：维护通知、预计恢复时间。
- `site.activity.notice`：活动、征集、运营提醒。
- `site.policy.notice`：规则补充、处理口径说明。
- `site.issue.update`：Bug、已知问题、问题处理进展。
- `site.generic.notice`：兜底全站通知。

### 定向通知模板

首版定义：

- `user.moderation.data_card_rejected`：公开数据卡未通过审核。
- `user.moderation.data_card_banned`：数据卡被封禁。
- `user.moderation.user_banned`：账号被封禁。
- `user.reputation.badge_awarded`：获得徽章。
- `user.reputation.card_trending`：公开卡上热门/被推荐。
- `user.generic.notice`：兜底定向通知。

投诉相关模板暂不实现，等投诉系统设计后再补。

### payload 规范

`payload_json` 只保存渲染通知需要的轻量信息，不保存完整数据卡、完整审核日志或投诉材料。

示例：

```json
{
  "dataCardId": "card_xxx",
  "dataCardName": "雪沫",
  "reason": "公开简介含针对性攻击描述",
  "actionLabel": "查看数据卡"
}
```

约束：

- 字符串字段需做长度上限。
- `reason` 等面向用户展示的字段应适合移动端折叠展示。
- 模板渲染失败时回退 `title_text/body_text`。
- 需要完整审计时，应在 `feat/admin` 或 moderation 域新增 action log 表，不能只依赖通知。

## 7. API 设计

全部端点运行在 Edge Runtime。

### GET /api/messages/summary

用途：顶部栏摘要。

鉴权：已登录用户。未登录返回 `unreadTotal=0` 或 401 均可；前端应兼容未登录无未读。

返回：

```ts
type MessageSummaryDto = {
  unreadTotal: number;
  siteUnread: number;
  directUnread: number;
  latest: MessagePreviewDto | null;
  fetchedAt: string;
};
```

要求：

- 只返回摘要，不返回完整列表。
- 不做实时订阅。
- 尽量使用索引条件，避免 offset。

### GET /api/messages

用途：`/messages` 主列表。

查询参数：

- `filter=all|unread|site|direct`
- `cursor`
- `limit`

返回：

```ts
type MessageListDto = {
  messages: MessagePreviewDto[];
  nextCursor: string | null;
};
```

统一列表项：

```ts
type MessagePreviewDto = {
  id: string;
  scope: 'site' | 'user';
  messageType: string;
  templateKey: string;
  title: string;
  body: string;
  actionUrl: string | null;
  priority: 'low' | 'normal' | 'high';
  readAt: string | null;
  createdAt: string;
};
```

`id` 使用 `scope:id` 组合，例如 `site:42`、`user:981`，避免两条轨道 ID 冲突。

实现建议：

- 分别读取 `site_messages` 与 `user_messages` 的少量候选行。
- service 层映射、合并、排序。
- 首版不写复杂 UNION；未来量级上来再优化。

### POST /api/messages/read

用途：批量标记定向通知已读。

请求：

```json
{
  "ids": ["user:123", "user:124"]
}
```

只操作 `user_messages`，忽略或拒绝 `site:*`。

### POST /api/messages/site/read

用途：推进当前用户全站通知已读游标。

请求：

```json
{
  "lastReadSiteMessageId": 42
}
```

实现必须只允许游标向前推进，不允许降低 `last_read_site_message_id`。

## 8. 前端设计

### 顶部栏

将 `TopBarMessagePlaceholder` 替换为真实消息入口组件，例如 `TopBarMessageButton`。

行为：

- 未登录：可点击进入 `/messages`，不显示未读数。
- 已登录：进入含 TopBar 页面时读取一次 `/api/messages/summary`。
- 浏览器标签从隐藏恢复可见时，如果超过本地限频窗口，再读取一次摘要。
- 未读数字封顶为 `99+`。
- 摘要请求失败时，按钮仍可进入 `/messages`，不打断页面。

本地限频建议：

- 内存缓存 + `sessionStorage` 缓存摘要。
- 默认 60-120 秒内不重复请求。
- 用户在 `/messages` 完成标记已读后通过自定义事件刷新顶部栏摘要。

### /messages 页面

`/messages` 页面需要作为正式消息中心设计，不做临时列表。

桌面端布局建议：

- 最大宽度使用 `max-w-screen-xl` 或类似宽度，充分利用横向空间。
- 顶部为标题、说明、未读统计、全部已读按钮。
- 主体可采用双栏：左侧筛选与说明，右侧消息列表。
- 列表项展示类型、标题、正文摘要、时间、优先级角标、操作按钮。

移动端布局建议：

- 单列布局。
- 筛选 Tabs 横向滚动或压缩成分段控件。
- 消息卡片正文默认 2-3 行截断，详情通过展开或跳转链接处理。
- “全部已读”放在标题区域下方，避免挤压顶部栏。

用户态：

- 未登录：可浏览全站通知，但不显示未读概念；展示登录提示。
- 已登录：显示全站通知 + 定向通知聚合列表。

空态：

- 全部为空：提示暂无消息。
- 未读为空：提示没有未读消息。
- 全站通知为空：提示暂无全站通知。
- 定向通知为空：提示暂无与你相关的通知。

### 导航入口

`/messages` 页面只通过顶部消息图标进入，不新增主导航下拉项。

## 9. 生命周期与清理

建议首版保留策略：

- 未读定向通知不自动删除。
- 已读且已归档定向通知保留 90 天后可清理。
- 过期 `site_messages` 不参与未读和列表。
- 未来可补清理脚本，并由 `feat/admin` 或 cron 调用。

可选后续增强：

- 将清理前的通知批量序列化为 JSONL。
- 写入 Cloudflare R2。
- D1 中只保留活跃通知和必要索引数据。

## 10. feat/admin 对接要求

本分支不开发管理员后台，但要预留 service 接口和文档，供 `feat/admin` 后续接入：

- 全站通知发布、撤回、延期、过期管理。
- 管理员定向发消息。
- 审核处理页可选择是否发送 `user.moderation.data_card_rejected`。
- 封禁处理页可选择是否发送 `user.moderation.data_card_banned` 或 `user.moderation.user_banned`。
- 通知发送必须是可选动作，不能成为封禁/审核状态变更的强制副作用。
- 如果管理员未勾选“发送通知”，状态变更应照常完成且不写入 `user_messages`。
- 审核/封禁/未来投诉处理若需要完整追溯，应新增独立 action log 表；通知只负责用户沟通摘要。

## 11. 测试策略

应覆盖：

- mapper：snake_case 行到 camelCase DTO 的转换。
- 模板渲染：已知模板、未知模板兜底、payload 字段缺失。
- repository：未读数、列表分页、全站游标推进、定向消息已读。
- API：未登录、已登录、非法 ID、越权标记已读、游标只前进不后退。
- 顶部栏：未登录入口、已登录未读数、摘要失败降级。
- `/messages`：筛选、空态、响应式结构的 SSR/静态渲染回归。

测试使用 Bun 测试体系，不引入其他测试框架。

## 12. 风险与取舍

- 全站通知游标模型不支持逐条任意已读，这是为节约 D1 存储和写入做出的明确取舍。
- `/messages` 首版 service 层合并两条消息流，不用复杂 SQL UNION，短期更易维护；未来如果消息量大，需要重新做分页优化。
- 当前仓库没有稳定持久化“审核未通过原因 / 封禁原因”的字段。首版可将原因写入通知 payload，但这不能替代管理审计。
- 低频拉取不保证强即时性，符合当前“消息通知暂时不需要太强即时性”的产品判断。
