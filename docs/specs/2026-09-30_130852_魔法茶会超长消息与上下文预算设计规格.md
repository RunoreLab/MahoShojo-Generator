# 魔法茶会超长消息与上下文预算设计规格

- 状态：已实施
- 编写时间：2026-09-30
- 适用模块：`apps/web` 魔法茶会（客户端 `lib/magic-tea-party/*` + Next.js Route Handlers `app/api/magic-tea-party/*`）
- 相关既有文档：`docs/specs/2026-07-30_003817_Workers_CPU异常修复与降耗方案.md`（CPU 与请求成本口径）

## 1. 背景与问题

用户反馈：游玩魔法茶会时因「单条消息内容超过 8000 字，请先精简」被完全卡住。

调查确认这不是「一个偏小的数字」，而是一个**把软性资源守卫实现成硬性请求墙**的设计缺陷：

1. **约束被复制 6 份且无共享定义。** `MAX_MESSAGE_CHARS = 8_000` 分散在 4 个服务端 handler 与客户端 2 处闭包中，无常量模块、无配置项。
2. **服务端在长度闸门处直接 400 拒绝**，不做任何降级。
3. **客户端主路径不做单条裁剪。** `buildHistoryForRequest`（覆盖发送/继续生成/生成选项/重新生成）只调用 `trimMagicTeaPartyHistory`，而后者**只整条丢弃消息，从不裁剪单条**。因此一条超长消息能完整穿过 token 预算裁剪，然后撞上 400。
4. **错误不可诊断。** 报错文本不含消息 id/序号，用户无法知道是哪一条。
5. **形成死锁。** 报错后 UI 只提供「重新生成」和「删除」；两者都会用同一段历史再次撞墙，且没有「编辑」或「精简」出口。唯一的破坏性出路是删除有价值的剧情内容。
6. **原有守卫没有守住它想守的东西。** `MessageSchema` 使用 `.passthrough()`，8000 检查只覆盖 `content` 字段，额外字段不受任何约束；同时 `messages` 数组上限 200 条却**没有总字符数上限**。也就是说：现状最坏请求体已达数 MB 量级，单条 8000 的限制在「防请求体过大」这件事上贡献为零。

## 2. 目标与非目标

### 目标

1. 单条消息超长不再让请求失败，改为**确定性降级**且信息可见。
2. 用**历史总字符数**替代单条字符数作为真正的硬边界。
3. 客户端与服务端共用同一套上限定义，消除客户端/服务端不对称与 6 份重复。
4. 提供非破坏性逃生口，用户无需删除内容或创建会话分支即可解除超长状态。
5. 不引入可观测的 Cloudflare 成本增量。

### 非目标

1. 不改变 `trimMagicTeaPartyHistory` 的「整条丢弃」语义（token 预算裁剪仍是它的事）。
2. 不引入 LLM 摘要去修复单条超长（摘要本身是有损、不可预测的压缩，且会额外产生一次模型调用）。
3. 不实现「把超长内容移出上下文 + 检索工具」的文档级方案（Alyx `LargeJSON` / Letta knowledge boundary），留作后续演进。
4. 不调整 `MAX_SAFETY_TEXT_CHARS = 50_000`（内容安全扫描上限），仅在文档中记录其已知盲区。

## 3. 设计

### 3.1 单一事实源

新增 `apps/web/lib/magic-tea-party/message-limits.ts`（纯函数、无服务端依赖，客户端与 4 个 handler 共用）：

| 导出 | 作用 |
| --- | --- |
| `MAGIC_TEA_PARTY_MIN_MESSAGE_CHARS` / `MAGIC_TEA_PARTY_MAX_MESSAGE_CHARS` | 单条预算区间 8,000 ~ 48,000 |
| `MAGIC_TEA_PARTY_MAX_TOTAL_CHARS` | 历史总量硬上限 800,000 |
| `resolveMagicTeaPartyMessageCharLimit(contextWindowTokens)` | 按上下文窗口分档解析单条预算 |
| `clipMagicTeaPartyMessageContent(content, limit)` | 单条中间截断 |
| `applyMagicTeaPartyMessageLimits(messages, limit)` | 对整段历史应用截断并统计 |
| `formatMagicTeaPartyTotalOverflowMessage(totalChars)` / `isMagicTeaPartyTotalOverflow(n)` | 总量守卫与提示文案 |

### 3.2 单条预算按上下文窗口分档

参考 Claude Code 的可见内容分档思路（8K→5,000 / 32K→15,000 / 128K→25,000 / 200K+→40,000 字符），按本项目量纲取：

| 上下文窗口 | 单条消息上限 |
| ---: | ---: |
| ≤ 8,192 | 8,000 |
| ≤ 32,768 | 16,000 |
| ≤ 65,536 | 24,000 |
| ≤ 131,072 | 32,000 |
| > 131,072 | 48,000 |

- 输入不是有限数（未配置 / 非法）时**回落到最大档**：宁可多截一点，也不把一条可能超出模型上下文的消息原样推给上游。
- 该值由客户端从现有 `resolveMagicTeaPartyTokenBudget` 的 `contextWindowTokens` 派生，并通过 `settings.contextWindowTokens`（`summarize` 为顶层同名字段）告知服务端，两者算出同一结果。

**保持向后兼容**：两个字段都是可选新增，服务端 zod schema 此前依靠 `.passthrough()` 已经放行这两个键，本次只是把它们显式声明并加上取值范围校验。旧客户端不发送时服务端回落到最大档 48,000 兜底。

### 3.3 单条降级：中间截断而非硬失败

超长消息保留**头部 70% + 显式标记 + 尾部 30%**，并为标记预留 48 字符预算，保证截断结果不超过目标长度。

选择中间截断而非只截头/只截尾的理由（来自成熟实践的收敛结论）：

- Arize 明确指出「取前 100 字等于没有」：只保留开头，模型不知道该内容「讲到哪里为止」；只保留结尾则完全丢失语境。
- Claude Code 的溢出兜底是「middle-truncates the transcript keeping 30% head and 30% tail」；OpenClaw 对 bootstrap 文件超预算时用 75% 头 / 25% 尾 + 标记。

标记文本为 `…（本条消息过长，已省略中段 N 字）…`，**刻意暴露给模型**，使其知道这是人为裁剪而非原文缺失（对应 Pi 的 continuation nudge 思路）。

> 备注：存在一条相反证据（EngineersOfAI 主张「Never truncate mid-message」）。本设计选择生产实践（Claude Code / OpenClaw）并用显式标记缓解，因为「整条丢弃」在单条超长时等价于**丢失该轮全部上下文**，代价比中段截断更大。

### 3.4 真正的硬边界：历史总字符数

- `MAGIC_TEA_PARTY_MAX_TOTAL_CHARS = 800_000`，按**原始长度**统计（在截断之前计算），因此截断不会帮助绕过该检查。
- 超限时返回 HTTP `413`，并带 `{ error, meta: { totalChars, limit } }`。
- 客户端 `runGenerateStream` 在发起请求前做同样的检查，命中则不发请求，直接产出错误提示。
- 选 800,000 而非更低：手动摘要路径历史上会发送未裁剪的全量历史（200 × 8,000 = 1,600,000），需要先修好客户端再收紧，否则会造成回归。该值已由客户端 token 预算裁剪兜住，正常会话远低于此。

### 3.5 客户端对齐

1. `buildHistoryForRequest` 在 token 预算裁剪之后追加单条截断，返回值新增 `clipStats`；有截断时通过 `emitNotices` 发一条 `message_content_clipped` 警告。
2. `normalizeFallbackHistory`（选项/摘要补生成）与自动摘要路径改用同一 clip 实现，替换原先的 `slice(0, 8000)`。
3. 手动「生成摘要」原先发送**完全未裁剪**的 `buildMagicTeaPartyHistory(...)`，本次补上 token 预算裁剪 + 单条截断；`summaryMeta.from/toMessageId` 仍按**完整**历史计算，保持自动摘要间隔语义不变。
4. 新增 `compactMessageContent`：就地把一条超长消息压到当前预算内并持久化。这是**非破坏性逃生口**——不必删除，也不必走「编辑并分支」。
5. 输入框增加 `本条 N / M 字` 计数器，超限变红并说明会自动省略中段。
6. 超长消息的操作行出现「精简长消息」按钮（用户消息与助手消息都有）。

### 3.6 错误呈现

原实现在 `inferErrorCategoryForError` / `inferEncyclopediaSlugForError` 中用 `status === 400` 兜底映射到「请求参数无效 / 校验失败」与数据卡百科，导致长度类错误被导向完全无关的「数据卡导入/解析/格式校验/签名」页面。

修正：

- 新增 `CONTEXT_LIMIT_MESSAGE_HINTS` 与 `ErrorCategoryId` 的 `context_limit`。
- 在 `inferErrorCategoryForError` 中让上下文超限提示优先于 `status === 400` 兜底分支（消息驱动判断必须排在 blanket 状态码分支之前，否则对 400 永远不可达）。
- 在 `inferEncyclopediaSlugForError` 中同样前置，并新增 `413 → magic-tea-party-context-limits`。
- 新增百科条目 `magic-tea-party-context-limits`。

## 4. 成本影响评估

| 维度 | 结论 |
| --- | --- |
| 模型 token 成本 | **由用户承担**。魔法茶会是纯 BYOK（`魔法茶会已禁用 system，请使用自备 Key`），放宽限制不增加平台模型支出。 |
| Cloudflare 请求数 | 不变。放宽限制不新增请求。 |
| Cloudflare CPU | Workers 只对 requests + CPU ms 计费，**带宽/出流量不收费**；CPU time 不含 I/O 等待，长时 AI 流式请求不计 CPU。增量仅为「多解析几 MB JSON + 多拼一段 prompt 字符串 + 一次已被 50,000 字封顶的正则扫描」，相对历史均值 78.4ms/次属噪声。 |
| 请求体上限 | 100MB 属**账号套餐**层级（Free/Pro），不是 Worker `limits` 旋钮。800,000 字符最坏约 1.6MB（UTF-8 CJK），远低于该上限。 |
| 真实成本转移方向 | 用户侧输入 token 账单上升、provider 上下文溢出（更难的报错）、长上下文中段信息丢失（Liu et al. 2023：关键信息位于中段时检索准确率约 95% → 60%）。已通过百科文档显式告知。 |

结论：符合「不明显增加 Cloudflare 付费资源消耗」的前提。同时保留 `cpu_ms: 10000` 熔断与 `MAX_SAFETY_TEXT_CHARS = 50_000` 扫描封顶不变。

服务端仅在发生截断时打一条结构化 info 日志（`sessionId` / `limit` / `clippedCount` / `omittedChars`），**不记录任何正文**，与既有 CPU 降耗方案的可观测性口径一致。

## 5. 兼容性

| 变更 | 兼容性 |
| --- | --- |
| 单条超长：400 → 降级放行 | 纯放宽，无客户端依赖 |
| 历史总量超限：新增 413 | 仅在原本就会失败的超大请求上出现；文案命中新的上下文超限提示词 |
| `settings.contextWindowTokens` / `responseReserveTokens` | 可选新增，`zod` 显式化 + 取值范围校验；旧客户端不发送时回落到最大档 |
| `summarize` 顶层 `contextWindowTokens` | 可选新增 |
| 新增百科 slug | 纯新增，不影响既有条目 |

## 6. 验证

- `apps/web/tests/magic-tea-party-message-limits.test.ts`：分档解析、中间截断的边界（截断后不超限、小预算不 panic、非法 limit 回落）、总量统计按原始长度、入参不可变、总量守卫边界（等于上限不拒绝）。
- `apps/web/tests/magic-tea-party-message-limits-handler.test.ts`：4 个 handler 均放行 50,000 字单条消息（断言停在 provider 校验而非长度闸门）、正常长度行为不变、总量超限返回 413 与结构化 meta、总量恰等于上限时放行。
- `apps/web/tests/error-help.test.ts`：413 与上下文超限文案路由到新条目、普通 400 仍为 `validation` 且仍指向数据卡百科（防回归）。
- `apps/web/tests/exited-api-contract.test.ts`：malformed-body 的既有 wire 不变。

## 7. 已知限制与后续项

1. **中段截断不可逆。** 关键设定若正好位于长消息中段会真正丢失。应引导用户把设定写进角色卡 / 情景卡 / 世界书（已在百科说明）。
2. **内容安全扫描存在相对盲区。** `MAX_SAFETY_TEXT_CHARS = 50_000` 作用于含完整历史的 `prompt`，历史越长，靠后部分参与敏感词扫描的比例越低。本次未改该常量，建议后续独立评估。
3. **`useCallback` 依赖面扩大。** `buildHistoryForRequest` 新增 `emitNotices` 依赖，会略微增加其重建频率；若后续观察到相关抖动，可将提示上移到调用方。
4. **更彻底的方案未实施。** 「超长内容移出上下文 + 预览 + 稳定 ID + 检索工具」是更优解，但需要新增存储与工具协议，成本与复杂度显著更高。
