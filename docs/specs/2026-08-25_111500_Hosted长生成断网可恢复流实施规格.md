## 1. 规范语言与目的

本文中的“必须 / MUST”“不得 / MUST NOT”“应 / SHOULD”“可以 / MAY”具有规范性，其解释遵循 RFC 2119 与 RFC 8174。

本文同时处理两个已经由生产证据支持、且在当前平台重整阶段可以共用同一架构解法的问题：

1. **Hosted AI execution placement**：高 CPU、高请求量、大 payload、安全扫描、流式解析与复杂 finalization 的 AI 执行不应因为历史 Next Route Handler 所在位置而长期占用 Cloudflare Workers CPU；在能够保持 shared service、contract parity 与灾备 adapter 的前提下，应以 `apps/api` / Hono 为主执行面，`apps/web` / Next/OpenNext 为受控 Cloudflare DR 执行面。
2. **长生成连接恢复**：AI 生成仍健康运行时，浏览器到 Hosted runtime 的下游连接可能因移动网络抖动、切网、后台冻结或短时断网而中断。当前 Arena 流把 `req.signal` 直接传给 AI 上游，导致 subscriber 断开会取消 Provider generation，无法恢复同一次逻辑生成。

Cloudflare Workers 当前 Standard 计费按请求与 CPU time 计算，HTTP wall-clock duration 本身不收费；等待外部网络响应的时间不计入 CPU。因此 **“长流”本身不是迁入 Hono 的充分条件**。route placement 必须看真实 CPU/request telemetry、payload/安全扫描/序列化成本、流式处理、可靠性与跨 runtime 编排收益，而不是只看模型响应耗时。

本文的恢复核心仍是把两个生命周期解耦：

```text
Generation producer
  start -> running -> completed / failed / cancelled

Subscriber connection
  connect -> disconnect -> reconnect -> ... -> terminal observed
```

**Subscriber disconnect MUST NOT 等价于 Generation cancel。**

首版完成后，短时断网必须优先恢复同一个 generation；不得以“重新 POST 一次生成”模拟恢复。

同时，Phase 2.5B 的 `exitedRouteIds` 是一次结构退出裁决，不是永久 runtime 禁令。任何退出 capability 重新进入 Hono，都必须重新证明 **运行成本 / 可靠性 / 平台解耦收益**，并走 shared-service + 双 adapter + replay/side-effect gate；不得恢复 legacy handler 动态导入。

## 2. 适用范围与非目标

### 2.1 v1 范围

v1 的**阻断性首发纵切** MUST 完成 Arena Hosted generation family 中最主要的热点与恢复链：

1. `arena/generate-stream` 的 generation lifecycle 与请求连接 lifecycle 解耦；
2. 稳定 `generationRequestId` 与幂等 reservation；
3. Hono-owned generation producer；
4. Redis 状态快照 + bounded replay stream；
5. 带 `id:` 的 SSE 事件；
6. fetch-SSE 自动重连与断点续传；
7. 显式 cancel；
8. D1/R2 terminal result fallback；
9. 排位、历史、R2、审计等副作用的单次 finalization；
10. `arena/generate-stream` 基于 shared business core 正式 re-enter Hono primary；
11. 断网、重连、Redis 降级、producer 丢失的故障测试与 telemetry。

在上述 vertical 稳定后，Arena family SHOULD 继续收口：

- `arena/generate`；
- `generate-battle-story`；
- `arena/session/generate-next`。

目标是把 Arena 的真实 AI execution / SSE orchestration 从 Cloudflare Worker 主路径迁到 Hono，而不是让 `session/generate-next` 长期作为 Cloudflare SSE 解析与再编码中间层。`me/battle-reports/[generationId]/regenerate` 当前不执行新的 Provider generation，默认继续由 Next 承载，不因名称或目录归组而机械迁移。

Arena 之后，`generate-magical-girl-details*` 与 `generate-sublimation*` SHOULD 作为下一批 Hosted AI execution re-entry candidate；Magic Tea Party / Tavern family MAY 按 telemetry 决定是否在 Phase 2.5 内迁入，或延后到平台退出后。共享抽象 SHOULD 为其他 Hosted 长生成复用，但 MUST NOT 为追求 Hono 覆盖率把全部 exited route 一次性迁回。

### 2.2 非目标

v1 MUST NOT 承诺：

- Hono 容器/整机死亡后无缝续接同一个上游模型 TCP/HTTP 请求；
- Redis 丢失后恢复尚未完成的所有逐字 delta；
- 跨运行时自动重放非幂等 AI generation；
- WebSocket 替代 SSE；
- Durable Object / Cloudflare Queues / Workflows 作为本问题的强制依赖；
- 原生 `EventSource` 取代当前需要 Authorization / activity headers 的 fetch-SSE 客户端；
- 将 Redis 提升为战报、排位或结算事实的权威存储；
- 把全部 14 条 Phase 2.5B exited capability 机械迁回 Hono；
- 因为 Cloudflare 等待模型时间较长就假定其一定产生等量 CPU 计费；
- 为 Hosted generation 默认启用 Hono / Cloudflare active-active 随机双写或透明重放。

Hono 进程/整机丢失属于 Hosted DR 的更高一级故障域。发生此类故障时，v1 的正确行为是对账并恢复已持久化终态；若无法证明原 generation 是否仍在运行，MUST 返回 `producer_lost` / `unknown` 一类明确状态，MUST NOT 自动发起第二次模型生成。

## 3. 既有文档关系

### 3.1 Hosted DR ADR

本文具体落实 `ADR-hosted-runtime-resilience-cloudflare-dr` 已接受的原则：

- generation/stream/settlement 不得做不安全透明 replay；
- 恢复应围绕稳定 `generationRequestId`、attempt、状态查询与最终结果；
- D1 保存业务事实，R2 保存最终大对象，Redis 只承担可重建的短期状态/stream；
- `mid-flight disconnect` 必须验证不会产生第二次 Provider/generation。

因此本文 **不新建顶层 ADR**。

### 3.2 Arena 多人 Hono + Redis

本文复用 Arena multiplayer 已接受的实现模式：

- Hono + Redis 首发；
- stable generation identity；
- snapshot + bounded replay；
- delta 合并后写入；
- Redis 不作为最终业务 authority；
- Hono process loss 时先对账，不自动重发 AI。

多人 Room runtime 的 WebSocket、presence、Proposal 等不属于本文范围。

### 3.3 2026-05 Cloudflare Queues 异步化设计

`docs/specs/2026-05-22_144846_Cloudflare_Queues_AI生成异步化设计.md` 保留为历史/未来后台异步执行方案，不被删除。

针对当前“客户端短时断网导致战报半途截断”的近期问题，v1 SHOULD 优先复用已经存在的 Hono + Redis + SSE + R2 能力，而不是先引入 Queue consumer。若未来需要“HTTP 请求结束后跨进程可靠排队、延时执行、长时间任务中心”，可重新评估 Queue/Workflows。

### 3.4 Phase 2.5B capability exit

Phase 2.5B 将 14 条高风险 capability 从旧 Hono manifest 安全退出，是为了删除 `legacy-next` 动态导入、避免在 shared service/replay contract 尚未成立时维持伪双运行时。该裁决继续有效的部分是：

- app-to-app / Hono -> Next handler 动态导入仍然禁止；
- capability re-entry 仍必须有明确 runtime benefit；
- non-idempotent generation / settlement 不得盲目跨 runtime replay；
- Next/Cloudflare DR adapter 与 Hono adapter 必须共享同一 business core。

本文新增的是**重新评估后的 placement 证据与顺序**，不是恢复 2.5B 以前的 legacy 架构。

## 4. 核心不变量

### RESUME-INV-001 Generation 与连接解耦

Hosted generation MUST 由服务器拥有独立的 `AbortController` / cancellation token。

`req.signal`、下游 `ReadableStream.cancel()`、socket close 或 subscriber abort MUST 只终止当前 subscriber，不得直接取消 AI provider request。

### RESUME-INV-002 只有显式动作可取消 generation

以下事件 MAY 取消 generation：

- 用户显式点击“停止生成”；
- 服务端 total/idle/resource budget 达到硬限制；
- 管理/安全策略明确终止；
- provider 明确失败且 retry policy 已耗尽。

网络离线、页面刷新、标签页后台冻结、subscriber EOF MUST NOT 自动取消 generation。

### RESUME-INV-003 稳定 generationRequestId

更新后的客户端 MUST 在首次网络请求之前生成稳定、不可预测的 `generationRequestId`，推荐 UUIDv4/UUIDv7 同等级随机标识。

该 ID 在同一次逻辑生成的所有 create/reconnect/status/cancel 请求中保持不变。

服务器 MUST 对 `(actor, generationRequestId)` 建立幂等 reservation，并保存请求 payload hash / semantic hash。相同 ID + 相同请求 MUST 复用原 generation；相同 ID + 不同请求 MUST 返回冲突，不得启动第二个 generation。

`generationRequestId` MAY 与最终 `generationId` 采用同一 UUID，但实现必须保留“请求幂等身份”和“业务 generation identity”两个语义概念，避免未来迁移时耦合。

### RESUME-INV-004 不以 generationId 作为凭证

`generationId` / `generationRequestId` MUST NOT 被视为 bearer secret。

resume/status/cancel 必须重新验证当前 auth user 或现有 activity identity 与 generation owner 的关系。PvP 场景继续遵守既有 match membership / authority contract。

### RESUME-INV-005 副作用最多一次

reconnect、snapshot、replay、多个 subscriber MUST NOT 重复触发：

- Arena rating settle；
- narrative/current-state/history write；
- battle report final record；
- R2 final object index；
- 其他一次性统计或结算事实。

终态提交必须以 `generationId` / business key 具备幂等保护，并保持既有 D1 unique/CAS/settlement 约束。

### RESUME-INV-006 Redis 非权威

Redis MAY 保存：

- running state；
- owner lease/heartbeat；
- generation request reservation；
- 当前展示 snapshot；
- bounded SSE replay events；
- subscriber/reconnect telemetry 的短期聚合。

Redis MUST NOT 成为：

- 完整战报最终 authority；
- rating/settlement authority；
- user/card/match/history 权威事实源；
- API Key / provider secret 存储。

终态事实仍落 D1；完整大输出仍落 R2/large-object 体系。

## 5. Runtime 与 route placement

### HOSTED-PLACEMENT-001 默认执行面

对于需要项目 Hosted runtime 的 AI 能力，默认目标形态为：

```text
Client
  -> stable logical API entry
      -> Hono / apps/api primary
      -> Next/OpenNext / apps/web DR adapter（仅 DR eligible capability）

             shared service / domain / contracts
```

Hono primary 与 Cloudflare DR MUST 共享同一业务核心；Cloudflare adapter 是灾备执行面，不是第二份业务实现。

对于 generation/stream/settlement 类能力，默认 MUST 使用 active-passive 语义：新请求在开始执行前选择 runtime；一旦 Provider 可能已经开始、权威写入可能已经发生，连接失败 MUST NOT 触发跨 runtime 透明重放。Cloudflare Load Balancing 或其他控制面即使支持 active-passive failover，也必须遵守这一业务 replay class。

### HOSTED-PLACEMENT-002 迁入 Hono 的证据门槛

“长时间等待模型”单独不构成迁移理由。一个 capability SHOULD 在以下一项或多项有真实证据时优先 re-enter Hono：

- Cloudflare dynamic Worker CPU 占比/CPU ms 为热点；
- 请求量高，且大部分请求会执行动态 Worker 代码；
- 存在大 payload、JSON stringify/parse、prompt composition、敏感词/安全扫描、schema repair 等明显 CPU 工作；
- 需要长流解析、SSE 重编码、snapshot/replay 或 server-owned producer；
- 需要 Redis lease/stream/state，放在 `apps/api` 可消除跨 runtime 往返；
- Hono 已有容量且迁移可降低 Cloudflare denial-of-wallet / CPU overage 风险；
- 迁移能删除“Cloudflare Worker 作为 Hono 上游流的中间解析器”一类无必要夹层。

以下情况反而支持继续留在 Next：

- Web-specific、轻量读操作或 edge-specific 能力；
- 不调用 Provider、CPU/请求量低且没有可靠性收益；
- 为迁移必须复制高权限 secret，但 DR/主路径收益不足；
- 未来明确更适合 Installed Client Direct，且当前 Hosted 使用量很低。

placement 决策 MUST 以 telemetry 持续复核，不以 `sharedRouteIds` 数量作为 KPI。

### 5.1 当前 14 条 exited capability 的重新分类

基于当前实现与既有生产证据，默认规划如下：

| family / route | 目标 placement | 时机 | 主要理由 |
| --- | --- | --- | --- |
| `arena/generate-stream` | Hono primary + Cloudflare DR | **第一优先** | 历史 Worker CPU hotspot；长流；断网恢复；Redis replay |
| `arena/generate` | Hono primary + Cloudflare DR | Arena 后续纵切 | 同一高成本 generation core |
| `generate-battle-story` | Hono primary + Cloudflare DR | Arena 后续纵切 | 完整 battle generation、复杂安全/持久化/finalize |
| `arena/session/generate-next` | Hono primary + Cloudflare DR | Arena 后续纵切 | 当前会代理、解析并重编码 Arena SSE；避免 Cloudflare CPU 中间层 |
| `me/battle-reports/[generationId]/regenerate` | **默认 Next** | 不因本轮迁移 | 当前主要读取、授权、敏感词检查与 hydrate，不启动新 Provider |
| `generate-magical-girl-details` / `-stream` | Hono primary + Cloudflare DR | Arena 后、G25E 前优先 | prompt/safety/AI stream；可复用 questionnaire generation seam |
| `generate-sublimation` / `-stream` | Hono primary + Cloudflare DR | Arena 后、G25E 前优先 | 大 DataCard/prompt、安全扫描、AI stream、finalization |
| Tea Party / Tavern `generate-stream` / `generate-choices` / `generate-updates` | telemetry-gated Hono candidate | 默认不阻塞 Phase 2.5 exit | 实际调用 AI 且 payload 较重，但 BYOK/Direct candidate 属性更强；先看负载 |

其中 Tavern alias MUST 随 Tea Party shared service 处理，不单独复制业务实现。

### RESUME-RT-001 Arena 精确 re-entry gate

`arena/generate-stream` 从 `exitedRouteIds` 移入 `sharedRouteIds` 之前 MUST 同时满足：

1. 业务 core 不由 Hono adapter 动态导入 Next handler；
2. Next 与 Hono adapter 复用同一 generation service / contract；
3. auth actor、activity identity、safety、provider resolution、signature、Arena v1 wire、D1/R2、rating/history side effect 有 contract parity 证据；
4. SSE `markdown/reasoning/meta/telemetry/ranking/error/done` 语义保持兼容；
5. 新的 disconnect/reconnect/cancel 语义有专项测试；
6. manifest/boundary/package/server/workspace/build 验证通过；
7. 独立 review 无未关闭 Critical/Important finding；
8. route cutover 可独立回滚；
9. Cloudflare DR adapter 不依赖 Hono 内部源码，且不会对未知 mid-flight generation 透明重放。

后续 family re-entry MUST 使用同等级 gate，并按其业务副作用补充 route-specific contract。

### RESUME-RT-002 与 G25D 的边界

Hosted re-entry 可以安排在 G25D 前或后，但 MUST 是独立 Goal / commit boundary，**不得混进 G25D 的 behavior-equivalent relocation diff**。

当前已有真实用户断流事件，且 Arena `generate-stream` 已有历史 CPU hotspot 证据，因此默认计划允许先完成 Arena G25R，再进入 G25D。若 G25D 在实施时已经开始且冲突面明显，则 MAY 先闭合 G25D，再恢复 G25R；不得让两个目标长期交叉成一个不可独立回滚的 run。

### RESUME-RT-003 rollout 原子性

后端 producer 解耦与前端 resume UX 不得以“半成品”公开切流。

实现 MAY 分多个 Goal 开发，但 `arena/generate-stream` production/public cutover MUST 在服务端 resume/status/cancel 与客户端 reconnect state machine 均可用后完成。

其他 AI family 可以在各自 shared-service / parity gate 完成后独立 re-enter；不得等待“所有 Hosted AI route 一次性完成”。

## 6. Generation 状态机

内部 generation control state SHOULD 至少包含：

```text
reserved -> running -> completed
                   -> failed
                   -> cancelled
                   -> producer_lost
```

说明：

- `reserved`：幂等身份已占用，但 provider 尚未开始；
- `running`：provider 已开始；
- `completed`：终态结果已完成并进入权威 finalization；
- `failed`：provider/业务失败；
- `cancelled`：显式 cancel 或硬资源预算终止；
- `producer_lost`：lease 过期且无法证明 terminal result，禁止自动重跑。

现有 `battle_report_generations.status` MAY 在 v1 继续保持现有 `completed / failed / aborted` 持久语义以避免无关 schema 扩张；内部 `cancelled` 可映射到现有 `aborted`。**普通 subscriber disconnect 不再产生 terminal `aborted`。**

## 7. Redis GenerationReplayStore

### 7.1 不暴露 raw Redis client

`apps/api` SHOULD 新增窄接口 `GenerationReplayStore`，由 Redis runtime 实现；shared/domain code MUST NOT 直接 import node-redis client。

建议能力：

```ts
interface GenerationReplayStore {
  reserve(input: ReserveGenerationInput): Promise<ReserveGenerationResult>;
  markRunning(input: MarkRunningInput): Promise<void>;
  heartbeat(input: GenerationLeaseInput): Promise<void>;
  appendEvents(input: AppendGenerationEventsInput): Promise<AppendResult>;
  writeSnapshot(input: WriteGenerationSnapshotInput): Promise<void>;
  readSnapshot(input: ReadGenerationSnapshotInput): Promise<GenerationSnapshot | null>;
  readAfter(input: ReadGenerationEventsInput): Promise<GenerationEventBatch>;
  markTerminal(input: MarkGenerationTerminalInput): Promise<void>;
  readState(input: ReadGenerationStateInput): Promise<GenerationState | null>;
}
```

### 7.2 Key 空间

实现 SHOULD 使用版本化、可批量清理的 namespace，例如：

```text
mahoshojo:gen:v1:{generationId}:state
mahoshojo:gen:v1:{generationId}:events
mahoshojo:gen:v1:req:{actorScope}:{actorHash}:{generationRequestId}
```

key MUST NOT 包含明文 API Key、Cookie、完整 IP 或完整敏感 prompt。

### 7.3 Snapshot + bounded replay

v1 MUST 同时保存：

- 当前 generation snapshot；
- 有界、有序的 event journal。

仅保存 event journal 而没有 snapshot，会在 trim/长时离线后失去可靠 bootstrap；仅保存 snapshot 又无法高效断点追加。

snapshot 至少应记录：

- generation status；
- 当前可展示 markdown；
- 当前 reasoning 展示状态（若产品允许展示）；
- last replay event id；
- provider/model 非敏感 telemetry；
- updatedAt / producer lease；
- terminal summary / final object ref（若已完成）。

snapshot 更新 SHOULD 批量化，不要求每 token 写 Redis。

### 7.4 Delta 合并

`markdown` / `reasoning` delta MUST NOT 每 token 一次 `XADD`。

实现 SHOULD 使用“时间 + 字节数”双阈值合并，默认设计区间：

- 约 50–100ms flush；或
- 约 0.5–2 KiB 累积后提前 flush。

终态/控制事件（`meta`、`telemetry`、`ranking`、`error`、`done` 等）SHOULD 立即写入。

具体默认值属于运行参数，不作为产品语义冻结；变更必须有 telemetry 支持。

### 7.5 TTL 与 trim

Redis state/events MUST 设置 TTL 与容量上限。

默认目标是覆盖“生成最长时长 + 常见移动网络短时离线 + 用户刷新恢复”窗口，而不是长期归档。建议首轮从 terminal 后 30–60 分钟量级开始，通过观测调整。

当 replay window 已不包含客户端 cursor 时，服务端 MUST NOT 静默从错误位置追加；必须：

1. 返回/发送当前 snapshot 作为 bootstrap，并声明新的 snapshot cursor；或
2. 若 generation 已 terminal 且 Redis snapshot 不可用，从 D1/R2 返回最终完整结果；或
3. 明确返回 `replay_window_lost` / degraded，不得自动重新生成。

## 8. SSE 协议

### 8.1 标准兼容

WHATWG SSE 以 `id:` / `Last-Event-ID` 定义重连游标。v1 的 fetch-SSE 客户端 SHOULD 保持该语义，即使不使用原生 `EventSource`。

每个可 replay 事件 MUST 带稳定、单调有序的 Redis stream ID：

```text
id: 1724570000000-0
event: markdown
data: {"chunk":"..."}
```

heartbeat/comment MUST NOT 推进 replay cursor。

### 8.2 Resume cursor

恢复 endpoint SHOULD 接受：

- `Last-Event-ID` header；
- 调试/兼容用途的 `after` query。

两者同时存在且不同 MUST 返回 400，避免游标歧义。

Redis `XREAD` 的“返回严格大于 caller 已见 ID 的 entries”语义 SHOULD 作为实现基础；浏览器 subscriber 是独立观察者，不得使用会把消息分摊给不同 consumer 的 consumer-group 语义。

### 8.3 事件类型

现有 Arena 事件保持兼容：

- `markdown`
- `reasoning`
- `reasoning_done`
- `meta`
- `meta_error`
- `telemetry`
- `ranking`
- `error`
- `done`

可新增：

- `snapshot`：恢复时的当前完整展示快照；客户端收到后必须 replace，而非 append；
- `resume`：可选诊断事件，描述 recovered/replayed 数量，不参与业务 finalization。

`debug` 与 keepalive MAY 不写入 replay journal。

## 9. HTTP API 契约

### 9.1 初始生成

为降低迁移风险，v1 MAY 保留现有入口：

```http
POST /api/arena/generate-stream?format=sse
```

更新后的 Web 客户端 MUST 在请求体或受控 header 中携带 `generationRequestId`。

服务器在调用 Provider **之前** MUST 完成：

1. actor / activity identity 解析；
2. request schema / safety / rate limit；
3. generation reservation；
4. payload hash 冲突检查；
5. producer ownership 建立。

只有 reservation 成功后才可以启动 provider。

### 9.2 Request lookup

新增逻辑 endpoint：

```http
GET /api/arena/generation-requests/{generationRequestId}
```

该 endpoint MUST 使用 create 相同的 actor identity 派生 generation ID，并返回 owned active state、durable
pending 或 terminal fallback。initial POST 一旦可能已经到达 runtime，客户端 MUST 只通过该 endpoint 查询后继续
resume，不得重放 create。lookup 返回的服务器最新 `lastEventId` 只供诊断，不得推进客户端尚未消费的 cursor。

### 9.3 Resume

新增逻辑 endpoint：

```http
GET /api/arena/generations/{generationId}/stream
Last-Event-ID: <cursor>
```

或等价 `?after=<cursor>`。

行为：

- owner 校验失败：401/403；
- generation running：snapshot/replay 后继续 tail；
- completed：补齐遗漏事件并发送 `done`，或返回 terminal snapshot/final result；
- failed/cancelled：发送对应 terminal 状态；
- producer_lost：明确报告，不自动生成；
- Redis replay unavailable 但 D1/R2 已 terminal：走 final fallback；
- 无法证明状态：返回 explicit unknown/degraded，不自动生成。

### 9.4 Status

新增逻辑 endpoint：

```http
GET /api/arena/generations/{generationId}
```

最小响应：

```json
{
  "generationId": "...",
  "generationRequestId": "...",
  "status": "running",
  "resumable": true,
  "lastEventId": "...",
  "updatedAt": "..."
}
```

终态可追加 final object / battle report reference，但不得泄露 provider secret。

### 9.5 Cancel

新增逻辑 endpoint：

```http
POST /api/arena/generations/{generationId}/cancel
```

cancel MUST：

- 校验 owner/authority；
- 幂等；
- 只影响对应 generation producer；
- 记录明确 cancel reason；
- 不因 subscriber disconnect 自动调用。

## 10. Producer ownership 与进程故障

### 10.1 单 producer

同一 `generationRequestId` 同一时刻 MUST 最多只有一个 active producer。

Redis reservation/lease SHOULD 使用原子 NX/CAS/Lua/transaction 等机制实现，禁止“先 GET 再 SET”的竞态窗口。

### 10.2 Redis 不可用

在 resumable route 已正式切流后，如果无法建立幂等 reservation / producer ownership，服务器 MUST 在调用 AI Provider 之前 fail closed；不得在“不知道是否已有 producer”的情况下继续创建新的 generation。

这不把 Redis 变成业务事实 authority；它只是把“无法证明单 producer”视为安全不可继续条件。

对已运行 producer，短暂 Redis 写失败 SHOULD 尽量继续生成并完成 D1/R2 finalization，同时标记 live resume degraded；恢复后可重新建立 snapshot。不得因 replay buffer 写失败自动二次调用 Provider。

### 10.3 Producer lease

running producer SHOULD 定期刷新 lease/heartbeat。

subscriber 读取到 `running` 但 lease 已过期时，不得无限等待；服务端必须先查 D1/R2 terminal evidence：

- 已完成：恢复最终结果；
- 有明确失败/取消：返回终态；
- 无证据：标记 `producer_lost` / `unknown`。

MUST NOT 自动从 prompt 重启模型。

## 11. R2 / D1 finalization

### RESUME-STORAGE-001 R2 属于 producer

当前 subscriber disconnect 路径会取消 R2 upload。v1 中 R2 final-output pipeline MUST 归 generation producer 所有，不得由 subscriber cancel 触发 abort。

### RESUME-STORAGE-002 Terminal fallback

若 Redis replay 已过期/丢失，但 generation 已成功完成，status/resume MUST 能依据现有 battle report record + R2/large-object 取回最终完整正文。

### RESUME-STORAGE-003 Partial output

v1 不要求把每个 partial delta 持久化到 D1/R2。Redis partial snapshot 属于短期恢复数据。

若 producer 自身死亡，已有 partial output MAY 用于排障/用户提示，但不得把不完整结果伪装为 completed。

### RESUME-STORAGE-004 Cross-runtime reservation 与 fencing

共享 Redis 是 active generation 的唯一 reservation、producer lease、running/finalizing lifecycle、snapshot 与
SSE replay authority；D1 不得被扩张成 job/lifecycle 表。`generationId` MUST 由 actor-scoped
`generationRequestId` 确定性派生，Redis reservation MUST 原子比较 semantic payload hash。

- Redis reservation/ownership 不可用时，create MUST 在 Provider 前 fail closed；不得以 process memory 或 D1
  占位行启动第二 Provider；
- Next/OpenNext DR adapter 在没有共享 Redis capability 时只能读取已完成的 D1/R2 terminal；其 active replay store
  MUST 显式 unavailable，MUST NOT 回退进程内 memory store 创建或接管 generation；
- producer token 及 lease 只属于短期 Redis 状态，MUST NOT 写入 D1 长期保存；
- Redis append/snapshot/finalizing/terminal mutation MUST 校验 producer token；
- producer token 的 mark-running、heartbeat、append、snapshot、finalization/terminal mutation 还 MUST
  验证当前 lease 未过期；过期 owner 不得自行续租。blocking `XREAD` 被唤醒后 MUST 重新原子验证
  cursor 仍在精确 trim window 中，不得直接信任唤醒时的 tail；
- cancel 与 finalization 必须通过 Redis CAS 排序：finalization 先赢则 cancel 返回 finalizing，cancel 先赢则
  finalizer 只能写 aborted terminal；
- 失去 lease 的旧 producer MUST 被 fenced；reaper 只有先取得 Redis expired-lease CAS，才可写最小
  `producer_lost`/failed terminal；
- D1 `battle_report_generations` 只在 durable finalization 阶段以 `completed | failed | aborted` 终态写入，
  `large_objects`/R2 保存完整正文；D1/R2 terminal evidence 是 Redis 过期后的恢复依据；
- Provider 已结束但 rating/history 等 bounded finalization 尚未全部完成时，D1 行仍然表达真实 Provider terminal，
  并以 `finalizationCompleted=false` 隐藏于 public completed fallback；同一 generation 的 Redis lease reaper 可在
  取得 expired-lease CAS 后从有界 manifest 重试收口。create 看到这种 pending finalization MUST 返回不可用，
  MUST NOT 再启动 Provider；
- 相同确定性 generationId 已有 D1 terminal 时，同 hash 复用终态，不同 hash 冲突；MUST NOT 重启 Provider。

本要求复用既有 `battle_report_generations`、`battle_report_generation_combatants`、`arena_rating_events`、
`large_objects` 与 R2，不新增 reservation/effect schema migration。

为避免将客户端大 payload 放大成 Provider、Redis 或 D1 资源消耗，v1 还固定以下 server-side 硬边界：

- create JSON UTF-8 body 最大 `12 MiB`；服务端先认证，再以原始字节流增量读取；`Content-Length`
  超限或读到首个超限字节时立即取消正文并在 Provider 前返回 `413`；
- combatants 最多 `32`，adjudication events 最多 `100`；aux scenarios、materials、questionnaires 与
  narrative history 不再采用低位的每类 count cap，而是合计最多 `256` 项，并在最终 Prompt 完整渲染后
  执行估算 token 预算：系统渠道 `128,000`，Hosted BYOK `1,000,000`；服务端和 UI 复用同一轻量
  近似 estimator，不得把 UTF-8 byte count 伪装成 token 数。这两个数值是应用保护预算，不代表模型
  真实 context window；
- 单人 Arena Web 的辅助情景、素材和问卷复用上述 `256` 项总预算，不得按旧的每类 `10` 项静默截断；多人
  Room 的独立 shared-config wire contract 仍维持辅助情景和素材各 `10` 项，单人状态投影超限时明确拒绝；
- reasoning 与 Provider 文本（包括隐藏 stream meta 和可见结果）合计最多 `4 MiB`；BYOK 只放宽模型输入
  预算，不放宽 body、角色、裁定、聚合引用项、输出或 durable storage 等本方资源边界；启用内建 AI
  safety 时 safety 输入仍按系统渠道预算；reasoning 回调失败必须传播到 raw pump 并立即取消上游 reader；
- companion/session 在原始 body 字节计量与单次 JSON parse 后复用 typed payload，PVP authority 不得 clone
  并重复读取完整 body；
- `battle_report_generations.extra_json` terminal/finalization manifest 最大 `96 KiB`，其中 local-card
  reconciliation candidate 最大 `64 KiB`，impacts/combatant fallback 各最多 `32`；超过预算时保留
  identity/finalization core 与明确 `manifest_budget_exceeded`，不保存完整卡片或无界数组；
- `battle_report_generation_combatants` 每个 generation 最多写 `32` 行，名称、template/data-card ID
  等列在写入前分别截断；完整正文仍只进 R2。

Provider 已交付完整正文后，R2 归档或 D1 附加 finalization 失败 MUST 返回
`completed` 与 `persistenceWarning`，不得制造 Redis `failed` / `producer_lost` terminal。Redis
finalization CAS 保存的 completed intent 是这条降级路径的最小因果证据；lease reaper
看到该 intent 且 D1 仍 pending/not-found/unavailable 时只能保持明确 pending，不得改判
`producer_lost`。没有 completed intent、Provider 确实在输出中途丢失时，仍由取得 Redis
reaper CAS 的请求写入最小 `producer_lost` 终态。owner/request/payload/status 冲突继续
fail closed。

### RESUME-STORAGE-005 Local-first card reconciliation

角色完整卡片继续由浏览器本地库拥有，服务器不得为了可恢复流把私有卡片提升为云端权威；但浏览器也不得决定
rating/history/current-state 的 report、impacts 或写入开关。completed finalization MUST 在现有
`battle_report_generations.extra_json` 冻结有界的服务器 report/impacts、原 generation roster 的稳定
identity、原生签名因果绑定与写入策略；不得持久化完整更新后卡片。

浏览器后续只提交其本地卡片正文和 generation actor credential。reconciliation endpoint MUST：

1. 先验证 generation owner 与 completed terminal；
2. 忽略客户端 report/impacts/guidance/write flags，按 room combatant key、DataCard ID、exact preset
   template 或无稳定 claim 时的唯一 `type + name` 对应冻结 roster；
3. 单角色身份歧义或缺失时局部跳过并返回 warning；全部角色都无法对应时才整体失败；
4. 客户端 `isNative` 不可信；只有当前合法签名与本次冻结签名一致，或 exact canonical preset
   与冻结 template 一致时才能重签；验证失败降级为 non-native 并继续低风险更新；
5. transformation 使用 generation 内冻结 effect 可安全重入；服务器 MUST NOT 持久化
   complete `updatedCombatants` result。

该设计保持本地数据所有权，同时把 AI 终态解释、服务器签名能力和云端业务副作用幂等留在服务器权威边界。

本条中的“浏览器不得决定”只约束上述 authoritative reconciliation：浏览器提交的数据不得覆盖 generation 冻结 effect，
也不得借此获得或延续服务器原生签名。generation 完成后，用户 MAY 按
[`SPEC-arena-post-battle-dual-trust-v1`](./2026-09-01_133000_Arena战后角色更新双信任通道规格.md)
创建只影响本人角色工作副本的 unsigned repair derivative；该通道不得修改 generation、战报、rating、ranking 或 Room authority。

## 12. Web 客户端状态机

客户端 SHOULD 使用：

```text
idle
 -> connecting
 -> generating
 -> reconnecting
 -> resuming
 -> generating
 -> completed

terminal alternatives:
 -> failed
 -> cancelled
 -> producer_lost
```

网络断开后：

- MUST 保留当前已展示正文与 `generationId/generationRequestId/lastEventId`；
- MUST NOT 自动创建新 generation；
- SHOULD 使用 bounded exponential backoff + jitter；
- `online` / `visibilitychange` MAY 触发立即状态探测，但不得形成高频轮询；
- 恢复成功后继续同一 generation；
- 收到 `snapshot` 时 replace 到 snapshot，再从 cursor tail；
- 只有 terminal failure 才显示真正“生成失败”。

Arena v1 Web public transport 固定为 fetch-SSE。历史持久化的 `plain-stream` preference MUST 单调迁移为 `sse`；
不得保留一个会绕过 generation ID/cursor/resume contract 的公开 transport selector。

用户提示 SHOULD 区分：

- “网络连接暂时中断，战报仍在服务器生成，正在恢复连接”；
- “已恢复连接，继续接收战报”；
- “生成进程已丢失，无法安全自动重试”；
- “生成失败/已取消”。

## 13. 安全与隐私

- Redis MUST NOT 保存 API Key、Authorization header、Cookie、完整 IP、完整敏感 provider config。
- 如果 snapshot 含用户生成正文，其 TTL 与访问控制必须与短期 generation 数据一致。
- 日志 SHOULD 记录 generation/request/event IDs、字节数、状态与错误码，不打印完整 prompt/正文。
- resume/status/cancel 的 actor 校验必须使用与 create 相同的业务身份语义。
- generation terminal reconciliation 必须使用与 create 相同的 actor credential；嵌套 Arena session 子请求必须
  透传并把升级后的 anonymous credential 返回浏览器，不得生成无法由浏览器恢复的孤儿 actor。
- `generationRequestId` 冲突响应不得泄露其他用户是否占用了某个 ID。

## 14. Telemetry

除了恢复 telemetry，Hosted execution placement MUST 能按 capability/runtime 比较至少：

- request count；
- Worker/Hono CPU 或可比的 process CPU 指标；
- p50/p95/p99 duration 与 AI TTFB/total；
- input/output bytes；
- safety/prompt/finalization 阶段耗时（能安全观测时）；
- provider starts / retries；
- disconnect/resume/cancel；
- D1/R2/Redis latency/error；
- runtime selection / DR reason（由可信入口观测时）。

这些指标用于判断 Details/Sublimation、Tea Party/Tavern 是否继续 re-enter Hono。**不得用“路由数量”或单纯 wall-clock stream duration 代替成本证据。**

至少新增以下指标/结构化事件：

- `generation_client_disconnect_total`
- `generation_resume_attempt_total`
- `generation_resume_success_total`
- `generation_resume_failure_total{reason}`
- `generation_replay_events_total`
- `generation_replay_bytes_total`
- `generation_resume_latency_ms`
- `generation_snapshot_bootstrap_total`
- `generation_request_reuse_total`
- `generation_request_conflict_total`
- `generation_producer_lost_total`
- `generation_redis_degraded_total`
- `generation_cancel_total{reason}`

每次 terminal audit SHOULD 能回答：

1. Provider 是否实际启动过；
2. 是否发生过 subscriber disconnect；
3. resume 次数；
4. 是否发生 snapshot bootstrap；
5. 是否触发 second-provider prevention；
6. terminal 原因；
7. R2/D1 finalization 是否成功。

## 15. 验收故障矩阵

v1 至少覆盖：

| 场景 | 必须结果 |
| --- | --- |
| 生成中关闭网络 5–30 秒再恢复 | 同一 generation 继续；无第二次 Provider |
| Wi-Fi ↔ 移动网络切换 | 可重连；无重复正文/副作用 |
| 页面刷新 | 已知 generationRequestId 时恢复同一任务 |
| 首次 POST 已被服务器接受、但响应头到达前断网 | 以相同 generationRequestId lookup 并 resume，不重放 create，不创建第二 generation |
| subscriber 主动取消 reader，但用户未点停止 | producer 继续 |
| 用户点击停止 | producer 被显式 cancel；重复 cancel 幂等 |
| 两个 tab 同时订阅 | 两者可观察；不重复 finalization |
| cursor 在 replay window 内 | 只返回严格晚于 cursor 的事件 |
| cursor 已被 trim | snapshot bootstrap 或明确 fallback，不乱序 append |
| Redis 短时写失败 | 不二次 Provider；live resume 可 degraded；终态仍尝试 D1/R2 |
| 创建时 Redis reservation 不可用 | Provider 调用前 fail closed |
| Hono producer 进程被杀 | lease 到期后对账；不得自动二次 Provider |
| generation 已完成但 Redis 已过期 | 从 D1/R2 恢复完整结果 |
| ranking/history/finalize 重连多次 | 业务副作用最多一次 |

测试 MUST 同时覆盖正常快速流与慢流；不得只 mock 一个同步完成的 stream。

## 16. 标准与实现指南

外部资料最近核验：2026-08-25。设计参考：

- Cloudflare Workers Pricing：<https://developers.cloudflare.com/workers/platform/pricing/>；Standard 主要按 requests + CPU time 计费，duration 本身不收费；
- Cloudflare Workers Limits：<https://developers.cloudflare.com/workers/platform/limits/>；Paid request CPU 上限与运行资源边界；网络等待不应与 CPU time 混同；
- Cloudflare Load Balancing active-passive：<https://developers.cloudflare.com/load-balancing/understand-basics/traffic-steering/steering-policies/standard-options/>；`Off - Failover` 可作为 active-passive 控制面参考，但业务层仍负责 non-idempotent replay safety；
- WHATWG HTML Living Standard — Server-sent events：<https://html.spec.whatwg.org/dev/server-sent-events.html>；`id`、`Last-Event-ID`、重连等待/退避语义；
- Redis `XREAD`：<https://redis.io/docs/latest/commands/xread/>；按“last seen ID”读取严格更大的 entries，并支持 blocking tail；
- Redis Streams：<https://redis.io/docs/latest/develop/data-types/streams/>；
- Hono Streaming helper：<https://hono.dev/docs/helpers/streaming>；SSE 输出与 connection abort hook；
- Vercel `resumable-stream`：<https://github.com/vercel/resumable-stream>；producer 与 reader 生命周期解耦的工程实践；
- AI SDK Resume Streams：<https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams>；Redis-backed resume 的参考实现。

本文只采纳其协议/生命周期原则，不要求切换到原生 EventSource、AI SDK Chat UI protocol 或第三方 resumable-stream 库。

## 17. 完成条件

本规格的 **Arena v1 阻断纵切** 只有在以下条件全部满足时可视为 implemented：

1. `req.signal` 不再直接代表 Arena generation cancellation；
2. explicit cancel 可用且幂等；
3. stable generationRequestId + single-producer reservation 生效；
4. Redis snapshot + replay + SSE event id 生效；
5. fetch-SSE reconnect/resume 生效；
6. D1/R2 terminal fallback 生效；
7. `arena/generate-stream` 的 Hono re-entry contract gate 全部通过并完成可回滚公开切流；
8. 故障矩阵验证无第二次 Provider、无重复副作用；
9. telemetry 能区分 disconnect / resume / provider failure / producer loss，并能比较 Hono/Cloudflare placement 成本；
10. 独立 review 无未关闭 Critical/Important finding。

规格本身保持 `accepted`；后续 family 是否已完成由实施计划与日志逐项记录：

- Arena companion routes：`arena/generate`、`generate-battle-story`、`arena/session/generate-next`；
- Details / Sublimation 四条 route；
- telemetry-gated Tea Party / Tavern family。

这些后续项未完成时不得伪称“所有 Hosted AI execution 已迁 Hono”，但也不阻止已通过 gate 的 Arena resumable vertical 单独上线。
