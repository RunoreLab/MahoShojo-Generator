状态：`proposed`
日期：2026-08-25
规格标识：`SPEC-hosted-resumable-generation-stream-v1`
依据 ADR：`ADR-hosted-runtime-resilience-cloudflare-dr`
关联 ADR：`ADR-arena-room-portable-runtime-hono-redis-first`
基线分支：`refactor/platform-rearchitecture`
基线提交：`f1d7c3ca476665224d46d6ffa083992d55ac466b`
首个落地点：Arena 战报 `arena/generate-stream`

## 1. 规范语言与目的

本文中的“必须 / MUST”“不得 / MUST NOT”“应 / SHOULD”“可以 / MAY”具有规范性，其解释遵循 RFC 2119 与 RFC 8174。

本文处理的首要故障不是模型语义提前结束，也不是 Hono 整机故障，而是：**AI 生成仍健康运行时，浏览器到 Hosted runtime 的下游连接因移动网络抖动、切网、后台冻结或短时断网而中断**。

当前 Arena 流把 `req.signal` 直接传给 AI 上游；因此客户端 HTTP 连接取消会传导成模型生成取消。客户端随后即使重新联网，也只能重新发起一次模型请求，既无法恢复原生成，又可能造成重复消耗和排位/历史副作用风险。

本文的核心目标是把两个生命周期解耦：

```text
Generation producer
  start -> running -> completed / failed / cancelled

Subscriber connection
  connect -> disconnect -> reconnect -> ... -> terminal observed
```

**Subscriber disconnect MUST NOT 等价于 Generation cancel。**

首版完成后，短时断网必须优先恢复同一个 generation；不得以“重新 POST 一次生成”模拟恢复。

## 2. 适用范围与非目标

### 2.1 v1 范围

v1 MUST 完成：

1. Arena `generate-stream` 的 generation lifecycle 与请求连接 lifecycle 解耦；
2. 稳定 `generationRequestId` 与幂等 reservation；
3. Hono-owned generation producer；
4. Redis 状态快照 + bounded replay stream；
5. 带 `id:` 的 SSE 事件；
6. fetch-SSE 自动重连与断点续传；
7. 显式 cancel；
8. D1/R2 terminal result fallback；
9. 排位、历史、R2、审计等副作用的单次 finalization；
10. 断网、重连、Redis 降级、producer 丢失的故障测试与 telemetry。

共享抽象 SHOULD 为其他 Hosted 长生成复用，但 v1 MUST NOT 因此把全部生成 route 一次性迁移或重写。

### 2.2 非目标

v1 MUST NOT 承诺：

- Hono 容器/整机死亡后无缝续接同一个上游模型 TCP/HTTP 请求；
- Redis 丢失后恢复尚未完成的所有逐字 delta；
- 跨运行时自动重放非幂等 AI generation；
- WebSocket 替代 SSE；
- Durable Object / Cloudflare Queues / Workflows 作为本问题的强制依赖；
- 原生 `EventSource` 取代当前需要 Authorization / activity headers 的 fetch-SSE 客户端；
- 将 Redis 提升为战报、排位或结算事实的权威存储。

Hono 进程/整机丢失属于 Hosted DR 的更高一级故障域。发生此类故障时，v1 的正确行为是对账并恢复已持久化终态；若无法证明原 generation 是否仍在运行，MUST 返回 `producer_lost` / `unknown` 一类明确状态，MUST NOT 自动发起第二次模型生成。

## 3. 既有文档关系

### 3.1 Hosted DR ADR

本文具体落实 `ADR-hosted-runtime-resilience-cloudflare-dr` 已接受的原则：

- generation/stream/settlement 不得做不安全透明 replay；
- 恢复应围绕稳定 `generationRequestId`、attempt、状态查询与最终结果；
- D1 保存业务事实，R2 保存最终大对象，Redis 只承担可重建的短期状态/stream；
- `mid-flight disconnect` 必须验证不会产生第二次 Provider/generation。

因此本文 **不新建顶层 ADR**。

### 3.2 Arena 多人 Hono + Redis

本文复用 Arena multiplayer 已接受的实现模式：

- Hono + Redis 首发；
- stable generation identity；
- snapshot + bounded replay；
- delta 合并后写入；
- Redis 不作为最终业务 authority；
- Hono process loss 时先对账，不自动重发 AI。

多人 Room runtime 的 WebSocket、presence、Proposal 等不属于本文范围。

### 3.3 2026-05 Cloudflare Queues 异步化设计

`docs/specs/2026-05-22_144846_Cloudflare_Queues_AI生成异步化设计.md` 保留为历史/未来后台异步执行方案，不被删除。

针对当前“客户端短时断网导致战报半途截断”的近期问题，v1 SHOULD 优先复用已经存在的 Hono + Redis + SSE + R2 能力，而不是先引入 Queue consumer。若未来需要“HTTP 请求结束后跨进程可靠排队、延时执行、长时间任务中心”，可重新评估 Queue/Workflows。

## 4. 核心不变量

### RESUME-INV-001 Generation 与连接解耦

Hosted generation MUST 由服务器拥有独立的 `AbortController` / cancellation token。

`req.signal`、下游 `ReadableStream.cancel()`、socket close 或 subscriber abort MUST 只终止当前 subscriber，不得直接取消 AI provider request。

### RESUME-INV-002 只有显式动作可取消 generation

以下事件 MAY 取消 generation：

- 用户显式点击“停止生成”；
- 服务端 total/idle/resource budget 达到硬限制；
- 管理/安全策略明确终止；
- provider 明确失败且 retry policy 已耗尽。

网络离线、页面刷新、标签页后台冻结、subscriber EOF MUST NOT 自动取消 generation。

### RESUME-INV-003 稳定 generationRequestId

更新后的客户端 MUST 在首次网络请求之前生成稳定、不可预测的 `generationRequestId`，推荐 UUIDv4/UUIDv7 同等级随机标识。

该 ID 在同一次逻辑生成的所有 create/reconnect/status/cancel 请求中保持不变。

服务器 MUST 对 `(actor, generationRequestId)` 建立幂等 reservation，并保存请求 payload hash / semantic hash。相同 ID + 相同请求 MUST 复用原 generation；相同 ID + 不同请求 MUST 返回冲突，不得启动第二个 generation。

`generationRequestId` MAY 与最终 `generationId` 采用同一 UUID，但实现必须保留“请求幂等身份”和“业务 generation identity”两个语义概念，避免未来迁移时耦合。

### RESUME-INV-004 不以 generationId 作为凭证

`generationId` / `generationRequestId` MUST NOT 被视为 bearer secret。

resume/status/cancel 必须重新验证当前 auth user 或现有 activity identity 与 generation owner 的关系。PvP 场景继续遵守既有 match membership / authority contract。

### RESUME-INV-005 副作用最多一次

reconnect、snapshot、replay、多个 subscriber MUST NOT 重复触发：

- Arena rating settle；
- narrative/current-state/history write；
- battle report final record；
- R2 final object index；
- 其他一次性统计或结算事实。

终态提交必须以 `generationId` / business key 具备幂等保护，并保持既有 D1 unique/CAS/settlement 约束。

### RESUME-INV-006 Redis 非权威

Redis MAY 保存：

- running state；
- owner lease/heartbeat；
- generation request reservation；
- 当前展示 snapshot；
- bounded SSE replay events；
- subscriber/reconnect telemetry 的短期聚合。

Redis MUST NOT 成为：

- 完整战报最终 authority；
- rating/settlement authority；
- user/card/match/history 权威事实源；
- API Key / provider secret 存储。

终态事实仍落 D1；完整大输出仍落 R2/large-object 体系。

## 5. Runtime 与 route placement

### 5.1 为什么 v1 需要 Hono

当前 Phase 2.5B capability-exit 后，`arena/generate-stream` 属于 `exitedRouteIds`，由 Next 同源执行；当前 Redis runtime 则属于 `apps/api` / Hono Node。

完整 resumable generation 需要服务器在 subscriber 消失后继续持有 provider stream，并需要 Redis replay/lease。因此 v1 允许 `arena/generate-stream` **基于明确可靠性收益重新进入 Hono shared-service seam**。

这不是为了提高 Hono route 覆盖率，也不撤销 Phase 2.5B 的 capability-exit 原则。

### RESUME-RT-001 精确 re-entry gate

`arena/generate-stream` 从 `exitedRouteIds` 移入 `sharedRouteIds` 之前 MUST 同时满足：

1. 业务 core 不由 Hono adapter 动态导入 Next handler；
2. Next 与 Hono adapter 复用同一 generation service / contract；
3. auth actor、activity identity、safety、provider resolution、signature、Arena v1 wire、D1/R2、rating/history side effect 有 contract parity 证据；
4. SSE `markdown/reasoning/meta/telemetry/ranking/error/done` 语义保持兼容；
5. 新的 disconnect/reconnect/cancel 语义有专项测试；
6. manifest/boundary/package/server/workspace/build 验证通过；
7. 独立 review 无未关闭 Critical/Important finding；
8. route cutover 可独立回滚。

G25D 的 `apps/web` relocation MUST 保持行为等价，不得夹带这一 re-entry。

### RESUME-RT-002 rollout 原子性

后端 producer 解耦与前端 resume UX 不得以“半成品”公开切流。

实现 MAY 分两个 Goal 开发，但 production/public route cutover MUST 在服务端 resume/status/cancel 与客户端 reconnect state machine 均可用后完成。

## 6. Generation 状态机

内部 generation control state SHOULD 至少包含：

```text
reserved -> running -> completed
                   -> failed
                   -> cancelled
                   -> producer_lost
```

说明：

- `reserved`：幂等身份已占用，但 provider 尚未开始；
- `running`：provider 已开始；
- `completed`：终态结果已完成并进入权威 finalization；
- `failed`：provider/业务失败；
- `cancelled`：显式 cancel 或硬资源预算终止；
- `producer_lost`：lease 过期且无法证明 terminal result，禁止自动重跑。

现有 `battle_report_generations.status` MAY 在 v1 继续保持现有 `completed / failed / aborted` 持久语义以避免无关 schema 扩张；内部 `cancelled` 可映射到现有 `aborted`。**普通 subscriber disconnect 不再产生 terminal `aborted`。**

## 7. Redis GenerationReplayStore

### 7.1 不暴露 raw Redis client

`apps/api` SHOULD 新增窄接口 `GenerationReplayStore`，由 Redis runtime 实现；shared/domain code MUST NOT 直接 import node-redis client。

建议能力：

```ts
interface GenerationReplayStore {
  reserve(input: ReserveGenerationInput): Promise<ReserveGenerationResult>;
  markRunning(input: MarkRunningInput): Promise<void>;
  heartbeat(input: GenerationLeaseInput): Promise<void>;
  appendEvents(input: AppendGenerationEventsInput): Promise<AppendResult>;
  writeSnapshot(input: WriteGenerationSnapshotInput): Promise<void>;
  readSnapshot(input: ReadGenerationSnapshotInput): Promise<GenerationSnapshot | null>;
  readAfter(input: ReadGenerationEventsInput): Promise<GenerationEventBatch>;
  markTerminal(input: MarkGenerationTerminalInput): Promise<void>;
  readState(input: ReadGenerationStateInput): Promise<GenerationState | null>;
}
```

### 7.2 Key 空间

实现 SHOULD 使用版本化、可批量清理的 namespace，例如：

```text
mahoshojo:gen:v1:{generationId}:state
mahoshojo:gen:v1:{generationId}:events
mahoshojo:gen:v1:req:{actorScope}:{actorHash}:{generationRequestId}
```

key MUST NOT 包含明文 API Key、Cookie、完整 IP 或完整敏感 prompt。

### 7.3 Snapshot + bounded replay

v1 MUST 同时保存：

- 当前 generation snapshot；
- 有界、有序的 event journal。

仅保存 event journal 而没有 snapshot，会在 trim/长时离线后失去可靠 bootstrap；仅保存 snapshot 又无法高效断点追加。

snapshot 至少应记录：

- generation status；
- 当前可展示 markdown；
- 当前 reasoning 展示状态（若产品允许展示）；
- last replay event id；
- provider/model 非敏感 telemetry；
- updatedAt / producer lease；
- terminal summary / final object ref（若已完成）。

snapshot 更新 SHOULD 批量化，不要求每 token 写 Redis。

### 7.4 Delta 合并

`markdown` / `reasoning` delta MUST NOT 每 token 一次 `XADD`。

实现 SHOULD 使用“时间 + 字节数”双阈值合并，默认设计区间：

- 约 50–100ms flush；或
- 约 0.5–2 KiB 累积后提前 flush。

终态/控制事件（`meta`、`telemetry`、`ranking`、`error`、`done` 等）SHOULD 立即写入。

具体默认值属于运行参数，不作为产品语义冻结；变更必须有 telemetry 支持。

### 7.5 TTL 与 trim

Redis state/events MUST 设置 TTL 与容量上限。

默认目标是覆盖“生成最长时长 + 常见移动网络短时离线 + 用户刷新恢复”窗口，而不是长期归档。建议首轮从 terminal 后 30–60 分钟量级开始，通过观测调整。

当 replay window 已不包含客户端 cursor 时，服务端 MUST NOT 静默从错误位置追加；必须：

1. 返回/发送当前 snapshot 作为 bootstrap，并声明新的 snapshot cursor；或
2. 若 generation 已 terminal 且 Redis snapshot 不可用，从 D1/R2 返回最终完整结果；或
3. 明确返回 `replay_window_lost` / degraded，不得自动重新生成。

## 8. SSE 协议

### 8.1 标准兼容

WHATWG SSE 以 `id:` / `Last-Event-ID` 定义重连游标。v1 的 fetch-SSE 客户端 SHOULD 保持该语义，即使不使用原生 `EventSource`。

每个可 replay 事件 MUST 带稳定、单调有序的 Redis stream ID：

```text
id: 1724570000000-0
event: markdown
data: {"chunk":"..."}
```

heartbeat/comment MUST NOT 推进 replay cursor。

### 8.2 Resume cursor

恢复 endpoint SHOULD 接受：

- `Last-Event-ID` header；
- 调试/兼容用途的 `after` query。

两者同时存在且不同 MUST 返回 400，避免游标歧义。

Redis `XREAD` 的“返回严格大于 caller 已见 ID 的 entries”语义 SHOULD 作为实现基础；浏览器 subscriber 是独立观察者，不得使用会把消息分摊给不同 consumer 的 consumer-group 语义。

### 8.3 事件类型

现有 Arena 事件保持兼容：

- `markdown`
- `reasoning`
- `reasoning_done`
- `meta`
- `meta_error`
- `telemetry`
- `ranking`
- `error`
- `done`

可新增：

- `snapshot`：恢复时的当前完整展示快照；客户端收到后必须 replace，而非 append；
- `resume`：可选诊断事件，描述 recovered/replayed 数量，不参与业务 finalization。

`debug` 与 keepalive MAY 不写入 replay journal。

## 9. HTTP API 契约

### 9.1 初始生成

为降低迁移风险，v1 MAY 保留现有入口：

```http
POST /api/arena/generate-stream?format=sse
```

更新后的 Web 客户端 MUST 在请求体或受控 header 中携带 `generationRequestId`。

服务器在调用 Provider **之前** MUST 完成：

1. actor / activity identity 解析；
2. request schema / safety / rate limit；
3. generation reservation；
4. payload hash 冲突检查；
5. producer ownership 建立。

只有 reservation 成功后才可以启动 provider。

### 9.2 Resume

新增逻辑 endpoint：

```http
GET /api/arena/generations/{generationId}/stream
Last-Event-ID: <cursor>
```

或等价 `?after=<cursor>`。

行为：

- owner 校验失败：401/403；
- generation running：snapshot/replay 后继续 tail；
- completed：补齐遗漏事件并发送 `done`，或返回 terminal snapshot/final result；
- failed/cancelled：发送对应 terminal 状态；
- producer_lost：明确报告，不自动生成；
- Redis replay unavailable 但 D1/R2 已 terminal：走 final fallback；
- 无法证明状态：返回 explicit unknown/degraded，不自动生成。

### 9.3 Status

新增逻辑 endpoint：

```http
GET /api/arena/generations/{generationId}
```

最小响应：

```json
{
  "generationId": "...",
  "generationRequestId": "...",
  "status": "running",
  "resumable": true,
  "lastEventId": "...",
  "updatedAt": "..."
}
```

终态可追加 final object / battle report reference，但不得泄露 provider secret。

### 9.4 Cancel

新增逻辑 endpoint：

```http
POST /api/arena/generations/{generationId}/cancel
```

cancel MUST：

- 校验 owner/authority；
- 幂等；
- 只影响对应 generation producer；
- 记录明确 cancel reason；
- 不因 subscriber disconnect 自动调用。

## 10. Producer ownership 与进程故障

### 10.1 单 producer

同一 `generationRequestId` 同一时刻 MUST 最多只有一个 active producer。

Redis reservation/lease SHOULD 使用原子 NX/CAS/Lua/transaction 等机制实现，禁止“先 GET 再 SET”的竞态窗口。

### 10.2 Redis 不可用

在 resumable route 已正式切流后，如果无法建立幂等 reservation / producer ownership，服务器 MUST 在调用 AI Provider 之前 fail closed；不得在“不知道是否已有 producer”的情况下继续创建新的 generation。

这不把 Redis 变成业务事实 authority；它只是把“无法证明单 producer”视为安全不可继续条件。

对已运行 producer，短暂 Redis 写失败 SHOULD 尽量继续生成并完成 D1/R2 finalization，同时标记 live resume degraded；恢复后可重新建立 snapshot。不得因 replay buffer 写失败自动二次调用 Provider。

### 10.3 Producer lease

running producer SHOULD 定期刷新 lease/heartbeat。

subscriber 读取到 `running` 但 lease 已过期时，不得无限等待；服务端必须先查 D1/R2 terminal evidence：

- 已完成：恢复最终结果；
- 有明确失败/取消：返回终态；
- 无证据：标记 `producer_lost` / `unknown`。

MUST NOT 自动从 prompt 重启模型。

## 11. R2 / D1 finalization

### RESUME-STORAGE-001 R2 属于 producer

当前 subscriber disconnect 路径会取消 R2 upload。v1 中 R2 final-output pipeline MUST 归 generation producer 所有，不得由 subscriber cancel 触发 abort。

### RESUME-STORAGE-002 Terminal fallback

若 Redis replay 已过期/丢失，但 generation 已成功完成，status/resume MUST 能依据现有 battle report record + R2/large-object 取回最终完整正文。

### RESUME-STORAGE-003 Partial output

v1 不要求把每个 partial delta 持久化到 D1/R2。Redis partial snapshot 属于短期恢复数据。

若 producer 自身死亡，已有 partial output MAY 用于排障/用户提示，但不得把不完整结果伪装为 completed。

## 12. Web 客户端状态机

客户端 SHOULD 使用：

```text
idle
 -> connecting
 -> generating
 -> reconnecting
 -> resuming
 -> generating
 -> completed

terminal alternatives:
 -> failed
 -> cancelled
 -> producer_lost
```

网络断开后：

- MUST 保留当前已展示正文与 `generationId/generationRequestId/lastEventId`；
- MUST NOT 自动创建新 generation；
- SHOULD 使用 bounded exponential backoff + jitter；
- `online` / `visibilitychange` MAY 触发立即状态探测，但不得形成高频轮询；
- 恢复成功后继续同一 generation；
- 收到 `snapshot` 时 replace 到 snapshot，再从 cursor tail；
- 只有 terminal failure 才显示真正“生成失败”。

用户提示 SHOULD 区分：

- “网络连接暂时中断，战报仍在服务器生成，正在恢复连接”；
- “已恢复连接，继续接收战报”；
- “生成进程已丢失，无法安全自动重试”；
- “生成失败/已取消”。

## 13. 安全与隐私

- Redis MUST NOT 保存 API Key、Authorization header、Cookie、完整 IP、完整敏感 provider config。
- 如果 snapshot 含用户生成正文，其 TTL 与访问控制必须与短期 generation 数据一致。
- 日志 SHOULD 记录 generation/request/event IDs、字节数、状态与错误码，不打印完整 prompt/正文。
- resume/status/cancel 的 actor 校验必须使用与 create 相同的业务身份语义。
- `generationRequestId` 冲突响应不得泄露其他用户是否占用了某个 ID。

## 14. Telemetry

至少新增以下指标/结构化事件：

- `generation_client_disconnect_total`
- `generation_resume_attempt_total`
- `generation_resume_success_total`
- `generation_resume_failure_total{reason}`
- `generation_replay_events_total`
- `generation_replay_bytes_total`
- `generation_resume_latency_ms`
- `generation_snapshot_bootstrap_total`
- `generation_request_reuse_total`
- `generation_request_conflict_total`
- `generation_producer_lost_total`
- `generation_redis_degraded_total`
- `generation_cancel_total{reason}`

每次 terminal audit SHOULD 能回答：

1. Provider 是否实际启动过；
2. 是否发生过 subscriber disconnect；
3. resume 次数；
4. 是否发生 snapshot bootstrap；
5. 是否触发 second-provider prevention；
6. terminal 原因；
7. R2/D1 finalization 是否成功。

## 15. 验收故障矩阵

v1 至少覆盖：

| 场景 | 必须结果 |
| --- | --- |
| 生成中关闭网络 5–30 秒再恢复 | 同一 generation 继续；无第二次 Provider |
| Wi-Fi ↔ 移动网络切换 | 可重连；无重复正文/副作用 |
| 页面刷新 | 已知 generationRequestId 时恢复同一任务 |
| 首次 POST 已被服务器接受、但响应头到达前断网 | 重试相同 generationRequestId 不创建第二 generation |
| subscriber 主动取消 reader，但用户未点停止 | producer 继续 |
| 用户点击停止 | producer 被显式 cancel；重复 cancel 幂等 |
| 两个 tab 同时订阅 | 两者可观察；不重复 finalization |
| cursor 在 replay window 内 | 只返回严格晚于 cursor 的事件 |
| cursor 已被 trim | snapshot bootstrap 或明确 fallback，不乱序 append |
| Redis 短时写失败 | 不二次 Provider；live resume 可 degraded；终态仍尝试 D1/R2 |
| 创建时 Redis reservation 不可用 | Provider 调用前 fail closed |
| Hono producer 进程被杀 | lease 到期后对账；不得自动二次 Provider |
| generation 已完成但 Redis 已过期 | 从 D1/R2 恢复完整结果 |
| ranking/history/finalize 重连多次 | 业务副作用最多一次 |

测试 MUST 同时覆盖正常快速流与慢流；不得只 mock 一个同步完成的 stream。

## 16. 标准与实现指南

设计参考：

- WHATWG HTML Living Standard — Server-sent events：<https://html.spec.whatwg.org/dev/server-sent-events.html>；`id`、`Last-Event-ID`、重连等待/退避语义；
- Redis `XREAD`：<https://redis.io/docs/latest/commands/xread/>；按“last seen ID”读取严格更大的 entries，并支持 blocking tail；
- Redis Streams：<https://redis.io/docs/latest/develop/data-types/streams/>；
- Hono Streaming helper：<https://hono.dev/docs/helpers/streaming>；SSE 输出与 connection abort hook；
- Vercel `resumable-stream`：<https://github.com/vercel/resumable-stream>；producer 与 reader 生命周期解耦的工程实践；
- AI SDK Resume Streams：<https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams>；Redis-backed resume 的参考实现。

本文只采纳其协议/生命周期原则，不要求切换到原生 EventSource、AI SDK Chat UI protocol 或第三方 resumable-stream 库。

## 17. 完成条件

本规格 v1 只有在以下条件全部满足时可标记 `accepted/implemented`：

1. `req.signal` 不再直接代表 Arena generation cancellation；
2. explicit cancel 可用且幂等；
3. stable generationRequestId + single-producer reservation 生效；
4. Redis snapshot + replay + SSE event id 生效；
5. fetch-SSE reconnect/resume 生效；
6. D1/R2 terminal fallback 生效；
7. Arena route 的 Hono re-entry contract gate 全部通过；
8. 故障矩阵验证无第二次 Provider、无重复副作用；
9. telemetry 能区分 disconnect / resume / provider failure / producer loss；
10. 独立 review 无未关闭 Critical/Important finding。
