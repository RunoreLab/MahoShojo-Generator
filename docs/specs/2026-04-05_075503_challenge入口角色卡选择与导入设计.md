# /challenge 入口角色卡选择与导入设计

## 背景

当前 `/challenge` 的 lobby 入口仍以“大段手动粘贴 JSON” 为主，只有“载入试玩示例”这一种快捷入口。相比 `/arena` 已经稳定提供的数据库选卡、随机匹配、文件上传与文本粘贴，这套入口存在几个明显问题：

1. 首屏交互负担过重，用户必须先面对原始 JSON。
2. 角色来源方式不统一，无法复用在线角色库与随机匹配能力。
3. `/challenge` 当前入口只适合单卡手动调试，不利于后续扩展到多人组队挑战。
4. 现有 arena 导入链路中已有大量成熟能力，但目前没有以合适边界复用到 challenge。

本次设计目标是在不把 `/challenge` 绑定到 arena 战斗 store 的前提下，复用 `/arena` 的成熟入口体验，让 challenge 也支持数据库选择、随机匹配、文件上传、粘贴文本和高级 JSON 编辑。

## 目标

1. `/challenge` 的 lobby 入口参考 `/arena` 的结构与视觉层次重构。
2. 支持以下角色卡来源方式：
   - 数据库选择
   - 随机匹配
   - 文件上传
   - 粘贴文本
   - 试玩示例
   - 高级 JSON 手动编辑
3. 数据库选择行为与 `/arena` 保持一致：
   - 已登录时可访问私有卡与公开卡
   - 未登录时仅访问公开卡
4. 现阶段 challenge 仍然保持“单卡入场”约束，但状态设计要为未来组队扩展预留空间。
5. 尽量复用已有组件、接口与解析逻辑，不新增平行的角色导入体系。

## 非目标

1. 本次不改动 challenge 的单人运行模型，不把 `playerSnapshot` 直接升级为多人 `partySnapshot`。
2. 本次不改动 challenge 的 bootstrap、checkpoint、resolver、节点结算等核心流程语义。
3. 本次不把 arena 的 `useBattleStore` 或 `useBattleActions` 直接并入 `/challenge`。
4. 本次不为 challenge 设计独立的新弹窗或新卡片视觉语言。
5. 本次不实现真正的多人组队挑战，只预留后续扩展边界。

## 现有可复用能力

### 可直接复用的组件

以下组件可以直接在 `/challenge` 中复用：

1. `DatabaseSelector`
   - 复用数据库选择与随机匹配的按钮布局与登录态提示。
2. `BattleDataModal`
   - 复用现有角色库浏览、公开/私有切换、搜索筛选和选卡交互。
3. `CollapsibleSection`
   - 复用分区折叠结构，让 challenge 的 lobby 布局与 arena 形成统一体验。

### 可复用但需要解耦的逻辑

以下能力不应继续隐藏在 arena store 适配层中，而应抽成 challenge 与 arena 都能调用的共享 helper：

1. 从 `BattleDataModal` 选中结果中提取标准角色卡对象。
2. 从 `/api/random-public-card?type=character` 拉取随机公开角色。
3. 从文件内容或粘贴文本中解析单张角色卡。
4. 将角色卡对象序列化回稳定 JSON 文本，用于 challenge 的高级编辑区。
5. 统一生成“来源方式”元信息，供 lobby 摘要展示。

### 不能直接复用的现有实现

`RosterUploader` 与 `useBattleActions` 当前强绑定以下 arena 语义：

1. `combatants`
2. `scenario`
3. `auxScenarios`
4. `MAX_COMBATANTS`
5. arena 专用随机占位、编队和战斗模式状态

因此不能把它们整套接入 `/challenge`。本次只复用其交互模式与底层解析逻辑，不复用其 store 耦合层。

## 推荐方案

本次采用“复用 UI + 抽共享导入适配层 + challenge 自有入场草稿状态”的方案。

### 方案说明

1. `/challenge` 直接复用 arena 已存在的数据库选卡 UI 与数据卡弹窗。
2. challenge 自己维护一份“挑战入场草稿状态”，不依赖 arena store。
3. 将 arena 现有的导入与卡片标准化逻辑抽为共享 helper，由 challenge 和 arena 各自调用。
4. 当前仍只允许一张角色卡进入 challenge，但内部状态使用数组形态建模，便于后续演进到多人组队。

### 不采用的方案

#### 不采用方案：直接接入 arena store

原因：

1. challenge 当前从类型、bootstrap 到裁定链路都是单玩家模型。
2. 直接引入 arena store 会把 challenge 提前绑定到 arena 的多人战斗语义。
3. 未来 challenge 即使支持组队，也未必与 arena 的 `combatants`、`scenario`、`auxScenarios` 建模一致。

#### 不采用方案：challenge 自建一套平行导入 UI

原因：

1. 会复制已成熟的数据库选择、筛选、随机匹配与登录态交互。
2. 后续很容易与 `/arena` 体验分叉。

## 用户体验设计

## Lobby 布局

`ChallengeLobby` 改造成左右两栏布局，整体视觉风格继续对齐 challenge 现有页面外壳。

### 左侧主区

左侧主区按从上到下的顺序展示：

1. 世界介绍与快速说明
2. 当前挑战者摘要卡
3. 在线角色库 / 随机匹配分区
4. 本地导入分区
5. 粘贴文本分区
6. 高级 JSON 编辑分区
7. “生成竞技场快照”主按钮

### 右侧侧栏

右侧继续保留：

1. `ChallengeResumePanel`
2. `ChallengeUnlockPanel`

这样可以保证现有挑战恢复和解锁入口不受本次改造影响。

## 当前挑战者摘要

当用户已选中一张角色卡时，主区顶部显示摘要卡，至少展示：

1. 角色显示名
2. 模板类型
3. 来源方式
4. 当前是否可用于 challenge bootstrap
5. 操作按钮：
   - 重新从数据库选择
   - 清空当前角色
   - 展开高级 JSON 编辑

当尚未选中角色卡时，显示空状态提示，引导用户使用下方任一入口。

## 各入口交互

### 在线角色库 / 随机匹配

该分区直接复用 `DatabaseSelector` 的交互样式，行为如下：

1. “浏览在线角色库”按钮打开 `BattleDataModal`
2. `BattleDataModal` 使用 `selectedType="character"`
3. 当前阶段使用 `selectionMode="single"`
4. 数据库访问权限与 `/arena` 保持一致
5. “随机匹配角色”按钮调用现有随机公开角色接口

选卡成功后，立即更新：

1. `entrantCards[0]`
2. `rawEditorText`
3. `sourceMode`
4. 当前挑战者摘要

### 本地导入

该分区提供文件选择入口，支持上传 `.json` 文件。

当前阶段规则：

1. 一次只接受一张角色卡
2. 如果文件内容解析为数组或多个拼接对象，直接报错，不自动截断
3. 成功导入后同步更新 `entrantCards[0]`、`rawEditorText`、`sourceMode`

### 粘贴文本

该分区默认折叠。

交互要求：

1. 默认不展开，避免首屏再次退化成“大 textarea”
2. 用户展开后可以粘贴 JSON 文本
3. 点击确认后按与文件导入一致的规则解析
4. 解析成功后自动折叠或保留展开均可，但需清空错误提示

### 高级 JSON 编辑

该分区默认折叠，仅作为高级入口存在。

用途：

1. 允许对数据库选择、随机匹配、文件导入得到的角色卡做小范围人工修订
2. 保留当前 challenge 调试体验
3. 为后续更复杂的数据卡兼容问题提供兜底入口

按钮文案与提示应明确说明：

1. 默认推荐优先使用上方入口
2. 此处主要用于高级编辑与排障

### 试玩示例

试玩示例继续保留，但从主按钮提升为一种来源方式。

行为：

1. 点击后写入示例卡到 `entrantCards[0]`
2. 同步刷新 `rawEditorText`
3. `sourceMode` 标记为 `demo`

## 状态模型设计

## Challenge 入场草稿状态

`useChallengeController` 新增并维护 challenge 自己的入场草稿状态，建议至少包含：

1. `entrantCards: unknown[]`
2. `sourceMode: 'demo' | 'database' | 'random' | 'file' | 'paste' | 'manual-json' | null`
3. `rawEditorText: string`
4. `inputError: string | null`

### 当前阶段的约束

1. `entrantCards.length` 当前最大为 `1`
2. `prepareChallenge()` 只会读取第一张角色卡
3. 当 `entrantCards` 为空时，才回退解析 `rawEditorText`

### 未来组队扩展的预留

通过保留数组结构，为未来演进留出扩展点：

1. 将来可把最大入场人数从 `1` 提升到 `2` 或更多
2. `BattleDataModal` 可从 `single` 切到 `multi`
3. 文件与粘贴入口可从“单卡解析”升级成“多卡解析”

本次不修改 challenge 运行期领域模型，只在 lobby 入口层预留能力。

## 数据流设计

### 入口到 bootstrap 的数据流

1. 用户通过任一入口选中或导入角色卡
2. 控制器更新 `entrantCards[0]`
3. 控制器将该角色卡序列化为 `rawEditorText`
4. lobby 摘要区刷新显示当前挑战者
5. 用户点击“生成竞技场快照”
6. `prepareChallenge()` 优先使用 `entrantCards[0]`
7. 如果 `entrantCards[0]` 为空，则尝试解析 `rawEditorText`
8. 生成 `bootstrapDraft`

### 高级编辑回写规则

当用户在高级 JSON 编辑区修改文本后：

1. 文本本身实时保存在 `rawEditorText`
2. 不要求每次输入都即时更新 `entrantCards`
3. 只有在显式提交 challenge 或点击“应用编辑内容”时，才重新解析并覆盖 `entrantCards[0]`

这样可以避免一边输入一边污染当前有效草稿。

## 共享 helper 设计

本次新增的共享 helper 应保持与业务 store 脱钩，输入输出尽量纯粹。

建议拆分为以下几类能力：

1. `resolveChallengeEntrantFromDataCardSelection`
   - 输入：`BattleDataModal` 选中的 payload
   - 输出：标准角色卡对象、显示名、模板类型、来源元信息
2. `fetchRandomCharacterCard`
   - 输入：可选筛选条件
   - 输出：随机公开角色卡 payload
3. `parseSingleCharacterCardFromText`
   - 输入：文件文本或粘贴文本
   - 输出：单张角色卡对象
   - 约束：若检测到多张卡，则直接报错
4. `stringifyCharacterCardForEditor`
   - 输入：标准角色卡对象
   - 输出：稳定格式化后的 JSON 字符串

这些 helper 应可被 challenge 当前实现直接调用，也可供后续 arena 或其他入口复用。

## 组件边界

### `ChallengePage`

负责：

1. 持有 challenge 页面级状态
2. 持有数据库弹窗开关状态
3. 把页面级动作透传给 `ChallengeLobby`

### `ChallengeLobby`

负责：

1. 页面布局
2. 分区展示
3. 当前挑战者摘要
4. 调用上层透传的入口动作

不负责：

1. 解析文件
2. 处理数据库选卡 payload
3. challenge bootstrap 逻辑

### `BattleDataModal`

继续作为现有统一数据卡浏览器使用，不新增 challenge 专属分支逻辑。challenge 只通过 props 限定其使用方式。

### `ChallengeCardImportPanel`

建议新增一个轻量的 challenge 本地导入组件，负责：

1. 文件上传 UI
2. 粘贴文本 UI
3. 折叠状态控制
4. 调用共享 helper

它不应依赖 arena store。

## 错误处理

1. 数据库选卡失败时，沿用现有弹窗内错误提示，不额外复制一套错误体系。
2. 随机匹配失败时，在 challenge lobby 中显示明确错误文案。
3. 文件或粘贴文本解析失败时，`inputError` 展示到本地导入区域。
4. 如果检测到多张角色卡，错误文案需明确指出 challenge 当前只支持单卡入场。
5. 高级 JSON 编辑区解析失败时，不应清空当前已经成功选中的 `entrantCards[0]`。
6. 任一入口失败都不应影响右侧“继续挑战”和“解锁”区域。

## 测试设计

## 控制器测试

补充 `useChallengeController` 相关测试，覆盖：

1. 数据库选卡成功后会更新 `entrantCards[0]`、`rawEditorText` 与摘要状态。
2. 随机匹配成功后会写入 challenge 入场草稿。
3. 文件导入成功后会写入 challenge 入场草稿。
4. 粘贴文本解析出多张卡时会报错。
5. 高级 JSON 编辑失败时不会清空已存在的有效角色卡。
6. `prepareChallenge()` 优先使用 `entrantCards[0]`，其次才回退 `rawEditorText`。

## 组件渲染测试

补充 challenge lobby 渲染测试，覆盖：

1. 首屏显示在线角色库 / 随机匹配入口。
2. 本地导入分区存在文件上传入口。
3. 粘贴文本分区默认折叠。
4. 高级 JSON 编辑默认折叠。
5. 选中角色后会显示当前挑战者摘要。

## 共享 helper 测试

补充共享导入 helper 测试，覆盖：

1. 从数据卡 payload 中正确剥离 transport meta。
2. 单张角色卡文本能正确解析。
3. 多张角色卡文本会被 challenge 单卡约束拒绝。
4. 序列化后的 JSON 文本稳定可读。

## 验收标准

1. `/challenge` lobby 入口默认不再以大段 JSON 文本为主交互。
2. 用户可以通过数据库选择、随机匹配、文件上传、粘贴文本和试玩示例五种方式快速得到角色卡。
3. 高级 JSON 编辑仍然可用，但默认折叠。
4. 数据库访问权限与 `/arena` 保持一致。
5. 现阶段 challenge 仍只允许单卡入场，并对多卡输入给出明确报错。
6. challenge 不依赖 arena 的 `useBattleStore` 也能完成上述入口体验。
7. 入口层状态设计为未来组队扩展保留了数组形态与多选切换空间。
