## 1. 目的

本修订处理 GMR-10P 完成后暴露出的另一类产品一致性问题：当前 Arena 多人仍存在若干历史性、多人专属或层级混淆的门禁，例如：

- 创建房间时要求当前共享配置已经至少包含 1 个角色；
- `ArenaRoomSharedConfig` 同时承担“房间里可以存在的配置”和“已经满足生成条件的配置”两种职责；
- 角色 `isValid` 实际来源于原生签名验证，却被多人共享层误当作“角色是否合法”的准入条件，从而阻止未带官方签名但可被单人 Arena 正常使用的自定义角色；
- multiplayer contract 单独设置 `10` 个角色、`10` 个辅助情景、`10` 个素材，而真实 Hosted Arena runtime 分别已有 `32` 个角色和 `256` 个参考项的资源 sanity budget；
- 创建房间的前端捕获多类异常后统一显示“当前竞技场配置无法安全共享，请检查角色、版本与数量限制”，导致用户无法知道具体条件、对象和修正方法；
- 多人 UI 仍直接暴露 `Proposal`、`typed diff`、`BASE/CURRENT/PROPOSED`、`revision`、`incarnation`、`host-local`、`working copy` 等开发术语；
- product parity 已覆盖核心 generation semantics，但尚缺一个更强的默认规则：**原始多人规格没有明确提出差异的地方，多人 Arena 应默认继承单人 Arena 的产品能力、语义、限制、默认值、文案和演进，而不是另起一套。**

本修订的目标不是“尽量少校验”，而是：

> **只在真正需要的阶段执行真正需要的门禁；安全、权限、分布式一致性和资源硬边界继续 fail closed，但生成就绪条件不得阻止房间存在，来源标签不得冒充格式有效性，历史实现数字不得自动升级为产品限制。**

## 3. 核心不变量

### INV-GATE-001：默认继承单人 Arena

除非多人上位规格或后续 accepted amendment **明确声明例外**，多人 Arena 默认与单人 Arena 保持一致，至少包括：

- 可使用的角色类型与内容格式；
- 战斗模式、情景、辅助情景、素材、队伍、引导、故事长度、语言等生成语义；
- 历战、当前状态、叙事历史等功能的用户可感知语义；
- 数据卡选择与预设能力；
- 默认值、输入范围与用户侧容量规则；
- 战报和结果 presentation；
- 本地化、可访问性和错误处理；
- 后续单人 Arena 新增/调整的 generation semantic 或产品能力。

“多人没有实现”不是合法例外理由。合法例外至少应属于以下一类，并有文档与测试：

1. `security/privacy`：例如 member 不得读取 host-local/private full payload；
2. `authorization/authority`：例如只有 host 可以开始生成、发布房间配置；
3. `distributed-consistency`：例如 exact version、revision/epoch、single-producer；
4. `resource/concurrency`：例如房间成员数、wire frame、待处理提案数量；
5. `explicit-product-non-goal`：上位规格明确冻结为非目标。

任何例外都必须满足：**理由明确、范围最窄、可测试、用户可理解；不能因为实现方便而扩大。**

### INV-GATE-002：房间存在条件与生成就绪条件分离

创建/加入房间不要求 Arena 已经能够立即开始生成。

以下状态都必须允许房间存在：

- 0 个参战角色；
- 用户打算先建房再选角色/情景/素材；
- 当前 host 本地编辑尚未发布；
- 当前配置仍有 generation-only 待处理项。

“至少 1 个参战角色”“情景模式所需主情景已存在”“随机占位符已 materialize”“exact ref 未 stale”等属于 **Generation Readiness**，不能作为 **Room Lifecycle** 的前置条件。

### INV-GATE-003：可共享不等于可生成

`ArenaRoomSharedConfig` 的 schema 应表达“可以安全存在于 Room authority 中的共享语义”，而不是强制表达“一定已经能开始生成”。

优先采用：

- 一个 draft-compatible `ArenaRoomSharedConfig`；
- 独立的 generation readiness evaluator / preflight；

而不是复制两套高度重复的 wire config schema。

### INV-GATE-004：来源可信度不得冒充内容有效性

必须区分至少三个概念：

- **结构/语义有效性**：内容是否满足 Arena 当前可接受的角色/情景/素材格式与生成兼容规则；
- **来源/原生签名验证**：是否具有项目自己的 HMAC/原生签名；
- **多人可物化性**：能否以 online exact ref、server-known preset 或 host-local payload + digest 安全进入权威生成。

原生签名可以用于原生徽标、可信来源、严格排位等明确功能，但不得作为普通 Arena 多人房间使用自定义角色的默认准入门槛。

当前 `combatant.isValid` 来源于 `/api/verify-origin -> verifySignature`，却在 `apps/web/lib/arena-room/shared-config.ts` 中被用作多人角色准入门禁；该语义必须整改。

### INV-GATE-005：限制只有一个产品权威来源

同一产品语义不得出现“单人一套、Hosted runtime 一套、Multiplayer contract 再一套”且无例外说明的数字。

对于与真实生成资源直接相关的限制：

- multiplayer 应继承 canonical Arena/runtime capability；
- contract 可为 wire 安全做额外 byte/frame ceiling，但不能随意设置更低的产品数量限制；
- 如需额外 multiplayer count ceiling，必须给出 worst-case serialized size / CPU / Redis / fan-out 等证据，并取满足要求的最小限制。

### INV-GATE-006：用户错误必须具体、可行动、可本地化

禁止继续使用 catch-all 用户文案掩盖不同失败原因。

每个用户可修复问题至少应说明：

1. **什么操作被阻止**；
2. **哪个对象/条件有问题**；
3. **当前值或状态**；
4. **允许值/期望状态**（若适用）；
5. **用户可以怎么修正**。

安全敏感的内部原因、调用栈、SQL/Redis key、secret、私有对象存在性等不应暴露给用户；它们应进入安全日志或受控技术诊断。

### INV-GATE-007：技术术语不得无必要暴露在普通用户界面

代码、协议、日志和开发文档可以继续使用 `Proposal`、`revision`、`expectedBase`、`atomicGroupId`、`host-local` 等英文技术名。

普通用户 UI 必须优先使用中文产品语言；技术 ID/错误码可放在“技术详情/诊断信息”中，不作为主文案。

## 4. 门禁分层模型

实现必须把至少以下门禁区分开，并避免一个 builder/schema/catch 同时承担全部责任。

### Gate A：Room Lifecycle / 房间生命周期

用于：创建、加入、离开、关闭、presence。

应检查：

- 登录/身份；
- 房间标题、visibility 等 room metadata；
- 创建预算/rate limit/incarnation fence；
- 房间是否开放；
- 加入时房间人数上限；
- membership/host/member authority。

**不得检查：**

- 是否至少有 1 个角色；
- 当前角色是否原生签名；
- scenario 是否已经选好；
- generation prompt 是否超预算；
- provider 是否已经配置；
- random placeholder 是否已经具体化。

### Gate B：Room Shareability / 房间配置可共享性

用于：初始 seed（若有）、host 发布/更新房间配置、member 同步配置。

应检查：

- allowlist projection；
- secret/private payload 不进入 Room；
- stable key / exact ref / version token；
- host-local 只暴露 stub + digest；
- schema 和引用关系；
- wire frame / snapshot byte ceiling；
- canonical product capacity ceiling。

**不得检查 generation-only completeness。** 例如 0 个 combatant 的 Shared Config 应合法。

### Gate C：Collaboration / 提案协作

用于：成员建立草稿、提交提案、房主审阅/接受/拒绝、撤回。

应检查：

- capability 与权限；
- typed changes；
- base/precondition；
- stale/conflict；
- dependsOn / atomic group；
- proposal byte/change/pending limits；
- member 不得通过提案提交本地/私有 full payload。

该层的协作限额属于多人特有资源边界，可以与单人不同，但错误码必须具体区分。

### Gate D：Generation Readiness / 生成就绪

仅在房主尝试开始多人生成时执行。

至少检查：

- 至少 1 个已解析的实际参战角色；
- 所有参战角色满足与单人 Arena 一致的生成兼容规则；
- unresolved random placeholder 已按权威规则 materialize，或明确提示先生成具体角色；
- mode-specific 必要输入已具备，例如情景模式主情景；
- online refs exact version / permission / approval 状态仍有效；
- host-local payload 存在、kind/type/digest 匹配；
- host working copy 与 Room authority reconciliation 已完成；
- 与单人 Arena 相同的历战/当前状态/叙事历史读取逻辑可以 materialize；
- 当前 Room Shared Config 对应的 generation semantic 完整。

### Gate E：Runtime Resource / 执行资源

在 materialization 后、provider execution 前执行。

应检查：

- request/body byte budget；
- combatant/reference/adjudication sanity budget；
- estimated prompt/token funding budget；
- provider/channel 能力；
- output ceiling；
- single-producer/idempotency reservation。

这些预算应复用真实 Arena/Hosted runtime 的 canonical budget，不应在多人层再造“看起来安全”的低数字。

### Gate F：Result/Persistence Action / 结果操作权限

用于生成后的保存、角色更新、redo/manual apply 等动作。

- presentation 尽量与单人一致；
- host/member 权限差异在 action capability 层处理；
- member 不因看到结果而获得写回 host/private card 的权限。

## 5. 创建房间的目标语义

### 5.1 0 角色必须可创建房间

当前 `ArenaRoomSharedConfigSchema` 使用 `combatants.min(1)`，导致创建房间必须先具备角色。应改为 draft-compatible：

- Room Shared Config 允许 `combatants=[]`；
- `>=1` 移到 Generation Readiness；
- 空房间成员仍可同步配置并从既有 Arena UI 逐步添加角色。

### 5.2 创建房间不得被当前本地配置的 generation-only 问题阻断

推荐行为：

1. 先通过 Gate A 创建房间；
2. 若当前 host Arena 配置通过 Gate B，则作为初始 Room config seed 或紧接一次显式/可恢复 publish；
3. 若当前本地配置不能安全投影，**房间仍创建成功**，Room 使用 canonical empty/draft config；
4. UI 明确提示“房间已创建，但当前本地配置尚未同步”，并列出具体 Gate B 问题；
5. 修正后由 host 点击“更新房间配置”。

不得静默丢弃不支持内容后让用户误以为已经同步。

实现可以在不破坏现有 create idempotency/unknown-result recovery 的前提下选择“create 携带可选 seed”或“create 后 publish”，但产品语义必须满足上述原则。

## 6. 非原生、自定义和兼容角色

### 6.1 默认规则

普通 Arena 多人模式必须允许单人 Arena 已允许并可安全 materialize 的自定义角色，无论其是否具有项目原生签名。

多人角色来源可以是：

- online DataCard exact ref；
- server-known preset；
- host-local 自定义 JSON / 粘贴内容，经 Arena 现有解析/校验后以 stub + request-scoped payload 进入多人生成。

### 6.2 `isValid` 语义整改

当前代码：

- `fileParser/useBattleActions` 将 `verifyOrigin()` 结果写入 `isValid`；
- `/api/verify-origin` 实际执行 `verifySignature()`；
- multiplayer `normalizeCombatant()` 又以 `!combatant.isValid` 直接拒绝。

这使“没有原生签名”错误地等同于“无效角色”。

整改要求：

- 不再以原生签名字段决定普通多人可用性；
- 若保留 `isValid` 历史字段，必须停止在新多人门禁中赋予“schema valid”语义；
- 优先逐步拆成清晰状态，例如 `originVerified/nativeSigned`、`validation/compatibility`、`multiplayerMaterializable`；
- 不要求为了本轮一次性全仓重命名而制造大范围风险，但新增代码不得继续混用。

### 6.3 真正应阻止生成的角色

只有在与单人 Arena 的真实兼容规则或多人 materialization 安全边界冲突时才阻止，例如：

- 内容无法被 Arena 角色 validator/compatibility layer 识别；
- payload 不是可安全 canonicalize 的 JSON value；
- host-local stub 类型与实际 payload 推断类型不一致；
- online/preset ref 已 stale 或不可读；
- 完整 host-local payload 已丢失或 digest 不匹配。

报错必须指出具体角色和修正办法，而不是“非原生角色不可用”。

## 7. 容量与资源上限调整

### 7.1 角色

当前事实：

- 单人 Arena Web `MAX_COMBATANTS = null`，UI 不自设固定角色数；
- Hosted Arena runtime `ARENA_RESOURCE_BUDGET.maxCombatants = 32`；
- Multiplayer contract `MAX_COMBATANTS = 10`。

本修订冻结：

> **多人不得继续保留无独立资源证据的 10 人角色上限。当前目标上限与真实 Hosted Arena runtime 对齐为 32；未来 runtime canonical capability 改变时，多人默认同步改变，除非有明确 multiplayer-specific exception。**

具体常量放置位置由实现阶段按依赖边界决定；不得为了共享常量制造 package 反向依赖。可放入 dependency-neutral domain/config package，或由 contract/runtime 分别从同一生成源派生并有 equality test。

### 7.2 辅助情景与素材

当前事实：

- Multiplayer contract 各自固定 `10`；
- Hosted Arena runtime 对 `auxScenarios + materials + questionnaires + narrativeHistory` 使用 `maxReferenceItemsSanity = 256` 的累计 sanity budget；
- Room control/snapshot 另有 `64 KiB` wire frame ceiling。

本修订冻结：

> **删除“辅助情景最多 10 / 素材最多 10”这种无独立证据的多人专属产品限制。优先使用与真实 Arena 一致的累计 reference budget，并继续受实际序列化 frame byte ceiling 约束。**

若 256 个 worst-case room ref/stub 无法落入 64 KiB frame：

- byte/frame gate 本身可以成为有效限制；
- 如确需额外 count ceiling，应以 worst-case/高分位 serialization 测试或性能证据推导；
- 取满足 wire/CPU/Redis/fan-out 要求的最小限制；
- 不允许重新随意写一个 10。

当 questionnaire/lore 以后进入 Shared Config 时，应加入同一个 canonical reference budget，而不是再创建第四套数量上限。

### 7.3 应保留的多人特有上限

以下限制有明确协作/协议理由，本修订不要求移除：

- `MAX_ROOM_MEMBERS = 8`；
- 每成员待处理提案数；
- 每提案 change 数；
- proposal/control/story/generation bridge frame byte ceilings；
- room lifecycle/create rate/incarnation fence；
- bounded directory pagination；
- terminal/proposal/member history retention ceiling。

但每一种上限必须有独立错误码。例如“房间人数已满”和“待处理提案已满”不得共享 `member-limit-reached` 这类含混原因。

## 8. 叙事历史等未特别规定能力的默认一致性

### 8.1 原则

多人原始规格没有明确要求差异的 Arena 能力，默认从单人 Arena 继承。不能因为多人 transport 尚未建模就静默降级。

对每项能力应问：

1. 单人 Arena 的用户可感知语义是什么？
2. 哪些状态必须共享才能维持同一语义？
3. 哪些正文/凭据/本地记录因隐私或 authority 必须保持本地？
4. 多人只需要同步“选择/设置”，还是需要同步“完整数据”？

### 8.2 叙事历史

叙事历史属于典型例子：

- **用户可感知的读取/写入能力、默认值、limit/unlimited 语义应与单人 Arena 一致；**
- 叙事历史正文是本地/私有数据时，不要求为了“产品一致”而广播给其他成员；
- host 多人 generation 需要读取历史时，优先复用单人 Arena 的读取、过滤、限额和 materialization 语义，在 host runtime/request scope 注入；
- Room Shared Config 可以只共享安全的 read/write/limit 选择；
- 多人结果写入叙事历史的客户端行为必须审计并绑定单人语义测试，不能默认为“多人不支持”；
- 如确需 host-only/member-local 等差异，应在 parity matrix 中记录明确 privacy/authority exception。

同样原则适用于：历战、当前状态、问卷/Lore、裁判事件、语言、队伍顺序、角色顺序、素材顺序、未来新增 Arena generation semantic。

## 9. 错误模型

### 9.1 稳定机器错误与用户文案分离

推荐引入或收敛为等价结构：

```ts
type ArenaGate =
  | 'room-lifecycle'
  | 'room-shareability'
  | 'collaboration'
  | 'generation-readiness'
  | 'runtime-resource'
  | 'result-action';

type ArenaGateIssue = {
  code: string;                 // 稳定、机器可读；业务逻辑只解析 code
  gate: ArenaGate;
  severity: 'blocking' | 'warning';
  target?: {
    kind: 'room' | 'combatant' | 'scenario' | 'material' | 'proposal' | 'reference';
    key?: string;
    displayName?: string;       // 仅允许安全展示的名称
  };
  params?: Record<string, string | number | boolean | null>;
  remediation?: string;         // 或本地化 message key
  technicalId?: string;        // 可选，供“技术详情”/支持定位
};
```

HTTP 层可以映射到 RFC 9457 Problem Details 或等价稳定结构；WSS/control path 可复用同一 domain code taxonomy。

客户端不得解析 `message/detail` 决定业务分支。

### 9.2 用户文案要求

示例：

- `GENERATION_COMBATANTS_EMPTY`
  - “还没有参战角色。请至少添加 1 位角色后再开始生成。”
  - 这是 generation readiness，不阻止建房。
- `GENERATION_COMBATANT_LIMIT`
  - “当前有 33 位参战角色，最多支持 32 位。请移除至少 1 位后再开始。”
- `HOST_LOCAL_PAYLOAD_MISSING`
  - “角色「星野」来自房主本地文件，但当前页面已无法取得完整内容。请房主重新载入角色或更新房间配置。”
- `REFERENCE_STALE`
  - “数据卡「X」在加入房间配置后已更新。请重新同步或重新选择该数据卡。”
- `RANDOM_COMBATANT_UNRESOLVED`
  - “随机角色尚未确定。请先生成具体角色后再开始。”
- `ROOM_MEMBER_LIMIT`
  - “房间已满（最多 8 人）。”
- `PROPOSAL_PENDING_LIMIT`
  - “你已有 8 个待处理提案。请先撤回一个，或等待房主处理后再提交。”

### 9.3 多错误展示

本地 preflight 已知多个可修复问题时，应一次列出所有安全、可行动的问题，而不是让用户反复点击才逐个发现。

每项错误应能定位到对应 Arena 区域/对象；条件允许时提供“去处理/定位”按钮。

### 9.4 安全信息边界

遵循：

- 用户文案具体到足以修正；
- 不暴露 secret、调用栈、内部路径、Redis/D1 key、SQL、私有卡存在性等；
- authorization failure 对无权用户保持必要的模糊度；
- 详细诊断进入服务端日志或显式“技术详情”，且技术详情仍不得包含 secret。

## 10. 用户术语与中文化

### 10.1 原则

用户界面应描述“用户正在做什么”，不是描述内部协议如何实现。

## 11. Canonical capability / gate registry

现有 `ARENA_PRODUCT_PARITY_COVERAGE` 应扩展或配套增加一份 machine-readable gate/capability registry，至少能回答：

```text
Arena capability / semantic / limit
-> single Arena behavior
-> room-host behavior
-> room-member/proposal behavior
-> create gate?
-> shareability gate?
-> generation gate?
-> runtime gate?
-> canonical limit source
-> multiplayer exception category/reason
-> user-facing error code
-> test id
```

必须做到：

- 新增单人 Arena generation semantic/limit 后，CI 能发现多人尚未分类；
- multiplayer-specific exception 没有 reason/test 时 fail；
- canonical limit 漂移（例如 runtime 32、contract 10）被测试发现；
- UI 不再把内部 error code 直接作为默认用户文案。

不要求一定创建新的 package；可以扩展现有 coverage registry，只要避免循环依赖和重复权威源。

## 13. 必测场景

### 13.1 房间生命周期

1. 0 个角色时创建房间成功；
2. 创建后 member 可加入并看到空 roster；
3. host 之后添加角色并更新房间配置；
4. 当前本地配置有 generation-only 问题时房间仍可创建；
5. 当前配置无法 share 时，房间创建成功但明确提示“尚未同步”及具体原因；
6. 房间已满时仅返回 `ROOM_MEMBER_LIMIT` 等明确错误。

### 13.2 自定义角色

1. 无原生签名、但通过单人 Arena 正常 validator 的本地角色可由 host 发布并生成；
2. online 非原生数据卡若满足正常 DataCard 规则可进入多人；
3. 原生签名状态不会改变普通多人生成 eligibility；
4. 真正格式无效/类型错配/digest mismatch 仍 fail closed；
5. 严格排位若另有 verified-only 规则，继续在严格排位自己的 gate 中执行。

### 13.3 数量与资源

1. 11~32 个角色不再因 multiplayer contract 的旧 10 上限失败；
2. 33 个角色在 canonical runtime/generation gate 给出明确 32 上限错误；
3. >10 个辅助情景/素材不再仅因旧 per-collection 10 被拒绝；
4. 累计 reference budget 和 64 KiB frame 各有边界测试；
5. 若 frame 比 count 更早触发，错误说明是“房间配置过大”，而不是伪装成任意数量限制。

### 13.4 错误 UX

至少验证以下错误不再合并成同一句：

- 空角色（只在 start 时）；
- 角色过多；
- ref 缺版本；
- stale ref；
- host-local payload 缺失；
- random placeholder 未解析；
- snapshot/frame too large；
- 房间人数上限；
- pending proposal 上限；
- 权限不足；
- provider/runtime budget。

WCAG 交互测试应确认：错误以文本描述、可被 assistive tech 感知、已知修正方式时提供建议。

### 13.5 文案

- 普通用户路径不再出现 Proposal、typed diff、BASE/CURRENT/PROPOSED、same-target conflict、revision、incarnation、host-local、working copy 等未解释技术词；
- 技术详情/日志仍可保留稳定英文 code；
- 测试不要绑定英文内部术语作为产品文案 contract。

### 13.6 默认一致性

建立 parity regression：

- 单人 Arena 新增 generation semantic / limit / history behavior 时，若多人没有 classification，测试失败；
- 叙事历史等现有能力明确记录 single / room-host / room-member 语义与必要 exception；
- 不允许 `deferred` 永久成为“不支持”的同义词；deferred 必须有 reason、owner/next condition 或明确 non-goal。

## 14. 外部设计指南

本修订参考以下通用标准/实践，但项目内部 domain contract 仍以本规格为准：

- RFC 9457, *Problem Details for HTTP APIs*：错误使用稳定、机器可读类型/结构；human-readable detail 应帮助纠正问题，客户端不应解析 detail 决定逻辑。
  - https://www.rfc-editor.org/rfc/rfc9457.html
- WCAG 2.2 SC 3.3.1 Error Identification：自动检测的输入错误应指出错误项并以文本描述。
  - https://www.w3.org/WAI/WCAG22/Understanding/error-identification
- WCAG 2.2 SC 3.3.3 Error Suggestion：已知修正方式时应给出建议，除非会破坏安全/目的。
  - https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html
- OWASP REST Security Cheat Sheet / Authorization Cheat Sheet：用户错误不要泄露内部技术和敏感信息；authorization 继续在服务器端 fail closed。
  - https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html
  - https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html

## 15. 非目标

本修订不要求：

- 放松身份验证、host/member authority；
- member 上传/粘贴本地 JSON 作为 Proposal；
- 把 host-local/private full payload 广播给成员；
- 取消 exact version/digest/ref stale 校验；
- 取消 wire/frame/token/body hard ceilings；
- 引入 CRDT/chat/host transfer；
- 为了解决一个字段命名问题强制一次性全仓重命名；
- 在本轮扩大 production infra 范围。

## 16. 完成定义

只有以下条件同时满足，本修订才可标记 `DONE`：

- 创建房间与 generation readiness 已分层；
- 0 角色建房成功；
- 普通自定义/非原生签名角色不再被多人层无理由拒绝；
- `isValid/native signature` 语义混用已切断；
- 角色上限与 canonical runtime 对齐，旧 10 被移除；
- aux/material 旧 10 被移除，改为 canonical reference + byte/frame budget；
- multiplayer-specific limits 都有明确理由、来源与独立错误码；
- catch-all “当前竞技场配置无法安全共享……”从主要产品路径移除；
- Proposal 等英文/内部术语从普通用户 UI 清理；
- 默认继承单人 Arena 的规则进入 machine-readable/test-bound parity gate；
- 叙事历史等未特别规定能力完成 parity 审计；
- targeted + package + workspace CI、`git diff --check`、相关真实 Room verifier 通过；
- 独立 architecture/security/product/UI/a11y review 无开放 Critical/Important finding；
- GMR-10Q exit audit 通过后，GMR-11 才恢复 `READY`。

GMR-10Q 的退出审计可以记录当时的 commit 或源码摘要作为历史证据，但 `READY` 不得用持续演进的全仓内容摘要作为永久
CI gate。后续回归由当前可执行行为测试、完整 CI 与真实 verifier 发现；精确的 production release 审查绑定属于 GMR-11。
可重复 READY 入口面向 clean checkout 的 CI/release 验证；它必须在完整验证后拒绝 tracked 工作树改写，因此从含有未提交
tracked 改动的本地开发工作树运行时预期失败。
