# MahoShojo-Generator 平台重整实施规格

状态：`accepted`
日期：2026-08-22
规格标识：`SPEC-platform-restructure-v1`

## 1. 规范语言

本文中的“必须 / MUST”“不得 / MUST NOT”“应 / SHOULD”“可以 / MAY”具有规范性，其解释遵循 RFC 2119 与 RFC 8174。

若实现需要违反 `MUST` 或 `MUST NOT`，必须先修改相关 ADR 与本规格。不得只通过 feature flag、PR 评论或运行时配置绕过。

## 2. 范围

本规格覆盖：

- pnpm Monorepo；
- Web、Admin、Hono API、Cloudflare Hosted DR、D1 Gateway、Arena Room Worker、Desktop、Mobile；
- Local-first / Direct-first AI；
- 自定义 Provider 与 Endpoint；
- 本地库、线上库和数据所有权；
- 原生签名、Strict、多人与服务器边界；
- GitHub Releases、自动更新和供应链；
- Admin 安全；
- 旧 PVP 去留门禁；
- Legacy 兼容边界。

## 3. 非目标

本规格不要求：

- 本轮下线 Legacy 登录；
- 本轮实现 Desktop/Mobile Hosted AI；
- 本轮实现本地库自动双向同步；
- 本轮确定 iOS 正式分发；
- 本轮删除旧 PVP；
- 本轮更换原生签名算法；
- 本轮一次性搬完全部目录并同时改变业务；
- 推翻已冻结的 Arena 多人协作 v1。

## 4. 仓库与依赖要求

### MONO-001 Workspace

根目录必须新增 `pnpm-workspace.yaml`，至少包含：

```yaml
packages:
  - apps/*
  - packages/*
```

迁移期间可以临时包含旧根应用，但最终 root package 只承担编排。

### MONO-002 应用边界

必须建立独立应用目录：

- `apps/web`
- `apps/admin`
- `apps/api`
- `apps/d1-gateway`
- `apps/arena-room`
- `apps/desktop`
- `apps/mobile`（可先只有 PoC/readme）

每个应用必须有自己的：

- `package.json` 或运行时 manifest；
- build/test/lint 命令；
- 环境变量说明；
- deployment/release 入口；
- health/readiness 定义（如适用）。

### MONO-003 禁止跨 APP 导入

任何 `apps/<a>` 不得通过路径别名或相对路径直接导入 `apps/<b>` 的内部源码。

共享代码必须进入 `packages/*` 或通过 API/协议交互。

### MONO-004 Package exports

共享 package 必须通过显式 `exports` 暴露公共 API。不得把 package 内部目录作为稳定 API 使用。

### MONO-005 依赖边界自动检查

CI 必须增加边界检查，至少发现：

- packages 导入 apps；
- client package 导入 server secret 模块；
- app 直接导入其他 app；
- `domain` 导入框架/runtime；
- 未声明的 package 深层导入。

实现方式可以是 ESLint、dependency-cruiser、自定义脚本或组合。

### MONO-006 行为分离

目录搬迁 PR 不得同时大规模重写业务。每一阶段必须先证明行为等价，再进入功能迁移。

### MONO-007 编排器

首期不得把 Turborepo/Nx 作为 Monorepo 成功的前置条件。若新增，必须有单独决策和 CI 数据。

### MONO-008 Arena Room 迁移

Arena 多人 v1 可以在 Monorepo 迁移前使用 `workers/arena-room` 或现有等价目录。

进入目标结构时：

- Worker/DO 部署进入独立 `apps/arena-room`；该独立性是运行时/部署边界，不得复制第二套 Arena 产品/UI；
- 共享 schema/投影/Proposal 进入 `packages/contracts` 或 `packages/multiplayer-core`；
- `apps/web` 调 Room 优先使用 Service Binding / typed RPC；
- `apps/api` / Hono 调 Room 使用 Arena Room ADR 定义的版本化 `GenerationBridge`，不得假定非 Worker 运行时拥有 Service Binding；
- 路径变化不得改变现有 v1 语义；
- 必须通过兼容夹具证明 DTO、事件、GenerationBridge 和 old/new peer version 未漂移。

### MONO-009 Hosted 双运行时 adapter

长期 Hosted DR 必须满足：

- `apps/api` / Hono 与 `apps/web` / Next/OpenNext DR adapter 调用同一 shared service/domain/contracts；
- `apps/api` 不得为了 DR 动态 import `apps/web/app/api/*` 或其他 app 内部源码；
- legacy root wrapper/动态 import 有删除门禁；经过 contract test 的 DR adapter 不因 legacy 删除而一并移除；
- DR capability/route manifest 显式声明长期双运行范围，不以 API 覆盖率为目标。

## 5. AI 执行要求

### AI-001 执行模式

统一使用：

```ts
type AiExecutionMode =
  | 'direct-local'
  | 'direct-remote'
  | 'hosted'
  | 'authoritative';
```

UI 不得用平台名代替执行语义。例如 Desktop 也可以请求 Hosted，Web 也可能使用 Direct。

### AI-002 APP 默认 Direct

Desktop/Mobile MVP 的 AI 默认实现必须为 Direct。Hosted 可以不存在。

Local-only 用户旅程必须在不登录、不调用项目域名的情况下完成：

1. 创建/导入卡；
2. 配置 Provider；
3. 调用 AI；
4. 保存本地；
5. 导出。

### AI-003 Catalog 不是 Allowlist

Provider Catalog 只用于自动填写和文档引导。用户必须可以不选 Catalog，显式填写自定义名称、adapter、base URL、model ID 和参数。

### AI-004 MVP Adapter

MVP 必须支持：

```text
openai-compatible + arbitrary user-selected baseUrl
```

Anthropic/Google adapter 可后续增加，但不得阻塞自定义 OpenAI-compatible Endpoint。

### AI-005 Native Direct Executor

Desktop/Mobile 的自定义 Endpoint 请求必须由 Native/Main 层执行，不得向 renderer 暴露通用 `fetchAny`。

Renderer 只可传：

- `providerProfileId`
- 标准化 generation request
- request ID / AbortSignal 等价物

秘密从 Secure Vault 在 Native/Main 层解析。

### AI-006 凭据隔离

Direct 请求必须满足：

- `credentials=omit` 等价语义；
- 不发送项目 Cookie；
- 不发送 Better Auth session；
- 不发送 Legacy `Authorization: Bearer <authkey>`；
- 不发送 activity token；
- 不发送 Cloudflare Access service token；
- 日志和错误不包含 API Key/secret header。

当前会自动附加项目 auth/activity headers 的 `generationApiFetch` 或等价客户端不得用于 Direct Endpoint。

### AI-007 Endpoint 来源

Provider Profile 只能由用户在设置页显式创建、修改或确认导入。

以下内容不得自动创建 Profile 或触发 Endpoint 请求：

- 数据卡；
- Prompt；
- 场景；
- Markdown/HTML；
- 多人消息；
- 在线卡 payload；
- 分享链接。

### AI-008 URL 与传输

Native Executor 必须：

- 使用标准 URL parser；
- 默认允许 HTTPS；
- 允许 loopback/localhost/私有网段 HTTP；
- 对公网 HTTP 要求用户逐 Profile 确认；
- 拒绝非 HTTP(S) scheme；
- 默认最多 3 次重定向；
- 跨 Origin 重定向不转发认证、Cookie 和 secret headers；
- 禁止覆盖 `Host`、`Content-Length`、`Connection` 等传输层 header；
- 按大小写不敏感语义处理 HTTP header 名；`publicHeaders` 与 `secretHeaderRefs` 各自内部及相互之间的 canonical 重名必须 fail closed，不定义覆盖优先级，也不得改写用户提供的 header casing；
- 每个 adapter 激活前必须显式定义 `apiKeyRef` credential placement；Executor 合并 adapter-managed credential、`publicHeaders` 与 `secretHeaderRefs` 得出的 effective headers 时，必须对 canonical 冲突 fail closed；该要求不授权实现根据 adapter 名猜测具体映射，也不要求在 placement 尚未定义时收紧 v1 Profile schema；
- 不提供全局忽略 TLS 校验开关。

### AI-009 取消与超时

Direct 执行必须支持用户主动取消。

Direct 执行不得强制继承 Hosted 的 300 秒 idle timeout。可以提供：

- 无 total timeout；
- 用户配置 idle/total timeout；
- 内存和输出落盘保护。

Hosted 继续由服务端预算控制。

### AI-010 输出不可信

所有模型输出，无论 Hosted 或 Direct，进入领域状态前都必须经过：

- schema 校验；
- 解析/修复；
- 大小限制；
- 危险字段过滤；
- 明确错误状态。

### AI-011 本地模型

Ollama、LM Studio 等本地 OpenAI-compatible 服务通过同一 Direct Profile 实现，不另建绕过安全检查的特殊调用路径。

### AI-012 多人中的 Provider

Arena 多人 v1 的 Room DTO、Proposal、事件和持久化不得包含 Provider Profile、API Key、secret header 或项目认证信息。

v1 权威生成继续使用服务器 Arena 生成链路。任何“房主 Direct 生成后广播”都属于未来非权威模式，必须另立 ADR。

## 6. Provider Profile 与秘密存储

### PROVIDER-001 Profile

非秘密配置必须持久化为版本化 Profile，至少包含：

```ts
type DirectProviderProfileV1 = {
  version: 1;
  id: string;
  name: string;
  adapter: 'openai-compatible' | 'anthropic' | 'google';
  baseUrl: string;
  modelId: string;
  apiKeyRef?: string;
  secretHeaderRefs?: Record<string, string>;
  publicHeaders?: Record<string, string>;
  generationDefaults?: Record<string, unknown>;
  transport?: {
    allowPublicHttp?: boolean;
    maxRedirects?: number;
  };
  createdAt: string;
  updatedAt: string;
};
```

### PROVIDER-002 Secret Vault

API Key 与 secret header 必须存入 Secure Vault：

- Tauri：Stronghold 或等价平台安全存储；
- Electron：OS-backed encryption/safeStorage 或等价实现；
- Mobile：Keychain/Keystore/Stronghold 或等价实现。

普通 SQLite、IndexedDB、localStorage、导出 JSON 和日志不得保存明文秘密。

### PROVIDER-003 导出

导出 Provider 配置时：

- 默认只导出非秘密字段；
- secret ref 不能解析成明文写入导出；
- 导入后要求用户重新填写秘密；
- 导入前显示 Endpoint 和 header 名称。

### PROVIDER-004 Profile 测试

`Test connection` 必须由用户主动触发，并显示实际目标 Origin、adapter 和模型。失败日志不得泄露秘密。

## 7. 本地库要求

### LIB-001 一等数据源

UI 和领域层必须把本地库作为正式 `CardRepository`，不得只实现为缓存、临时草稿或文件导出列表。

### LIB-002 Web 独立数据库

Web 本地库必须使用独立 IndexedDB，不能复用：

- AI session DB；
- public card cache；
- rank cache；
- localStorage。

### LIB-003 Web 持久化提示

Web 必须：

- 调用 `navigator.storage.persist()`；
- 读取 `navigator.storage.estimate()`；
- 展示是否获得 persistent storage；
- 提醒清除站点数据会删除本地库；
- 提供导出备份入口。

用户拒绝或浏览器不支持 persistent storage 时，本地库仍可使用，但 UI 必须显示风险。

### LIB-004 Installed APP 存储

Desktop/Mobile 使用 SQLite 保存结构化记录。大型附件可以使用文件系统，但必须：

- 限定在应用数据目录或用户显式选择的位置；
- 避免任意路径访问；
- 使用原子写入；
- 清理 orphan file；
- 在数据库记录 content digest。

### LIB-005 数据模型

本地卡记录必须至少具有：

- local ID；
- schema version；
- card type；
- card payload；
- content digest；
- provenance；
- optional cloud ref；
- created/updated timestamps；
- soft delete 或回收站语义。

### LIB-006 不占线上卡槽

本地保存、复制、编辑和删除不得检查或消耗线上卡槽。只有线上持久化 API 才执行 slot policy。

### LIB-007 显式复制

MVP 必须提供：

- 保存本地；
- 上传线上副本；
- 下载本地副本；
- 导入；
- 导出；
- 备份恢复。

MVP 不得声称本地与线上自动同步。

### LIB-008 上传重验

线上上传必须把本地数据当不可信输入，重新执行 schema、大小、权限、slot、内容策略、作者归一化、签名与幂等检查。

### LIB-009 Import 不触网

导入本地库不得因为导入内容中的 URL、provider、图片或脚本自动发起网络请求。任何外部资源获取必须由用户单独确认。

### LIB-010 备份不含秘密

本地库导出不得包含 API Key、session、authkey、私钥或生产凭据。

### LIB-011 迁移与恢复

本地 schema migration 必须：

- 有单调递增版本；
- 可在旧版本夹具上重复测试；
- 失败时不删除原库；
- Installed APP 在高风险迁移前创建可恢复备份；
- Web 至少保留导出恢复路径。

### LIB-012 多人投影

房主可以从本地库选择内容进入单人 Arena，但多人房间只允许按 Arena v1 规格生成安全投影或 stub。普通成员的 Proposal 不能直接携带本地完整 payload。
## 8. 原生、排位与多人权威

### AUTHORITY-001 签名服务器专属

`SIGNATURE_SECRET_KEY` 或未来私钥不得进入 Web bundle、Desktop/Mobile bundle、公开仓库或客户端更新资产。

### AUTHORITY-002 客户端声明无效

服务器不得根据客户端提交的 `isNative`、`trusted`、`official`、rating delta 或 winner 直接形成权威结果。

### AUTHORITY-003 存储与 provenance 分离

本地保存有效签名卡不得自动去除签名；编辑签名覆盖字段后必须显示签名失效。

- `official-signed` 与 `signature-invalid` provenance 必须保留非空 `signature`；legacy 有效签名可以没有 `signatureVersion` 或 `signatureKeyId`。
- `unsigned` provenance 不得携带 `signature`、`signatureVersion` 或 `signatureKeyId`。
- provenance schema 只验证记录结构，不得被视为服务器验签结果；服务器仍是签名有效性的最终权威。
- 本次 provenance 结构收紧不得改写或迁移 legacy `data.signature`。

### AUTHORITY-004 Strict 实体

Strict MVP 只接受服务器可解析的 online card ID 或 preset ID。纯 local ID 不能直接参加。

### AUTHORITY-005 Rating Event

Strict rating event 必须由服务器：

- 生成唯一/幂等 event；
- 重新读取 eligibility；
- 计算 winner slot；
- 原子应用或标记冲突；
- 保留 audit lineage。

### AUTHORITY-006 Multiplayer

多人房间状态、参与者权限、隐藏信息、Proposal、revision、投票、结算和恢复由服务器/DO 权威维护。客户端只能提交意图。

## 8.1 Hosted 运行时容灾要求

### DR-001 主执行面与灾备执行面

Hosted HTTP 默认由 `apps/api` / Hono HK 执行。`apps/web` / Cloudflare Next/OpenNext 只对显式 DR manifest 中的能力提供长期灾备 adapter。DR adapter 不得被描述为等待删除的 legacy 业务实现。

### DR-002 稳定逻辑入口

目标客户端不得把物理 Hono origin 作为唯一 Hosted API 入口。故障路由必须能够在不重新构建/发布客户端的情况下改变执行面。具体 Cloudflare 产品可替换，但切流控制面必须独立于待容灾的香港 Hono 实例。

### DR-003 显式 capability/route manifest

长期 DR 范围必须机器可读或可自动校验，并为每项能力记录：

- method/route 或 capability ID；
- safe/idempotency/replay class；
- 所需 secret；
- DatabaseProvider/外部依赖；
- contract test 与故障演练状态。

不要求所有 Hono API 都拥有 DR。未列入的能力在主执行面不可用时应明确 `503`/degraded。

### DR-004 同一业务核心

Hono/Next 两个 runtime 必须共享同一 service/domain/contracts。runtime adapter 只负责平台差异，不得复制 authentication/actor resolution、权限、结算、签名、生成或领域校验逻辑形成长期双实现。

### DR-005 数据权威与计算节点分离

- D1/DO/R2 按既有领域定义继续持有权威事实；
- Redis 只持有可重建/临时/允许损失状态；
- VPS 本地磁盘不得成为唯一用户资产、rating、settlement、audit 或其他 server-authoritative truth；
- 计算节点切换不得改变数据所有权或信任语义。

### DR-006 Redis non-authority

所有 Redis-only 状态必须满足：Redis 全量清空后可从权威状态恢复正确业务结果，或该状态本身被明确允许丢失。Redis lease/idempotency 不得替代 D1 unique/CAS、DO 原子状态转换或权威幂等记录。Redis outage 不得把 cache 提升成 write authority。

### DR-007 DatabaseProvider 故障隔离与一致性

Hono 正常路径可以使用 D1 Gateway；Cloudflare DR 在平台允许时应优先使用独立 D1 binding/Sessions，避免再次依赖与 Hono 相同的 Gateway transport。

两个 provider 必须实现同一业务一致性 contract。启用 D1 read replication 时：

- replica-ok 读取可以从 `first-unconstrained` 开始；
- 权威写、写后读和需要最新状态的命令使用 `first-primary` 或等价强语义；
- bookmark 必须在一致性 scope 中传播，不能因 runtime failover 丢失已承诺的 sequential consistency/read-your-own-writes。

### DR-008 Failover 与重放

- safe/read 请求可以在健康状态变化后自动选择 DR；
- 写命令只有在具有稳定 operation/request ID 且权威层能证明重复提交不会产生第二次业务效果时，才可以自动重试/跨 runtime 重放；
- generation/stream/settlement 等昂贵或非幂等操作，一旦请求可能已经到达主执行面、Provider 已开始计费或副作用可能发生，不得仅因连接失败透明地把整个请求发往 DR。

生成恢复应使用稳定 `generationRequestId`/attempt、状态查询和最终结果恢复。任何底层 Load Balancer/Proxy 的 request-level retry 必须服从本条，而不是覆盖业务幂等规则。

### DR-009 语义等价与 fail closed

DR 可以使用更紧的并发、quota、provider allowlist 或输出预算，并通过 `429`/`503` 保护资源；但不得静默改变签名、Strict、rating、审核、权限、幂等或数据所有权语义。

某项能力缺少必要 secret/platform capability 时必须 fail closed，不得返回伪装成原语义的降级成功；认证失败不得静默降级为匿名成功。

### DR-010 Secret 最小复制

DR 只获得其 manifest capability 所需的最小 secret。不得因为“备用”而把 `apps/api` 的全部生产 secret 复制给 `apps/web`。DR secret 必须拥有独立 deployment permission、rotation/audit；secret 缺失必须反映在 capability/readiness 中。

### DR-011 D1 共同故障域

本轮不要求第二套跨云 SQL authority 或双写。D1 不可用时，需要线上权威状态的 Hono/DR 能力显式失败或降级；不得提升 Redis/VPS 为 authority。Local/Direct 路径按本地优先 ADR 继续工作。

### DR-012 备份与恢复

必须维护 D1 point-in-time recovery 与长期导出 runbook，并定期验证恢复步骤。恢复演练不得直接对生产库执行破坏性 restore；使用受控副本/演练环境或等价安全流程验证。若未来恢复目标扩展到 Cloudflare 账号/供应商级灾难，应另行评估 off-account/off-provider 备份，不把同账号 R2 描述成完整跨供应商备份。

### DR-013 默认 active-passive

DR capability 默认采用 active-passive，不得在没有专项证明时把 Hono 与 Next 作为 active-active 权威/非幂等写节点。safe/read 或经过并发、幂等、quota 和一致性验证的能力可以另立配置。failback 只选择后续新请求，不得重放状态未知的旧 operation。

### DR-014 Standby freshness 与版本兼容

DR adapter 必须随 shared core 持续构建和 contract test，并保持可接管的已验证 artifact/runtime。生产 schema/contract 变更必须支持短暂 Hono/DR version skew，按 backward-compatible expand -> runtime rollout -> contract/destructive cleanup 执行。

任何会使当前 DR 无法读取生产 schema、解析当前 client request 或维持认证/权威语义的变更，都必须在进入生产前被兼容门禁阻止。

## 9. Arena 多人协作要求

本节补充而不取代 `docs/specs/2026-08-21_arena-multiplayer-v1-spec.md`。

### MULTI-001 Shared Config 白名单

Room Shared Config 必须由显式白名单构建，不得序列化整个 Arena store。

### MULTI-002 敏感信息排除

Room DTO、事件、日志和持久化不得包含：

- `userProviderConfig`；
- API Key 或 secret header；
- Better Auth/Legacy credential；
- 完整 host-local 私有卡；
- 战报运行时内部状态；
- 不必要的 Prompt/输出正文副本。

authoritative generation 确有需要时，host-local generation payload 或现有 Hosted Provider credential 可以按既有 generation contract **直接**进入 generation service，但不得经 Room plane 中转、持久化或广播。

### MULTI-003 Host-local Stub

host-local 内容只能生成规格允许的 stub。普通成员不能通过 Proposal 获取完整 payload 或把本地任意 JSON 注入房间。

### MULTI-004 Proposal

Proposal 必须是版本化 typed semantic changes，并包含 base revision。每个 change 还必须携带 typed `expectedBase` / precondition，使 DO 能在不保存无限 revision 历史的情况下验证 BASE。

服务端/DO 必须重新验证：

- schema；
- capability；
- size/count；
- dependency/atomic group；
- expectedBase vs current semantic value；
- online card ref eligibility 与版本。

### MULTI-005 Revision 与 Snapshot

接受 Proposal 后，selected changes、dependency/atomic group、Shared Config、Proposal state 与 room revision 必须在单房间原子状态转换中提交。

开始生成时必须冻结不可变 shared config、participant snapshot、revision、`collaborativeInfluence`、online ref versions 与 snapshot digest。

### MULTI-006 唯一生成与幂等

v1 只有房主能发起权威生成，且现有 Arena AI 链路只执行一次。普通成员不得触发额外生成、redo 或 host-only 写操作。

一次开始意图必须具有稳定 `generationRequestId`。浏览器重试、API 重试和 bridge 重试不得创建第二个 generation；旧 generation attempt 的 terminal event 不得覆盖当前 attempt。

房主浏览器不得作为 AI stream -> Room 的唯一中继。generation service 接受任务后应直接向 Room 发布批量事件。

### MULTI-007 广播成本与恢复

AI stream delta 必须按时间或字节阈值批处理；不得每 token 调用 Worker/DO。

`story.delta` 是临时低延迟展示事件，不要求逐 chunk 持久化。replay gap 无法恢复时客户端必须能回到 snapshot/resync，最终完整战报从 authoritative generation storage / R2 获取。

### MULTI-008 Hibernation

Room Worker 必须使用 Durable Object Hibernation WebSocket API，并禁止：

- per-room `setInterval`；
- 应用层高频 ping；
- 固定频率 polling fallback；
- presence/story chunk 高频写 D1。

WebSocket attachment 只保存恢复连接所需的最小 connection metadata；durable room state 不得只存在内存。

### MULTI-009 Cleanup 与 Alarm

统一 `destroyRoom(reason)` 必须幂等；alarm 执行前重新读取当前状态，避免旧 alarm 删除活跃房间。

每个 DO 只有一个物理 alarm。多个 host-offline / room-idle / recovery deadline 必须存入 durable state，由统一 scheduler 设置最早 deadline；alarm 为 at-least-once，处理后重新计算下一个 deadline。

### MULTI-010 本地编辑无网络

普通成员同步后编辑 working copy 不应产生网络请求；只有 Proposal 提交、显式同步、房间操作和生成广播联网。

### MULTI-011 Monorepo 兼容

迁移到 `apps/arena-room` 与 `packages/multiplayer-core` 时，必须使用现有多人规格夹具进行契约回归。

### MULTI-012 独立部署与调用路径

Arena 多人产品/UI 保持现有 `/arena`，但 realtime coordination 必须独立部署为 `apps/arena-room`。

- Worker caller -> Room：Service Binding / typed RPC；
- Hono generation -> Room：generation-scoped authenticated `GenerationBridge`；
- bridge batch 必须带 generation attempt 与单调 batch sequence，并可幂等去重；
- 不得把 bridge secret/token 下发到普通浏览器或 Room snapshot。

### MULTI-013 版本化引用

Room/Proposal 中的 online DataCard ref 必须包含服务器可验证 `versionToken` 或等价不可歧义版本标识。对象版本/权限变化时必须显式 stale/reference-changed，不得静默解析到最新版而保持 room revision 不变。

### MULTI-014 Reconnect Cursor

Room control reconnect 必须使用持久化 `roomEpoch + control seq` 或等价 durable cursor。Hibernation 后不得依赖 constructor 前的纯内存 seq。

Story stream 使用独立 `generationId + chunkSeq` 或等价 cursor，不要求和 control replay 共用无限事件日志。

### MULTI-015 D1 Directory

D1 room directory 只是跨房间派生索引；ArenaRoom DO 是单房间 lifecycle 真相源。

- join 最终由 DO 验证；
- closed DO 不得被残留 D1 row 复活；
- directory create/update/delete 幂等、可重试；
- 应有低频 orphan reconciliation，不得用高频全表 polling 维持一致。

### MULTI-016 Membership / Connection

Membership 以 user 为单位，presence 以 connection 为单位。多标签页/多设备不能重复计成员。

socket close 只改变 presence；user leave、host explicit leave/close、kick 都必须是显式授权 command。kick 后旧 ticket 重连仍需由 DO membership 拒绝。

### MULTI-017 WebSocket 安全与大小

浏览器 handshake 必须使用显式 Origin allowlist；非浏览器 Installed Client 不得把 Origin 当信任根，统一依赖短期 room ticket、membership 和 message-level authorization。

所有 WS 消息必须有 schema、capability、byte limit、rate limit 与 backpressure budget。对外 `roomId` 必须是服务端生成的高熵 opaque id，不直接暴露 Durable Object internal id。

### MULTI-018 Wire Compatibility

`apps/web`、`apps/arena-room`、`apps/api` 独立部署时必须定义：

- protocol version；
- room snapshot schema version；
- GenerationBridge version；
- supported peer versions。

发布遵循 expand -> caller rollout -> contract。DO storage migration 独立门禁；普通 Worker rollback 不得被描述成自动回滚 DO/D1 state。

## 10. Admin 要求

### ADMIN-001 独立应用

Admin 必须独立构建部署，不能只把页面隐藏在公共 Web 导航中。

### ADMIN-002 Access 与 Origin 防护

Admin 生产入口必须使用 Cloudflare Access。

- 若 `apps/admin` 的 origin 是自托管/VPS，必须使用 Cloudflare Tunnel 或等价的 direct-origin bypass 防护；
- 若 Worker 本身就是 origin，可以直接使用 Worker/hostname Access，不得为了形式一致强制增加 Tunnel；
- 任何额外网络入口都必须有等价访问控制，不能绕过 Access/RBAC。

### ADMIN-003 Origin JWT / Access identity

自托管 origin 必须验证 `Cf-Access-Jwt-Assertion`：

- signature/JWKS；
- issuer；
- audience；
- expiry；
- 必需 identity claim。

不得只检查 header 是否存在。

### ADMIN-004 应用层 RBAC

Access 通过后仍必须映射内部管理员身份和 capability。建议至少拆分：

- `users.read`
- `users.write`
- `content.review`
- `reports.decide`
- `ratings.reset`
- `multiplayer.recover`
- `data.maintenance`
- `system.config`
- `exports.read`

### ADMIN-005 高风险操作

批量、删除、封禁、重置、维护、导出与配置操作必须具备：

- 明确 confirmation；
- reason；
- idempotency key；
- expected version/乐观锁；
- audit log；
- 最小权限；
- 必要时 fresh/step-up auth。

### ADMIN-006 无浏览器数据库密钥

Admin renderer 不得获得 D1 管理 API Token、Gateway HMAC secret 或服务器数据库凭据。

### ADMIN-007 分支迁移

`feat/admin` 的 handler 在移植前逐个分类为 read-only、mutating、destructive、export 或 maintenance。每个 mutating/destructive handler 必须先补授权与测试，才能上线。

## 11. 资源预算要求

### RESOURCE-001 Hosted Budget

Hosted/authoritative 服务必须有显式预算：

- per-user/IP concurrency；
- rate/burst；
- daily quota；
- max output；
- idle/total/provider timeout；
- memory/socket limit；
- DB/R2/DO limit。

### RESOURCE-002 Direct 不套项目额度

Direct 不得请求项目服务器“代转”自定义 Endpoint，也不得计入项目 Hosted quota。

### RESOURCE-003 可观察性

服务器必须记录足以分析成本但避免收集无必要内容的指标：

- execution mode；
- endpoint class（项目/第三方/localhost，不记录 API Key）；
- duration；
- output size；
- abort/timeout；
- server CPU/wall；
- D1/R2/DO usage；
- error class。

Direct 本地内容 telemetry 默认关闭或最小化，不上传 Prompt/输出正文。

### RESOURCE-004 多人资源

Arena Room 必须记录房间、连接、Proposal、广播、清理和 reconnect 的聚合指标，但不得记录 API Key、完整本地卡或不必要正文。

### RESOURCE-005 Hono Node 容量观测

Hono 主执行面至少必须采集或可导出：

- process CPU、RSS、heap used/limit；
- event-loop utilization 与 delay；
- active HTTP requests、active streams、socket/long connection；
- AI upstream active、TTFB、duration、abort/timeout；
- D1 round trips、latency、rows read/written、error；
- Redis latency、error、hit/miss、memory/eviction；
- runtime origin、DR selection 与 failover reason。

阈值在生产基线后设定；不得只以 CPU 单指标判定 readiness。

### RESOURCE-006 DR 保护预算

DR 可以比主执行面采用更严格资源预算。容量不足时优先 `429`/`503`、缩小 provider/capability，而不是绕过限流、降低权威检查或重复执行生成。

## 12. 发行与秘密要求

### RELEASE-001 Tag 驱动

正式 Desktop/Android Release 必须从版本 tag 构建，不从任意 branch push 直接发布。

### RELEASE-002 可验证元数据

Release 必须记录：

- source commit；
- version；
- target/arch；
- build workflow；
- checksums；
- updater signatures（Desktop）；
- artifact attestation；
- release notes。

### RELEASE-003 Desktop Updater

Desktop updater 必须验证签名，不能提供关闭验证的生产配置。

Public key 可以公开；private key 必须：

- 存在受保护发布环境；
- 有离线备份；
- 不出现在日志；
- 不提供给普通 PR workflow；
- 有丢失/泄漏应急流程。

### RELEASE-004 Android Signing

Android APK 必须使用稳定 signing key。CI 只在受保护 tag/release 环境读取 key。

### RELEASE-005 Mobile Update 边界

不得在文档或 UI 中宣称 Tauri Desktop Updater 自动覆盖 Android/iOS。Android 更新使用平台安装流程；iOS 独立设计。

### RELEASE-006 Supply Chain

Release workflow 应：

- 最小化 `GITHUB_TOKEN` permissions；
- 第三方 Action pin 到完整 SHA；
- 生成 artifact attestation；
- 生成 checksum；
- 使用 draft release 汇集全部资产后再发布；
- 启用 immutable release 时不得替换已发布资产。

### SECRET-001 公开仓库

仓库中只允许变量名、占位值、公钥、非秘密配置和测试用假凭据。

### SECRET-002 扫描

必须启用或增加：

- GitHub secret scanning/push protection（可用时）；
- CI secret scan；
- `.env`、key、keystore、certificate ignore/deny rules；
- release log redaction。

### SECRET-003 部署隔离

Web、Admin、API、D1 Gateway、Arena Room、Release 使用独立最小权限秘密。不得以一个全能 `.env.production` 供所有应用复用。

## 13. Legacy 兼容

### COMPAT-001 行为冻结

本轮不得：

- 移除 Legacy 登录入口；
- 改变 authkey 的用户语义；
- 强制 Legacy 用户迁移；
- 把旧密钥批量转换成密码；
- 用本轮 Monorepo PR 顺带更换 Hono 鉴权。

### COMPAT-002 等价搬迁

如果文件路径变化，必须用回归测试证明 Legacy 与 Better Auth 行为等价。

### COMPAT-003 后续独立决策

Auth 收口必须有独立指标、ADR、迁移窗口和回滚。

## 14. 旧 PVP 决策门禁

本节中的 PVP 指旧房间制卡组对战，不是 Arena 多人协作 v1。

### PVP-001 先测量

删除或冻结 PVP 前必须形成至少覆盖连续 90 天的报告，包含：

- overall MAU；
- PVP MAU；
- rooms created/started/completed；
- completion rate；
- unique repeat users；
- 30-day repeat；
- AI cost per completed match；
- D1 reads/writes；
- incidents/support burden；
- 与 Arena 多人与其他玩法的复用价值。

### PVP-002 下线顺序

若决定下线：

1. feature flag 禁止新房；
2. 移除导航和入口；
3. 保留历史只读；
4. 导出/归档；
5. 抽取 `multiplayer-core`；
6. 删除 runtime/API；
7. 经过稳定发布周期后再清理 schema。

### PVP-003 不提前 DROP

不得在使用报告和归档完成前删除生产表或不可逆迁移。

## 15. Mobile PoC 门禁

Mobile runtime ADR 前，Tauri Mobile 与 Capacitor PoC 必须使用同一验收清单：

1. 至少 10 个代表性页面；
2. Direct OpenAI-compatible stream；
3. cancel/retry；
4. arbitrary Endpoint Profile；
5. SQLite migration；
6. Secure Vault；
7. local library import/export；
8. file picker/share；
9. Android signed APK；
10. GitHub Actions build；
11. memory/startup/app size；
12. plugin maintenance and testability。

未通过任一安全必需项的候选不能作为默认 runtime。

## 16. 验收场景

### ACCEPT-001 零项目请求

在网络代理/测试拦截下完成本地创建、Direct 生成和本地保存，项目域名请求数必须为 0。

### ACCEPT-002 凭据不离设备

Direct API Key 不得出现在项目 API request、telemetry、log、crash report、export 或 SQLite plain text 中。

### ACCEPT-003 客户端不能伪造原生

修改客户端提交 `isNative=true` 或伪造签名时，服务器必须拒绝或标记非原生。

### ACCEPT-004 Local Slot

创建 1000 张本地卡不得改变线上 `slot_count` 或触发线上卡槽请求。

### ACCEPT-005 上传重验

本地卡上传时必须重新校验并产生明确 cloud ID；失败不得损坏本地副本。

### ACCEPT-006 Admin 绕过

绕开 Cloudflare Access 或使用错误 audience 的 JWT 访问 Admin Origin 必须失败。

### ACCEPT-007 Release

Desktop 更新包签名错误、缺失或版本回退时不得安装。

### ACCEPT-008 Legacy

结构迁移后现有 Legacy 与 Better Auth 登录回归测试必须通过。

### ACCEPT-009 Arena 多人敏感信息

Room snapshot、Proposal、DO storage、WebSocket event 和日志中不得出现 Provider API Key、完整 Profile 或 host-local 完整 payload。

### ACCEPT-010 Arena 多人单次生成

1 host + N members 的一次多人生成只能产生一次 AI generation；成员只消费广播结果。

### ACCEPT-011 Arena 多人低空闲成本

idle room 不得依赖固定轮询或应用层高频 ping，且 Hibernation、alarm cleanup 与 reconnect 测试通过。

### ACCEPT-012 Hono 主执行面故障

模拟 Hono 进程/主机不可达后，至少一条 DR eligible safe/read 路由无需重新发布客户端即可由 Cloudflare DR adapter 提供；响应/日志能够识别实际 runtime，且业务 contract 不漂移。

### ACCEPT-013 生成中途故障不重复

模拟 generation 请求已经到达 Hono 或上游 Provider 后连接中断，不得因为 failover 自动创建第二个 generation/Provider 调用；客户端应使用稳定 operation ID 查询/恢复状态或得到明确失败。

### ACCEPT-014 Redis 全量丢失

在测试环境清空/断开 Redis 后，账号、线上卡、rating、settlement、audit 等权威事实不得丢失或被缓存值改写；允许的 cache/presence/matchmaking/telemetry 按设计重建或降级。

### ACCEPT-015 D1 Gateway 故障隔离

模拟 D1 Gateway 失败时，Hono readiness/熔断按设计生效；至少一条适合 DR 的 Cloudflare 数据路径能够通过独立 D1 binding provider 工作，不依赖同一个 Gateway。

### ACCEPT-016 D1 故障不提升缓存

模拟 D1 不可用时，Redis/VPS local state 不得被提升为 authority；需要权威数据的写操作必须 fail closed，Local/Direct journey 仍符合既定本地优先语义。

### ACCEPT-017 DR 版本偏差

在测试中组合当前 Hono 与允许的 DR version skew / schema expand 状态，DR eligible capability 必须仍通过 public contract、auth actor resolution 和数据库读写语义；不兼容的 destructive schema cleanup 必须被 rollout 门禁阻止。

### ACCEPT-018 用户可感知行为契约

runtime、placement、transport、schema 或数据层迁移必须相对当前默认分支执行 user-visible contract audit，至少覆盖成功
wire、参数校验、错误信息、限流、timeout/abort、stream terminal、断线恢复、鉴权、持久化失败、DR unavailable 与用户设置。
有意变化必须有 accepted authority、兼容/迁移策略和显式差分 fixture；不得以“内部重构”为由把未登记的行为漂移标为等价。

AI Provider 的人类可读 message、HTTP status 和公开 request ID 在经过白名单提取与 secret/request-content 净化后必须可供
用户排障；未知内部异常继续 generic。完整约束见 `SPEC-user-visible-contract-ai-error-v1`。

## 17. 追踪要求

后续 PR 应在描述中引用规格 ID，例如：

```text
Implements: MONO-001, MONO-003, AI-005
Validates: ACCEPT-001, ACCEPT-002
Preserves: MULTI-001..MULTI-011
Deferred: RELEASE-003
```

每个阶段结束时，实施日志必须列出已满足规格、未满足规格、临时兼容、回滚点和后续 ADR。
