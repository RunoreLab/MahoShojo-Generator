# /challenge 战斗判定去关键词化设计

## 一、背景与问题

当前 `/challenge` 的战斗节点在进入 AI 裁定前，会先由本地逻辑构造 `resolverEnvelope`，并在其中写入 `recommendedOutcome`。该字段来自 [`lib/challenge/resolver-envelope.ts`](/home/notuhao/code/MahoShojo-Generator/lib/challenge/resolver-envelope.ts) 内部的 `inferRecommendedOutcome()`，其核心问题是：

1. 它会根据 `recommendedActionId`、`note` 中的关键词或短语直接推断胜负倾向。
2. 该本地推断结果会继续传入 [`lib/challenge/server/adjudicate-stream.ts`](/home/notuhao/code/MahoShojo-Generator/lib/challenge/server/adjudicate-stream.ts) 的 prompt，影响 AI 的最终裁定。
3. 当 AI 输出失败或尾注校验失败时，系统 fallback 也会复用同一套启发式逻辑，导致“关键词套利”从降级链路继续生效。

这会带来两个不可接受的问题：

1. 战斗结果会向“猜关键词”和“写术语”倾斜，而不是围绕角色设定、战术可行性和当前局面推演。
2. 某些文本表达会被启发式错误奖励或惩罚，例如“直接摆烂睡觉进入深度睡眠”可能被误判为观察/蓄势，“不要正面硬拼，等对面冲上来偷袭”也可能因为出现局部词语而落入不合理惩罚。

因此，本次设计目标不是移除玩家输入，而是移除“本地先验胜负结论”，把 `resolverEnvelope` 收缩回“资源与结果边界约束层”。

## 二、设计目标

本次设计目标如下：

1. `resolverEnvelope` 只负责结果边界，不再内置任何本地胜负倾向判断。
2. `recommendedActionId` 保留，但只表达“玩家声明的战术姿态”，不再直接决定 outcome。
3. `note` 保留为自由意图补充，由 AI 结合完整上下文判断其是否合理。
4. AI 裁定 prompt 明确要求模型自行分析打法是否成立，而不是接受玩家自述或本地倾向。
5. system fallback 改为独立、保守、确定性的 baseline，不读取 `note` 文本语义，不允许再被关键词利用。
6. 保持当前前端/API 输入契约与 envelope 校验机制稳定，尽量把变更限制在判定语义层。

## 三、非目标

本次不处理以下事项：

1. 不改动 `/challenge` 的节点 UI 结构，不移除现有推荐动作按钮。
2. 不把战斗改造成逐回合行动模拟，不引入更精细的回合制结算。
3. 不扩充新的战斗 outcome 类型，仍然保持 `victory / costly_victory / defeat`。
4. 不重写奖励、状态、checkpoint、存档或恢复机制。
5. 不改变 `playerInput` 的 DTO 字段结构。

## 四、现状问题拆解

### 4.1 本地启发式提前决定 outcome 倾向

当前 `inferRecommendedOutcome()` 会综合以下信号：

1. 玩家与敌人的 `strengthTier`
2. 节点类型 `battle / elite / boss / event`
3. `recommendedActionId`
4. `note` 中的若干正则关键词
5. 玩家标签与动作组合

这意味着 outcome 倾向并不是由 AI 基于完整战斗推演得出，而是被本地 heuristic 预先“设定基调”。

### 4.2 本地结论继续污染 AI prompt

`buildChallengeAdjudicationPrompt()` 当前会把 `recommendedOutcome` 明确写进 prompt。这样 AI 在生成正文和尾注时，会受到本地结论的强引导，削弱其对：

1. 角色设定摘要
2. 双方战斗画像
3. 当前资源与状态
4. 玩家自由意图是否合理

这些真正重要因素的独立分析。

### 4.3 fallback 链路继承同一问题

`buildSystemFallbackResolution()` 目前仍然复用 `inferRecommendedOutcome()`。这会导致：

1. AI 两次失败后，仍然会按关键词逻辑结算。
2. fallback 反而成为可预测、可利用的“保底漏洞”。

## 五、方案比较

### 方案 A：保留预设动作，但降级为意图标签

做法：

1. 保留 `recommendedActionId`
2. 删除 `recommendedOutcome`
3. AI 根据双方快照、玩家动作姿态、自由意图、资源与状态自行推演
4. fallback 不读取文本语义

优点：

1. 保留 `/challenge` 当前较低的输入门槛
2. 不再鼓励关键词套利
3. 不会让整个模式退化成“谁更会写提示词”
4. 接口与 UI 变更最小

缺点：

1. 需要同步改 prompt、fallback 和测试

### 方案 B：保留动作，但仅作极弱提示，主要依赖自由文本

优点：

1. 自由度更高

缺点：

1. 玩家若不写 `note`，输入语义会过稀
2. 玩法更容易退化成写 prompt
3. 移动端和轻量游玩体验更差

### 方案 C：彻底删除预设动作，只保留自由输入

优点：

1. 最彻底摆脱标签

缺点：

1. 严重提升输入门槛
2. 不能根本解决“文本自述是否可信”的问题
3. 与当前 `/challenge` 交互模型割裂过大

### 结论

本次采用方案 A。

## 六、最终设计

### 6.1 `resolverEnvelope` 收缩为纯边界约束

[`lib/challenge/resolver-envelope.ts`](/home/notuhao/code/MahoShojo-Generator/lib/challenge/resolver-envelope.ts) 中的 `ChallengeResolverEnvelopeV1` 调整为仅包含：

```ts
interface ChallengeResolverEnvelopeV1 {
  version: 1;
  worldPresetId: string;
  nodeId: string;
  nodeType: SupportedAiNodeType;
  outcomeSet: ChallengeAdjudicationOutcome[];
  trackDeltaRanges: ChallengeTrackDeltaRangeV1[];
  allowedAddStatuses: string[];
  allowedRemoveStatuses: string[];
  rewardSelectionMode: RewardSelectionModeV1;
  rewardOptionIds: string[];
  forbiddenFlags: Array<'one_shot' | 'full_restore' | 'free_persistent_item' | 'out_of_band_status'>;
}
```

删除字段：

1. `recommendedOutcome`

保留原则：

1. envelope 只定义“允许输出什么”
2. envelope 不定义“更推荐输出什么”

兼容边界：

1. `resolverEnvelope` 是 challenge 内部裁定链路使用的内部结构，服务于 envelope builder、prompt 组装、fallback 和 validator。
2. 本次允许同步修改其内部字段与消费点，不承诺对历史内部字段做兼容保留。
3. “接口契约保持稳定”仅指前端页面状态、API request body 中的 `playerInput` 结构，以及最终 AI 裁定输出仍受 envelope 校验约束。
4. 因此实现计划需要把 `recommendedOutcome` 的所有内部调用点视为同一批迁移目标，而不是把它当成需要兼容保留的外部协议字段。

### 6.2 `recommendedActionId` 的新语义

`recommendedActionId` 保留，但重新定义为：

1. 玩家声明的战术姿态
2. 对当前意图的结构化标签
3. 帮助 AI 理解玩家想“前压 / 诱导 / 稳守”的方向

它不再承担：

1. 胜负加分器
2. 固定收益来源
3. 本地 heuristic outcome selector

### 6.3 `note` 的新语义

`note` 继续作为自由输入存在，但新设计下：

1. 它只是“玩家意图描述”
2. 它不自动成立
3. AI 必须结合双方设定、资源、状态、敌人特征与节点强度判断其可行性

也就是说，玩家可以写“稳扎稳打等对方冲上来偷袭”，但是否真的能成功，要看这名角色是否具备这样的战术能力，以及对手是否会暴露这种破绽。

### 6.4 AI prompt 改造

[`lib/challenge/server/adjudicate-stream.ts`](/home/notuhao/code/MahoShojo-Generator/lib/challenge/server/adjudicate-stream.ts) 中的 prompt 应做如下调整：

1. 删除 `recommendedOutcome` 展示
2. 保留 `recommendedActionId` 和 `note`
3. 增加明确指令：`recommendedActionId` 与 `note` 只是玩家意图，不保证其有效，必须结合上下文独立判断
4. 增加反作弊倾向约束：不要因为玩家自称“稳健”“偷袭成功”“轻松拿下”就直接给出更好结果

建议新增的 prompt 语义要求：

1. 你必须分析该战术是否与玩家角色设定相符
2. 你必须分析该战术是否能在当前敌人风格与资源局面下成立
3. 若玩家意图明显空泛、矛盾、无效或不切实际，可以判定为代价更高甚至失败
4. 若玩家输入极少，也要根据双方快照与当前局面给出合理推演，而不是默认偏向任一 outcome

### 6.5 system fallback 改为独立保守基线

当前 fallback 最大的问题不是“写得不够真”，而是“复用了可被利用的 heuristic”。本次应将 fallback 改为独立 baseline：

1. 不读取 `note` 文本语义
2. `recommendedActionId` 最多影响叙述措辞，不影响胜负
3. 只基于稳定结构化信息决定 outcome

baseline 可参考以下输入：

1. `nodeType`
2. 玩家 `strengthTier`
3. 敌方 `strengthTier`
4. 当前 `hp`
5. 当前 `radiance`
6. 当前已有负面状态数量与类型

为避免实现期再次出现“语义上差不多”的松散解释，本次 fallback 采用最小 deterministic 决策表。

#### 6.5.1 评分输入离散化

1. `strengthTier` 映射：
   - `common = 0`
   - `elite = 1`
   - `boss = 2`
2. `tierDiff = playerTierScore - enemyTierScore`
3. `hpRatio = currentHp / maxHp`
   - `hpRatio >= 0.6` 记为 `healthy`，得分 `+1`
   - `0.35 <= hpRatio < 0.6` 记为 `strained`，得分 `0`
   - `hpRatio < 0.35` 记为 `critical`，得分 `-1`
4. `radianceRatio = currentRadiance / maxRadiance`
   - `radianceRatio >= 0.5` 记为 `stable`，得分 `+1`
   - `0.25 <= radianceRatio < 0.5` 记为 `low`，得分 `0`
   - `radianceRatio < 0.25` 记为 `depleted`，得分 `-1`
5. 负面状态惩罚：
   - `fatigued = 1`
   - `exposed = 1`
   - `shaken = 2`
   - `statusPenalty = sum(activeKnownNegativeStatuses)`，但上限为 `2`
   - 未列入该表的其他状态在 fallback 评分中按 `0` 处理，除非后续显式加入此决策表
6. `resourceScore = hpScore + radianceScore - statusPenalty`
7. `advantageScore = tierDiff * 2 + resourceScore`

#### 6.5.2 outcome 决策表

1. `battle` 与 `event`：
   - `advantageScore >= 2` => `victory`
   - `advantageScore <= -2` => `defeat`
   - 其余 => `costly_victory`
2. `elite`：
   - `advantageScore >= 3` => `victory`
   - `advantageScore <= -2` => `defeat`
   - 其余 => `costly_victory`
3. `boss`：
   - 若 `hpState = critical`，直接 => `defeat`
   - 否则若 `advantageScore >= 4` 且 `hpState = healthy` 且 `radianceState != depleted`，=> `victory`
   - 否则若 `advantageScore <= -1`，=> `defeat`
   - 其余 => `costly_victory`

#### 6.5.3 优先级与约束

1. 以上决策不读取 `note` 的任何文本语义。
2. 以上决策不读取 `recommendedActionId` 的策略标签。
3. 若缺少敌方快照或关键 track，则回退到当前 `nodeType` 的保守默认值：
   - `battle / elite / boss / event` 一律默认为 `costly_victory`
4. fallback 只负责选出保守 baseline outcome；`trackDeltas` 仍继续使用现有实现中对应节点类型的固定 fallback delta 预设，本次不重新设计 delta 取值。

### 6.6 fallback 叙事风格

fallback 的目标是稳定收束，不是精细模拟。建议：

1. 保留短篇战报文本
2. 保持语义中性、偏保守
3. 避免伪装成复杂战术推演的详细结论

这样可以让用户区分：

1. AI 成功裁定时，结果具有更强的上下文推演特征
2. system fallback 触发时，结果是一个可靠的保守收束

### 6.7 保持不变的部分

以下能力保持不变：

1. `playerInput` DTO 结构不变
2. `validateAdjudicationAgainstEnvelope()` 的越界校验逻辑不变
3. 奖励模式 `none / auto / choose-one` 语义不变
4. 负面状态 allowlist / remove list 机制不变
5. 节点结算、checkpoint、runState 写回流程不变

## 八、兼容性与迁移影响

### 8.1 对前端的影响

前端无需改动交互契约：

1. 推荐动作按钮继续存在
2. 自由输入框继续存在
3. 页面仍然把同一份 `playerInput` 提交给后端

### 8.2 对存档与历史数据的影响

本次不引入新的持久化字段，也不改变已有 `playerInput` 结构，因此：

1. 已有 node record 不需要迁移
2. 旧 runState / checkpoint 结构不需要升级

### 8.3 对裁定稳定性的影响

本次会降低本地可预测性，但这是设计目标的一部分。期望效果是：

1. 结果更依赖真实上下文
2. 结果更难被关键词操控
3. fallback 更保守但更稳定

## 十、验收标准

本次设计完成后，应满足以下标准：

1. 本地逻辑不再根据 `recommendedActionId` 或 `note` 的关键词直接推断 `outcome`
2. `resolverEnvelope` 中不再包含 `recommendedOutcome`
3. AI prompt 明确把玩家输入视为“待验证意图”，而不是“可信结论”
4. system fallback 不再读取 `note` 文本语义
5. 同一结构化战斗上下文下，改变 `note` 的措辞不会改变 fallback 结果
6. 现有 UI 与 API 输入结构保持兼容
7. 同一结构化战斗上下文下，改变 `recommendedActionId` 不会改变 fallback 结果
