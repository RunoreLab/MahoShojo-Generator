# 流式生成链路审计报告（2025-12-24）

## 背景

本次审计聚焦“流式生成战报”链路，目标是降低**未开启任何数据写入功能**时的误更新风险，并梳理流式生成在健壮性与安全边界上的潜在改进点。

用户关注点：当 `writeArenaHistory=false` 且 `writeCurrentState=false` 时，不应再提示模型输出“【角色更新元数据（可选）】”，以免在存在漏洞/误解析的情况下导致用户不希望的更新发生。

## 审计范围（本次已覆盖）

- 提示词拼接：`lib/arena/logic.ts`（`createStreamPromptBuilder`）
- 前端流式读取与后处理：`components/arena/hooks/useBattleEngine.ts`
- 元数据注释解析：`lib/arena/stream-meta.ts`
- 服务端流式转发与记录：`pages/api/arena/generate-stream.ts`
- 底层流式 AI 适配：`lib/stream/raw-ai.ts`

## 已落地的改进（可确认无误且已实现）

### 1) 未开启写入时不再引导模型输出元数据

- 修改 `createStreamPromptBuilder`：当写入开关全关时，不再附加“【角色更新元数据（可选）】”段落。
- 同时将“仅允许在最后一行 HTML 注释元数据中出现 JSON 与字段名”的说明改为**条件化**：
  - 写入开启：允许并要求按约定输出元数据注释。
  - 写入关闭：明确要求**不要追加任何 HTML 注释元数据**，也不要输出类似 `MAHOSHOJO_ARENA_META` 的标记。

### 2) 前端仅在写入开启时解析/信任元数据（并修复 UI 展示）

- 之前前端会在任何情况下尝试 `extractStreamUpdateMeta()`，并在“检测到 impacts”时将其视为“战报完整”，可能带来：
  - 未开启写入时的**冷却误触发**（只输出元数据注释也会被判定为 complete）。
  - 元数据注释在 UI 中“漏出”风险（即便不更新，也会显示系统专用内容）。
- 现在调整为：
  - 写入开启：解析并使用元数据（用于更新 & 兜底 headline/winner）。
  - 写入关闭：不解析元数据，仅做“剥离尾部元数据注释”，保证 UI 不展示。

### 3) 修复 TextDecoder 的末尾 flush，避免丢字

- 在前端流式读取结束后补充 `decoder.decode()` flush，避免最后一个 chunk 以多字节字符结尾时出现字符丢失/乱码的边界问题。

### 4) 增加“只剥离不解析”的工具函数与测试

- 新增 `stripStreamUpdateMetaComment()`（只移除带 marker 的 HTML 注释，不做 JSON 修复/解析），便于在未开启写入时降低解析面。
- 为该行为补充了基础单测，避免回归。

## 仍建议关注/后续可改进点（本次仅分析，未强行落地）

### A) “战报完整性”判定逻辑可更贴合提示词约束

当前前端的 `looksLikeCompleteReport` 主要依赖“长度 + 是否包含二级以上标题”进行启发式判断。建议后续考虑：

- 解析式校验：至少校验 `# 标题`、`## 胜利者`、`## 最终结果` 是否存在，并对“胜利者段落”做轻量提取。
- 与服务端/提示词规则统一：避免“模型输出格式接近但缺关键段落”时进入冷却或触发更新流程。

### B) 输出体积与内存上限策略

前端目前将全文累积到 `accumulatedText`，并在每个 chunk 都触发一次 state 更新。若模型输出异常膨胀，可能造成：

- 前端内存压力与渲染抖动
- `quickCheck` 频繁 await 带来的吞吐下降

建议后续引入：

- 最大字符数上限（达到上限后停止读取/提示用户）
- UI 渲染节流（例如按时间片/字符增量批量更新）

### C) 写入开关的“请求时快照”一致性

极端情况下用户在流式生成过程中切换写入开关，可能导致“提示词/服务端意图/前端后处理”不一致。

建议后续：

- 将写入开关在请求发起时固化为快照，并随 `x-mahoshojo-stream-meta` 一并返回（或在请求体/响应头中带回），前端后处理以快照为准。

### D) 元数据注释的更严格约束（防误触发/防注入）

虽然当前仅在写入开启时才会用于更新，但仍建议后续进一步收紧：

- marker 必须完全匹配（例如要求 `<!-- MAHOSHOJO_ARENA_META ` 前缀），避免“正文里提到 marker 字符串”导致误剥离/误解析。
- 增加 impacts 覆盖 roster 的强校验（缺人/多余/重复时直接降级为“仅 Markdown 解析”）。

## 验证建议

- 手工回归：
  - 写入全关：流式战报不应再出现“元数据可选”的提示引导；UI 不应展示任何 HTML 注释元数据。
  - 写入开启：仍可在文末输出元数据注释；更新逻辑正常工作；正文末尾注释不会显示到 UI。
- 自动化：
  - 继续补齐 `stripStreamUpdateMetaComment` 的边界测试：多个注释、超长尾部、无 `-->` 闭合等。
