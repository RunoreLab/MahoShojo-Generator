## 结论

我赞成开这一轮“机制简化”，而且从仓库现状看，这已经不只是代码洁癖问题，而是**过度防御开始直接降低产品可靠性**。

我以 `cc217a0c...` 的父提交 `e2cdb423...` 作为平台重整前基线，对照当前默认分支 HEAD `c9aea49b...`。`cc217a0c...` 本来只是 workspace 骨架，但从那之后逐渐叠加了 workspace 边界检查、Hosted DR 证明体系、Arena hardening、production activation、product parity、source hash、独立审查 evidence、release tuple 等大量机制。 当前 HEAD 甚至就是一个“修正 provenance 字段命名门禁”的提交，而实际业务修改只是 D1 row 属性访问写法变化；与此同时 `d1-finalization.ts` 已经到了 1300 多行的位置。这很能说明现在已经出现了“为了维护门禁而修代码”的反馈循环。

所以我不建议“回滚平台重整”，而建议做一次**复杂度预算重置**：

> 保留真正创造用户价值或防止实际损失的复杂度；删除用于证明、冻结、审计、强一致性和理论完美性的复杂度。

尤其是你对“原生性”的新风险偏好，我认为完全合理：**只在原生性会因果性地影响当前决策时验证；无法确认就按非原生处理。不要为了证明一张卡从生成开始到战后更新全过程都保持完美 provenance，而让整个业务失败。**

## 现在这个 409，基本就是过度工程化的典型案例

平台重整前的 `update-combatants-after-stream` 很简单：

客户端提交角色、战报和 impacts；如果某角色声称 `isNative=true`，服务端验签；验签不通过就**降级成非原生**，然后照常执行战后更新。也就是说，原生性验证失败不会破坏主流程。

现在则变成了：

`generationId`
→ 当前用户/actor 身份
→ D1 durable reconciliation
→ generation 已完成
→ finalization 已完成
→ terminal manifest 可用
→ server native authority 重算
→ `baseRevisionHash`
→ legacy signature-only revision compatibility
→ rosterCount
→ 最后才能 `applyPostBattleUpdates`。

而最关键的问题是，所谓 `baseRevisionHash` 并不是一个“小型并发版本号”。它把每名角色的：

`type + 整个 data + isNative + isPreset + characterGuidance`

全部 canonicalize 后做 SHA-256。

这意味着，下列任何事情都能让一次已经成功生成的战报无法更新角色：

角色本地字段发生变化；某些 UI/存储过程重新序列化内容；characterGuidance 改动；preset/native 状态判断发生变化；旧 generation 当时使用的 native authority 与现在不同；或者服务器这次把 `isNative` 重新判成了不同的值。

而 native authority 本身现在又不是简单验签了。内建 preset 会先 canonicalize 整个 JSON，再算 SHA-256，与生成的 `ARENA_PRESET_AUTHORITY` registry 比对；不匹配才回落到签名验证。

于是出现一个很不划算的耦合：

**“这张角色是不是原生” → “整张卡的 revision hash 是多少” → “这次战后更新能不能执行”。**

你的 409 正是这种设计的自然结果，而不只是某个漏修的 bug。

### 我建议这块不要继续修 compatibility branch

当前代码已经为了旧版本又增加了 `signatureOnlyBaseRevisionHash` 作为第二套兼容 revision。

继续修很容易变成：

current-authority revision

* signature-only revision
* historical-preset revision
* updated-preset revision
* 某种 retry revision……

应该直接降低不变量。

更合适的新语义应该是：

**generation 负责冻结“这场战斗产生了什么结果”；战后更新负责把这些 effects 尽可能应用到当前角色。**

`generationId` 可以继续作为可信结果索引。服务器可以继续读取自己保存的 report / impacts，避免客户端伪造 AI 结果。但不再要求客户端当前整张角色卡与生成开始时字节级/字段级等价。

如果担心用户在生成后把 A 角色换成 B 角色吃成长，真正应该校验的是**角色稳定身份/参战槽位与 impact 的对应关系**，而不是整个角色 JSON。存在冲突时也更适合“该角色跳过更新并告警”，而不是整场 409。

原生性同理：如果某个 effect 或内容安全规则**此刻**依赖原生性，就此刻验签；失败就是 `isNative=false`。这已经足以抵御你所说的 causal attack。没有理由让 provenance 不一致导致战报、角色成长、历史记录整个失败。

## `user-visible-contracts.json` 确实应该重点清理

这里需要稍微区分两个概念。

你说的“各种 sourceDigest”，其中 **GMR-10Q 的全仓 source digest 当前实际上已经不在 product-parity checker 里了**；现在这个 checker 主要检查七个 slice、状态、独立审查和审计日志。

但是 GMR-11 production activation 仍然真的会遍历整个 Git tree，计算 source digest，并要求当前源码树和 reviewed commit 摘要完全一致。

而 `config/user-visible-contracts.json` 虽然字段名不是 `sourceDigest`，却仍然有同类问题：它给退出的 API handler/route **固定 SHA-256**。 检查器会读取这些文件、重新计算 SHA-256，只要文件变化就直接 CI 失败，并要求补所谓 runtime differential evidence 后才能更新契约；同时还硬编码了哪些测试属于哪些 audit dimension。

这类机制对于受监管、高风险、大团队软件也许有价值。

对于 MahoShojo-Generator，它实际上意味着：

**改一个 handler → 不仅要让测试通过 → 还得更新一个机器审计账本 → 有时还要同步文档 evidence → 然后再修验证这个账本的测试。**

我认为应该直接删除这种“源码形态是契约”的思想。

真正的用户可见契约应该由**行为测试**保证：

相同请求是否还能成功；错误响应是否合理；授权有没有破坏；BYOK 是否还能工作；SSE 是否还能完成；角色更新是否还能应用。

至于 handler 文件 SHA 是多少，用户并不关心。

## Hosted DR 也是一个非常大的简化空间

`hosted-dr-capabilities.json` 现在已经把每条 route 分成 `non-idempotent-operation`、`durably-idempotent-command`、`safe-read`，再配 `drMode`、`replayPolicy`、required secrets、bindings、primary/dr database provider、contractStatus、drillStatus 等。

这里面有一个**真正值得保留的核心原则**：

> AI Provider 已经开始执行的生成请求，不能因为网络错误就在另一个 adapter 上自动重放，否则可能重复计费/重复生成。

但这一个原则完全不需要一个 21 KB capability manifest。

可以缩成全平台三条规则：

安全 GET 可以 fallback；还没 dispatch Provider 的生成 POST 可以换后端；一旦 Provider 已 dispatch，就绝不重新 POST，而是通过 `generationId` 查询/重连。

这就足够了。

长生成的 `generationId + reconnect + replay` 我反而建议保留，因为这是平台重整里少数**复杂度与用户收益高度匹配**的机制。只是不用再让它背负整套 DR control-plane 证明体系。

## R2/D1 “没保存完就不准 done”也应该反过来

`user-visible-contracts.json` 目前明确把这条列成 intentional contract：

**R2 和 D1 terminal finalization 必须先于 done，甚至存储失败可以让已经完成的 AI request 失败。**

我认为这非常值得在简化轮中推翻。

对于这个产品：

AI 已经把完整战报生成出来，而且客户端已经能看到完整结果，这才是主业务成功。

D1/R2 是持久化和恢复基础设施。

更合理的是：

**generation success 和 archival durability 分离。**

如果 Redis/D1/R2 某一层暂时出错，可以告诉客户端“战报已生成，但云端保存/恢复能力暂不可用”，后台或下一请求重试保存，而不是把一个已经成功的几分钟 AI 生成重新定义成失败。

这不只是代码少一点，而且会直接改善用户体验。

## Room hardening：测试值得留，“证明这些测试存在”的系统不值得留

当前 hardening checker 固定了整整十类故障演练，包括真实 socket disconnect、host refresh、Redis unavailable、Hono restart、checkpoint loss、orphan directory、generation 中途 SIGKILL、slow consumer、oversize flood、VPS unreachable；甚至要求 evidence 里的 owner、命令、恢复语义、assertion 文本都严格匹配。

这里千万不要走到另一个极端。

例如这些是真有价值的：

WebSocket 消息大小限制；慢客户端 bounded queue；membership/ticket 认证；Redis 中断后不要乱写；AI Provider 不重复调用。

但是：

**测试这些行为是好的；再建一个 JSON 清单证明测试按照某个固定命令和固定文字存在，就是过度。**

因此建议删除：

`arena-room-hardening-evidence.json`
→ checker
→ checker 自身测试
→ CI gate

留下普通 Vitest/integration tests 即可。

真正危险的回归自然会让测试红。

## 部署流程也已经明显“企业发行系统化”

重整前 Hono 部署大体是：

测试 → build 单文件 → SHA256 → scp → deploy script → `/health/ready` + CORS smoke test。

现在则包含：

Redis service、product parity readiness、GMR-11 approval、container config、release gate、release manifest、manifest SHA、D1 Gateway 本地进程、Room Redis verifier、generation Redis verifier、process recovery verifier、staging installer，最后才部署并联动 Cloudflare。

Preview workflow也已经发展为 Hono release tuple + Cloudflare build + SSH staging + 三个 Origin 的 HTTP/WSS 激活 canary 等完整流程。

对于目前这个项目，我更推荐恢复到：

**build → tests → deploy preview → smoke test → production approval → deploy → health check → 能回滚上一 release。**

artifact SHA/image digest可以保留，它确实能防止传输或部署错包。

但是没必要让 artifact 同时背负：

“这份源码经过 GMR-10Q、GMR-11、Room release gate、独立 reviewer 和 source digest 认证过”

这种职责。

## 但我不建议把平台重整新增内容全部删掉

这里有几个东西是“看起来复杂，但确实解决真实问题”的。

**monorepo 的 `apps/web`、`apps/api`、packages 物理边界值得保留。**现在再搬回单根应用，产生的迁移风险很可能超过收益。要删的是自定义治理，不是目录结构。

**Hono 独立服务值得保留。**尤其长时间 AI 生成移出 Cloudflare 请求生命周期，本身有明确价值。

**长生成可恢复能力值得保留。**`generationId`、断网重连、服务端保存短期 replay，这些是真实用户问题。

**Provider 调用防重复值得保留。**但只需要简单明确的“dispatch 后绝不自动重放”。

**真正的身份认证、Admin 授权、secret redaction、基本限流、WebSocket ticket 和有界发送队列值得保留。**这些保护的是账户、管理权限、费用或者资源耗尽，和 native provenance 的风险等级完全不同。

另外，D1 Gateway 也不是这轮平台重整凭空创造出来的；重整前基线已经有 `dev:d1-gateway` / `deploy:d1-gateway`。 所以不能简单看到它在 `apps/d1-gateway` 就一起删掉。

## 我建议把这一轮简化拆成三批

1. **P0：先解除正在制造用户故障的强一致性与 CI 门禁。**重点是取消战后角色完整 `baseRevisionHash` 门禁；native failure 改回降级；删除 GMR-11 sourceDigest、`user-visible-contracts` 的源码 SHA/evidence gate；合并 parity / activation / release 三套门禁；把根 CI 收缩为 lint/typecheck/test/build + 少量真正的 integration tests。这一批最可能立刻减少你现在这种“修了几轮角色更新还是 409”的问题。

2. **P1：缩减平台证明与容灾体系。**把 Hosted DR 从 per-route manifest/control-plane 模型收缩成少数通用规则；让 D1/R2 持久化与 generation success 解耦；删除 hardening evidence、Admin migration inventory 长期 CI、各种 verifier-of-verifier；部署流程恢复成构建、smoke、发布、回滚。

3. **P2：做代码结构减负。**审查 `d1-finalization`、Arena generation lifecycle、Room actor/recovery、错误 taxonomy、custom workspace/naming/source-ownership checker，把已经因为历史 hardening 长成“大状态机”的模块重新折叠。这个阶段不要以“测试越少越好”为目标，而要以**一个业务规则只存在一个实现、一份事实来源、一组行为测试**为目标。

其中我建议明确立一条新的仓库级设计原则：

> **Fail closed 只用于账号权限、secret、付费/资源滥用、会造成不可逆数据破坏或重复 AI 调用的边界。对于 provenance、native classification、审计 evidence、缓存/归档、可选容灾等低风险能力，默认 fail soft / degrade gracefully。**

这会比逐项说“这个 gate 删、那个 gate 留”更能防止几个月后重新长回现在这个样子。

### 对当前 409 的优先判断

我不建议再单独投入一轮去“修好现有 baseRevision compatibility”。

**它应该成为简化轮第一个被拆掉的机制。**

最小目标可以定成：

`generationId → 服务端可信 report/impacts → 按稳定参战角色身份应用到当前卡 → native 在必要决策点重新验签、失败按 false → 单个角色冲突局部跳过 → 不因 provenance/revision 不一致整场失败。`

这样既保留了真正需要的防伪造边界，又基本恢复到平台重整前那种“主流程优先”的可靠性模型。

如果接下来要正式开展这轮工作，我建议下一步不是马上改代码，而是先基于这次盘点写一份很短的 **“Platform Simplification / Complexity Budget” 冻结规格**，把“允许牺牲什么、不允许牺牲什么、哪些机制明确删除”定死，然后让 Codex 按 P0→P1→P2 系统性清理。否则 Agent 很可能在拆掉一个 gate 的同时，又为了“保证拆除安全”新增两个新 gate。
