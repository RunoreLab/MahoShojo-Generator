# 肉鸽玩法调研与基础方案建议

更新时间：2026-04-03 19:35:55
状态：`research`
归类：`docs/reports/` `roguelike` `ai-narrative` `indexeddb`

## 1. 本轮目标

围绕“在本项目中加入类似《杀戮尖塔》的可选路径肉鸽玩法”做前期调研，回答以下问题：

1. 现有仓库中，哪些能力已经足够支撑第一版肉鸽基础循环。
2. 路径式肉鸽、事件系统、AI 推演、浏览器本地存档，各自有哪些成熟做法值得借鉴。
3. 结合本项目“角色卡 + 数值 + 文本设定 + AI 战报”的特点，第一阶段最稳妥的落地形态应是什么。
4. 哪些内容适合一开始就做，哪些内容应明确延后。

---

## 2. 先说结论

我的总体判断是：

1. 这个项目**适合做“路径式叙事肉鸽 / roguelite”**，但第一阶段**不适合直接做完整的《杀戮尖塔》式卡牌战斗复制品**。
2. 你当前最强的资产不是“纯规则战斗引擎”，而是：
   - 角色卡已经有可持续利用的数值层
   - 角色文本设定已经能进入战报上下文
   - 已经有连续战报、本地会话、分支与摘要能力
   - 已经有本地 IndexedDB 的经验
3. 因此首版更合理的定位是：
   - **玩家沿地图节点推进**
   - **节点用确定性规则结算数值骨架**
   - **AI 负责把结果写成有角色味道的战斗 / 事件 / 后果**
   - **成长以货币、遗物/物品、少量技能分支、状态变化为主**
4. 最需要坚持的一条边界是：
   - **胜负、掉血、资源变化、掉落、分支解锁**不能完全交给 AI 随口编
   - AI 更适合负责“如何表现结果”，而不是“结果本身是否成立”

一句话概括：

- 第一版应该先做成“**AI 叙事驱动的路径式成长冒险**”
- 而不是“**先做一套重规则 deckbuilder，再硬把 AI 套上去**”

## 3. 现有仓库里已经具备的可复用能力

### 3.1 角色参数已经能随角色卡进入后续战报

`/creator` 的规则车卡结果已经不是页面内一次性 UI，而是会沉淀为角色卡上的“角色参数”，并在后续故事生成里继续生效。

可参考：

- [`public/encyclopedia/creator.md`](../../public/encyclopedia/creator.md)
- [`docs/specs/2026-04-03_112622_创作页角色卡车卡规则展示设计.md`](../specs/2026-04-03_112622_创作页角色卡车卡规则展示设计.md)
- [`lib/creator/build-rules.ts`](../../lib/creator/build-rules.ts)

这意味着肉鸽首版不必重新发明“角色基础属性来源”：

- 力量层级
- 核心属性
- 派生值
- 专长 / build rule 结果

这些都可以直接作为 run 初始状态或判定输入。

### 3.2 连续战报已经验证了“本地长链会话 + 分支 + 摘要”的模式

连续战报当前已经具备：

- 章节规划
- 会话快照
- 分支 / 重写 / 删除
- `workingCombatants`
- 摘要而不是全文回放

可参考：

- [`public/encyclopedia/continuous-battle-story.md`](../../public/encyclopedia/continuous-battle-story.md)
- [`lib/ai-session/battle-story/types.ts`](../../lib/ai-session/battle-story/types.ts)
- [`lib/ai-session/battle-story/storage.ts`](../../lib/ai-session/battle-story/storage.ts)

这对肉鸽的意义很大，因为“run”本质上也是一条本地状态链，只是单位从“章节”变成“节点”。

### 3.3 仓库已经有可复用的 IndexedDB 基础设施

当前项目已经把较复杂、本地且结构化的数据放入 IndexedDB，而不是全塞进 `localStorage`。

可参考：

- [`lib/ai-session/storage.ts`](../../lib/ai-session/storage.ts)
- [`lib/magic-tea-party/storage.ts`](../../lib/magic-tea-party/storage.ts)

其中已经包含：

- object store 设计
- index 设计
- checkpoint / session 设计
- 迁移与版本升级思路

这说明“肉鸽 run 存档完全本地化”这条路对本仓库是自然延伸，不是额外风格切换。

### 3.4 `localStorage` 仍适合作为轻量 UI 偏好层

竞技场主配置当前通过 Zustand `persist` 挂在 `localStorage`，适合保存：

- 当前页面配置
- 偏好项
- 轻量草稿

可参考：

- [`components/arena/stores/useBattleStore.ts`](../../components/arena/stores/useBattleStore.ts)

这也意味着未来肉鸽模块可以继续保持分层：

- `localStorage`：筛选器、UI 偏好、最近选择
- `IndexedDB`：run 存档、节点历史、快照、解锁进度

## 4. 外部调研归纳

### 4.1 路径式肉鸽的关键不只是“有地图”，而是“每一步都在做风险收益权衡”

外部资料里有两个点非常值得拿来做第一原则：

1. 《Slay the Spire》开发者强调，玩家喜欢的不是单一随机性，而是**层层叠加的决策**，包括路径、卡组、遗物、战斗顺序等带来的规划感。
2. 路线图设计如果要成立，**奖励、风险、未来空间要尽量可预判**，这样路径选择才不是盲抽。

对本项目的含义：

- 节点地图不能只是“战斗 / 事件 / 商店”的图标排列
- 每条路要能让玩家在进入前看到一部分信息，例如：
  - 接下来 2~3 行的节点类型分布
  - 精英 / Boss / 休整的相对位置
  - 世界专属危险值或收益倾向
  - 某些事件需要特定资源或特定角色标签

如果玩家在地图上看不出差别，就不会有真正的路线博弈。

### 4.2 叙事事件系统更适合走 state-driven storylet / quality-based narrative，而不是纯分支树

Emily Short 对 quality-based narrative 的总结，以及 Failbetter 对 storylet 结构的长期实践，有一个共同核心：

1. 事件不是沿固定树一路分叉到底。
2. 事件的可见性由“状态 / qualities / tags / 前置条件”决定。
3. 事件执行后更新状态，再让后续事件池重新洗牌。

这非常适合本项目，因为你已经有：

- 角色数值
- 角色文本设定
- 当前状态
- 历战记录
- 世界观情景卡

与其写一棵巨大的硬编码分支树，不如写成：

- 事件模板
- 前置条件
- 权重
- 选项
- 成功 / 失败 / 特殊分支的 effect envelope

再让系统按当前 run 状态筛选能触发的事件。

这能避免两个问题：

1. 分支树爆炸后很难维护
2. 多世界预设一多，树状结构会迅速失控

### 4.3 叙事型 roguelike 要成立，失败也必须是内容的一部分

《Hades》的经验很重要：它并不是把“失败”当成纯惩罚，而是把失败也纳入叙事循环，因此玩家重复跑不会只觉得自己在白打工。

对本项目的启发是：

- 肉鸽 run 的失败不应该只有“Game Over”
- 更适合做成“**失败也会产出战报、日志、解锁记录或世界认知**”

例如：

- 战败也会生成一段失败战报与角色状态变化
- 世界图鉴 / 事件词条 / 敌人情报可以被记录
- 某些世界中失败会触发专属结局或下次开局修正

这样更符合你项目的叙事优势。

### 4.4 LLM 更适合作为“受约束的叙事执行者”，不适合作为唯一状态机

近期关于 LLM + 游戏叙事的研究里，一个非常一致的结论是：

1. 单纯把所有状态推进都交给模型，会出现一致性与可控性问题。
2. 更稳妥的做法是保留作者 / 系统定义的结构层，再让模型在结构内补叙事、补表现。

对本项目最重要的含义是：

- AI 不应直接决定：
  - 这局有没有掉 12 点血
  - 商店卖什么
  - 玩家是否真的拿到某遗物
  - 下一个节点是什么
- AI 更适合决定：
  - 为什么这场战斗是这样赢 / 输的
  - 角色文本设定如何影响了这次事件的表现形式
  - 同一个规则结果下，故事如何写得更像这个角色

换句话说，最稳的结构是：

- **系统管“状态”**
- **AI 管“演出”**

### 4.5 浏览器端本地存档应优先使用 IndexedDB，不应把 run 全部压进 `localStorage`

MDN 对 Web Storage 和 IndexedDB 的定位很清楚：

1. `localStorage` / `sessionStorage` 是同步 API，更适合轻量数据。
2. IndexedDB 更适合大体量、结构化、需要索引和事务的数据。

对肉鸽来说，这几乎是直接结论：

- 单局 run 会包含：
  - 地图
  - 当前状态
  - 节点日志
  - AI 输出片段
  - 奖励记录
  - 快照 / checkpoint
- 这些内容很快就会超过轻量偏好存储的合理范围

所以存档层应直接按 IndexedDB 设计，不建议先偷懒用一个大 JSON 塞 `localStorage`，后面再迁移。

## 5. 对本项目的定位建议

### 5.1 第一阶段不要做“纯卡牌战斗 clone”

原因很直接：

1. 你现在已经有的是角色卡、角色参数、故事生成、连续战报，而不是完整的 deterministic 回合制战斗模拟器。
2. 如果第一阶段就上完整 deck / hand / draw / energy / enemy AI / 数值平衡，范围会立刻膨胀。
3. 项目特色本来就不在“机械复制《杀戮尖塔》”，而在“数值 + 文本设定 + AI 推演”。

因此更建议把第一阶段定义为：

- **地图式推进**
- **节点式结算**
- **成长式 build**
- **AI 演出式结果书写**

而不是：

- 先做完整卡牌对战
- 再想办法给每一张卡和每一场战斗写剧情

### 5.2 更准确的产品形态是“叙事肉鸽跑图器”

第一版更像：

1. 用户选择角色卡与世界预设
2. 系统生成一条 run 地图
3. 用户选路
4. 节点发生战斗 / 事件 / 商店 / 休整
5. 系统按规则更新数值状态
6. AI 把结果生成成短战报 / 事件演出 / 状态日志
7. 玩家拿奖励继续推进
8. 通关或失败时，生成一份 run 总结与角色变化摘要

这比“从一开始就做重规则桌游化战斗”更贴合仓库现状。

## 6. 推荐的系统分层

### 6.1 建议划分为 5 层

1. `worldPreset`
   - 世界预设
   - 定义规则口径、资源词汇、事件池、敌人池、Boss、结局规则、提示词风格

2. `runState`
   - 单局状态
   - 包括当前节点、角色生命/资源、货币、物品、技能分支、世界状态标记、已触发事件

3. `mapGenerator`
   - 生成地图节点与路径
   - 可基于 seed，确保可复现

4. `resolver`
   - 负责战斗 / 事件 / 商店 / 奖励的确定性结算
   - 产出合法的状态变化结果

5. `aiNarrator`
   - 在系统给定的合法结果范围内，把这次节点结算写成文本

### 6.2 建议明确“系统职责 / AI 职责”边界

| 层 | 更适合系统处理 | 更适合 AI 处理 |
| --- | --- | --- |
| 地图 | 节点生成、路径合法性、节点类型权重 | 地图段落说明、世界氛围描述 |
| 战斗 | 敌人强度、掉血、资源消耗、胜负、掉落 | 战斗过程的描写、角色风格化表现 |
| 事件 | 触发条件、选项是否合法、数值效果 | 事件文本、选项文案、结果表现 |
| 成长 | 物品数值、技能解锁、货币变化 | 获得成长时的叙事包装 |
| 存档 | 快照、checkpoint、分支、恢复 | 总结、日志、回顾 |

这个边界越清晰，后面世界扩展越稳。

## 7. 推荐的首版核心循环

### 7.1 节点类型先收敛到 6 种

建议首版只做：

1. 普通战斗
2. 精英战斗
3. 事件
4. 休整
5. 商店
6. Boss

理由：

- 这是最容易让玩家立刻读懂的经典结构
- 也最方便以后做世界变体

例如后续可以让世界预设去“换皮”：

- 休整 -> 宿营 / 医务室 / 校园天台 / 监狱禁闭前喘息
- 商店 -> 黑市 / 小卖部 / 神秘交易 / 乐器店
- 精英 -> 乱入强敌 / 中 Boss / 世界事件首领

### 7.2 地图规模建议先短，不要一上来做三幕超长 run

建议 MVP 的 run 规模：

- 1 个世界
- 8~12 个节点
- 1 个最终 Boss
- 1~2 次中途强敌或强事件

理由：

- 这样一次 run 的 AI 调用次数可控
- 也更容易先验证“地图选择有没有意思”
- 如果一开始就做 3 幕长跑，调试成本会显著上升

### 7.3 首版成长系统建议先做“小而硬”的 4 件套

建议优先做：

1. `currency`
   - 货币
2. `consumables`
   - 消耗品
3. `relics/items`
   - 被动强化物
4. `small skill branch`
   - 小型技能分支或专精节点

不建议首版就做：

1. 完整大技能树
2. 复杂背包管理
3. 大量装备栏位
4. 多货币经济系统

因为这些会让第一版很快从“验证玩法骨架”变成“做一个大型 RPG 子系统”。

## 8. 数值与文本设定如何共同参与判定

这是本项目最关键的差异点，必须明确设计口径。

### 8.1 不建议让文本设定无上限地改写数值结果

如果 AI 看到角色设定很帅，就随意让她跨等级反杀，系统很快会失去可预期性。

所以更建议把文本设定的影响限制在以下三类：

1. **分支解锁**
   - 某些设定让角色拥有特殊选项
2. **有限幅度修正**
   - 在可控范围内给予加减成
3. **后果形态变化**
   - 同样是失败，但失败表现可能不同

### 8.2 推荐的判定思路

可以用这样一套口径：

1. 数值层先给出基础成功率 / 伤害区间 / 资源消耗区间
2. 文本设定转成标签或倾向值
3. 标签只做以下事情：
   - 给某类节点增加 / 减少少量修正
   - 解锁特殊事件选项
   - 决定结果文案和附带状态
4. 最终结果必须落在系统允许的 envelope 之内

例如：

- “怯场”标签
  - 在舞台类 / 社交类节点上，降低表现阈值
- “复仇执念”标签
  - 遇到特定敌系时可解锁高风险高收益选项
- “火焰适性”标签
  - 在火系世界里获得额外事件分支

这能让文本设定真的有用，但又不会把平衡完全交给自由发挥。

### 8.3 文本设定最好抽成“可判定标签层”

如果未来要长期做肉鸽，建议不要每次都把整张卡原文扔给模型自己猜重点。

更稳妥的长期方向是增加一层抽象：

- 人格标签
- 风格标签
- 关系标签
- 世界相性标签
- 禁忌 / 执念 / 弱点标签

这些标签可以：

- 由问卷直接生成
- 由规则预设补充
- 或由 AI 首次解析角色卡时生成，再人工确认

这层一旦有了，多世界预设和事件筛选都会稳很多。

## 9. 多世界预设的建议

### 9.1 不同世界应该共享框架，但不能共享语义

你的判断是对的：

- 总体框架一致
- 世界规则和设计不同

建议把“共框架”与“异语义”拆清楚。

### 9.2 建议每个世界预设至少定义以下内容

1. 基础资源模型
   - 例如 HP / 金钱 / 理智 / 光辉 / 热度 / 嫌疑值
2. 节点权重
   - 事件多、战斗多、商店多，还是偏长线剧情
3. 敌人与事件池
4. 世界专属标签规则
5. 结局与失败语义
6. AI 提示词风格包

换句话说，世界预设不应该只是一组美术皮肤，而要真正定义“这世界里什么才算一次 run”。

### 9.3 适合优先尝试的世界

如果结合仓库现有内容，我更推荐优先考虑这几类：

1. **魔法少女竞技场世界**
   - 最接近现有系统
   - 容易复用战斗与角色参数
2. **魔女审判 / 监狱岛世界**
   - 很适合做高压力事件链、嫌疑值、审判阶段
3. **少女乐队 / 对邦世界**
   - 适合把“战斗”换成“演出 / 对邦 / 舆论 / 创作压力”

这三类都能证明“同一骨架、不同世界语义”是可行的。

## 10. 存档与数据结构建议

### 10.1 存档层建议直接沿用 AI session 的思路

建议新增类似下面的对象层：

1. `roguelikeWorldProfiles`
   - 已解锁世界与世界级配置
2. `roguelikeRuns`
   - run 主记录
3. `roguelikeRunNodes`
   - 已经过的节点记录
4. `roguelikeRunCheckpoints`
   - 关键快照
5. `roguelikeUnlocks`
   - 解锁内容
6. `roguelikeRunDigests`
   - 摘要与回顾

### 10.2 自动保存节点

建议至少在以下时机自动保存：

1. 创建 run 后
2. 进入节点前
3. 节点结算后
4. 领取奖励后
5. 通关 / 失败后

这样即使 AI 节点生成中断，也不会把整局 run 弄坏。

### 10.3 不建议每次都回放完整历史

和连续战报一样，肉鸽也不应该每次把所有历史全文重新喂给模型。

更好的做法是：

- 保存当前状态快照
- 保存最近 1~2 个节点摘要
- 保存 run 累计摘要
- 保存角色关键变化摘要

这样能显著降低 token 消耗。

## 11. 推荐的 MVP 范围

### 11.1 第一版建议只验证一个最小纵切

建议 MVP 范围是：

1. 只做 **1 个世界**
2. 只做 **1 套共享地图骨架**
3. 只做 **6 类节点**
4. 只做 **基础货币 + 遗物/物品 + 小型成长**
5. 只做 **本地存档**
6. 只做 **单 run 回顾，不做复杂 meta progression**

### 11.2 第一版最好验证的不是“内容量”，而是这三个问题

1. 路线选择有没有真实权衡感
2. 数值层和文本层能不能稳定协同
3. AI 写出的节点结果，是否真的让这个玩法比纯数值结算更有特色

如果这三个问题成立，再扩内容池才有意义。

## 12. 明确建议延后的内容

以下内容都很诱人，但我建议不要放进首版：

1. 完整 deckbuilder 卡牌系统
2. 大技能树
3. 多角色同时可控的复杂战术编队
4. 在线同步与跨设备云存档
5. 复杂经济体系
6. 大量世界同时首发

原因只有一个：

- 这些都是“放大器”，不是“地基”

先把地基跑通，后面每个方向都还能继续加。

## 13. 分阶段推进建议

### Phase A：规格与数据层

目标：

- 定义 `worldPreset`、`runState`、`nodeRecord`、`checkpoint`、`unlock` 的 schema
- 明确 AI / 系统分层边界
- 明确首个世界的资源模型

### Phase B：可玩的最小 run

目标：

- 生成地图
- 进入节点
- 完成战斗 / 事件 / 休整 / 商店 / Boss 结算
- 本地存档与恢复
- 产出短结果日志

### Phase C：AI 演出增强

目标：

- 节点结果改由 AI 写成短战报 / 事件演出
- 失败与通关产出总结
- 角色文本设定真正参与分支和后果

### Phase D：内容扩展与第二世界

目标：

- 扩事件池
- 扩掉落池
- 增加第二个世界预设
- 验证共享骨架是否足够稳

## 14. 当前最值得先确认的开放问题

1. 首版 run 是以“**单角色**”为主，还是允许“**小队**”进入？
   - 我倾向先做单角色或 1 主角 + 轻伴随层，复杂度更可控。

2. 玩家在节点里是只做“**选路**”，还是还要做“**节点内选项**”？
   - 我建议保留节点内选项，因为这正好能让 AI 叙事发挥价值。

3. meta progression 首版是做“**纯内容解锁**”，还是做“**数值永久成长**”？
   - 我更建议先做内容解锁或弱数值解锁，避免早期平衡崩得太快。

4. 失败后的语义是什么？
   - 完全失败重开
   - 带失败日志与少量解锁
   - 或世界特定的 fail-forward

5. 文本设定的“标签抽取”要不要在第一版做？
   - 如果不做，就先手工定义少量标签入口
   - 如果要做，必须保证结果可校验、可复用

---

## 15. 我当前的推荐方向

如果现在就要开始做，我建议路线是：

1. 先把它定义为“**路径式叙事肉鸽**”
2. 首版先做“**一个世界 + 一个短 run + 六类节点 + 本地 IndexedDB 存档**”
3. 用系统结算数值骨架，用 AI 负责战斗 / 事件结果的表现
4. 把角色文本设定先做成“**有限加成 + 特殊分支解锁**”，不要无上限影响平衡
5. 等第一轮验证完成，再决定是否引入更重的技能树、物品体系或长期 meta progression

这是我认为**最能发挥本项目特色、同时风险最低**的切入方式。
