# 肉鸽玩法调研与基础方案建议

更新时间：2026-04-03 19:35:55
状态：`research`
归类：`docs/reports/` `roguelike` `ai-narrative` `indexeddb`

## 1. 本轮目标

围绕“在本项目中加入类似《杀戮尖塔》的可选路径肉鸽玩法”做前期调研，回答以下问题：

1. 现有仓库中，哪些能力已经足够支撑第一版肉鸽基础循环。
2. 路径式肉鸽、事件系统、AI 推演、浏览器本地存档，各自有哪些成熟做法值得借鉴。
3. 结合本项目“角色卡 + 数值 + 文本设定 + AI 战报”的特点，第一阶段最稳妥的落地形态应是什么。
4. 哪些内容适合一开始就做，哪些内容应明确延后。

---

## 2. 先说结论

我的总体判断是：

1. 这个项目**适合做“路径式叙事肉鸽 / roguelite”**，但第一阶段**不适合直接做完整的《杀戮尖塔》式卡牌战斗复制品**。
2. 你当前最强的资产不是“纯规则战斗引擎”，而是：
   - 角色卡已经有可持续利用的数值层
   - 角色文本设定已经能进入战报上下文
   - 已经有连续战报、本地会话、分支与摘要能力
   - 已经有本地 IndexedDB 的经验
3. 因此首版更合理的定位是：
   - **玩家沿地图节点推进**
   - **节点用确定性规则结算数值骨架**
   - **AI 负责把结果写成有角色味道的战斗 / 事件 / 后果**
   - **成长以货币、遗物/物品、少量技能分支、状态变化为主**
4. 最需要坚持的一条边界是：
   - **胜负、掉血、资源变化、掉落、分支解锁**不能完全交给 AI 随口编
   - AI 更适合负责“如何表现结果”，而不是“结果本身是否成立”

一句话概括：

- 第一版应该先做成“**AI 叙事驱动的路径式成长冒险**”
- 而不是“**先做一套重规则 deckbuilder，再硬把 AI 套上去**”

## 3. 现有仓库里已经具备的可复用能力

### 3.1 角色参数已经能随角色卡进入后续战报

`/creator` 的规则车卡结果已经不是页面内一次性 UI，而是会沉淀为角色卡上的“角色参数”，并在后续故事生成里继续生效。

可参考：

- [`public/encyclopedia/creator.md`](../../public/encyclopedia/creator.md)
- [`docs/specs/2026-04-03_112622_创作页角色卡车卡规则展示设计.md`](../specs/2026-04-03_112622_创作页角色卡车卡规则展示设计.md)
- [`lib/creator/build-rules.ts`](../../lib/creator/build-rules.ts)

这意味着肉鸽首版不必重新发明“角色基础属性来源”：

- 力量层级
- 核心属性
- 派生值
- 专长 / build rule 结果

这些都可以直接作为 run 初始状态或判定输入。

### 3.2 连续战报已经验证了“本地长链会话 + 分支 + 摘要”的模式

连续战报当前已经具备：

- 章节规划
- 会话快照
- 分支 / 重写 / 删除
- `workingCombatants`
- 摘要而不是全文回放

可参考：

- [`public/encyclopedia/continuous-battle-story.md`](../../public/encyclopedia/continuous-battle-story.md)
- [`lib/ai-session/battle-story/types.ts`](../../lib/ai-session/battle-story/types.ts)
- [`lib/ai-session/battle-story/storage.ts`](../../lib/ai-session/battle-story/storage.ts)

这对肉鸽的意义很大，因为“run”本质上也是一条本地状态链，只是单位从“章节”变成“节点”。

### 3.3 仓库已经有可复用的 IndexedDB 基础设施

当前项目已经把较复杂、本地且结构化的数据放入 IndexedDB，而不是全塞进 `localStorage`。

可参考：

- [`lib/ai-session/storage.ts`](../../lib/ai-session/storage.ts)
- [`lib/magic-tea-party/storage.ts`](../../lib/magic-tea-party/storage.ts)

其中已经包含：

- object store 设计
- index 设计
- checkpoint / session 设计
- 迁移与版本升级思路

这说明“肉鸽 run 存档完全本地化”这条路对本仓库是自然延伸，不是额外风格切换。

### 3.4 `localStorage` 仍适合作为轻量 UI 偏好层

竞技场主配置当前通过 Zustand `persist` 挂在 `localStorage`，适合保存：

- 当前页面配置
- 偏好项
- 轻量草稿

可参考：

- [`components/arena/stores/useBattleStore.ts`](../../components/arena/stores/useBattleStore.ts)

这也意味着未来肉鸽模块可以继续保持分层：

- `localStorage`：筛选器、UI 偏好、最近选择
- `IndexedDB`：run 存档、节点历史、快照、解锁进度

## 4. 外部调研归纳

### 4.1 路径式肉鸽的关键不只是“有地图”，而是“每一步都在做风险收益权衡”

外部资料里有两个点非常值得拿来做第一原则：

1. 《Slay the Spire》开发者强调，玩家喜欢的不是单一随机性，而是**层层叠加的决策**，包括路径、卡组、遗物、战斗顺序等带来的规划感。
2. 路线图设计如果要成立，**奖励、风险、未来空间要尽量可预判**，这样路径选择才不是盲抽。

对本项目的含义：

- 节点地图不能只是“战斗 / 事件 / 商店”的图标排列
- 每条路要能让玩家在进入前看到一部分信息，例如：
  - 接下来 2~3 行的节点类型分布
  - 精英 / Boss / 休整的相对位置
  - 世界专属危险值或收益倾向
  - 某些事件需要特定资源或特定角色标签

如果玩家在地图上看不出差别，就不会有真正的路线博弈。

### 4.2 叙事事件系统更适合走 state-driven storylet / quality-based narrative，而不是纯分支树

Emily Short 对 quality-based narrative 的总结，以及 Failbetter 对 storylet 结构的长期实践，有一个共同核心：

1. 事件不是沿固定树一路分叉到底。
2. 事件的可见性由“状态 / qualities / tags / 前置条件”决定。
3. 事件执行后更新状态，再让后续事件池重新洗牌。

这非常适合本项目，因为你已经有：

- 角色数值
- 角色文本设定
- 当前状态
- 历战记录
- 世界观情景卡

与其写一棵巨大的硬编码分支树，不如写成：

- 事件模板
- 前置条件
- 权重
- 选项
- 成功 / 失败 / 特殊分支的 effect envelope

再让系统按当前 run 状态筛选能触发的事件。

这能避免两个问题：

1. 分支树爆炸后很难维护
2. 多世界预设一多，树状结构会迅速失控

### 4.3 叙事型 roguelike 要成立，失败也必须是内容的一部分

《Hades》的经验很重要：它并不是把“失败”当成纯惩罚，而是把失败也纳入叙事循环，因此玩家重复跑不会只觉得自己在白打工。

对本项目的启发是：

- 肉鸽 run 的失败不应该只有“Game Over”
- 更适合做成“**失败也会产出战报、日志、解锁记录或世界认知**”

例如：

- 战败也会生成一段失败战报与角色状态变化
- 世界图鉴 / 事件词条 / 敌人情报可以被记录
- 某些世界中失败会触发专属结局或下次开局修正

这样更符合你项目的叙事优势。

### 4.4 LLM 更适合作为“受约束的叙事执行者”，不适合作为唯一状态机

近期关于 LLM + 游戏叙事的研究里，一个非常一致的结论是：

1. 单纯把所有状态推进都交给模型，会出现一致性与可控性问题。
2. 更稳妥的做法是保留作者 / 系统定义的结构层，再让模型在结构内补叙事、补表现。

对本项目最重要的含义是：

- AI 不应直接决定：
  - 这局有没有掉 12 点血
  - 商店卖什么
  - 玩家是否真的拿到某遗物
  - 下一个节点是什么
- AI 更适合决定：
  - 为什么这场战斗是这样赢 / 输的
  - 角色文本设定如何影响了这次事件的表现形式
  - 同一个规则结果下，故事如何写得更像这个角色

换句话说，最稳的结构是：

- **系统管“状态”**
- **AI 管“演出”**

### 4.5 浏览器端本地存档应优先使用 IndexedDB，不应把 run 全部压进 `localStorage`

MDN 对 Web Storage 和 IndexedDB 的定位很清楚：

1. `localStorage` / `sessionStorage` 是同步 API，更适合轻量数据。
2. IndexedDB 更适合大体量、结构化、需要索引和事务的数据。

对肉鸽来说，这几乎是直接结论：

- 单局 run 会包含：
  - 地图
  - 当前状态
  - 节点日志
  - AI 输出片段
  - 奖励记录
  - 快照 / checkpoint
- 这些内容很快就会超过轻量偏好存储的合理范围

所以存档层应直接按 IndexedDB 设计，不建议先偷懒用一个大 JSON 塞 `localStorage`，后面再迁移。

## 5. 对本项目的定位建议

### 5.1 第一阶段不要做“纯卡牌战斗 clone”

原因很直接：

1. 你现在已经有的是角色卡、角色参数、故事生成、连续战报，而不是完整的 deterministic 回合制战斗模拟器。
2. 如果第一阶段就上完整 deck / hand / draw / energy / enemy AI / 数值平衡，范围会立刻膨胀。
3. 项目特色本来就不在“机械复制《杀戮尖塔》”，而在“数值 + 文本设定 + AI 推演”。

因此更建议把第一阶段定义为：

- **地图式推进**
- **节点式结算**
- **成长式 build**
- **AI 演出式结果书写**

而不是：

- 先做完整卡牌对战
- 再想办法给每一张卡和每一场战斗写剧情

### 5.2 更准确的产品形态是“叙事肉鸽跑图器”

第一版更像：

1. 用户选择角色卡与世界预设
2. 系统生成一条 run 地图
3. 用户选路
4. 节点发生战斗 / 事件 / 商店 / 休整
5. 系统按规则更新数值状态
6. AI 把结果生成成短战报 / 事件演出 / 状态日志
7. 玩家拿奖励继续推进
8. 通关或失败时，生成一份 run 总结与角色变化摘要

这比“从一开始就做重规则桌游化战斗”更贴合仓库现状。

## 6. 推荐的系统分层

### 6.1 建议划分为 5 层

1. `worldPreset`
   - 世界预设
   - 定义规则口径、资源词汇、事件池、敌人池、Boss、结局规则、提示词风格

2. `runState`
   - 单局状态
   - 包括当前节点、角色生命/资源、货币、物品、技能分支、世界状态标记、已触发事件

3. `mapGenerator`
   - 生成地图节点与路径
   - 可基于 seed，确保可复现

4. `resolver`
   - 负责战斗 / 事件 / 商店 / 奖励的确定性结算
   - 产出合法的状态变化结果

5. `aiNarrator`
   - 在系统给定的合法结果范围内，把这次节点结算写成文本

### 6.2 建议明确“系统职责 / AI 职责”边界

| 层 | 更适合系统处理 | 更适合 AI 处理 |
| --- | --- | --- |
| 地图 | 节点生成、路径合法性、节点类型权重 | 地图段落说明、世界氛围描述 |
| 战斗 | 敌人强度、掉血、资源消耗、胜负、掉落 | 战斗过程的描写、角色风格化表现 |
| 事件 | 触发条件、选项是否合法、数值效果 | 事件文本、选项文案、结果表现 |
| 成长 | 物品数值、技能解锁、货币变化 | 获得成长时的叙事包装 |
| 存档 | 快照、checkpoint、分支、恢复 | 总结、日志、回顾 |

这个边界越清晰，后面世界扩展越稳。

## 7. 推荐的首版核心循环

### 7.1 节点类型先收敛到 6 种

建议首版只做：

1. 普通战斗
2. 精英战斗
3. 事件
4. 休整
5. 商店
6. Boss

理由：

- 这是最容易让玩家立刻读懂的经典结构
- 也最方便以后做世界变体

例如后续可以让世界预设去“换皮”：

- 休整 -> 宿营 / 医务室 / 校园天台 / 监狱禁闭前喘息
- 商店 -> 黑市 / 小卖部 / 神秘交易 / 乐器店
- 精英 -> 乱入强敌 / 中 Boss / 世界事件首领

### 7.2 地图规模建议先短，不要一上来做三幕超长 run

建议 MVP 的 run 规模：

- 1 个世界
- 8~12 个节点
- 1 个最终 Boss
- 1~2 次中途强敌或强事件

理由：

- 这样一次 run 的 AI 调用次数可控
- 也更容易先验证“地图选择有没有意思”
- 如果一开始就做 3 幕长跑，调试成本会显著上升

### 7.3 首版成长系统建议先做“小而硬”的 4 件套

建议优先做：

1. `currency`
   - 货币
2. `consumables`
   - 消耗品
3. `relics/items`
   - 被动强化物
4. `small skill branch`
   - 小型技能分支或专精节点

不建议首版就做：

1. 完整大技能树
2. 复杂背包管理
3. 大量装备栏位
4. 多货币经济系统

因为这些会让第一版很快从“验证玩法骨架”变成“做一个大型 RPG 子系统”。

## 8. 数值与文本设定如何共同参与判定

这是本项目最关键的差异点，必须明确设计口径。

### 8.1 不建议让文本设定无上限地改写数值结果

如果 AI 看到角色设定很帅，就随意让她跨等级反杀，系统很快会失去可预期性。

所以更建议把文本设定的影响限制在以下三类：

1. **分支解锁**
   - 某些设定让角色拥有特殊选项
2. **有限幅度修正**
   - 在可控范围内给予加减成
3. **后果形态变化**
   - 同样是失败，但失败表现可能不同

### 8.2 推荐的判定思路

可以用这样一套口径：

1. 数值层先给出基础成功率 / 伤害区间 / 资源消耗区间
2. 文本设定转成标签或倾向值
3. 标签只做以下事情：
   - 给某类节点增加 / 减少少量修正
   - 解锁特殊事件选项
   - 决定结果文案和附带状态
4. 最终结果必须落在系统允许的 envelope 之内

例如：

- “怯场”标签
  - 在舞台类 / 社交类节点上，降低表现阈值
- “复仇执念”标签
  - 遇到特定敌系时可解锁高风险高收益选项
- “火焰适性”标签
  - 在火系世界里获得额外事件分支

这能让文本设定真的有用，但又不会把平衡完全交给自由发挥。

### 8.3 文本设定最好抽成“可判定标签层”

如果未来要长期做肉鸽，建议不要每次都把整张卡原文扔给模型自己猜重点。

更稳妥的长期方向是增加一层抽象：

- 人格标签
- 风格标签
- 关系标签
- 世界相性标签
- 禁忌 / 执念 / 弱点标签

这些标签可以：

- 由问卷直接生成
- 由规则预设补充
- 或由 AI 首次解析角色卡时生成，再人工确认

这层一旦有了，多世界预设和事件筛选都会稳很多。

## 8.5 2026-04-03 晚间讨论补充共识：战斗应采用“系统约束下的 AI 裁定”

在进一步讨论后，本轮对战斗节点又补了几条更明确的共识。

### 8.5.1 不做纯数值硬算，也不做纯 AI 放飞

战斗不建议走两种极端：

1. 纯数值硬算  
   会过度削弱本项目“角色设定 + 用户意图 + AI 演出”的特色。

2. 纯 AI 自由生成  
   会让胜负、掉血、资源消耗与特殊胜利条件变得过于漂移，长期很难控。

因此更推荐：

- **系统先限定合法结果范围**
- **AI 再在范围内推演故事与结果**

这可以理解为：

- 系统负责“结果带宽”
- AI 负责“结果落点 + 叙事表现”

### 8.5.2 战斗不做细回合制，而做粗粒度节点裁定

首版不建议处理：

- 每回合行动顺序
- 每次攻击精确扣血
- 逐技能 CD / 施法条 / 连击帧

更推荐的表现形式是：

- 进入一个战斗节点
- 用户给出一次主要战术意图
- 系统结合数值、资源、世界规则与敌人模板，给出约束
- AI 一次性裁定整场战斗，并产出：
  - 胜负
  - 损伤结果
  - 资源消耗
  - 特殊后果
  - 战斗战报

也就是说，更接近“竞技场战报节点化”，而不是“战棋化”。

### 8.5.3 用户输入应采用“推荐动作 + 自由意图”

用户已经明确倾向于保留自由度，因此首版不适合做死菜单输入。

推荐方案：

1. 系统展示 2~4 个当前推荐动作
2. 用户可直接选其中之一
3. 用户也可以自由输入一句战术意图
4. 系统先尝试把自由输入归类到已有动作
5. 若归类失败，但语义合理，则生成临时动作意图交给 AI 裁定
6. 只有明显越界时，才做软性驳回或降级

这样既保留跑图效率，也保留“像竞技场一样描述操作思路”的项目特色。

### 8.5.4 动作来源不能写死，应按世界 / 战斗 / 状态动态生成

战斗动作不应是全局固定菜单，而应由三层手工配置叠加：

1. `world actions`
   - 世界预设中的常规动作池
2. `encounter actions`
   - 具体战斗模板追加的特殊动作
3. `character/unlock actions`
   - 由角色 build、物品、标签、遗物等解锁的动作

首版先以**手工配置**为主，未来再考虑引入 AI 动态补动作。

这么做的原因是：

- 世界差异更可控
- 特殊战斗更容易设计特解
- 更容易测试、调平与回溯问题

### 8.5.5 损伤表现采用“内部粗数值 + 外显状态层级”

用户已经同意：

- 内部保留粗数值或区间化 HP / 资源
- 对外主要展示状态层级

因此建议：

- 系统内部保存：
  - `hpCurrent / hpMax` 或离散化生命区间
  - 关键资源消耗
- UI 与叙事外显为：
  - `完好 / 受创 / 重伤 / 濒危`
  - 或更贴近世界语义的状态标签

这样既方便系统判定，也避免首版陷入过细的 UI 与回合演算复杂度。

### 8.5.6 默认失败语义：结束 run，但保留失败战报与少量长期收益

用户已经同意首版默认采用：

- **失败即结束当前 run**
- **但失败会生成失败战报**
- **并给予少量长期收益 / 解锁**

不优先采用：

- 纯粹 Game Over 什么都不给
- 全局默认“带伤继续”

原因是这套默认值最平衡：

- 保留肉鸽张力
- 又不会让失败变成纯浪费
- 还能发挥本项目“失败也能是故事内容”的优势

同时允许未来由世界预设覆写为特殊失败机制，例如：

- 被俘
- 堕落
- 带伤续行
- 特殊败北分支

### 8.5.7 单角色首发，但底层预留小队兼容

用户对“小队制”持开放态度，但为了控制首版复杂度，当前仍建议：

- 首版玩法与主要 UI 先按单角色 run 设计
- 数据结构与 resolver 预留 future squad compatibility

这样能兼顾两点：

1. 首版不被多角色状态同步、奖励分配、AI 提示词膨胀拖慢
2. 后续若要靠近现有竞技场“分队制”味道，不需要推倒重来

## 8.6 2026-04-03 晚间讨论补充共识：长期成长以内容解锁为主

关于 run 外的长期成长，用户已经同意首版采用偏保守方案：

- **长期成长以内容解锁为主**
- **永久数值成长尽量弱化，或首版暂不做**

### 8.6.1 首版优先的长期收益类型

建议首版优先放这些：

1. 世界 / 世界线解锁
2. 事件、敌人、Boss、结局词条解锁
3. 起始可选物、起始动作、起始路线倾向解锁
4. 图鉴、档案、失败分支、特殊文本解锁
5. 某些角色标签或世界标签对应的额外选项解锁

这些奖励更符合本项目的内容沉淀优势，也更适合与“失败战报”“世界认知”结合。

### 8.6.2 首版不建议做强永久数值成长

例如以下内容应谨慎，最好延后：

- 永久增加大量 HP
- 永久提高基础伤害
- 永久让某类 build 明显强于其他 build
- 让玩家必须先刷很多次失败收益，run 才真正可玩

原因：

1. 这会显著削弱 run 本身的紧张感。
2. 早期平衡很容易被永久成长污染，导致很难判断问题出在世界设计、敌人设计还是长期养成。
3. 当前项目的核心吸引力更偏“角色故事、世界体验、生成结果”，不是“长期刷数值”。

### 8.6.3 若要有永久成长，也应尽量做成弱成长或侧向成长

如果首版之后需要加一点长期成长，更推荐：

- 多一个起始动作槽
- 多一个起始物候选
- 开局可重掷一次推荐动作
- 某类世界中更容易遇到特殊事件

也就是：

- 优先增加“玩法选择面”
- 尽量不要直接增加“硬数值碾压能力”

### 8.6.4 这与失败收益是相容的

当前已确认默认失败语义为：

- run 结束
- 生成失败战报
- 给予少量长期收益

这套收益如果以内容解锁为主，会比纯数值奖励更自然：

- 失败不会显得白跑
- 但也不会鼓励玩家故意刷失败拿数值
- 更适合和多世界预设、图鉴、特殊结局、额外动作系统结合

## 9. 多世界预设的建议

### 9.0 2026-04-03 晚间讨论补充共识：首发世界优先做“魔法少女竞技场”

用户已经明确首版优先世界为：

这是当前最稳妥的选择，原因不是“题材最保守”，而是它在本仓库里拥有最完整的现成资产链。

这意味着首版不必重新发明：

- 力量层级

- 基础战斗 / 魔法 / 社交 / 调查技能语义

#### 9.0.2 现成角色池可直接作为敌人与遭遇素材

用户指出两类现成来源，这个判断成立：

1. **预设角色池**
   - 仓库中已有大量魔法少女预设角色
   - 其中包含明确贴近竞技场世界观的角色，例如雪绒等

2. **公开数据卡库**
   - 当前仓库已有公开角色库入口，可用于拉取最新公开角色
   - 支持按类型、搜索、标签、作者、互动指标等做筛选

可参考：

因此，首版竞技场世界的敌人来源可以按优先级设计为：

1. 本地手工维护的预设敌人池
2. 公开角色库筛选得到的动态候选池
3. 随机公开角色兜底

#### 9.0.3 公开角色通常只有文本设定，因此需要“程序补全数值快照”

用户判断也很准确：

- 公开库角色往往以文本设定为主
- 不能假设它们天然带有可直接用于 run 的完整数值卡

因此首版需要明确一个补全边界：

- **敌人加入 run 前，程序先把角色补全成可战斗的快照**

建议流程：

1. 读取角色原始数据卡
2. 若已有 `buildState` 或规则参数，则优先复用
3. 若没有，则根据：
   - 角色文本设定
   - 标签
   - 公开排行或使用度信号
   - 世界预设默认模板
   自动补出一份简化战斗快照
4. 补全结果冻结为本次 run 的敌人数据，不在战斗中再次漂移

这样能避免“同一名公开角色在同一次 run 中，数值口径前后不一致”。

此外，用户已经明确同意：

- **允许任意角色卡进入竞技场世界 run**
- **在开局自动补全一份竞技场快照**

这意味着首版玩家入口不应只限于“已经带竞技场规则参数的角色”，而应支持：

1. 若角色已有 `buildState` / 角色参数，则优先复用
2. 若角色没有，则在开局按竞技场世界规则自动投影出一份临时快照
3. 该快照在本次 run 内冻结，不回写污染原始角色卡

这对用户体验是明显更好的：

- 角色来源更自由
- 公开库与旧角色也能直接参与
- 玩家不会因为“没有先去 `/creator` 车卡”而被挡在玩法外

#### 9.0.3.a 自动补全快照的推荐输入信号

自动补全时，建议优先参考以下信号：

1. 现有规则参数 / `buildState`
2. 角色原卡中的显式强度描述
   - 例如预设角色中常见的 `powerLevel`
3. 角色标签、定位与文本设定
4. 若角色已有公开排位数据，则参考 rating / tier / games
5. 世界预设中的默认补全模板

可参考：

- [`public/presets/M12_greatness_in_simplicity.json`](../../public/presets/M12_greatness_in_simplicity.json)
- [`public/presets/M90_goose.json`](../../public/presets/M90_goose.json)
- [`pages/api/data-card-meta.ts`](../../pages/api/data-card-meta.ts)

也就是说，预设角色介绍里的强度描述并不是纯文案噪声，而是可以作为 run 内补全战斗快照的参考信号。

#### 9.0.4 精英怪与 Boss 很适合接入赛季排行与历史高位角色

用户提出：

- 精英怪 / Boss 可从当前和历史赛季的高排位角色中抽取

这条思路非常好，因为它能自然把竞技场的社区资产接进肉鸽玩法。

仓库内已经有现成排行与赛季快照入口：

- [`components/ranking/RankingPage.tsx`](../../components/ranking/RankingPage.tsx)
- [`/api/arena/leaderboard`](../../components/ranking/RankingPage.tsx#L341)
- [`lib/seasons.ts`](../../lib/seasons.ts)
- [`pages/api/data-card-meta.ts`](../../pages/api/data-card-meta.ts)

建议首版把它设计成：

1. **普通敌人**
   - 优先从当前 / 历史赛季的低中位公开角色池抽取
   - 按 rating / tier 分带控制强度
   - 本地预设池作为稳定补位
2. **精英敌人**
   - 当前赛季中高强度公开角色池
3. **Boss**
   - 当前或历史赛季高位角色池
   - 或手工指定的竞技场代表角色

这里用户又补充了一条很重要的控制原则：

- **普通敌人不应主要靠公开库纯随机抽取**

这个补充非常合理。因为如果普通战斗直接随机公开角色，很容易出现：

- 前几场普通战斗就撞到榜首角色
- 敌人强度波动过大
- run 节奏失真

因此更推荐：

1. 普通敌人主来源：赛季排行中的低中位角色段
2. 精英 / Boss：赛季排行中的高位角色段
3. 公开库随机匹配：仅作为补充内容源或兜底，不作为普通战斗主来源

#### 9.0.4.a 可操作的强度分层建议

首版可以先粗分成几档：

1. `common`
   - 低中位 rating / tier 段角色
2. `elite`
   - 中高位 rating / tier 段角色
3. `boss`
   - 高位、峰值高、或具代表性的角色

同时允许预设角色用自己的强度描述参与校准：

- 若预设自带明显强度定位或 `powerLevel` 描述
- 可用于把它映射到 `common / elite / boss` 档位

这样做的好处是：

- 普通战斗更稳定
- 赛季高位角色能自然承担“强敌感”
- 预设角色不会因为没有在线排行而完全失去参战价值

#### 9.0.5 需要一个离线/失效兜底

虽然“在线数据库即时匹配最新公开角色”很有吸引力，但它本质上是动态数据源，因此首版仍建议准备兜底：

1. 若线上公开库不可用，自动回退到本地预设池
2. 若排行角色已不再公开或数据缺失，则跳过并重抽
3. 对 run 而言，一旦抽取完成，就保存为本地快照，不依赖后续在线状态

也就是说：

- **在线数据源负责扩充内容池**
- **本地快照负责保证 run 稳定**

#### 9.0.6 竞技场世界非常适合先验证“AI 裁定战斗”

之所以首发世界选竞技场，不只是因为有角色和规则，更因为它天然兼容当前已确认的战斗模型：

- 允许用户输入战术意图
- 允许角色设定影响战斗结果
- 又不必强行做成细回合制

换句话说，竞技场世界能最顺滑地验证：

- 推荐动作 + 自由意图
- 系统约束下的 AI 裁定
- 粗数值 + 状态层级
- 失败战报
- 排名高位角色作为强敌/Boss

### 9.1 不同世界应该共享框架，但不能共享语义

你的判断是对的：

- 总体框架一致
- 世界规则和设计不同

建议把“共框架”与“异语义”拆清楚。

### 9.2 建议每个世界预设至少定义以下内容

1. 基础资源模型
   - 例如 HP / 金钱 / 理智 / 光辉 / 热度 / 嫌疑值
2. 节点权重
   - 事件多、战斗多、商店多，还是偏长线剧情
3. 敌人与事件池
4. 世界专属标签规则
5. 结局与失败语义
6. AI 提示词风格包

换句话说，世界预设不应该只是一组美术皮肤，而要真正定义“这世界里什么才算一次 run”。

### 9.3 适合优先尝试的世界

如果结合仓库现有内容，我更推荐优先考虑这几类：

1. **魔法少女竞技场世界**

2. **魔女审判 / 监狱岛世界**
   - 很适合做高压力事件链、嫌疑值、审判阶段
3. **少女乐队 / 对邦世界**
   - 适合把“战斗”换成“演出 / 对邦 / 舆论 / 创作压力”

这三类都能证明“同一骨架、不同世界语义”是可行的。

## 10. 存档与数据结构建议

### 10.1 存档层建议直接沿用 AI session 的思路

建议新增类似下面的对象层：

1. `roguelikeWorldProfiles`
   - 已解锁世界与世界级配置
2. `roguelikeRuns`
   - run 主记录
3. `roguelikeRunNodes`
   - 已经过的节点记录
4. `roguelikeRunCheckpoints`
   - 关键快照
5. `roguelikeUnlocks`
   - 解锁内容
6. `roguelikeRunDigests`
   - 摘要与回顾

### 10.2 自动保存节点

建议至少在以下时机自动保存：

1. 创建 run 后
2. 进入节点前
3. 节点结算后
4. 领取奖励后
5. 通关 / 失败后

这样即使 AI 节点生成中断，也不会把整局 run 弄坏。

### 10.3 不建议每次都回放完整历史

和连续战报一样，肉鸽也不应该每次把所有历史全文重新喂给模型。

更好的做法是：

- 保存当前状态快照
- 保存最近 1~2 个节点摘要
- 保存 run 累计摘要
- 保存角色关键变化摘要

这样能显著降低 token 消耗。

## 14. 当前最值得先确认的开放问题

1. 首版 run 是以“**单角色**”为主，还是允许“**小队**”进入？
   - 我倾向先做单角色或 1 主角 + 轻伴随层，复杂度更可控。

2. 玩家在节点里是只做“**选路**”，还是还要做“**节点内选项**”？
   - 我建议保留节点内选项，因为这正好能让 AI 叙事发挥价值。

3. meta progression 首版是做“**纯内容解锁**”，还是做“**数值永久成长**”？
   - 我更建议先做内容解锁或弱数值解锁，避免早期平衡崩得太快。

4. 失败后的语义是什么？
   - 完全失败重开
   - 带失败日志与少量解锁
   - 或世界特定的 fail-forward

5. 文本设定的“标签抽取”要不要在第一版做？
   - 如果不做，就先手工定义少量标签入口
   - 如果要做，必须保证结果可校验、可复用

1. 先把它定义为“**路径式叙事肉鸽**”
2. 首版先做“**一个世界 + 一个短 run + 六类节点 + 本地 IndexedDB 存档**”
3. 用系统结算数值骨架，用 AI 负责战斗 / 事件结果的表现
4. 把角色文本设定先做成“**有限加成 + 特殊分支解锁**”，不要无上限影响平衡
5. 等第一轮验证完成，再决定是否引入更重的技能树、物品体系或长期 meta progression

这是我认为**最能发挥本项目特色、同时风险最低**的切入方式。
