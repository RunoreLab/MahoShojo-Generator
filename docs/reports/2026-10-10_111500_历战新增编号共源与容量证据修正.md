## 复现与最小修复

旧 Next 从最后条目的 `id + 1` 取号，`"legacy"` 会得到 `"legacy1"`，9 MiB 字符串会完整复制到新条目。茶会只认末条 number，`[2, 1]` 再分配 2；domain 原先扫描全部 finite number 的最大 floor + 1，但安全整数边界仍会越界，再次递增可能不增长。repair-create 的旧 safe-integer max + 1 同样可能越界。

共同纯 helper 为 `@mahoshojo/domain/arena-history-id`，上述四条真实写入路径直接使用它：

1. 全部正有限数值 ID 取最大 floor，正常从该值加一开始
2. 新 ID 永远为正安全整数，遇到安全上界改从 1 找最小空位；不依赖历史排序
3. canonical 正整数数字字符串只占用同一显示编号，不迁移为 number，也不抬高数值序列；例如 number 1 与 string `"2"` 后追加 number 3
4. `"01"`、`"1e0"`、空白、任意旧文本均不强制转号；字符串先判长度，超过 16 个 code unit 不转换
5. 不改旧编号、不排序、不消除既有重复，不扩宽 `ArenaHistoryEntrySchema` 的 number-optional 写入规范

编辑器按原数组位置删除，编号只作 `String(id)` 展示，因此没有引入第二种身份匹配语义。缺号、未命名、空数组、重复和乱序 number、数字字符串、超长旧字符串及极大数均有目标回归。

为保证追加过程不会清理旧数据，同步保住三个局部损耗点：domain 不再过滤 entries 内无法预览的旧值；Next 在缺少可选 attributes 时保留已有数组和 history 扩展；茶会保留 history/attributes 的未知扩展。helper 不修改输入；追加不修改输入卡内容及旧历史，旧条目的内容与顺序原样保留。Next 原有 fallback 对不可支持的非 record attributes / 非 array entries 保持既有默认处理；本片不引入通用旧卡迁移或重建。升华已有的重编号策略未改。

Hosted 原冻结 legacy fixture 保留原件；仅 `legacy-history + writeHistory` 两个 golden case 显式修正 oracle 为保留原 opaque entries，并由既有真实签名服务签署期望结果。其它完整载荷、原生性因果与 generation 幂等比较保持。

## 容量证据的精确分层

修复后的新编号不再复制旧长字符串。前次验收中的 16 MiB 真实 producer recipe 是旧树真实结果，历史报告与原件仍保留；它不能用作当前树 producer 可达性证明。

本片外部 recipe 生成两组独立 manifest，不提交大 fixture：

- 实际 producer：12,582,911 B 输入（12 MiB 减 1），含动态生成的 9 MiB 字符串旧 ID，经真实 Next handler、owner/D1 reader 和未修改的 producer 得到 12,583,469 B 响应；旧 ID 原样保留，新 ID 为 number 1
- 传输防御：测试 spy 仅在真实 producer 返回后加入明确标记的 padding，构造 16,777,216 B 和 16,777,217 B 合成响应。真实 handler 与协议 parser 分别接受恰好上限、拒绝上限加一；后者返回 503，未交付部分角色
- 同四份原始 JSON 已逐份通过真实 Native loopback/Channel 与生产 TS bridge：实际 producer 195 条消息、恰好 16 MiB 合成体 258 条消息、加一体零 IPC、503 错误体 263 B / 3 条消息；逐字节 SHA-256 一致。四条 TS 条件测试均显式执行且通过，没有依赖缺省 skip
- 不把合成边界称为合法输入可达的 producer 容量，也不据此证明所有合法请求响应的数学上界

32 角色、12 MiB 请求、64 KiB effects manifest、16 MiB 角色响应预算与原 64 KiB 文本片 / 512 KiB IPC 封套均未改变。
