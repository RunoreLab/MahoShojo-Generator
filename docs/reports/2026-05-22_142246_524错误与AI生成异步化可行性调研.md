# 524 错误与 AI 生成异步化可行性调研

更新时间：2026-05-22 14:22:46
状态：`research`
归类：`docs/reports/` `cloudflare` `ai-generation` `d1` `async-job`

## 1. 本轮目标

近期大量用户报告 524 错误。当前判断是：AI 生成耗时过长，HTTP 连接在 Cloudflare 侧超时或断开，导致用户无法拿到结果。

本报告回答三个问题：

1. “连接超时后重新开连接，从数据库查生成结果”是否可行。
2. 在 Cloudflare Edge Runtime + D1 的当前项目里，哪些做法可靠，哪些只是看起来可行。
3. 后续如果要落地，推荐采用怎样的任务状态、API 与存储边界。

## 2. 结论

该方向**可行**，但核心不是“请求里顺手写数据库”，而是把 AI 生成改造成**可恢复的异步任务**：

1. 首个请求只负责校验、扣频控、创建任务记录，并尽快返回 `jobId`。
2. 真正的 AI 生成必须在独立任务执行环境中运行，例如 Cloudflare Queues consumer 或 Cloudflare Workflows。
3. 生成过程把状态、错误、结果摘要和最终产物写入 D1；产物过大时写入 R2，并在 D1 存引用。
4. 前端断线、刷新或遇到 524 后，可以用 `jobId` 重新查询任务状态。

如果仍然让 AI 生成绑定在当前 HTTP 请求生命周期里，**即使有 D1，也不能可靠解决丢失问题**。原因是客户端断开后，Cloudflare Workers/Pages 会取消该请求关联的任务；`waitUntil()` 只能把取消延后最多约 30 秒，不能把一个数分钟级 AI 生成变成稳定后台任务。

## 3. 外部约束调研

### 3.1 524 的直接含义

Cloudflare 官方文档说明：524 表示 Cloudflare 已经成功连接到源站，但源站没有在默认 120 秒 Proxy Read Timeout 内返回 HTTP 响应。官方给出的规避方向之一就是对长 HTTP 过程实现状态轮询。

这说明用户的直觉方向是对的：长生成不应该让浏览器一直等同一个响应。

来源：

- Cloudflare Support：Error 524，默认 120 秒 Proxy Read Timeout，并建议对大型 HTTP 过程实现 status polling。
- Cloudflare Fundamentals：Proxy Read Timeout 为 120 秒，达到限制时返回 524，Enterprise 可配置。

### 3.2 Workers/Pages 的请求生命周期限制

Cloudflare Workers 文档里有两个关键点：

1. HTTP 触发的 Worker 在客户端保持连接时没有硬性 wall time 上限。
2. 客户端断开后，与请求关联的任务会被取消；`event.waitUntil()` 最多只能延后约 30 秒。

因此，流式输出确实可以缓解 524，因为连接持续收到数据时不容易触发代理读超时；但它不能保证“用户断线后后台继续生成”。如果上游模型很久才返回首字、浏览器/网络中断，或 Cloudflare 连接被动断开，当前请求仍然会失败。

来源：

- Cloudflare Workers Limits：HTTP 请求在客户端保持连接时无硬性 duration 限制；客户端断开后任务取消，`waitUntil()` 只能延后最多 30 秒。
- Cloudflare Workers Context：`ctx.waitUntil()` 可在响应返回后继续短尾工作，但不是长任务执行器。

### 3.3 D1 能承担任务状态，但不应承担所有大产物

D1 适合作为任务状态库：任务 ID、状态、用户归属、输入摘要、错误信息、进度、最终结果引用，都很适合存 D1。

需要注意的限制：

1. D1 单个字符串、BLOB 或行大小上限为 2 MB。
2. 单条 SQL 查询时长上限为 30 秒。
3. 单个 D1 数据库是单线程处理查询；高并发写入需要避免热行与大事务。

这意味着：常规角色卡 JSON / Markdown 结果可以直接存 D1；长篇战报、带 reasoning 的长输出、未来多附件或图片类结果，应继续沿用项目已有的 `large_objects` + R2 引用模式。

来源：

- Cloudflare D1 Limits：最大字符串/BLOB/行 2 MB，最大 SQL 查询时长 30 秒，D1 数据库单线程处理查询。

### 3.4 Queues 与 Workflows 的适配性

Cloudflare Queues 用于异步处理、重试和延迟消息。consumer invocation 的 wall time 上限是 15 分钟，并支持默认重试、显式 ack、延迟重试和 dead-letter queue。

Cloudflare Workflows 更适合长链路和可恢复多步骤任务。官方限制显示 Workflows 每个 step 的 wall time 可为 unlimited，Workflow instance 可长期运行，只要不超过 CPU 与步骤数限制。

对本项目的含义：

- 如果目标是先解决 120 秒级别的 524，Queues 足够适合第一版。
- 如果目标是支持多阶段生成、用户确认、数分钟到更长的任务恢复，Workflows 更适合作为后续升级方向。

来源：

- Cloudflare Queues Overview / Batching, Retries and Delays / Dead Letter Queues。
- Cloudflare Workers Limits：Queue consumer wall time 15 分钟。
- Cloudflare Workflows Limits：每个 step wall time unlimited，实例可长期运行。

## 4. 当前仓库现状

### 4.1 生成接口仍以请求生命周期为主

当前自由生成接口：

- `pages/api/generate-free.ts`
  - 非流式 JSON 生成，调用 `generateWithAI()` 后直接返回结果。
- `pages/api/generate-free-stream.ts`
  - 流式 Markdown 生成，调用 `generateWithStreamAI()` 后直接返回响应流。
  - 传入了 `abortSignal: req.signal`，因此客户端断开时，上游流式请求会被取消。

当前战报流式接口已经做了更完善的完成后审计：

- `pages/api/arena/generate-stream.ts`
  - 包装响应流，收集输出预览与统计信息。
  - 在完成、中断或失败后写入 `battle_report_generations`。

但 `battle_report_generations` 的定位仍然更接近“生成审计日志 / 历史记录”，不是“生成任务控制表”。它的状态只有 `completed`、`aborted`、`failed`，缺少 `pending`、`processing`、重试计数、幂等键、轮询游标、可恢复输入、取消语义等任务字段。

### 4.2 仓库已有可复用基础

已有基础对异步化有利：

1. D1 与 Drizzle 已接入，schema 与 repository 分层清晰。
2. `large_objects` 已存在，可用于把大输出转到 R2，仅在 D1 保存引用。
3. `battle_report_generations` 已经沉淀了 AI 模型、token、输出预览、敏感词状态等审计字段，适合作为后续任务完成后的统计来源或被新任务表引用。
4. 前端已有流式与非流式两套生成体验，可以渐进迁移，不需要一次性替换所有入口。

## 5. 可选方案比较

### 5.1 方案 A：在当前请求内写 D1，然后轮询

做法：

- 请求开始时写入 `processing`。
- 请求内继续调用 AI。
- 生成成功后写入 `succeeded`。
- 前端若超时，再查 D1。

判断：**不推荐作为可靠方案**。

问题：

1. 客户端断开后请求关联任务可能被取消，后续 AI 调用和 D1 写入不保证执行。
2. `waitUntil()` 最多只适合短尾记录，不足以承载数分钟生成。
3. 当前流式接口显式传入 `req.signal`，断线会取消上游请求。

这个方案只能改善“生成已经完成但响应返回失败”的极小窗口，不能解决主要问题。

### 5.2 方案 B：D1 任务表 + Cloudflare Queues

做法：

1. `POST /api/generations` 校验输入、敏感词、频控和权限。
2. 写入 `ai_generation_jobs`，状态为 `pending`。
3. 向 Queue 发送 `{ jobId }`。
4. 立即返回 `202 Accepted`：`{ jobId, status: "pending", pollAfterMs: 1500 }`。
5. Queue consumer 读取任务、置为 `processing`、调用 AI、写入结果。
6. `GET /api/generations/:jobId` 返回任务状态和结果。

判断：**推荐作为第一阶段方案**。

优点：

1. 与 HTTP 连接解耦，浏览器断线不会天然丢任务。
2. D1 能提供稳定状态查询。
3. Queues 自带重试、延迟重试和 DLQ，适合处理上游 429、5xx、网络抖动。
4. 对前端改造可渐进：先给最容易 524 的入口接入后台生成。

风险：

1. Queue consumer 单次 invocation 仍有 15 分钟 wall time 上限。
2. 需要设计幂等：同一 `jobId` 被重复投递时，不能重复写最终结果或重复扣费。
3. 用户自定义 API Key 不能明文落库；这类请求需要单独策略。

### 5.3 方案 C：D1 任务表 + Cloudflare Workflows

做法：

- `POST /api/generations` 创建任务后启动 Workflow instance。
- 每个 Workflow step 处理安全检查、生成、结构化修复、存储、通知。

判断：**适合第二阶段或长任务升级**。

优点：

1. 更适合多步骤、可恢复、长等待任务。
2. 每个 step 可有更长 wall time，天然适合“生成、修复、再生成、总结、入库”等链路。
3. 可表达更复杂的重试与补偿逻辑。

风险：

1. 接入复杂度高于 Queues。
2. 需要确认当前 Cloudflare Pages 部署链路、wrangler 配置和本地测试方式是否已经准备好 Workflows。

### 5.4 方案 D：保留流式直出，增加任务兜底

做法：

- 用户点击生成后先创建 `jobId`。
- 如果模型能快速流式返回，页面继续显示流式内容。
- 同时把最终内容写入任务表或 R2。
- 如果连接中断，前端凭 `jobId` 进入轮询/恢复页。

判断：**体验最好，但应建立在方案 B 或 C 的任务底座之上**。

它不应实现成“一个 HTTP 请求既负责流式传输，又负责唯一后台执行”。正确边界是：任务存在于后台执行器，流式连接只是一个观察通道。

## 6. 推荐落地形态

### 6.1 第一阶段范围

建议先选择最容易触发 524、且结果天然可离线领取的入口做试点：

1. 自由生成非流式：`/api/generate-free`
2. 战报生成：`/api/arena/generate-stream` 或相关 PVP / battle story 长生成入口

不建议第一阶段覆盖所有流式聊天式能力。对话类交互对实时性更敏感，后台化后还需要处理消息顺序、用户取消和上下文过期，复杂度更高。

### 6.2 数据模型建议

新增 `ai_generation_jobs`，数据库层使用 `snake_case`，TypeScript DTO 使用 `camelCase`。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | text primary key | 任务 ID，对外返回 `jobId` |
| `kind` | text | `free_card`、`arena_story`、`pvp_round` 等 |
| `status` | text | `pending`、`processing`、`succeeded`、`failed`、`cancelled`、`expired` |
| `user_id` | integer null | 登录用户归属 |
| `activity_user_key` | text null | 未登录活动身份归属，避免匿名用户无法找回 |
| `idempotency_key` | text null | 防止重复提交 |
| `input_hash` | text | 输入摘要，用于排查与幂等 |
| `input_json` | text | 生成必要输入；需避免保存明文用户 API Key |
| `provider_json` | text null | 模型与供应商快照，不含密钥 |
| `result_json` | text null | 小结果直接存储 |
| `result_object_kind` | text null | 大结果类型，例如 `ai_generation_result` |
| `result_object_ref_id` | text null | 对应 `large_objects.owner_ref_id` 或 R2 引用 |
| `progress_json` | text null | 阶段、预览、token 等进度 |
| `error_code` | text null | 稳定错误码 |
| `error_message` | text null | 用户可理解错误摘要 |
| `attempt_count` | integer | 已尝试次数 |
| `locked_at` | text null | consumer 幂等锁 |
| `started_at` | text null | 处理开始时间 |
| `finished_at` | text null | 处理结束时间 |
| `expires_at` | text | 结果保留期限 |
| `created_at` | text | 创建时间 |
| `updated_at` | text | 更新时间 |

推荐索引：

1. `(user_id, created_at)`
2. `(activity_user_key, created_at)`
3. `(status, updated_at)`
4. unique `(user_id, idempotency_key)`，仅在 `idempotency_key IS NOT NULL` 时生效

### 6.3 API 契约建议

创建任务：

```http
POST /api/generations
```

请求体按业务类型分发，例如：

```json
{
  "kind": "freeCard",
  "payload": {
    "schema": "general",
    "prompt": "...",
    "language": "zh-CN"
  },
  "idempotencyKey": "client-generated-key"
}
```

响应：

```json
{
  "jobId": "gen_...",
  "status": "pending",
  "pollAfterMs": 1500
}
```

查询任务：

```http
GET /api/generations/{jobId}
```

响应：

```json
{
  "jobId": "gen_...",
  "kind": "freeCard",
  "status": "processing",
  "progress": {
    "stage": "generating",
    "preview": "..."
  },
  "result": null,
  "error": null,
  "updatedAt": "2026-05-22T06:22:46.000Z"
}
```

成功后：

```json
{
  "jobId": "gen_...",
  "kind": "freeCard",
  "status": "succeeded",
  "result": {
    "templateId": "通用角色",
    "name": "...",
    "content": "..."
  },
  "error": null
}
```

取消任务：

```http
POST /api/generations/{jobId}/cancel
```

取消只能保证“未开始或下一次检查点停止”。已经发给上游模型的请求不一定能立刻取消，尤其是在 Queue consumer 中没有持续可用的客户端 abort signal。

### 6.4 前端体验建议

1. 点击生成后立即进入任务态，显示“生成中”。
2. 前 60-90 秒可保持现有流式体验；超过阈值后提示“已转入后台，可稍后回来查看”。
3. 页面刷新后从 `jobId` 或“最近任务列表”恢复。
4. 524 或网络错误时，不直接判定失败；如果前端持有 `jobId`，应自动切换到查询任务。
5. 任务成功后允许一键写入当前卡片结果区，避免用户感知为“去了另一个系统”。

### 6.5 用户自定义 API Key 的特殊处理

当前自由生成支持用户自定义供应商和 API Key。异步化时不能把用户 API Key 明文写入 D1。

可选处理：

1. 第一阶段：自定义 API Key 请求仍走前台流式/非流式，不进入后台队列。
2. 后续：只允许用户保存加密后的 provider credential，并通过服务器端密钥解密使用。
3. 或要求用户自定义 provider 使用短期一次性 token，但这需要额外凭据系统，不建议第一阶段做。

推荐第一阶段采用第 1 种：后台任务只支持系统供应商，先解决公共模型长生成的 524。

## 7. 错误处理与幂等

### 7.1 状态流转

推荐状态机：

```text
pending -> processing -> succeeded
pending -> processing -> failed
pending -> cancelled
processing -> cancelling -> cancelled
processing -> failed -> pending    (仅限可重试错误)
pending/processing -> expired      (后台清理)
```

### 7.2 可重试与不可重试

可重试：

1. 上游 429。
2. 上游 5xx。
3. 网络超时。
4. Queue consumer 暂时失败。

不可重试：

1. 输入参数无效。
2. 敏感词拦截。
3. 用户无权限或额度不足。
4. 用户自定义供应商凭据无效。
5. Schema 校验在多次修复后仍失败。

### 7.3 幂等要求

1. 创建任务时使用 `idempotencyKey`，防止浏览器重试创建多个任务。
2. Queue consumer 必须在写结果前检查当前状态；只有 `pending` 或可重试 `failed` 能进入 `processing`。
3. 结果写入与状态置为 `succeeded` 应尽量在同一个逻辑事务或最小写入窗口中完成。
4. 重复投递同一 `jobId` 时，如果任务已 `succeeded`，consumer 应直接 ack。

## 8. 安全、配额与滥用控制

异步化会降低用户等待成本，也会提高滥用风险。必须前置以下限制：

1. 创建任务前执行敏感词检查，失败任务不入队或直接入库为 `failed`。
2. 创建任务前执行当前 public AI 频控；不要等到 consumer 才发现超额。
3. 限制每个用户/活动身份同时 `pending + processing` 的任务数。
4. 设置任务结果过期时间，例如 7-30 天。
5. 对匿名用户，必须有可恢复身份键；否则刷新后无法查询自己的任务。
6. 查询任务必须校验所有权，不允许通过猜 `jobId` 查看他人结果。
7. 后台任务的输入快照需要脱敏，不保存用户 API Key、Cookie、完整 IP 等敏感信息。

## 9. 与现有表的关系

不建议直接把 `battle_report_generations` 改造成通用任务表。原因：

1. 它已承载战报审计语义，字段很重。
2. 它缺少任务生命周期字段。
3. 自由生成、情景卡、战报、PVP 判定的输入和结果结构差异较大。

推荐关系：

1. 新增 `ai_generation_jobs` 作为任务控制表。
2. 战报类任务成功后，继续写 `battle_report_generations` 作为审计和历史记录。
3. 长输出沿用 `large_objects` + R2。
4. `ai_generation_jobs.result_object_ref_id` 可以引用 `large_objects.owner_ref_id`，但不做数据库外键，避免跨存储强耦合。

## 10. 推荐实施顺序

### Phase 1：观测与止血

1. 在现有生成接口里记录请求耗时分布、上游首字节耗时、完成耗时、524 前后相关 `cf-ray`。
2. 前端捕获 524 / network error，并把错误提示改为“生成可能仍在进行，稍后可重试/恢复”的保守文案。
3. 对最慢模型或最长故事长度增加前端预期提示。

### Phase 2：任务表与状态查询

1. 新增 `ai_generation_jobs` schema、repository、mapper 和 contract test。
2. 新增创建任务与查询任务 API。
3. 先用模拟 worker 或本地直接执行验证状态流转，不接真实 Queue。

### Phase 3：Queues 接入

1. 配置 producer / consumer / DLQ。
2. consumer 按 `jobId` 拉取任务，执行系统供应商生成。
3. 写入结果、错误、重试次数和审计字段。
4. 前端在 524 或刷新后能恢复任务。

### Phase 4：体验整合

1. 对自由生成和战报入口接入“后台生成 + 轮询”。
2. 保留流式输出作为实时观察通道，而不是唯一执行通道。
3. 增加“我的生成任务”轻量列表，帮助用户找回结果。

### Phase 5：长任务升级

当 Queues 的 15 分钟 invocation 上限或多步骤恢复变成瓶颈时，再评估 Cloudflare Workflows。

## 11. 最终建议

建议采用：

```text
D1 任务表 + Cloudflare Queues + 结果轮询
```

作为第一版方案。

这条路线能直接解决 524 的主要成因：HTTP 连接不再是生成成功与否的唯一载体。D1 负责“任务是否成功、结果在哪里”，Queues 负责“连接断开后继续执行和重试”，R2 负责“大结果存储”。

不建议把 `waitUntil()` 或“当前请求内写库”作为主方案。它们适合审计日志、尾部清理、短时间通知，不适合承载用户可恢复的长 AI 生成。
