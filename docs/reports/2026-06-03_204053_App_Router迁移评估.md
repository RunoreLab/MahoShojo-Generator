# App Router 迁移评估

> 调研时间：2026-06-03 20:40:53（Asia/Shanghai）  
> 适用项目：`MahoShojo-Generator`  
> 背景：项目已迁移到 `@opennextjs/cloudflare`，当前为 Pages Router 为主、局部 App Router 的双 Router 状态。

## 结论

建议继续迁移到 App Router，但不建议做一次性全量重写。

更合适的路线是：先把 `pages/api/*` 迁到 `app/api/*/route.ts`，再建立 App Router 的全局 `layout` 与页面壳，最后按业务岛迁移页面。这样可以尽快减少双 Router 带来的维护成本，同时避免一次性触碰 33 个页面和 125 个 API 路由造成不可控回归。

短期优先级建议为 P1，不是 P0。当前项目已经能通过 OpenNext Cloudflare 链路运行，App Router 迁移的收益主要是长期维护、路由一致性、布局/metadata 收编和未来 Server Component 能力，不是立即修复线上阻断问题。

## 当前仓库状态

### 路由结构

本地静态检索结果：

1. `pages/` 顶层页面：33 个。
2. `pages/api/` API 文件：125 个。
3. `app/api/auth/*` 已存在 Route Handler 形态的认证路由。
4. `pages/_app.tsx` 负责全局样式、默认 `<Head>`、顶部导航、公告条和 Google Analytics。
5. `pages/_document.tsx` 负责 `lang="zh-CN"` 与首次渲染前的 color mode 初始化脚本。

当前实际结构是：

```text
app/
  api/auth/*        # 已迁移的认证 Route Handlers
pages/
  *.tsx             # 主页面仍在 Pages Router
  api/**/*.ts       # 大部分业务 API 仍在 Pages API 文件布局中
```

### API 形态

虽然文件仍在 `pages/api`，但绝大多数 API 已经不是传统 `NextApiRequest/NextApiResponse` 写法，而是 Web `Request`/`Response` 写法再通过适配器导出：

```ts
export default withPagesApiResponse(handler);
```

相关文件：

1. `lib/pages-api-adapter.ts`
2. `tests/pages-api-adapter.test.ts`
3. `tests/pages-api-edge-runtime.test.ts`

这说明 API 迁移到 App Router 的工程成本相对可控：很多接口可以从“适配 Pages API 响应”改为“直接导出 `GET/POST/...`”。风险主要来自动态路径参数、流式响应、子请求鉴权、Cookie/header 透传，以及 Cloudflare 预览链路验证。

### 页面形态

页面迁移难度高于 API：

1. 页面与组件大量使用 `next/router`，包括 `pages/*`、`components/*`、`lib/use-next-router.ts`、`lib/magic-tea-party/*`、`components/arena/*`、`components/pvp/*` 等。
2. 多个页面使用 `next/head`，迁移后需要转为 `metadata`、`generateMetadata` 或页面内客户端侧 head 替代方案。
3. 当前没有发现 `getServerSideProps/getStaticProps/getStaticPaths/getInitialProps` 的明显依赖，页面主要是客户端工作台型应用。这降低了数据获取迁移难度，但也意味着 App Router 的 Server Component 收益不会自动出现。
4. 顶部导航和公告条集中在 `pages/_app.tsx`，迁移 App Router 时需要设计 `app/layout.tsx` 与客户端 Providers，而不能简单移动文件。

## 外部依据

### OpenNext Cloudflare 支持矩阵

OpenNext Cloudflare 官方文档显示，当前适配器支持：

1. App Router
2. Route Handlers
3. Dynamic routes
4. SSR / SSG
5. Middleware
6. Pages Router
7. ISR
8. Turbopack

同一文档还说明，使用 `@opennextjs/cloudflare` 时应用应使用 Next.js 的 Node.js runtime，因为 Cloudflare Workers runtime 提供了部分 Node.js API；这与旧 `@cloudflare/next-on-pages` 只支持 Edge runtime 的约束不同。

对本项目的含义：

1. 完成 OpenNext Cloudflare 迁移后，继续迁 App Router 不再被部署适配器阻挡。
2. 不应把“App Router”误解为必须显式 `runtime = 'edge'`。当前 `app/api/auth/*` 已经没有显式 runtime 导出，后续应继续以 OpenNext Cloudflare 的实际构建结果和预发验证为准。
3. `next.config.ts` 当前已将 `images.unoptimized = true`，这与 Cloudflare Workers 默认图片优化限制保持一致；迁 App Router 不应顺手改动图片策略。

### Next.js 官方迁移方向

Next 官方 App Router 迁移文档强调可以从 Pages Router 渐进迁移到 App Router，且新旧 Router 可以在一个项目中共存。Next 官方 Route Handlers 文档则将 `app/api/**/route.ts` 作为 App Router 的 API 入口。

对本项目的含义：

1. 技术上可以分批迁移，不需要冻结业务做大爆炸重写。
2. 但 App Router 与 Pages Router 共存期间，页面跨 Router 导航与预取体验存在差异，因此不应长期保留“主导航一半 Pages、一半 App 页面”的状态。
3. 最合理的顺序是先迁 API，因为 API 不涉及页面导航体验；页面迁移要按导航/布局边界成批推进。

> 注：本次 shell 环境对 `nextjs.org` 出现 TLS handshake failure，未能直接抓取 Next 官方正文；本文保留官方文档链接作为参考，强结论主要来自本地代码检索和 OpenNext Cloudflare 官方支持矩阵。

## 是否值得迁移

### 值得迁移的理由

1. 减少双 Router 维护成本  
   当前认证 API 已在 `app/api`，其余业务 API 仍在 `pages/api`。继续保留会让新功能需要反复判断放在哪个 Router，测试和约定也会分裂。

2. 移除 `withPagesApiResponse` 适配层  
   现有 API 已经大量使用 Web `Response`，继续放在 `pages/api` 只是为了适配文件布局。迁到 Route Handlers 后可以直接导出 Web 标准响应，降低一层自定义兼容代码。

3. 统一鉴权与 Cloudflare 运行时入口  
   Auth 已经先行迁入 App Router。将受保护业务 API 也迁到 App Router 后，`requireAuthUserForApp`、Cookie 会话、Cloudflare Access 透传等链路更容易统一。

4. 收编全局布局、SEO metadata 与跨页面 UI  
   `_app.tsx` 和 `_document.tsx` 的职责可以拆到 `app/layout.tsx`、客户端 Providers 和 metadata 配置中。后续页面标题、描述、Open Graph、脚本放置会更清晰。

5. 为后续 Server Component / streaming / cache 能力留出空间  
   当前页面多为客户端工作台，不会立刻从 Server Components 获得显著收益。但百科、排行榜、公开数据列表、消息摘要等读多写少区域未来可以逐步引入 App Router 数据获取和缓存边界。

### 不应立即全量迁移的理由

1. 页面数量和业务面太大  
   33 个页面覆盖生成、竞技场、PVP、角色管理、消息、徽章、众查、百科等。全量迁移会同时触碰导航、登录态、草稿、流式生成和本地存储。

2. `next/router` 依赖广泛  
   App Router 中需要使用 `next/navigation`，但它的 API 与 Pages Router 的 `NextRouter` 不完全等价。不能只做全局替换。

3. 当前 App Router 收益主要是架构收益，不是性能必然收益  
   大量页面本质是客户端交互工具，迁移为 App Router 后如果仍全部 `use client`，首屏与交互性能不会自动大幅改善。

4. Cloudflare 真实链路仍是验收重点  
   本地 `next build` 通过不等于 OpenNext Cloudflare preview/deploy 全链路通过，尤其是流式响应、D1 binding、R2、Cookie、多 Set-Cookie header 和子请求鉴权。

## 推荐迁移路线

### 阶段 0：迁移准备与门禁

目标：建立不影响业务的迁移规则。

建议动作：

1. 新增或更新内部约定：新 API 默认写 `app/api/**/route.ts`，不再新增 `pages/api`。
2. 保留 `withPagesApiResponse`，但标记为迁移期适配器。
3. 建立路由迁移清单，记录每个 API/页面的状态：`pages`、`dual-test`、`app`、`removed`。
4. 明确 App Router route 文件默认不显式声明 `runtime`；如确需声明，必须先通过 `pnpm run build:cf` 和预发验证。

阶段验收：

```bash
pnpm test
pnpm lint
pnpm run build:cf
```

### 阶段 1：API 优先迁移

目标：先摆脱后端双 Router。

推荐顺序：

1. 低风险只读 API：`get-presets`、`get-scenario-presets`、`tags`、`public-data-cards`、`public-decks`。
2. 已有充分测试的业务 API：`data-cards`、`decks`、`favorites`、`badges`、`messages`。
3. 认证相关依赖 API：`me/*`、`user-capacity`、`redeem-code`。
4. 流式 AI API：`generate-*-stream`、`arena/generate-stream`、`challenge/adjudicate-stream`、`pvp/**/resolve-stream`。

迁移模式：

```text
pages/api/foo/bar.ts
  -> app/api/foo/bar/route.ts

pages/api/pvp/rooms/[roomId]/rounds/[roundId]/resolve.ts
  -> app/api/pvp/rooms/[roomId]/rounds/[roundId]/resolve/route.ts
```

代码组织建议：

1. 把业务处理函数保留为 `(req: Request) => Promise<Response>`。
2. Route Handler 文件只做 HTTP method 导出与参数拼接。
3. 动态参数通过 `context.params` 传入；不要在业务函数里重复解析 pathname，除非已有兼容需求。
4. 流式接口迁移后必须单独验证：取消、超时、SSE header、客户端断开、上游 abort。

每批验收：

```bash
pnpm test tests/<相关测试>.test.ts
pnpm test
pnpm lint
pnpm run build:cf
pnpm preview
```

API 阶段完成标准：

1. `pages/api` 为空或仅剩明确标注的兼容路由。
2. `tests/pages-api-edge-runtime.test.ts` 删除或改为断言不再新增 Pages API。
3. `lib/pages-api-adapter.ts` 没有生产调用点。

### 阶段 2：App Router 全局壳

目标：让页面迁移有稳定公共外壳。

建议动作：

1. 新建 `app/layout.tsx`，迁入：
   - 全局 CSS import
   - `lang="zh-CN"`
   - favicon / 默认 metadata
   - Google Analytics
2. 新建客户端 Providers 组件，承载：
   - `GlobalTopBar`
   - `AnnouncementTicker`
   - color mode 初始化后的客户端状态
   - 未来 React Query Provider（如需要）
3. 将 `_document.tsx` 中 color mode 初始化脚本改造为 App Router 可用方案。优先考虑 `beforeInteractive` 脚本或内联脚本，目标是避免暗色模式首屏闪烁。
4. 不立即删除 `_app.tsx/_document.tsx`，直到 Pages 页面全部迁移完成。

阶段验收：

1. 新 App 页面与旧 Pages 页面视觉壳一致。
2. 顶部导航覆盖路径与 `lib/navigation.ts` 一致。
3. 首屏 color mode 不闪烁。
4. Google Analytics 只注入一次。

### 阶段 3：低风险页面迁移

目标：验证页面迁移方法，优先迁移不依赖复杂实时状态的页面。

候选页面：

1. `pages/index.tsx`
2. `pages/beta-access.tsx`
3. `pages/redeem.tsx`
4. `pages/password-recovery.tsx`
5. `pages/encyclopedia/index.tsx`
6. `pages/encyclopedia/[slug].tsx`
7. `pages/report-appeals.tsx`
8. `pages/messages.tsx`

迁移规则：

1. 页面组件如果使用 hooks 或浏览器 API，页面入口保留 `use client` 或把交互部分拆成客户端组件。
2. `next/head` 改为 `metadata` / `generateMetadata`；纯客户端动态标题可以先保守保留页面内处理，但要记录原因。
3. `next/router` 改为 `next/navigation` 的 `useRouter/usePathname/useSearchParams/useParams`。
4. 不做 UI 重构，不借迁移改设计。

阶段验收：

1. 每个页面有对应渲染/交互回归测试，至少覆盖原有核心入口。
2. 页面 URL、query、hash、登录态跳转行为保持兼容。
3. 顶部导航与公告条行为一致。

### 阶段 4：高风险页面按业务岛迁移

目标：迁移复杂工作台页面，同时控制回归范围。

建议业务岛顺序：

1. 创作域：`name`、`details`、`canshou`、`free`、`scenario`、`creator`、`questionnaire-editor`。
2. 角色域：`character-manager`、`character-party`、`me`、`badge-manager`。
3. 茶会/酒馆/立绘：`magic-tea-party`、`magic-tavern`、`tavern`、`tachie`。
4. 竞技域：`battle`、`arena`、`arena-stream`、`challenge`、`ranking`。
5. PVP 域：`pvp`、`pvp/[roomId]` 最后迁。

PVP 最后迁的原因：

1. 动态路由、房间状态、轮次状态、聊天、机器人、流式结算、投票和权限都集中在同一业务域。
2. 它对 query、params、push/replace、轮询和流式 API 的组合依赖最多。
3. 一旦迁移中出现跨 Router 导航或缓存行为差异，用户感知明显。

阶段验收：

1. 对每个业务岛执行局部测试与核心人工冒烟。
2. 流式生成类页面必须验证 abort/stop、首字节等待、SSE、错误提示和恢复入口。
3. PVP 必须验证建房、加入、换角色、提交、结算、投票、聊天、踢人/权限、机器人加入/移除。

### 阶段 5：收尾

目标：移除双 Router 残留。

建议动作：

1. 删除 `pages/_app.tsx`、`pages/_document.tsx`、空的 `pages/api` 与不再使用的页面入口。
2. 删除 `lib/use-next-router.ts`。
3. 删除 `lib/pages-api-adapter.ts` 与相关 Pages API 适配测试。
4. 更新 README、AGENTS、部署文档和路由约定。
5. 增加防回归测试：禁止新增 `pages/api`，除非迁移状态表显式允许。

最终验收：

```bash
pnpm test
pnpm lint
pnpm run build:cf
pnpm preview
```

并在 Cloudflare 预发环境做：

1. 注册/登录/verify/recover/reset。
2. 公开生成与流式生成。
3. 数据卡保存、读取、收藏、举报。
4. PVP 完整对局。
5. 消息、徽章、兑换码、用户中心。

## 风险清单

| 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- |
| 动态 API 参数行为差异 | 中 | Pages API 过去可能通过 URL 解析参数，Route Handler 有 `params` | 每个动态路由迁移时补参数单测 |
| 多 Set-Cookie header 丢失 | 高 | Auth 曾经处理过 header 兼容问题 | 认证相关迁移必须保留 `Set-Cookie` 回归测试 |
| 流式响应取消行为差异 | 高 | 多个 AI/PVP 接口依赖 `ReadableStream`、abort、timeout | 流式接口单独批次迁移并预发验证 |
| `next/router` 到 `next/navigation` 不等价 | 中 | `pathname/query/asPath` 等 API 不同 | 建立 App Router 专用 hook，不做盲替换 |
| 全局壳重复渲染 | 中 | 共存期 `_app` 与 `app/layout` 同时存在 | 确保每个路由只走一个壳，GA/公告条不重复 |
| 页面全 `use client` 导致收益有限 | 中 | 工作台型页面多，迁移不自动优化性能 | 先把架构统一作为目标，读多页面再单独引入 RSC |
| Cloudflare 构建/预览差异 | 高 | `next build` 成功不代表 OpenNext Worker 成功 | 每批执行 `pnpm run build:cf` 与 `pnpm preview` |

## 决策建议

采用“API 优先、页面分岛”的 App Router 迁移路线。

不建议：

1. 一次性把 `pages/` 全部移动到 `app/`。
2. 在页面迁移期间顺手重构 UI 或状态管理。
3. 为每个 Route Handler 机械添加 `runtime = 'edge'`。
4. 长期保留主页面一半 Pages Router、一半 App Router 的状态。

建议：

1. 下一轮先做一个小批次 API 迁移试点，选择 3-5 个只读或低风险接口。
2. 试点通过后，按业务域迁移剩余 API。
3. API 完成后再建立 `app/layout.tsx` 和客户端 Providers。
4. 页面按业务岛迁移，PVP 与竞技场最后处理。
