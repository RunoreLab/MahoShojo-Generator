# Web 数据卡 Runtime 与媒体资产原生支持设计建议

状态：**历史调研 / 已由 Web Package 决策承接，保留设计背景**
日期：2026-09-17  
适用范围：未来 Arena Web 内容、数据卡创作生态、可复用 Web Runtime 与媒体资产

关联当前事实：

- `docs/specs/2026-09-17_080700_Arena Web战报生成与沙箱渲染规格.md`
- `apps/web/public/encyclopedia/web-data-card-authoring.md`
- `apps/web/public/encyclopedia/scenario-advanced.md`
- `apps/web/lib/wantu-card/types.ts`

本文记录未来可能的产品 / 架构方向，不改变当前 accepted Arena Web 战报规格，也不授权立即增加 schema、存储、远程迁移、生产入口或 Host Bridge。

> **2026-09-22 架构更新**：`Runtime + Data + Assets` 已统一为 Web Experience Package：不可变多文件 Base Package + AI 单文件 Overlay。Package 进入生成环境，只有 Prompt Projection 进入模型上下文；`entry` 与唯一 `generation.target` 分离，V1 只允许 `replace`，仍属于 `reportFormat='web'`。后续规范见 [Web Package 决策](../decisions/2026-09-22_142300_WebExperiencePackage上位抽象与单文件Overlay决策.md)与 [V1 规格](../specs/2026-09-22_142300_WebExperiencePackageV1架构规格.md)。本文下文分类和建议作为历史背景保留，不覆盖新规格。

---

## 1. 背景

Arena Web V1 已经允许模型直接生成完整 HTML5 战报，并在 `sandbox="allow-scripts"` 的 iframe 中运行。

这让数据卡创作者能够仅靠现有 AI 上下文完成：

- Web UI；
- Canvas / SVG / 动画；
- 小游戏；
- Galgame / Visual Novel；
- Raid HUD；
- 调查板；
- 直播模拟器；
- 终端 / Dashboard 等特殊玩法。
但当前实现有一个天然限制：**所有 Runtime 代码和媒体资源说明都必须先进入 AI 上下文，再由 AI 重新输出到最终 HTML。**

这在探索期足够简单，也符合 YAGNI；但如果社区开始形成成熟、稳定、反复使用的 Web 系统，会逐渐出现明显浪费：

1. 已经验证稳定的 Runtime 每一局仍要占用输入 token；
2. 模型每一局还要重新复制 / 改写同一份代码，产生输出 token 与截断风险；
3. 弱模型可能破坏本来正确的 Runtime；
4. 图片、立绘、BGM、SFX 等资产只能以 URL / 文字说明进入上下文，缺少一等资产语义；
5. AI 必须充当“搬运工”，即使某些字节实际上根本不需要 AI 理解或重写；
6. 历史战报若依赖外部 Runtime / 资源的“最新版”，将难以保证长期重放一致性。

因此，未来可以考虑把：

> **AI 创作内容**

与：

> **已经存在、可以直接运行 / 直接加载的 Runtime 与媒体资产**

分离。

---

## 2. 目标方向

目标不是建设浏览器 IDE，也不是给 AI 提供 npm / Node / bundler。

更合适的目标是：

> 创作者可以事先创作或导入一套可复用的 Web Runtime 和媒体资产；生成时模型只获得它真正需要理解的“能力说明、资产目录和输出契约”，只输出本局需要创作的数据 / 剧本 / 内容；宿主直接把这些输出交给已经存在的 Runtime 渲染。
典型例子：

```text
Visual Novel Runtime（固定）
        +
背景 / 立绘 / BGM / SFX（固定资产）
        +
角色 / 情景卡语义（输入 AI）
        +
AI 只生成 Scene Script / GAME_DATA
        ↓
Runtime 直接渲染
```

这会把模型任务从：

> “请重新制作一个完整 Galgame 网页”

收敛成：

> “请使用给定资源 ID 和 DSL，生成本场剧本。”

---

## 3. 设计原则

### 3.1 语义、Runtime、资产三层分离

建议未来明确区分：

1. **Story / Card Semantics**：角色、世界、情景、玩法规则，供 AI 理解；
2. **Web Runtime**：已经实现的交互和渲染逻辑；
3. **Media Assets**：图片、立绘、音频、视频、字体（若允许）等静态资源。

AI 不应为了“能使用某张图片”而必须接收该图片的二进制；Runtime 也不应因为“能切换立绘”而必须被完整塞进每次 Prompt。
### 3.2 确定性内容不要反复生成

已经由作者测试通过的代码属于确定性资产。

默认应倾向：

> **Runtime 原样复用，AI 只生成变量部分。**

这既能降低 token，也能避免较弱模型把正确代码改坏。

### 3.3 模型看到的是“接口”，而不是所有实现

生成 Prompt 理想上只需要告诉模型：

```text
可用动作：
- scene(backgroundId)
- show(characterId, expressionId, position)
- say(speaker, text)
- bgm(assetId)
- choice(options)

可用资产：
- bg.school.rooftop.sunset
- char.alice.neutral
- char.alice.embarrassed
- bgm.daily
```

而不是把实现这些动作的几百行 JavaScript 重新发送给模型。

### 3.4 仍然坚持“事实与表现分离”

Runtime 可以控制页面怎样显示、怎样交互，但不应凭 DOM 状态反向决定 Arena winner 或覆盖服务器已经冻结的事实。

如果未来需要 Runtime → Host 的业务动作，应另立严格 typed capability bridge；不能因为 Runtime 原生化就顺手开放任意宿主命令。
### 3.5 Progressive Enhancement / 可降级

即使 Runtime、媒体、动画或网络资源不可用，仍应尽量保留可读的核心故事 / 结果。

未来原生 Runtime 不应把“加载一个第三方脚本失败”升级为“整个权威战报失败”。

### 3.6 Runtime 的 capability 声明不是权限授予

未来包格式可以声明：

```text
uses: canvas, audio, network-images
```

用于 UI 提示、预检、兼容性和统计。

但声明 `audio` / `network` 不应自动扩大 iframe 权限或 CSP；真正权限仍由宿主策略决定。

## 4. 候选概念：Web Experience Package

可以考虑一种逻辑上的“Web Experience Package”（名称待定），用于打包：

```text
manifest
runtime
assets
prompt contract / input schema
fallback
```

首版若未来实施，应尽量简单，不需要立即设计一个庞大插件系统。

一个概念性 manifest 可以类似：

```json
{
  "format": "mahoshojo-web-experience",
  "version": 1,
  "id": "vn.basic",
  "name": "Basic Visual Novel Runtime"
}
```
更完整时再逐步扩展：

```json
{
  "format": "mahoshojo-web-experience",
  "version": 1,
  "id": "vn.basic",
  "runtime": {
    "entry": "index.html",
    "contractVersion": 1
  },
  "outputContract": {
    "kind": "json",
    "schema": "scene-script-v1"
  },
  "assets": [
    {
      "id": "char.alice.smile",
      "path": "assets/alice-smile.webp",
      "mimeType": "image/webp",
      "digest": "sha256:..."
    }
  ],
  "fallback": {
    "kind": "markdown"
  }
}
```

这里的 `digest`、版本号和文件名只是候选形态，不是当前约定。

---

## 5. Runtime 与 AI 输出之间应该有窄契约

最值得优先探索的不是“AI 可以修改 Runtime 哪些 DOM”，而是：

> **Runtime 接收什么最小数据，就能完成渲染？**

视觉小说可能只需要一个 Scene Script；Raid HUD 可能需要事件流和最终状态；CaseBoard 可能需要人物、证物、时间线与关系边。
例如 Visual Novel 数据：

```json
{
  "scenes": [
    { "type": "bg", "asset": "bg.school.rooftop" },
    { "type": "show", "character": "alice", "expression": "smile", "position": "center" },
    { "type": "say", "speaker": "Alice", "text": "……" }
  ]
}
```

这种输出比完整 HTML：

- 更短；
- 更容易 schema 校验；
- 更适合弱模型；
- 更容易 repair；
- 更容易测试；
- 不会让模型误改 Runtime；
- 可以被不同版本 Runtime 重放或迁移。

如果未来确实存在需要 AI 生成少量 HTML Fragment 的 Runtime，也应作为独立 output contract，而不是默认允许任意字符串进入宿主 DOM。

## 6. 建议的数据流

当前：

```text
Card（含玩法 + 代码 + 资产 URL）
        ↓
完整进入 Prompt
        ↓
AI 重新输出完整 HTML
        ↓
srcdoc sandbox
```

未来候选：

```text
Card / Scenario Semantics ──→ AI Prompt
Runtime Manifest ───────────→ 只投影 API / Schema / 使用说明
Asset Registry ─────────────→ 只投影语义 ID / 必要元数据
                                ↓
                        AI 输出 Experience Data
                                ↓
                        Schema / Contract Validation
                                ↓
Runtime + Assets + Data ─────→ Sandbox Renderer
```
关键点是：**模型只处理需要创作和理解的东西。**

Runtime 本身不需要模型理解时，就不应消耗模型上下文。

---

## 7. 媒体资产应成为一等资源，而不是 Prompt 文本附件

未来媒体资产库至少应能表达：

- `id`：稳定语义 ID；
- `kind` / `mimeType`：图片、音频、视频等；
- `name` / description：给创作者和 AI 理解的含义；
- location / object key：实际存储位置；
- digest：内容版本 / 完整性；
- 可选版权 / 来源 / 作者信息；
- 可选 tags：`background`、`sprite`、`expression`、`bgm`、`sfx` 等。

模型理想上只看到：

```text
char.alice.smile — Alice 微笑表情立绘
bg.school.sunset — 学校天台夕阳背景
bgm.daily — 平静日常 BGM
```

而 Runtime 可以直接获得对应的实际资源 URL / Blob，不要求 AI 再把 URL 抄写一遍。

这样可以显著减少 URL 幻觉、资源 ID 搞混和上下文噪声。
### 7.1 资产许可与来源不能完全忽略

如果未来站内支持上传 / 公开分发资产，至少需要保存能够支持后续治理的来源 / 许可元数据，而不能默认“上传即拥有版权”。

首版是否强制填写许可证可以以后决定，但数据模型最好不要把这条路堵死。

### 7.2 外部 URL 与托管资产可以并存

候选策略可以同时支持：

- creator-provided HTTPS URL；
- 站内托管不可变资产；
- 内置预设资产；
- 未来本地客户端文件资产。

但是外部 URL 天然有失效、追踪、限流、CORS 和内容漂移风险；正式可复现体验更适合内容寻址 / 受控托管资产。

## 8. 重放与版本冻结

Web Runtime 一旦脱离模型输出，历史重放就会出现新的版本问题：

> 一份 2026 年生成的 Experience Data，应该用“当时的 Runtime”还是“最新版 Runtime”打开？

建议默认倾向可复现：历史战报保存 / 引用：

- Runtime package id；
- Runtime version 或 immutable digest；
- Experience contract version；
- 所引用资产的稳定版本 / digest。
这样即使作者后来更新 Runtime，旧战报仍然能按原始语义重放。

这与当前 Room replay “恢复同一份最终 Web source bytes，不重新调用模型”的可复现原则一致，只是未来冻结单位从 HTML bytes 扩展成 Runtime + Data + Assets 的组合。

---

## 9. 安全边界：原生 Runtime 不等于可信 Runtime

用户导入的 Runtime 仍然应视为不可信 Web 内容。

当前 `sandbox="allow-scripts"`、不启用 `allow-same-origin` / forms / popups / top navigation 等边界仍然是一个合理起点。

尤其不应因为 Runtime 是“作者上传而不是 AI 生成”就默认给予更高权限。

MDN 对 sandbox 的建议同样支持最小权限；缺少 `allow-same-origin` 时 iframe 使用特殊 / opaque origin，可限制存储、cookie 和同源能力。

如果未来需要更多 capability，应按具体需求单独讨论，而不是创建一个通用“trusted runtime”开关。

### 9.1 Runtime Import 的风险提示可以与 Web 执行确认复用思想

未来如果导入第三方 Runtime，UI 可以展示：

- 作者 / 来源；
- Runtime 版本 / digest；
- 使用的 capability；
- 是否请求外部网络资源；
- 是否包含音频 / 视频；
- 是否是官方 / 内置 / 用户导入。

但这些是透明度信息，不应伪装成代码已经安全审计。

---

## 10. 不建议未来首版直接做的东西

即使决定推进原生 Runtime，也建议继续 YAGNI：

- 不建设在线 npm 安装器；
- 不在不可信 Runtime 中提供 Node.js；
- 不建设完整 WebContainer / 浏览器 IDE；
- 不支持任意 Runtime 直接调用 Host 内部函数；
- 不让 Runtime DOM 成为权威游戏状态；
- 不一开始就设计跨 Runtime 通用组件市场协议；
- 不为了“插件生态”立即引入复杂签名 / 审批 / capability negotiation；
- 不强制所有普通数据卡迁移到 Runtime 体系。

现有“模型直接生成完整 HTML”应该继续长期存在，因为它对于一次性创意页面、实验玩法和强模型特别方便。

原生 Runtime 应当是**新增的复用路径**，不是替代 Web HTML generation。

---

## 11. 候选生成模式

未来如果需求成熟，可以考虑并列三种概念模式：

### A. Generated Web（当前）

```text
AI → 完整 HTML → sandbox
```

自由度最高，零额外基础设施。

### B. Runtime + Data（优先候选）

```text
AI → schema 化 Experience Data
固定 Runtime + Assets → sandbox
```
适合成熟、稳定、重复运行的视觉小说、Boss HUD、直播、调查板等系统。

### C. Runtime + Generated Fragment（以后再看）

Runtime 固定大框架，AI 生成少量 HTML / SVG / CSS fragment。

这个模式灵活，但安全、校验和兼容性都比 JSON / DSL 数据复杂；没有明确用例前不必优先。

---

## 12. 与 Wantu / 现有资产模型的关系

当前仓库已经存在一些可以借鉴但不必强行复用的概念：

- Wantu Card 有 `visualAssets`、`generationHints`；
- Wantu Data Card 有独立 `assets`，并带 `digest`、`mimeType`、`byteSize` 等；
- Arena materials 已经会把卡 / 素材投影成模型上下文，而不是直接把所有内部传输字段交给模型。

未来 Web Experience 可以复用“**领域数据 → Prompt Projection**”这一思想：

> 完整 Runtime / Asset Registry 存在于产品域；模型只得到精简的可用能力与语义资源清单。

是否直接扩展 Wantu Data Card 格式，还是建立独立 Web Experience 类型，应等跨产品互通需求更明确后再决定，不宜现在预先耦合。

## 13. 建议实施阶段（未来需求成立时）

### Phase 0：当前阶段 —— 只做创作方法验证

保持现状：Runtime 与外部资产说明都写在数据卡上下文里，让 AI 完整输出 Web HTML。

目标是先观察：

- 社区实际做出了哪些玩法；
- 最常复用的 Runtime 是什么；
- 哪些资产类型真的频繁出现；
- 弱模型最常失败在哪里。
只有出现重复痛点后，再进入原生支持。

### Phase 1：内置 / 开发者提供 Runtime PoC

先不开放任意用户包。

选择 1 个非常明确的运行时（例如 Visual Novel Lite），验证：

- AI 只输出 JSON / DSL；
- Runtime 直接渲染；
- 资产按语义 ID 解析；
- 失败可回退普通展示；
- replay 能冻结版本。

这是验证架构价值的最小路径。

### Phase 2：用户导入 Runtime Package

只有 Phase 1 证明明显节省 token、提高弱模型可靠性并出现真实创作者需求后，再考虑：

- 本地导入；
- 云端保存；
- manifest 校验；
- Runtime / asset digest；
- 基础 capability 展示；
- 导出 / 分享。

### Phase 3：媒体资产库 / 创作者工具

再根据实际需求增加：

- 背景、立绘、差分、BGM、SFX 管理；
- 语义 ID 编辑；
- 资源预览；
- 批量替换；
- 引用关系检查；
- 许可 / 来源元数据；
- Package 打包与导出。
### Phase 4：Typed Host Bridge（仅有明确需求时）

例如真正出现：

> “Runtime 中玩家的选择必须写回下一轮 Session / 角色状态。”

再独立设计：

```text
choice.select
puzzle.complete
session.submitResult
```

等有限、typed、可校验动作。

仍不提供通用 `executeHostCommand(string)`。

## 14. 需要未来决策的问题

在真正实施前，至少需要重新讨论：

1. Runtime 是绑定到数据卡、情景卡，还是作为独立可复用资源？
2. 一张卡能否引用多个 Runtime？优先级怎么处理？
3. Runtime 与资产是仅本地、私有云端，还是允许公开分享？
4. Package 大小 / 单资产大小 / 总配额是多少？
5. 公共资产如何处理版权、下架与引用失效？
6. 外部 URL 是否允许成为正式 Package 的关键依赖？
7. Runtime 更新后历史战报如何冻结和重放？
8. Experience Data 失败校验时回退 Markdown、Generated Web，还是报错？
9. Web Runtime 是否需要独立于现有 `reportFormat='web'` 的新格式语义？
10. 多人房间由谁决定 Runtime？成员是否需要额外本地确认？
11. 未来 Desktop / Mobile 本地资产是否允许引用文件系统资源？如何避免把本地路径泄漏到共享内容？
这些问题现在都不需要冻结答案。

---

## 15. 建议的长期判断标准

未来是否值得从“卡里塞代码”升级到原生 Runtime，不应该以“技术上能不能做”为标准，而应该看：

- 是否已经出现多张卡重复携带同一套 Runtime；
- Runtime 是否占据显著上下文与输出 token；
- 模型复制 / 修改 Runtime 是否成为主要失败源；
- 创作者是否已经形成可复用模板生态；
- 是否有大量媒体资产需要稳定组织；
- 是否存在明确的历史重放 / 版本冻结需求；
- 原生化后是否能显著降低复杂卡对强模型的依赖。

如果这些问题尚未出现，当前 Generated Web 已经足够，不应提前建设平台。

如果这些问题反复出现，则 `Runtime + Data + Assets` 会比继续扩大 Prompt 更自然。

---

## 16. 结论

当前阶段继续采用：

> **数据卡上下文提供玩法规则、参考代码与外部媒体；AI 输出完整 HTML。**

这是低成本、YAGNI、最适合快速观察社区创造力的方案。

但长期应保留一条明确的演进方向：

> **将成熟、确定性的 Web Runtime 与媒体资产从 AI 生成链路中拆出，作为可直接复用的一等资源；AI 只接收语义接口和资产目录，只生成真正需要创作的 Experience Data。**

这样既保留强模型自由生成 Web 的创造力，也能让复杂玩法在弱模型上获得更高稳定性。
