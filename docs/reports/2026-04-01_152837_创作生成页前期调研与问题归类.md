# 创作生成页前期调研与问题归类

更新时间：2026-04-01 15:28:37
状态：`research`
归类：`docs/reports/`

## 1. 本轮目标

围绕“新增创作生成页”做前期调研，明确以下问题：

1. 现有 `/details` 页面有哪些能力可以直接复用。
2. “问卷输入”和“车卡规则输入”应如何分层，避免后续越改越乱。
3. `魔法少女竞技场 TRPG` 简化角色卡预设，第一阶段至少需要落哪些规则。
4. 哪些问题必须先确认，哪些可以延后到实现阶段。

---

## 2. 已确认的现状

### 2.1 `/details` 已经具备的可复用能力

现有 [`pages/details.tsx`](../../pages/details.tsx) 不是“单问卷单答案”的简单页面，而是一套已经比较完整的问卷输入引擎：

- 支持多问卷叠加。
- 支持纯 lore 问卷与有题目问卷混搭。
- 支持 `displayIf`、`jump`、`optionsFrom`、`suggestionsFrom`。
- 支持本地草稿恢复、批量粘贴导入、数据库问卷/上传问卷载入。
- 支持保存问卷为数据卡。
- 支持流式与非流式两种生成模式。
- 支持把问卷答案写回结果 JSON 的 `userAnswers` 字段。

结论：

- 新创作页完全没必要重写“问卷部分”。
- “先复制一份 `/details` 再改”的方向是可行的。
- 真正需要新增的是“除问卷之外的结构化输入块”。

### 2.2 当前问卷系统的边界

[`lib/questionnaires.ts`](../../lib/questionnaires.ts) 当前把题目类型基本收敛在：

- `text`
- `select`

这套模型很适合：

- 自由文本回答
- 单选/带自定义选项
- 依赖前题答案的条件显示与跳题

但它不适合直接承载以下交互：

- 点数池分配
- 数值上下限校验
- 多字段联动预算
- 派生数值实时计算
- 专长/标签的多选限制

结论：

- “车卡规则”不应直接塞进 `questionnaires[].questions[]`。
- 更稳妥的做法是引入一条与问卷并列的新输入通道。

### 2.3 当前生成目标的现实情况

当前仓库已经存在几类“输出模板”：

- 结构化魔法少女卡
- 结构化残兽卡
- 通用角色卡（`templateId=通用角色`，Markdown）
- 通用情景卡（`templateId=通用情景`，Markdown）

参考：

- [`pages/free.tsx`](../../pages/free.tsx)
- [`lib/schemas/index.ts`](../../lib/schemas/index.ts)
- [`lib/stream/markdown-card.ts`](../../lib/stream/markdown-card.ts)

这意味着新创作页不必从零定义“数据卡类型选择器”，已有现成模式可借鉴。

但也有一个关键约束：

- 现有 `details` 的后端是强绑定“问卷生成魔法少女”这一路的。
- 现有 `questionnaire.kind` 只有 `magical-girl | canshou`，它决定了不少流程分支。

结论：

- 新创作页不能继续把“问卷 kind”当成“输出模板”的总开关。
- 必须显式拆分：
  - 输入来源类型
  - 输出数据卡模板

## 3. 参考项目中可提炼的 TRPG 简化规则

参考来源：

- [`/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/lib/trpg/rulebook.md`](/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/lib/trpg/rulebook.md)
- [`/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/lib/trpg/data/leveling.json`](/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/lib/trpg/data/leveling.json)
- [`/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/components/character-creator/DerivedStatsPanel.tsx`](/home/notuhao/code/MahoShojo-ARENA-TRPG-Helper/components/character-creator/DerivedStatsPanel.tsx)

### 3.1 第一阶段最适合纳入的核心字段

用户当前明确要求保留的，是“简化版核心属性 + 状态值”：

- `STR`
- `CON`
- `AGI`
- `MAG`
- `WILL`
- `PER`
- `CHM`

派生值：

- `HP = ceil((CON + STR) / 10)`
- `MP = ceil(MAG / 4)`
- `Radiance = ceil(WILL / 5)`

可以补充但不一定必须在第一阶段展示的派生值：

- `Dodge = ceil(AGI / 2)`
- `DB / Build`（由 `STR + CON` 区间决定）

### 3.2 力量层级带来的预算差异

参考项目已经把“不同力量层级的预算”抽成了配置文件：

- `seed`: 属性 280 / 技能 150 / PCP 20
- `sprout`: 属性 285 / 技能 170 / PCP 25
- `leaf`: 属性 290 / 技能 190 / PCP 30
- `bud`: 属性 300 / 技能 215 / PCP 40
- `flower`: 属性 310 / 技能 240 / PCP 50
- `gemScepter`: 属性 325 / 技能 270 / PCP 65

对本项目第一阶段的建议：

- 先只接入“力量层级 -> 属性点预算”这条主链。
- 技能点、PCP、魔装设计、羁绊预算暂不进入第一阶段 UI。
- 但规则配置结构里要预留这些字段，避免以后再次破 schema。

### 3.3 适合写进规则文件、而不是硬编码的内容

以下内容都适合像问卷预设一样，存放到独立 JSON/配置文件中：

- 规则 ID、标题、描述
- 支持的输出模板
- 力量层级列表与预算
- 属性字段定义
- 属性最小值/最大值
- 派生值公式说明
- 可选专长/标签列表
- 提供给 AI 的规则提示词
- 是否允许脱离问卷单独使用

## 4. 推荐分层

### 4.1 推荐把新页拆成 4 个概念

建议不要把“问卷”“规则”“输出模板”混成同一层，而是明确拆为：

1. `GenerationTemplate`
   - 这次最终要生成什么卡。
   - 例如：`magical-girl`、`canshou`、`general`、`general-scenario`。

2. `QuestionnairePreset`
   - 负责叙事、背景、人格、世界观补充。

3. `BuildRulePreset`
   - 负责点数、专长、预算、派生数值等结构化输入。

4. `GenerationInputBundle`
   - 一次生成请求的统一输入包，允许同时包含多问卷与多规则。

### 4.2 推荐的数据流

推荐的数据流如下：

1. 用户选择输出模板。
2. 用户选择 0~N 份问卷。
3. 用户选择 0~N 套车卡规则。
4. 页面分别采集：
   - 问卷答案
   - 规则输入结果
5. 前端先完成规则校验与派生数值计算。
6. 将“叙事输入 + 结构化输入 + 规则提示词”一起发给 AI。
7. 生成结果写回数据卡 JSON。

其中最重要的一点是：

- 规则输入结果必须以结构化 JSON 保存。
- 不建议把属性、预算、专长硬转成一长串文本再塞进 `userAnswers`。
- 多套车卡规则必须能并列启用，并各自保留独立结果，而不是先在前端压平成一份共享对象。

### 4.3 推荐新增并列输入结构，而不是污染 `userAnswers`

现有 `userAnswers` 很适合作为“问卷回答留痕”，但不适合作为车卡规则的唯一承载体。

建议第一阶段新增一个类似下面的字段作为规范化入口：

```json
{
  "creationInputs": {
    "questionnaires": [
      {
        "questionnaireId": "magical-girl-default",
        "answers": [
          { "questionId": "MG-1", "question": "你的名字是？", "answer": "星见遥" }
        ]
      }
    ],
    "buildRules": [
      {
        "ruleId": "arena-trpg-lite",
        "selections": {
          "powerLevel": "seed",
          "attributes": {
            "STR": 35,
            "CON": 45,
            "AGI": 50,
            "MAG": 55,
            "WILL": 40,
            "PER": 30,
            "CHM": 25
          },
          "specialties": ["远程压制", "感知警戒"]
        },
        "derived": {
          "HP": 8,
          "MP": 14,
          "Radiance": 8
        }
      }
    ]
  }
}
```

兼容建议：

- `userAnswers` 继续只保存问卷回答。
- 新页面的规则输入走 `creationInputs.buildRules`。
- 如果后续某些旧流程必须读一份“文本化概述”，可以在 prompt 组装阶段生成，不要把文本概述当 canonical source。

多规则补充约束：

- `buildRules` 必须保持数组结构，而不是单对象。
- 每条规则结果都应保留独立的 `ruleId`、`blockResults`、`derived`、`validationSummary`。
- 持久化层不应把多条规则预先合并成一个“大而平”的结果对象。
- prompt 组装阶段可基于规则顺序做汇总，但 canonical source 仍然是分规则存储。

## 5. 规则文件建议长相

第一阶段不一定要一次性把所有字段都做完，但规则文件建议从一开始就留足扩展位。

### 5.1 规则预设需要声明的边界

规则预设不应只是“blocks + formulas”的裸数据，还需要显式声明自己能做什么，避免页面和后端长期靠硬编码判断。

建议至少声明这些顶层字段：

- `id`
  - 规则定义的稳定机器标识。
- `title` / `description`
  - 给用户看的名称与说明。
- `version`
  - 规则版本，便于后续兼容与迁移。
- `supportedTemplates`
  - 这套规则可以服务哪些输出模板。
  - 这是必要字段，因为创作生成页不仅生成角色卡，后续也会支持情景卡。
- `allowStandalone`
  - 是否允许脱离问卷单独使用。
- `mainRuleEligible`
  - 是否允许被选为主规则。
  - 未来某些纯补充规则可能只能作为参考规则存在。
- `projectionPolicy`
  - 这套规则默认如何参与目标卡。
  - 第一阶段建议先只支持：
    - `primary-structured`
    - `reference-only`
- `aiPromptHint`
  - 提供给 AI 的规则解释提示。
- `uiSummary`
  - 指定前端摘要面板优先展示哪些 block / derived 字段，避免 UI 自己猜。
- `blocks`
  - 类型化规则块定义。
- `budgets`
  - 可选，声明预算池。
- `derivedStats`
  - 可选，声明派生值公式。

其中最关键的是 `supportedTemplates`：

- 规则不一定只服务于角色卡。
- 某些规则未来可能主要服务于情景卡或通用情景卡。
- 因此“规则支持哪些输出模板”必须由规则预设自己声明，而不是让页面写死。

block 能力补充约束：

- `select`、`multi-select` 不应只支持“纯选择”，`number` 也建议不仅仅是“纯输数字”。
- 它应支持可选的点数/配额机制，例如：
  - 每个选项有 `cost`
  - block 自身有 `selectionBudget`
  - 程序校验总花费是否超限

这样未来遇到“专长需要花费点数”的规则时，不需要额外发明新的 block 类型。

示意结构：

```json
{
  "id": "arena-trpg-lite",
  "title": "魔法少女竞技场 TRPG 简化角色卡",
  "description": "仅包含核心属性、状态值与少量附加选择。",
  "kind": "build-rule",
  "version": "1.0.0",
  "supportedTemplates": ["general", "magical-girl"],
  "allowStandalone": true,
  "mainRuleEligible": true,
  "projectionPolicy": "primary-structured",
  "aiPromptHint": "以下输入来自 TRPG 车卡规则，请理解各字段含义并自然融入设定。",
  "uiSummary": {
    "priorityBlocks": ["powerLevel", "attributes", "specialties"],
    "priorityDerived": ["HP", "MP", "Radiance"]
  },
  "blocks": [
    {
      "id": "powerLevel",
      "type": "select",
      "required": true
    },
    {
      "id": "attributes",
      "type": "point-buy",
      "required": true
    },
    {
      "id": "specialties",
      "type": "multi-select",
      "required": false
    }
  ],
  "budgets": {
    "seed": { "attributePoints": 280, "skillPoints": 150, "pcp": 20 },
    "sprout": { "attributePoints": 285, "skillPoints": 170, "pcp": 25 }
  },
  "derivedStats": [
    { "id": "HP", "formula": "ceil((CON + STR) / 10)" },
    { "id": "MP", "formula": "ceil(MAG / 4)" },
    { "id": "Radiance", "formula": "ceil(WILL / 5)" }
  ]
}
```

这里的重点不是字段名本身，而是先确立一个原则：

- 问卷文件负责“问什么”。
- 规则文件负责“怎么算、怎么校验、怎么存”。
- 规则预设还必须负责声明“自己适用于什么输出模板、能不能做主规则、该如何参与投影和提示组装”。

## 6. 三种实现路线

### 路线 A：把车卡规则继续伪装成问卷

做法：

- 继续使用 `questionnaires` 模型。
- 用 select/text 勉强表达点数分配与专长选择。

优点：

- 改动表面最少。

缺点：

- 点数预算与派生公式会非常别扭。
- 校验逻辑会越来越分散。
- 很难支持后续“自定义车卡规则”。

结论：

- 不推荐。

### 路线 B：新页复用 `/details`，但新增“规则引擎”作为并列输入层

做法：

- 页面 UI 和问卷流程大量复用 `/details`。
- 新增 `BuildRulePreset`、规则输入状态、预算校验、派生值计算。
- 输出模板继续复用现有角色/情景卡体系。

优点：

- 与当前仓库结构最兼容。
- 既保留问卷能力，也能正交扩展规则输入。
- 后续做“自定义车卡规则”时有稳定落点。

缺点：

- 需要新建一层配置与状态模型。
- 需要定义 `creationInputs` 等新字段边界。

结论：

- 推荐作为第一阶段主线。

### 路线 C：直接引入新的专用 TRPG 角色卡模板

做法：

- 新建专用 schema、专用卡面组件、专用导入导出/校验流程。

优点：

- 表达能力最强，展示也最完整。

缺点：

- 改动范围最大。
- 需要同步修改 schema、校验、渲染、卡片识别、可能还有竞技场兼容逻辑。

结论：

- 更适合作为第二阶段，而不是当前的起步版本。

## 7. 当前推荐方案

当前最稳妥的建议是：

1. 新创作页先复制 `/details`。
2. 保留原有问卷引擎，不重写。
3. 新增“规则预设”配置目录与读取逻辑。
4. 新增“规则输入结果”状态，与问卷答案并列保存。
5. 第一阶段输出模板优先复用现有体系，不急着加新主模板。
6. `魔法少女竞技场 TRPG 简化角色卡` 先作为第一套规则预设接入。

换句话说：

- 新页的核心创新点应该是“输入模型升级”。
- 不应把第一阶段做成“模板体系大重构”。

### 7.1 已确认决策

2026-04-01 用户已确认：

1. 第一阶段采用“复用现有输出模板”的路线。
2. 不立即新增 `TRPG 专用角色卡模板/卡面/schema`。
3. 规则输入的保存结构必须为未来扩展预留，不得只围绕“属性加点”设计。
4. 规则配置层采用“类型化规则块”路线，不走固定字段模型，也不在第一阶段引入过重的通用 DSL。
5. 车卡规则必须像问卷一样支持同时启用多套规则。
6. 多套规则允许存在同名字段，但默认视为不同规则上下文中的独立数据，不在持久化层自动合并。
7. 当多套规则同时启用时，生成链路采用“主规则 + 补充规则”模式：用户指定一套主规则，其余规则作为补充参考输入给 AI。
8. 车卡规则数据属于程序维护的结构化层，默认不写入数据卡正文，避免与正文叙事内容重复、漂移或冲突。
9. 新创作页保留独立的自由文本补充输入层，用于承载创作要求、风格偏好、禁忌与额外说明，不强行塞进问卷或规则块。
10. 自由文本补充输入在 prompt 组织中优先于问卷与规则解释层，但不覆盖结构化规则结果。
11. 生成请求体升级为统一输入包，结果卡在顶层持久化 `creationInputs`，不把这部分藏进正文或松散 metadata。
12. `creationInputs` 只表示生成留痕；当前附着在卡上的程序维护规则数据单独放在顶层 `buildState`，二者职责分离。
13. 规则结果标识采用最小模型：`ruleId` 必有，`version` 建议保留，`ruleInstanceId` 暂时可选；第一阶段不引入额外 `namespace` 字段。
14. 页面实现路径必须基于现有 `/details` 页面复制后增量改造，优先复用现有问卷、草稿、导入、生成与结果展示链路，不重复造轮子。
15. 新创作生成页的首选路由为 `/creator`，对应实现文件建议为 [`pages/creator.tsx`](../../pages/creator.tsx)。
16. 新创作页使用独立 API 边界，建议新增 `pages/api/creator/generate.ts` 与 `pages/api/creator/generate-stream.ts`，而不是继续扩写旧接口的入参形状。
17. 第一阶段流式能力边界遵循现有成熟模式：`non-stream` 支持所有模板，`stream` 只支持通用角色卡与通用情景卡。

这意味着第一阶段虽然只落地：

- 力量层级
- 核心属性
- 派生值
- 少量附加选择

但底层设计必须能够容纳未来的：

- 技能树
- 专长
- 标签/天赋
- 可解锁项
- 多组预算联动
- 用户自定义规则块

因此后续设计时要避免以下反模式：

- 把所有规则输入写死成 `attributes + derived`
- 把未来可能扩展的内容压扁成纯文本说明
- 把规则 UI 写成只服务于 `arena-trpg-lite` 一套预设的特殊分支
- 让规则组件直接读写一个巨大的全局 State

对应的正向约束：

- 规则文件应由一组可组合的 block 构成。
- block 至少允许覆盖：
  - `select`
  - `multi-select`
  - `number`
  - `point-buy`
  - `derived`
  - `section`
  - 后续可扩展的 `repeatable-list` / `tree-select`
- 页面与存储层都围绕“block 结果”组织，而不是围绕某一套固定字段硬编码。
- 多规则场景下，命名空间先属于“规则实例”，再属于 block 本身，避免不同规则之间直接覆盖。
- 同名字段只有在“面向用户展示统一摘要”或“投影到某个目标模板”时，才讨论如何解释；在原始存储里保持规则隔离。
- 规则原始结果、派生值与校验摘要应只存在于结构化字段中，不默认复制进 `content` 或其他正文文本字段。
- 自由文本补充应作为独立输入来源保存，与问卷回答、规则输入并列，而不是寄生在某个问卷答案或规则 block 中。
- 因为每条规则结果本身已经处于 `rules[]` 数组项内，第一阶段无需再额外引入 `namespace`；规则定义身份由 `ruleId` 承担。

## 8. 未决问题归类

### 8.1 输出模板范围

当前已确认：

1. 第一阶段不新增“TRPG 专用角色卡模板”。
2. 创作页模板选择器直接复用 [`pages/free.tsx`](../../pages/free.tsx) 当前 5 个模板 ID：
   - `magical-girl`
   - `canshou`
   - `general`
   - `scenario`
   - `general-scenario`
3. `stream` 仅支持：
   - `general`
   - `general-scenario`
4. 其余模板走 `non-stream`。

这是当前最关键的范围问题，因为它决定：

- schema 改动量
- 卡面组件数量
- 保存/导入/展示逻辑要改多深

### 8.2 规则输入写回 JSON 的 canonical 字段

当前已确认：

- 结果卡顶层 canonical 留痕字段使用 `creationInputs`
- 当前程序维护的规则状态字段使用 `buildState`
- 请求体与 `creationInputs` 内的主规则字段统一使用 `primaryRuleId`

建议：

- 统一使用一个新字段承载结构化输入。
- 不要让“问卷回答文本”和“点数分配结果”长期混在同一字段。

进一步补充：

- 该字段内部也不应只保留“最终值”。
- 对未来自定义规则，最好同时保留：
  - 规则定义引用
  - 用户选择结果
  - 前端计算得到的派生值
  - 可选的预算/校验摘要

否则到了技能树、专长、条件解锁场景，只有最终值会不足以回放和编辑。

### 8.3 创作页与“自由生成”的关系

当前已确认：

- 创作页允许无问卷、无规则、只靠“输出模板 + 自由文本”生成。
- 创作页也允许“模板 + 规则”生成；若存在 `allowStandalone = false` 的规则，则必须同时选择至少一套问卷。
- 若问卷与规则都为空，则自由文本不能留空。
- 创作页不是 [`/free`](../../pages/free.tsx) 的完全替代，而是面向“多输入源创作工作台”的升级入口。

建议执行方式：

- 第一阶段允许“只选输出模板 + 可选规则 + 可选问卷”。
- `/free` 保持轻量自由生成入口定位。

### 8.4 原生性签名

当前已确认：

- 创作页第一阶段不追求 `native`。
- 如果新页接入了新的规则输入与新字段，签名链路基本不可能“天然复用”。
- 第一阶段更现实的预期是：先做非原生、结构正确、可保存、可继续使用。

### 8.5 自定义车卡规则

当前用户要求是“先不做，但要预留”。

建议的预留方式：

- 规则文件与问卷预设同样走文件化配置。
- 前端状态模型与校验模型不要写死在 `arena-trpg-lite` 上。
- 页面上可以先不暴露“自定义规则编辑器”。
- 规则块类型至少要支持“数值输入 / 单选 / 多选 / 点数池 / 派生显示”这类可组合组件，而不是只支持题目式问答。

### 8.6 多规则组合时的冲突策略

当前已确认的处理原则：

- 多套规则允许作用于看起来相似的语义域，例如不同世界观下都存在 `STR`。
- 这些字段默认不视为冲突，因为它们属于不同规则上下文。
- 持久化层保持隔离，不自动折叠成统一属性表。

真正需要定义策略的场景改为：

- 如何把“主规则 + 补充规则”组织成稳定 prompt。
- 如何在页面上给出一个不会误导用户的汇总视图。
- 当未来某个目标模板只接受一套结构化规则结果时，如何从多规则输入中选择投影来源。

第一阶段建议：

1. 原始数据全部保留。
2. 用户必须指定主规则。
3. 默认只把主规则的结构化结果视为“主投影来源”。
4. 其他规则以补充参考的形式写入 prompt 和留档，但不强制映射到主模板字段。

### 8.7 通用角色卡中的规则展示方式

当前已确认：

- 与其他数据卡一致，规则数据默认不写入正文。
- 通用角色卡的 `content` 仍以角色设定、叙事描述、背景与风格化文本为主。
- 主规则与补充规则的数据由结构化字段保存，并由程序在页面层做独立展示。

这样做的原因：

- 规则数据进入正文后，会形成“结构化字段 + 正文文本”两份来源，后续难以程序化修改。
- 后续若把规则数据再次提供给 AI 生成故事，正文中的重复描述可能与结构化字段发生漂移或冲突。
- 保持“正文负责叙事，结构化字段负责规则”能显著降低维护成本。

第一阶段建议：

1. UI 层可以展示“主规则摘要”和“补充规则摘要”面板。
2. 这些摘要来源于结构化字段实时渲染，而不是写回卡正文。
3. 只有当用户未来明确选择“导出带规则附录的文本版本”时，才考虑生成临时文本摘要，但不作为 canonical source。

### 8.8 自由文本补充输入的定位

当前已确认：

- 新创作页保留自由文本补充输入框。
- 该输入框的职责是承载：
  - 创作要求
  - 人物气质
  - 风格偏好
  - 禁忌与避雷
  - 其他无法被问卷或规则块自然表达的说明

设计约束：

- 这部分内容不应伪装成问卷答案。
- 也不应被拆进规则 block。
- 它应作为独立输入源参与 prompt 组装，并单独持久化，便于后续编辑与复用。
- 在 prompt 中，它应位于问卷摘要与规则摘要之前，作为用户的直接创作意图输入。

### 8.9 生成请求体与结果落盘边界

当前已确认：

- 前端提交给生成 API 的内容不再只围绕 `answers + questionnaires` 组织。
- 应升级为一个统一的输入包，例如 `generationInputBundle`。
- 结果卡在顶层持久化 `creationInputs`，保存本次生成使用过的输入快照。

建议的请求体方向：

- `template`
- `freeformBrief`
- `questionnaires`
- `questionnaireAnswers`
- `buildRules`
- `primaryRuleId`

建议的结果落盘方向：

- 卡正文层继续遵循现有模板要求，例如通用角色卡仍然是 `name + content`。
- 输入留痕层统一进入顶层 `creationInputs`。

这样做的原因：

- 便于后续重生成、局部修改、替换主规则、删除补充规则。
- 避免把规则与输入实现细节散落在正文文本或不稳定 metadata 中。

留痕粒度约束：

- 默认不在结果卡中内嵌完整问卷定义快照。
- 默认不在结果卡中内嵌完整规则预设定义快照。
- `creationInputs` 只保留：
  - `questionnaireId` / 可选 `version`
  - 问卷答案结果
  - `ruleId` / `version`
  - 规则输入结果与派生值
- 如果将来一张旧卡里引用的 questionnaireId 或 ruleId 已经不存在、下线，或者版本不兼容，保留旧卡里的已有答案/规则结果并允许继续查看，页面提示“原预设缺失”，但相关输入区改为只读；如果用户要继续编辑该部分，再手动重新选择新预设。

这样做的原因：

- 降低卡数据体积。
- 避免把大量可能过期的预设定义副本塞进每张卡里。
- 让卡内保存的重点回到“用户当时实际选择了什么”，而不是“系统当时整份定义长什么样”。

### 8.10 生成留痕与当前规则状态分离

当前已确认：

- `creationInputs` 只表示“这张卡最初/最近一次生成时用了什么输入”。
- 它属于生成留痕，不应承担“当前可编辑规则状态”的职责。
- 当前附着在卡上的、由程序维护的规则数据，单独放在顶层 `buildState`。
- 若本次生成未选择任何车卡规则，则结果中不写 `buildState`，保持卡数据尽量干净。

推荐的职责划分：

- `creationInputs`
  - 保存生成时快照。
  - 适合用于重现 prompt、回看来源、辅助重生成。
- `buildState`
  - 保存当前权威规则状态。
  - 适合用于后续程序化修改、重新计算派生值、作为故事生成时的规则输入来源。

这样做的原因：

- 如果后续用户或程序修改了规则数据，继续覆盖 `creationInputs` 会导致历史来源和当前状态混淆。
- 分层后可以同时保留“它最初是怎么来的”和“它现在是什么状态”。

建议的 `buildState` 最小结构：

```json
{
  "buildState": {
    "primaryRuleId": "arena-trpg-lite",
    "rules": [
      {
        "ruleId": "arena-trpg-lite",
        "version": "1.0.0",
        "blockResults": {},
        "derived": {},
        "validationSummary": {}
      }
    ]
  }
}
```

第一阶段约束：

- `primaryRuleId` 只引用 `rules[]` 中的一条。
- `rules[]` 保存当前权威规则状态，而不是生成时快照。
- `blockResults` 只存用户输入或程序维护的原始结果。
- `derived` 只存程序计算出的派生值。
- `validationSummary` 只存程序校验摘要。
- 第一阶段不持久化 `dirty`、`disabled`、`source` 等运行态字段。

### 8.10.1 结构化模板 schema 兼容性前置条件

当前已确认：

- 仓库内结构化 `magical-girl`、`canshou`、`scenario` schema 对顶层字段采用白名单校验。
- 因此若要把 `creationInputs` 与 `buildState` 作为结果卡 canonical 顶层字段持久化，必须同步修改 schema、验证入口与映射边界。
- 通用 Markdown 模板当前允许额外字段，但结构化模板不能假设自动兼容。

### 8.11 规则结果标识模型

当前已确认：

- `ruleId` 是规则定义的稳定机器标识，必须保留。
- `version` 建议保留，用于规则演进与兼容判断。
- `ruleInstanceId` 仅在未来出现“同一规则可被同一张卡启用多次”的场景时再启用，第一阶段不作为必需字段。
- 第一阶段不单独增加 `namespace`。

原因：

- `rules[]` 数组项本身已经形成天然隔离。
- 只使用一个规则，或者多规则但互不重复时，`ruleId` 已足够引用。
- 额外引入 `namespace` 会增加概念成本，但当前没有等价收益。

### 8.12 程序职责边界

当前已确认：

- 规则数据的权威来源只能是程序，不是 AI。

职责划分建议：

- 前端负责：
  - 规则 block 输入状态维护
  - 主规则选择
  - 派生值实时计算
  - 预算与上下限校验
  - 草稿保存与恢复
- 后端负责：
  - 统一整理 prompt 输入
  - 做最终一次规则数据合法性校验
  - 生成结果并把 `creationInputs` / `buildState` 正确落盘
- AI 负责：
  - 基于已经整理好的输入生成卡正文内容

AI 明确不负责：

- 决定规则值
- 修改规则值
- 重算派生值
- 自动修复程序校验失败的数据

### 8.13 提交流程与失败行为

当前已确认：

- 规则输入与正文生成遵循“先校验、后生成”的流程。
- 不能先让 AI 生成，再回头尝试修补规则数据。

建议流程：

1. 用户点击生成前，前端先做本地校验。
2. 若主规则未选、某条规则预算校验失败、必填 block 缺失，则不发请求。
3. 请求发出时，提交统一输入包：
   - `template`
   - `freeformBrief`
   - `questionnaires`
   - `questionnaireAnswers`
   - `buildRules`
   - `primaryRuleId`
4. 后端收到后，再做一次兜底校验。
5. 若规则数据非法，直接返回结构化错误，不让 AI 介入“猜修复”。
6. 若 AI 生成失败，保留用户已填写的问卷、规则与自由文本，不清空 `buildState`。
7. 若生成成功，同时写入：
   - 正文模板结果
   - `creationInputs`
   - `buildState`

失败时的用户体验约束：

- 不回滚用户输入。
- 不清空草稿。
- 错误信息优先指出是“规则校验失败”还是“AI 生成失败”。

### 8.14 规则投影的定义与处理方式

当前已确认：

- 规则预设与卡模板之间通过“投影”连接，而不是直接绑定。
- 投影不是持久化层的原始数据，也不是卡正文内容。
- 投影是程序在“生成时”或“页面预览时”根据 `buildState` 计算出的模板消费视图。

投影的核心作用：

- 告诉后端和 AI：对于当前输出模板，这套规则里的哪些内容应被重点参考。
- 保持 `buildState` 原始结构不变，不把多规则数据提前压扁合并。

#### `primary-structured`

含义：

- 这套规则可以作为主规则。
- 程序会把它整理成一份高优先级、结构化、稳定的模板输入视图。
- AI 必须尊重该视图中的规则事实，但不得修改其中数值。

处理方式：

1. 从 `buildState.rules[]` 中找到 `primaryRuleId` 对应规则。
2. 提取其核心 `blockResults`、`derived` 与必要校验摘要。
3. 组装成面向当前模板的一份结构化摘要。
4. 在 prompt 中以“固定事实”的形式提供给 AI。

约束：

- 该视图是临时计算产物，不写回 `buildState`。
- 不自动修改原始规则数据。
- 不直接写入卡正文。

#### `reference-only`

含义：

- 这套规则只作为补充参考。
- 它可以提供世界观、风格、附加限制或辅助灵感，但不覆盖主规则的结构化事实。

处理方式：

1. 从补充规则中提取适合展示的摘要。
2. 在 prompt 中以较低优先级的参考信息提供给 AI。
3. 不强制映射到目标模板的主体字段。

约束：

- 不覆盖主规则。
- 不视为主投影来源。
- 不强制写入目标模板结构。

### 8.15 页面结构与复用约束

当前已确认：

- 新创作页虽然会新增多个输入区块，但实现路径仍然必须基于 [`pages/details.tsx`](../../pages/details.tsx) 复制后增量改造。
- 目标是“在现有问卷生成页上扩展能力”，而不是重新发明一套新页面框架。

复用优先级：

1. 优先复用现有问卷选择与跳题链路。
2. 优先复用现有草稿保存与恢复逻辑。
3. 优先复用现有生成模式切换、结果展示、保存到云端等成熟流程。
4. 只在无法自然承载车卡规则与多输入源时，才新增独立状态与组件。

页面分区的含义：

- 这是在 `/details` 现有结构上增加“输出模板区 / 自由文本补充区 / 车卡规则区 / 输入摘要区”等新块。
- 不意味着重新实现一套完全独立的创作页骨架。

### 8.16 路由命名

当前已确认的建议：

- 新创作生成页使用 `/creator`。

选择理由：

- 简短，易记，和现有路由风格接近。
- 语义上更像“创作工作台”，比 `/creative` 更像页面入口而不是形容词。
- 当前仓库中不存在同名路由，不会与现有页面直接冲突。

实现建议：

- 页面文件为 [`pages/creator.tsx`](../../pages/creator.tsx)。
- 内部实现以 [`pages/details.tsx`](../../pages/details.tsx) 为母版复制后增量演进。

### 8.17 组件边界

当前已确认的方向：

- 页级状态仍由 [`pages/creator.tsx`](../../pages/creator.tsx) 统一协调。
- 问卷相关能力优先复用现有 `/details` 逻辑与问卷组件。
- 新增的创作页能力拆到 `components/creator/` 下，避免把新增逻辑继续堆回单个大页面文件。

建议的组件拆分：

- [`pages/creator.tsx`](../../pages/creator.tsx)
  - 负责整页状态协调、提交流程、结果展示总控。
- `components/creator/TemplateSelector.tsx`
  - 输出模板选择。

- `components/creator/BuildRulePicker.tsx`
  - 规则选择与主规则指定。
- `components/creator/BuildRulePanel.tsx`
  - 单条规则的 block 输入面板。
- `components/creator/BuildSummaryPanel.tsx`
  - 程序维护的规则摘要展示。

复用约束：

- 问卷题目展示与跳题交互，优先继续使用 [`components/questionnaire/QuestionnaireQuestionPanel.tsx`](../../components/questionnaire/QuestionnaireQuestionPanel.tsx) 及现有问卷状态组织方式。
- 不重写一套新的问卷组件树。
- 不把车卡规则输入硬塞回问卷组件。

### 8.18 API 边界

当前已确认的方向：

- 新创作页不继续直接扩写旧的生成接口语义。
- 建议新增独立接口：
  - `pages/api/creator/generate.ts`
  - `pages/api/creator/generate-stream.ts`

这样做的原因：

- 旧接口大多围绕单一生成场景设计，例如问卷生成魔法少女、自由生成、情景生成。
- 创作页的输入模型已经升级为统一输入包，如果继续把它强塞进旧接口，会让语义越来越混乱。
- 独立接口能保持创作页的请求体稳定，同时内部仍可复用现有生成工具函数与 prompt 组装能力。

实现约束：

- 独立接口复用内部工具，不复用旧接口的请求体形状。
- 创作页统一走独立接口，不在页面层按模板直接切换到旧接口。

### 8.19 流式与非流式边界

当前已确认：

- 第一阶段 `non-stream` 支持所有创作页输出模板。
- 第一阶段 `stream` 只支持通用角色卡与通用情景卡。

原因：

- 这与现有 [`pages/free.tsx`](../../pages/free.tsx) 和 [`pages/details.tsx`](../../pages/details.tsx) 的成熟能力边界更接近。
- 可以最大化复用现有流式 Markdown 输出与卡片转换链路。
- 避免第一阶段在结构化模板上同时推进流式协议、模板约束与复杂输入拼装，复杂度过高。

### 8.20 `arena-trpg-lite` 第一阶段落地范围

当前已确认：

- 第一套规则预设为 `arena-trpg-lite`。
- 第一阶段只做“简化角色卡规则输入”，不扩展成完整 TRPG 编辑器。
- 虽然创作页本身支持情景卡，但 `arena-trpg-lite` 第一阶段只服务角色卡模板。

对应的模板支持边界：

- `supportedTemplates = ["general", "magical-girl"]`

原因：

- 这套规则本质上是角色向车卡规则。
- 创作页支持情景卡，不代表第一套规则也必须支持情景卡。
- 情景卡后续更适合接入面向世界观、资源、阵营、事件约束的专用规则预设。

第一阶段建议 block：

1. `powerLevel`
   - `select`
   - 选项：`seed / sprout / leaf / bud / flower / gemScepter`
2. `coreAttributes`
   - `point-buy`
   - 管理 7 项核心属性：
     - `STR`
     - `CON`
     - `AGI`
     - `MAG`
     - `WILL`
     - `PER`
     - `CHM`
   - 受力量层级预算限制
3. `specialties`
   - `multi-select`
   - 允许可选点数成本与总预算限制
   - 第一阶段内容可参考“设定卡（原作）：心之花体系与能力边界（留空规则）”中的基础能力模块：
     - 魔力放出：魔弹、魔力冲击、魔炮（高输出炮击）
     - 防御：魔力护盾
     - 强化：身体强化、魔力附着
     - 飞行与机动：悬浮、魔力受身、炮弹起射、永动飞行、超速闪现
     - 魔力感知：感知强化、环境魔力侦测
   - 这些内容第一阶段主要作为 AI 参考输入，不做复杂联动
4. `derivedStats`
   - `derived`
   - 展示：
     - `HP`
     - `MP`
     - `Radiance`
5. `ruleNotice`
   - `section`
   - 展示简化规则说明与边界提示

第一阶段明确暂不做：

- 技能树
- 技能点分配
- PCP
- 魔装构筑
- 羁绊预算
- `repeatable-list`
- `tree-select`

## 9. 建议的第一阶段里程碑

### 里程碑 1：页面复制与概念拆分

- 从 `/details` 复制出新页。
- 保留问卷相关功能。
- 增加输出模板选择。
- 增加规则预设选择 UI 占位。

### 里程碑 2：规则配置与前端校验

- 新增规则预设文件目录。
- 接入 `arena-trpg-lite`。
- 实现力量层级、属性分配、派生值计算。

### 里程碑 3：生成请求与 JSON 存储

- 请求体支持问卷 + 规则输入并列提交。
- 结果 JSON 增加 `creationInputs`。
- AI prompt 接入规则提示词。

### 里程碑 4：卡面与后续兼容

- 确认第一阶段是否只复用现有模板。
- 若需要，再决定是否追加专用 TRPG 卡面模板。

## 10. 本轮结论

当前最重要的结论有三条：

1. `/details` 可以复用，但“车卡规则”不能继续伪装成问卷。
2. 最值得先做的是“输入体系升级”，而不是先扩写大量新模板。
3. 第一阶段最关键的产品决策，是要不要立即做“TRPG 专用角色卡模板”。

如果这条没有先定，后续实现会在“继续复用通用角色卡”与“直接新增专用 schema/卡面”之间反复摇摆。
