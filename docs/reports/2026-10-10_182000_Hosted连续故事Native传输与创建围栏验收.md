## 1. 本片实现范围

复用原 `arena_hosted_stream`，只增加 `create-story-stream` 和 `reconcile-story`：创建由 exact sealed input
进入固定 Hono `/api/arena/session/generate-next`，角色来源取原 input 的 workingCombatants，沿固定 Next
runner。原 actor/funding、秘密槽、SSE/JSON Channel、cursor、C0、ordinary C1/C2/C3 保持原归属。

- 生产 ArenaState 与 LocalLibrary/binder 共享同一个 `Arc<StoryStore>`、同库和每 product admission；
  首次 seal、普通 SSE/JSON 创建、故事创建与可重绑 Flight 的控制共同守护原槽，没有第二套 Flight registry
- schema7 只新增 `create_claim TEXT`；`MIGRATION_6` 与当前基底逐字节一致。Native-only 闭合 claim
  跨 revision 传递、普通重启保留，backup restore 加 restored fence；历史 v6 audit 不查询不存在的新列
- metadata 与 claim 每行仍合计64KiB。创建和新 revision 发布在许可前还预留未知 observedGeneration 的最大
  合法 generationId 与 serverPayloadHash 空间，避免 POST 后才发现无法持久绑定原 generation；不是扩大预算
- 首次持久 claim 只给原进程不可 Clone、单次 permit；claim 后即使 POST 前失败仍只查原 request。
  404、能力撤回、回放不完整或 renderer 的未派发说法都不补发 create 许可
- inputDigest 是原 input bytes 的 SHA-256，clientBodyHash 是协议/inputDigest/冻结 funding 的 binary v1
  非秘密意图摘要，serverPayloadHash 是受检原 generation 返回的服务端摘要；三者不互代。TS/Rust 采用
  [同一16例金样](../../packages/contracts/fixtures/desktop-story-client-body-intent.json)，不新建通用 JSON canonicalization
- 原输入与角色 data 使用 RawValue，最终创建 body 连资金配置、Key 与 wrapper 一起计入12MiB；不截文、
  不递归清洗业务卡，不把输入转义保真扩大成既有 SSE Value 投影全域保真的结论
- pointer v4/purpose=story 仍使用原两个 public keys 和16,384 code units；不存 funding/pendingRevision/
  writeOptions，恢复依据 Native pending。旧 owner 不能接管、覆盖或清除故事记录
- telemetry 只保存原成功分支 version?:1、aiModel、usage、narrativeHistoryReadCount；保数字/null/布尔，
  沿 eventWireBytes=25,231,360 bytes，不借 CompanionUsage/ModelId 或人为短字符串上限收窄原域。
  共享投影与 Native content coverage 对齐，header/readCount 冲突拒绝冻结并保留原件

实现入口：[`arena_hosted_story.rs`](../../apps/desktop/src-tauri/src/arena_hosted_story.rs)、
[`arena_story_pending_native.rs`](../../apps/desktop/src-tauri/src/arena_story_pending_native.rs)、

## 2. 已闭合的独审问题

下列修复已进入当前源码，最终只读独审没有未闭合阻断。该独审不代替实跑；TS 终检、受测字节冻结与完整 CI 结果分别见 §3/§4，不能据底座通过宣称用户旅程已经可用。

### 2.1 可取消 preflight 与唯一 Flight

慢能力探测必须可被本机 detach 取消。preflight 暂占原唯一 Flight 槽，并持有可取消 token；它不安装 bootstrap、
Cookie 秘密槽或 durable claim，不建立旁路 registry。冻结角色写选项所需的固定 Next 能力在 claim/秘密占槽前检查。
成功转正沿用同一个 token，转换过程处于同 admission 内，避免 detach 落入临时换槽空隙。

### 2.2 维护窗口仍允许本机 detach

取消使用同一 admission mutex 的纯内存 cancellation guard，不进入 maintenance write gate，也不能作为存储 API
许可。备份/恢复维护窗口不能阻止终止正在等待的能力探测；本机 detach 仍不等于已向服务器 stop 或服务器终态。

### 2.3 Exact Arc/token CAS 与 claim 后失败

preclaim 失败恢复旧 Flight 时检查 exact Arc 身份，取消 token 不得恢复或覆盖随后进入的新 Flight；失败探测、
账号变化与晚到清理分别覆盖。claim 后若 prepare 失败，只释放仍匹配的 reservation/旧 Flight，以便原 request
lookup 能重新绑定；保留 durable claim 和秘密，绝不重新 create，也不删除另一任务的 Flight。

首次 seal 的准入已精确对齐：无 active pending 时，允许无 Flight，或 terminal 且 request 不同的既有 Flight，
包括成功保存、已释放 pending 的旧 story。普通非 terminal Flight 仍拒绝；同 requestId 的普通 Flight 绝不改绑成故事。

### 2.4 角色 generation 与 opaque wrapper

角色请求先校验 claim.observedGeneration 与请求 generationId，不能借同原 input 对账别的 generation；新 POST
还要 fresh 原 request lookup 确认 completed，已 accepted roleResponse 只本地回读。

角色 wrapper 是业务投影，不是新的闭合 authority：未知键可以包含孤立 UTF-16 转义，未知字段重复也不应让
原卡域缩窄。适配器只挑选共享角色投影的已知字段，沿 JSON.parse 末项语义处理这层投影，忽略未知 wrapper
扩展，不解码或重写 data 原字节。filename/source/room 等匹配 hint 按共源 trim 处理，不能替代 data 原件。
此修复不放宽 command、claim 或其他闭合权限载体的严格字段/重复键检查。

### 2.5 旧 owner 的只读保护

旧单次 owner 先识别 v4/purpose=story；即便故事指针畸形，也不能成为旧 owner 的修复、替换或清除目标。
超过原指针读取上限的原件不先无界 JSON.parse 猜归属，直接只读保留。已驻留旧 owner 写回前还核对存储原文，
不以旧内存快照覆盖后来出现的 v4 或超限原件。
