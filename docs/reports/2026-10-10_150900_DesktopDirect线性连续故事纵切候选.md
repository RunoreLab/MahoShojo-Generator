依据：[唯一 Desktop 计划](../plans/2026-09-30_160100_Desktop客户端阶段实施计划.md)、DESK-PARITY-002 与[双端产品对齐规格](../specs/2026-10-06_084200_双端产品对齐与设置共源规格.md)。Native 合同、受限命令/ACL、保存/导出容量及 53 章仓储链另见[原生存储报告](./2026-10-10_143200_Desktop连续故事原生存储候选与容量实测.md)。前置读取生命周期与 Web 原子保存均保留，未以本片替代其竞态边界。

## 1. 当前能力与必要宿主差异

- `/battle`、`/arena` 真正消费同一设备级故事目录和同一 Desktop owner。两页普通单次草稿仍各自独立；账号变化取消当前执行，但不清除设备故事、未保存结果或未知保存证据。
- 新建冻结当前页故事种子，续写读取原种子、最新章末 checkpoint 与最近十二章投影；最近两章走原 6000 字符正文投影，其余走确定性摘要。列表每页 25 个摘要，选章才读全文，不让 Desktop 复制 Web 的 100/200/400 全记录读取假设。
- 只开放 Direct-local/Direct-remote 线性 Markdown 流式首章/续写。每次显式生成最多一次原执行端口 dispatch；Provider 来源仅存非秘密显示信息，每章使用当前显式选择并冻结的执行目标，旧连接指针不提供权限。
- Hosted 选择时连续故事给出明确不可用说明，原 Hosted 单次保持可用；本片没有分支、重写、删除、插图、隔离内容执行或自动付费摘要。Web 仍保留自身原有分支/重写/删除与付费摘要机制。
- 沿现 Web 连续种子字段，不额外注入普通单次的活动历史/历史引用/分队显示名称。角色历战和当前状态按冻结设置在故事工作副本生效，不写回原卡、单次草稿或账号权威签名。
- 未知保存仅查询原 operation；查询 missing/异常不降格为可重写，也不重新调用模型。Desktop 提供完整原文/正文文件导出、明确丢弃，不新增“另存为新故事”的恢复写入口；Web 原有确认另存语义保持。

## 2. 实际共源入口

1. `domain/arena-battle-story-request` 的 `buildBattleStoryArenaRequest` 由 Hosted session 与 Desktop Direct 实际消费。`baseContext:'arena-provided'`、连续章语义和受控 `internalGuidance` 共源；签名与服务器权限仍在 Hosted。普通 Renderer draft 不能传任意 internal guidance。
2. `ai-core/arena-generation/input-snapshot` 的正式 story snapshot seam 进入原 `executeArenaDirect` / `AiExecutionPort`。最终实际 payload 含 internal guidance 并接受原 12 MiB 预算；没有第二条生成 transport。
3. `ui-web/arena-story-session` 的受控会话目录、章目录、异步阅读区和动作区由真实 Web `BattleStorySessionPanel` 与 Desktop 两页消费。`arena-story-session-read` 的独立通道意图围栏同时保旧 Web reader 和 Desktop 按需读取。
4. Desktop `story-snapshot.ts` 用原 unsigned candidate producer 和共享 completed-record assembler；`story-session.ts` 管 device ownership、冻结图、原包保存/回执查询及导出状态；`story-controls.tsx` 只组装上述真实控件；默认 `arena-story-native.ts` 进入真实受限 Native commands。

### 共同的超长内容呈现保护

共享 `BattleStoryContentPreview` 在正文长度超过 `256 * 1024` 个 JavaScript 字符时默认不挂载报告 renderer，展示完整保留说明、显式展开/收起与直接导出。这个保守阈值用于避开数 MiB Markdown 在默认 DOM/解析路径的即时开销，不声称是某机型的性能极限；不是生成、保存、导出预算。普通正文连额外 wrapper 都不增加。

两端的所选章与实时结果实际消费；Web 待存章同用。换章 key 重置展开状态，Desktop 新请求先卸载上次结果。标题共用最多 192 UTF-8 字节（含明确缩短标记）的有界扫描显示函数，不先 encode/展开完整巨标题、不塞入 title 属性。原 title、正文、保存记录与导出完全不截断。Web 两处删除成功 notice 仅改显示 helper，原删除与写入顺序不变。折叠态 Web 单章导出保原 snapshot 判定附加/去重；Desktop “完整正文”救援出口逐字保正文，原增强报告卡功能在展开后仍可用。

## 3. 九条旅程与失败边界

| 旅程 | 真实消费与验证重点 |
| --- | --- |
| 1 首章 | 两路由显式新建；当前页种子冻结；一次 Direct dispatch；同事务首章及 checkpoint 0/1 |
| 2 续写 | 当前模型新权限，原 seed/最新 checkpoint/最近 12 章；显式引导独立于单次草稿；无 20 章总存储限 |
| 3 取消/失败 | 原 Direct 接收部分原文与仅 meta 原文都保留可导出；0 章/角色效果提交；账号/目标改变不抹掉结果 |
| 4 保存拒绝 | Native 实际暂存 busy 保全文；释放后重试同包同身份；128 MiB 超限不展示无限重试，也不重模型 |
| 5 未知回执 | end 已落库但回执丢失；query-only；missing 不重写；账号变化与 Native 进程重开后原 receipt 可收口 |
| 6 重开/阅读 | 两页共目录；25 项摘要分页；所选详情按需读取；过时详情不能顶替新选择 |
| 7 保存中选旧章 | 用户选章优先；同会话 head/目录仍推进至已知新 revision，下一次续写不被旧 head 卡住 |
| 8 全故事导出 | 固定 head 两遍：count-first 资源预检，再顺序输出/哈希；Native end 校完整长度/摘要/head 才发布；目录页不截全文 |
| 9 宿主并存 | Hosted 连续禁用但原单次可用；唯一关闭守卫覆盖生成/未保存/保存/导出；Web 原分支、重写、动作焦点和选择生命周期保持 |

取消晚于已核验导出 end 回执时仍显示真实已发布文件路径；不会隐藏已创建文件并假称全部取消。导出失败/提前取消不能把 begin 或 partial 当成成功。未提交结果只驻当前窗口内存，离开守卫与文案明确提示原文可能丢失，不承诺抗崩溃恢复。

## 4. 两类容量证据不能混称

原 Native 报告的约 100 MB 长标题 recipe 是当时的基础仓储组装样本；常规 32 预设约 1.14 MB 也只代表该固定配方，不代表所有最终 owner 结果。

本次另跑真实 `DesktopArenaStorySession → executeArenaDirect → completeDesktopStoryRecords → prepareStoryStorageCommit` 极端：2 个普通角色、精确 4,194,304 B 的 U+0000 长标题输出，角色 history/state 写关闭。最终 owner 保留 `report.article.body`，且每章写确定性 fallback summary，因而六个实际字段各约 25.17 MB：session title、session summary、chapter title、markdown、reportJson、deterministicDigest。整体超过 128 MiB。

- 真实终态为 completed + 未保存/tooLarge；只发生 1 次合成模型 dispatch，0 次 receipt/begin/append/end，后点保存也不重模型或 IPC
- 完整 Markdown（4,194,304 B）和 raw JSON 已另存、重读，原文/收到正文/导出 SHA-256 均为 `3f2afc09ed853b298b88b812ad750bc93f4f44a98b07a2ea3b3dd4dd69a6e371`
- 该单进程 2704 ms，maxRSS 419948 KiB；它不包含浏览器 Markdown 渲染，不代替 WebView 内存测量
- 当时 HEAD `e24306b063950c362074b390c99b28542e171a1e` 加 WIP 的源前后清单相同；owner blob SHA-256 `5905bc534a06255109b82a78294cf39fe03a3d2421ada42cf99a267066b91680`，snapshot blob `03e3430b1f2b28a9ed74462888aee9518cb2dfa329a0a7cfa7585af9b278a5c4`。后续 UI 保护与错误文案另经最终定向复核，不冒称这个极端测试是在最终 clean tree 上重跑

既有业务输入 12 MiB 与正文/reasoning 合计 4 MiB 含义不变；128 MiB 只限制一次本地保存的原件字节。本轮在精确 count-before-clone、超限保全文/可导出/零模型重发及真实 Native/UI 证据完成后，认可此独立保存预算；这不是“所有合法 Direct 结果都能保存”的保证。Native 128 MiB/+1、TS 精确 count-before-stringify 与实际 SQLite 原件链详见独立存储报告。拒绝保存合法生成结果是一条明确可恢复的用户路径，不能通过默默删字段、截原文或自动重模型掩盖。
