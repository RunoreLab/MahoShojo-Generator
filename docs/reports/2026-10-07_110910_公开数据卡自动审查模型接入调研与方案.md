# 公开数据卡自动审查模型接入调研与方案

日期：2026-10-07 · 修订：r2（2026-10-07，按维护者口径收敛）· 状态：调研与设计建议（**未评审、非 accepted**）· 依据：`.tmp/safety-eval/` 实测（mercury/span 24 卡、clef-flash 194 卡全量）+ 生产样本 194 张

> 本文档为调研结论与作者建议，不构成已接受的决策或实施计划；待评审通过后再按 docs/ 惯例拆分 ADR/spec/plan。

## 0. 已确认口径（r1/r2 修订来源）

- 旧版 AI 自动审查（`generateWithAI` 结构化 JSON 通路）**统一收编进新设计**，作为 `llm` 后端类型之一，与其他后端走同一套裁决/策略逻辑；其提示词与输出契约按实测结论重构（见 2.2），不机械保留旧 prompt。
- 审核模型与生成模型一样走**环境变量多模型配置**（`AI_REVIEW_PROVIDERS_CONFIG` JSON 数组），可混配不同类型（决策模型、omni-moderation、nemotron、通用 LLM 等）；**各类凭据（含 Workers AI 的 accountId/apiKey）直接写在该条目内**，不设独立 CF_* 环境变量约定。
- **单模型单审**：一次审查只选一个后端执行一次，不做主审+交叉复审；多后端只承担"选择"与"失败回退"。
- 确定结果自动处理；**不确定**按配置走：正常流程（默认）/ 全部保留待审 / 全部通过 / 全部拒绝。
- 按模型类别提供不同适配器，**保留各类后端特有数据**（分类分、flagged、原始类目串、逐题概率等）落入 `details` 供裁决、通知与后续调参使用。
- **默认参数登记实测调优值**：各后端未配置 `thresholds` 时使用代码内登记的实测默认值（来源 `.tmp/safety-eval/` 实验），而不是空值或厂商通用值。
- 落地不设 shadow 期：直接实现到自动拒绝 + omni/nemotron 接入。
- 已决项：自动拒绝**不动 `is_public`**；豁免用户默认 `skip`；**暂不回填**存量 pending；审计表**视情况评估**，首期用应用日志。

## 1. 现状盘点

### 已有机制（apps/web）

- 用户公开新卡：`POST /api/data-cards` → `review_status = is_review_exempt ? 'approved' : 'pending'`；非豁免用户公开卡进 pending。
- 已批准卡的公开更新：写入 `data_card_updates` 待审表，线上版本保持原样。
- 自动审查已有雏形：`config.DATA_CARD_AUTO_REVIEW`（硬编码于 `apps/web/lib/config.ts`）+ `autoReviewLatestPendingPublicDataCardsForUser/UpdatesForUser`（`apps/web/lib/review/auto-data-card-review.ts`），走 `generateWithAI` 结构化输出（`{id, suggestion: approved|rejected, reason}`），**只会 approve，不会 reject**——reject 语义实际是"留 pending 等人工"。
- 敏感词前置检查：`quickCheck` 已挡一层（403+跳转）。
- 模型通路：`parseAIProvidersFromEnv`（`AI_PROVIDERS_CONFIG` JSON / `AI_API_KEY`+`AI_BASE_URL`+`AI_MODEL`）→ OpenAI 兼容 chat 端点；已带负载均衡（random/sequential/round_robin）与渠道可用性记录（`recordAiChannelOutcome`）。
- 消息：`user_messages` 表 + `user.moderation.data_card_rejected` 模板渲染 `payload.reason`，人工拒绝即走此通道（channel='admin'，带 principalId）；系统侧通知用 channel='system'。
- 豁免标记：`users.is_review_exempt`（boolean）。
- 人工审核语义：`cards.review` rejected 只动 `review_status`，不动 `is_public`（拒绝卡仍是 public=1 但不进公开列表）；案件处置类才 `is_public=-1`（封禁）。更新被拒=删除待审行+通知。

### 实测结论（.tmp/safety-eval，详见 REPORT.md）

| 模型 | 接入形态 | 全量/样本 | 最佳规则 | P | R | F1 |
|---|---|---|---|---|---|---|
| clef-flash（Workers AI, 9B） | Jev decisions（state+questions） | 194 全量 | 任一分类分≥0.4 | 85% | 83% | 84% |
| mercury-decide（OpenRouter） | Jev decisions 同上 | 24 子集 | overall≥0.5 或分类≥0.7 | 93% | 81% | 87% |
| span-01-lite（OpenRouter） | 同上 | 24 子集 | pass≤0.5 或分类≥0.7 | 87% | 81% | 84% |
| 现有 generateWithAI（JSON 判定） | OpenAI 兼容 chat | — | — | 未评测 | — | — |

- 决策模型统一返回 0–1 概率；**clef 分类问题强/总分弱，mercury 总分强**——归一化用"任一分类分"对两者都有效；mercury 系建议并入 `v_overall` 否决。
- 漏报集中在软色情边界卡（模型给 0.2–0.48 灰分）与中文政治影射（三模型全部漏判，硬盲区，必须留人工兜底）。
- "高分×已批准"复核清单已被证实有效（欲梦魇经管理员复审转 rejected；da16fea7 同）。友哈巴赫、全局数据卡人工确认 approved（spam 维度误报）。
- 三路分流仿真（clef-flash）：阈值 [0.2, 0.6] → 自动拒 74（误拒9）、自动过 70（漏违规4）、送审 44（违规20/清白24）。自动通道消化 ~76% 流量。

## 2. 方案总览

在现有 `auto-data-card-review.ts` 位置上引入**审查后端抽象 + 归一化裁决 + 策略路由**，旧 LLM 通路收编为普通后端：

```
pending 卡 → 抽取审查文本 → 路由选一个后端 → 归一化 {verdict, score, category, reason, details}
           → verdict=approve → review_status='approved'
           → verdict=reject  → review_status='rejected' + 系统消息（user.moderation.data_card_rejected）
           → verdict=uncertain → onUncertain 策略（默认 normal）
           → 所选后端调用失败 → 路由层换下一个后端重试；全部失败 → 按 uncertain 处理（fail-closed）
```

单次审查 = 单后端单调用；多后端只承担"选择"与"失败回退"职责。

### 2.1 审查后端接口

```ts
type ReviewTarget = { id: string; name: string; description: string; data: string /* JSON 文本 */; type: string };

type ReviewOutcome = {
  verdict: 'approve' | 'reject' | 'uncertain';
  /** 归一化违规倾向分 0–1（各类后端按自身口径折算；无分数语义的给 0/1） */
  score: number;
  /** 归一化违规分类（映射到站内红线类目，见 2.3） */
  category?: string;
  /** 面向用户的简短中文理由（通知文案素材） */
  reason?: string;
  /** 后端原生明细：逐题概率、category_scores、原始类目串等——保留供日志/审计/调阈 */
  details?: Record<string, unknown>;
};

interface AutoReviewBackend {
  readonly id: string;       // 配置中的实例 id
  readonly kind: string;     // 'jev-decisions' | 'omni-moderation' | 'nemotron' | 'llm'
  review(target: ReviewTarget): Promise<ReviewOutcome>;
}
```

### 2.2 配置与后端适配器

环境变量 `AI_REVIEW_PROVIDERS_CONFIG`（JSON 数组，与 `AI_PROVIDERS_CONFIG` 同风格）。每个条目声明 `kind`、连接信息与**该 kind 的特有字段**；凭据（`apiKey`/`accountId` 等）直接写在条目内（或用 `apiKeyEnv` 引用环境变量），不设独立的 CF_* 变量约定：

```jsonc
[
  {
    "id": "clef-flash", "kind": "jev-decisions",
    "endpoint": "workers-ai",
    "accountId": "93d7...", "apiKey": "cfut_...",      // Workers AI 专用账号/凭据就写在这里
    "model": "clef-flash",                              // 或 "clef"（27B）
    "weight": 3
    // thresholds 省略 → 用实测默认（见下表）
  },
  {
    "id": "mercury", "kind": "jev-decisions",
    "endpoint": "https://openrouter.ai/api/alpha/decisions",
    "apiKeyEnv": "OPENROUTER_API_KEY",
    "model": "inception/mercury-decide", "weight": 1
  },
  {
    "id": "omni", "kind": "omni-moderation",
    "baseUrl": "https://api.openai.com/v1", "apiKeyEnv": "OPENAI_API_KEY",
    "model": "omni-moderation-latest", "weight": 1
  },
  {
    "id": "nemotron", "kind": "nemotron",
    "baseUrl": "https://integrate.api.nvidia.com/v1", "apiKeyEnv": "NVIDIA_API_KEY",
    "model": "nvidia/nemotron-3.5-content-safety", "weight": 1,
    "options": { "customPolicy": null }                // 可注入站内红线文本（实验性）
  },
  {
    "id": "generic-llm", "kind": "llm", "weight": 1,
    // 复用既有 PROVIDERS 池 + modelFallbacks；或显式 providerOverride
  }
]
```

**实测默认参数登记**（代码内常量，被条目 `thresholds` 覆盖时以条目为准）：

| kind / 模型 | rejectAt | approveBelow | 附加规则 | 来源 |
|---|---|---|---|---|
| jev-decisions / clef-flash | 0.5 | 0.2 | — | 194 卡全量实测（F1 84%；阈值 0.4 时 F1 相同但误拒多 3） |
| jev-decisions / clef | 0.5 | 0.2 | — | 同族推断，未单独实测 |
| jev-decisions / mercury-decide | 0.5 | 0.2 | `useOverallVeto`（overall≥rejectAt 或任一分类≥0.7 判拒） | 24 卡实测 F1 87% |
| jev-decisions / span-01-lite | — | — | `passVeto`（should_pass≤0.5 或任一分类≥0.7 判拒） | 24 卡实测 F1 84% |
| omni-moderation | 官方 flagged | — | `useFlagged`（官方口径=厂商校准阈值） | OpenAI 官方推荐 |
| nemotron | — | — | 二值：unsafe→reject / safe→approve | 无概率分 |
| llm | — | — | verdict 直读输出 | 见下"llm 重构" |

**`jev-decisions`**——`POST {endpoint}` body `{model, state, questions}`，Jev 形状同时兼容 Workers AI clef 与 OpenRouter decisions；`endpoint="workers-ai"` 时按 `{accountId, apiKey}` 组装 `https://api.cloudflare.com/client/v4/accounts/{accountId}/ai/run/@cf/cloudflare/{model}`。问题集固定为 `.tmp/safety-eval/` 验证过的 **v2 集**（v_overall + 7 分类 + should_pass，9 个 noul，内置 adapter）。归一化 `violationScore = max(分类分)`，按上表规则出 verdict。

**`omni-moderation`**——`POST {baseUrl}/moderations`，`{model, input:[text]}`。类别映射：sexual(+sexual/minors)→sexual、violence/graphic→gore、hate(+threatening)→hate、illicit(+violent)/self-harm*→illegal。**political/spam/inject 无对应类目**——该后端这些维度不报分，覆盖率缺口在文档与日志中显式标注。

**`nemotron`**——OpenAI 兼容 chat：`{baseUrl}/chat/completions`，输出 `User Safety: safe|unsafe`、`Safety Categories: csv`；`options.customPolicy` 可把站内红线翻译成其 taxonomy 注入（实验性）。unsafe→reject（category=首类目原值）、safe→approve、解析失败→uncertain。

**`llm`（现状收编 + 提示词重构）**——复用 `generateWithAI`，但提示词与契约按实测结论重做，对齐决策模型范式：

- 新输出契约（单卡）：`{ verdict: 'approved'|'rejected'|'uncertain', violationScore: 0–1, categories: string[], reason: string }`——显式 uncertain 档与分类数组让 llm 后端也产出可分流灰区，而不是旧设计的二值硬判。
- 系统提示词并入 v2 实测有效的关键口径：**"诱导 AI 生成违规内容"视同违规**（不只描写本身）、**明示违规卖点/发情机制等设计目的**即违规、**中文政治谐音/代称/颂歌**计入 political、**正常生成引导词与社区默许对抗机制表述不算 inject**。
- `reason` 直出中文短句供通知；`categories` 映射到站内类目进 `details`。
- 旧 prompt/schema 不再保留——旧逻辑里 `rejected` 的真实语义是"留 pending"，直接并入新契约的 `uncertain`，语义反而更准。

### 2.3 归一化红线类目

站内统一类目集：`sexual | gore | hate | political | illegal | spam | inject | other`。各适配器把自家分类映射进来；后端未覆盖的维度不参与评分（omni 缺 political/spam/inject，nemotron 按其 taxonomy 映射）。

### 2.4 路由策略（`AI_REVIEW_ROUTING`）

```jsonc
{ "strategy": "priority" | "weighted-random" }
```

- `priority`：按数组顺序尝试，首个成功即采用，后续仅失败回退。
- `weighted-random`：每卡按 `weight` 随机选一个后端，失败按 priority 回退——摊薄各家免费额度。
- 不做结果合并/投票；单次审查最多一条裁决。

### 2.5 策略项（`AI_REVIEW_POLICY`）

```jsonc
{
  "onUncertain": "normal" | "hold" | "approve" | "reject",   // 默认 "normal"
  "exemptUserPolicy": "skip" | "review",                     // 默认 "skip"
  "notifyOnAutoReject": true                                 // 默认 true
}
```

- `onUncertain='normal'`：豁免用户 uncertain→通过；普通用户 uncertain→保留 pending（=现状语义）。`'hold'`=全部留 pending；`'approve'`/`'reject'`=uncertain 一律按该结论处理。
- `exemptUserPolicy='review'`：豁免用户也跑模型——approve 照常通过；reject 同样拒绝+通知；uncertain 按 normal 语义仍通过。

### 2.6 拒绝副作用与通知

- 新卡：reject → `review_status='rejected'`，**不动 `is_public`**（与人工拒绝同语义；`is_public=-1` 封禁保留给案件处置，模型不直接封禁）。
- 待审更新：reject → 删除 `data_card_updates` 行（与人工拒绝一致）+ 通知；线上版本不受影响。
- 消息：`INSERT user_messages(channel='system', message_type='moderation', template_key='user.moderation.data_card_rejected', payload={dataCardId, dataCardName, reason})`，`actor_user_id`/`created_by_admin_principal_id` 均为 NULL——复用现有渲染器零改动。reason 形如"自动安全审查检测到疑似违规内容（性内容/血腥猎奇/政治影射/…）；如属误判，请修改后重新公开或联系管理员"。

### 2.7 审计（可选，视情况评估）

`auto_review_decisions(data_card_id|update_id, backend_id, model, details_json, verdict, reason, latency_ms, created_at)`。价值：阈值离线重仿真、误拒申诉溯源、后端 AB 对比。首期只落应用日志（verdict+backend+score+category+latency），申诉场景出现或需调参时再建表——不阻塞上线。

## 3. 落地顺序（不设 shadow 期，直接到自动拒绝）

1. **骨架 + 全适配器**：`AutoReviewBackend` 抽象、`AI_REVIEW_PROVIDERS_CONFIG` 解析、jev-decisions / omni-moderation / nemotron / llm（含提示词重构）四种适配器、实测默认参数表、路由与策略执行、拒绝副作用+系统消息。
2. **上线即 enforce**：`rejectAt` 用登记默认值（clef-flash 0.5）；建议先用 `onUncertain='normal'`、豁免 `skip`。
3. 观察期**只靠应用日志与人工抽样**看误拒率；确需重仿真再补审计表。
4. （可选）uncertain 卡联动众裁任务闭环消化灰区流量。

## 4. 风险与边界

- **政治影射盲区不可解**（三模型一致漏判中文谐音/典故类）：靠举报+人工兜底，不应为调阈值而压低 approveBelow——会把大量正常卡打进送审队列。
- **"诱导生成"语义**已固化在 jev 问题集与 llm 新提示词中；自定义 prompt/策略变更时需保留该口径，否则杀人版/伍萬类卡会漏。
- omni-moderation 对中文、社区梗、抄袭类违规覆盖差且无 political/spam/inject 类目；nemotron 二值判定无灰区——两者定位为**备选/兜底**，不建议做唯一主审。
- 免费额度：clef-flash ~1M tokens/日 ≈ 150–300 卡/日，覆盖日常增量充足；存量 12.5k pending 按已决口径不回填。
- `onUncertain='approve'/'reject'` 保留为可选项但默认不建议：approve 有漏放风险，reject 会放大模型误报。

## 6. 实施状态（2026-10-07）

第 3 节第 1 步已落地：

- 共享层：`packages/hosted-runtime/src/auto-review/`（`types/question-set/state/config/backends/engine`），经 `./auto-review` export 对外；四类后端（jev-decisions / omni-moderation / nemotron / llm）与路由（priority / weighted-random）、实测默认阈值表、v2 问题集齐备。

- `exemptUserPolicy='review'` 已接入创建/更新两条写路径（豁免用户同样进 pending/待审更新队列）。
- 环境变量文档补进 `apps/web/env.example`。
- 测试：`packages/hosted-runtime/tests/auto-review.test.ts`（24 项：配置解析/阈值登记/四后端解析/路由回退/uncertain 策略）、`apps/web/tests/auto-data-card-review.test.ts`（8 项：状态流转/消息/幂等/豁免/更新拒绝）。
