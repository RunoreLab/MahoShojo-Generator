## 2. resolver 修复的锁源依据

适用锁文件：`apps/desktop/src-tauri/Cargo.lock`，Tauri / tauri-runtime-wry 2.12.0、Wry 0.57.0、http 1.5.0。

1. Wry [WebView2 注册及请求准备](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/webview2/mod.rs#L925-L1085) 匹配 `http://<scheme>.*`，在构建 `http::Request` 前调用 URI 还原函数
2. [原始还原函数](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/custom_protocol_workaround.rs) 将 `http://maho-webpkg.` 前缀换回 `maho-webpkg://`。因此正规浏览器 URL 的 Native 形态为 `maho-webpkg://localhost/...`；`http://maho-webpkg.evil.example/...` 的 handler authority 为 `evil.example`
3. [tauri-runtime-wry 透传](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.0/crates/tauri-runtime-wry/src/lib.rs#L4847-L4855) 与 [Tauri manager 透传](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.0/crates/tauri/src/manager/webview.rs#L213-L223) 均未再改写 request

本次 resolver 只接受 `http::Uri.scheme_str() == maho-webpkg` 且**完整 authority 字节等于 `localhost`**。不经 URL 规范化，不只比较 host，因而 Native 收到的 userinfo、显式端口、尾点、别名、缺少 scheme/authority 或未经还原的 HTTP URI 均走同一 404。然后继续原 label ↔ instance、包内路径、声明文件与 Range 边界；失败时不泄漏文件长度。导航回调处理的是浏览器 URL，继续使用独立判据，本次不改。

浏览器可能先把 HTTP 默认端口、大小写等规范化；Native 严格拒绝的是**实际收到**的非规范 URI，不能把人工构造的 `http::Uri` 单测当成浏览器会逐字保留输入的证据。

定向源码验证：真实 `webpkg_instance.rs` 的 20 条 Rust 测试通过，其中新增 24 类非法 URI × 无 Range / 有效 Range / 不可满足 Range，断言 status、全部 headers、body 与同一 404 完全相同；正规请求含 query / 206 与原 label 隔离保留。另实际调用下载的 Wry 0.57.0 原始映射函数，8 个映射输入及上游单测通过，总 22 条。`rustfmt --check`、`git diff --check` 通过。无新增生产依赖。

此验证直接编译真实模块与锁定依赖；只有 Tauri GUI 外壳以调用即 panic 的替身提供类型，未执行 GUI、真实 IPC、Windows、WebView2 或完整 Tauri 构建。完整 workspace CI 也未由此宣称通过。

## 4. D4-S01：规范来源的真实 handler 采样

只在 `resolve_webpkg_request` 入口、origin 判定**之前**加入以下临时观测；本次包路径固定且全部是合成内容：

```rust
#[cfg(debug_assertions)]
if request.uri().path().ends_with("/d4-origin-probe.png") {
    eprintln!("d4-origin label={} uri={}", webview_label, request.uri());
}
```

在包窗真实按钮触发以下三组资源请求，并各记录浏览器请求 URL、Native URI、instance / label、status 和固定响应体。先做正规正对照，拿到真实 200 后再做负向：

- 正规相对 `./d4-origin-probe.png`；预期 Native 为 `maho-webpkg://localhost/__web-package__/instance/<本id>/d4-origin-probe.png`，200 图片正常
- 同路径改成 `http://maho-webpkg.localhost.localhost/...`；预期映射后 authority `localhost.localhost`，404 `Not Found`
- 同路径改成 `http://maho-webpkg.localhost:47991/...`；预期保留非默认端口并被统一 404。无需启动该端口服务

这些 Windows 地址均使用 localhost 名称，Wry 应在本机协议层处理；如果没有 Native trace 或出现真实连接尝试，立即停负向探针，记“未到达 handler”，不当成 resolver 拒绝，也不继续探测网络。旧 `.evil.example` 等后缀由本页纯 Rust 回归覆盖，本轮不再向外部名称发请求。若新策略先阻断请求，记录实际 CSP 阶段并保留 Native 项待测，不能临时放宽策略绕过。

用两个新实例 A / B 的正规 URL 重验一次 A 读取 B 同名图仍 404，A 自身图仍 200。非规范 origin 的有效 / 不可满足 Range 若能由当前浏览器发出，也都应是同一 404；若预检或浏览器先拦，记录其层级，不能替代 Native Range 单测。

## 5. D4-S02：`javascript:` 返回新 Document 与 policy 继承

标准的 [`javascript:` URL 特例](https://html.spec.whatwg.org/multipage/browsing-the-web.html#the-javascript:-url-special-case)在返回字符串创建 Document 时沿用现文档 policy container；这是预期，仍需本次 WebView2 的实际证据。

准备两个只差一个 CSP meta 的合成入口：

- 对照包：不含额外 CSP meta，包内同一 PNG 正常加载
- 收紧包：`head` 开始放 `<meta http-equiv="Content-Security-Policy" content="img-src 'none'">`，入口自身的同一 PNG 被 CSP 拒绝；这只进一步收紧合成页

两包入口均有旧 DOM 标识和真实 `<a>` 链接。用入口脚本设置链接 `href` 为 `javascript:` 加一个**返回完整 HTML 字符串的表达式**；不能用 `void`，不能只修改原 DOM。可按以下形态生成，返回页本身不要含新的 CSP meta：

```javascript
const nextHtml = '<!doctype html><meta charset="utf-8"><title>D4 new document</title>'
  + '<p id="d4-new-document">new-document</p>'
  + '<img id="policy-image" src="./d4-policy-probe.png">';
document.querySelector('#replace-document').href = 'javascript:' + JSON.stringify(nextHtml);
```

真实点击链接后：

1. 记录新 DOM 标识出现、旧节点消失、Document / CDP frame 与 securityOrigin，及 `location.href`。URL 不变本身不能否定新 Document，也不能用 location URL 当安全 origin
2. 重新观察 `localStorage`、cookie、IndexedDB 的允许/异常和固定合成值，不读取其他数据；用原 W02 方式重放**一条无副作用** `desktop_runtime_info`，记录实际拒绝类别。若仍 `Origin invalid`，只记命令未执行
3. 对照包返回的新页中，PNG 应正常解码；收紧包返回的新页中，PNG 应继续被 CSP 拒绝。保存 Network 的 blocked reason / CSP violation 及 `naturalWidth`；仅 `img.onerror` 无法区分 CSP 与资源错误
4. 若导航回调拒绝导致未产生新 Document，如实记“未创建，继承项未测”。若已创建却出现 storage / IPC 能力或丢失 policy 的证据，停止此执行分支，保留日志并报告，不自行添加权限补救

原地 JS 执行与新 Document 两项必须分列；不要把“脚本能运行”单独判为 escape。

## 6. D4-S03：包内真实 `window.close()`

新小包入口放真实按钮，click handler 仅调用 `window.close()`。先记录 OS 顶层 HWND、WebView target、instance / label 和窗口正常可见/可交互；再真实点击按钮，不能用 CDP `Page.close` 代替。

可在既有 `WindowEvent::Destroyed` 分支与 `remove_by_label` 完成后加只含合成 label 的 debug 时间戳日志，不新增 query / close command。记录三层是否都结束：OS 窗口、WebView target、Native registry。随后在主窗沿现临时诊断的 `openSameInstance` 调同一 id 一次，预期 missing / 明确已销毁，不应返回成功却聚焦空窗。

- 若浏览器明确拒绝页面关闭、原页和 OS 窗口仍正常，记录这种限制；不能强判为资源泄漏
- 若 WebView 已死、OS 空窗与 registry 仍活，才确认页面 close 也命中旧僵尸表现；立即通过该测试窗正常 OS 关闭并验清理，回报后单独修复
- `WM_CLOSE` 是 OS 关闭正对照；CDP `Page.close` 仅标作调试路径历史对照。无必要重跑 CDP 异常，更不能把三者合并为一个“关闭通过”

锁定 [Wry 0.57.0](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/webview2/mod.rs#L625-L630) 在 `WindowCloseRequested` 销毁的是其容器 HWND；仅这段源码不足以推出 Tauri 顶层 `Destroyed` 已发生。本片不修改生命周期。
