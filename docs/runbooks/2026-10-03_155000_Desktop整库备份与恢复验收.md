# Desktop 整库备份与恢复验收

状态：真机待验；D2.4 实现的补充验收入口。
依据：[运行时规格 DESK-058 / DESK-073](../specs/2026-09-30_160000_Desktop客户端实施规格.md)、
[阶段计划 D2.4](../plans/2026-09-30_160100_Desktop客户端阶段实施计划.md)。

维护者已允许先开发 D2.4；本记录不关闭 [D2.3 / D2.5 既有真机门禁](./2026-10-03_120000_Desktop归档与产品壳真机验收.md)。

## 验收准备

使用可丢弃的测试数据与本地构建。先保留需要的真实用户数据；本流程中的“恢复”会整体替换当前客户端库。
构建、测试与启动命令以根及 `apps/desktop/package.json` 为准。不要运行生产部署或远端迁移。

备份范围是当前 SQLite 管理的数据卡、Web 包、软删除记录、Provider 配置及凭据引用，以及数据库管理的
blob。它不包含 OS 凭据明文、未迁入本地库的其他草稿/历史、已有导出和已有备份。移动备份时复制整个
备份目录，不要只复制 `library.sqlite`。应用没有自动清理备份的策略。

## 真机步骤

1. 在本地库页面创建备份 A，记录页面回显的完整目录。核对目录含数据库、`blobs/` 和最后发布的
   `manifest.json`；备份列表刷新后仍显示 A。大库备份期间观察窗口重绘、CPU/内存与导航/关闭保护。
2. 导入另一批可识别的测试数据 B，再创建备份；同秒反复创建也不能覆盖 A。检查备份与归档操作不会同时启动。
3. 选择 A 的恢复入口，先取消二次确认；应用应继续使用 B，且不能产生恢复请求。再次选择 A 并确认：
   必须先成功创建当前 B 的恢复前备份，随后安排恢复并退出应用。退出失败时应保留提示及重试退出入口。
4. 重新打开客户端。确认本地库回到 A，B 的恢复前备份仍可见。Provider 凭据不随备份迁移；缺失时设置页
   应明确提示重新录入 API Key。再写入新数据 C 并重开，确认不会重复恢复 A 而丢掉 C。
5. 在可丢弃的备份副本中删除 manifest 或修改一个 blob 的字节，刷新列表；该目录只能计入无效项，不能选择恢复。
   备份期间磁盘不可写/空间不足的手动测试也必须使用测试环境；失败不得将不完整目录列为可恢复备份。
6. 记录 Windows 构建版本、各步结果与日志。原生文件交换的自动故障注入验证的是进程中断后重放的文件状态，
   不等同于实机断电测试；不要为了验收在真实用户库上强杀或断电。

## 恢复失败的处理边界

未完成恢复时客户端拒绝打开数据库，保留 `restore.intent`、`.restore-staging/`、`.restore-old/` 与
`.restore-journal/`。旧库 SQLite 主文件和原有 WAL/SHM 在同一旧代际目录中保留，不能随意混搭。
提交成功后也保留这些诊断目录和恢复前备份，当前版本不自动淘汰。

遇到失败先记录错误码、构建版本和目录存在情况；不要删除 intent、单独搬回 WAL、手工创建空数据库或
重复覆盖正式目录。应根据恢复日志确认完整代际后再进行人工恢复。修复磁盘/权限问题后，重新启动可继续重放。
