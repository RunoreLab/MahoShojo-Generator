# Arena 多人发布最小检查清单

状态：`accepted`
日期：2026-09-01
用途：替代 GMR-10Q / GMR-11 / sourceDigest / evidence 型生产发布阻断

## 1. 原则

多人发布判断只回答：

> 当前候选版本是否存在会让用户实际遭遇严重权限、安全、数据或资源问题的已知 blocker？

不回答：

> 是否已经产生足够多的机器审计证据来证明我们准备好了？

普通 bug、边缘恢复缺陷、文档未更新、evidence 过期，不应自动阻断发布。

## 2. 必须通过

### 服务

- [ ] production Hono `/api/health/ready` 正常；
- [ ] Redis 可连接；
- [ ] Room 所需环境变量存在；
- [ ] production CORS / Origin 与实际 Web origin 一致；
- [ ] feature flag 可以关闭多人入口。

### 授权

- [ ] 未登录访问 Room endpoint 被拒绝；
- [ ] 无 ticket WebSocket upgrade 被拒绝；
- [ ] member 无法执行 host-only command；
- [ ] Room ticket 不能跨 Room 使用；
- [ ] 客户端不能通过提交 `isNative=true`、revision 或 role 字段提升权限。

### 主流程

至少一次双客户端 smoke：

```text
Host 登录
-> 创建 Room
-> Member 登录并加入
-> 双方看到同一 Room
-> Member 提交 Proposal
-> Host 接受或拒绝
-> Host 发起 generation
-> 两端获得结果 / terminal
-> 任一端刷新/重连后 Room 仍处于合理状态
```

注：此项已在先前完成并通过

### 资源

- [ ] client frame 有大小限制；
- [ ] outbound send queue 有边界；
- [ ] 单用户 / 单 Room 存在合理连接 / 操作限制；
- [ ] generation 不会因为客户端重连自动重新 dispatch Provider。

### 回滚

- [ ] 可以把 multiplayer feature flag 关闭；
- [ ] Hono 有上一版 release 可回滚；
- [ ] rollback 不要求执行破坏性数据库回迁。

## 3. 非阻断项

以下项目可以 release 后继续改进：

- host refresh 的极端竞态；
- 个别 UI 文案 / 可发现性问题；
- 不影响权限边界的 presence 显示错误；
- 某个 fault injection 场景未自动化；
- slow consumer 的体验优化；
- Room directory 的非关键性能优化；
- GMR 状态、review marker、source digest 未更新；
- 没有独立 reviewer evidence；
- 普通 Arena 战后角色更新等不属于多人核心路径的独立 bug。

如果某“普通 bug”实际上会导致数据破坏、权限提升、凭据泄露或重复大额 Provider 调用，则重新升级为 blocker。

## 4. 发布后的观察

首发后重点观察：

- Room create/join 成功率；
- WebSocket 非正常关闭率；
- generation start/terminal 比例；
- duplicate Provider start；
- Redis error；
- host/member authorization rejection；
- feature flag rollback 是否需要使用。

这些数据用于发现真实问题，不要求先建立新的 release evidence gate。
