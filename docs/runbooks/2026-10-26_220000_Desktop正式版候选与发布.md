## 发布范围

维护者确认 Beta 测试基本完成，目标为 Desktop 0.1.0，Windows x64、NSIS currentUser、GitHub Releases。
Windows 11 x64 正式支持，Windows 10 22H2 经实机验收后兼容处理；不新增其他平台或安装格式。
Windows Authenticode 首发暂缓，Tauri 更新包签名保留。应用 identifier、数据目录与凭据 service 不变。
本轮不修改生产数据库格式，不新增业务 API、镜像服务或自动生产部署。

这是非商业社区项目：沿用已有 CI 和合理验收，不新增 enable 开关、多层人工审批或强制 RC 轮次。
维护者负责合并到默认分支、部署官网并手动发布 GitHub Release；本次开发不执行这些公开操作。

| 文案 | [0.1.0 发布说明](../references/2026-10-26_224500_Desktop010发布说明.md)、[公告草案](../references/2026-10-26_220000_Desktop正式版公告草案.md)、双端百科 |

官网以 `apps/web/lib/desktop-release.ts` 的版本为当前发布目标，查询缓存约五分钟。
仅有 CI artifact、草稿 Release、预发布版本或缺少资产时不会开放正式下载。GitHub 暂时不可达会显示重试说明。
下次发布需随代码更新该目标版本；不使用仓库级 `releases/latest`，避免 Web tag 或 RC 干扰桌面更新。

Beta 没有内置 updater，首次升级须手动下载覆盖安装。0.1.0 起可通过设置检查后续版本。
插件的 check / download / install / download_and_install 权限均未授予 renderer；仅有三个应用自有 command。
renderer 不能提供下载 URL、路径或公钥。官方插件完成验签后才调用安装器；安装交接会关闭应用。

## 手动构建

两份桌面打包 workflow 都只有 `workflow_dispatch`，普通 push 不打包：

- `Desktop Package`（`desktop-package.yml`）：内部不签名打包，临时关闭 updater artifacts，无发布凭据。
- `Desktop Release Candidate`（`desktop-release-candidate.yml`）：运行既有 Repository CI 与 Windows Rust 检查，生成签名候选及摘要、attestation，不创建 tag 或 Release。

GitHub 签名构建前，在 `desktop-release` environment 配置 `TAURI_SIGNING_PRIVATE_KEY` 与
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。该 environment 仅隔离签名凭据，不要求额外审批人。
当前未上传或配置远端凭据。也可使用本机密钥构建，再运行候选整理脚本。

选择含最终代码的分支手动运行候选 workflow，输入：

- version：`0.1.0`
- channel：`stable`
- notes_file：`docs/references/2026-10-26_224500_Desktop010发布说明.md`

本地整理同一提交构建的产物：

```powershell
node scripts/prepare-desktop-release.mjs --version 0.1.0 --channel stable --commit <完整SHA> --bundle-dir <NSIS产物目录> --output-dir <尚不存在的目录> --notes-file docs/references/2026-10-26_224500_Desktop010发布说明.md
```

脚本检查版本、配置、公钥、HEAD 和干净源码，检查签名信封与版本，然后保留安装包/签名字节，导出：
`MahoShojo-Generator_0.1.0_x64-setup.exe`、同名 `.sig`、`latest.json`、`SHA256SUMS.txt`、`RELEASE_NOTES.md`、`release-metadata.json`。
使用 ASCII 发布文件名，避免 [GitHub 重命名特殊字符资产](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset)导致清单 URL 不匹配（2026-10-26 核验）。
GitHub 构建另附 `provenance.jsonl`。脚本不覆盖已有输出目录，也不发布任何内容。
信封检查不能替代密码学验签；真正安装仍由官方 updater 验证。任意手动放入的 exe 也不能仅靠 metadata 证明其源码来源。

## 最后验收与手动发布

Beta 已完成的功能不机械重跑。对最终签名安装包核实以下增量，并记录版本、源码 SHA、安装包 SHA256、Windows / WebView2 版本：

1. Windows 11 普通用户安装、启动；缺失 WebView2 时的联网引导与断网提示。
2. 备份后由 Beta 覆盖安装，确认本地库、图片、设置、会话与凭据保留；不要先卸载或清理数据。
3. 小屏和常用 DPI 下的主窗口/确认弹窗、输入法与焦点。窗口下限 800×450，启用启动时 `preventOverflow`。
4. 后续不同版本的签名包升级：正确签名可安装，错误/缺失/损坏包拒绝，取消与忙碌期保留当前安装。自动测试不替代安装器实机交接。
5. 如宣称 Windows 10 22H2 兼容，补充该环境结果。没有结果时不标为已通过。

完成后由维护者按以下顺序发布：

1. 合并到默认分支，生产部署 Web。此时未发布 Release，下载页仍显示筹备状态。
2. 手动构建并验收最终候选；使用该提交创建 `desktop-v0.1.0` 的 GitHub Release 草稿。
3. 将候选目录中的文件上传到草稿，核对资产名称及 SHA256，再手动发布为正式 Release。不要重新编译或替换已验收文件。
4. 公开后检查官网显示下载、安装包可下载、官网更新入口指向该 Release 的 `latest.json`。无需再改开关或额外部署下载配置。
5. 将核对后的公告正文加入 `content/announcements.json`，使用实际发布日期，再按正常 Web 流程发布公告。

发生发行问题时先撤下有问题的分发入口，以更高版本修复；不覆盖旧 tag 的安装包。
安装旧程序不能回滚数据库 schema，必要时使用升级前备份。本次无数据库迁移。
