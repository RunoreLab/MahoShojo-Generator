## 候选构建底座

新增 `.github/workflows/desktop-release-candidate.yml`，只可手动运行。流程为：无凭据源码前检 →
Repository CI → `desktop-release` environment 审批 → Windows Rust 检查、签名 NSIS 构建 →
候选清单与摘要 → artifact attestation → 上传待验收文件。该 workflow 没有 `contents: write`，不创建 tag/Release 或发布在线清单。

启用前需完成 updater 接线并把版本切为 RC/Stable。维护者还需在 GitHub 配置 `desktop-release` environment 的
审核人与允许分支，确认保护规则后设置 `DESKTOP_RELEASE_ENABLED=true`，并安全配置
`TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。
单有 environment 名称或 enable 变量不证明已启用审批；当前仓库尚未配置这些远端凭据。
workflow 使用输入版本、通道和同一提交已跟踪的 Release Notes 路径；它从本次 dispatch 的完整 SHA checkout。

`scripts/prepare-desktop-release.mjs` 也可本地准备候选目录：

```powershell
node scripts/prepare-desktop-release.mjs --version 0.1.0-rc.1 --channel rc --commit <完整SHA> --bundle-dir <NSIS产物目录> --output-dir <尚不存在的输出目录> --notes-file <仓库内已跟踪的ReleaseNotes文件>
```

`--check-source` 可单独校验版本/配置/HEAD/干净源码。helper 拒绝 Beta 混入 RC/Stable、四处版本不一致、
通道端点不匹配、缺失公钥/签名、空文件、多安装包及覆写输出。忽略目录之外的未跟踪源码也会被拒绝。
它还要求 `requireSignedVersion: true`、签名 packet 与公钥 key ID 一致、trusted comment 中的唯一版本与候选版本一致；
此版本绑定由当前 Tauri CLI 构建自动生成，手工签名时使用官方 `--app-version` 参数。
输出包含原字节安装包、`.sig`、`latest.json`、`RELEASE_NOTES.md`、`release-metadata.json`、`SHA256SUMS.txt`。
metadata 记录候选状态、commit 和通道；下载 URL 只指向固定版本 tag 的 GitHub 安装包，文件名按 URL 编码。
手动传入的任意 exe 不能仅凭 metadata 就证明来自所填 commit，源码与构建关系依赖实际连续构建和 attestation。

签名检查只验证信封结构，不能取代 Updater 的密码学验签；最终候选需要真实正确/错误签名与损坏包测试。
当前 Beta + 无 updater 配置会在轻量前检失败，不应为让流程通过而填入假公钥、放宽前检或跳过验证。
GitHub 构建与 attestation 尚未实际运行。`.github/ISSUE_TEMPLATE/desktop.yml` 为安装、升级和功能问题提供脱敏反馈字段。

## 更新密钥保管

维护者已授权生成新的更新密钥。2026-10-26 已完成：

- 私钥位于当前 Windows 用户的 `%LOCALAPPDATA%\MahoShojo-Release\signing\updater.key`，由高熵随机口令加密。
- 口令以当前用户 Windows DPAPI 密文保存在同目录 `updater-password.dpapi`；目录去掉继承权限，只允许当前用户与 SYSTEM。
- 公开文件为 `apps/desktop/src-tauri/updater-public-key.pub`；目前仅保存信任根，尚未配置为运行中的 updater 公钥。
- 公钥文件 SHA-256：`19bc4d6ecfab7c6b8a1cb55808910e2590078e2d82c4579ee1acc4d32b97fb0c`。
- 已实际恢复 DPAPI 口令并签署无业务内容的测试文本，CLI 生成的签名信封通过检查；这不是安装包更新验收。

DPAPI 密文依赖当前 Windows 用户环境，直接复制到其他机器不能视为可恢复备份。
首次发行前还须把加密私钥与可恢复的口令分别备份到维护者控制的离线介质/密码库，并做恢复试验。
生产应用服务器不参与签名，当前不向它上传更新密钥。若以后采用服务器备份，应使用独立备份位置，
解密材料分离保管，且不能把它当作离线备份；发布私钥不进入 Web/Hono、普通 CI 或客户端。

后续更新接线应按 DESK-011 逐项记录官方 Updater 的权限与窄自有 command；不得直接向 renderer 开放插件的全套更新权限。
同样需要确认签名绑定版本，防止仅修改未签名清单的版本字段而复用旧包；默认版本比较不等于对安装包版本的认证。

## 安全更新的实施边界

采用官方 Tauri 2 Updater；[官方文档](https://v2.tauri.app/plugin/updater/)已于 2026-10-26 核验。
Native 层负责固定更新端点、版本与更新资源，只有可信主窗口获得窄更新能力，不为不可信 Web 内容增加权限。
客户端内置公钥；私钥只进入受保护发布环境并做离线备份，不进入仓库、客户端、日志或普通 CI。

1. 先确定密钥保管与恢复责任，再接入公钥、插件与固定 HTTPS 清单。
2. 正式通道计划为 `https://mahoshojo.colanns.me/desktop/updates/stable/latest.json`；
   RC 使用独立通道，不把 RC 清单复制到 stable，也不依赖仓库级 `releases/latest`。
3. 启动检查不阻塞本地操作；设置提供手动检查、版本、摘要及错误反馈。
4. 安装须用户确认，且不能中断生成、写库、备份或恢复。不得强制静默重启。
5. 正确签名可更新；缺签名、错误签名、损坏包、网络错误与降级请求均不改变当前安装。
6. Beta 未内置 updater，首次进入正式版本须手动下载覆盖安装；先备份再升级。

密钥丢失或泄漏时先停止分发，不修改旧资产。密钥轮换与向旧客户端交付新信任根要单独设计；
不能假定换公钥后所有已安装客户端自动接受新包。

## 最终候选的验收与提升

沿用内部安装包 runbook 的 A–E 表，并记录源码 SHA、版本、安装包 SHA-256、OS build、WebView2 版本和测试人。
重点增量验收如下，不机械重跑已无影响的全部 Beta 功能：

| 范围 | 需要的证据 |
| --- | --- |
| 安装 | 干净 Windows 普通用户；WebView2 缺失的联网引导及断网失败；中文路径 |
| 数据 | Beta → RC → Stable 覆盖安装，卡片、图片、Web 包、设置、会话与 OS 凭据保留；升级前整库备份可恢复 |
| 窗口 | 1366×768 @150%、125% DPI、真实 WebView2 的按钮/弹窗/IME/焦点；最小尺寸已改为 800×450 并启用启动 preventOverflow，实机验收仍待完成 |
| 更新 | 两个不同版本的实际签名包；正确/错误/缺失签名，损坏、断网、取消、忙碌期与拒绝降级 |
| 核心功能 | Direct/Hosted、登录、本地库、离线首页和百科、独立 Web 内容窗口；只在已支持范围抽查 |
| 许可 | 核实实际打包的品牌图、预设、图标、字体和依赖；`ASSET_LICENSE.md` 的保留权利不是第三方再分发授权 |
| 制品 | 版本一致、固定 tag URL、SHA256、更新签名、清单、Release Notes 和 artifact attestation |

RC 验收后更改版本号并重新构建 Stable 会改变安装包字节，因此 Stable 仍须验收自身的最终 SHA-256。
最终安装包验收后直接发布同一份字节，不重新编译后把新产物当作已验产物。记录可下载 URL 与摘要核对结果。
安装旧程序不能回滚 SQLite schema；发生发行故障优先停止更新推送并用更高版本修复，必要时使用升级前备份。

公开操作顺序：经维护者批准 → 创建固定 `desktop-v<version>` Release → 上传已验资产且不覆盖旧文件 →
独立下载核对 → 发布对应更新清单 → 更新 Web 下载配置并部署 → 最后发送站内公告。
tag、Release、凭据配置及生产切换需要按根 AGENTS 的高风险边界获得相应授权。
