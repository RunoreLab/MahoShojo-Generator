状态：`ready-for-controlled-acceptance`，生产配置与发布尚待单独授权。
日期：2026-09-12。
适用入口：`admin.mahoshojo.colanns.me`。`homura-admin.colanns.me` 是 Arcane Docker 控制面，不是业务管理端。

本文执行已批准的 [Admin 安全规格](../specs/2026-08-29_Admin回归安全与迁移规格.md)与[迁移计划](../plans/2026-09-12_130000_独立线上管理端迁移实施计划.md)，遵循[复杂度预算 ADR](../decisions/2026-09-01_193200_平台复杂度预算与故障降级决策.md)。它记录上线和恢复操作顺序，不新增 source digest、evidence registry 或追溯式发布门禁。

## 1. 当前状态与责任边界

仓库已具备独立 React/Hono Worker、D1 principal、操作级授权、审计、持久作业、合成本地环境和受控部署工具。真实 Access Application、邮箱名单、AUD、资源绑定、远程 migration 和生产发布均需要在具体目标与产物可审阅后单独授权；本地测试不能替代这些验收。

运行命令、配置变量和工具参数以 [Admin README](../../apps/admin/README.md)、[package.json](../../apps/admin/package.json)、[部署工具](../../apps/admin/scripts/deploy.mjs)与 [principal 工具](../../apps/admin/scripts/principals.ts)为准。发布仅通过[手动 workflow](../../.github/workflows/admin-deploy.yml)的 `admin-production` environment；测试、build 和 dry-run 不发布。

## 2. 配置与资源准备

[合成配置示例](../../apps/admin/scripts/deploy.example.json)能通过部署工具的结构检查，所有账户相关值均为示例，**不代表任何已核实资源，也不是可直接上线的配置**。复制到仓库外的私有文件后，逐项替换和核实 Access 与资源标识。不要把实际邮箱、token、密钥或私有配置提交到公开仓库；不要以修改仓库 deny-all 默认值的方式部署。

| 资源 | 绑定和核实事项 |
| --- | --- |
| D1 | `DB` 指向当前业务数据所在的正确环境；生产 Admin 与 Web 共享业务数据，但 Admin 通过当前请求原生 binding 访问。测试与演练使用独立库，不能沿用生产 ID。 |
| R2 | `ADMIN_OBJECTS` 专用于私有导出、AI 结果和恢复材料；`LARGE_OBJECTS` 指向同环境业务对象库。两者分开核实，无公开 bucket、公开自定义域或匿名下载地址。 |
| Queue | `ADMIN_QUEUE` 与唯一 consumer 指向独立 Admin 队列，不能混入公共 Web/Arena 队列。保留有界批次、重试和补偿扫描。 |
| Access | issuer、AUD、JWKS 属于本次新建的 Admin Application；邮箱允许名单在 Access 中管理，不是 D1 principal key。 |
| Writer | 首发 `ADMIN_ENABLED_ACTIONS` 为 `[]`，只读验收完成后逐动作开启。应用内 capability 仍单独检查。 |

部署工具固定 hostname、Worker-first assets、资源结构和禁止公开入口的配置；它不能证明真实账户资源、Access policy 或邮箱名单配置正确。`workers_dev=false`、preview URLs 关闭、`run_worker_first=true` 在私有配置中也必须保留。

只读模型、签名或 AI 等可选能力所需的私密配置，按实际功能经受控环境提供，不能塞进示例 JSON 或浏览器包。自动每日快照另需显式设置 `ADMIN_ANALYTICS_PRINCIPAL_ID`，并启用 `analytics.snapshot`；委托者须为当前 active human principal 且具有 `analytics.write`。默认不配置该项。定时过程每次最多补一日、只检查最近七天缺日；管理端手动回填仍按业务接口限制，不能把 cron 当作无限历史修复任务。

先按 README 完成本地构建，再对私有配置运行 dry-run；例如在 PowerShell 中设置 `ADMIN_DEPLOY_CONFIG` 为已审阅文件的绝对路径后：

```powershell
node apps/admin/scripts/deploy.mjs --dry-run
```

保存本次候选版本、实际检查结果、已知环境限制和回滚目标即可，不生成额外源码证明清单。

## 3. Access 与首个管理员上线顺序

1. **先封闭入口。** 在获授权后，为固定 hostname 创建独立 Access Application，初始 deny-all；不要复用 Arcane Application/AUD，也不要添加 Bypass、Everyone 或其他可绕过精确名单的 policy。核实目标 Worker 没有其他 route、公开 workers.dev 或 preview 入口。
2. **准备数据库与私有资源。** 核对 migration 状态和可恢复备份，按下一节执行获授权的增量 migration；部署候选只读 Worker 时维持 Access 封闭与 writer 关闭。
3. **只开放维护者身份。** 配置 One-time PIN 登录，将允许条件限定为维护者本人精确邮箱地址。逐项 read-back 实际 Application、policy、邮箱与 AUD；不要使用整个邮箱域名的允许规则。此时 Access 登录成功后，应用因尚无 D1 principal 返回拒绝属于预期。
4. **从真实验签结果 bootstrap。** 由维护者在受控客户端取得该 Application 的新 Access token，暂存到权限受限文件，通过 principal 工具读取。工具校验签名、issuer、AUD、期限和 human 身份，再按稳定 `issuer + subject + kind` 建立主体；初次只授予已核实的只读 capability。不要将 token 粘贴进工单、日志、公开文档或普通命令参数，不使用 decode-only 或本地合成 token 替代真实验签。
5. **执行受控初始化。** 配置项和临时 token 文件位置见 principal 工具与 README。远程命令同时需要明确目标环境、维护者授权、受保护 gateway 和 `--confirm-remote`；这项标志本身不代替授权。核验成功审计、主体身份和授予的 capability 后，移除临时 token 文件。
6. **验证只读，然后逐域开放。** 登录工作台，检查用户、卡片与安全摘要的真实数据闭环。完成下表验收，再按业务域开放已验证动作。启用导出、维护、AI 时，额外检查对应作业、恢复和成本边界。

Cloudflare 账户控制是入口策略恢复的根权限；应用不增加隐藏登录、邮箱自助 bootstrap 或 SQL 控制台。

## 4. Migration 与备份

本次机械提取 schema 不产生数据库结构变化。管理能力的增量结构为：

- [0014_admin_foundation.sql](../../drizzle/0014_admin_foundation.sql)：principals、operations、audit events、jobs。
- [0015_admin_actor_attribution.sql](../../drizzle/0015_admin_actor_attribution.sql)：保留原业务用户外键，另加 Admin attribution。
- [0016_admin_object_tombstones.sql](../../drizzle/0016_admin_object_tombstones.sql)：已脱离元数据的 R2 key 墓碑及防复用 trigger。

先核实目标库已有 migration 和实际结构，仅对缺失的增量按顺序执行；`0015/0016` 不可盲目重复执行。具体远程 migration 命令、目标 ID、预期变化与备份恢复点必须单独审阅授权。禁止将本地合成初始化工具或整个 `schema.sql` 用于生产已有库。

备份不只包含业务表：需要保留 principals、操作与幂等记录、审计、jobs、tombstones，以及匹配的 R2 业务对象、导出/恢复材料和必要私有配置引用。Queue 只负责通知，D1 作业状态才是恢复依据。不要把 Access token 或 Provider secret 写进数据库备份说明。

恢复顺序：

1. Access 切为 deny-all，关闭 writer；同时暂停 Admin Queue consumer、cron 和正在运行的作业步骤，等待已取得 lease 的步骤停止。**仅 Access deny-all 不会停止后台作业；仅关闭 writer 也不会停止到期审计/对象清理。** 若恢复共享业务库，另行评估并协调 Web/Arena 写入，不能在其他 writer 继续写同一库时覆盖生产快照。
2. 优先在隔离资源恢复、核对同一恢复点。按 schema/外键依赖恢复 D1 principals、operations、jobs、业务元数据、审计及 tombstones；恢复所需 R2 对象后，检查 D1 引用与实际对象一致。对象未就绪前不要恢复消费。
3. 从故障后的可信记录核对并重放撤权状态，避免旧快照重新启用已撤销主体。保留原 principal ID、历史 attribution、幂等记录与审计；不要删除后重新 bootstrap。
4. 核对非终结作业的范围、进度、lease、恢复对象与授权。正常可重试步骤由现有 lease/幂等协议恢复；`uncertain` AI dispatch 不自动重放，先核对已发生的 Provider 请求与结果。不要把所有 running/uncertain 作业批量改回 queued。
5. 确认 tombstone trigger 和旧 key 禁复用仍生效。大对象恢复使用新的 `recovered/admin/…` key；不要删除墓碑或恢复到已退休 key 来绕过保护。
6. 先恢复只读入口验证业务与审计，再恢复 consumer/cron，并逐域开放 writer。使用 D1 补偿扫描恢复遗漏通知，不依赖旧 Queue 消息全部仍存在。

恢复生产数据、调整授权、暂停或恢复调度都属于具体环境操作，需确认范围与维护窗口；本 runbook 不表示已经执行演练。

## 5. 保留期限与业务恢复

私有导出自作业创建起默认 **24 小时**有效，下载由 Admin BFF 重新授权，并检查提交者仍为 active 且保留相应 capability。过期后拒绝下载，物理删除由有界补偿过程推进；不能以 R2 URL 绕过授权或把 24 小时解释为逐秒物理删除保证。

成功、失败与拒绝审计按 **180 天**保留策略有界清理。未终结作业以及关联步骤、恢复源作业所需审计保留到终结；审计到期维护独立于业务清理面板。当前清理作业的私有恢复材料也有 180 天有效窗口，进行中的关联恢复会阻止其到期清理。自动维护事实以 [jobs 实现](../../packages/hosted-runtime/src/admin/jobs.ts)和 [Worker 调度](../../apps/admin/src/index.ts)为准。

业务清理先预览明确 ID 范围，再提交带原因、预览版本和幂等键的作业。恢复要求原提交者仍具权限、来源作业有已处理部分且恢复资料尚有效；通过 `jobs.restore` 创建独立恢复作业，不能重新执行清理来“重试恢复”。已有主键或版本冲突不自动覆盖。R2 删除失败应保留 detached 进度和恢复资料，由原作业重试或停止后恢复；不要手工先删元数据、再猜测对象删除状态。

恢复演练至少覆盖：D1 成功审计写入失败回滚、同幂等键重试、CAS 冲突无额外通知、R2 部分删除失败后恢复、提交者撤权阻止下一步骤与下载、过期导出拒绝访问，以及 AI 未知 dispatch 不重放。认证审计、密码重置 token、Better Auth verification、账号关联四类目标仍只有必要安全计数，不能用于清理演练。

## 6. 撤权与唯一管理员恢复

`revoke` 通过受控工具禁用 D1 principal 并写入审计。保留已签发的浏览器 token 重试 session、资源、下载与操作，确认即时拒绝；同时撤销 Access 会话/邮箱允许项，验证入口也被关闭。验证后台作业不会因旧队列消息继续执行新的受限步骤。对已经 dispatch 的 AI 请求，不将撤权视为可以重复发送的依据。

唯一管理员被撤权后，先通过 Cloudflare 账户恢复精确 Access 邮箱策略并取得新真实 token，再使用 principal 工具的 `restore`，显式提供原 principal ID、恢复原因、受控操作会话引用和本次授予的 capability 数组。`restore` 仅允许已禁用的同一验签 human identity，由 D1 CAS 执行 disabled→active 和审计原子更新；它不新增主体、不恢复 active 主体、不覆盖另一身份，也不从历史权限或本地 fixture 隐式推导权限。

```text
node apps/admin/scripts/principals.mjs restore --remote --confirm-remote
```

此命令仍须独立生产授权。restore 专用权限数组由 `ADMIN_RESTORE_CAPABILITIES` 显式提供；其余所需项参见 README。恢复后先验证只读和审计，再逐项开放写能力。身份的 issuer/subject/kind 若已变化，应停止并核实身份迁移，不能用该命令替换旧身份。

## 7. 真实入口验收与回滚

| 场景 | 预期 |
| --- | --- |
| 白名单 OTP 与有效 JWT | 只在匹配 D1 active principal/capability 时返回受授权数据。 |
| 无 token、错误签名、错误 AUD/issuer、过期 token | 拒绝业务 API、页面及静态资源，不显示配置或 token。 |
| 伪造 email/header、service/human 混用 | 无法冒用另一主体。 |
| workers.dev、preview URL、其他自定义域或 Worker 直达路径 | 不存在公开业务入口；绕过 Access 边缘时，Worker 自身仍验签。 |
| 未声明 API 与错误方法 | 拒绝且不回退 SPA，不执行副作用。 |
| Origin、Fetch Metadata、CSRF header 或 JSON 不符 | 写入拒绝，业务记录、通知与成功审计不产生副作用。 |
| 撤权后的旧会话与旧下载链接 | 逐请求拒绝；未开始的后台步骤不继续执行。 |
| deny-all | 精确允许名单用户也无法进入；后台调度需另行暂停。 |
| R2 匿名访问 | 私有产物不能绕过 BFF 授权下载。 |

`/health/live` 仅提供进程存活信息，不访问业务数据；不要将它返回成功当成 Access 或 D1 readiness 验收。

普通回滚优先关闭相应 writer、回退独立 Admin Worker 或 Access deny-all。导出/清理/AI 已产生的副作用按操作和作业状态核对；关闭浏览器不取消服务器任务。需要完全冻结时同时停止 consumer/cron。保留新增表、审计与墓碑，不以破坏性 down migration、删除远程分支或回滚公共 Web/Arena 来替代 Admin 回滚。
