# Hono 服务部署与自动发布指南

本文说明如何在 Linux 服务器部署 `apps/api` 持有的 Hono Node 服务，以及如何通过 GitHub Actions 构建
content-addressed release tuple 并在受保护生产分支发布。当前生产方案使用单文件 Node bundle、Docker、
独立 Redis、Caddy HTTPS 和 Bearer authkey 鉴权。

## 一、部署架构

生产请求链路如下：

```text
客户端
  → HTTPS / Caddy :443
  → 127.0.0.1:8080
  → Hono 容器 :8787
  → Redis（Docker 私有网络）
  → D1 Gateway 或 Cloudflare D1 管理 API
```

相关项目文件：

- `.github/workflows/hono-deploy.yml`：GitHub Actions 构建与发布流程；
- `apps/api/deploy/compose.yml`：随 release 发布的生产 Compose 配置；
- `apps/api/deploy/deploy-bundle.sh`：随 release 发布的校验、预检、事务和回滚脚本；
- `apps/api/deploy/install-bundle.sh`：随机 staging、持锁校验和原子纳管脚本；
- `apps/api/README.md`：Hono 路由、运行时、telemetry 与部署边界；
- `apps/api/env.example`：Hono 环境变量示例。

当前 Compose 默认将 Hono 发布到宿主机 `127.0.0.1:8080`，不会直接开放公网端口。Redis 只加入 Docker
私有网络，也不应开放公网端口。

## 二、服务器要求

推荐环境：

- Ubuntu 22.04 或更新版本；
- Docker Engine 及 Docker Compose Plugin；
- `util-linux` 的 `flock`、GNU `coreutils` 的 `sha256sum`、`realpath`、`mktemp`、`findutils` 的
  `find -printf`、`diffutils` 的 `cmp`，以及 `curl`；
- Caddy 2；
- 至少 1 GB 可用内存；
- 已将业务域名解析到服务器公网 IP；
- 防火墙只对公网开放 SSH、TCP 80 和 TCP 443。

安装 Docker：

```bash
sudo apt update
sudo apt install -y ca-certificates curl
curl -fsSL https://get.docker.com | sudo sh
docker version
docker compose version
```

生产环境使用 root 部署时可以省略示例中的 `sudo`。如果改用普通部署用户，需要保证其可以写入部署
目录并调用 Docker。请注意：加入 `docker` 用户组本质上等同于授予较高的服务器权限。

## 三、初始化部署目录

在服务器创建固定目录：

```bash
sudo install -d -m 755 /opt/mahoshojo-hono/releases
```

新服务器不再预置根 `compose.yml` 或全局 deploy script；Compose 与脚本属于每个 release tuple，由 workflow
一起上传。部署根和 `releases` 必须是无符号链接的 canonical 路径。

服务器最终目录结构如下：

```text
/opt/mahoshojo-hono/
├── .env
├── .env.hono
├── current -> releases/<release-id>
├── deployment-format
├── deploy.lock
└── releases/
    └── <release-id>/
        ├── index.mjs
        ├── compose.yml
        ├── deploy-bundle.sh
        ├── arena-room-release-gate.json
        ├── arena-room-release-gate-schema.mjs
        ├── release.manifest
        └── release.sha256
```

其中 `.env`、`current`、`deployment-format` 和 `deploy.lock` 由发布脚本维护；`.env.hono` 由运维人员
维护，用于保存生产密钥。事务进行中还会存在 `deploy.transaction`，不得手工删除；失败恢复成功后脚本才会
清理它。

### 从旧根布局自动纳管

旧手册创建的服务器会有根 `.env`、`compose.yml`、`deploy-bundle.sh`，且 `.env` 指向仅含
`index.mjs`/`index.mjs.sha256` 的 `releases/<旧 bundle sha256>`。首次新版发布会在激活 candidate 前精确
校验旧 `.env` 单字段、64 位目录 ID、旧 checksum、普通文件、根 Compose config 和旧 runtime 生产配置；
全部通过后复制为带 `legacy-layout` 标记的新 tuple，并写入不可降级的 `deployment-format` marker。candidate
失败时会重新启动该纳管 tuple。

纳管后至少在约定 rollback window 内保留旧 release 的 `index.mjs`/`index.mjs.sha256` 及根
`compose.yml`，因为脚本会复验真实旧 source，拒绝对已漂移文件执行伪回滚。marker 已存在后，`.env` 或
`current` 缺失/不一致会 fail closed，不会把残留旧文件重新登记为 baseline。
新版 workflow 永远只调用 release-local deploy script，不会调用残留的根 `deploy-bundle.sh`。为了保留首次
迁移的可逆证据，自动纳管不会擅自修改旧脚本权限；确认新版成功且度过 rollback window 后，应由运维将其
归档并取消执行位，避免人工误用不具备新锁/journal/marker 的旧协议。

## 四、部署 Redis

当前 `apps/api/deploy/compose.yml` 使用名为 `mahoshojo-redis` 的外部 Docker 网络，并通过网络别名 `redis`
连接 Redis。

创建网络和数据卷：

```bash
docker network create mahoshojo-redis
docker volume create mahoshojo-redis-data
```

生成 Redis 密码：

```bash
openssl rand -base64 36
```

启动 Redis，将 `REDIS_STRONG_PASSWORD` 替换为生成的密码：

```bash
docker run -d \
  --name redis \
  --restart unless-stopped \
  --network mahoshojo-redis \
  -v mahoshojo-redis-data:/data \
  redis:7.4-alpine \
  redis-server --appendonly yes --requirepass 'REDIS_STRONG_PASSWORD'
```

检查 Redis：

```bash
docker exec redis redis-cli -a 'REDIS_STRONG_PASSWORD' ping
```

预期输出为 `PONG`。命令中不要添加 `-p 6379:6379`，否则 Redis 可能被宿主机或公网访问。

如果服务器已经运行 Redis，可以复用现有容器，但必须确保：

- 容器加入 `mahoshojo-redis` 网络；
- 在该网络中的别名为 `redis`；
- Hono 配置的密码与 Redis 一致。

## 五、配置 Hono 环境变量

创建权限为 `600` 的生产配置：

```bash
sudo install -m 600 /dev/null /opt/mahoshojo-hono/.env.hono
sudo nano /opt/mahoshojo-hono/.env.hono
```

最低配置示例：

```dotenv
AI_PROVIDERS_CONFIG=[{"name":"primary","apiKey":"replace_me","baseUrl":"https://api.example.com/v1","model":["model-name"],"type":"openai","weight":1}]
SIGNATURE_SECRET_KEY=replace_with_at_least_32_random_characters

REDIS_PASSWORD=replace_with_the_redis_password

D1_GATEWAY_URL=https://d1-gateway.example.com
D1_GATEWAY_HMAC_SECRET=replace_with_at_least_32_random_characters

ARENA_FINALIZATION_URL=https://web.example.com
ARENA_FINALIZATION_HMAC_SECRET=replace_with_an_independent_32_character_secret
R2_ACCESS_KEY_ID=replace_me
R2_SECRET_ACCESS_KEY=replace_me
R2_BUCKET_NAME=replace_me
R2_ACCOUNT_ID=replace_me
```

`AI_PROVIDERS_CONFIG` 在 Docker env 文件中必须保持单行。生产启动预检会检查至少存在一个有效 provider。

### D1 连接方式

推荐使用 D1 Gateway：

```dotenv
D1_GATEWAY_URL=https://d1-gateway.example.com
D1_GATEWAY_HMAC_SECRET=至少32字符的随机密钥
```

也可以使用固定 Gateway token：

```dotenv
D1_GATEWAY_URL=https://d1-gateway.example.com
D1_GATEWAY_TOKEN=replace_me
```

如果暂时没有 Gateway，可使用 Cloudflare 管理 API 回退：

```dotenv
CLOUDFLARE_ACCOUNT_ID=replace_me
CLOUDFLARE_API_TOKEN=replace_me
D1_DATABASE_ID=replace_me
```

管理 API 路径受到 Cloudflare API 限流约束，只建议用于迁移阶段。生产业务优先使用 D1 Gateway。

生产配置只接受 HTTPS、无凭据/路径/查询/片段的精确 Gateway root origin，并要求 HMAC 或 Bearer transport
credential。Gateway URL 与 allowlist 若由同一 runtime env owner 提供，重复登记不能形成独立信任边界，因此不再要求
`D1_GATEWAY_ALLOWED_ORIGINS`；需要 egress allowlist 时应由独立 deploy/platform policy 提供。只有 local/test fault-injection 明确设置
`HOSTED_DR_LOCAL_FAULT_INJECTION=true` 且 `HOSTED_API_ENVIRONMENT=local|test` 时，才允许 loopback HTTP Gateway；
生产/preview 必须显式声明对应 target，不能把本机 fault-injection authority 带入 production。

### Arena terminal 与 finalization

`ARENA_FINALIZATION_URL` 必须是承载内部 Arena finalization route 的独立 HTTPS origin，不能携带用户名、密码、
路径、查询或片段。`ARENA_FINALIZATION_HMAC_SECRET` 必须至少 32 字符，并且不得复用
`SIGNATURE_SECRET_KEY`、`D1_GATEWAY_HMAC_SECRET` 或 `BETTER_AUTH_SECRET`。Hono 只通过该 HMAC bridge 提交
幂等 terminal finalization；它不是客户端凭据，不得暴露给浏览器。

Arena 最终快照需要 R2 S3 凭据。默认由 `R2_ACCOUNT_ID` 组成 Cloudflare R2 endpoint；使用兼容对象存储时可以
显式设置无凭据、无路径/查询/片段的 HTTPS `R2_ENDPOINT`。bucket 应只授予该服务所需的对象读写权限。部署前
不得通过“临时跳过 R2/finalization”绕过生产预检。

Arena 可恢复生成不需要新增 D1 schema migration。共享 Redis 是 active generation 的 request identity、producer
fencing、lease、snapshot 与 replay 权威；D1 仅复用现有 `battle_report_generations`/`large_objects` 保存终态索引，
完整正文进入 R2。Redis capability 缺失必须阻止 Arena create，不得退回 process-memory 单 producer 假设；
producer token/lease 与完整本地卡片不得写入 D1。Provider terminal 与 bounded finalization 分两步收口时，D1
`finalizationCompleted=false` 只表示真实终态正在对账，不得作为 completed fallback；Next/OpenNext DR 在没有共享
Redis 时同样只能恢复已完成的 D1/R2 terminal，不能创建 active generation。

运维不应通过放大 request/proxy body limit 绕过应用层边界：Arena create 最大 12 MiB、32 位角色；
D1 terminal manifest 最大 96 KiB、32 行 generation combatant，完整正文只进 R2。这些限制是资源/
权威边界，不是可由生产环境变量放宽的调优参数。

客户端配置使用 `https://api.mahoshojo.colanns.me` 作为稳定逻辑入口。该 hostname 必须由独立控制面以
active-passive 选择 Hono primary 与 Next/OpenNext DR；`https://homura.colanns.me` 只用于物理 Hono health/deploy。
本指南不会自动创建或修改 DNS/Load Balancer；正式切流前必须在受控环境证明 generation/stream route 不启用失败后
跨 runtime 自动重放，并完成新请求 failover、mid-flight unknown fail closed 与 cutback 演练。

### Better Auth 与 Bearer authkey

独立 Hono 服务固定使用：

```dotenv
HONO_AUTH_MODE=bearer
```

在该模式下，Hono 不初始化 Better Auth，因此不需要：

```dotenv
BETTER_AUTH_SECRET
BETTER_AUTH_URL
BETTER_AUTH_TRUSTED_ORIGINS
```

这些变量仍可能是 Next.js/Cloudflare 主站的必需配置，不应从主站环境中删除。

需要身份认证的 Hono API 使用用户表中的 `authkey`：

```http
Authorization: Bearer <authkey>
```

只有 Cookie、没有有效 Bearer header 的请求不会被视为已登录。端点是否强制身份认证由对应 handler 是否
调用 `requireAuthUser` 决定；未要求身份的生成端点仍可匿名访问。

### 生产启动预检

Hono 在 `NODE_ENV=production` 时会检查：

- Redis URL 或 Redis host 配置；
- 有效的 AI provider；
- 至少 32 字符的 `SIGNATURE_SECRET_KEY`；
- 不含 localhost 的明确生产 CORS 来源；
- D1 Gateway 凭据，或完整的 Cloudflare 管理 API 三项凭据；
- Arena finalization HTTPS origin 与独立 HMAC secret；
- R2 access key、secret、bucket，以及 account ID 或显式 HTTPS endpoint；
- `hybrid` 模式下额外需要的 Better Auth 配置。

`deploy-bundle.sh` 会在替换线上容器前执行该预检。配置不完整时，本次发布会直接终止，当前服务不会被
替换。

## 六、配置域名、Caddy 和 HTTPS

先将域名的 A 记录指向服务器公网 IP。然后确认 `apps/api/deploy/compose.yml` 和
`apps/api/deploy/deploy-bundle.sh` 中的 `HONO_CORS_ORIGINS` 都与生产域名一致：

```yaml
HONO_CORS_ORIGINS: https://hono.example.com
```

如果需要使用不同宿主机端口，修改：

```yaml
ports:
  - "127.0.0.1:8080:8787"
```

Caddy 配置示例：

```caddy
hono.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

重新加载 Caddy：

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy 会自动申请和续期 HTTPS 证书。防火墙不应开放 8080 和 6379。

如果域名不是当前默认值，还要修改 `.github/workflows/hono-deploy.yml` 传给 release-local deploy script
的公网 origin。域名目前属于版本化部署配置，不存放在 GitHub Secret 中。

## 七、手动构建和首次发布

在项目根目录构建单文件服务：

```bash
pnpm install --frozen-lockfile
pnpm --filter @mahoshojo/api run deploy:prepare
cp apps/api/deploy/compose.yml apps/api/dist/compose.yml
cp apps/api/deploy/deploy-bundle.sh apps/api/dist/deploy-bundle.sh
```

生成校验文件：

```bash
cd apps/api/dist
sha256sum index.mjs compose.yml deploy-bundle.sh > release.manifest
sha256sum release.manifest > release.sha256
release_id="$(awk '{print $1}' release.sha256)"
case "$release_id" in
  ''|*[!0-9a-f]*) echo "artifact release id 非法" >&2; exit 1 ;;
esac
test "${#release_id}" -eq 64
cd ../../..
```

上传并发布：

```bash
upload_dir="$(ssh root@SERVER_IP 'sh -s -- create' \
  < apps/api/deploy/install-bundle.sh)"
case "$upload_dir" in
  /opt/mahoshojo-hono/releases/.upload.*) ;;
  *) echo "远端返回了非法 upload staging" >&2; exit 1 ;;
esac
upload_suffix="${upload_dir##*/.upload.}"
case "$upload_suffix" in
  ''|*[!A-Za-z0-9]*) echo "远端 upload staging 后缀非法" >&2; exit 1 ;;
esac

scp apps/api/dist/index.mjs \
  apps/api/dist/compose.yml \
  apps/api/dist/deploy-bundle.sh \
  apps/api/dist/release.manifest \
  apps/api/dist/release.sha256 \
  root@SERVER_IP:"$upload_dir/"

installed_dir="$(ssh root@SERVER_IP \
  "sh -s -- install '$release_id' '$upload_dir'" \
  < apps/api/deploy/install-bundle.sh)"
test "$installed_dir" = "/opt/mahoshojo-hono/releases/$release_id"

ssh root@SERVER_IP \
  "HONO_HOSTED_API_ENVIRONMENT=production '$installed_dir/deploy-bundle.sh' '$release_id' https://homura.colanns.me"
```

不要直接创建或 `scp` 到最终 release ID 路径。`install-bundle.sh` 先在 canonical `releases` 下创建私有随机
staging；上传完成后持有与部署事务相同的 `flock`，复验精确五文件 tuple，再原子 rename 到最终路径。最终
路径已存在时只允许逐文件完全一致后复用；symlink、损坏或内容不同都会保留 staging 并 fail closed。

发布脚本依次执行：

1. 获取非阻塞主机锁并恢复可能遗留的 pending journal；
2. 校验 candidate 的完整 manifest、release ID、Compose config 与生产 runtime config；
3. 精确识别并纳管旧文档布局，或复验 managed previous tuple 的 checksum/config/runtime；
4. 原子写入 `deploy.transaction`，再更新 `.env` 并重建 Hono 容器；
5. 轮询本机 readiness，并验证公网 `/health/ready` 与 retained shared route wire/CORS contract；
6. contract 全部通过后原子 promotion `current` 并写入 format marker；
7. 任一步失败或收到 HUP/INT/TERM 时复验并恢复 previous tuple；无 previous 时只有 `compose down` 成功后才清 metadata/journal；
8. SIGKILL、主机中断或回滚失败会保留 journal，由下一次运行先恢复并 fail closed。

## 八、配置 GitHub Actions

当前 `.github/workflows/hono-deploy.yml` 会在任意分支 push 后执行 build/verification，但只有
`feature/v0.2.0_Battle_Growth_MahoShojo` 会进入受 `hono-production` Environment 保护的 deploy job：

1. 安装锁定版本的依赖；
2. 运行 Hono、认证和运行时测试；
3. 构建并验证 `apps/api` container 与 `apps/api/dist/index.mjs`；
4. 生成覆盖 bundle、Compose、deploy script、Arena Room gate 与严格 schema validator 的 manifest 和
   content-addressed release ID；
5. 上传到随机 staging，由持锁 installer 复验两层 checksum 后原子纳管七文件 release tuple；
6. 调用该 release 自带的部署脚本；
7. 在同一持久部署事务内验证公网 health 与 retained route contract。

在 GitHub 仓库的 `Settings → Environments` 中创建或进入 `hono-production`。

添加 Environment variables：

```text
VPS_HOST=服务器公网IP或SSH主机名
VPS_USER=root
```

添加 Environment secret：

```text
VPS_SSH_PRIVATE_KEY=用于登录服务器的完整私钥
```

私钥对应的公钥必须出现在目标服务器用户的 `~/.ssh/authorized_keys` 中。建议使用专用部署密钥，不要
复用个人日常 SSH 密钥。

### 固定 SSH host key

workflow 会固定服务器的 ED25519 host key，避免连接被中间人劫持。在可信网络或服务器控制台执行：

```bash
ssh-keyscan -t ed25519 SERVER_IP
```

通过服务器控制台或云厂商控制面板核对指纹后，将 workflow 中现有的：

```text
ssh-ed25519 AAAA...
```

替换为新服务器的 ED25519 公钥。`VPS_HOST` 可以通过 Environment variable 修改，但换服务器时 host key
也必须同步更新，否则 Actions 会按预期拒绝连接。

### 分支与 Environment 保护

所有分支都会运行相同 build gate，但 workflow 的 deploy job 还会精确检查生产 branch ref，其他分支不会
获得 `hono-production` Environment 的 SSH Secret，也不会连接服务器。Environment 仍应设置部署分支规则
或 required reviewers，形成与 workflow 条件相互独立的保护层。若生产分支更名，必须同步修改 workflow
的 push 触发范围策略、deploy job 条件与 Environment 规则，不得只放宽其中一处。

## 九、更换服务器

使用新服务器替换旧服务器时：

1. 在新服务器安装 Docker 和 Caddy；
2. 初始化 `/opt/mahoshojo-hono`；
3. 部署 Redis；
4. 创建新的 `.env.hono`；
5. 配置反向代理和 HTTPS；
6. 若域名变化，同步修改 Compose、发布脚本和 workflow 中的域名；
7. 更新 `hono-production` 的 `VPS_HOST`、`VPS_USER` 和必要时的私钥；
8. 更新 workflow 中固定的 SSH host key；
9. 使用 `workflow_dispatch` 手动触发一次发布；
10. 验证服务后再切换 DNS；
11. 等待 DNS TTL 和业务验证完成后再下线旧服务器。

不要直接复制旧服务器的完整 `/opt` 目录。应显式迁移 `.env.hono` 中需要的配置，并在传输后检查文件
权限为 `600`。

## 十、同时部署多台服务器

当前 workflow 面向一台生产服务器。如果要同时发布多台，推荐以下两种方案之一。

### 方案 A：每台服务器一个 Environment

例如：

```text
hono-production-hk
hono-production-us
```

每个 Environment 独立保存 `VPS_HOST`、`VPS_USER` 和 `VPS_SSH_PRIVATE_KEY`，workflow 为每台服务器建立
独立 deploy job。该方案权限边界清晰，适合生产环境。

### 方案 B：Actions matrix

使用 matrix 并行或串行部署多个目标。每台服务器仍需独立 host key 和 SSH 凭据。生产环境建议设置
`max-parallel: 1` 或采用分批发布，避免一次错误同时替换全部实例。

多实例可以共用 D1，但不应跨公网直接访问某台服务器上的 Redis。应为每台机器部署本地 Redis，或使用
支持 TLS、访问控制和私网连接的集中式 Redis 服务。

## 十一、验证与排障

检查容器：

```bash
docker ps --filter name=mahoshojo-hono
docker logs --tail 100 mahoshojo-hono
docker stats --no-stream mahoshojo-hono
```

检查本机健康状态：

```bash
curl --fail http://127.0.0.1:8080/health/live
curl --fail http://127.0.0.1:8080/health/ready
```

检查公网 HTTPS：

```bash
curl --fail https://hono.example.com/health/ready
```

验证 retained shared route 确实进入 Hono dispatcher，而不只检查会对任意 `/api/*` 返回的 CORS preflight：

```bash
curl -i -X POST \
  -H 'Origin: https://mahoshojo.example.com' \
  -H 'Content-Type: application/json' \
  --data '{}' \
  https://hono.example.com/api/generate-magical-girl
```

预期返回 `400` 和 `{"error":"Name is required"}`，同时包含允许上述 Web origin 的 CORS header。该无效请求在参数校验阶段短路，不会调用 AI、签名或活动记录。不要使用仅有 `OPTIONS` 的探针：全局 CORS middleware 会在 route dispatcher 之前对未挂载的 `/api/*` 也返回 `204`。

当前 `me/battle-reports/[generationId]/regenerate` 已退出 Hono、继续由 Next 承载，因此 Hono 对它应返回 `404`，不能再用它验证 Hono Bearer 鉴权。Bearer/hybrid 兼容由 CI 中的 auth/runtime contract 验证；如将来 retained 清单加入受保护 capability，须同时增加无副作用的公网 `401` 探针。

常见问题：

- `502 Bad Gateway`：Hono 容器未运行、8080 未监听，或 Caddy upstream 配置错误；
- `Redis 未配置/无法连接`：检查 Docker 网络、容器别名和密码；
- `D1 未配置`：检查 Gateway URL/密钥，或 Cloudflare 管理 API 三项凭据；
- `Host key verification failed`：目标服务器已变化，核对后更新 workflow 中固定的 host key；
- Actions 无法读取变量：确认变量位于 workflow 指定的 `hono-production` Environment；
- `401`：受保护端点没有携带有效的 `Authorization: Bearer <authkey>`；
- 新版本自动回滚：查看 Actions 日志和 `docker logs mahoshojo-hono`，确认配置预检及就绪探针结果。
- `deploy.transaction` 保留：上次事务或自动回滚未能完整恢复；不要删除证据，先修复 Docker/runtime/旧 tuple
  校验问题，再重新运行同一 release-local script 触发 next-start recovery；
- `deployment-format` 存在但 `.env/current` 缺失：managed metadata 已损坏，脚本会按预期 fail closed，需先按
  审计记录人工恢复一致的已校验 tuple，不能删除 marker 重新走 legacy adoption。

## 十二、安全注意事项

- `.env.hono` 权限保持为 `600`，不得提交到 Git；
- Redis、Hono 8080 和 D1 Gateway 管理入口不得直接暴露公网；
- GitHub 只保存 SSH 私钥为 Secret，主机和用户名使用 Environment variables；
- 固定并核验 SSH host key，不使用 `StrictHostKeyChecking=no`；
- 定期轮换 SSH、Redis、D1 Gateway、Cloudflare API 和签名密钥；
- 为 GitHub Environment 配置合理的部署分支和审核规则；
- 不在 Actions 日志中输出 `.env.hono`、私钥或用户 authkey；
- release 目录不会自动清理，确认回滚窗口后再定期删除过旧 bundle。
