## 2. 分层门禁与容量整改

- Room Lifecycle：创建房间只要求可信身份、metadata、预算和幂等 fence；0 个角色或当前本地配置尚不可共享都不再阻止建房；
- Room Shareability：Shared Config 允许空 roster，继续检查 allowlist、唯一 key、引用完整性、exact ref、host-local stub/digest、
  canonical 容量和 frame；随机占位符及其 team 引用在投影中省略而不是报共享失败，其他真实共享问题才会逐项提示；若仍无法
  安全投影，房间本身使用 canonical 空草稿创建且不伪称本地配置已同步；
- Collaboration：typed change、authority、revision/precondition、dependsOn/atomic、pending/change/byte limit 分别保留，
  change count 与 byte overflow 不再落入同一个 503；
- Generation Readiness：空角色、mode-specific 最低人数、scenario 主情景、随机占位符、host-local payload、exact ref 和
  Room/local reconciliation 只在生成前检查；
- Runtime Resource：Hosted 的 body、角色、累计参考项、adjudication、prompt、provider 和 output ceiling 继续 fail closed；
- Result/Persistence：host/member 共享同一权威结果呈现与保存图片动作，只有房主在最终权威终态按本地设置写叙事历史正文；
  需要完整私有角色正文的 redo/manual apply/save 不在安全结果 projection 上伪开放。

依赖中立的 capability source 冻结 `maxCombatants=32` 与 `maxReferenceItemsSanity=256`，contracts、core、Web 和 Hosted
通过等值与边界测试防止再次出现多人私有 `10/10/10` 漂移。房间成员 `8`、每成员 pending proposal `8`、proposal/frame
byte ceiling 等有明确协作或 wire 理由的多人边界保持不变。

## 3. 错误 taxonomy 与兼容性

- 浏览器 Web 使用 CORS-safelisted `Accept: application/json; arena-error-taxonomy=2` 协商 Room error taxonomy v2，不向旧 API
  发送会导致预检失败的新自定义 header；新 API 兼容 Accept 与已部署的 custom-header 客户端，并以 `Vary`/`no-store` 响应；
- 未协商或未知版本客户端只收到 `0bb6b883` 可识别的九个基础 code 与兼容 status；全部新增细分 code 都有基础降级映射；
  deprecated host-local combined code 继续可解析，但 v2 不再发出；
- schema preflight 分别报告角色上限、累计引用上限、版本缺失、shareability、proposal change/byte limit；
- host-local missing、invalid、kind、type、digest、version 分别给出安全且可行动的目标提示；
- `ROOM_REFERENCE_DENIED` 在 v2 区分为权限失败，v1 保留原 conflict/forbidden 语义；
- Hosted 明确拒绝只在 allowlist code + 确定性 4xx 时取消 Room reservation；未知 400、408/425/429 和 5xx 保持
  operation unknown，避免因错误泛化允许第二个 producer 静默重跑。

## 4. 单人一致性与补充审查整改

叙事历史设置继续通过 Shared Config 同步，但历史正文只在房主 request scope materialize，不进入 Room checkpoint 或 fanout；
只有房主对最终权威结果执行本地写入，成员读取相同结果但不获得房主私有存储写权限。

来源可信语义与内容可共享性已经切断：随机生成角色默认非原生；host-local 与在线卡重建必须通过服务端 `verifyOrigin` 才能
取得原生标记，校验异常按非原生 fail closed；内置 preset 只有在同源生成目录、kind、versionToken 与正文 digest 均吻合时
才按可信 preset 处理。来源状态不再作为普通多人 Room 的 shareability eligibility gate。

补充审查 `.tmp/GMR-10P整改审查.md` 指出的两项 Important 在当前 Goal 一并闭合：

1. member 新增并由 host 接受的 canonical 角色/情景 preset，现在由 Web reconciliation 从同源静态资源加载，先对 generated
   catalog 的 kind/version 做匹配，再重算正文 digest；版本或正文不一致时在写 BattleStore 前 fail closed；
2. reconciliation 不再无条件写 `adjudicationEvents=[]`，而是复用 source key 过滤，仅移除因角色/主情景/辅助情景被删除或
   替换而失效的来源事件，保留手工事件与仍有效来源。

对应回归覆盖 preset 正常 round-trip、篡改正文拒绝、角色删除与情景替换的 source-aware 清理。原 GMR-10P 日志的
“无开放 finding”是当时审计记录；本日志记录后续审查与实际闭合结果。
