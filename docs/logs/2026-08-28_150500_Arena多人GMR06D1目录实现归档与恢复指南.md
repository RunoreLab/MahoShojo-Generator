## 1. 归档目的

2026-08-28 的 GMR-06 已完成一套质量较高、经过真实 Redis/SQLite fault coverage 与多轮独立审查的 D1 derived room directory 实现。

后续架构复核认为：在当前 v1 里，D1 directory 不能提供独立 Room authority、恢复或 DR 价值，却要求 Redis registration、跨存储补偿、tombstone 和 reconciliation，属于首发阶段不必要的复杂度。因此当前目标态移除该实现。

删除代码不等于丢弃工程成果。本档案记录：

- 精确提交链；
- 完整变更文件范围；
- 哪些文件可未来直接恢复；
- 哪些共享文件不能粗暴回退；
- 已解决的关键竞态；
- 未来如果重新引入 D1，如何最大化复用而不是从零实现。

## 5. 值得保留的设计资产

即使当前删除 D1，这些经过审查的原则仍有复用价值。

### 5.1 D1 永远只是 derived index 时的 authority fence

历史实现明确：

- D1 candidate 必须重新读取 Redis checkpoint；
- 只有 open + exact epoch + exact host 才能返回；
- D1 orphan 不得创建/恢复 Room；
- close/delete 必须按 exact epoch，不能用 stale row 删除新 incarnation。

如果未来 D1 仍只是 derived index，应继续保留这些原则。

### 5.2 create 的 prepare / projection race

历史实现最终采用：

```text
Redis registration pending-create
  -> Room checkpoint SAVE Lua 同时验证 exact pending
  -> checkpoint commit + registration projecting
  -> D1 projection
  -> confirm projected
```

它解决了：

- cleanup-first 后迟到 create 重新提交；
- D1 write 成功但 confirm 失败；
- recovery epoch 前进时 predecessor 丢失。

如果未来重新引入跨存储 projection，这些竞态必须再次被明确解决，不能回到“checkpoint 成功后异步 best-effort upsert D1”的简单双写。

### 5.3 cleanup race

历史 `MARK_CLOSING` 最终把 authority 验证放进 Redis Lua：

- 先前观察 absent -> 线性化时 checkpoint 必须仍 absent；
- terminal -> raw 必须 absent 或与 strict parser 得到的 canonical terminal raw exact-equal；
- malformed/open/new epoch/concurrent replacement -> fail closed。

这是重要的 destructive correctness 资产。

### 5.4 tombstone 与 retry

D1 delete 失败时历史实现保留 `closing` tombstone，直到：

1. exact-epoch delete 成功；
2. 再确认 D1 absent；
3. 才删除 Redis registration。

如果未来再次有跨存储 destructive cleanup，该模式比“删失败就忘掉”安全得多。

### 5.5 orphan reconciliation

历史实现最后同时具备：

- registration reconciler；
- 独立 D1 reconciler，处理 registration 已丢失但 D1 row 残留。

两者均低频、有界、不重叠执行，不能成为维持 Room lifecycle 的 polling loop。

这说明一旦重新引入独立 D1 derived index，真正完整的 reconciliation 成本不能被忽略。

## 8. 未来恢复策略

如果新的 ADR 决定重新引入 D1，推荐按以下顺序。

### 方案 A：参考实现重做（默认推荐）

1. 阅读本档案与原 GMR-06 日志；
2. `git diff a84a1a6..4f9b5295`；
3. 复用算法/测试 fixture；
4. 按当前 Room runtime 重新实现 adapter；
5. 新建当前编号 migration；
6. 做新的 fault matrix。

优点：最少继承历史耦合。

### 方案 B：隔离分支 cherry-pick 12 个提交

仅当当前代码结构仍高度兼容时：

```text
e4bb94d7
d1384e2d
2351528b
d0b2ca6e
629dafae
ed9e89ac
c9468b3c
b15d5b0e
a9e0a75a
f89f51fa
c4cfc39c
4f9b5295
```

在隔离 branch/worktree 中按序 cherry-pick，解决 shared-file conflict，再做完整重审。

不得直接 cherry-pick 到 production branch。

### 方案 C：只恢复专属文件

可以从 `4f9b5295` 读取 D1 adapter/test 作为参考，但：

- `room-directory-service.ts` 先与当前版本 diff；
- migration 必须改用未来的正确编号；
- shared wiring 逐 hunk 重建；
- contract 默认使用当前 retained 版本。

## 9. 重新引入前的强制问题

恢复任何 D1 代码前必须先回答：

1. 新 D1 directory 比 Redis-only 具体多提供什么用户/运维价值？
2. VPS/Redis 丢失时，D1 row 能否支持真实动作，还是仍只能显示一个 orphan？
3. directory 是否跨 runtime / cluster / region？
4. 是否需要 durable room registration，而不仅是 derived listing？
5. public query 规模、过滤需求、P95/P99 和内存数据是否已经证明 Redis 不够？
6. 双写失败时以谁为准？
7. 是否接受恢复 registration/tombstone/reconciler 的维护成本？
8. Cloudflare/D1 成本和 schema migration 是否有清晰 owner？
9. 是否存在更合适的 DO / control-plane / Redis replica 方案？

如果这些问题没有明确答案，历史实现只能作为资料，不应恢复。
