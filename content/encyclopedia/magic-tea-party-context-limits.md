# 魔法茶会：上下文与超长消息

> 更新时间：2026-09-30

本文说明魔法茶会如何处理「单条消息过长」和「历史总量过大」，以及你在界面看到相关提示时应该怎么做。

## 1) 为什么以前会「被卡住」

早期版本对单条消息设了固定 8000 字上限，超过就直接拒绝请求，并且：

- 提示里不告诉你是**哪一条**消息超长；
- 「重新生成」和「删除」都会撞上同一面墙，形成死锁；
- 报错链接指向的是「数据卡问题」百科，与茶会无关。

现在这条硬墙已经移除。**单条超长不会再让请求失败。**

## 2) 现在的规则

### 2.1 单条消息超长 → 自动省略中段

超长消息会被**中间截断**：保留开头和结尾，中间替换为一段显式标记。

```text
（正文开头……）

…（本条消息过长，已省略中段 12480 字）…

（……正文结尾）
```

这么做的原因：

- 只保留开头，模型看不到这段内容「讲到哪里为止」，容易误判；
- 只保留结尾，则完全丢失语境；
- 标记是刻意写给模型看的，让它知道这是人为裁剪，而不是原文本来就这么短。

被截断时，界面顶部会出现一条黄色提示，写明截断了几条、共省略多少字。

### 2.2 单条预算按模型上下文窗口分档

单条消息的字数上限跟随你配置的上下文窗口：

| 上下文窗口 | 单条消息上限 |
| ---: | ---: |
| ≤ 8K | 8,000 字 |
| ≤ 32K | 16,000 字 |
| ≤ 64K | 24,000 字 |
| ≤ 128K | 32,000 字 |
| > 128K | 48,000 字 |

上下文窗口越小，单条上限越低，避免小窗口模型被单条巨量文本顶爆。

### 2.3 历史总量有硬上限

单次请求携带的对话历史合计上限为 **800,000 字**。超过会返回 HTTP `413` 并提示你减少消息条数。

这条上限与「单条」不同：

- 单条超长 → **自动降级**，请求继续；
- 历史总量超限 → **真的拒绝**，因为它直接决定请求体大小。

## 3) 界面上会看到什么

| 你看到的 | 含义 | 该怎么做 |
| --- | --- | --- |
| 黄色提示「有 N 条消息超过单条 … 字预算，已自动省略中段」 | 已自动降级，生成照常进行 | 通常无需处理；若在意被省略的内容，见下一节 |
| 输入框下方 `本条 3200 / 16000 字` | 当前输入长度与单条预算 | 超限会变红并提示会自动省略 |
| 某条消息下方出现「精简长消息」 | 该条超过单条预算 | 点一下即可就地压缩（保留首尾 + 省略中段），不需要删除，也不需要创建分支 |
| 红色错误「对话历史共 … 字，超过单次请求 … 字上限」 | 历史总量超限（HTTP 413） | 见下一节 |

## 4) 遇到历史总量超限怎么办

按代价从低到高：

1. **先生成摘要。** 侧栏「生成摘要」把早期对话压成一段摘要，历史量会显著下降。摘要本身也是走模型的一次调用。
2. **精简超长消息。** 对每条超长消息点「精简长消息」。
3. **删除无关长消息。** 用「删除」移除不再需要的段落。
4. **开新会话 / 分支。** 长线剧情建议按章节分会话，依赖摘要衔接。

## 5) 三个容易混淆的概念

| 机制 | 作用对象 | 触发时机 | 是否额外调用模型 |
| --- | --- | --- | --- |
| 单条截断 | 一条消息 | 该条超过单条预算时 | 否 |
| Token 预算裁剪 | 整段历史 | 历史 token 超出预算时，整条丢弃最旧的消息 | 否 |
| 自动摘要 | 整段历史 | 历史 token 或条数超过阈值时 | **是** |

前两者是确定性的、零额外成本；摘要会额外调用一次模型，但能真正保住早期剧情的连续性。

「Token 预算提示」面板变黄/变红，说明历史正在逼近预算，此时生成摘要比等着被裁剪更划算。

## 6) 已知限制

- 截断是不可逆的信息损失。如果某段关键信息正好在长消息中段，它会真的消失。重要设定建议写进**角色卡 / 情景卡 / 世界书**，而不是只留在一条很长的消息里。
- 自动摘要基于模型改写，属于有损压缩，可能遗漏细节。这是当前实现的取舍：先用确定性的规则保证「不崩」，再由摘要保住「连续性」。
- 内容安全检查只覆盖提示词的前 50000 字。历史极长时，靠后的部分不参与敏感词扫描。
