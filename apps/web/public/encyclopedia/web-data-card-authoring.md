# Web 战报数据卡创作进阶：从“写故事”到“生成互动体验”

> 适用范围：竞技场 Web 战报（实验性）  
> 面向对象：角色卡 / 情景卡创作者  
> 更新日期：2026-09-17

Web 战报让数据卡创作多了一层新的可能性。

过去，创作者主要通过角色设定、情景规则、状态继承和输出格式，告诉 AI：

- 这个世界是什么；
- 角色会怎么行动；
- 每一轮应该发生什么；
- 最后要写出什么样的故事或报告。

现在，如果用户选择 **Web 战报**，AI 最终生成的不再局限于普通 Markdown 文章，而可以是一份完整 HTML 页面：它可以包含自定义布局、动画、SVG、Canvas、JavaScript 交互、Tab、时间线、状态面板、地图、图表、音视频等。

这意味着高级数据卡可以进一步告诉 AI：

> **“不要只告诉玩家发生了什么；请为这次故事即时制作一个怎样的网页体验。”**

本页重点讨论的是**数据卡怎么写**。你不需要修改网站代码，也不需要发明新的数据卡字段；现阶段只要把相关要求、代码参考和外部资源作为角色卡 / 情景卡能够进入 AI 上下文的内容提供即可。

---

## 1. 先换一个思路：Web 不只是“更漂亮的战报”
Web 战报最简单的用法，是把原来的文章做得更漂亮：卡片式角色档案、折叠内容、战斗时间线、技能面板、雷达图或动画结算页。

但更进一步，你可以把整份战报设计成一种**小游戏、模拟器或工具界面**。

| 数据卡方向 | Web 表现可以变成 |
| --- | --- |
| BOSS 战 | Raid HUD、阶段切换、机制解锁、倒计时、战斗日志 |
| 日常养成 | 日历、人物关系、状态面板、事件日志、成长进度 |
| 直播经营 | 仿直播平台、弹幕、在线人数、直播目标、投票与后台面板 |
| 调查推理 | 时间线、人物档案、证物区、线索墙、最终推理 |
| 视觉小说 / Galgame | 背景、立绘、表情差分、对话框、BGM、选项、转场 |
| 研究院评估 | 扫描终端、检测动画、参数面板、异常警告、综合报告 |
| 元对话 / 工具卡 | 终端、数据库、文件树、问答档案、分析 Dashboard |
| 地牢 / 探索 | 地图、房间节点、已探索区域、资源栏、事件记录 |
| 角色卡评价 | 多维评分、证据引用、问题定位、创作建议面板 |

现有很多高级情景卡其实已经在做类似事情：它们通过自然语言把竞技场从“普通战斗故事”改造成长期生活模拟、评估工具、直播经营、元对话、机制 BOSS 等玩法。

Web 只是让这些卡第一次可以真正**长得像它们所模拟的东西**。

---

## 2. 好的 Web 卡先设计“体验”，再设计页面

不要先问“我要几个 `<div>`、按钮放哪里、CSS 用什么”。先问：**玩家打开这份 Web 战报后，究竟在体验什么？**

建议先回答下面几个问题：
1. **体验定位**：这是文章、游戏、工具、终端、模拟器、档案库，还是视觉小说？
2. **核心循环**：玩家主要反复做什么？查看 → 点击 → 推理？对话 → 选择 → 反馈？探索 → 结算 → 下一节点？
3. **视觉隐喻**：玩家“身处”什么界面？直播网站、研究终端、魔法书、手机、战术 HUD、调查板？
4. **常驻信息**：什么东西必须一直看得见？HP、日期、关系、任务、Boss Phase？
5. **逐步揭示**：什么信息应该一开始隐藏，什么时候才允许显示？
6. **交互对象**：玩家可以点击、切换、输入、拖动什么？
7. **操作反馈**：操作以后是展开文本、切换图片、播放动画，还是解锁线索？
8. **结算方式**：页面什么时候算“体验结束”？怎样呈现结果？
9. **移动端**：没有 hover、屏幕很窄时是否仍然可用？
10. **降级**：动画或外部资源失败后，核心故事还能不能看？

这就是 Web 数据卡的“体验设计”。

---

## 3. 最推荐的写法：给 AI 一段“Web 演出指导”

你不需要新增任何特殊字段。对通用情景卡，可以直接在 Markdown 中加入一节；结构化情景卡也可以放在现有能进入故事上下文的说明 / 规则区域。

例如：

```markdown
## Web 战报演出指导

如果当前输出格式支持 Web：

本情景不要呈现为普通长文章，而应制作成“卢恩诺雷研究院能力检测终端”。
### 核心视觉
- 白色研究设施 + 淡蓝色 HUD。
- 检测异常时出现黄色 / 红色警告。
- 风格像严肃科研设备，不要做成花哨手游界面。

### 页面结构
1. 受试者档案
2. 外观扫描
3. 魔装测试
4. 能力参数
5. 异常检测
6. 综合评价

### 交互
- 用 Tab 切换不同测试项目。
- 点击参数可查看详细解释。
- 异常项目可以展开完整分析。
- 最终评级可以使用仪表、条形图或雷达图。
- 可以加入扫描动画和检测进度条。

### 信息原则
- 页面里的数据必须来源于本次实际分析。
- 不要为了填满 UI 编造角色不存在的能力。
- 尚未检测到的信息不得提前展示。
```

这种写法通常比“请生成一个很酷的网页”稳定得多。关键不是教 AI 写前端，而是告诉它：**它正在制作什么产品，以及这个产品中的每个交互是什么意思。**

## 4. 不同模型能力，应该使用不同的创作方式

没有必要规定所有数据卡都使用同一种方法。可以把 Web 卡创作理解成一条连续光谱：

```text
自由度高                                              稳定性高

纯自然语言
   ↓
自然语言 + UI / 代码范例
   ↓
页面骨架 + AI 补充实现
   ↓
完整 Runtime + AI 只填写 GAME_DATA
   ↓
固定 Runtime + 固定 DSL + AI 只生成少量内容
```

### 4.1 方式 A：相信模型，自由生成

适合强模型、页面并不复杂、更看重每一局的创造惊喜、也不需要严格复现同一种 UI 的卡。

你只要写清楚体验要求、视觉方向和交互语义即可。

优点是自由、灵活、每场可能都有不同设计；缺点是能力较弱的模型可能漏功能、写坏 JavaScript，或者看懂玩法但做不出可靠页面。
### 4.2 方式 B：给代码范例，让 AI 模仿

适合中等能力模型、有几个关键效果希望稳定复用、但又不想完全锁死页面结构的卡。

你可以在卡中放一段经过验证的对话框、Tab、立绘切换、SVG 动画、音乐控制或 Canvas 小游戏，然后告诉 AI：

> 下列代码是可运行参考。优先复用其中实现方式；可以根据本次故事调整内容和布局，但不要重新发明已经给出的关键逻辑。

这样模型不必每次重新思考“怎么做表情差分”或“怎么控制 BGM”。

### 4.3 方式 C：提供完整 Runtime，让 AI 只填数据

如果你正在制作一套成熟、反复使用的玩法，这通常是**最稳定**的方法。

思路是：

> **确定性的东西由作者写好；AI 只生成每一局真正变化的内容。**

例如你制作了一个视觉小说 Runtime，它已经支持：

```text
setBackground(asset)
showCharacter(character, expression, position)
hideCharacter(character)
say(speaker, text)
playBgm(asset)
playSfx(asset)
transition(type)
choice(options)
```
那么不必再让 AI 每次重新写视觉小说引擎。可以明确要求：

```text
【重要】下方 HTML/CSS/JavaScript 是已经验证可以运行的 Reference Runtime。
原则上不要修改 Runtime 的内部逻辑。

你只需要根据本次角色与故事生成 GAME_DATA。
除 GAME_DATA、标题和明确标注的可编辑区域外，不要自行重写其它代码。
```

模型真正需要创作的内容就可能缩小成：

```js
const GAME_DATA = {
  scenes: [
    { type: "bg", asset: "bg.school.rooftop" },
    { type: "bgm", asset: "bgm.daily" },
    { type: "show", character: "alice", expression: "neutral", position: "center" },
    { type: "say", speaker: "爱丽丝", text: "……你怎么也来了？" },
    { type: "show", character: "alice", expression: "embarrassed" }
  ]
};
```

这样即使模型不擅长前端，也仍有机会稳定生成完整可玩的页面。

## 5. 给代码时，把“不可修改”和“允许生成”分开
弱模型常见的问题不是完全不会写代码，而是复制长代码时漏掉一段、随手改变量名，或者“优化”掉它认为没用的逻辑。

所以建议明确分区：

```text
====================
【Reference Runtime：原则上不可修改】
====================

...经过测试的 HTML/CSS/JS...

====================
【本次允许创作：GAME_DATA】
====================

请在这里生成场景、角色、对话、选项和资源调用。
```

如果代码很长，还可以再加一句：

> 先复制 Runtime，再只替换指定占位符；不要重构、压缩、删减或重新命名 Runtime 的接口。

### Runtime 越小越好

如果几十行原生 JavaScript 能解决，就没有必要塞进几千行框架代码。Runtime 越长：

- 输入 token 越高；
- 模型越容易漏复制；
- 输出越容易被截断；
- 调试成本越大。

现阶段尤其推荐：**单文件、原生 HTML/CSS/JavaScript、自包含。**

## 6. 视觉小说 / Galgame：非常适合“Runtime + 资源表”

视觉小说是一类特别适合当前 Web 数据卡玩法的方向，因为它的基础操作非常稳定：

- 换背景；
- 显示 / 隐藏角色；
- 更换表情差分；
- 切换角色位置；
- 显示对话；
- 播放 BGM / SFX；
- fade / dissolve 等转场；
- 给玩家选择。

### 6.1 不要只给 AI 一堆 URL，要给资源起“语义名字”

不推荐：

```text
图片1：https://...
图片2：https://...
图片3：https://...
```

更推荐：

```text
【可用资源】

角色 Alice：
- char.alice.neutral = https://...
- char.alice.smile = https://...
- char.alice.angry = https://...
- char.alice.embarrassed = https://...

背景：
- bg.school.classroom.day = https://...
- bg.school.rooftop.sunset = https://...
- bg.cafe.evening = https://...

音乐：
- bgm.daily = https://...
- bgm.tension = https://...
- bgm.ending = https://...

音效：
- sfx.door = https://...
- sfx.message = https://...
```

然后说明调用规则：

```text
Alice 正常说话时默认使用 char.alice.neutral。
出现害羞反应时优先切换 char.alice.embarrassed。
夕阳天台场景必须使用 bg.school.rooftop.sunset。
日常段落使用 bgm.daily；出现明显冲突时可切到 bgm.tension。
```

这会比让模型猜“第三张图是什么”稳定得多。

### 6.2 一个简化的 Galgame 卡结构
可以按下面几块组织：

```text
1. 世界 / 角色 / 本次玩法规则
2. Web 视觉小说演出原则
3. 可用背景 / 立绘 / 差分 / BGM / SFX 资源表
4. 剧本指令约定（scene/show/say/choice/...）
5. Reference Runtime
6. 本轮生成要求
```

这已经很接近一个由 AI 临时填充剧本的微型视觉小说引擎。

## 7. 不只有 Galgame：几种很适合复用 Runtime 的方向

### 7.1 Raid / Boss Runtime

固定实现 Boss HP、Phase、角色状态、战斗日志、机制提示、倒计时和技能演出。

数据卡只需要描述：Boss 机制、Phase 切换条件、哪些信息初始未知、本场故事实际发现了哪些机制，以及每个阶段应该怎样演出。

尤其适合“先观察、再推理机制”的 Boss 卡。

### 7.2 Live / 直播 Runtime

固定实现视频窗、弹幕、在线人数、关注变化、投票、后台统计和直播目标；AI 只需要生成本场直播内容、弹幕、事件和数据变化。

### 7.3 CaseBoard / 调查板 Runtime
固定实现人物、证物、时间线、线索关系、调查笔记和推理总结。

作者要特别明确：**角色尚未发现的事实不能因为网页需要填满内容而提前泄漏。**

### 7.4 Terminal / OS Runtime

适合研究所、异常档案、军事、赛博、太空、元对话等题材。

固定实现文件树、日志、邮件、数据库、命令行和监控面板；AI 只负责生成本场实际存在的文件、记录与回应。

## 8. 可以让角色卡和情景卡分工

一个很有意思的设计方式是：

> **情景卡决定“这一局是什么玩法”；角色卡决定“这个角色如何改变表现”。**

例如调查情景卡规定：

```text
本场 Web 战报使用 CaseBoard：人物、证物、时间线、线索关系和最终推理。
```

某个侦探角色卡再补充：

```text
与本角色有关的 Web 战报应重点显示观察笔记和推理链。
尚未确认的事实显示为“待验证”，不要当作事实直接揭示。
关键推理完成时可以使用线索连线动画表现思维收束。
```
另一个黑客角色可以补充：

```text
本角色发动能力时适合使用终端日志和模块启动动画表现。
```

这样同一个情景遇到不同角色，页面仍然可能有很强的个性差异。

## 9. 小游戏怎么设计最合适？

当前 Web 战报中的交互适合用来**增强体验**，不要把它当作竞技场权威裁定来源。

很适合的例子包括：

- 点击正确符文；
- 简单节奏点击；
- 记忆翻牌；
- 密码锁；
- 拼图；
- 线索配对；
- 简单躲避；
- 骰子 / 抽牌演出；
- 战斗后的“亲自体验一下刚才的机制”。

例如 BOSS 战已经结束，Web 战报可以让读者再玩一个 10 秒的小挑战：“试试看你能不能躲过角色刚才面对的弹幕。”

小游戏成功与否可以解锁额外台词、动画或彩蛋，但不要伪装成可以修改网站已经记录的正式胜负。
### 9.1 当前没有宿主通信时，也能做“人工接力”

如果你希望小游戏结果影响**下一次**生成，可以让页面最后输出一段容易复制的结果：

```text
【交互结果】
破解方式：逆序第三环
耗时：17秒
选择：保留核心
结果码：MIRROR-C3-PRESERVE
```

再提供一个“复制结果”按钮。玩家下一轮把这段文字粘贴进故事引导，AI 就可以继续使用。

这是一种不需要网站新增功能，也能实现：

```text
Web 小游戏 → 玩家操作 → 下一轮故事
```

的办法。

## 10. “模型自由发挥”与“固定 Runtime”不是二选一

同一张卡甚至可以同时兼容两种策略：

```text
【Web 实现策略】

优先满足本节定义的体验、资源调用和交互语义。
如果你能够在一次响应中可靠实现全部要求，可以自行设计页面与代码，
不必拘泥于 Reference Runtime 的具体 DOM 和样式。

如果无法确保背景切换、立绘差分、音乐、转场、选项和移动端适配全部可靠工作，
则必须使用下方 Reference Runtime，只填写 GAME_DATA，不要重新实现基础设施。
```

这种写法的好处是：

- 强模型仍然可以发挥创造力；
- 弱模型有稳定兜底；
- 模型升级后不需要立刻重写整张卡。

不要过度依赖“某某模型一定强 / 一定弱”的硬编码名单。模型版本、上下文长度和实际任务都会影响表现。

## 11. 当前 Web 战报运行环境：创作者必须知道的边界

当前 Web 战报会在独立沙箱 iframe 中运行完整 HTML。创作时请按下面的现实条件设计。

### 11.1 推荐自包含

最可靠的是 inline CSS、inline JavaScript、原生浏览器 API，并使用 `addEventListener` 绑定交互。

第三方 JavaScript、CSS、字体等资源可能受到主站 CSP 或浏览器规则限制，**不要把关键玩法建立在“某个 CDN 一定能加载”上。**

### 11.2 外部图片、音乐和视频也要准备失败降级
你可以向 AI 提供 HTTPS 资源 URL，让页面尝试加载背景、立绘、音乐、音效或视频。

但外部资源可能因为 URL 失效、网络问题、CSP、CORS 或第三方服务限制而加载失败。

建议要求：

> 外部媒体加载失败时，核心剧情、对话、选项和结算必须仍然可用；使用文字、色块或占位符降级，不要让页面整个报废。

### 11.3 不要依赖访问主站

当前 Web 页面不应假设可以访问：

- 宿主 React 组件；
- 宿主 DOM；
- 宿主 cookie / localStorage；
- 房间配置；
- 角色数据库；
- 其它网站内部变量或函数。

如果数据很重要，就让 AI 在生成页面时直接把数据写进当前 HTML。

### 11.4 页面交互不能修改正式胜负

Web 页面里的按钮可以显示“假如她在这里选择另一条路线……”，但这不会改变竞技场已经记录的真实 winner 或角色更新。

把 Web 交互理解成：**这一份战报内部的体验层。**

---

## 12. 手机、可访问性和性能：不要为了炫技把卡做坏
一个好 Web 卡不仅应该“能跑”，还应该“能用”。建议在卡里要求 AI：

```text
- 页面必须适配桌面和手机窄屏。
- 核心操作同时支持鼠标和触摸。
- 不要把 hover 作为唯一的信息获取方式。
- 如果使用拖拽，必须同时提供点击 / 按钮等替代操作。
- 点击目标不要过小。
- 尊重 prefers-reduced-motion；用户偏好减少动画时应降低非必要动画强度。
- 避免无限动画、大量粒子和持续高频 Canvas 重绘。
```

尤其不要为了一个背景特效让整个页面长期满负荷占用 CPU。

## 13. 调试 Web 数据卡：先测试系统，再追求文笔

如果你在开发一张复杂 Web 卡，建议按这个顺序迭代。

### 第一步：只测试玩法骨架

确认页面能打开、按钮能点、Tab 能切、选项能继续，而且资源加载失败不会白屏。

### 第二步：测试 AI 是否正确使用数据

确认它没有凭空编造能力、没有提前泄漏未知信息、正确使用角色名和状态、正确选择资源 ID，并且不会把 Reference Runtime 当成故事内容复述。

### 第三步：测试弱模型
如果你希望卡能被更多用户使用，专门拿能力较弱的模型试几次。

常见改进方式：

1. 减少 Runtime 长度；
2. 减少可用 API 数量；
3. 给一份完整 GAME_DATA 示例；
4. 明确哪些代码不能改；
5. 把“必须”要求集中到一个短清单；
6. 不要同时给两套互相冲突的实现。

### 第四步：最后再加视觉效果

系统稳定之后，再逐步增加动画、粒子、高级转场、小游戏、音频和更复杂的图表。

不要一上来同时调玩法、代码、素材和文笔。

## 15. 最后记住：Web 卡的目标不是“代码越多越高级”

一张优秀的 Web 数据卡应该让技术服务于玩法。

如果你的核心体验只是“阅读一篇很漂亮、可以切换人物视角的故事”，那么几个按钮和一点 CSS 就够了。

如果你的目标是“做一套反复运行、拥有背景 / 立绘 / 音乐 / 选项 / 状态的视觉小说系统”，那么提供经过测试的 Runtime 很合理。

可以用一句话概括：

> **先定义交互语义，再决定实现自由度。越追求一次性的生成惊喜，越可以相信模型自由发挥；越追求成熟、稳定、可重复的游戏系统，越应该把确定性的代码与资源提前准备好，让 AI 只创作真正需要变化的部分。**
Web 战报真正扩大的不是“排版能力”，而是数据卡创作者可以设计的**体验空间**。
